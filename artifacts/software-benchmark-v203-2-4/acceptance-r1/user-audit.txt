# v203.2.3 实验审计与后续研究方案

**审计日期：2026年11月16日**

首先明确本轮研究方向的调整：

**我们不再把上下文管理作为主要算法创新点，而是将其定位为多智能体 Harness 的工程适配能力。研究主线继续集中在组织架构的动态适配，以及基于真实任务反馈的闭环优化。**

上下文管理仍然重要，但它应该服务于组织架构：组织发生变化时，成员需要获得与新职责相匹配的信息；而不是反过来把信息筛选、压缩或角色感知排序本身作为主要研究贡献。

**本轮审计结论**

代码端点补评 (完成)

实验执行完整性 (存在严重故障)

上下文机制接线 (已验证)

上下文方法效果 (无法判断)

组织动态适配 (尚未验证)

闭环优化收益 (尚未验证)

我的总体判断是：

**v203.2.3 没有提供角色感知上下文优于其他方法的证据，但提供了一个更重要的研究启示：当前实验的主要瓶颈已经从观测能力逐渐转向真实协作过程中的状态理解、组织需求识别，以及可靠的干预反馈。**

下一阶段不应继续投入大量实验资源比较 K0/K1/K2，而应该把这轮数据作为工程机制和故障案例保留，重新聚焦组织动态适配。

# 一、实验结果审计

## 1.1 首先确认实验实际完成了什么

本轮原计划：

\\[ 4\text{题}\times3\text{条件}=12\text{个回合} \\]

实际完成：

- K0：4回合。
- K1：3回合。
- K2：4回合。
- 合计11回合。
- Flask K1 未启动。

较早阶段还有9次模型尝试，其中48次物理 API 请求，随后发生SDK索引故障。

因此，本轮不能简单描述为12题实验完成，而应该拆分为：

| 证据层次    | 实际状态          |
| ------- | ------------- |
| 策略实现    | K0/K1/K2均已实现  |
| CPU机制验证 | 已通过相关控制       |
| 真实模型执行  | 11个恢复批次回合     |
| 原始生成实验  | 受测试接口故障污染     |
| 官方代码补评  | 11份全部完成       |
| 合法交付评价  | 不完整，不能据代码补评恢复 |
| 方法效果比较  | 不具备有效比较条件     |

这里最关键的是：**官方补评解决的是代码结果未知问题，而不是实验执行有效性问题。**

这是本轮必须坚持的证据边界。

## 1.2 K0/K1/K2 结果不能证明方法等效

表面结果：

| 条件 | 通过  | 通过率   |
| -- | --- | ----- |
| K0 | 3/4 | 75.0% |
| K1 | 2/3 | 66.7% |
| K2 | 3/4 | 75.0% |

但真正具有完整三组数据的只有三道题：

| 任务            | K0 | K1 | K2 |
| ------------- | -- | -- | -- |
| Astropy-13033 | 失败 | 失败 | 失败 |
| SymPy-17655   | 通过 | 通过 | 通过 |
| Requests-1766 | 通过 | 通过 | 通过 |

三题完全一致。

这并不证明三种方法等效，原因有四个：

1. 共同样本只有三题。
2. 三题全部受到同一种测试反馈故障影响。
3. 每个条件的 Token 使用都接近共同预算上限。
4. Flask K1 缺失，破坏了完整配对设计。

即使三题结果一致，也可能是因为任务难度较低、较高，或者故障环境下不同策略最终都无法获得有效反馈。

本轮不能计算有意义的算法优越性，也不能宣称角色感知上下文没有价值。

## 1.3 预算饱和使成本指标失去区分能力

三组均接近500万预算上限。

这有一个容易忽略的问题：

**当三个条件都被相同的硬预算截断时，最终 Token 总量不再是衡量上下文策略效率的充分指标。**

例如，K2 即使减少了无关信息，也可能将节省出来的预算继续用于代码阅读、测试或额外调用，最终仍然消耗接近500万。

因此，未来如果还需要评价上下文工程，不能只看总 Token。

更适合的指标包括：

- 单位有效任务进展的 Token。
- 关键证据获取成本。
- 重复呈现成本。
- 有效测试反馈成本。
- 预算耗尽时的任务完成状态。

不过，这些只作为组织动态适配的辅助工程指标，不构成当前主研究线。

## 2.4 本轮真正的 Blocking Defect：测试反馈链路失效

(直接影响实验有效性)

这是本轮最严重的问题，我认为其影响比样本量不足更大。

问题链路：

## 测试反馈故障传播

Agent 完成代码修改并封存工作区

**测试预加载缓存键不一致**

`load_base()` 与 `load_base(None)` 被识别为不同缓存键

实际测试重新读取已清理的私有脚本，触发 FileNotFoundError

测试传输通道持续失败，模型无法获得正常测试反馈

模型继续尝试修改和执行，消耗剩余 Token 预算

最终同步失败，任务终态无法按原协议完整闭合

这里有一个非常重要的实验方法论问题：

**测试工具发生故障，不仅会造成测量误差，还会改变 Agent 后续的行为轨迹。**

它不是一个可以在实验结束后简单剔除的评分故障。

测试反馈是 Agent 进行代码修复、决策和协作的重要信息来源。测试持续失败意味着：

- Agent 无法确认自己的修改是否有效。
- 开发者无法根据可靠反馈决定是否继续修改。
- 复核者可能无法获得有效验证依据。
- 任务可能产生无效重复操作。
- 最终 Token 消耗不再代表正常工作条件下的协作成本。

因此，尽管事后补评可以确认8份代码通过，但无法恢复测试反馈正常时模型本来会产生的后续行为。

**本轮11个回合全部属于受损执行条件，不能用于 K0/K1/K2 的任务效率和协作机制效果比较。**

### 故障修复本身是否通过？

报告中的 r5 已通过3项 CPU 控制，并加入永久传输失败后的停止调用机制。

这是正确的修复方向，但目前仍缺少一个关键证据：

> 修复后的缓存规范化、actor 工作区封存、测试执行、结果回传、模型继续决策、最终交付，是否在真实完整调用路径中连续正常工作？

CPU 测试通过不能完全替代真实端到端验证。

因此，我建议将它设为下一次模型实验的硬性前置 Gate，而不是边做组织实验边观察是否还会发生。

## 2.5 实验设计本身还有一个问题：K0/K1/K2 的研究价值有限

我认为即使没有测试故障，当前 K0/K1/K2 也不是我们最应该长期投入的研究方向。

三个条件实际上研究的是：

- 原有历史呈现。
- 通用历史字段选择。
- 根据角色调整历史字段优先级。

它们没有改变：

- 谁负责什么。
- 什么时候调整责任。
- 谁需要与谁协作。
- 如何处理新出现的跨任务依赖。
- 如何判断组织结构不再适合当前工作。
- 如何根据实际任务结果改进下一轮组织策略。

换言之，它们主要改变 Agent 获取历史信息的方式，而没有改变多 Agent 的组织决策机制。

而且，K1/K2 的本地4096 Token选择上限，并不意味着整个模型请求减少了4096 Token；实际节省还取决于原历史字段、模板、其他输入和后续请求。

因此，我的判断是：

**v203.2.3 的主要研究任务已经完成，不建议继续追加 K0/K1/K2 规模，也不建议将 K2 作为后续算法的基础创新模块。**

保留它的工程价值即可。

# 三、重新明确研究主线：从动态组织适配到闭环协同进化

这里我想把研究对象再向前推进一步。

此前 SEWG 的初步设计已经明确：

- 项目图描述工作结构。
- 组织图描述成员责任与协作关系。
- 通信和上下文围绕图状态同步。
- 真实执行反馈用于改进图构建和组织策略。

但目前的设计仍然有些偏向一个规则驱动的组织控制器。

我认为我们真正值得研究的是：

**多智能体组织架构如何根据真实任务结构持续调整，并通过任务结果反馈优化自身的组织决策能力。**

这与简单的动态任务分配、通信拓扑优化、角色自动选择都有区别。

## 3.1 研究对象的重新定义

建议将系统状态分成三个核心对象：

## 动态组织系统的三个核心对象

**1. 工作结构 \\(G_t^p\\)**

当前任务、代码结构、工作依赖、产物、版本和验证关系。

---

**2. 组织结构 \\(G_t^o\\)**

成员、角色、责任区域、任务所有权、协作关系和交付职责。

---

**3. 组织策略 \\(\pi\_\theta\\)**

根据工作结构与组织状态识别需求、生成调整方案、选择行动并根据结果更新策略。

其中，通信和上下文是组织结构变化后的配套机制，不再单独作为主要优化对象。

## 3.2 任务内动态适配

在一个真实任务执行过程中：

\\[ G\_{t+1}^{p}=F_p(G_t^p,e_t) \\]

其中 \\(e_t\\) 是新产生的真实工作事件。

组织策略依据新工作结构与当前组织结构，判断是否需要调整：

\\[ M_t=f\_\theta(G_t^p,G_t^o,S_t) \\]

随后生成合法的候选组织动作：

\\[ \mathcal A_t= \\{ \text{Reassign, Split, Merge, AddHandoff, AddReviewer} \\} \\]

选择动作：

\\[ a_t^\*=\pi\_\theta(G_t^p,G_t^o,S_t) \\]

执行后：

\\[ G\_{t+1}^{o}=T(G_t^o,a_t^\*) \\]

这里必须允许三种结果：

- 需要调整，执行组织变更。
- 需要调整，但当前约束下无法执行，保持原状态并记录原因。
- 当前组织仍然合理，不进行调整。

第三种尤其重要。

**动态组织不是频繁变化的组织，而是能够在必要时变化、在不必要时保持稳定的组织。**

## 3.3 跨任务闭环优化

仅有任务内适配还不足以构成我们希望研究的持续进化。

还需要一个跨任务反馈环：

\\[ \mathcal D_t \rightarrow \text{Diagnosis} \rightarrow \text{Policy Update} \rightarrow \pi\_{\theta\_{t+1}} \\]

其中 \\(\mathcal D_t\\) 是多个任务的真实执行结果和组织调整记录。

这里需要学习的不是某个任务的具体角色分配，而是更一般的组织决策规律，例如：

- 什么类型的工作依赖容易造成责任冲突？
- 什么情况下重新分配责任比增加交接更有效？
- 什么情况下应该合并任务区域？
- 哪些调整容易导致组织振荡？
- 哪些调整虽然提高局部完成速度，却降低最终交付质量？
- 何时不应该调整？

因此，后续研究的核心对象可以正式凝练为：

**面向软件工程工作结构的反馈驱动多智能体动态组织适配与闭环优化。**

这应该成为 SEWG 项目的核心算法方向。

# 四、下一阶段理论设计：组织适配不等于任务分配

我认为需要特别注意与现有工作拉开差异。

简单的图划分、任务分配、动态角色选择都不是充分的创新点。

我们的算法至少需要体现三个不同层次。

### 4.1 组织需求识别

不是看到新的依赖边就调整组织，而是判断当前组织是否无法有效满足新出现的工作需求。

定义：

\\[ M_t=\Phi(G_t^p,G_t^o,S_t) \\]

这里 \\(M_t\\) 不只是一个二元标签，而应当描述：

- 失配类型。
- 涉及的任务区域。
- 涉及的成员。
- 形成原因。
- 影响范围。
- 当前严重程度。
- 证据可信度。
- 是否仍然存在。

特别是，需要将技术问题和组织问题分开。

例如，某次测试失败可能来自代码错误，不应该直接触发组织重组。

### 4.2 组织干预选择

即使确认组织失配，也不代表所有组织动作都合适。

我们可以把候选干预表示为：

\\[ a_t\in\mathcal A_t^{valid} \\]

其中 \\(\mathcal A_t^{valid}\\) 是经过权限、成果所有权、交付规则和版本约束筛选的动作集合。

对于每个候选动作，需要估计：

\\[ V(a_t\mid S_t) = \mathbb E[\Delta U_t\mid a_t,S_t] - \lambda C(a_t) - \mu R(a_t) \\]

分别对应：

- 预期任务收益。
- 组织调整成本。
- 调整引入的风险。

这里的 \\(\Delta U_t\\) 应当以最终合法交付为重要端点，同时保留代码正确率、依赖满足和资源效率等指标。

不应只优化短期局部任务完成率。

### 4.3 组织策略的跨任务更新

这是我认为最值得投入原创研究的部分。

假设任务 \\(i\\) 的实际组织调整轨迹为：

\\[ \tau_i^o= (G\_{i,0}^p,G\_{i,0}^o, a\_{i,0},e\_{i,1},\ldots, U_i) \\]

系统根据多任务的真实反馈，更新组织策略：

\\[ \theta\_{k+1} = \operatorname{Update} \left( \theta_k, \\{\tau_i^o\\}\_{i\in\mathcal B_k} \right) \\]

但这里不能简单采用成功轨迹模仿。

因为：

- 成功任务中的某次组织调整未必是成功原因。
- 失败任务中也可能存在正确的组织决策。
- 没有发生调整的任务同样提供重要信息。
- 不同任务的结构和难度并不相同。

所以需要重点研究组织动作的反事实价值估计与跨任务策略改进。

这也是未来闭环优化的核心科学问题，而不是简单地让模型总结过去的成功经验。

# 五、后续实验方案：重新规划 v203.2.4—v206

我建议不再沿用原先 v203.2.2、v203.2.3、v204 的简单串行关系，而是根据当前真正的研究瓶颈重新规划。

## 5.1 v203.2.4：Harness 故障修复与完整执行链验收

(第一优先级，无需新增模型调用)

本轮已经发现明确的工程故障，因此下一步不应直接重新运行组织实验。

### 实验目标

验证修复后的真实执行链：

\\[ \text{Actor} \rightarrow \text{Artifact Freeze} \rightarrow \text{Test} \rightarrow \text{Feedback} \rightarrow \text{Agent Resume} \rightarrow \text{Review} \rightarrow \text{Delivery} \\]

### 必须通过的控制

| 编号 | 测试内容        | 通过要求               |
| -- | ----------- | ------------------ |
| F1 | 缓存键规范化      | 不同调用形式按真实语义正确处理    |
| F2 | Actor 清理后测试 | 不依赖已删除的私有脚本        |
| F3 | 测试反馈        | 原始结果完整返回正确成员       |
| F4 | 连续测试        | 多轮修改、测试、反馈均正常      |
| F5 | 测试失败        | 正确区分代码失败与测试基础设施失败  |
| F6 | 永久传输故障      | 立即停止后续无效模型调用       |
| F7 | 最终同步        | 提交版本、最终版本及评分对象一致绑定 |
| F8 | 故障恢复        | 不重复执行已经发生的世界动作     |

另外，应当增加两个特别控制：

- 一个代码正确但测试失败的控制。
- 一个代码错误但测试正常执行的控制。

这两个控制可以直接检验评分系统是否混淆代码错误与环境错误。

**准入条件：** 所有核心控制通过，且真实SDK与Harness完整执行链可以连续完成。

这一阶段不需要新的模型 API 消耗，也不需要占用剩余31.26元预算。

## 5.2 v203.3：自然组织需求识别与动态适配机制验证

(核心科学实验准备阶段)

这一阶段我建议把此前的组织失配识别和自然协作机制审计合并，但不把它们混成一个指标。

研究问题分成两个：

**问题 A：当前工作结构产生了什么组织需求？**

**问题 B：现有组织是否能够满足这些需求？**

建立：

\\[ D_t=\text{工作依赖与协调需求} \\]\\[ C_t=\text{当前组织的需求满足能力} \\]\\[ M_t=\text{组织失配状态} \\]

这里可以进一步建立一个需求—能力映射：

\\[ M_t= \Psi(D_t,C_t,S_t) \\]

例如：

| 工作需求    | 现有组织能力         | 判断       |
| ------- | -------------- | -------- |
| 跨模块接口协作 | 双方已有明确交接       | 可能无需调整   |
| 跨模块接口协作 | 双方没有有效交接机制     | 可能存在失配   |
| 独立验证    | 有明确复核成员        | 组织可能合理   |
| 独立验证    | 作者同时承担最终复核     | 可能存在职责冲突 |
| 多任务并行   | 一个成员长期承担全部阻塞任务 | 可能存在负载失衡 |
| 补丁集成    | 存在版本冲突但责任清晰    | 不一定是组织失配 |

注意，这里的表格是判断示例，不是已经确认的标注规则。

### v203.3 的实验内容

1. 从 v203.2.1 和历史材料中提取真实组织事件。
2. 对 v203.2.3 中的事件进行故障边界标注，仅保留测试反馈失效前可独立核验的材料。
3. 建立工作需求与组织能力的时间对齐关系。
4. 进行独立审阅。
5. 分析失配类型及持续时间。
6. 检查失配是否确实需要组织调整，而不是通过正常通信即可解决。

特别强调：v203.2.3 的11个回合不能作为正常反馈环境下的组织策略效果样本，但其故障前的真实消息、交接和责任事件仍可以在原始来源完整的前提下作为过程材料。

### 新增一个重要评价对象：失配持续时间

过去我们更多关注某个时刻是否存在失配。

但我认为还应该研究：

\\[ T\_{\text{mismatch}} = t\_{\text{resolved}}-t\_{\text{emerged}} \\]

即失配从出现到解决经历的时间。

还需要记录：

- 是否被 Agent 主动发现。
- 是否被其他成员发现。
- 是否需要外部提示。
- 是否通过正常交接解决。
- 是否需要调整组织。
- 调整后是否再次出现。

这可以帮助我们判断动态组织究竟是在解决真正的问题，还是只是在增加组织变化。

## 5.3 v204：SEWG 驱动的动态组织适配实验

(主要算法验证)

我建议这是下一阶段真正的核心实验。

### 第一部分：实验条件

不再使用 K0/K1/K2。

保留固定 REVIEW2 作为基础组织，新增两个组织策略。

## v204 三组组织策略

**O0：Fixed Organization**

(基线)

固定001开发、002复核及原有交付责任。允许正常通信和补丁交接，但不进行动态组织调整。

---

**O1：Event-driven Organization**

(强基线)

根据明确的阻塞、责任冲突、任务状态及工作事件调整组织。不使用完整SEWG结构关系进行联合判断。

---

**O2：SEWG-driven Organization**

(核心方法)

根据项目图、组织图及任务状态的关联变化识别失配，选择合法的组织调整动作，并通过实际执行结果验证调整效果。

这三个条件可以回答三个不同的问题：

| 比较    | 研究问题               |
| ----- | ------------------ |
| O1－O0 | 普通事件驱动的组织调整是否有效？   |
| O2－O0 | 完整图驱动组织适配是否优于固定组织？ |
| O2－O1 | 图结构及跨图关系是否提供额外价值？  |

这里 O1 必须是一个足够强的事件驱动基线，不能故意设计得很弱。

### 第二部分：任务选择

本轮实验应当优先选择真正需要跨模块协作的任务，而不是简单扩大 SWE-bench 题目数量。

候选任务至少应覆盖：

- 跨文件修改。
- 跨模块接口变化。
- 多组件依赖。
- 测试与实现职责分离。
- 补丁集成与版本协调。
- 需要独立验证的复杂修改。

但是任务选择不能依据历史最终成绩挑选。

应当先建立候选任务池，依据静态任务属性和预先规定的结构条件筛选，再冻结题单。

还需要注意一个问题：

此前整个 SWE-bench Verified 500题已经有研究历史曝光。

所以如果希望获得更强的独立确认，最好另外选择具有未曝光仓库来源的任务集合。Verified 可以保留用于开发与工程对照，但不能把它包装成全新确认集。

### 第三部分：控制变量

| 维度    | 要求              |
| ----- | --------------- |
| 模型    | 相同模型配置          |
| Agent | 相同成员数量          |
| 初态    | 相同任务、仓库提交和初始工作区 |
| 权限    | 相同工具权限          |
| 预算    | 相同团队预算          |
| 交付    | 相同合法交付规则        |
| 复核    | 相同独立复核要求        |
| 组织动作  | 相同合法动作集合        |
| 评分    | 相同官方评分器         |
| 随机性   | 预先固定运行种子及重复方案   |

同题同seed只能提供配对控制，不能保证模型 API 完全确定性。每个条件必须使用独立的运行身份和工作区。

### 第四部分：主要评价指标

我建议将主要终点设为：

**合法交付成功率。**

代码正确率作为重要共同报告指标。

其次评价：

| 维度   | 指标               |
| ---- | ---------------- |
| 组织适配 | 失配识别准确性、调整合理性    |
| 工作执行 | 依赖满足、阻塞解除        |
| 组织稳定 | 不必要调整、组织震荡       |
| 协作效率 | 交接数量、重复工作、有效补丁采用 |
| 资源效率 | Token、测试成本、墙钟时间  |
| 交付质量 | 官方代码正确率、合法交付率    |

这里我建议不要过早把所有指标加权成一个总分。

先看任务质量是否改善，再判断资源成本是否合理。

例如：

如果 O2 的成功率提升，但 Token 大幅增加，就不能直接称为整体效率改善。

反过来，如果 O2 减少了组织调整和通信，但没有损失任务质量，也可能具有研究价值。

### 第五部分：实验规模

现在还不能合理地冻结任务数量。

建议先完成 v203.3 的自然失配率估计，再根据：

- 仓库间方差。
- 配对任务差异。
- 失配事件数量。
- 多次运行的随机波动。
- 预期最小有意义效应。

进行功效分析。

不能直接把12题扩展成36题就宣称具备统计检验能力。

## 5.4 v205：从单次组织适配走向组织策略闭环优化

这是我认为真正可能形成核心算法贡献的阶段。

v204 主要验证：

给定一个固定的组织策略，能否依据工作图调整组织？

v205 要进一步研究：

**组织策略本身能否通过多个任务的反馈持续改进？**

需要区分两个时间尺度：

## 双时间尺度优化

**内层：任务内动态组织适配**

根据当前任务结构、失配及执行反馈，调整当前组织。

\\[ G_t^p,G_t^o\rightarrow M_t\rightarrow a_t\rightarrow G\_{t+1}^o \\]

**外层：跨任务组织策略优化**

从多个任务的完整执行结果中学习更好的组织调整规则。

\\[ \mathcal D\_{1:k}\rightarrow\pi\_{\theta_k}\rightarrow\pi\_{\theta\_{k+1}} \\]

这里不能直接把内层成功的调整规则复制到外层。

需要判断它是否真正产生了增量。

例如：

某个任务中把责任从001转移到002，最终任务成功。

但如果固定责任不变也能成功，那么这次转移可能没有产生正向价值，甚至可能增加了额外成本。

因此，外层策略优化需要研究：

1. 如何估计组织动作的边际贡献。
2. 如何识别真正有价值的组织调整。
3. 如何利用 NO_CHANGE 轨迹。
4. 如何避免只学习成功案例。
5. 如何防止组织策略过拟合特定仓库。
6. 如何控制调整频率与策略振荡。
7. 如何验证后继组织策略优于原组织策略。

### 我建议的外层更新机制

第一版不必直接引入复杂的强化学习。

可以从以下机制开始：

- 基于真实事件的组织失配诊断。
- 生成有限数量的组织策略候选。
- 在固定开发任务上进行配对验证。
- 根据任务质量与成本选择候选。
- 冻结新的组织策略。
- 在独立确认任务上验证。

但需要强调，简单的候选搜索本身并不是充分的算法创新。

真正值得研究的是：**如何构建可信的组织策略反馈信号，以及如何估计一个组织决策对后继任务效用的贡献。**

这部分需要结合 v204 的真实实验结果进一步推导，暂时不冻结具体优化公式。

# 六、后续实验的严格准入与执行顺序

这里我建议做一个重要调整：不要为了尽快进入算法实验而跳过基础条件。

| 阶段       | 工作            | 模型调用   | 进入下一阶段的条件     |
| -------- | ------------- | ------ | ------------- |
| v203.2.4 | 测试链路修复及完整性验收  | 不需要    | 完整端到端控制通过     |
| v203.3-A | 现有真实轨迹的组织需求分析 | 不需要    | 建立可信的需求与失配证据  |
| v203.3-B | 独立失配识别验证      | 需要单独授权 | 达到预注册识别准入要求   |
| v204     | 三组动态组织配对实验    | 需要单独授权 | 图驱动组织产生可重复增量  |
| v205     | 跨任务组织策略闭环优化   | 需要单独授权 | 策略更新优于固定策略    |
| v206     | 独立确认与多轮持续运行   | 需要单独授权 | 证明收益能够持续且不过拟合 |

注意，v203.3-A 可以先利用 v203.2.1 的12题，以及之前的历史事件开展分析。

v203.2.3 的11个受损回合可以补充故障前的行为证据，但必须与正常反馈条件分开。

不能把它们混入正常运行样本，直接估计组织策略的效果。

## 六个必须保留的研究原则

1. **不以组织变化次数衡量动态组织质量。** 必要时调整，不必要时保持稳定。
2. **不把代码问题直接归因为组织问题。** 技术失败、环境失败、预算限制和组织失配必须区分。
3. **不把依赖直接转化为失配。** 依赖可能通过正常通信得到满足。
4. **不把单次成功调整视为策略贡献。** 需要配对反事实或其他可信对照。
5. **不把任务内适配与跨任务进化混为一谈。** 前者调整当前组织，后者改进未来决策策略。
6. **不把上下文管理升级为主算法贡献。** 它作为组织变化所需的信息交接、局部视图更新和状态恢复机制存在。

# 七、我认为还需要重点研究的一个问题：组织架构的自适应空间

这里进一步提出一个值得深入讨论的方向。

我们之前主要使用 Reassign、Split、Merge、AddHandoff、AddReviewer 作为组织调整动作。

但这实际上预先规定了组织能够如何变化。

未来可能存在一个更大的问题：

**组织架构本身应该具有什么样的可变结构？**

例如：

- 固定角色与动态角色如何共存？
- 一个 Agent 能否同时承担多个责任区域？
- 一个复杂任务是否应该形成临时子团队？
- 任务完成后，临时组织是否应该自动解散？
- 组织关系是否需要根据项目阶段变化？
- 是否应该允许成员自主提出组织重构，而不是只能由外层控制器分配？
- 组织变化后，如何保证历史成果、责任和验证关系不被破坏？

我建议把组织结构表示为：

\\[ G_t^o=(A_t,R_t,O_t,H_t) \\]

其中：

- \\(A_t\\)：Agent 成员集合。
- \\(R_t\\)：角色及能力职责。
- \\(O_t\\)：任务所有权和责任区域。
- \\(H_t\\)：协作、交接及验证关系。

那么，动态组织不只是改变任务分配，而是改变这些对象之间的结构关系。

未来可以进一步研究：

\\[ G\_{t+1}^o = \mathcal T\_\theta(G_t^o,G_t^p,S_t) \\]

这里的 \\(\mathcal T\_\theta\\) 是组织架构变换策略。

这比单独研究任务重分配具有更大的研究空间。

但第一版仍应保留两名成员、原 REVIEW2 交付约束，先验证责任区域、交接与角色变化。不能一开始就引入无限成员扩张和复杂团队拓扑，否则会导致研究变量过多。

# 八、最终审计结论与决策建议

## 当前研究决策

**核心研究方向**

软件工程动态工作图驱动的多智能体组织架构动态适配与闭环优化。

---

**保留的工程能力**

- 被动观测及版本化事件记录。
- 项目图与组织图映射。
- 责任迁移和完整交付控制。
- 上下文局部视图与信息恢复。
- 原有 REVIEW2 Harness。

---

**不再作为主要创新方向**

- 独立的角色感知上下文排序。
- 单纯的消息压缩。
- 单纯的通信拓扑剪枝。
- 简单的任务分配和角色选择。

---

**近期第一优先级**

v203.2.4 测试链路验收，以及利用已有有效轨迹分析组织需求。

## 我对研究价值的判断

我认为当前最值得探索的创新点不是：

「让多个 Agent 根据任务依赖自动分配工作」。

而是：

**让多智能体系统能够从真实工作结构中发现自身组织架构与工作需求之间的不匹配，自主选择合适的组织变换，并利用实际任务结果持续改进组织决策策略。**

其中包含两个需要分别证明的能力：

- 当前组织是否能够根据任务变化及时适配。
- 组织适配策略是否能够从过去的任务反馈中持续改进。

第二个问题尤其重要，因为它决定了我们最终做的是一个动态组织控制器，还是一个能够持续改进自身组织方式的系统。

这也构成了从 v204 到 v205 的核心研究递进。

**当前预算边界：** v203.2.3 累计费用上界约98.74元，130元上限剩余约31.26元。你已经明确要求只补评、不再生成，因此这部分余额不自动授权用于下一轮实验。

**当前执行状态：** 以上为审计和理论方案，不代表新实验已启动，也不授权模型调用。

---

我的建议是，接下来先把研究主线正式收敛为：

**SEWG：面向真实软件工程任务的多智能体动态组织适配与反馈驱动协同进化。**

先解决组织需求识别，再验证动态适配，最后研究跨任务闭环优化。上下文、通信和版本管理全部作为支撑这一主线的 Harness 工程机制。

这条路线比继续做角色感知上下文消融，更接近我们希望形成的核心算法贡献。
