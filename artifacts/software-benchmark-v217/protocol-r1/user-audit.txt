# 三、项目图：只补齐决策需要的关系，不重建整个仓库世界

## 3.1 本轮项目图的最小内容

复用已有世界状态，增加面向决策的项目关系投影。

| 实体或关系 | 来源 | 对组织决策的作用 |
|---|---|---|
| 需求—工作范围 | 原始公开题意、冻结范围锚 | 确认工作覆盖什么目标 |
| 工作—代码区域 | 实际读取、编辑和当前工作上下文 | 识别实现区域重叠与协调风险 |
| 工作—所需产物或接口 | 明确的公开工作说明、实际回执、带来源的成员声明 | 识别交接和等待需求 |
| 工作—固定产物—版本 | 固定、发布及实际采用记录 | 判断伙伴成果是否已经可用 |
| 测试—被检验版本 | 真实测试回执 | 判断证据是否支持当前版本 |
| 复核—完成条件 | 精确候选、复核决定和工作修订 | 判断哪些工作真正闭合 |
| 冲突、过期证据、交付缺项 | 原有世界检查结果 | 区分返修、验证、集成与提交需求 |

每条关系至少保存：

```text
关系身份
来源事件或公开文档
观测时序
对应版本或工作修订
事实状态
可见范围
当前有效性
```

事实状态应区分“工具直接观测”“成员声明／模型推测”“尚未知”。例如：

- 同一文件被两个工作包修改，说明存在协调风险，不能直接证明必须转交。
- 模型写了`depends_on`，不能自动升级为软件语义上的必要依赖。
- 复核接受不能制造一次不存在的测试，也不能把失败公测改成通过。

现有系统已经维护工作修订、版本和证据有效性，不必再另造一套世界状态。[现有工作与证据维护](https://github.com/haoyueliuzhao/ProWorkSim/blob/5d44f8f0531dac096290fafdabb207245ec35ef9/src/proworksim/software_organization_world_v212.py)。

## 3.2 分清工程依赖与组织安排

这是这次必须明确的语义边界。

| 关系 | 含义 | 如何改变 |
|---|---|---|
| 工程依赖 | 某项工作需要一个接口、产物或验证条件 | 根据新证据更新其成立状态 |
| 执行安排 | 当前决定由谁先做、如何交接、谁验证 | 通过合法组织操作调整 |

**删除执行安排中的依赖边，不能把已知工程依赖一起删除。**

组织策略应当适应项目事实，而不是通过修改项目图，把难以处理的事实抹掉。

## 3.3 增量维护与权限

每次真实工具回执后更新投影：

- 编辑产生新版本，旧测试继续绑定原版本；
- 发布产生可交接产物；
- 采用产生实际进入某版本的关系；
- 合并记录新树与真实冲突；
- 返修更新工作修订；
- 测试和复核补入对应证据；
- 正式提交沿用现有终止机制。

失败调用只记录为尝试或拒绝，不能更新成已经发生的责任变化。

生成器使用001有权看到的投影。002未公开的私有代码和历史、参考修复、隐藏测试及后继评分，都不能从评测侧图进入决策输入。现有被动观测器明确区分了评测记录与Agent可见信息，这个边界继续保留。[被动观测器](https://github.com/haoyueliuzhao/ProWorkSim/blob/5d44f8f0531dac096290fafdabb207245ec35ef9/src/proworksim/software_passive_observer_v203_2.py)。

# 四、组织方案：保留组合自由度，取消强制转交

## 4.1 每个状态生成完整方案

每个状态的目标候选集合为：

\[
Z_i=\{\text{KEEP},z_{i,1},z_{i,2}\}.
\]

两个生成方案不再固定对应ASSIST或TRANSFER。它们可以由当前已接线的动作组合而成，例如：

- 调整未产生代码贡献的剩余工作范围；
- 改变某项工作的负责人；
- 调整合法的验证安排；
- 补充必要协作关系；
- 修改有明确依据的执行依赖安排；
- 保持负责人，仅改变验证或交接安排。

**下一轮应删除“每个非KEEP候选必须至少包含一次JOINT_ASSIGN”的机制探针限制。** 当前编译器确实有这个限制，它适合验证责任转移能否发生，但会妨碍策略选择“不转交而解决协作问题”的方案。[当前目标编译器](https://github.com/haoyueliuzhao/ProWorkSim/blob/5d44f8f0531dac096290fafdabb207245ec35ef9/src/proworksim/software_organization_generator_v216_1.py)。

与此同时，继续保持真实能力边界：

- 不开放尚未接线的任务合并、扩员、子团队和调度优先级。
- 不删除已有作者贡献。
- 不强迫接收者接受。
- 不用宿主直接修改owner。
- 不通过换包名制造“不同组织”。

每状态少量候选只是评测预算限制，**不是把整个组织空间重新固定成三种模板**。

## 4.2 候选必须说明项目依据

每个候选增加结构化记录：

```text
源项目图身份
触发事件
引用的项目关系
主张存在的协作需求
涉及的工作包和成员
完整目标配置
合法工具步骤
预期收益与切换成本
```

例如：

> 工作B需要已发布产物P，但接收工作区尚未采用；候选保持B的负责人，先安排明确交接和验证。

或者：

> 两个剩余工作范围涉及同一实现区域；候选集中实现责任，伙伴负责独立验证，以减少交叉修改和后续集成义务。

模型的解释只是待检验的决策依据，不能直接作为收益标签。

## 4.3 不为了凑齐三个候选制造变化

候选生成最多一次正常请求和一次格式／合法性修正，修正不得使用后继成绩。

若只获得一个有效调整方案，就冻结实际有效集合；若只获得KEEP，记录生成覆盖不足或实际适用性限制。**“没有生成出来”不能直接写成“其他方案不可行”。**

所有有效候选都运行，实际主续跑数可能少于42。不得为了填满42条而重命名方案、强制转交或在看见成绩后补候选。

# 五、C/N如何真正进入下一轮

## 5.1 使用同一候选面板比较多个选择器

这是本轮最重要的设计。

| 选择器 | 使用的信息与更新 | 用途 |
|---|---|---|
| \(q_0\) | 冻结候选集合上的初始参照分布 | 初始策略基线 |
| \(q_{L,CN}\) | 原工作台账特征，使用C/N更新 | 项目关系选择器的对照 |
| \(q_{P,C}\) | 项目关系特征，只使用C更新 | 检查N的增量 |
| \(q_{P,CN}\) | 项目关系特征，联合C/N更新 | **主要研究方法** |
| 始终KEEP | 对KEEP赋全部概率 | 固定分工参照 |

其中：

- \(L\)表示以工作包、owner、声明依赖和状态计数为主的台账特征。
- \(P\)表示利用需求、产物、版本、采用和验证关系重新计算的项目关系特征。

两类选择器都保持低维。建议沿用当前七维框架，只对负载、跨成员依赖、验证义务和集成义务四项进行关系化计算，保留协调步骤及两个交互项。**特征定义、归一化、缺失处理在开发结果出现前冻结。**

两类选择器使用相同初始化、优化步数、正则和开发材料，分别拟合自己的参数；不能先拟合项目选择器，再把参数复制给台账选择器。负载和预计集成义务仍是代理量，不能包装成精确工程耗时。

这个对照不增加完整模型续跑，只增加少量本地计算。它检验的是：

> **同一候选支持下，项目关系特征相对原台账特征的选择增量。**

它不单独识别“整个项目图系统相对于完全不用图的系统”的总收益，因为候选生成和执行合同仍然共享。

## 5.2 效用继续以真实交付为核心

沿用：

\[
U_{i,z}
=
Y^{\text{合法且正确交付}}_{i,z}
-
0.1\frac{T_{i,z}}{5{,}000{,}000}.
\]

同时单列最终代码正确率、正式提交是否存在、合法交付正确率和Token。

正常预算耗尽、拒绝候选、部分执行、代码失败和未提交，都保留在被分配方案的结果中。技术故障另列，不能填成普通代码失败。

**不奖励转交次数、图边数量或两人都改代码。** 如果增加组织复杂度没有带来交付收益，C应当反映这一点。

每个开发状态的经验贡献估计为：

\[
\widehat C_i(z)
=
U_{i,z}
-
\sum_{z'\in Z_i}q(z'\mid \xi_i)U_{i,z'}.
\]

欠覆盖探索项为：

\[
N_i(z)
=
\left[\log \frac{r_i(z)}{q(z\mid \xi_i)}\right]_+.
\]

继续使用已经实现的有界正值变换、历史／参照约束和总探索质量混合，不在本轮同时搜索新优化器与超参数。这里的C是**完整组织方案的后继效用比较**，不是某个成员或单个工具动作的名义贡献。

## 5.3 两轮更新必须落到实际选择

执行顺序应冻结为：

1. 窗口1的三个任务完成全部有效候选，计算第一轮反馈，得到各选择器的第一版参数。
2. 窗口2在后继结果产生前，使用更新后的主要选择器计算候选概率并记录其实际选定方案。
3. 选定方案真实运行，其余候选作为评估分支同样运行；不能把不同分支的补丁择优合并。
4. 窗口2结束后完成第二次更新。
5. 冻结所有参数，在八个确认任务上不再更新。

这样既有真实反馈更新，也能证明更新后的策略参与了后续选择。其他候选的探测成本全部进入实验总账。

# 六、为什么确认阶段运行全部候选

v209已经出现过：两个概率配置在所有确认任务上选中同一候选，导致实际比较缺少处理差异。下一轮不再依赖两种策略各抽一次。

对每个确认状态运行全部冻结候选后，计算：

\[
\widehat V_i(q)
=
\sum_{z\in Z_i}q(z\mid\xi_i)U_{i,z}.
\]

建议预注册以下比较：

| 比较 | 解释 |
|---|---|
| **\(q_{P,CN}-q_0\)** | **主要比较：学习后的项目关系选择器相对初始策略** |
| \(q_{P,CN}-q_{L,CN}\) | 项目关系特征相对工作台账特征的增量 |
| \(q_{P,CN}-q_{P,C}\) | 在同一设计下加入N的增量 |
| \(q_{P,CN}-\text{KEEP}\) | 相对保持分工的候选选择价值 |

这一办法能避免抽样碰巧同选的浪费，但仍有边界：

- 每个候选只有一次后继生成，估计仍包含模型运行波动。
- 确认样本是8个任务，不是24个独立任务。
- 分布变化很小，效用差也可能很小，全候选评测不会自动创造检出力。
- 全部候选都被执行，不能据此证明N降低了探索预算。
- KEEP承担共同候选准备成本，因此不能直接等同于部署时完全不生成候选的固定分工系统。

结果应展示逐题效用差、代码与交付差异、仓库分组和留一任务敏感度。八题确认仍是初步验证，不应承诺统计功效或总体稳定提升。

# 七、持续维护项目图，但本轮只评价一个主决策点

这是为保持识别清楚而作出的范围选择。

**项目图在整个任务过程中持续更新；组织策略在本轮每题只进行一次主决策。**

决策点由预先规定的真实工作状态触发，例如已有实际修改和测试，且存在可处理的剩余工作、产物交接或验证义务。触发不能依赖后继评分，也不能要求“调整肯定有利”。

之所以暂不把多次重规划混入这42条：

> 第一次选择会改变后续状态。如果不同策略随后又作不同选择，就不能再用一次候选面板的 \(\sum qU\) 解释整条闭环策略价值。

因此，本轮完成的是：

- 任务内持续维护项目关系；
- 一个真实决策点上的完整组织方案选择；
- 跨任务两轮反馈更新。

允许每题两次以上重规划，应作为后续完整策略分支实验。当前不需要为了这一扩展再推迟C/N开发。

\[

\]

\[

\]

结算，共同前缀和生成只付费一次。项目关系的模型解释、候选生成及必要修正全部计入G，不设置免费分析器。

# 九、准入与停止规则应当调整，避免继续陷入回归循环

## 9.1 新协议建议修改旧学习门槛

旧协议要求先取得两条ADAPT正式交付，才能进入开发。v216仍然没有通过这项旧门，历史结论不变。

但对于下一轮，建议明确修订：

> **进入C/N开发的前提是方案真实可执行、过程可追踪、结果可判定，而不是先观察到调整成功或调整优于保持。**

否则研究会变成不断修订和重跑，直到出现预期正例。合法执行后的失败本身就是贡献度信息。

必要的新增控制只围绕本次变化：

1. 项目关系增量更新与事件重建一致。
2. 版本变化不会让旧证据继续冒充当前证据。
3. 生成器实际收到有权限的关系投影。
4. 候选引用的关系与实际组织步骤能对应。
5. C/N参数确实改变下一窗的选择分布，且确认数据未参与更新。

未改变的缓存、FIFO、评分镜像和提交后终止机制不重复做整套验收。

## 9.2 哪些情况应该停止

| 情况 | 处理 |
|---|---|
| 测试、恢复或计量出现确定性设施故障 | 停止受影响运行及后续准入，修复后另立版本 |
| 候选在图上不同，但没有实际执行差异 | 记为候选／执行覆盖不足，不包装成有效干预 |
| 所有候选的选择特征都相同 | 先检查特征是否实例化了研究对象，不继续消耗大量后继预算 |
| ADAPT正常执行但交付失败 | 保留为有效负结果，允许进入C计算 |
| C/N逐步提高KEEP概率 | 如实报告，不修改奖励强迫产生组织变化 |
| 确认增益集中在一题 | 报告单题敏感性，不称稳定提升 |
| 确认没有改善 | 结束本轮并分析，不自动追加样本直到变好 |

# 十、下一轮报告应围绕四张主表

最终交付材料建议固定为：

1. **项目关系表**：哪些关系被构建、来自什么证据、如何更新、哪些仍未知。
2. **组织决策链表**：关系变化、协作需求、候选、实际选择、成员操作和后继工作。
3. **开发更新表**：两轮C、N、共享参数和选择分布变化。
4. **冻结确认表**：每题全部候选的代码、合法交付、成本，以及各冻结选择器的加权效用。

这样下一轮就能直接回答两个核心问题：**项目图是否真正参与并改善了组织方案选择；在这一条件下，C/N反馈是否让后继选择策略比初始策略更有价值。**
