# v217–v221近期实验审计与下一阶段方案

**审计基准：2026年11月20日**

## 一、总体判断

这几轮实验已经把研究推进到一个新的阶段，但目前出现了一个需要及时纠正的问题：

**项目图、组织结构生成、C/N策略更新和测试验证正在同时发展，但它们之间的独立贡献尚未被充分识别。**

目前已经具备的能力：

1. 真实工作事件能够持续维护工作包、责任、产物、版本及部分依赖关系。
2. 组织候选能够根据当前状态生成，并通过真实成员操作改变责任。
3. C/N已经完成四次策略更新，且使用了真实任务反馈。
4. 项目图定位工具已经通过CPU、真实SDK脚本控制及历史快照检查。
5. 官方评分、版本追溯、共享预算和多任务运行已经形成较完整的执行链。

但尚未证明：

- 项目图比普通工作台账提供更好的组织决策依据；
- 项目图驱动的组织策略比简单候选搜索更好；
- Novelty能够改善组织结构探索，而不是仅仅改变概率分布；
- C/N更新能够在独立任务上提高正确且合法交付率；
- 多轮组织策略已经趋于稳定。

**我的核心判断**

当前最大的瓶颈已经不是组织变换工具不足，而是算法有效性识别不足。

下一轮应该从继续扩大工程功能，转向检验项目图的决策增量与C/N策略的后继效用增量。

我建议保留v217–v221所有历史结果，不重跑、不合并不同协议的成功率，也不通过修改旧参数重新解释既有结果。

下一轮需要适当扩大独立任务数量，但更重要的是改变实验比较方式。

## 2.3 v217：确认面板存在严重的有效支持不足

这是目前最需要重视的统计问题。

v217确认阶段虽然有13个任务，但其中：

- 8题只有KEEP；
- 5题有多候选；
- 只有5题能够真正比较不同组织方案。

这意味着13题并不等于13题都能提供C/N策略选择的比较信息。

更关键的是：

- 五种选择器代码正确率全部为69.23%；
- P_CN合法交付率低于KEEP；
- P_CN没有超过L_CN；
- 删除产生候选差异的关键任务后，效用差接近零。

因此，v217不能支持项目图或C/N已经改善组织策略。

我认为这里有一个比样本数量更本质的问题：

**我们之前把“任务有评分”当成了“任务对策略比较有信息量”。**

下一轮必须区分：

1. 任务是否有有效候选；
2. 候选是否存在真实结构差异；
3. 结构差异是否会改变实际执行；
4. 实际执行是否形成可比较的后继效用。

缺少其中任何一层，都不能简单把任务计入有效策略支持。

---

## 2.4 v218、v219：不能通过修复失败状态来扩大有效样本

v218只有一个任务形成完整面板，v219恢复了五个状态，其中四个进入确认。

修复原始JSON、编译候选和恢复会话是必要的工程工作，但需要区分：

- 原始模型输出是什么；
- 离线修复了什么；
- 哪些状态重新获得了合法候选；
- 哪些状态实际重新生成了模型轨迹。

特别是v219五个状态的离线修复，没有新增模型生成成本，但这也意味着不能将其解释成模型已经学会生成更可靠的候选。

我的建议是：以后将候选生成质量单独作为一个工程和算法指标。

例如：

\\[ R\_{\mathrm{valid}} = \frac{\text{合法且可执行的生成候选数}} {\text{生成候选总数}} \\]

同时记录：

\\[ R\_{\mathrm{diverse}} = \frac{\text{结构上实质不同的合法候选数}} {\text{合法候选总数}}. \\]

不能只统计JSON格式正确率。格式正确但目标结构与KEEP相同，也不是有效的组织探索。

## 2.5 v219确认：成本有改善信号，但不能说策略更优

P_CN相对KEEP平均Token减少约6.1%，但代码正确率和合法交付率没有提高，且Token略高于q0。

这里存在两种可能：

- 项目关系确实帮助选择了成本更低的方案；
- 少量任务上的生成波动使某些分支提前结束，但没有获得更高质量。

而且本轮C/N新增的有效成功交付正例不足，主要更新信号来自成本差异。

因此，下一轮必须把：

\\[ C^{quality},\quad C^{delivery},\quad C^{cost} \\]

分开。

不能让某个方案因为提前结束、消耗较少Token，就被认为已经具有更高的组织价值。

# 三、v221项目图：已经具备定位能力，但尚未证明它能改善组织分工

我认为这是下一轮最应该优先验证的部分。

## 3.1 当前项目图定位究竟解决了什么

v221新增了两项比较重要的能力。

**第一，全局代码定位与符号关系检索。**

不再只依靠Agent自己逐个读取文件，而是能够根据当前授权快照检索：

- 文件；
- Python符号；
- 导入关系；
- 名称引用；
- 对应源码行；
- 来源版本。

这相当于给项目图增加了一个工程结构定位入口。

**第二，定位结果与实际工作证据绑定。**

新增的\`locate_work\`能够返回原始读取参数，固定补丁可以通过合法的patch_id导航，\`record_public_check\`可以把公开需求与实际测试、版本关联。

这意味着定位结果可以进入工作和证据链，而不只是作为一段搜索摘要。

但现在有三个重要限制：

1. 图定位只提供软排序，不证明返回的邻居就是必要依赖。
2. 测试通过与需求覆盖仍然是两个不同判断。
3. 图工具是否改善模型的实际定位效率，还没有与普通全局检索进行同条件比较。

特别是4个历史快照的热更新耗时0.05–0.13秒，只能证明索引热更新很快，不能证明模型定位更快，更不能证明组织分工更好。

## 3.2 项目图必须进入组织策略，而不只是进入代码定位

这是下一轮的重点。

我建议把项目图的使用划分为三个层次：

**P1：工程定位**

(已有原型)

根据需求和当前工作状态定位相关代码、符号及引用关系。

---

**P2：工作关系构建**

(需要加强验证)

把需求、代码区域、工作包、产物、测试及版本连接起来，识别真实协作需求。

---

**P3：组织决策驱动**

(尚未验证)

利用项目关系生成、比较和选择完整组织方案，决定任务拆分、责任分配、协作及验证安排。

目前P1已经有工程证据，P2部分实现，P3尚未得到独立收益证据。

下一轮必须把这三层连起来。

例如，项目图发现：

- 两个工作包涉及同一个公共接口；
- 一个下游工作需要另一个成员尚未发布的产物；
- 某个测试实际覆盖两个工作包；
- 某个成员已经承担大量未完成的上游工作。

这些关系可以帮助组织生成器提出：

- 将两个工作包交由同一成员实现；
- 将接口验证单独交给另一成员；
- 先完成上游产物，再开放下游工作；
- 保持现有责任，但调整验证顺序。

这才是项目图对组织分工的实质驱动。

## 3.3 不能把项目图推测的关系直接当作真实关系

建议给关系增加三个证据等级：

| 等级 | 来源                  | 能否直接驱动组织变换         |
| -- | ------------------- | ------------------ |
| E1 | 真实工具回执、实际版本、测试及产物记录 | 可以                 |
| E2 | 公开源码静态分析、符号及引用候选    | 可以生成候选，但需保留不确定性    |
| E3 | 模型根据上下文提出的关系假设      | 不能直接作为已证实事实，需进一步核验 |

例如：

两个文件之间存在名称引用，不一定意味着它们属于同一个工作包；两个工作包修改同一文件，也不必然意味着应该合并。

因此，组织策略应该根据关系的可信程度、工作状态和剩余资源决定是否调整。

**这也给Contribution提供了更明确的评价对象：不是评价某种图结构是否漂亮，而是评价利用这些关系形成的完整组织方案，是否真正改善了后继工作。**

# 四、v220的B/V实验与v221的L/G实验应该分开

这是我对现有冻结方案最重要的调整建议。

当前有两条不同的研究问题：

- B/V：公开需求验证方式是否提高了需求覆盖和最终正确性？
- L/G：项目图定位是否比普通全局检索更有价值？

它们不应该直接放在同一个2×2实验里。

因为如果同时改变测试验证方式和图定位能力，即使最终成绩改善，也无法判断来源。

## 4.1 B/V：需求覆盖验证

v220原计划：

\\[ 4\text{个状态}\times 2\text{种组织方案}\times 2\text{种验证方式} =16\text{条}. \\]

其中：

- B：原有验证方式；
- V：从公开需求形成可运行检查，并由复核者检查输入、期望和版本。

我认为B/V值得研究，因为v219已经出现过：

> 合法提交完成，但实际测试没有覆盖题面关键组合。

这说明正确的组织结构也可能因为验证不足而产生错误交付。

但B/V不是项目图收益，也不是C/N收益。

建议保留原始协议作为历史设计，不直接启动。下一轮若要做B/V，应重新核对任务、预算和验证范围，确保V不会把模型自建测试的数量当作语义覆盖率。

## 4.2 L/G：项目图定位对照

这一项更直接关系到当前研究主线。

建议：

| 条件 | 内容                           |
| -- | ---------------------------- |
| L  | 全局代码检索、文件读取和原有工作台账           |
| G  | 相同基础工具，增加项目图关系检索、符号定位和版本绑定证据 |

两组保持：

- 同一模型；
- 同一任务初态；
- 相同系统提示主体；
- 相同工具权限；
- 相同输出和输入预算；
- 相同测试和交付合同。

G组不能通过额外提示获得更多修复信息，也不能访问L组不可见的隐藏材料。

两组的差异应当是：**是否利用结构化项目关系来指导定位与组织候选生成。**

需要特别注意：如果G增加了新工具，L也应当拥有同等的工具Schema和调用机会，只是普通检索路径不使用图排序。否则测到的可能是工具数量差异，而不是图信息的增益。

# 五、下一轮实验设计：v222–v224

我建议下一阶段不要同时开展B/V、L/G和C/N三个完整实验。

按照研究依赖关系，应该先验证项目图的信息增量，再验证其组织决策增量，最后检验C/N更新。

## v222：项目图驱动的定位与工作关系实验

(优先级最高)

### 5.1 实验目标

回答：

**在相同工具和预算下，显式项目关系能否帮助Agent更有效地定位代码、识别工作依赖和形成可执行的工作分工？**

### 5.2 实验规模

建议先准备6个真实任务状态，来自6个不同仓库。

每个状态运行L/G两个条件：

# 6

**独立任务状态**

# 12

**主运行上限**

---

| 任务类型    | 数量 |
| ------- | -- |
| 跨模块引用   | 2  |
| 共享接口与依赖 | 2  |
| 多工作包集成  | 1  |
| 验证与版本关系 | 1  |

每个任务先建立共同检查点，然后分别运行L和G。

与此前的初始组织架构实验不同，这里重点观察图信息是否改变实际定位与分工。

### 5.3 主要评价指标

| 指标      | 说明                |
| ------- | ----------------- |
| 定位有效率   | 实际读取的代码是否与当前需求相关  |
| 定位成本    | 达到可执行诊断所用Token及时间 |
| 依赖识别准确性 | 真实依赖与错误依赖分别统计     |
| 工作范围覆盖  | 工作分解是否覆盖原始公开需求    |
| 组织方案质量  | 是否提出合法且有实际执行意义的安排 |
| 责任执行    | 是否真实完成认领、转移和协作    |
| 最终结果    | 代码正确、合法交付、完整成本    |

项目图的独立收益不能只看定位耗时。

例如，G比L快，但产生更多错误依赖，最终交付反而下降，就不能认定项目图有效。

### 5.4 必须增加的图质量评价

建议新增：

\\[ P\_{\mathrm{edge}} = \frac{\text{正确关系数}}{\text{已核验关系数}} \\]\\[ R\_{\mathrm{edge}} = \frac{\text{被发现的必要关系数}}{\text{参考必要关系数}} \\]

但参考关系必须来自公开事实、真实事件和独立审阅，不能用模型自己生成的图作为金标准。

对于尚未确认的关系，单独报告Unknown，不强行归为错误或正确。

另外需要报告：

- 图冷构建时间；
- 热更新时间；
- 索引内存；
- 检索返回量；
- 新工具的输入Token；
- 生成器实际消费的图信息量。

这样才能计算图的真实净收益。

## v223：项目图驱动的组织分工与动态适配

(核心机制验证)

如果v222获得了足够的图质量与定位证据，就进入这一阶段。

### 6.1 实验目标

检验：

**利用项目图中的真实关系生成组织方案，是否比只依赖普通工作台账更能改善后继组织决策？**

### 6.2 实验设计

建议采用6个不同任务状态。

每个状态生成相同候选面板：

\\[ Z_i=\\{z_0,z_1,z_2\\}. \\]

其中：

- \\(z_0\\)：保持当前组织；
- \\(z_1\\)：第一种合法组合组织；
- \\(z_2\\)：第二种实质不同的合法组合组织。

但候选生成和选择需要区分。

| 模块   | L条件         | G条件         |
| ---- | ----------- | ----------- |
| 状态   | 普通工作台账      | 工作台账＋项目关系   |
| 候选生成 | 使用同一冻结语法    | 使用同一冻结语法    |
| 选择依据 | 工作台账特征      | 项目关系特征      |
| 执行   | 相同真实Harness | 相同真实Harness |
| 评价   | 完整后继效用      | 完整后继效用      |

两个条件的候选应当事先冻结，避免G生成更多、更好的候选，导致无法区分生成与选择的贡献。

每个状态三个候选全部运行，共18条主续跑。

同时，在同一候选结果上离线计算：

- 均匀策略；
- L条件选择器；
- G条件选择器。

这样可以减少额外模型运行。

### 6.3 关键评价

\\[ \Delta_G = \frac1n \sum_i \left[ \widehat V_i(q_G)-\widehat V_i(q_L) \right]. \\]

同时报告：

- 组织结构是否真正不同；
- 是否改变实际工作承担；
- 是否减少未满足的工程依赖；
- 是否降低返工和集成冲突；
- 是否提高正确且合法交付；
- 是否增加了图处理和组织协调成本。

需要说明：如果两个条件共享同一候选面板，主要识别的是**图关系对方案选择的增量**，而不是图生成器对候选发现的全部增量。后者需要独立实验。

## v224：C/N组织策略进化验证

(最终核心算法验证)

这是当前研究最重要的一步，但不应该在图关系尚未证明有用之前，直接将所有新增图特征放进C/N选择器。

### 7.1 实验目标

检验：

**利用项目图关系和后继任务效用更新的组织策略，能否比初始策略、普通工作台账策略和不使用Novelty的策略更有价值？**

### 7.2 设计

开发阶段建议12个不同状态，分成两个窗口，每个窗口6个。

每个状态运行三个完整候选：

\\[ Z_i=\\{z_0,z_1,z_2\\}. \\]

因此：

\\[ 12\times3=36\text{条开发运行}. \\]

两个窗口分别完成一次更新：

\\[ q_0\rightarrow q_1\rightarrow q_2. \\]

开发过程中：

- 项目图生成器版本冻结；
- 组织执行器版本冻结；
- 特征定义冻结；
- 评分和资源口径冻结；
- 不使用确认集调整参数。

### 7.3 确认阶段

使用8个新的任务状态。

每个状态仍保留三个候选，使用完整候选结果评价：

\\[ \widehat V_i(q) = \sum\_{z\in Z_i}q(z\mid\xi_i)U\_{i,z}. \\]

主要比较：

| 对照              | 研究目的                      |
| --------------- | ------------------------- |
| \\(q_0\\)       | 初始策略                      |
| \\(q_L\\)       | 工作台账驱动策略                  |
| \\(q\_{P,C}\\)  | 项目关系＋Contribution         |
| \\(q\_{P,CN}\\) | 项目关系＋Contribution＋Novelty |
| KEEP            | 固定组织基线                    |

这一阶段必须冻结参数，不允许根据确认任务成绩更新。

重点检验：

\\[ \Delta\_{CN} = \mathbb E[ V(q\_{P,CN})-V(q_0) ]. \\]

以及：

\\[ \Delta_N = \mathbb E[ V(q\_{P,CN})-V(q\_{P,C}) ]. \\]

如果C/N联合策略没有超过简单的台账选择器，就不能将项目图与C/N的联合设计宣布为有效。

**这一设计的确认规模仍然只是初步研究规模，不足以保证统计功效。** 8个状态需要展示所有逐题结果、仓库聚类及单题删除敏感性，不能以候选数36或24扩大统计分母。

# 八、v222之后，怎样判断是否值得继续进入C/N

我建议冻结三个明确的阶段门。

## Gate A：项目图信息质量

必须证明：

- 图关系具有真实来源；
- 版本变化能够更新或使旧关系失效；
- E1、E2、E3证据等级被正确区分；
- 生成器实际读取了项目关系；
- 不存在越权读取私有内容；
- 图定位不会把静态引用直接升级为确定的工程依赖。

如果Gate A不通过，继续修图，不进入策略收益验证。

## Gate B：项目图决策增量

至少观察：

- G与L实际产生不同的组织方案；
- 不同方案引起真实成员行为变化；
- 项目关系能解释为什么改变了分工；
- 没有通过增加不必要工作包制造组织差异。

四个配对任务不足以确认总体收益，但能够判断机制是否值得扩展。

如果G始终只改变定位结果，却没有改变任何有意义的组织决策，就应该重新考虑项目图在算法中的位置。

## Gate C：C/N策略进化

进入C/N之前必须确保：

1. 有足够的多候选有效任务状态；
2. 每个状态的候选方案有实质结构差异；
3. 所有候选拥有完整且可比较的后继结果；
4. C和N都能在同一个冻结候选空间中计算；
5. 共享选择器能够把更新后的策略应用到后续任务。

注意，Gate B不要求G一定战胜L才能开展C/N研究。即使项目图没有表现出独立收益，也可能作为状态表示的一部分参与C/N；但不能将其称为已验证的增量贡献。

# 九、需要增加一个此前没有充分考虑的分析：项目图与组织图是否相互适配

我认为这是后续可以形成重要研究贡献的地方。

此前我们主要考虑：

\\[ G^P\rightarrow G^O \\]

即项目图驱动组织图。

但实际上组织调整也可能反过来影响项目图的可观测性。

例如：

- 工作拆分后，原本混合在一起的代码区域被分别定位；
- 责任转移后，新的成员发现了此前没有记录的依赖；
- 伙伴产物发布后，原先未知的下游关系变成可确认关系；
- 合并冲突产生新的工程依赖；
- 测试失败使原先认为满足的需求关系重新变成待验证。

因此真正的过程是：

\\[ G_t^P,G_t^O \rightarrow \text{组织变换} \rightarrow \text{实际工作事件} \rightarrow G\_{t+1}^P,G\_{t+1}^O. \\]

这意味着组织架构不只是项目图的被动输出，组织行动本身也会产生新的项目证据。

我建议在v222就开始记录这种双向更新，但暂时不把它作为额外的独立学习器。

未来可以进一步研究：

**组织结构是否能够改变项目图的发现能力，项目图的更新又是否能够反过来促进组织结构调整？**

这比单纯使用代码依赖图指导任务分配更有研究空间。

   6个不同任务状态，比较台账选择与项目关系选择。验证关系驱动的完整组织方案是否有增量。

B/V单独安排，不混入v222的L/G比较。多次任务内重规划则放在v225之后。

## 最后，我认为近期研究最需要明确的科学命题

现在我们已经有了两个可以相互作用的核心对象：

**项目图：描述真实工作世界中的工程事实、依赖、产物与验证关系。**

**组织图：描述成员如何围绕这些工作事实形成角色、责任和协作关系。**

下一步真正需要研究的是：

\\[ \boxed{ \text{项目关系变化} \rightarrow \text{组织结构调整} \rightarrow \text{后继工作效用} \rightarrow \text{组织策略进化} } \\]

其中：

- 项目图决定当前有哪些工作关系值得考虑；
- 组织策略决定如何安排这些工作；
- Contribution评价完整组织方案对后继效用的边际价值；
- Novelty保护尚未充分探索的合法组织结构；
- 跨任务共享选择器学习如何在不同工作状态下作出更好的组织决策。

**我建议下一轮先做v222的L/G配对实验，暂定4题、8条，具备条件时扩展到6题、12条。不要再同时修改C/N公式、验证策略和组织动作空间。**

这样才能真正回答我们现在最关心的问题：项目图究竟只是让Agent更容易找到代码，还是能够让多智能体系统形成更合理的工作分工，并最终改善交付。
