## 一、综合审计：研究已经走到哪里

我认为近期最大的进步不是多完成了几轮模型运行，而是三个研究对象已经开始在真实执行环境中形成联系：

- 项目图：描述当前软件工程工作及其关系。
- 组织图：描述Agent围绕这些工作形成的职责、协作和验证关系。
- 组织策略：根据项目和组织状态决定如何改变组织。

但这三个对象目前还没有形成真正的双向闭环。

这里有一个必须纠正的研究表述：

**v222不是一次完整的项目图驱动组织调整实验，而是一次项目关系辅助组织方案生成实验。**

原因是：

- G组的关系确实进入了生成器请求；
- 只有scikit-learn观察到L/G不同的实际组织调整；
- SymPy的G组提出了不同方案，但转交没有成功；
- Django、Astropy没有形成不同的目标组织调整；
- G组后续没有实际调用新增的\`locate_work\`。

因此，当前不能将v222的结果表述为“项目图驱动的动态组织适配已验证”。

### 2. v222结果本身说明了什么

这不是项目图无效的证据，因为本轮的候选生成和实际调整覆盖太低。

但是，它暴露了两个具体问题：

**第一，项目图增加了生成信息，却没有稳定增加有效组织候选。**

L生成器使用74,934 Token，G使用107,166 Token，增加32,232 Token，约43%。

如果G只是增加了关系信息，却没有增加可执行方案，那么这种信息扩展可能只是提高了生成成本。

**第二，组织调整发生在正确的时机之前或之后。**

SymPy、scikit-learn的决策点尚未满足真实责任转移的前置条件，导致生成方案虽然存在，却无法执行。

这说明我们之前将“组织调整的需求识别”和“组织调整的合法执行时机”混在了一起。

后面必须将它们分开。

# 二、问题一：什么时候需要调整组织架构？

我认为这是下一阶段最值得优先研究的问题。

之前的组织策略基本采用：

> 当前状态 → 生成候选 → 选择方案 → 执行。

但这个过程缺少一个独立判断：

**当前项目状态是否已经出现了值得组织调整的变化？**

我们不应该让组织策略每次观察到状态变化都重新分工，也不应该等到任务预算耗尽才发现原有分工已经不合适。

因此，我建议在项目图和组织图之间增加一个明确的模块：

**组织需求识别器（Organizational Demand Detector）。**

## 2.1 项目图变化不等于组织调整需求

首先需要区分三种事件。

| 事件类型   | 例子                          | 是否一定需要调整 |
| ------ | --------------------------- | -------- |
| 工程事实变化 | 新增代码、测试失败、补丁发布              | 否        |
| 项目关系变化 | 新增依赖、产物采用、版本冲突、验证失效         | 否        |
| 组织适配需求 | 当前owner无法及时处理下游工作、责任冲突、验证缺口 | 可能需要     |

例如，一次测试失败可能产生以下情况：

- 代码本身存在错误，但原负责人能够直接修复；
- 同一个问题涉及两个工作包，需要协调实现；
- 失败源于上游接口变化，需要调整依赖和责任；
- 测试本身没有覆盖题目要求，需要重新安排验证；
- 原有代码已经正确，只需要重新运行最终验收。

这些情况都可能出现\`test_failed\`事件，但适合的组织策略完全不同。

所以不能采用简单规则：

\\[ \text{测试失败次数}\geq k \Rightarrow \text{组织重构} \\]

这会把普通代码困难错误地解释成组织问题。

## 2.2 项目图应该记录事件和状态，而不只是当前图

建议将项目图定义为带版本的动态状态：

\\[ G_t^P=(V_t^P,E_t^P,\mathcal E_t,\mathcal V_t) \\]

其中：

- \\(V_t^P\\)：需求、工作范围、代码、测试、产物等节点；
- \\(E_t^P\\)：工程依赖、实现关系、产物流和验证关系；
- \\(\mathcal E_t\\)：原始事件及其时间顺序；
- \\(\mathcal V_t\\)：节点、边及其证据版本。

项目图的维护不应简单地把最新状态覆盖旧状态，而应当保留变化：

\\[ G\_{t+1}^P = \operatorname{Update}(G_t^P,e\_{t+1}). \\]

例如：

**一个典型的项目图变化过程**

1. **初始状态**

   工作A和工作B分别关联两个代码区域，存在潜在接口关系。
2. **发生实际测试失败**

   测试T关联版本V1，失败证据被记录。
3. **产生新修改**

   A发布V2，原测试证据不再直接证明V2正确。
4. **发现跨工作依赖**

   B需要A发布的接口或产物，项目图新增有来源的依赖关系。
5. **组织需求出现**

   B当前owner无法在现有安排下获得所需产物，形成协作或责任调整候选。

这里的关键是：组织需求来自多个项目事实及当前组织安排之间的关系，而不是某个孤立事件。

## 2.3 组织需求识别器应该观察什么？

建议第一版采用五类组织需求。

| 组织需求 | 项目图中的证据                 | 可能的组织调整       |
| ---- | ----------------------- | ------------- |
| 责任缺口 | 有未完成工作但缺少有效owner        | 重新分配责任        |
| 依赖瓶颈 | 下游等待跨成员产物或接口            | 调整责任、交接或执行顺序  |
| 负载失衡 | 一名成员承担大量未完成工作，另一成员有可用机会 | 重新分配剩余工作      |
| 验证缺口 | 候选版本、测试和验证责任无法闭合        | 调整验证关系        |
| 集成冲突 | 多个贡献进入同一工作树后出现冲突        | 集中集成责任或调整工作边界 |

还需要一个反向判断：

**当前组织已经足够好，不需要调整。**

因此，组织需求识别器的输出不应只有一个布尔值，而应当包含：

\\[ d_t=(\text{类型},\text{证据},\text{紧迫性},\text{适用工作范围},\text{不确定性}). \\]

它负责发现“是否值得重新考虑组织”，不直接决定采用什么组织方案。

### 2.4 专门安排一个Agent负责组织图构建与优化

我支持你的这个想法，但建议明确其职责边界。

不建议把它设计成一个普通第三开发成员，而应当是一个**组织架构Agent（Organization Agent）**，作为控制平面的专门角色。

## 三种职责分离

**Project Agent / Graph Agent**

构建和维护项目图，整理需求、代码、产物、测试、版本和工程关系。

**Organization Agent**

识别组织需求，生成目标组织图，评估可行性，提出责任、协作和验证调整方案。

**Worker Agents**

根据新组织安排接受任务、执行修改、发布成果、测试、交接和复核。

组织Agent不直接修改成员工作区，不强制改变owner，也不替成员完成工作或验收。

这里不必立刻增加第三个长期工作的模型实例。

首版可以让组织Agent：

- 使用单独的逻辑会话；
- 在决策事件发生时按需调用；
- 读取经过权限过滤的项目图和组织图；
- 产生候选及依据；
- 不持有代码写权限；
- 不参与最终代码评分。

它的输入和输出Token全部计入团队预算。

我更倾向于这种架构，而不是让001既负责修复代码，又负责维护项目图、识别组织需求、生成新组织和评价自己的决策。职责分离可以减少策略生成和执行者自身局部目标之间的混淆。

**但要注意：组织Agent是一个可检验的架构假设，不是已经证明必须增加的第三Agent。** 下一轮应先比较专门组织Agent与普通成员自行提出组织方案的效果。

# 三、问题二：一个项目图应该对应什么样的组织图？

这是整个研究最核心的理论问题。

我认为不能简单地定义：

\\[ G^P\rightarrow G^O \\]

因为一个项目图通常存在多种合理组织方式。

同一个软件项目可以：

- 按模块分工；
- 按功能分工；
- 按阶段分工；
- 按依赖关系分工；
- 按成员能力分工；
- 按验证与实现分工。

所以我们不应该研究一个项目图对应一个唯一组织图，而应该研究：

\\[ \boxed{ G^P\longrightarrow \mathcal G^O(G^P) } \\]

即：**一个项目图对应一个可行组织架构集合，组织策略负责根据当前状态从中选择合适的组织图。**

## 3.1 建立项目图与组织图的形式化映射

先定义项目图：

\\[ G^P=(V^P,E^P,X^P) \\]

其中：

| 项目图节点       | 具体对象        |
| ----------- | ----------- |
| Requirement | 原始需求及验收条件   |
| Work Scope  | 可验证的工作范围    |
| Code Entity | 文件、类、函数、接口  |
| Artifact    | 补丁、文件、构建产物  |
| Test        | 测试用例及其执行结果  |
| Version     | 代码树、补丁及测试版本 |

项目图的边表示：

- 需求由哪些代码实体实现；
- 哪些工作依赖某项接口；
- 哪些产物被下游采用；
- 哪些测试检查哪些行为；
- 哪个版本满足或未满足哪些验收要求。

组织图定义为：

\\[ G^O=(V^A,V^R,V^W,E^O) \\]

其中：

- \\(V^A\\)：Agent成员；
- \\(V^R\\)：职责与角色；
- \\(V^W\\)：工作包；
- \\(E^O\\)：所有权、协作、交接、验证等关系。

两个图之间还需要一个映射：

\\[ M:G^P\leftrightarrow G^O. \\]

这个映射是非常关键的。

例如：

**项目图中的工作关系**

Requirement A

Code Module X

Artifact P

Test T

映射 M

**组织图中的工作安排**

**Agent 001**

实现X

**Agent 002**

独立验证T

项目图中的产物和测试依赖，决定组织图需要安排什么交接与验证关系。

映射不是简单的节点对应，而是一个约束关系。

例如：

- 一个代码模块可以由一个工作包负责；
- 一个工作包可以覆盖多个代码实体；
- 多个工作包可能依赖同一个公共接口；
- 一个测试可能覆盖多个工作包；
- 一个产物可能被多个下游工作包使用。

因此，映射应该允许多对多关系，但工作包仍保留唯一问责owner。

## 3.2 组织图的生成应当满足项目约束

可以将组织图生成定义为：

\\[ \mathcal G^O\_{\mathrm{feasible}}(G^P,S) = \left\\{ G^O: \mathcal C(G^P,G^O,S)=1 \right\\}. \\]

其中 \\(\mathcal C\\) 包含：

1. 工作范围完整覆盖；
2. 所有未完成工作有唯一owner；
3. 必要工程依赖得到处理；
4. 已有代码作者身份保留；
5. 复核与验证职责合法；
6. 成员权限符合要求；
7. 资源和预算可行；
8. 最终交付路径完整。

这意味着组织Agent不能为了让组织图更漂亮而忽略项目图中的工程事实。

同时，也不应当要求所有项目依赖都变成组织依赖。

例如，一个模块内部存在十条函数调用关系，并不意味着需要十次跨Agent交接。

**项目图描述工程关系，组织图只需要处理那些对工作分解、责任、协作和验证具有实际意义的关系。**

## 3.3 如何评价一个项目图对应的组织图是否合理？

不能直接评价组织图与项目图的图结构相似度。

项目图和组织图本来就是两种不同的对象。

建议从五个方面评价映射质量：

| 评价维度  | 具体问题                  |
| ----- | --------------------- |
| 工作覆盖  | 项目图中的必要工作是否都被组织图承接？   |
| 依赖处理  | 跨工作包依赖是否有明确的责任和交接安排？  |
| 责任合理性 | 工作分配是否考虑成员负载及已有贡献？    |
| 验证闭合  | 项目图中的测试与版本要求是否有合法验证者？ |
| 资源可行性 | 当前组织能否在剩余预算内完成剩余工作？   |

可以定义一个组织映射可行性函数：

\\[ F(G^P,G^O,S)\in\\{0,1\\}. \\]

但是需要特别区分：

\\[ F=1 \\]

只表示组织安排满足约束，不表示它一定有效。

最终效果仍然由后继效用决定。

# 四、项目图与组织图的映射经验，如何跨任务使用？

这是当前共享选择器最需要升级的部分。

此前我们使用：

\\[ q\_\theta(z\mid\xi) \\]

其中 \\(\xi\\) 是工作状态，\\(z\\) 是完整组织方案。

这个方向正确，但目前特征主要是工作包数量、owner负载、依赖和验证义务等。

这些特征还不够表达：

**为什么某一种项目结构需要某一种组织结构。**

我建议将跨任务共享知识从简单的组织方案特征，升级为**项目结构—组织结构映射特征**。

## 4.1 学习的是映射规律，而不是具体图

例如：

任务A：

- 两个模块共享公共接口；
- 一个成员掌握接口上下文；
- 另一个成员负责下游测试。

任务B：

- 两个不同文件之间存在共享状态；
- 一个成员负责上游实现；
- 另一个成员需要下游验证。

这两个任务的代码和工作包完全不同，但组织问题可能相似。

因此，不能迁移：

```
任务A：工作包A1 -> Agent001
```

而应该迁移：

```
项目关系特征：
上游接口依赖 + 跨成员工作 + 下游验证需求

组织关系：
上游负责人明确发布接口产物
下游负责人获得采用与测试权限
必要时安排交叉验证
```

也就是说，跨任务迁移的基本单位是：

\\[ \text{项目关系模式} \longleftrightarrow \text{组织关系模式}. \\]

## 4.2 建立项目—组织映射的联合特征

建议将映射特征分成四组。

| 特征组     | 示例                           |
| ------- | ---------------------------- |
| 项目结构    | 依赖密度、共享接口、关键路径、代码区域重叠        |
| 当前组织    | owner负载、工作包分布、验证缺口、协作关系      |
| 项目—组织匹配 | 依赖是否跨owner、测试是否跨工作包、产物是否有接收方 |
| 资源状态    | 剩余Token、待完成工作、等待时间、集成负担      |

尤其是第三组，应该成为研究重点。

例如：

\\[ f\_{\mathrm{cross}}= \frac{ \text{跨owner工程依赖数} }{ \text{有效工程依赖总数} } \\]\\[ f\_{\mathrm{verification}}= \text{尚无合法验证安排的必要测试关系比例} \\]\\[ f\_{\mathrm{artifact}}= \text{已发布但尚未被必要下游采用的产物比例}. \\]

这些只是候选特征，需要根据真实关系质量进行筛选，不能直接把所有图边都算进去。

## 4.3 用跨任务共享选择器学习映射规律

建议将选择器升级为：

\\[ \boxed{ q\_\theta(z\mid G^P,G^O,S) } \\]

首版继续采用可解释的低维模型：

\\[ q\_\theta(z\mid\xi) = \frac{ r(z\mid\xi)\exp(\theta^\top f(\xi,z)) }{ \sum\_{z'}r(z'\mid\xi)\exp(\theta^\top f(\xi,z')) }. \\]

这里的 \\(f\\) 不再只是组织方案本身的属性，而是：

\\[ f(\xi,z)= f(G^P,G^O,M,z,S). \\]

即评价：

> 当前项目结构与当前组织安排之间存在什么不匹配，候选方案如何改变这种关系？

这样，跨任务共享的是映射决策规律，而不是图ID、工作包ID或具体成员角色。

# 五、问题三：C/N应该如何与项目图和组织图联系起来？

这里需要对之前的C/N设计做一个重要修订。

此前Contribution和Novelty主要作用于完整组织方案：

\\[ C(\xi,z),\qquad N(\xi,z). \\]

但现在我们有了项目图、组织图和二者映射，应该明确它们分别发挥什么作用。

我建议分成三个层次。

## 5.1 Contribution：评价组织映射改变的后继效用

先定义当前映射：

\\[ M_t=M(G_t^P,G_t^O). \\]

一个组织方案 \\(z\\) 对应新的组织图：

\\[ G\_{t+1}^O=T(G_t^O,z). \\]

因此得到新的映射：

\\[ M\_{t+1} = M(G\_{t+1}^P,G\_{t+1}^O). \\]

注意，项目图也可能因为组织行动而变化。

例如：

- 新成员定位出此前未知的代码依赖；
- 新补丁发布后增加产物关系；
- 合并冲突产生新的工程关系；
- 测试失败使原有验证状态失效。

因此，贡献度应该评价：

\\[ m(\xi,z) = \mathbb E[ U\mid G\_{t+1}^P, G\_{t+1}^O, M\_{t+1} ]. \\]

再定义：

\\[ \boxed{ C_t(\xi,z) = m(\xi,z) - \sum\_{z'}q_t(z'\mid\xi)m(\xi,z') } \\]

这意味着Contribution不再只衡量某种责任调整有没有效果，而是衡量：

**通过某种组织变换，项目中的工作关系与组织中的责任关系是否变得更适配，并最终产生了更好的后继任务结果。**

但不能直接将映射完整度作为主要奖励。

否则算法可能学会把图变得非常完整，却没有提高软件交付能力。

映射完整度、依赖处理和责任覆盖应该作为中间机制指标；最终Contribution仍然由完整后继效用决定。

## 5.2 Novelty：探索不同的项目—组织映射

这一点也需要改变。

之前的Novelty主要衡量组织候选是否欠覆盖：

\\[ N(z)= \left[ \log\frac{r(z)}{q(z)} \right]\_+. \\]

但如果我们要研究跨任务映射，就应该关注：

**当前选择器是否过度依赖少数项目结构—组织结构匹配模式？**

例如：

- 项目依赖密集时，总是选择集中式组织；
- 工作包增加时，总是选择并行分工；
- 有测试缺口时，总是选择固定复核者。

如果这些模式过早固化，系统可能无法探索其他有效映射。

因此可以定义：

\\[ N_t^{map}(\xi,z) = \left[ \log \frac{ r\_{map}(\phi(G^P,G^O,z)\mid\xi) }{ q\_{\theta,t}(\phi(G^P,G^O,z)\mid\xi) } \right]\_+. \\]

这里的 \\(\phi\\) 是规范化后的项目—组织映射特征。

我建议保留两个Novelty分量：

\\[ N_t= \gamma N_t^{map} + (1-\gamma)N_t^{struct}. \\]

其中：

- \\(N^{map}\\)：映射模式的欠覆盖；
- \\(N^{struct}\\)：实际组织结构的欠覆盖。

不过这两者都只能作用于冻结生成器提供的合法支持，不应把不存在的组织方案视为已探索。

**Novelty不是鼓励频繁改变组织图，而是避免策略过早丢失有潜在价值的项目—组织匹配方式。**

## 5.3 最终联合目标

我建议下一版理论基线使用：

\\[ \widetilde C_t = \epsilon+(1-2\epsilon) \sigma(C_t/T_C) \\]\\[ \widetilde N_t = \epsilon+(1-2\epsilon) (1-e^{-N_t/T_N}) \\]\\[ \boxed{ \Phi_t(\xi,z) = \widetilde C_t(\xi,z)^\alpha \widetilde N_t(\xi,z)^\beta } \\]

更新：

\\[ \boxed{ q\_{t+1}(z\mid\xi) \propto q_t(z\mid\xi)^\rho r(z\mid\xi)^{1-\rho} \Phi_t(\xi,z)^\eta } \\]

再进行总探索质量混合与共享参数拟合。

这里有一个重要原则：

**项目图负责提供决策状态与映射依据，C负责评价完整组织变换的后继价值，N负责维持映射与组织结构的探索支持。**

不要让C/N直接优化项目图的完整程度，也不要让项目图的边数量直接成为奖励。

# 六、如何真正做到任务内与任务间持续优化？

这里需要区分两个时间尺度。

## 6.1 任务内：项目图持续更新，组织策略按事件重新决策

任务内的循环：

\\[ G_t^P,G_t^O \rightarrow \text{事件} \rightarrow \text{项目图更新} \rightarrow \text{组织需求识别} \rightarrow \text{候选生成} \rightarrow \text{选择与执行}. \\]

我建议不采用固定每5次行动重新组织的方式，而是采用事件触发机制。

首版定义六类触发事件：

| 事件      | 项目图变化           | 组织策略需要考虑的问题        |
| ------- | --------------- | ------------------ |
| 连续测试失败  | 测试与当前版本的失败关系增加  | 是否需要重新诊断、改变责任或验证安排 |
| 新依赖确认   | 工作包之间增加有来源的必要依赖 | 是否需要调整先后顺序、交接或责任   |
| 产物发布/采用 | 产物关系和可执行条件改变    | 是否需要开放下游工作         |
| 集成冲突    | 多个修改区域或产物出现冲突   | 是否集中集成责任或重新划分工作    |
| 证据失效    | 测试或复核绑定的版本过期    | 是否重新分配验证工作         |
| 资源不平衡   | 成员剩余工作和预算发生明显变化 | 是否调整未完成工作的承担者      |

其中，连续测试失败需要进一步研究。

例如：

\\[ F_t= \sum\_{j=t-k+1}^{t} \mathbf1[\text{test}\_j\text{ failed}] \\]

它可以作为触发特征，但不能直接决定调整。

必须进一步检查失败类型：

- 目标测试失败；
- 原通过测试回归；
- 测试环境问题；
- 测试选择或参数错误；
- 证据与版本不匹配。

只有结合当前项目关系，才能判断是否需要调整组织。

### 任务内的调整频率

建议首版使用：

- 一个初始组织决策；
- 最多两个中途重新决策机会；
- 只有项目状态出现新的实质变化才触发；
- 每次决策都允许KEEP；
- 同一原因未出现新证据时不重复触发。

这比每轮强制重构更合理。

特别是提交前，如果项目图已经表明只剩最终验证和交付，就应该优先完成当前工作，而不是再创建新的协作关系。

## 6.2 任务间：更新的是映射策略，而不是直接继承组织图

任务结束后，需要保存：

\\[ \mathcal D_t= (G^P,G^O,M,z,\text{Events},U). \\]

但不能将整个项目图或组织图直接复制到下一任务。

需要从中提取跨任务可复用的经验：

- 哪种项目依赖模式容易产生跨成员瓶颈；
- 哪种责任分配能够处理类似依赖；
- 哪种协作结构降低了返工；
- 哪种验证关系容易产生证据缺口；
- 哪种调整在高预算压力下不值得采用。

然后利用C/N更新共享选择器。

这里需要特别注意：

**一个任务中的组织调整可能成功，但它的映射规律未必能迁移到另一个任务。**

因此任务间需要保留独立确认，而不是每完成一道题就立即把结果视为普遍规律。

# 七、建议增加一个专门的组织Agent，但先检验其增量价值

你提出的专门Agent值得进入下一轮设计。我建议将它正式命名为：

**Organizational Architect（组织架构Agent，OA）。**

它不是普通项目经理，也不是直接代替其他Agent分配工作的人。

## 7.1 OA的具体职责

| 职责     | 输入                 | 输出            |
| ------ | ------------------ | ------------- |
| 项目图维护  | 真实工作事件、代码和测试证据     | 更新后的项目图       |
| 组织图维护  | 当前owner、角色、协作和验证关系 | 当前组织图         |
| 组织需求识别 | 项目图与组织图之间的不匹配      | 是否需要调整及其依据    |
| 候选生成   | 当前项目状态和剩余资源        | 多种完整组织方案      |
| 合法性检查  | 目标组织图及现有权限         | 可执行或拒绝理由      |
| 反馈分析   | 完整后继结果             | 供跨任务学习使用的反馈记录 |

但是，OA不应该自己判断自己的方案有效。

方案是否产生价值，仍然通过真实后继任务效用评价。

## 7.2 OA的权限边界

建议明确：

- 可以读取经过权限过滤的项目图；
- 可以读取当前组织状态；
- 可以提出完整组织变换；
- 可以请求成员确认；
- 不可以直接修改成员工作区；
- 不可以绕过owner的接受动作；
- 不可以替成员发布补丁；
- 不可以接受自己的组织方案作为执行事实；
- 不可以读取隐藏测试或官方评分结果；
- 不可以修改自己的Contribution定义和评价参数。

这样可以形成职责分离。

## 7.3 如何检验专门OA是否有价值？

不能直接把OA加入系统，然后比较最终成功率。

因为同时增加了一个Agent、一个提示和一套工作流程，无法知道哪个因素发挥了作用。

建议后续比较：

| 条件 | 组织决策来源          |
| -- | --------------- |
| W0 | 工作Agent自行提出组织方案 |
| W1 | 专门OA根据项目图提出组织方案 |

两组保持同一项目图数据、工具权限、候选生成语法和预算。

这样可以回答：

**将组织决策从工作Agent中分离出来，是否能够产生更合理的项目—组织映射？**

我倾向于最终采用OA，但不建议在第一轮就让OA承担所有图构建、策略更新和执行监督。首版先验证它的候选生成与组织需求识别价值，C/N仍然由独立的共享选择器负责。

| ---------------- | ------------------------ |
| Static           | 只使用决策点的当前状态快照            |
| Event-driven     | 从原始工作事件增量维护项目图           |
| Agent-maintained | 由专门Graph Agent解释、确认和维护关系 |

三者使用相同历史事件，比较：

- 是否发现了新的必要关系；
- 是否正确识别过期关系；
- 是否识别出新的协作需求；
- 是否过早触发组织调整；
- 是否遗漏了真实工作状态变化。

这可以先用v216、v217、v222的历史事件完成离线重放。

但历史回放只能验证状态重建与需求识别，不能证明Agent在线使用图后会表现更好。

另外，我不建议让Graph Agent和Organization Agent完全合并。

二者虽然可以共用底层模型，但职责不同：

- Graph Agent负责事实与关系维护；
- Organization Agent负责组织结构推理和方案生成。

否则同一个Agent可能先提出某种组织方案，再把项目关系解释成支持自己方案的证据，产生循环论证。

# 十一、下一轮需要特别关注的失败模式

为了避免v217–v222的问题重复出现，我建议提前冻结以下检查。

| 问题             | 下一轮处理                   |
| -------------- | ----------------------- |
| 生成器不能产生有效候选    | 统计生成覆盖率，不将格式失败算成策略失败    |
| 项目图包含未经确认的依赖   | 事实、静态候选、模型假设分级          |
| 调整时机不合法        | 区分需求触发和动作可执行条件          |
| 组织Agent生成过多方案  | 候选数量受限，计入所有生成成本         |
| 责任变化只停留在图上     | 必须核验真实offer、accept及后续工作 |
| 多次测试失败被误判为组织问题 | 分析失败原因，不采用简单次数阈值        |

| 成本下降但代码错误      | 正确性、交付、成本分开报告           |
| 证据绑定旧版本        | 版本变化后重新验证               |
| 确认结果进入策略更新     | 冻结确认集，禁止反向拟合            |

尤其是最后一点，下一轮必须严格区分开发与确认。

# 十二、最终研究方向：从项目图驱动分工到组织协同进化

结合近期讨论，我建议把理论研究对象正式凝练成三个层次。

## 项目—组织协同进化框架

**第一层：Project World**

\\[ G_t^P \\]

维护真实工作事实、代码、依赖、产物、测试和版本。

**第二层：Organizational World**

\\[ G_t^O,\quad M_t \\]

根据项目关系建立组织架构、角色职责、工作分配和协作映射。

**第三层：Organizational Evolution**

\\[ q\_\theta(G^O\mid G^P,G^O,S) \\]

由Contribution评价完整组织方案的后继价值，由Novelty保护组织映射的探索空间。

**真实工作反馈**

新的代码、产物、测试和协作事件反过来更新项目图与组织图。

完整过程是：

\\[ \boxed{ \begin{aligned} &\text{项目事实与关系构建}\\\ &\downarrow\\\ &\text{组织需求识别}\\\ &\downarrow\\\ &\text{项目图—组织图映射}\\\ &\downarrow\\\ &\text{C/N驱动的组织方案选择}\\\ &\downarrow\\\ &\text{真实成员执行}\\\ &\downarrow\\\ &\text{后继效用反馈}\\\ &\downarrow\\\ &\text{跨任务策略更新} \end{aligned} } \\]

这里有一个我认为值得保留的研究假设：

**组织行动不只是项目图的结果，它也会改变项目图的可观测性；项目图更新又会影响下一次组织决策。**

例如，责任重新分配可能使新的成员发现之前没有被记录的代码依赖，形成新的项目关系；这个新关系又可能要求下一次调整组织结构。

因此，这不是简单的单向：

\\[ G^P\rightarrow G^O. \\]

而是一个双向演化系统：

\\[ (G_t^P,G_t^O) \rightarrow \text{组织行动} \rightarrow (G\_{t+1}^P,G\_{t+1}^O). \\]

**这部分有可能成为区别于普通依赖图驱动任务分配的重要研究内容。** 但需要通过后续实验确认它是否真的带来额外收益。

## 最后，我对三个问题的回答

**1. 什么时候需要调整组织架构？**

当项目图中出现新的工程事实或关系变化，并且这些变化与当前组织安排之间产生了可识别的不匹配时，组织需求识别器才触发重新决策。测试失败只是信号之一，不是自动重构指令。

**2. 一个项目图应该对应怎样的组织图，经验如何跨任务使用？**

一个项目图对应一组可行组织图，而不是唯一答案。通过映射 \\(M(G^P,G^O)\\) 将工程关系与责任、协作、验证关系连接起来。跨任务迁移的是项目结构—组织结构的匹配规律，不是具体任务ID或组织图模板。

**3. 两种策略如何持续优化？**

任务内由项目事件驱动图更新和组织重新决策；任务间由真实后继效用更新共享选择器。Contribution评价完整组织方案的边际价值，Novelty保护尚未充分探索的合法映射模式。专门的Graph Agent维护事实，Organization Agent负责组织推理，工作Agent执行。

**我认为这才是目前应该集中投入的研究方向：不是简单地让Agent更自由地分工，而是让系统逐渐理解项目的工程结构，发现当前组织与工程需求之间的不匹配，并通过真实工作结果持续进化这种映射能力。**
