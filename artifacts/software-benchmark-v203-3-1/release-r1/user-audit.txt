# v203.2.4／v203.3-A 审计与后续实验方案

**总体判断：本轮应当按声明范围通过，但下一步需要调整研究验证方式。**

工程上，已经有证据支持“修复后的测试—反馈—复核—交付链在受限真实组件控制中可以连续工作”，不应继续把它当成尚未打通的链路。研究上，已经更清楚地看到：**现有固定组织能够处理不少协作需求，但我们仍未验证，改变组织是否能在相同资源下做得更好。**

因此，下一步不应继续循环于“扩大历史审阅，等待出现明确失配阳性”，也不应直接启动大规模 O0／O1／O2 比较。更合适的过渡实验是：

> **先确认组织调整确实改变了执行安排，再从同一工作状态出发，对“保持组织”和“一次合法组织调整”进行小规模配对续跑，检验组织调整是否存在可测量的净收益。**

本次除了阅读报告，我还只读核对了综合验收汇总、反馈核验、错误帧控制、历史分析汇总、分析脚本、需求校验器和研究修订协议。以下属于**报告与已发布工件、关键源码之间的一致性审计**，不是重新执行容器控制，也不是对全部原始日志的逐条复核。

## 一、本轮验收结论：哪些通过，哪些仍然阻断下一步

| 审计对象 | 本轮结论 | 对下一阶段的影响 |
|---|---|---|
| 缓存修复、封存后测试、连续执行和版本绑定 | **限定通过** | 不需要再完整重做八轮诊断 |
| 测试结果进入正确成员后续请求 | **已发布核验工件支持** | 可以承认反馈呈现链已经打通，不能扩张为模型理解 |
| 永久错误传播与停止门 | **组合证据限定通过** | 正式部署中仍需覆盖一次运行中故障，而不只是终态拒绝 |
| 正式 FIFO 服务、实际任务解释器 | **尚未准入** | 继续阻断新的付费执行 |
| 历史协作区间及故障边界分析 | **描述性分析通过** | 可用于设计机制实验，不能作为组织调整收益 |
| 组织决策定义与动作空间 | **存在需要修正的设计问题** | 应在 O1／O2 实现前解决 |

综合验收文件明确写的是 `qualified_for_mechanism_controls_only`，正式部署状态为 `HOLD`，并且没有准入 v204。这与报告的限定结论一致，没有把局部控制包装成正式部署通过。

### 1. 本轮确实修复了上轮最关键的机制缺口

最有价值的证据不是“pytest 最后通过”，而是：

**错误代码得到真实断言失败 → 正确成员后续输入包含对应测试信息 → 后续修改与复测继续 → 复核和交付完成。**

反馈核验文件逐一列出了四次测试的报告身份、原记录哈希、测试计数和后续请求身份，覆盖一次失败、三次通过，并明确限定为实际输入字段呈现，不声称自主模型决策质量。这个证据层级是合理的。

因此，我认可：

**v203.2.3 暴露的缓存错误及反馈链断裂，已经在本轮受限组件组合中得到实质修复，而不只是修改了某个单元测试。**

### 2. r8 非零退出不应推翻整个控制，也不能被忽略

r8 的诊断入口漏捕获了预期异常子类。实际工作链与终态拒绝已经发生，随后只对保留的错误帧检查 `failed` 状态和停止门，没有重新执行世界动作。这允许组合形成限定证据，但不能写成“同一个原入口全程正常退出”。目前报告保留了这一边界，我认为处理正确。

这里仍有一个**针对下一步的窄缺口**：

> “锁定后拒绝写入”触发停止，与“任务进行中第一次公开测试发生永久设施故障”触发停止，不是完全相同的运行路径。

下一轮只需在正式 FIFO 路径中补一个针对性控制：在任务尚未结束、下一次模型调用尚未预约时，注入永久测试设施故障，核验后续付费调用准入被阻止。

同时，普通断言失败、非法选择器、可处理的操作拒绝，不能因此一律升级为永久通道故障。**应验证错误分类和停止传播，不需要扩张为全系统容错认证。**

### 3. 91.54%说明故障停止很重要，但不应继续占据研究主线

按已发布汇总复算：

\[
\frac{50{,}045{,}483}{54{,}670{,}031}=91.541\%.
\]

首次故障前的响应用量为：

\[
54{,}670{,}031-50{,}045{,}483
=4{,}624{,}548\text{ Token}.
\]

报告对这组数字的解释正确：后续成本发生在反馈失效之后，不等于这些成本都能被无损节省；故障前保留下来的十条协作回执也只是过程证据。

**工程修复应当到此收敛。** 完成正式路径的有限准入后，主要研究资源应回到组织适配，而不是继续围绕旧故障构造更多验收指标。

## 二、本轮最重要的问题，不是工程，而是研究对象仍有些偏窄

### 1. “原组织能够处理需求”不等于“原组织已经足够高效”

历史汇总显示，16个发布—集成区间都观察到了集成操作；4个冲突区间中3个观察到了所定义的内容恢复；12个复核区间中11个观察到了同版本证据匹配。原108窗仍然只是旧 AI 辅助参考，97个 ABSENT、11个 UNKNOWN，没有新增独立确认。

这组结果反对的是一种过强叙述：

> 原有组织普遍不能处理交接、冲突与复核，因此必须动态重组。

但它没有回答：

> 原有组织虽然能完成这些工作，是否付出了本可避免的等待、重复修改、集成返工或协调成本？

**组织优化不应只研究“原组织做不了”，还应研究“原组织能做，但另一种组织安排更合适”。**

例如，两个成员分别处理耦合较强的修改，通过反复交接最终可以完成；把相关修改临时集中到一名成员、另一名成员承担验证，也可能减少往返。两者都可行，区别在于完成质量、成本和风险，而不是一个“有能力”、另一个“没能力”。

这是对目前研究定义的一项建议修订，**不意味着把旧 ABSENT 改成阳性，也不意味着已经发现效率收益**。应当分开记录：

- 已有证据支持的组织约束缺口。
- 尚待实验检验的组织效率改进机会。

否则，我们会把“优化”收缩成“处理无法继续执行的异常”。

### 2. 不能把“先取得确证阳性”设为所有干预实验的前提

我需要修正此前建议中过于严格的一点。

**独立失配标签是评价失配识别器的重要前提，但不是所有安全、合法的组织对照实验的必要前提。**

人工审阅可以判断当前存在什么工作需求、责任是否明确、哪些操作合法；但它通常不能仅凭一段轨迹，确定“另一种组织安排一定会带来更好的最终结果”。

这恰恰需要干预实验回答。

因此应区分：

**识别问题：** 当前是否存在某种可观察的组织缺口？

**决策问题：** 从当前状态出发，调整组织是否比保持原状更有价值？

不能要求先证明第二个问题的答案为正，才允许开展用于回答第二个问题的实验。否则会形成研究上的循环。

### 3. 当前任务与组织设置，可能没有充分展开适配空间

SWE-bench 的基本任务是给定问题与仓库状态，生成能够修复问题的补丁；它本身并不保证每道题都需要多成员组织调整。这一点来自基准的任务定义，而不是本轮负结果。[SWE-bench](https://www.swebench.com/SWE-bench/faq/?utm_source=chatgpt.com)

在目前两人 REVIEW2 条件下，还要进一步问：

**所谓“调整组织”，到底可以改变什么？**

如果始终是001执行主要修改、002复核，任务板又没有实际参与工作安排，那么改变一个 `owner` 字段，未必改变模型后续工作。若 `AddHandoff` 只是调用原来就能调用的交接工具，也未必构成组织架构变化。

因此，当前首个研究准入条件应当是：

> **组织动作必须改变真实的工作承担、执行顺序、依赖等待或验证责任，而不是仅改变图上的标签。**

两名成员足以研究责任重分配、任务顺序和验证职责的适配；但不能凭两人实验就声称已经验证了复杂团队拓扑或一般性的组织架构搜索。

## 三、关键源码审计：发现一个可复现的决策语义问题

### 1. `NO_CHANGE` 被错误地绑定到“没有失配”

当前 `validate_mismatch()` 包含以下逻辑：

```python
if row.get('decision') == 'NO_CHANGE' and row['mismatch'] != 'ABSENT':
    raise ValueError(...)
```

也就是说，只要失配为 PRESENT，就不能选择 NO_CHANGE。

我对该条件做了最小逻辑复现。如下情况会被拒绝：

> 有证据证明当前存在责任缺口；但所有合法重组方案都超过剩余预算，或者会破坏现有验证条件，因此决定保持当前组织。

这不是证据不足的 `ABSTAIN`。它是**知道存在问题，比较可行选择后决定不调整**。

这直接关系到我们的核心算法，而不是单纯的字段命名。

建议把三个轴分开：

| 轴 | 回答的问题 | 示例 |
|---|---|---|
| 状态判断 | 当前有什么问题或改进机会？ | PRESENT／ABSENT／UNKNOWN |
| 可行性判断 | 有无满足权限、版本和复核约束的组织动作？ | 可行／无可行动作／未知 |
| 行动选择 | 现在实际怎么做？ | 保持／调整／因证据不足暂缓 |

“保持”至少可以有不同理由：当前组织合适、调整收益不足、切换成本过高、剩余预算不足、没有合法替代方案。

**不能为了允许保持组织，就把真实存在的缺口改标成 ABSENT。**

这项问题不推翻本轮的工程控制和历史计时结果，但应当阻断直接按现有校验器实现 O1／O2 决策逻辑。

### 2. 历史脚本现在完成的是“事件链与能力的对齐”，不是需求发现

`analyze_organization_demand_v203_3.py` 按既有链类型赋予 `work_demand` 和 `existing_capability`：例如发布—采用链对应“采用已发布候选”，冲突链对应“恢复精确发布内容”，复核链对应“同版独立复核”。它没有独立推断这些需求的必要性，也没有实现组织优化决策。

所以，当前结果适合表述为：

**这些已发生的协作过程，可以与现有工具能力建立来源明确的对应。**

还不能表述为：

**系统已经能够从任意真实工作状态发现全部必要组织需求。**

这不是要求立即补一个大模型需求识别器，而是避免下一阶段把描述性字段直接当成监督标签。

### 3. 两个区间定义需要保留原义，不能进一步泛化

**第一，集成操作结束不等于需求满足。**  
脚本在对应接收者出现 `ok` 的集成回执后结束 A 类区间，报告也明确其中有冲突。因此，这个终点只能表示操作发生；后续训练或策略评分不能把它自动理解成“交接问题已解决”。

**第二，恢复原候选内容不等于所有意义上的冲突解决。**  
合法合并可能保留接收方的其他必要修改，结果并不与发送方候选完全相同。因此，未观察到“精确原候选恢复”，不能直接推断冲突没有解决。当前脚本测量的确实是前者。

同样，当前中位数只来自观察到终点的区间，不能当作全部需求的平均解决能力；没有结束时刻、候选被替代、观察期结束，也应当保留不同状态。**这些是后续使用指标时的边界，不需要因此否定本轮已正确限定的描述结果。**

## 四、研究命题应收敛为三个可证伪问题

我建议将后续主线从“找失配—做调整”改得更完整一些：

### 命题 A：组织变化是否真正改变了执行过程？

同一成员集合、相同工具权限下，组织动作能否改变工作包承担者、依赖处理顺序、交接责任或验证安排？

这里验证的是**真实可干预性**。只有图记录变化、没有后续执行变化，不算通过。

### 命题 B：组织变化是否产生了局部净收益？

令 \(x\) 表示某个决策前的完整工作状态，\(a\) 是一个合法组织动作，\(a_0\) 是保持原组织。定义：

\[
\Delta_Y(x,a)
=
\mathbb E[Y\mid x,\operatorname{do}(a)]
-
\mathbb E[Y\mid x,\operatorname{do}(a_0)],
\]

其中 \(Y\) 优先取**合法提交且通过官方验收**。同时单独报告：

\[
\Delta_C(x,a)
=
\mathbb E[C\mid x,\operatorname{do}(a)]
-
\mathbb E[C\mid x,\operatorname{do}(a_0)].
\]

这里暂不把质量、Token、等待和风险任意加成一个总分。

这个命题允许出现多种结果：调整提高交付率；质量相近但减少成本；没有明显影响；或者反而造成损失。最后一种同样有研究价值，因为它约束策略何时应该保持稳定。

### 命题 C：执行反馈是否改善了未来的组织决策？

在任务内适配之外，比较更新后的组织策略与原策略：

\[
\Gamma_k
=
\mathbb E_{x\sim D_{\mathrm{eval}}}
\left[
Y(\pi_{\theta_{k+1}},x)-Y(\pi_{\theta_k},x)
\right].
\]

只有在相同执行预算、明确开发与评价分离的条件下，才能讨论闭环更新是否有效。

**一次调整成功只涉及命题 B 的一个样本；不能直接作为命题 C 的证据。**

此外，动态规划、任务分配和失败后重规划本身已经有成熟先例，例如 Magentic-One 的协调者会规划、追踪进展并重规划。因此，我们的差异化不能停留在“有一个会动态分工的管理者”，而应落到**版本化工作依赖与组织责任的联合判断，是否改善组织变换选择，以及这种判断能否被真实反馈校准**。[微软](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/?lang=zh-cn\&utm_source=chatgpt.com)

这仍是候选研究机制，不是已经确立的原创性结论。

## 五、下一轮零 API 工作：只解决四个有明确出口的问题

建议下一轮仍然不启动外部模型，但不要继续扩大历史计时或工程控制范围。工作应当有明确结束条件。

### 1. 完成正式执行路径的最小准入

沿用修复后的源码，通过批次专属正式入口、FIFO 路径和确定性模型替身，完成：

**正常路径：** 封存后首次公开测试、真实失败反馈、继续修改、复测、复核、交付和最终同步。

**故障路径：** 工作尚未结束时发生永久设施故障，原错误正确传播，后续模型调用预约被阻止，已发生动作不被重放。

只对下一批实际使用的解释器和必要环境做针对性检查。通过后关闭该工程事项，不再因为“没有证明所有故障都能恢复”而无限延长准入。

### 2. 修正决策状态，不改旧标签

修复 NO_CHANGE 与 ABSENT 的绑定，明确区分：

**没有问题、问题存在但不调整、证据不足暂缓、没有合法替代方案。**

旧108窗保持原样；新定义以新版本保存。需要重新解释的地方明确列出差异，不静默回写历史。

### 3. 建立最小可执行组织动作，而不是一次实现完整动作库

首版建议只考虑：

> **重分配一个未完成工作包，并同步明确其交付与验证责任。**

暂不同时实现 Split、Merge、增加成员及复杂团队重组。当前修订协议也明确，Split／Merge 尚未验证为可执行能力，不能直接进入在线条件。

这个动作必须回答四个具体问题：

**究竟改了什么？**  
不只是 owner 字段，还要改变哪名成员接下来处理什么、另一名成员做什么。

**为什么原工具权限下可行？**  
不能通过新增权限、额外成员或隐藏的免费信息制造优势。

**怎样保留工作连续性？**  
既有补丁、未完成事项、当前有效版本和测试证据如何交接。

**复核是否仍满足冻结规则？**  
不能通过重新发布补丁改变名义作者，把实际自审包装成独立复核。原协议若只要求复核者不同于固定产物发布者，就应按这一范围报告，而不是扩张为完全独立于代码贡献者。

若这些问题的答案表明：两人和当前交付约束下，该动作不能真正改变执行安排，那么应先修订研究动作空间，**而不是启动一个只有图标签发生变化的组织实验**。

### 4. 冻结一小组“可进行分支比较的状态”

不再以“有没有人工确认阳性”作为唯一入选标准，而按以下条件准备：

状态来源完整；没有已知永久环境故障；存在合法、非平凡的组织动作；保持原组织也是合法选项；可以恢复决策前状态；不需要利用未来结果挑选动作。

来源可以分成两类，但必须分开报告：

**历史自然状态。** 主要来自 v203.2.1 中可核验的交接、冲突、复核前窗口。不能默认十二题全部无环境问题，也不能把历史终态反向填入早期状态。

**受控机制状态。** 从真实仓库工作结构构造依赖变化、责任重叠及稳定负例，用于验证组织动作和比较机制。它们不是自然失配率样本；若改变了原 Issue 或任务要求，也不能再称为原 SWE-bench 任务成绩。

没有可合法恢复的历史状态，就先准备新试跑的检查点保存能力，不能拼接一份“看似相同”的历史上下文冒充配对起点。

## 六、后续首次付费实验：先做小规模“组织调整价值探测”

这是我认为比直接扩大 O0／O1／O2 更重要的一步。它需要单独授权；下面是设计建议，不是执行安排。

### 1. 实验规模与对象

建议起步为：

\[
4\text{个决策前状态}
\times
2\text{个分支}
\times
2\text{次重复}
=
16\text{个短续跑}.
\]

四个状态尽量来自不同任务，并覆盖至少三个仓库。这个规模**只用于检查机制和发现明显方向，不具备正式功效保证**，四个状态也不能因重复执行而被称为十六个独立任务。

状态应同时覆盖可能需要调整和可能不需要调整的情况，例如：

| 状态类型 | 要回答的问题 |
|---|---|
| 新依赖已经出现，原分工产生往返协调 | 集中相关工作是否比继续交接更合适？ |
| 修改或验证工作分布明显不均 | 调整工作承担能否改善剩余工作推进？ |
| 出现冲突，但责任和恢复路径清晰 | 重组是否反而没有必要？ |
| 现有交接与复核正在正常推进 | 策略是否能够保持稳定，避免多余变更？ |

这些是入选的结构特征，不是预先指定哪一分支必须胜出。

### 2. 两个分支到底比较什么？

**保持分支：** 保留当前组织安排，继续原有通信、工具和工作规则。

**调整分支：** 执行一次事前规定的合法组织变换，之后继续工作。

后续其他策略保持一致，避免把“组织调整＋新上下文策略＋额外诊断器”打包比较。必要的信息交接是动作执行成本的一部分，但不能顺便加入新的上下文优化算法。

每个配对需要恢复相同的代码版本、成员私有历史、工作区、剩余事项、已知测试状态和剩余预算。**不能只恢复同一 Git 提交，却让两边拥有不同的信息或已完成工作。**

### 3. 怎样避免观察到成功后才解释组织动作有用？

动作候选和窗口选择必须在分支结果出现前冻结。审阅者可以提出可行替代组织，但不能依据原最终成绩挑出“肯定能救回来”的状态。

所有预定状态都保留，包括：

调整没有发生、调整被合法性检查拒绝、两边均失败、保持分支更好，以及环境故障导致无法判断的情况。

独立审阅仍然有用，但主要用于核验当前需求、信息边界和动作合法性，**不要求审阅者事前给出“哪个动作必然提高最终分数”的金标准**。

### 4. 评价什么？

主要评价仍为合法交付与官方代码端点，同时记录分支总成本和关键过程结果。过程指标重点放在：

组织动作是否真正落地、相关依赖是否得到处理、返工或往返是否减少、是否产生新的版本或验证问题。

不能把“执行了转移”当成功；不能把“冲突消失”替代最终任务质量；也不能根据隐藏评分选择中途最好的候选。

若配对两边都耗尽共同预算，应比较预算内的任务结果与有效进展，不能仅凭最终 Token 几乎相同就判断效率等效。

### 5. 这一步的出口是什么？

**存在值得继续检验的局部差异：** 再实现自动选择策略，进入 O0／O1／O2。

**主要只看到正常通信就能解决问题：** 保留这些负例，重新检查任务工作结构是否真的包含组织适配空间。

**动作根本不改变执行：** 返回动作定义，而不是增加模型规模或采样次数。

**结果波动大、样本太少：** 报告不确定；不得在没有预定范围的情况下不断补样直到出现正收益。

这一步不会证明总体优越性，但可以直接检验：**我们准备研究的组织动作，到底有没有值得算法优化的价值空间。**

## 七、再进入 O0／O1／O2：需要防止三个混淆

### 1. 保留强事件基线，而不是让 O2 获得额外事实

O1 和 O2 应当从相同的、当时可合法获得的事实出发。O1 可以使用完整普通事件历史和动态重规划；O2 的增量是组织化地利用依赖、责任、版本和验证关系，而不是独占其他成员私有信息或评测侧全局状态。

图构建、控制器推理、候选比较和迁移交接的成本，都计入各自团队预算。O0 不必为了形式上“等调用数”而空跑一个控制器，但不能让 O2 获得预算之外的决策资源。

### 2. 区分“更好的组织”与“必须动态调整”

O2 优于固定 REVIEW2，可能只是因为它找到了一种更好的分工，不一定证明任务中途适配是关键。

因此，在局部机制成立后，还需要一个针对性比较：

**任务开始时选择一次组织、之后不再改变**，与**根据执行中新信息继续适配**。

这不必立即扩成四组大规模网格，但最终要声称“动态适配”的贡献，就需要排除“只要初始组织选得更好即可”的解释。

### 3. 不把检测准确率当成最终算法目标

失配 Precision／Recall 可以诊断一个识别模块，但我们最终关心的是：

**相同预算下，策略有没有作出更有价值的组织决定。**

高准确率检测器可能识别了大量不值得干预的小问题；较保守的策略也可能通过少量高价值调整改善任务结果。因此，识别性能、干预选择和最终收益应分别报告，不能以某一项替代另外两项。

## 八、闭环优化应从一开始就准备，但不要提前宣称进化

对于跨任务闭环，我建议首版仍不训练模型权重，而优化有限的组织策略配置：触发条件、候选生成规则、局部责任调整范围、切换代价处理和保持策略。

可以沿用以下顺序：

**完整记录成功、失败与保持案例 → 提出有限策略修改 → 在开发状态上配对比较 → 冻结后继策略 → 在未用于选择的任务上验证。**

关键不是生成了多少“经验总结”，而是后继策略是否比原策略作出了更好的决定。

还要控制一个常见混淆：反馈驱动候选如果比固定策略获得更多搜索和试验预算，结果变好可能来自额外搜索。因此，闭环机制最终应与**相同候选数量、相同验证预算的普通候选搜索**比较。所有被淘汰候选的成本也必须计入。

这一阶段可以研究“基于受影响工作子图的有限组织变换、切换成本约束、真实后续结果校准”这一候选机制。但在取得局部组织动作收益之前，不宜同时优化图抽取、组织策略、上下文和评分规则，否则又会失去可解释性。

## 九、最终审计意见与推进顺序

**本轮没有发现足以推翻“限定工程通过＋描述性历史分析”声明的反例。** 但在面向下一阶段的源码中，发现了 NO_CHANGE 与 ABSENT 错误绑定的问题；在研究设计上，还需要避免把“原组织无法完成”当作组织优化的唯一入口。

接下来建议只推进以下顺序：

| 顺序 | 工作 | 结束标准 |
|---|---|---|
| 近期零 API | 正式 FIFO 最小链路与运行中故障停止控制 | 正式路径正常闭合，永久故障不再触发后续付费机会 |
| 同期零 API | 修正决策语义、明确最小组织动作 | 能表达“有问题但不调整”，组织动作能改变真实执行 |
| 同期零 API | 准备少量合法可恢复状态及稳定负例 | 不使用未来信息，保持与调整两分支都可执行 |
| 单独授权后 | 小规模配对续跑 | 判断局部组织变换是否存在值得继续研究的价值 |
| 后续 | O0／O1／O2与一次性组织选择对照 | 分离普通重规划、图结构和动态适配的贡献 |
| 再后续 | 跨任务策略更新 | 证明反馈更新优于冻结策略及等预算普通搜索 |

旧130元账本和剩余 **31.25543296元**继续保持原边界，不自动转用于上述续跑；本次没有启动新的模型实验或修改项目运行环境。该预算边界也与已发布研究修订一致。

**核心结论是：现在不缺更多“能看到协作事件”的证据，而缺“同一工作状态下，改变组织究竟比不改变好在哪里”的证据。**

把这个局部反事实问题先做清楚，组织需求识别、图驱动决策和跨任务闭环优化才能连接成一条可验证的研究链，而不会继续停留在图结构、工具调用和工程验收之间。
