一、总体审计结论
这轮实验比 v203.2 更进一步：我们已经从历史轨迹重放进入真实模型执行中的前瞻性被动观测。

我认为本轮完成了一个重要的阶段性目标：

在不改变原 REVIEW2 组织和 Agent 行为策略的条件下，获得了12个真实 SWE 任务的完整执行、协作、版本及交付证据。

但本轮仍然只有一个实验条件，即固定 REVIEW2，没有动态组织、动态通信或上下文管理对照。

因此，58.3%的代码正确率和合法交付率只能描述这12题，不能证明：
- REVIEW2 优于单 Agent。
- 双 Agent 协作本身提高了成功率。
- 观测器帮助 Agent 改善了任务执行。
- 交接和补丁采用证明了组织合理。
- 动态工作图已经具有实际收益。
我将本轮的主要成果归纳为三点：
1. 真实执行过程的可观测性取得了重要进展。
2. 自然协作行为已经有一定数量的真实材料，但显式依赖和责任转移仍然缺失。
3. 任务失败、Token 预算和协作行为之间出现了值得深入分析的关联，但目前还不能进行因果归因。
我的建议是：不要马上进入 v204 动态组织干预。下一阶段应当利用本轮12题，先完成自然协作机制分析和组织失配独立审阅。

这只是简单的任务级描述区间，尚未处理仓库聚类及历史曝光问题。

本轮的主要价值是过程数据，而不是最终成绩排名。

机制 A：任务难度导致高消耗。

复杂任务需要更多源码阅读、测试和修改，最终也更容易失败。

机制 B：协作开销导致预算提前耗尽。

两个 Agent 分别维护上下文，产生额外的代码读取、消息、复核和摘要成本。

机制 C：失败导致反复尝试。

代码问题没有解决，模型持续尝试修改、测试和修复，导致 Token 增长。

三者可能同时存在。

因此，本轮不能简单地把失败归因于协作开销，也不能认为只要增加预算就能提高正确率。

不过，我认为这已经构成下一阶段非常值得研究的一个问题：

在固定资源预算下，如何根据任务结构与当前执行状态，合理配置两个 Agent 的工作量、通信成本和上下文预算？

这里有一个需要进一步审查的细节。

- 成功集成。
- 冲突拒绝。
- 冲突解决。
- 集成后版本验证。
这也是下一轮数据分析必须补充的地方。
3.2 信息交接仍然是一个明显的问题
本轮有26次成功消息发送和16次补丁交接。

但：
- 显式通信正文回读：0次。
- 原文工作事件回读：2次。
- 伙伴发布补丁文件显式读取：1次。
不能由此断定 Agent 没有获得信息，因为它们可能通过请求预览、工具返回和工作区状态获得信息。

但可以确定：

当前仍缺少足够完整的证据，证明跨 Agent 信息是如何进入接收者上下文、如何被利用，以及最终如何影响交付。

这恰恰是后续研究通信与上下文机制的关键。

目前还不能将这16次补丁交接解释成16次有效的信息传递，更不能认为补丁成功集成就代表整个任务协作有效。
3.3 为什么没有显式依赖声明和责任转移？
本轮任务板创建、任务领取、显式依赖声明和责任转移均为0。

这里我不认为应该继续把重点放在提高工具调用率上。

原因是本轮已经证明：
- Agent 确实获得了相应工具。
- 自然任务中确实发生了补丁交接和成果采用。
- 但 Agent 没有使用任务板和显式责任转移机制。
我认为更重要的问题是：

当前 REVIEW2 是否已经提供了足够的固定责任结构，使 Agent 可以通过补丁交接完成协作，而不需要显式调整任务所有权？

如果答案是肯定的，那么我们需要寻找真正使固定组织失效的任务，而不是人为制造责任转移。

这也是为什么下一阶段应当先分析自然协作需求，再进入动态组织实验。

四、观测器工程审计
本轮12题全部标记为 COMPLETE，这是一个重要进展，但我不建议直接把它理解为观测器已经达到长期生产级可靠性。
4.1 通过的部分
- 915次物理 API 请求均已结算。
- 863次执行 Agent 请求均有 SDK 决策关联。
- 831次执行器工具尝试均有对应回执及决策来源。
- 807次工具成功，24次拒绝或错误。
- 请求和响应原件可关联。
- 用量及费用闭合。
- 12题九个完整性维度均为 COMPLETE。
尤其值得肯定的是，前两题最初被标记为 PARTIAL，随后通过验证压缩归档的完整性、重新读取 SDK 轨迹，恢复了真实关联。

没有重新执行模型动作，也没有补造事件。

这是正确的恢复方式。
4.2 仍然存在的工程限制
本轮报告明确指出，9.19秒 CPU、9.76秒墙钟以及3.91GiB峰值 RSS，并不是观测器自身的完整增量成本。

因为这些指标包含整个控制器，而且没有关闭观测器的同条件对照。

另外，host HTTP 捕获、归档和离线解析也没有全部计入。

因此，下一阶段需要增加：
- 观测开启与关闭的配对 CPU 控制。
- 独立进程 RSS 和磁盘增长。
- 请求延迟分布，而非只有累计时间。
- 长时间运行下的资源增长。
- 故障后完整性恢复时间。
不过，这些属于工程成本测量，不应该阻断已经完成的科学问题分析。
4.3 评分环境适配必须单独保留
Pylint 和 Requests 的评分环境进行了离线依赖与 CA 加载适配，并通过了 gold/empty 控制。

这比直接忽略环境问题要好。

但它仍然意味着这两个任务的评分环境并非完全未经修改的原生环境。

建议后续保留三种字段：
- 原始基准环境。
- 经过验证的离线适配环境。
- 实际任务执行环境。
确保适配只解决环境依赖，不改变测试语义和评分标准。

尤其是 Requests 的 TLS/CA 修订，未来需要保留与标准环境的等价性证据。


五、最重要的研究判断：本轮已经暴露出三个新的研究切入点
结合 v203.2.1 的真实执行数据，我认为应该适当调整此前的实验优先级。
5.1 从显式责任转移转向隐式协作需求
之前我们比较关注：
- 任务认领。
- 显式依赖声明。
- 责任转移。
- 组织拓扑调整。
但本轮自然执行中，这些操作均为0。

与此同时，却发生了：
- 16次补丁交接。
- 16次补丁采用/集成记录，其中有冲突。
- 12次复核决定。
- 43次实际执行失败的公开测试。
这说明固定 REVIEW2 下，已经存在相当多的协作和成果依赖行为，只是它们没有通过显式任务管理机制表达。

我认为这提示我们需要重新审视组织失配的定义。

例如：

某个 Agent 多次尝试集成伙伴补丁并发生冲突，究竟属于：
1. 正常的代码集成问题；
2. 补丁版本和依赖管理问题；
3. 责任区域划分不合理；
4. 缺乏必要的协调和交接；
5. 上下文不足导致的错误采用。
不能直接把冲突计为组织失配，但也不能只因为没有显式转移责任，就认为当前组织没有失配。

因此，下一轮应重点分析隐式协作需求及其未被满足的情况。
5.2 从最终成功率转向过程中的决策质量
本轮有12题、64个阶段点、831次执行器尝试。

这些数据提供了一个此前相对缺失的研究机会：

我们可以分析 Agent 在某个时间点是否作出了合理的协作决策，而不只是判断最终代码是否正确。

例如：
- 是否应该向伙伴发送消息？
- 是否应该先读取伙伴补丁再集成？
- 是否应该在冲突后重新协商？
- 是否应该请求独立复核？
- 是否应该继续由原成员负责？
- 是否应该调整任务责任区域？
- 是否应该减少已经没有必要的上下文？
这意味着可以逐渐建立一种过程级评价：
\[
Q_{\text{decision}}
=
f(\text{Evidence},\text{Role},\text{State},\text{Action})
\]

但必须强调，过程决策的合理性不能直接由最终成功与否定义。失败任务也可能作出正确的协作决策，成功任务也可能包含不必要的协作开销。
5.3 从组织动态性转向资源约束下的协作效率
本轮还有一个值得关注的现象：

7题触及5M Token门，其中5题失败、2题成功。

双 Agent 的输入 Token 占比达到99.61%，复核成员占全队Token的37.83%。

这意味着我们的研究不能只关注组织结构是否合理。

还需要关注：

在相同资源约束下，如何让不同 Agent 把有限的上下文和执行预算投入到真正有价值的工作中。

这里的资源分配不应等同于简单的成员 Token 配额。

例如：
- 复杂代码定位阶段可能需要更多输入预算。
- 补丁复核阶段需要精确的版本与差异信息。
- 交接阶段需要完整的必要证据，而非重复传输整个工作历史。
- 交付阶段需要保留验证和版本闭合预算。
这与 SEWG 中的项目图、组织图及成员局部上下文有天然联系。

不过，当前还没有证据说明资源配置是本轮失败的原因，因此这应该是新的待验证机制，而不是对本轮失败的既定解释。

6.3 重点建立四种事件链
事件链 A：交接—信息获取—采用
补丁发布
接收者实际获得的信息
读取、采用或拒绝
集成、测试与版本结果

事件链 B：冲突—处理—恢复

补丁冲突 → 冲突原因 → Agent 决策 → 修改或重新集成 → 最终验证

事件链 C：复核—返修—交付

固定版本 → 独立复核 → 接受/返修 → 新版本验证 → 合法提交

事件链 D：预算—决策—终止

剩余预算 → 下一步操作预约 → 预算门 → 放弃、提交或继续 → 最终结果

这里需要从原始请求和回执恢复每个事件的准确时间顺序，不可以只使用最终汇总表。

v203.3：组织失配识别独立验证
依赖 v203.2.2
这一阶段才正式验证：
\[
\hat M_t=f(G_t^p,G_t^o,S_t)
\]

是否能够在真实任务中识别需要调整的组织状态。

我建议保留之前的五类失配：
1. 依赖满足失配。
2. 责任冲突。
3. 责任缺口。
4. 协调瓶颈。
5. 验证职责失配。
但增加一个重要区分：

真实存在的协作需求，不一定意味着存在组织失配。

例如：

跨模块依赖可能通过一次正常交接解决，不需要调整责任区域。

因此建议增加两个中间变量：
\[
D_t=\text{实际工作依赖}
\]

\[
N_t=\text{当前组织未满足的协作需求}
\]

再判断：
\[
M_t=\text{组织失配}
\]

这样可以避免把所有依赖都变成失配阳性。

- 阳性失配发生率。
- 各类失配的分布。
- 仓库内相关性。
- 审阅者一致性。
再进行基于仓库聚类的样本量规划。

独立确认应尽量采用研究历史未使用过的仓库。现有12题全部已经曝光，不能承担最终独立确认任务。

如果自然阳性不足，则继续采集，而不是人为制造阳性或降低识别标准。

v203.2.3：角色感知上下文管理 Pilot
建议独立于组织干预开展
这是我建议新增的一条实验支线。

原因是本轮已经有真实补丁交接和复核行为，却缺少充分的信息呈现与使用证据。

相比直接调整组织结构，先验证上下文管理可能更容易形成清晰的实验。
核心研究问题
在固定 REVIEW2 的组织结构下：

根据接收者的当前角色和任务状态选择上下文，是否比通用上下文选择更有效？

可以设计：
条件	上下文策略
K0	原有上下文管理
K1	通用相关性选择
K2	角色感知选择

其中：
- K0 保持原 Harness。
- K1 根据当前任务相关性选择必要信息，不使用角色特定规则。
- K2 在 K1 基础上考虑成员角色、责任区域、版本和验证职责。
三组必须使用相同的原始信息权限、候选信息池和预算约束。

不能让 K2 获得额外的私有信息。
核心评价
指标	目的
关键证据保留率	是否遗漏必要信息
过期版本误用率	是否使用失效证据
伙伴成果正确采用率	信息是否真正帮助工作
复核缺陷检出率	是否帮助独立复核
输入 Token	是否减少无效上下文
最终代码正确率	是否影响任务质量
合法交付率	是否影响交付闭环

这里有一个重要的实验设计问题：

K1 与 K2 必须采用相同的信息来源和相同的信息总预算。否则，最终差异可能只是上下文长度不同造成的。

本轮12题可以用于机制分析和方案校准，但不能再次充当独立效果确认集。

我建议先在小规模、独立的新任务面板上验证上下文选择机制，再决定是否扩大实验。

v204：项目图驱动的动态组织干预
等待前置验证
这是整个研究的核心算法验证阶段。

但根据本轮新结果，我建议对之前的四组对照方案作一个重要修正。
6.6 正确区分图质量实验与组织收益实验
此前设计的 O0—O3 中，O1 是动态项目图、固定组织。

如果 O1 不改变 Agent 输入、工具行为和组织决策，那么它不应该被期待产生代码正确率提升。

它主要验证的是：
- 项目图更新是否准确。
- 版本变化是否及时反映。
- 依赖边失效是否正确。
- 图构建成本是否可接受。
因此，O1 应当作为图质量实验，而不是直接拿来和组织干预组比较任务成绩。

我建议 v204 正式采用三个主要条件：
条件	项目图	组织策略	核心作用
O0	观测，不参与决策	固定 REVIEW2	基础对照
O1	动态更新	普通事件驱动调整	非图结构强基线
O2	动态更新	SEWG图驱动调整	检验核心方法

三个条件使用相同的合法调整动作：
- Reassign
- Split
- Merge
- AddHandoff
- AddReviewer
同时固定：
- Agent 数量。
- 模型和运行配置。
- 工具及权限。
- 任务初始状态。
- 总预算。
- 最终交付和独立复核规则。
普通事件驱动基线必须比简单的 blocked 次数规则更强，至少使用实际失败原因、版本状态、工作量和依赖解除情况。

主要比较：
\[

=

\]

同时保留：
\[

前者回答图驱动组织是否比普通事件驱动组织更有效。

后者回答完整动态组织方法是否优于固定组织。

这两个问题不能互相替代。

七、需要补充的理论设计：SEWG 不应该只是一个组织控制器
我认为本轮实验还给我们带来了一个重要启发。

目前的 SEWG 可以表示为：
\[
G_t=(V_t,E_t)
\]

但未来需要进一步区分三个状态：
\[
G_t^{global}
\]

全局评测图，包含所有可以由评测器核验的任务、代码、成果和证据关系。
\[
G_{i,t}^{local}
\]

Agent \(i\) 在当前时刻实际能够获得的局部工作图。
\[
\hat G_{i,t}
\]

Agent 根据自身信息形成的工作结构认知。

这三个对象不能直接等同。

例如：

全局图中已经存在某个补丁及其测试结果，但 Agent 002 可能还没有收到补丁，也没有读取测试报告。

此时：
\[
G_t^{global}\neq G_{002,t}^{local}
\]

而且 Agent 对当前任务结构的理解也可能不完整：
\[
G_{002,t}^{local}\neq \hat G_{002,t}
\]

这个区别非常重要。

因为我们的研究不只是要构建一个准确的项目图，还要研究：
- 图信息如何被不同 Agent 获取。
- 不同 Agent 如何形成各自的工作认知。
- 信息不对称如何影响协作。
- 如何根据成员实际掌握的信息调整组织与通信。
- 最终执行结果如何修正全局图。
这比直接把全局图输入一个组织控制器更接近真实的多智能体工作环境。

我建议把它纳入 SEWG 后续理论设计，但不立即扩大 v203.2.2 的实验范围。

十、最终建议
我认为目前研究已经进入一个比较关键的转折点。

之前我们的主要问题是：

如何构建动态工作图，并让它驱动多智能体组织调整？

现在应该先回答：

在真实软件工程任务中，固定组织究竟在哪些情况下不能有效满足工作需求？这些问题又有多少是信息管理问题、代码问题和资源问题，而不是组织问题？

这决定了后续算法是否有真正的必要性。

我建议近期只推进一项正式工作：
下一步优先工作
v203.2.2：12题自然协作机制审计
不新增模型调用，不重新评分，不消耗新实验预算。

重点完成：
1. 16次补丁交接的完整事件链。
2. 4次冲突的原因及后续处理。
3. 12次复核的缺陷、返修与版本关系。
4. 43次实际失败测试的原因分类。
5. 7题预算门触发前后的行为分析。
6. 独立审阅组织失配及上下文不足的真实证据。
最终判断自然任务中是否已经出现足够明确的组织失配，以及哪些问题值得进入动态组织干预。

我的核心判断是：目前不应该为了证明动态图组织有效而寻找调整机会，而应该先从真实轨迹中证明固定组织在哪些地方确实存在不足。

只有这样，v204 的组织干预才有明确的科学问题、可靠的对照条件和可证伪的研究价值。
