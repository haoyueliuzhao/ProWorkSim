# v155机制分析工作笔记（非最终报告）

口径：使用`../final-report-r1/episodes.json`的120个最终选定回合，99个原正常回合＋21个首次独立恢复。正式机制统计对每份选定controller结果读取一次，共175,695,875字节；附加读取99份已有观察摘要及21份未finalize的小型events侧录（后者5,385,722字节）。未解压归档、未读完整SDK会话、未查询API账本、未调用模型或评分。逐题指标见`per_episode_metrics.json`，聚合见`summary.json`。

## 实际比较了什么

三组均是ProWorkSim受管OpenHands，不含本轮REF。S1为1人；FREE2为2人自主协作；REVIEW2为开发者001＋独立复核者002。每队共享5M输入＋输出、512次模型尝试／决策上界；DeepSeek Flash非思考，131072上下文、98304输入、32768输出，temperature=top_p=1。最终代码只取001；不从两成员中择优。合法交付只取001最后真实合法提交；REVIEW2额外要求002实际采纳同一固定版本、执行公开测试、明确accept。

队内公平轮转、单writer，每个成员每次行动机会只完成一项动作；不是两个成员同时推理。跨题可并发。三组各成员基本文件和测试权限一致，S1有32个可见工具，双人各有38个；双人多出消息、交接、责任转移和review等入口。每人保有私有会话，不直接共享伙伴私有历史。所有组使用相同LLMSummarizingCondenser（max_size80、keep_first4、每成员独立历史、同模型同总池）；摘要作为衍生记忆，不是权威证据。结束自检每人最多一次，双人因此最多两次，总预算不重置。

## token成本应怎样解释

主体账本统计由统计同伴提供，本笔记不重复读取账本。统计结果表明平均单次输入三组均约5.3万token，差异主要在调用数，不是双人单次输入更大。源码和侧录支持：当前完整保留的私有上下文、工具schema、既有反馈会在后续请求再次进入输入；随着调用次数增加，累计输入扩大。不能将这些输入全部归为通信。

下列数据仅是可直接观察的通信／读取行为：

| 指标（40题合计） | S1 | FREE2 | REVIEW2 |
|---|---:|---:|---:|
| 成功send_message | 0 | 50 | 82 |
| 消息正文字符 | 0 | 96,026 | 103,844 |
| 消息正文独立内容token | 0 | 24,282 | 26,412 |
| 成功read_file | 559 | 773 | 631 |
| 返回的字符 | 1,238,008 | 1,678,233 | 1,468,845 |
| 同成员再次读取相同内容的重叠字符 | 216,842 | 203,652 | 173,441 |
| 跨成员读取相同内容的重叠字符 | 0 | 340,991 | 234,320 |
| 已观察到的读取结果进入模型输入次数 | 6,302 | 7,536 | 6,329 |
| 对应被观察到进入模型的独立读取事件 | 556 | 765 | 630 |

正文token采用原固定本地tokenizer对成功消息body独立编码，不包括chat模板、历史重复和其他观察，也不作为供应商费用。显式message正文体量不足以直接解释数千万级累计token差；组织状态、读伙伴代码、测试与发布流程及两套私有历史带来的请求开销可能重要，但没有隔离测得其净边际份额。跨成员读取重叠占返回字符的FREE2约20.3%、REVIEW2约16.0%；独立复核本来就可能需要重复读取，不能把这部分直接叫浪费。

重复输入的存在有实际侧录支撑：约556／765／630个不同读取事件分别出现6,302／7,536／6,329次。但117/120题缺完整presentation覆盖，因此次数是可观察下界，不能据此恢复全部实际重复token。

## 预算与交付边界

不能仅按顶层`all_members_stopped_or_no_reachable_event`归为自然结束；它可能包住成员的`model_budget_exhausted`或`team_budget_exhausted`。

| 指标 | S1 | FREE2 | REVIEW2 |
|---|---:|---:|---:|
| 明确模型／团队token预算边界 | 7/40（17.5%） | 30/40（75.0%） | 17/40（42.5%） |
| 其中最终代码通过 | 2 | 17 | 11 |
| 其他成员结束／等待且无明确预算边界 | 33 | 10 | 23 |
| code通过、delivery失败 | 2 | 2 | 5 |
| code失败、delivery通过 | 0 | 0 | 0 |

“其他结束／等待”不等于全部成功，也不表示合作已顺利完成。选定120回合没有现金截断或行政时间截断。9个code通过而delivery失败的回合全部遇到明确预算边界，因而不能把缺失交付独立归因于组织坏：预算和流程同时参与。

其中7题完全没有合法提交（S1 1、FREE2 1、REVIEW2 5）；另外2题已有合法提交但不是最终正确版本：S1 Matplotlib-22865／10060与FREE2 Pytest-7490／10072，旧合法提交评分失败、后来最终工作树通过。因此2/2/5不能直接改写为“这么多题从未提交”。九题逐项版本、锁及工具证据在`cases.json:gaps`。

REVIEW2的5个缺交付例子：Sphinx-8593／10001尚无固定补丁；Xarray-4687／10010有request_changes而无accept；Astropy-13579／10022临尾固定后handoff明确因剩余团队预算被拒；Pytest-10081／10042已认可过patch-1，但最终代码版本又不同且没有提交；Seaborn-3069／10210临尾才完成固定、伙伴采纳和测试，尚未review／提交。不能把它们全部简化成API不支持提交，也不能说复核本身必然造成失败。

## 三个有边界的病例

1. **有真实伙伴整合且最终代码通过：FREE2 Sympy-19954／10056。** 002固定patch-3，001显式integrate后成为v11；锁定最终代码的source_reference与该整合返回值完全一致，官方代码通过。旧v10合法提交也通过；最终工作树与旧提交不同，observer显示伙伴补丁没有进入既有合法交付链。该例证明实际整合发生，不证明它是本题通过的必要原因。
2. **正确代码但闭合被预算挡住：REVIEW2 Astropy-13579／10022。** 最终代码通过，001晚期才固定patch-1；handoff被明确拒绝“Recipient cannot receive new work under the remaining shared budget”，没有review或submit。这里有直接预算约束证据，不能单独归咎于复核组织。
3. **多轮公开测试仍未通过：REVIEW2 Seaborn-3187／10017。** 12次run_tests调用、9次回读，期间有公开测试通过，但最终官方代码和交付均失败，且团队预算终止。不同选择的测试不自动算重复浪费；只能说公开反馈和多轮检查没有保证最终正确性。另一个更直接的生成失误是Pytest-6197／10219：outcome[42]成功执行模型工具参数`write_file(..., text='placeholder')`，返回source v3和完整files摘要与最终锁一致，故placeholder不是导出器生成。证据在`pytest6197-model-write-provenance.json`。

## 仍未修复的测量问题

6个REVIEW2回合共有7条同类ObservationError：`Acceptance cannot turn failed or missing test evidence into passing`。执行World的accept要求采纳＋同版本测试真实执行，并不要求公开测试passed；侧录器却要求passed=True，属于观察语义与执行规则不一致。桥接代码先完成世界动作，再用`safely`捕获观察异常；不回滚动作、不重复模型。6题中4题最终代码及交付均通过，不能把这类测量错误算成生成失败。本轮只报告该缺口，未修改冻结实现。

21个独立恢复因原导出身份异常未调用observer.finalize，虽保留events，但不能补造coverage=True或“伙伴产物进入最终交付链”的完整观察值。与以上6题测量错误和摘要后来源映射缺失合并，导致通信净输入token无法完整分解。明确未统计：全部私有历史重复输入token、通信净边际成本、移除某协作规则后的因果增益、协作对正确率的单独因果贡献。

相关题目、错误明细和源码引用见`observer-error-evidence.json`；这与API500/503、闭合身份错误、官方评分传输问题是不同层次的问题。
