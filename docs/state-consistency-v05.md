# v0.5：内核状态一致性与有界恢复

本版继续完善经营模板与文稿微模板共同使用的工作世界规则。目标是在可信检查点之后，使基础事实、派生视图、工具许可与持久化结果有明确的一致性关系。范围不扩展到新行业、真实模型能力评价或参数训练。

本文说明实现合同及预先声明的实验协议，不记录正式实验成绩。实验结果、开发期失败、脚本修订、代码冻结身份与复验结论应分别保存在 `docs/experiments/`。下列实验数量是机制覆盖的组织方式，不是统计独立样本数。

## 1. 状态所有权：B、P、Q、O

`S = (B, P, Q, O)` 是本版的语义分类，不表示已经把存储拆成四个数据库。当前仍使用一个 JSON 状态快照、不可变版本文件和可恢复的当前文件副本。

| 分类 | 当前实现中的代表记录 | 所有权与用途 |
|---|---|---|
| B：基础事实 | 文件版本及哈希、正式 `attestations`、精确版本授权、工作定义、`work_replacements`、`requirement_events`、提交及其正式审阅、`artifact_edits`、条件定义与事件历史、`raw_condition_responses` | 由已授权动作或环境事件建立。派生过程读取这些事实，不反向创造批准、提交、回复或文件内容。 |
| P：派生视图 | 条件状态、兼容 blocker、当前工作状态、当前适用性、前驱就绪、结构上可执行的行动、回复满足关系 | 可从相同基础事实重新计算。已有缓存不决定新的解释。 |
| Q：运行记录 | `events`、`event_history`、`operation_commits`、`state_revision`、事件身份、操作负载摘要 | 区分已提交效果与仍待处理的事件，支持单写者环境中的有限重试与恢复。 |
| O：已保存的实际观察 | 消息正文、交互输入与工具返回、交互读取/写入引用、`knowledge` 中的读取记录、运行器另行保存的观察与模型调用记录 | 保留工作人员当时实际获得的内容。重建当前视图不重写已有工具返回、不增加读取收据、不重发消息。 |

同一现实事件可以同时有不同用途的记录。例如，原始回复是收到过什么的事实；它对某个条件是否有满足作用，是派生关系。`interactions` 也同时承担运行证据和已保存观察的用途。分类要求明确字段的解释权，不要求物理上所有记录严格互斥。

当前 `observe()` 会在内存中重建视图，再返回角色可见信息；调用本身不把新的观察对象追加到状态文件。因此，本版不宣称每次读取观察接口都自动形成一份永久观察快照。已存在的交互、消息和读取记录仍必须保持原样。

独立评价记录不参与上述制度事实的创造。即使评价器发现内容错误，有权审阅者已经作出的批准仍然存在；评价结论与制度决定分开报告。

## 2. K1：转换回执准确区分阶段与字段区域

### 2.1 实际阶段差分

`core.transitions.execute_transition()` 保存三个状态边界：

1. `before`：进入该次业务转换、执行 Apply 之前。
2. `after_apply`：适配器动作或事件处理函数执行之后。
3. `after_derive`：共享与模板派生过程执行之后。

回执版本为 `phase-deltas-v0.5`，语义版本为 `work-world-v0.5`。

| 字段 | 准确含义 |
|---|---|
| `apply_delta` | `before → after_apply` 的实际变化路径。 |
| `derive_delta` | `after_apply → after_derive` 的实际变化路径。 |
| `net_delta` | `before → after_derive` 的净变化路径。 |
| `primary_region_changes` | 上述净变化中不在声明派生区域内的路径。 |
| `projection_region_changes` | 上述净变化中在声明派生区域内的路径。 |
| `state_digests` | 三个阶段边界的规范化 JSON 摘要。 |
| `effect_refs` | 此次业务转换新建的产物版本引用；不是所有外部副作用的通用清单。 |

“哪个阶段产生变化”和“变化落在哪类字段”是两个维度。若 Apply 把视图从 `0` 写成 `1`，而 Derive 不再修改，回执应同时显示 Apply 变化和派生区域净变化。若 Apply 写成 `1`、Derive 又写回 `0`，两个阶段差分都存在，而净差分可以为空。

这些 delta 当前是变化路径列表，不包含所有旧值与新值，不能当作足以重放整个世界的补丁。字典通常细分到字段；列表内容发生变化时可记录其所在路径。

### 2.2 Preflight 与持久化边界

`World.act()` 先加载已提交状态、恢复文件，再进行一次 `_preflight()` 视图重算。Preflight 用于避免旧缓存进入工具判断；它发生在业务转换的 `before` 之前，并单独记录为 `preflight_projection_delta`。它不应被误认为工作人员动作产生的新业务效果。

业务转换完成后，运行器还会推进逻辑时间、追加交互、安排由动作触发的环境事件、登记操作身份及提交修订号。这些运行器记账动作位于 `execute_transition()` 的阶段快照之外。因此：

- `net_delta` 是该次业务 Apply/Derive 的净变化，不是最终 `state.json` 全部字段的净变化。
- `state_digests.after_derive` 不是最终持久化状态文件的摘要。
- `committed_revision` 标识随后共同提交的状态修订，不能把它解释成阶段快照已经包含日志自身。

底层转换最初返回 `execution_outcome="applied_uncommitted"`。只有运行器登记操作并保存状态之后，回执才具有已提交修订号。正式操作记录包含 `transition_id`、`bound_actor`、`request_digest`、`pre_state_revision`、`semantics_version`、`committed_revision` 和 `execution_outcome`。

如果普通工具执行被拒绝，业务效果会回滚，但拒绝尝试、逻辑时间及交互仍可作为一次状态修订提交。此时公开结果可同时出现 `ok=false` 与 `command_committed=true`，回执为 `rejected_attempt_committed`；含义是“尝试已记录”，不是“业务动作成功”。

`ActionFrame` 限定允许改变的业务路径与派生路径。Derive 不得写出声明的派生区域；历史版本事实、正式确认、已完成审阅、提交固定字段、原始回复和追加式历史另受保持检查保护。部分适配器目前仍在 Apply 内刷新投影，本版准确记录其实际阶段，不宣称所有缓存写入都已经移动到 Derive。

v0.4 回执保留原格式和原含义。历史 `direct_changes/derived_changes` 不事后改写成 v0.5 的阶段轨迹。

## 3. K2：条件与当前工作的纯投影

### 3.1 唯一的重建方向

本版提供：

```python
derive_condition_view(state)       # 返回条件视图，不修改输入
derive_current_work_view(state)    # 返回包含历史项的工作视图，不修改输入
rebuild_projections(state)         # 仅覆盖声明的兼容缓存
```

权威方向为：

```text
条件定义、绑定与事件历史 + 原始回复及接收时事实
  → condition_view
  → blocker 兼容投影

工作定义、替代关系、提交/审阅、实际编辑事实 + condition_view
  → current_work_view
  → work_item 兼容状态字段
```

`blockers` 不反向决定条件是否满足。`condition_responses` 是可重建的满足结果缓存，不是回复事实的唯一来源。

当前工作视图区分：是否仍是当前义务、状态摘要、需求适用性、待解决条件、当前前驱是否被接受，以及结构上可用的 `submit/withdraw/approve`。公开工具观察还按工作所有者和制度权限过滤行动。行动列表不是对所有参数、文件可见性或业务质量检查的预先保证；真实工具仍检查提交身份、版本及其他参数约束。

旧工作已有的批准可以保持 `accepted`，同时 `is_current=false`、`applicability="superseded_requirements"`。这三个维度不能合并为“旧批准被取消”。没有提交的工作是否已开始，由明确的 `artifact_edits` 记录决定，不以旧 `status` 缓存作为依据。

经营模板创建初始工作时，将正式 `required_basis` 同步绑定为共享内核使用的 `required_credentials`。需求替代也沿用该关系。短回答任务按其合同创建，不因存在 `basis` 对象就凭空增加批准要求。

### 3.2 明确可删除与改坏的缓存

E1 所干预的范围由 `core.projections.projection_paths(state)` 在每个未修改检查点上展开并记录：

| 路径 | 被声明为缓存的字段 |
|---|---|
| `condition_specs.<id>` | `status`、`unavailable_providers`、`resolution_ref`、`response_checks` |
| `work_items.<id>` | `status`、`blocker`、`blocker_ids`、`applicability` |
| `blockers` | 整个兼容映射 |
| `condition_responses` | 整个回复满足结果映射 |

条件定义、绑定、`history`、`raw_condition_responses`、工作替代关系、`artifact_edits`、提交与审阅、文件版本和正式确认均不在此可删范围内。

产物 freshness、按工作上下文的依据适用性以及文稿策略适用性仍有各自派生过程。E1 的上述缓存干预范围不等于“删除任意世界字段都能恢复”，也不等于对所有领域派生字段完成了穷尽证明。

### 3.3 回复保存接收时事实，不保存不可质疑的正确结论

`apply_response()` 把每一条实际处理的回复存入 `raw_condition_responses`，包括未满足条件、依据不足与迟到的回复。其身份不得以不同内容复用。

原始记录包含回复负载、`received_at`、`received_sequence`，以及有限的 `receipt_context`：

- 接收时的组织授权配置。
- 回复引用的对象版本元数据及对应正式确认。
- 当时的条件证据要求、上下文、提供者、版本和权力要求。
- 工作替代关系、需求版本，以及是否已经存在批准或取消。

这份上下文保存的是当时可检查的事实，不是预存一个必定应为 PASS 的判断。纯投影沿条件本地事件顺序重新执行关系判断。同一逻辑 tick 内后发生的确认或需求替代，不应改变先前回复到达时的效力；已在旧要求下满足的条件也不因后来换代而被抹除。

如果条件历史引用的原始回复缺失，重建显式报错，不从私有规格补造回复。证据引用、正式确认或适用上下文不足时，相关关系保持未评或失败，不能自动制造正式批准。历史工具返回与消息内容始终作为原观察保留。

## 4. K3：单世界、单写者的提交与恢复协议

### 4.1 操作身份与负载冲突

世界写入受 `fcntl.flock` 保护。命令身份为 `command:<actor>:<request_key>`；没有提供键时生成新身份。因此，调用方需要重复使用同一个键，才能表达同一次命令重试。命令键按 actor 分域；不同 actor 使用同一文本键不等于同一个命令身份。

请求摘要使用排序键、确定分隔符的 JSON SHA-256，覆盖动作名与参数；actor 另由操作记录绑定。事件身份为 `event:<event_id>`，事件摘要覆盖其身份、类别、计划时刻与负载。

- 相同操作身份、相同 actor、相同摘要：返回已提交的公开结果，不再次创建该操作的正式效果。
- 已存在操作身份与不同负载冲突：明确返回 `CommandConflict`，不静默返回旧结果。
- 原命令重试仍可处理尚未完成的到期环境事件；这不构成原命令的第二次执行。

`operation_commits` 与业务效果、状态指针放入同一次 JSON 状态保存。`state_revision` 连续递增；启动恢复核对可信检查点之后的日志修订前缀和操作身份关系。这是检查点上的操作日志，不是脱离检查点即可还原所有基础事实的完整事件溯源。

### 4.2 命令提交与事件提交相互独立

运行顺序为：

```text
加载已提交状态并恢复文件
→ Preflight
→ 命令 Apply/Derive
→ 命令交互、身份与状态一起提交
→ 逐个执行到期事件
→ 每个事件各自登记身份、结果并提交
```

同一到期时刻按队列插入顺序执行，不以随机事件 ID 排序。事件审阅发现提交已撤回或被替代时，可以提交明确的 `superseded` 处理结果，而不是再次批准旧提交。

如果命令已经提交，但随后某个环境事件处理失败：

- 命令返回保留 `command_committed=true` 和其原有业务结果。
- 错误由 `pending_event_errors` 单独描述，失败事件标为尚未提交。
- 失败事件及其后的有序待处理部分保留，等待后续显式恢复或命令重试。
- 不把“事件尚未完成”包装成“先前命令从未提交”。

`World.recover()` 从当前已提交状态恢复文件，重建内存视图并处理到期事件；它不会重新运行工作人员策略。已记录操作的重复事件仅确认队列状态，不产生第二次正式效果。

### 4.3 版本文件与状态指针共同属于已提交前缀

`Store.put()` 先写不可变版本文件，再更新当前文件副本；`state.json` 通过临时文件、文件 `fsync` 和 `os.replace` 保存。进程在文件写入后、状态提交前退出时，磁盘可能暂时存在未被已提交状态引用的版本。

恢复时以已提交状态为权威：

1. 核对状态内操作日志的连续修订关系。
2. 将未被状态引用的版本目录移到 `control/uncommitted/`，不把它们当作正式新版本。
3. 核对每个已提交不可变版本的文件哈希；缺失或损坏不能用猜测内容替代。
4. 当前物化文件与已提交指针不一致时，从已提交不可变版本恢复其字节，不重新计算业务答案。

保留未提交目录用于检查，不意味着它们是正式历史版本，也不承诺该目录承担永久追加式审计档案的职责。

故障注入挂点包括 `version_staged`、`after_apply`、`after_command_commit`、`before_event_commit`、`after_event_commit`。它们用于限定范围内的子进程中断实验；普通异常回滚与进程直接退出应分别记录。

## 5. 预先声明的实验矩阵

正式运行前冻结代码、脚本及协议。各组使用新输出目录，记录源码身份、脚本摘要、原始状态或必要检查点以及明确的检查分母。开发期失败不可由后续复验覆盖；构造失败或未执行比较应与实际语义不一致分开计数。

| 组别 | 计划对象与边界 | 预声明验收 |
|---|---|---|
| E1：派生重建 | 两个真实模板，各 6 个检查点；每个检查点使用正常、删除声明缓存、错误缓存、重复重建四个副本，共 48 变体 | 每变体检查纯查询无修改、视图相同、基础事实保持、版本与物化文件字节保持、实际观察相同、重建幂等，共 288 项。 |
| E2：适配器符合性 | 两条抽象轨迹 × 两个模板，共 4 个真实工具世界；另设一个明确分开的共享内核范围确认 fixture | 11 个跨模板标记比较、16 项世界内检查；组件 fixture 检查 A 确认允许、B 拒绝及无额外事实，共 4 项。合计 31 项，不能将组件 fixture 称为第五个适配器世界。 |
| E3：有界序列 | 两角色、两工作、两产物，A 为 B 的前驱；工作版本与产物版本各不超过 3；深度最多 4；两个初始检查点 | 用不同表示的独立参考账本对照共享组件；报告唯一访问状态、尝试转换、拒绝类型、边界截断及最短反例，不以“路径全部枚举”表述去重探索。 |
| E4：故障与恢复 | JSON 写入、提交、回复事件、依据修订 4 类操作；4 个无中断控制世界、10 个冻结故障组合 | 每故障 6 项检查，共 60 项：实际到达退出点、已提交前缀一致、状态等同控制、文件字节等同控制、命令结果等同控制、第二次重试无效果。 |
| E5：语义负对照 | 7 个事先命名的错误规则；每个控制版本与突变版本分别运行在新 Python 子进程 | 先确认控制版本可通过，再确认错误版本触发预先指定的失败；区分检出、幸存和实验脚本异常。不是任意缺陷覆盖率或生产恢复正确性证明。 |

E1 检查点为 `initial`、`pending_reply`、`in_review`、`withdrawn`、`revised`、`late_reply`。全部先经真实工具建立，再复制世界；只对事先展开的缓存路径进行实验干预。

E2 的两条轨迹边界为：

```text
ConfirmGrant → Submit1 → Withdraw → Submit2 → Approve
ConfirmGrant → OldRequest → ReviseLateReply → NewReply → Submit → Approve
```

初始 `ConfirmGrant` 是编译器建立的正式 bootstrap；第二条轨迹另先完成一次请求/回复，以建立相同的可见依据起点。这不等于声称经营模板存在一个在实验中实际调用的通用 Confirm 工具。

经营回复由到期事件触发，文稿回复由编辑者工具触发，因此 `ReviseLateReply` 是明确的宏边界。比较不要求两个模板拥有相同工具次数或内部事件时刻，也不修改队列时间来制造一致。

跨模板只比较预声明的共同制度关系。工作、凭据、请求与条件 ID 使用显式别名，角色按该制度动作中的职责映射；业务正文、文件格式、产物数量与时钟不参与领域间相等比较。工作状态、条件状态与正式决定直接比较。运输标签 `outdated_reply/delivered` 保存在原始记录中，共同关系分别查询“是否记录回复”和“请求是否指向当前义务”，不将两个标签强制改写为同一枚举。

E3 只覆盖内存 `core.work/core.conditions`；编辑作为明确的外部版本元数据输入，不替代真实文件工具测试。动作集合为 `submit/withdraw/approve/revise/reply/edit`，包括错误角色、旧工作、错版本、重复回复与缺前驱等邻近非法动作。它不生成任意新请求、任意组织或任意图；历史非交换动作按各自顺序解释，不要求撤回、批准、修订可交换。

E4 的冻结故障矩阵如下。每类操作先建立一个真实工具检查点，再逐字节复制到无中断控制和故障世界。

| 操作 | 中断挂点 | 故障数 |
|---|---|---:|
| JSON 文件写入 | `version_staged`、`after_apply`、`after_command_commit` | 3 |
| 提交 | `after_apply`、`after_command_commit` | 2 |
| 回复事件 | `before_event_commit`、`after_event_commit` | 2 |
| 依据修订 | `version_staged`、`after_apply`、`after_command_commit` | 3 |

故障子进程使用 `os._exit(73)`，不会执行 finally 清理或内存回滚。恢复后使用相同 command key 重试，并与无中断控制比较完整状态；规范化只去掉 `wall_seconds` 和包含时长差异的诊断 `state_digests`，其他身份、业务事实、投影、日志结果与已保存观察均保留。同时比较每个已提交版本及当前物化文件的字节摘要、公开命令结果与再次重试前后的完整状态。写入类检查点包含通过真实工具写入的错误公式 `=1/0`；恢复不应修正这段历史字节。负载冲突等额外协议属性由对应单元检查验证，不计入上述 60 项恢复验收分母。

E5 的 7 个规则突变为：v2 授权额外泄露 v3、回复影响另一项工作、用全局最新版本替代上下文凭据、批准忽略当前前驱、重复事件产生第二次正式效果、Derive 改写基础事实、需求修订重写旧答案。突变仅在实验子进程中注入，不改写生产源文件。

## 7. 受测范围与明确边界

- 恢复从一份可信 JSON 检查点和已提交不可变文件出发。日志身份与修订连续性检查不是密码学防篡改证明，也不能补回已经丢失的基础事实。
- 支持范围是当前文件存储、当前工具与事件、单世界的受锁写入者。没有跨机器共识、分布式事务或任意插件外部副作用的 exactly-once 承诺。
- 子进程退出挂点不等于模拟所有硬件故障。当前原子写使用文件 `fsync` 与替换，本文不据此宣称经过断电、磁盘控制器或网络文件系统耐久性验证。
- 重建视图不重新发邮件、不重新读取文件、不重新批准，不通过评价器补业务答案。文件恢复只恢复已提交版本的字节。
- 已授权的错误内容和错误批准仍可存在。有限内容合同、制度许可、领域独立正确性与专业工作真实性不能相互替代。
- 本版不宣称任意旧版本世界都可以删去旧状态后重建成相同 v0.5 语义。旧实验与旧回执保留其原版本解释，不为兼容旧布局放松新的基础事实合同。


## 本轮边界复核补充

- 新运行器只接受当前 schema 0.5；旧检查点须使用对应冻结运行器或未来明确导入，不能静默把旧缓存当新事实。
- 待审事实用 pending_submission_id/submission_state 独立表达，批准还需匹配当前版本／凭据。前驱等待不阻止 owner 撤回真实待审提交。
- 非有限 JSON 在身份摘要形成前拒绝，不把截断 repr 当请求标识。
- 普通异常若发生在事件保存之后，只记录 event_delivery_errors，重新载入已提交状态；不得执行提交前回滚。失败事件尝试作为 event_attempts 诊断保存，不产生第二次正式业务效果。
- E4 原十个 os._exit 切点分母保持不变；另预注册一项保存后 ValueError 确认异常探针（4 检查），避免把进程终止覆盖误当成普通异常覆盖。
