# 三、需要修订的是停止层级，而不是把真实缺陷改名成“没有问题”

## 1. 当前代码把不同性质的问题合并成了全局停止

冻结`stop_decision`将以下项目放进同一组`violations`：

- 页面、权限或版本异常；
- 实际输入投影异常；
- 已有后续生成但应有反馈未呈现；
- `context_blocked_feedback_ids`。

任何一项出现，就产生`mechanism_fault`，暂停所有未开始槽。代码忠实实现了原协议，不能称为本轮监督器错误。

但作为后续研究政策，这个作用域过于统一。

| 问题 | 是否还能信任记录 | 应优先影响什么 |
|---|---|---|
| 已知请求过长，执行前拒绝、无输出和收费 | 可以，前提是绑定完整 | 当前成员的可继续性 |
| 团队预算不足，正常拒绝 | 可以 | 当前episode的资源范围 |
| 已发生后续生成，却漏掉规定反馈 | 需要调查 | 实际输入正确性 |
| 越权效果、身份或结果被污染 | 可能不可以 | 执行安全与完整性 |
| 共同服务或存储损坏 | 可能影响多个槽 | 全局执行 |

**一个成员不能继续，不必然意味着其他独立episode不应该开始。**把二者绑定，会让整个面板是否完整取决于某条先发生的轨迹、其反馈体积和并行时序，而不是只取决于原任务清单。
