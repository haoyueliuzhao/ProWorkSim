> 六组属性来自首轮通过证据；组合属性来自修正后的单项复验。

# 三、本次确认的一处记录口径限制：回执不是实际的阶段差分

这不是推翻本轮世界结果的缺陷，但它与下一轮的重算和恢复直接相关，建议先处理。

## 1. 当前代码实际怎样划分变化

`execute_transition()` 保存了：

```python
before
applied
state_after_derive
```

但最后的回执不是分别比较这三个状态，而是先取得**最终净变化**，再根据字段是否属于 `derived_paths` 分类：

```python
direct_changes  = 不属于派生区域的最终变化
derived_changes = 属于派生区域的最终变化
```

也就是说，分类依据是**变化落在哪里**，不完全是**变化发生在哪个阶段**。

## 2. 本次实际执行的刻画结果

使用原始函数构造：

```text
初始：base=0，view=0
Apply：把 view 改为 1
Derive：不做任何修改
```

其中 `view` 被声明为派生区域。

得到的回执是：

```json
{
  "direct_changes": [],
  "derived_changes": [["view"]]
}
```

**它准确表达了“派生区域发生净变化”，却不能证明“这个变化由 Derive 执行产生”。**

这个测试是一个内核接口刻画，不是声称已在真实工作人员路径中造成了错误批准或文件损坏。

## 3. 为什么要在下一轮处理

本轮行动合同写的是“记录 Apply 与 Derive 的实际效果”。如果继续使用现在的字段含义，后续容易将它误读为阶段级因果记录，或者用它定位恢复点。

建议明确保存三种差分：

\[
\Delta_A=\operatorname{diff}(S_{\text{before}},S_{\text{after apply}})
\]

\[
\Delta_D=\operatorname{diff}(S_{\text{after apply}},S_{\text{after derive}})
\]

\[
\Delta_{\text{net}}=\operatorname{diff}(S_{\text{before}},S_{\text{final}})
\]

字段所属区域可以另行记录：

```text
primary_region_changes
projection_region_changes
```

**执行阶段与字段类别是两个维度，不应继续用同一组字段同时表达。**

迁移时不必立即禁止 Apply 更新所有旧投影。可以先准确记录，再逐个移除适配器中的提前刷新和重复状态推进。旧回执保留原格式与版本，不能事后改写成新的阶段轨迹。

# 四、当前内核的主要不足，不是规则数量，而是“状态解释权”还没有完全收敛

本轮已经做到了很多共同函数的抽取，但尚未完全实现：

> 同一份基本事实，只能导出一种工作状态解释。

这也是报告已经承认的范围限制，不应重新包装成隐瞒的问题。

## 1. 生命周期状态仍然由多个位置共同维护

例如：

- `core.work` 更新提交、撤回、批准和替代工作的状态；
- `core.conditions` 在回复满足后尝试重开工作；
- 经营工具门面的 `_put()` 会把工作从 open 改为 in_progress，或使待审提交失效；
- 文稿适配器在创建请求时，直接创建条件、blocker，并把工作置为 blocked。   

这些路径目前可以在已测序列中协同工作，**但共享函数的存在，尚不能保证所有适配器对状态的解释永远一致。**

下一轮需要减少的是这种重复的解释权，而不是再把文件拆得更细。

## 2. “共享查询”与“共享决策”还可以进一步统一

当前 `submit`、`approve` 与公开 `dependency_readiness` 已经共同使用当前前驱解析，这是正确进展。 

下一步应继续确保：

> 观察界面说工作已就绪、回复处理决定重开工作、提交前置检查允许执行，三者依据相同的当前事实和关系。

否则，可能出现“界面显示 open，但提交因为另一套状态判断而拒绝”，或者“条件已经满足，但兼容 blocker 仍阻塞”的分歧。

**这不是要求把所有事实压成一个 `status` 字段。相反，应当把几个独立维度保留下来，再生成界面需要的状态摘要。**

## 3. 当前范围不需要完整事件溯源数据库

`STATE_OWNERSHIP.md` 已明确：部分状态仍以 JSON 快照保存，不宣称仅靠日志能重建所有文件和状态。

所以，本轮不应因为没有完整事件溯源而判失败。下一轮也不必直接迁移数据库或建设分布式事务。

**更合适的目标是：从一个明确可信的检查点出发，对新增动作和有限派生关系提供统一的重算与恢复协议。**

# 五、建议将下一轮定位为：基础事实—派生视图—执行结果的一致性

我建议使用以下工作名称：

## **v0.5 内核状态一致性与有界恢复**

它继续完善当前“工作世界底层规则”，不增加新的业务方向。

一个有用的状态分解是：

\[
S_t=(B_t,P_t,Q_t,O_t)
\]

这里是建议的设计，不是当前代码已经完成的结构。

| 部分 | 内容 | 关键约束 |
|---|---|---|
| \(B\)：基础事实 | 文件版本、正式确认、真实提交、制度审阅、需求修订及其关联 | 不由评价器或缓存反向创造 |
| \(P\)：派生视图 | 当前工作、就绪条件、上下文适用性、状态摘要 | 能从基础记录重新计算 |
| \(Q\)：运行记录 | 排队事件、已提交标记、幂等记录和处理进度 | 决定恢复后还有哪些效果需要执行 |
| \(O\)：实际观察 | 工作人员实际得到的消息、工具返回及读取记录 | 新投影不能改写旧观察历史 |

派生过程写成：

\[
P_t=D(B_t,\text{clock}_t,\text{policy version},\text{context})
\]

### 两个特别重要的限制

**第一，制度决定仍是基础事实。**一个有权编辑批准了错误文稿，这个批准不应在重算时因为独立评价失败而消失。

**第二，重算不等于重新执行。**重算不能生成新文件、发出新邮件、增加一次批准或补一条读取收据。它只能重新解释已经成立的事实。

这与项目最初“先让工作世界成立，而不以训练收益作为当前验收条件”的定位保持一致。:chatgpt-content-reference{index="17"}

# 六、先实现三个小工作包，而不是全面重写

## K1：精确的转换回执和提交边界

每次工具动作与每个环境事件，都应有独立的转换身份和结果。

建议记录：

```text
command_id / event_id
bound_actor
request_digest
pre_state_revision
semantics_version
apply_delta
derive_delta
net_delta
effect_refs
committed_revision
execution_outcome
```

这里不要求每条回执存一份巨大快照。可以保存有限差分和不可变对象引用。

更重要的是区分：

> 工作人员动作已经提交，但随后到期事件处理失败。

与：

> 工作人员动作本身没有提交。

目前运行器确实先持久化动作，再处理到期事件；后续恢复协议应保留这个边界，不能把两者混成一个笼统的“工具失败”。 

## K2：先统一两个纯投影

建议优先实现：

```text
derive_condition_view(...)
derive_current_work_view(...)
```

`condition_view` 回答：哪些条件未解决、哪些回复满足了什么、是否仍有配置内的获取机会。

`current_work_view` 回答：当前实例是谁、当前前驱是否满足、是否存在待审提交、哪些条件阻塞执行、哪些行动在制度上可执行。

它们不回答“下一步最聪明的行动是什么”，也不泄露参考答案。

对于兼容 blocker，必须明确一种权威关系。例如：

```text
条件定义＋实际回复记录 → condition_view → blocker 兼容投影
```

不能同时允许：

```text
condition.status 决定 blocker.status
blocker.status 又反过来决定 condition.status
```

否则所谓重算会变成两份缓存互相纠错，而不是从基础事实推导。

## K3：单世界、单写者、有限工具的恢复协议

范围先固定为现有存储和工具，不扩张到跨机器共识或任意插件副作用。

建议要求：

**相同标识、相同负载重试，不产生第二次正式效果。**

**相同标识、不同负载，应显式冲突，而不是静默返回旧结果。**

**恢复后的文件版本、状态指针、提交记录和事件结果，属于同一个已提交前缀。**

这里可以继续使用 JSON 快照和不可变版本目录，只增加必要的操作记录、完成标记和启动核对。没有必要为了“内核化”立即换成复杂数据库。

# 七、下一轮实验方案

建议五组实验围绕同一套内核建设展开。它们的数量是**机制覆盖组织方式**，不是统计独立样本数，也不是必须一次全部完成的授权。

## E1：派生视图重建与缓存无关性

### 要检验的命题

> 在基础事实、时间和规则版本相同的条件下，派生结果不应取决于旧缓存内容或此前调用过哪些查询接口。

### 实验方法

在两个模板中，各自选择其**已经支持**的状态检查点，例如初始、未授权、请求待回复、待审、撤回、需求替代、当前前驱尚未完成、旧回复晚到等。

对每个检查点建立副本：

| 条件 | 操作 |
|---|---|
| 正常缓存 | 直接查询 |
| 无缓存 | 删除预先声明的派生字段，再重算 |
| 错误缓存 | 将这些派生字段置为不一致状态，再重算 |
| 重复重算 | 连续运行两次派生过程 |

验收应包括：

\[
D(B)=D(B;\text{任意旧缓存})
\]

以及重算后再次重算不改变结果。

同时核对基础事实、文件、消息、批准和观察记录不变。**只能删除事先声明为派生的字段，不能把删坏基础事实也解释成“缓存重建”。**

若依据不足，应得到 unknown／未评或显式恢复错误，不能借隐藏规格补足。

### 本组的价值

它比再运行几十个随机种子更直接地检查：内核是否已经摆脱多套状态各自推进的问题。

---

## E2：两个适配器对相同抽象轨迹的符合性

### 要检验的命题

> 在业务对象名称和文件形式不同的情况下，相同的制度关系应产生一致的制度后果。

选取已有抽象轨迹，例如：

```text
Confirm → GrantVersion → Submit → Withdraw → Submit → Approve
```

以及：

```text
Confirm(r2) → ReviseRequirement
→ LateReply(r1) → NewReply(r2)
→ Submit → Approve
```

分别实例化到经营模板和文稿模板。

比较的是共同语义：

**授权了哪个版本、满足了哪个条件、哪项工作成为当前义务、哪个提交被撤回或批准、历史保持了什么。**

不比较两个领域的文件字节，也不要求它们具有相同质量标准。

角色测试可以比本轮改名再前进一步：使用当前已经支持的范围授权，设置“对工作 A 有确认权，对工作 B 没有确认权”。这仍是静态制度测试，不必引入动态撤权。

### 重要要求

相同抽象轨迹不能由同一段测试代码偷偷替两个模板补齐不同状态。应分别经过它们真实的工具适配入口，再在事先定义的语义投影上比较。

## E3：有界动作序列与独立参考状态机

本轮七组属性提供了有价值的见证，但仍主要是人工挑选的路径。下一步可以在很小的范围内，系统探索动作组合。

建议初始边界为：

```text
2 个角色
2 项工作
2 个产物
每对象至多 3 个版本
先探索长度不超过 4 的动作序列
```

是否扩到长度 6，应根据第一批状态数量和覆盖缺口再冻结，不必预先追求大规模。

生成器应同时产生合法行动和邻近的非法变体，例如错角色、旧工作、错版本、重复请求和缺前驱。

### 参考模型必须独立

可以用更简单、不同表示的小型状态机作参考，但**不能调用被测的 `current_id`、`approve_submission` 或 `match_response` 来计算期望结果**。否则只是两次调用同一个实现。

输出应记录访问状态数、尝试转移数、拒绝类型、截断边界及最短反例，而不是只报告“多少条通过”。

### 不要把非交换动作当成错误

独立对象写入可以比较预先声明的业务投影；涉及同一提交的撤回、批准和修订，则应按顺序分别满足合同。

\[
T_a(T_b(S))\neq T_b(T_a(S))
\]

对很多工作动作是正常现象。真正要检查的是：**每种顺序的后果是否有明确、稳定的语义。**

## E4：单写者范围内的故障注入与恢复

这组实验不是生产级灾备，而是检查当前执行模型能否承担自己的状态后果。

建议选择版本创建、提交、回复和需求修订作为代表，在下列位置注入进程中断：

| 中断位置 | 恢复时需要判断什么 |
|---|---|
| 文件已暂存，状态未提交 | 不得把孤儿文件当成正式新版本 |
| 内存状态已变化，尚未持久化 | 应恢复到明确的旧提交前缀 |
| 动作已提交，结果尚未返回 | 重试不能重复创建正式效果 |
| 事件已到期，效果尚未提交 | 事件不能无故丢失 |
| 事件效果已提交，交付确认尚未完成 | 重试不能重复批准、授权或解除条件 |

每个故障运行与一个不中断对照比较。

比较对象应包括基础事实、不可变文件、请求与事件状态、正式决定以及对外返回，而不只是最终 `complete`。

**恢复不能修正工作人员写错的公式，也不能重新采样模型来重建旧观察。**否则测试的是“重新做了一遍任务”，不是恢复。

通过结论也必须限定在测试的单写者、文件系统和切点范围内，不宣称获得了任意并发的“恰好一次”保证。

## E5：给验收本身设置错误实现负对照

这组实验很重要，因为本轮已经说明：**验收脚本也会错，测试全绿不自动意味着测试足够敏感。**

在隔离副本中，植入少量明确违反现有合同的变异：

| 故意引入的错误 | 应当被哪个机制发现 |
|---|---|
| 授权 v2 时同时开放 v3 | 精确版本访问检查 |
| 回复解除另一项工作的阻塞 | 局部性检查 |
| 用全局最新代替上下文适用性 | 适用关系检查 |
| 批准时不检查当前前驱 | 工作就绪检查 |
| 重复事件追加第二次正式效果 | 幂等与恢复检查 |
| Derive 修改基础事实或文件 | 状态归属与保持检查 |
| 修订后重写旧提交答案 | 历史保持检查 |

每个变异在运行前就应指定“必须触发的具名断言”。

存活变异应记录为验收盲点，不能在看到结果后删掉，或者将其重新归类为无关情况。

这不需要实现一个大型自动变异框架；先做少量有语义目的的负对照，就能显著提高我们对验收体系的信任。

# 八、怎样组织验收，避免又变成无止境的工程审计

建议按下面的顺序推进，而不是一次把五组实验全部堆上去：

\[
\boxed{
\text{回执语义}
\rightarrow
\text{两个纯投影}
\rightarrow
\text{双模板符合性与短序列}
\rightarrow
\text{有限恢复}
}
\]

负对照伴随各阶段加入。

每一阶段的结论只回答当时声明的问题：

| 阶段 | 足够的通过依据 | 不应追加的要求 |
|---|---|---|
| 回执修正 | 阶段差分与实际执行相符，旧格式不被改写 | 全量历史迁移 |
| 投影统一 | 指定视图能重算、幂等且不改基础事实 | 所有世界对象完整日志溯源 |
| 双模板符合性 | 共同动作的制度语义一致 | 第三行业或专业质量认证 |
| 有界序列 | 冻结边界内无未处理反例 | 无限状态证明 |
| 故障恢复 | 指定切点恢复到正确提交前缀 | 跨机共识、断电持久性或任意插件事务 |

当前静态组织配置、有限领域规则和不完整专业评价，都应继续作为范围限制保留，不必成为本轮的阻断项。

相反，**在已声明范围内出现“公开就绪与提交许可矛盾”“同一回复重复产生正式效果”“恢复后指针与版本不一致”**，才是需要阻断相应门槛的具体问题。

也不要把所有计数加成一个总分。代码断言、属性组、世界终态、制度批准与独立质量结果，继续分别报告。

# 九、对当前内核路线的进一步判断

你之前提出的“物理法则之于物理引擎”的问题，到这一版已经有了更明确的答案：

**内核不是职业任务的正确解题流程，而是行动后果的统一解释器。**

v0.4 已经初步回答：

> 谁能够确认什么；哪个版本适用于哪个工作；什么回复能够满足什么条件；提交、撤回和修订分别留下什么历史。

下一版应该进一步回答：

> **即使从不同适配器进入、缓存被清空、动作顺序变化或执行中断，这些事实是否仍然具有相同含义？**

这才是底层规则稳定性的下一层证据。

因此，我建议保持现有经营模板和文稿微模板，不再扩张业务对象，也不把训练重新设为近期目标。**先使同一份事实在查询、执行、观察和恢复四条路径上获得一致解释，再谈更丰富的模拟工作世界。**

本轮成果应保留；下一轮需要深化的不是“场景数量”，而是**内核的状态一致性、组合语义与恢复边界**。
