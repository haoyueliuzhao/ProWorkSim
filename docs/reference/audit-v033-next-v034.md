# 二、对0/16的解释需要落到三个不同问题上

## 1. 六份固定交付失败，不只是提交手续的问题

六份交付全部通过公开七项检查，但独立内容验收全部失败。其中两份Devstral交付已经满足规定的load/dump路径，内容仍然不正确。

因此：

> **取消API过程要求、放宽提交备注或自动补交付，都不能使这六份已测成果变成正确结果。**

实际缺口包括未知字段处理、精度、非法金额语法、默认值和完整加载状态，而且不同槽的原因不完全相同。报告对“某槽只少了一条0.01记录”和“另一槽还存在大数精度损失”的区分是必要的，不能用一种静态解释覆盖所有失败。

这些义务原来已经公开，应保持原分数。后续设计小任务，可以减少新合同的领域负担，但不能回头删除旧合同要求，再说模型能力提高。

## 2. 十份未提交，不能被当成已经测过内容的失败代码

当前正确分母是：

\[
\text{完整交付}=0/16,\qquad
\text{已提交内容通过}=0/6,\qquad
\text{未提交内容未知}=10.
\]

十条未提交都发生在token预算停止的episode中，但没有独立验收对象，不能断言“最后代码已经正确，只差提交”，也不能补测可变工作区后替换原episode结果。

还有一个报告细节建议继续改进：settings异常时没有输出`source_api_used`，可以按原完整合同判为“未证明满足”，但**不能解释成确定没有调用任何API**。后续最好分开记录“过程要求是否满足”和“过程观测是否完整”，无需改判本轮R。

## 3. 自主组织工具已经存在，但实际合作很有限

本轮任务确实由模型创建，O1不是名义上的。可是八个T槽没有记录到工作消息、责任转交、任务修订或依赖声明，显式导入仅一次；同时出现重复领取和精确编辑失败。

这说明：

**开放组织自由度，不等于模型已经学会使用它，也不等于已经产生适合分配研究的多样协作经历。**

但不应反向加入“必须发消息”“必须双方改代码”等得分条件。公共任务板本身也可能传递信息，一人集中完成仍然可以是合法方式。当前更准确的结论是：**实际可观察的跨成员成果使用与责任协调很少，且没有形成完整有效交付。**

# 三、预算不只是“还有没有额度”，还决定实际能够工作多少步

这是本轮最有价值的新诊断之一。

依据报告中的实际计数复算：

| 派生量 | 数值 |
|---|---:|
| 输入token占总实际token | **98.38%** |
| 每次实际调用平均输入 | **约12,179 token** |
| 每次实际调用平均输出 | **约201 token** |
| 每次实际调用平均总用量 | **约12,380 token** |
| 500,000除以上述平均用量 | **约40次调用的量级** |

最后一项只是尺度说明，不是精确可用次数预测：请求长度随过程变化，生成前还需预约最多2,048输出。它解释了为什么**128次决定是名义上限，而多数轨迹在约几十次调用后就碰到token边界**。 

这不是预算实现错误。重复送入的prompt确实产生了计算，不能为了让实验继续而从账中扣掉。

同时，**13/16预算终止不证明预算是全部失败的原因**：其中已有三份固定交付仍失败，另外三条主动结束的episode也失败。所以不建议下一步直接把50万改成更大数字，然后继续旧任务。

## 源码中存在一个值得核查的重复呈现路径

本次读取发现：

- 底层观察将`contract.md`全文放入`contract`；
- 上层观察又加入`root_goal.description`；
- v0.33将`root_goal`设为同一份中性化后的合同全文。

观察还包含任务、补丁和交付记录，SDK又保留首个与最新观察。**这提供了重复合同和增长元数据进入请求的静态线索。**  

但本次没有逐条拆分575份实际渲染输入，因此不能给出“删掉这些就节省多少”的实测结论。

建议只做一次窄核查：按预定工作阶段抽取请求，统计合同、工具schema、任务板、历史观察、版本元数据、代码和最新反馈各占多少。**确认重复后才去重，保留完整合同、当前相关状态和最新真实反馈。**不另建摘要模型、长期记忆平台或自动规划器。

这会形成新Γ，所有方法必须一致采用；即使事实保持，也不能声称模型行为分布完全不变。

# 四、下一轮的任务应当“领域规则更少，组织选择仍然真实”

V1.3要求区分领域计算、协作组织和状态依赖三个维度。当前将较多边界规则同时压在一个任务里，单人也无法完成，导致分配实验一直没有完整有效输入。**减少初期领域负担，是为了提高算法问题的可辨识性，不是降低旧实验标准。**:chatgpt-content-reference{index="11"}

## 新任务应满足的条件

| 保留 | 暂不叠加 |
|---|---|
| 固定真实代码来源、完整根目标 | 货币大数与复杂精度规则 |
| 实际库API与调用方兼容关系 | 多层partial/default覆盖 |
| 两项变化之间的共享接口或产物依赖 | secret过滤、深层异常树等全部组合 |
| 空任务表、自主创建与调整职责 | 预设开发者／消费者／复核者 |
| 实际修改、测试、发布、导入与交付 | 自动分工、自动修复或自动提交 |
| 独立完整验收与必要回归 | 为凑成功事后删除验收项 |

可考虑两个**候选结构**，具体仓库与代码尚需绑定：

**记录目录规范化与批量输出。**要求有效输入转换、顺序保持、空输入，以及可复用库行为与应用输出一致。重点在接口落实和消费关系，不再叠加金额、嵌套默认值等规则。

**共享名称规则下的检索与导出兼容。**两个功能使用同一明确名称规则，修改共享模块后要保持两边兼容。成员可以集中完成，也可以协商分工、分支实现后集成。

这些是问题约束，不是执行任务卡。环境不能预先写“先让A实现规范化，再让B实现导出”。

## 先检查真实依赖，不强迫模型表现出合作

新任务应有联合可满足性和针对性负例：原始版本、只改一侧、只改另一侧、联合参考实现。必要时用两种合法程序路线检查环境确实允许不同工作方式。

但程序见证只证明**路线可以存在**，不进入提示、不作为教师训练标签，也不算当前策略支持。模型仍可能集中完成、出现单一方法或全部失败，应如实报告。

如果加入局部资料互补，必须来自合理的应用约束和合法获取渠道；不能为了逼迫通信，任意隐藏正常公开代码。

# 五、建议 v0.34 分成四段，避免再次无限停留在诊断

## P0：一次性完成新目标与必要呈现核查

复用现有O1、预算账本、记录恢复、数值路径和两个模型。只补：

**新目标合同与独立检查对应；实际请求的重复呈现核查；新来源的完整交付路径。**

不重做相同近16K训练资格，不改精度，不增加模型。不要求所有潜在错误都可恢复，只确认必要合法路线能在预算内完成，并留有明确的探索余量。

公开检查应覆盖不同要求的含义，而不是只有一条正常例子；隐藏检查仍使用独立输入。不要把本次已知的`ignored`、大金额和secret失败直接改写成新任务的答案提示。

## P1：只做一次较小的T开发批，不再重复整套S/T

建议上界：

\[
2\text{个新开发根目标}
\times2\text{个固定seed}
\times2\text{个现有模型}
=8\text{条T经历}.
\]

本轮已经回答了“同样复杂任务下单人是否能完成”，无需在每次改目标后再复制整套16槽诊断。新的小批重点是：**是否出现完整有效工作，以及模型实际采用了什么工作方式。**

9B与Devstral仍是诊断对象，不追认任何旧筛选赢家。事前冻结完整库存、接口、先手和结束规则；有真实T完整交付，才进入新来源支持规划。多个模型都可行时，再按预定的完整结果、跨根覆盖、成本与固定顺序选择一个。

**这一条成功只是有限可行性，不是稳定能力认证，更不等于已有重配支持。**如果全部失败，本批按计划结束，不再围绕同一小题逐句改提示直到成功。

## P2：重新采集正式训练用途的当前窗口

P1开发经历不能改标为训练。选定共同载体后，按用途隔离的新任务采集当前策略窗口，分别检查：

\[
M,\quad n_{\xi iz},\quad n^+_{\xi i},\quad
v_{\xi i},\quad b_{\xi iz}.
\]

这里不能机械沿用8次。**重复数由全体有效产出率和估计精度规划，而不是由成功池内部的类别比例推测。**16可以作为预算讨论档位，但也不保证获得两类支持。:chatgpt-content-reference{index="12"}

必须继续保持：

- 不合并不同模型、先手、参数窗口和信息条件。
- 集中完成可以是合法方法，但不能把同一方法随意拆成两类。
- 失败、未映射和低频类保留基础处理，不删掉后重新平均。
- 无支持的有限配置试验可以事前结束；完整在线研究则保留基础回退。

## P3：直接执行B／G-raw／I-P的完整规则比较

| 方法 | 作用 |
|---|---|
| **B：\(Q=B\)** | 保持基础经验组成 |
| **G-raw** | 对同一合格原始成员分支作一般元重加权，不读取专用图／类别 |
| **I-P** | 对可靠工作类别作成员条件化配置，以真实试训估计C |

三个方法共享完整学习起点、原始材料、优势、基础mask和分母。I-P使用V1.3的**中心化Contribution、对数N、历史／覆盖双锚**；现有共享类别先验的G应保留为G-lift辅助对照，不冒称无结构基线。:chatgpt-content-reference{index="13"} :chatgpt-content-reference{index="14"}

C来自候选**实际更新后**的开发工作，而不是原任务成功率、人工“协作感”或技术诊断信号。配置选定后回共同起点正式更新，不能把试训分支累加。

独立确认给出：

\[
\Delta_{I-B}=J_{\mathrm{test}}(\theta_I^+)-J_{\mathrm{test}}(\theta_B^+),
\qquad
\Delta_{I-G}=J_{\mathrm{test}}(\theta_I^+)-J_{\mathrm{test}}(\theta_G^+).
\]

如果新小任务分数高于旧复杂任务，只能说明载体改变；**同一载体中I相对B/G的更新结果，才是分配增量。**

# 六、需要警惕：支持变多以后，试训费用会迅速增长

冻结采集只用了约2.59 GPU小时，不代表完整分配实验也很便宜。

按现有完整方向有限差分，一个成员块的分支数为：

\[
T_G=1+2(n^+-1),\qquad T_I=1+2(K-1).
\]

| 实际支持 | 唯一试训，共享B一次 | 再加B/G/I正式更新 |
|---|---:|---:|
| \(n^+=4,\ K=2\) | 9 | 12次窗口更新 |
| \(n^+=8,\ K=2\) | 17 | 20次窗口更新 |
| \(n^+=16,\ K=2\) | 33 | 36次窗口更新 |

每次试训还要执行贡献开发任务。**更高的支持密度有利于统计，却会扩大原始轨迹基线的维度，不能等采完才发现预算无法承担。**

首次可按预定顺序只配置一个合格成员块，其他材料仍进入基础损失；不能挑掉部分成功轨迹来压缩费用。较大规模的G应事先采用经过校准的可扩展元优化，而不是临时删探测方向削弱基线。

同正式更新次数回答“怎样更好地使用规定更新机会”；同总资源才回答学习效率。B节约的外层资源应允许按预定规则用于合理训练，不能要求它空等。

# 八、本轮成本与下一步边界

报告显示的四个worker时长之和为 **9,330.211501秒，即2.591725 GPU小时**，与逐卡区间并集口径一致。排队等待没有混入其中；本次也没有再预约显存。

报告提到的微秒级差异来自更细的浮点原件，本次只核对显示值，没有重建那些更细时间。此前v0.30—v0.32的历史预约与worker区间仍应各自按并集核算，不能把简单相加的旧数字混入本轮。

旧累计GPU／worker／统一墙钟上限不由本建议恢复；但取消旧上限不意味着自动授权新的8槽、训练窗口或数十次试训。**本轮原队列已经结案，新的任务与计算清单须另行冻结。**本次没有启动任何模型或远端任务。

## 最终推进判断

**v0.33不是又一轮没有信息的全零：它确认了单人也无法完成同样的复杂根目标，并把内容失败、未交付、预算停止与有限协作区分开了。**但继续在这两个根目标上搜索更多seed，研究收益已经很低。

下一轮应集中于：

\[
\boxed{
\text{低一些的领域规则负担}
+\text{真实自主组织与产物依赖}
+\text{可承担的实际输入成本}
\rightarrow
\text{当前有效方法支持}
\rightarrow
\text{B/G/I独立学习增量}
}
\]

**要降低的是初期问题中与分配研究无关的组合负担，不是降低验收可信度；要保留的是模型自行组织工作的自由，不是要求它表演更多合作。**

最终目标仍然不是终于在小题上取得高分，而是借助这些真实经历，完成一项能够回答“我们的分配规则是否比强基线更有用”的实验。
