**建议将原来“恢复高资源执行、完成118例基础学习”的计划，重设计为：以同领域协作能力为主目标，以单共享模型直接在线训练为主路线，分阶段验证基础学习、经验配置与外部迁移。**

这次调整不只是减少GPU数量。更重要的是，让**训练来源、任务结构、采样密度、算法对照和benchmark各自对应一个清楚的研究问题**，避免继续出现“工程检查不断通过，但核心协作学习始终没有获得检验”的情况。

以下是新的实验草案，**不覆盖ID‑VTDO V1、不重判旧实验，也不解除原GPU和队列暂停**。原归档明确记录了后继学习未启动及恢复前需要重新确认资源的边界。:chatgpt-content-reference{index="0"}

# 一、先改变实验中心：从“能运行”转向“协作是否学得更好”

新方案建议命名为：

## **ID‑VTDO：同领域协作在线学习与经验配置实验**

近期只围绕四个问题展开：

| 研究问题 | 需要取得的证据 |
|---|---|
| **模型能否真正协作？** | 在局部信息下取得必要依据、交接约束、使用他人成果、独立复核 |
| **直接在线训练是否有效？** | 固定模型与harness，训练后在未用于更新的工作情境中改善 |
| **ID‑VTDO是否有增量？** | 同起点、同材料或可比总预算下，优于基础RL与一般元重加权 |
| **收益能否迁移？** | 在同领域的新数据库、项目、伙伴与外部benchmark上保持 |

其中，第三项才是算法的主要科学命题。V1要求分别验证信息结构、成员条件化配置、联合探测和迁移，不能将世界建设、模型升级和算法效果合并成一个系统改善。:chatgpt-content-reference{index="1"}

相较旧计划，主要调整如下：

| 原安排 | 新安排 |
|---|---|
| 默认恢复27B、FP32、双采样副本 | 资源先冻结，默认单模型实例、单学习器，多角色分别保留局部会话 |
| 先做低密度基础pilot，再看是否出现方法支持 | 在线窗口同时安排情境覆盖与同情境重复，避免数学上不可能形成多类支持 |
| 以UCI内部得分与SQL能力为主要结果 | 同领域协作基准主导，SQL基准承担基础能力控制 |
| 不断增加新的框架、数值与队列验收 | 保留已有模块，只修复影响当前实验的必要路径 |
| 用一次参数更新或少数成功作为阶段终点 | 完成预定学习、独立评价和明确的正／负结果 |

**旧H1不需要重做或重排。**它已经完整收口，但48例只有5例完整责任，完整复核和chain均为0；选中27B＋SDK是原排序规则的结果，不代表它在所有工作与成本条件下最好。:chatgpt-content-reference{index="2"}

# 二、训练来源与benchmark：收敛到同一工作领域，但分工不同

## 1. 统一领域：结构化数据分析与数据工程协作

不再同时铺开金融、通用办公、电信和开放软件工程。近期训练与评价围绕：

**数据字典与业务规则理解、查询实现与修复、数据核对、schema／接口维护、共同分析，以及交接、复核和持续更新。**

这里既要保留SQL，也不能只剩SQL。否则最后可能证明模型更会修查询，却没有证明它更会合作。

## 2. 训练素材保留“两类主来源＋一个明确缺口”

| 来源 | 新方案中的作用 | 当前边界 |
|---|---|---|
| **UCI Online Retail** | 真实业务表格、口径、指标、分析消费与多项目维护 | 保留现有接入，不把同表客户隔离称为独立来源 |
| **Six-Gym-SQLite** | 数据库问题、待修SQL、初始化和独立验证，增加工作任务的广度 | 作为拟接入来源，不使用参考SQL或教师轨迹替代当前模型工作 |
| **数据质量／schema／管线维护情境** | 补充共同转换、接口变化、消费者适配和复核 | 尚需构造与准入，不能声称前两类已覆盖所有数据工程任务 |

Six-Gym-SQLite官方提供数据库问题、错误SQL、初始化、参考解及测试等字段，适合作为可执行工作起点；但需要将参考解与隐藏测试留在评价侧。**复用任务环境，不等于采用其已有轨迹做SFT。**:chatgpt-content-reference{index="3"}

新增任务应形成实际工作对象。例如，schema变化必须使消费者读取或转换真的受到影响；数据核对必须存在可执行的重算；并行分析必须共享真实接口。不要仅给独立SQL题换上“提供者、实现者、复核者”的角色名。

## 3. 外部评价采用“三类协作证据＋一个基础能力控制”

| Benchmark | 拟选范围 | 在新方案中的地位 |
|---|---|---|
| **TeamBench** | 数据工程相关任务 | **角色分工、需求交接与独立复核主验证候选** |
| **Co-Gym** | Tabular Analysis | **共同分析、伙伴反馈与共享工作空间协作** |
| **BIRD Mini-Interact** | a-Interact | **信息缺口发现、需求澄清与取得解释后的工作调整** |
| **BIRD-Critic-SQLite** | 原生数据库问题解决 | **个体能力和退化控制，不承担核心协作结论** |

TeamBench通过访问控制分离完整需求、工作空间修改与最终验证，适合检验角色之间是否真正传递约束。这里选的是数据工程子集，不是整个基准；其产物分数与验证者职责诊断仍应分别报告。:chatgpt-content-reference{index="4"}

Co-Gym表格分析允许双方参与共同工作，额外领域知识与元信息提供给模拟用户。首轮建议固定伙伴策略，只替换被测工作模型，检验模型加入既有合作关系的能力。其数据来自DiscoveryBench子集，需要追踪来源；评分包含语义评价，不能描述成全部由独立数值重算得到。:chatgpt-content-reference{index="5"}

Mini-Interact当前公开版主要覆盖SQLite上的知识歧义SELECT任务，适合作为信息协作验证；标准答案与测试需要按官方流程取得。BIRD-Critic则主要测数据库问题修复，保留它有助于判断协作收益是否只是个体SQL能力变化。:chatgpt-content-reference{index="6"}

**四项是目标评价组合，不是四个必须同时完成移植的新平台。**可以先接TeamBench数据子集和Mini-Interact，再接Co-Gym；BIRD-Critic复用数据库评价能力。某项尚未准入时就限定结论，不能用SQL成绩替代缺失的协作证据。

# 三、先划分研究用途，再构建角色和任务

建议建立四类用途，而不是先生成大量轨迹后随机切分：

| 用途 | 允许做什么 |
|---|---|
| **接口与选型开发** | 修改模板、工具呈现、harness及资源profile |
| **策略训练** | 当前共享模型直接交互并更新 |
| **贡献开发** | 配置试训、贡献校准与方案选择 |
| **锁定评价** | 预定节点测量，不反向修改模型、harness、奖励或配置 |

划分单位应优先是**来源数据库、目标数据表、任务模板家族及其派生产物关系**。同一发票表的改写问题、同一数据库的近重复修复、同一世界的信息重分配，不自动成为独立来源。共享检索索引、角色记忆和准备示例也必须遵守同一边界。:chatgpt-content-reference{index="7"}

尤其需要核查：

**Six-Gym与BIRD-Critic的实际问题／数据库关系；Mini-Interact与LiveSQLBench祖先任务；Co-Gym与DiscoveryBench原任务；TeamBench数据任务是否与训练素材重合。**

发现重合后，应按预先规定的谱系规则隔离，而不是看模型成绩后挑选测试题。外部benchmark的技术split名称也不能自动决定本项目用途。

**现有UCI只能承担部分同源验证。**要声称同领域的新来源迁移，仍需实际保留不同数据库或资料家族，而不是继续换客户、金额和任务编号。

# 四、执行方案：一个共享模型、一个采样实例，不绑定FP32或双副本

## 1. 保留一个通用模型作为最终产物

所有目标岗位共用同一套有效actor参数、一个共享LoRA和actor优化器；critic是独立训练辅助组件。

提供者、实现者和复核者拥有不同会话、权限与局部历史，但可以由同一常驻模型依次服务。**多成员协作不要求多副本并发，也不要求分别训练岗位权重。**共享参数下，成员索引表示训练项来源，不代表只改变某一岗位的能力。:chatgpt-content-reference{index="8"}

配对试训同样可以顺序执行：共同学习状态保存在磁盘，逐分支加载、训练和评价，不要求同时驻留所有模型分支。

## 2. 资源profile作为新选择，不追溯修改旧条件

近期最多在已有9B、27B两个候选中作有界确认，不重新展开大规模模型搜索。

优先研究**冻结基座采用合适的低存储精度、训练adapter及必要归约保持明确精度**的配置。但这仍是待验证路径，不能承诺27B一定单卡可训，也不能仅开启autocast就声称权重存储已经减半。

正式启动前需要冻结：

**允许设备数、显存与主机内存余量、单任务上限、总分配设备时间、存储，以及外部模拟用户／评审API额度。**

原报告已说明，27B的FP32基座权重本身约100.195 GiB，双采样副本的四卡需求来自具体部署组合，不是研究理论要求。:chatgpt-content-reference{index="9"}

新精度检查的是**自身采样与可微复算的对应关系**，不是要求新配置逐位复现旧FP32输出。旧概率门可继续作为首版候选准入；若需改变，另行校准和冻结，不现场放宽、不裁尾、不替换原行为概率。

## 3. harness不再做全因子搜索

从现有native或受管SDK中选择一套可用主配置。SDK没有必须胜出的地位，也不需要为它增加更多功能来追求胜出。

选定之后，算法比较固定：

**工具、角色信息、上下文管理、笔记和检索能力、错误反馈、停止协议与行动预算。**

机械记账由系统完成；业务依据选择、实现和复核仍由模型承担。模型主动生成的笔记、检索和编辑要有动作归属，工具返回与同事消息不成为接收者的生成目标。

# 五、重新设计训练窗口：既有广度，也允许多方法支持出现

旧pilot当窗每个精确情境最多2条，最低每类2条，因而最多一类达标。**这不是采样运气问题，而是设计上没有组成优化自由度。**:chatgpt-content-reference{index="10"}

建议的新窗口算例是：

| 窗口内容 | 计划数量 | 目的 |
|---|---:|---|
| 联合情境A，从同一精确初态重复 | 8 | 信息获取—交接—实际实现 |
| 联合情境B，从同一精确初态重复 | 8 | 独立复核—反馈—定向修复 |
| 单岗位实现 | 4 | 基础计算与修改能力控制 |
| 单岗位复核 | 4 | 独立核验能力控制 |
| **合计** | **24** | 兼顾联合方法密度与基础工作 |

四个窗口共96个训练episode。窗口间按预定清单轮换事实与来源，窗口内保持同一 \((\theta,\Gamma,\xi)\) 的重复，**不跨权重或不同信息布局拼池**。

这里的“2∶1联合／单岗位份额”和“8次重复”都是新建议，不是V1已冻结参数。最低每类2条也只能是pilot输入门，不是贡献估计充分性的证明。即使 \(M=8\)，当前模型仍可能只产生一类或全部失败。

重要的是：

> **基础RL不等待多方法支持；ID‑VTDO只使用当前实际存在的支持。**

无支持、单类和零优势分别记录；不删除困难情境，不把预算转给容易任务，不补采到类别齐全。V1明确要求残余失败保持基础处理，权重不能创造新支持或零优势之外的信号。:chatgpt-content-reference{index="11"} :chatgpt-content-reference{index="12"}

### 四项目暂时怎样处理

四项目继续承担持续协作与维护评价。**在真实训练投影尚未接通时，不因为已有正式效用就把它算作已经进入RL。**

短责任学习可以先运行；四项目自主执行同步验证。两者互不成为无限前置条件，也不互相代替成果。

# 六、分阶段实验：先完成有限学习，再进入有证据的配置干预

## P0：来源与评测准入

这一阶段形成可执行资产、领域过滤规则、来源划分、角色权限和独立评分边界。

只验证当前需要的路径，不重做全部世界内核。程序见证用于证明存在合法路径和错误可区分，**不计入当前模型经验支持，也不作为SFT示范**。

TeamBench子集按领域与执行能力确定，不按目标模型成功率筛选；Co-Gym固定伙伴和评分配置；Mini-Interact取得完整评价资产。接口开发和最终锁定任务分开。

## P1：确定可工作、可训练的初始化

使用小型固定开发情境，对不超过两个候选执行配置做确认，重点看：

**真实实现、有据复核、合法信息获取、有效停止、原始token／概率，以及实际可微路径和资源余量。**

不要求所有完整项目先成功，但也不能只凭“模型装得下、会读文件”就认证基础能力充分。

这一阶段选定的是**模型—harness—数值执行组合**，不是重新修改旧H1排名。用户恢复授权前，P1仍不执行GPU工作。

## P2：完成共享模型基础在线pilot

建议先执行上述四窗×24例，共96条训练经历，固定 \(Q=B\)。

内部评价可采用12个预定情境：

**信息交接与实际使用4例、复核修复4例、项目维护4例；各重复2次。**

初始和最终各24例，共48次评价，因此基础pilot合计：

\[
96\text{ 训练}+48\text{ 评价}=144\text{ episode}.
\]

**这是新计划算例，不是已批准预算，也不包含选型、贡献探测或外部测试。**具体独立来源与情境尚需实际准入。

保留现有CTDE actor–critic／PPO基础路线。首版可以沿用已经实现的terminal MC，减少同时变化的因素；这不表示MC优于RTG。若开发阶段需要更改时间信用，应在主比较前固定，不与ID‑VTDO变化混算。

每个窗口由当前模型实际工作，更新后生成新经历。H0/H1输出不变成训练示范库，历史数值诊断也不变成离线RL数据。

**四次更新只是pilot训练剂量。**它可以测成本、信号和初步变化，不能承担稳定收益或总体无效的判断。预定终点后没有收益也要完整报告，不追加到幸运成功才停止。

## P3：在在线窗口内做有界Contribution校准

不必等基础RL已经取得显著提升才研究贡献；但必须有可信的基础学习信号和对应的真实可重配支持。

建议预定两个窗口位置，每处最多选择两个不同成员块的可行方向，执行四个分支：

\[
F_0,\qquad F_A,\qquad F_B,\qquad F_{AB}.
\]

所有分支从同一个 actor、critic、优化器状态出发，使用同一当前窗口材料和规定更新预算；然后分别进入配对开发世界实际工作。

单点贡献用有限差分估计，联合项为：

\[
I_{AB}=F_{AB}-F_A-F_B+F_0.
\]

这对应V1的学习贡献与联合配置交互，不是当前消息的执行功劳。:chatgpt-content-reference{index="13"}

一个有界算例是：每分支8个开发episode，两处全部有资格时，至多8个试训分支、64条开发执行。**这是诊断规模，不是精确导数或功效保证。**无支持则记录未执行，不能换到表现最好的窗口或追加成功样本。

探测完成后回到共同起点进行正式更新，探测参数不累加。新正式策略继续进入世界。**这是在线训练内部的干预，不是把路线改成固定数据离线训练。**:chatgpt-content-reference{index="14"}

## P4：算法主比较

第一批主比较先收敛为三个训练方法：

| 方法 | 作用 |
|---|---|
| **基础在线MARL，\(Q=B\)** | 测ID‑VTDO总体增量 |
| **一般成员—原始轨迹元重加权** | 排除“只是验证驱动调权”的解释 |
| **ID‑VTDO第一阶结构化成员配置** | 检验信息依赖、语义类别和成员条件化的价值 |

再逐步加入**结构化单点与联合项、图引导与随机选对、成员共用权重、去历史锚／覆盖项**等消融，不一次铺开所有模型、harness、精度和算法组合。V1要求一般元重加权取得相同类型的开发信号及可比外层资源。:chatgpt-content-reference{index="15"}

一个探索档可按：

\[
3\text{ 方法}\times1\text{ seed}\times4\text{ 窗}\times24
=288\text{ 条训练episode}
\]

核算；三seed扩展为864条。**两者均不含贡献探测、开发执行和测试，不能直接当作总预算，也不建议一次性全部启动。**

P2结果只有在模型、协议、优化设置和预定复用关系完全一致时，才可以作为这里的基础RL分支；否则不能拼接。

# 七、计算公平性要分两类实验，不能只对齐更新次数

这是新方案必须强化的一项。

## 1. 固定材料机制比较

保持共同学习起点、同一窗口经历和相同正式更新，观察不同配置造成的差异。额外试训和开发成本完整报告。

它回答的是：**同一批真实工作经历，怎样使用更有利于学习？**

## 2. 同总资源效果比较

给各方法同样的总预算上限，包括：

\[
C_{\mathrm{交互}}
+C_{\mathrm{正式更新}}
+C_{\mathrm{试训}}
+C_{\mathrm{开发执行}}
+C_{\mathrm{外层优化}}.
\]

基础RL不做贡献探测，节省的资源可以按预声明规则用于额外交互或更新；**不能让baseline空耗同样时间来制造“公平”**。一般元重加权也必须得到有竞争力的验证与计算资源。

这一层回答的是：**付出全部额外估计代价后，ID‑VTDO是否仍值得？**相同训练步数不等于同总资源，这也是V1的明确要求。:chatgpt-content-reference{index="16"}

资源不足时，先完成固定材料机制实验，并限定结论；不要把它包装成已经证明资源效率。

# 八、效果验证：必须区分个体解题、协作执行和算法学习

## 1. 内部保留三类执行条件

在小型独立诊断组上比较：

| 条件 | 解释作用 |
|---|---|
| **正常局部信息团队** | 主要协作表现 |
| **允许信息并集的单执行者，匹配总推理预算** | 检查是否主要是个体能力或额外推理资源 |
| **缺关键交接／独立复核，或受控延迟** | 检验相关信息与执行环节的作用 |

全信息单人是参照，不是数学上限；信息不足单人可能本来就不可解，不能把它当唯一弱基线。

分别观察训练前后在各条件下的变化，可以帮助辨识协作收益。**但“团队增幅减单人增幅”仍不能不加假设就称为纯协作因果效应。**

## 2. 主要指标围绕真实成果

建议主要报告：

**独立正确交付、完整团队责任、复核错收／错拒与缺席、依据实际使用、针对同一问题的有效修复，以及跨项目保持性。**

成本、权限问题、不可恢复错误和合理阻塞单列。通信次数、解释长度、工具ok、批准数量和参数变化不作为能力主分数。:chatgpt-content-reference{index="17"}

尤其应防止三个替代：

- 正确build替代固定交付；
- 一致意见替代独立复核；
- 上游交接成功替代整个团队完成。

## 3. 外部多个benchmark分批运行，不要求全部搬入WorldCore

训练仍在ProWorkSim内直接发生，外部测试使用原生环境。参数冻结后，TeamBench的所有目标岗位可以使用同一检查点；Co-Gym和Mini-Interact首轮固定外部伙伴，只替换目标模型。

初期可以为每个benchmark预先选择至多12个符合领域与去重规则的任务。四项、初始／最终两个checkpoint，最多96次外部运行；**这只是资源规划上界，不能当作完整benchmark成绩或充分统计规模**。对更多训练方法评价时必须重新乘相应策略数，不能继续沿用96作总预算。

如果TeamBench合格数据任务不足，就报告实际子集；不能扩展到其他行业凑数。如果Co-Gym评分或Mini的测试资产未就绪，就保留待执行，不用不完整评价填0。

正式验证再依据开发方差、独立来源簇与目标效应确定规模。重复运行和多个成员不增加独立来源数；多个benchmark也不合成一个任意总分。

# 九、推进顺序与停止条件

建议下一阶段只按这条主线推进：

\[
\boxed{
\text{同领域来源与评测清单}
\rightarrow
\text{资源内的共享模型配置}
\rightarrow
\text{基础在线pilot＋当前支持诊断}
\rightarrow
\text{有界贡献干预}
\rightarrow
\text{强基线与同领域迁移}
}
\]

四项目效用与模型入口可以并行完善，但不另起一套训练器。前缀缓存、更多并行、副本同步和大型harness功能暂不作为必经任务。

实际停止条件来自**授权撤回、资源上限、关键身份／数值错误和评价不可判定**，不来自“当前成绩不好”。业务失败继续作为真实结果保留；补修在新协议和新目录中执行，不覆盖旧轨迹、不重采补成功。

如果所有方法在工作上都没有起色，应定位基础能力、任务复杂度、反馈和更新幅度；如果基础学习有效而ID‑VTDO无增量，则检查贡献估计、支持密度和结构价值。**两种负结果的研究含义不同，不能都归结为“平台还不够完善”。**

## 最终建议

原方案保留了正确的资源收缩方向，但现在还需要进一步把**资源收缩与科学问题收敛**连接起来：

> **一个共享模型，在同领域的真实数据工作中直接在线学习；用多个互补协作benchmark和内部受控情境证明它更会合作，再用同起点、同材料及同总成本的对照判断ID‑VTDO是否真正有增量。**

近期最值得完成的是**一个144例量级的基础pilot及其完整评价、一个存在实际支持时的有限贡献干预，以及多个同领域外部入口的小型冻结测试**。这些数量只是待核定的设计档位，不是自动执行清单。

**不再把27B全FP32双副本作为默认条件，不再把SQL分数作为协作的替代，也不再让“基础pilot的采样结构根本不允许两类支持”成为算法实验反复后置的原因。**

当前可以继续整理来源、协议与实现差异；在资源和恢复权限重新确认前，GPU、模型调用和后继队列仍保持暂停。
