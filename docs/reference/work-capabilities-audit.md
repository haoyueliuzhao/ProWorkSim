## 三、两处需要补修的接口问题

### F1：同项目精确分享成功，但读取检查忽略该授权

**位置：`world_core.py::_action_share` 与 `_can_read`。**

`_action_share()` 允许将对象版本分享给指定目标项目及其成员，并写入精确分享记录；没有排除目标项目与来源项目相同的情况。

但读取判断采用了提前返回：

```python
if artifact.get("project_id") == project_id:
    return actor in artifact["readers"]

return any(匹配的精确分享记录)
```

因此，只有跨项目情况才会继续检查 `shares`。

本次构造的条件是：A 项目中 Alice 拥有一份私有对象，Bob 是同项目成员但不在原 readers 中。Alice 有该对象的 share 权，只分享 v1。

| 操作或对照 | 实际观察 |
|---|---|
| 分享前，Bob 在 A 读取 v1 | 拒绝 |
| Alice 将 v1 分享给 A 中的 Bob | 分享记录生成 |
| 分享后，Bob 在 A 读取 v1 | **仍然拒绝** |
| 同一 v1 分享给 B 中的 Bob | 可以读取 |
| Bob 读取未分享的 v2 | 拒绝 |
| 未分享的 Carol 读取 v1 | 拒绝 |

**问题不是原有私有权限太严格，而是系统已经记录了一个成功的授权动作，却没有执行对应读取效果。**

这条路径对真实工作世界很重要：团队成员之间经常需要按版本分享原本私有的材料。若暂时只支持跨项目分享，也应显式拒绝不支持的同项目请求，而不是返回成功；更符合当前目标的做法，是补全它。

**建议修复：**读取权限应同时考虑基础 ACL 与合法的精确分享。不能简单把 Bob 加入对象的全版本 readers，否则修复 v1 的同时会错误开放 v2。

正式回归应从项目包创建私有对象，通过真实 `ProjectSession` 验证“分享前拒绝、分享后指定版本成功、其他版本和其他人员仍拒绝”。

---

### F2：对象级采用权限合法，但适配器没有传递对象上下文

**位置：`world_core.py::_action_adopt_version`。**

权限函数已经支持 `project_id`、`work_node`、`object_id`。当授权只覆盖某个对象时，缺少对象上下文会被保守拒绝，这是合理行为。

但采用更新入口先调用：

```python
self._project_power(actor, project_id, "adopt", "artifact")
```

没有传入实际采用对象。首次 `_action_adopt()` 也存在相同的静态遗漏。

本次实际执行覆盖的是 `adopt_version`：

| 条件 | 结果 |
|---|---|
| 主体具有目标对象的 adopt 权 | 带 `object_id` 的权限查询为 true |
| 新版本可读取 | true |
| 经采用更新入口执行 | **“Actor lacks project power: adopt”** |
| 明确使用全对象授权的新对照夹具 | 可以更新 |
| fixed 政策下尝试直接换版 | 仍拒绝，符合要求 |

这也是**合法窄授权路径的误拒绝**，不是权限函数本身应当放宽。

**建议修复：**在可信项目范围内解析采用声明，取得真实对象和目标工作集合，再把对象上下文传给权限检查；授权还限定工作范围时，逐项检查受影响工作。

不能通过给所有人授予通配权来“解决”问题。修复后还应保留错对象、错项目和 fixed 政策的拒绝对照。

但它们不直接推翻报告中使用其他授权配置的固定实例。

## 四、当前更大的架构问题：世界已能放项目，但实质工作能力尚未汇合

报告公开说明：**新 WorldCore 仍是受控 JSON 工具；完整经营 XLSX 模板、DeepSeek 运行和训练导出仍在旧单项目入口。**:chatgpt-content-reference{index="16"}

因此，下一步不应仅仅是再增加一类 JSON 项目。否则可能形成两条长期分离的路线：

```text
新核心：身份、权限、项目、声明与状态管理越来越完整
旧入口：真正的表格、计算、分析产物仍在单独运行
```

**这不是本轮未兑现的声明，而是下一阶段应解决的首要能力缺口。**

建议将后续主线明确为：

# **通用工作能力接入与跨项目成果使用**

重点不是让核心理解所有金融公式，而是让领域工具真正运行在同一个世界核心之上。

### 1. 将应用名称变成有限、可调用的工作能力

目前 `applications` 和 `event_policy` 主要是配置与记录入口，文档没有宣称已经实现任意应用插件。

下一步可以先形成小型能力注册与适配机制：

| 层次 | 应负责什么 |
|---|---|
| **世界核心／运行器** | 身份、权限、精确引用、版本、事件、提交与恢复 |
| **文件／表格适配器** | 真实读取、编辑、计算和序列化 |
| **领域合同** | 指标定义、期间、单位、允许假设、交付要求 |
| **独立评价** | 从固定提交版本检查内容、来源和实际计算后果 |
| **工作人员** | 选择资料、组织操作、创建产物、检查并提交 |

先保留 JSON，再迁入现有受限 XLSX 能力即可。**不是把旧经营世界作为子目录挂进去，而是让表格对象使用新核心的对象身份、权限、版本和动作提交。**

不需要同时实现完整 GUI、宿主 Shell、任意插件或全部 Excel 函数。

### 2. 明确草稿、发布、采用与实际使用的区别

当前 `write_object()` 每生成新版本，就会触发 `_publish_shared()`；订阅者据此得到新版本分享和通知。这个行为在 v0.6 的有限政策下是自洽的，但不能直接代表一般工作中的发布过程。

未来需要区分：

\[
\text{生成新版本}
\neq
\text{正式发布该版本}
\neq
\text{另一个项目采用}
\neq
\text{下游成果已正确更新}
\]

例如，分析师保存一个未完成草稿，不应自动使所有下游项目认为正式输入已经换版。

建议新增明确的发布记录，绑定**精确对象版本、发布主体、时间和范围**。原来的“写入即发布”保留为旧政策，不改写历史；新项目可以配置显式发布。

同样，采用声明更新为 v2，不代表工作簿已经按 v2 重算。当前独立评价只检查 JSON 字段存在与冲突，尚未检查这类内容关系，因此不能用 `adoption_view=current` 替代成果正确性。

### 3. 让工作人员从公开界面完成工作，而非由实验脚本预知结构

最终观察补齐公开合同、需求版本和可读别名，是必要修订。:chatgpt-content-reference{index="20"}

下一步应进一步检验：工作人员只使用公开会话，能否发现可用工具、取得必要材料、识别适用版本并形成交付，而不是依靠实验脚本预知后台对象 ID、准确金额和事件顺序。

这可以先用透明程序工作人员验证，不必立即进行模型能力实验。

## 五、建议的下一轮实验方案

建议继续限定为**一个世界、两个项目、单写者交错执行**。新增实验围绕真实工作能力组织，不靠增加行业名或随机种子扩展。

### N0：合法授权路径补修

先完成 F1／F2 的正式工具回归。

| 分享检查 | 采用检查 |
|---|---|
| 同项目、跨项目均使用合法精确授权 | 指定对象授权能够更新指定对象 |
| 分享 v1 不开放 v2 | 错对象、错项目仍拒绝 |

| 分享记录与实际读取效果一致 | fixed 政策不能被直接更新绕过 |

本组应从合法项目包创建世界状态，不直接补写后台 ACL。保留修复前后结果，相关 M2、M3、M3F 作回归即可。

### N1：两种实际产物能力运行在同一个世界核心上

**命题：不同文件能力共用一个世界机制，而不是各自运行一个专用世界。**

A 项目创建和更新受限公式工作簿；B 项目形成 JSON 交付。两者采用同一身份、版本、权限、动作回执和存储提交。

重点检查：

| 条件 | 应有后果 |
|---|---|
| 合法表格编辑 | 实际 XLSX 字节与公式改变，形成新版本 |
| 错误公式 | 可以真实落盘，独立检查识别错误 |
| 提交后再编辑 | 旧提交固定版本不被改写 |
| 同名对象位于不同项目 | 不混淆、不覆盖 |
| 未授权操作 | 拒绝且不产生正式文件效果 |
| 独立评价 | 读取实际提交，不读取后台预制正确模型 |

数值期望使用预先固定的标量或独立参考计算，不能调用被测公式引擎生成“正确答案”。

**本组证明的是工具能力迁入多项目核心，不是金融专业能力。**具体经营算式仍留在领域模块，不能进入通用核心分支。

### N2：草稿—发布—采用的关系实验

**命题：内部版本变化、正式发布和下游更新具有不同后果。**

世界材料 v1 由 A 按“跟随已发布版本”采用，B 固定 v1。从相同检查点构造有限条件：

| 条件 | 预期 |
|---|---|
| 只创建 v2 草稿 | 不把它自动当成下游正式输入 |
| 有权发布 v2 | 按明确订阅产生授权、通知与需检查关系 |
| 无权发布 | 不产生正式发布效果 |
| B 固定 v1 | 历史使用继续按其合同解释 |
| A 只更新采用标签 | 文件不自动改变，错误结果仍可被独立拒绝 |
| A 实际更新工作成果 | 新文件及其输入绑定满足当前要求 |

这里的“跟随已发布版本”也不能自动解释成领域适用性已证明。某个新版本是否适合特定期间或用途，仍可能需要领域检查或工作人员判断。

### N3：跨项目成果能否被继续使用

**命题：项目之间共享的是有明确接口的成果，而不只是同一个文件 ID。**

A 负责一个有限计算产物，B 使用 A 明确发布的版本形成说明。A 的部分上游材料对 B 私有，分享产物不能递归开放这些材料。

建议保留五种策略条件：

| 条件 | 应检查什么 |
|---|---|
| 正确继续使用 | B 的内容与约定输入版本相符 |
| 沿用旧版本 | 按 B 的固定或跟随政策分别判断 |
| 只换标签不更新结果 | 不能仅凭元数据 current 获得内容通过 |
| 错误计算得到正式批准 | 历史制度决定保留，独立评价仍拒绝 |
| 另一种合法交付组织 | 不因一份／两份文件或合理步骤不同而判错 |

A 完成后，被 B 引用的成果应继续存在；环境不能代替 B 更新内容。

同时，**B 不一定必须读取 A 的全部上游材料**。如果合同允许消费经过约定的中间成果，就应评价这个交付接口，而不是强制所有项目重复全部上游工作。

---

### N4：公开可操作性与少量新增恢复检查

**命题：同一工作在公开观察、工具执行和持久化结果之间能够完整衔接。**

程序工作人员只使用将来模型也会获得的会话接口，不读取 `control/state/spec`。测量程序可以在运行后独立检查后台。

先覆盖有限情境：已有适用信息、可发现的正确版本、已明确可取得的资料请求，以及信息缺失时的合理等待。当前无法表达的请求应标为能力缺口，不能用隐藏参数或固定剧情补齐。

记录真实观察、工具定义、请求／返回和对象版本。**重建后的观察不能替换工作人员当时实际看到的内容。**

恢复只针对新能力增加少量必要切点，例如一次表格写入和一次显式发布后的返回中断；不把原十个故障点机械乘以所有项目、格式和策略。

\boxed{\text{N2 发布／采用}+\text{N3 持续使用}+\text{N4 公开可操作性}}
\]

各组在运行前明确对象、合法动作、拒绝或阻塞出口、比较字段和独立预期。**断言数量应由实际合同确定，不先规定一个“必须达到的测试总数”。**

阶段通过标准应是：

> 两个项目能够通过同一组实际工作能力创建、修改、发布和使用成果；共享、采用和正式批准不再替代实际内容检查；工作人员无需后台信息就能进入并推进工作。

本阶段不要求模型训练、第三行业、动态撤权、通用并发或完整专业质量评价。它们可以在明确需求出现后另行设定边界。

---

## 七、真实金融工作流材料的作用：校准，而不是改变主线

你的前一条要求应继续保持：**真实金融工作流数据是完善项目的支撑，采集不是当前重点。**

v0.6 已为来源设置 `observed / reconstructed / synthetic / unknown`，并禁止项目包装载时伪造审批历史，这为后续接入提供了必要边界。:chatgpt-content-reference{index="21"}

后续实际取得合法材料时，可以用一组已有工作包——需求、初始模型、修订版本、确有记录的口径和审阅意见——检验三类问题：

| 材料揭示的差异 | 优先完善的位置 |
|---|---|
| 文件格式、布局、读取与编辑方式 | 应用适配层 |
| 财务定义、期间、计算和交付要求 | 金融领域合同与评价 |
| 共享、授权、交接和工作替代无法表达 | 通用世界核心 |

缺失的批准、回复和时间顺序不能补造成 observed；有来源引用也不自动意味着其内容真实或专业正确。

**真实过程是一条实际发生过的工作路径，不应被强制作为唯一合法路径。**它的价值是约束和纠正模拟器，而不是把模拟世界退化为历史轨迹复读。

## 最终推进判断

**本轮最大的进展是：世界已经不再只是某个项目模板的外壳。**这个方向应保持，不需要因两处合法路径的误拒绝而推倒重做。

但下一阶段也不能只让注册、授权和审批机制越来越丰富，却把真正的工作留在旧单项目入口。

建议将近期目标收敛为：

\[
\boxed{
\text{修复合法作用域路径}
\rightarrow
\text{接入共享的实际工作能力}
\rightarrow
\text{区分草稿、发布、采用与产出}
\rightarrow
\text{验证跨项目持续使用}
}
\]

**v0.6 主要解决了“项目在哪里运行、如何隔离与共享”；下一轮应解决“项目如何在同一个世界中真正完成工作，并留下能被后续项目使用的成果”。**这比继续增加纯 JSON 情境，更能推动 ProWorkSim 成为动态专业工作世界的基础。
