# 二、这次不同于此前团队预算耗尽：单次请求已经无法发出

## 1. 两种限制必须彻底分开

本轮固定：

\[
\text{context}=16,384,\qquad
\text{输出预留}=2,048。
\]

所以单次实际prompt必须满足：

\[
\boxed{P_{\mathrm{selected}}\le 14,336。}
\]

而团队500,000-token池决定的是整个episode能够累计花多少token。这两个条件必须同时满足，不能用团队剩余额度抵消单请求超长。

关键ST例中：

\[
14,365+2,048=16,413>16,384,
\]

另一个成员为16,408，分别超过29和24 token；此时团队还有480,453 token。**继续给团队更多累计额度，或者再提供几张GPU，都不会改变这个请求的16K边界。**

## 2. 不同条件获得的实际工作深度差异很大

| 条件 | 4槽真实调用合计 | 成员公开测试 | 本轮可观察的工作深度 |
|---|---:|---:|---|
| SB | 19 | 1 | 部分槽较早停止 |
| ST | **8** | **0** | 四槽均每名成员只生成一次 |
| PB | 47 | 8 | 能推进更多行动，但仍在容量处停止 |
| PT | 45 | 8 | 同样未能消费后续测试反馈 |

六个episode总共只有两次真实调用，占本轮库存的37.5%。终态各槽仍有275,427—480,453团队token余额。上述数字由报告逐槽表复算，不能理解为修复后能节省或多执行多少。

这意味着，shared比split携带更多信息、team说明增加文字，本来就是实验处理的一部分；但**冗余复制又进一步将这些差异转化成了不同程度的提前终止**。

可以报告实际受限协议下的分数结果，却不能从中单独提取“信息共享对协作的作用”。

## 3. 最有诊断价值的不是全零，而是17次测试反馈无人收到

本轮明确缺失的是：

\[
\text{执行测试}
\rightarrow
\text{产生真实返回}
\;\not\rightarrow\;
\text{进入下一次模型输入}
\rightarrow
\text{据此继续工作}.
\]

所以不能说split成员已经“通过复测获得并利用了另一份信息”。它们执行了检查，系统也保存了结果，但结果没有进入后续实际生成。

两次公开检查通过同样不能自动补成提交，更不能推定隐藏验收也会通过。**它们说明某些历史版本取得了局部正确结果，不说明团队已经完成任务。**

# 三、源码已经定位到一个具体机制，不应再泛化为“模型需要更大上下文”

## 1. 新静态字段没有进入原去重范围

冻结`software_context_v034.py`只处理两类重复：

- 与完整合同相同的`root_goal.description`；
- 与最新合同完全相同的历史`contract`。

它没有处理新增的`initial_diagnostics`和重复的`role_task`。关键例中，这两类文本分别为4,880字符和2,819字符，并同时出现在首末观察。 

## 2. 原选择器无法删除这些受保护内容

继承的`software_context_v028.py`只移除较旧的完整assistant/tool回合，保留全部system/user消息及最新完整工具回合。

因此，当只剩：

> 系统说明＋首次观察＋唯一工具回合＋最新观察

时，选择器已经没有可删除的旧工具回合。**反复放入的静态诊断留在user观察里，不能被这个机制清理。**

这也说明，不能简单把“保护最新反馈”当作错误。真正的问题是：**前面保留了多份相同静态内容，最后又只能在丢掉最新反馈与拒绝生成之间二选一。**正确做法是减少前面的重复，而不是牺牲反馈。

## 3. 准备阶段缺少的是组合检查，不是更多测试数量

原52项控制对错误政策、诊断隔离、任务、工作链和库存提供了证据；但准备报告没有给出足以证明以下组合可运行的容量结果：

> **新增初始诊断＋首末观察保护＋真实工具返回＋下一次模型请求。**

此前方案也低估了这个组合的输入成本。下一轮应补上这一项直接关系科学对象的准入，而不是继续以“又通过几十项测试”作为阶段终点。

# 四、建议的最小修订：一份静态事实，当前动态状态，完整最新反馈

## 1. 首先只推广精确去重

下一版可以延续现有实现方式：**最新观察保留完整值，较早观察中的完全相同副本删除。**

将去重范围扩展到预先声明的静态观察字段，例如`initial_diagnostics`和静态`role_task`，但必须限定在：

\[
\text{同一成员}
+\text{同一证据身份与版本}
+\text{相同语义字段}
+\text{完全相同的值}.
\]

不需要先引入长期记忆系统、向量库或模型摘要。

模型一次实际输入中应能得到：

| 内容 | 保留原则 |
|---|---|
| 共同根合同及当前适用说明 | 至少一份完整内容；不同版本不混合 |
| 已授权初始诊断 | 至少一份完整内容，明确对应初始版本 |
| 当前任务、成员、代码版本与预算 | 保留真实动态状态，不能被旧观察覆盖 |
| 最新完整工具往返 | 保留原调用及原协议规定的可见反馈 |
| 较旧工具历史 | 继续按共同冻结规则处理，不为了fit随意剪断一条反馈 |

这里的“完整最新反馈”，指**v0.40已经规定给模型看的反馈**。不能借这次修订，把原本只存审计的全部stdout/API细迹又免费补入模型；那是另一项信息条件改变。

## 2. 必须守住四条信息边界

**去重只在成员自己的请求内进行。**A拥有的报告不能因后台知道内容，就出现在B或新成员输入中。

**保留的正文必须真的存在于selected请求。**不能删掉正文后只留下一个hash，声称“模型之前见过，所以等于仍然知道”。

**相同文本不一定是相同事件。**旧版本和新版本的同值、两次独立测试、不同诊断来源，不能被当作同一件事消除。去重处理重复快照字段，不删除行动与来源历史。

**初始诊断不能冒充当前诊断。**代码修改以后，保留的初始失败仍对应原初态；新的测试结果应保持独立版本、时序和含义。

即使唯一信息内容保持，位置、重复次数和注意力条件仍可能影响行为。因此这是**新Γ**，不是与v0.40行为等价的“纯工程无影响修复”。

## 3. 不采用这些快捷方式

本次不应通过删除shared的一份诊断、取消team说明、丢弃最新失败、自动摘要或自动提交取得通过；也不临时缩小2048输出预留。

如果精确去重后，**独特的必需信息与合法最新返回仍然放不下**，就应在新采样前明确返回范围或精确分页规则。不能提前保证“删重复肯定够”，更不能在正式批次中临时切换有损投影或更长context。

# 七、下一轮应同时测量工作结果与反馈机会

## 1. 主结果继续保持完整交付

提交、内容正确、过程满足及相关未知字段分别报告，不补验未提交工作区，不把公开测试通过当成隐藏验收通过。

## 2. 增加一张反馈闭环表，比增加组织计数更重要

| 阶段 | 应当记录什么 |
|---|---|
| 反馈产生 | 哪个版本执行了什么工具，返回是否保存 |
| 实际呈现 | 返回是否进入之后一次真实生成请求 |
| 后续行为 | 成员是否作出与该反馈有关的查询、修改、验证或交接 |
| 工作闭合 | 是否连接到最后固定交付 |
| 未能继续的原因 | context、团队预算、主动结束、等待无事件、真实故障分别记录 |

“没有后续输入”本身也要有分母：成员可能已经合法结束，也可能等待没有事件，不能全部解释成容量问题。

**反馈进入输入仍不等于理解或因果采用。**需要后续实际关系作为辅助证据；消息数量、任务数量和人数变化只能是过程诊断。

## 3. 不能挑出工作较深的槽，再作为新的主比较

如果某条件仍更容易早停，应保留在全库存结果中，并单列终止原因。不能只比较“已经收到过测试反馈的成功成员”，把其他成员和槽删除。

否则，原本要研究的信息布局与工作定位，会被后验选择掩盖。
