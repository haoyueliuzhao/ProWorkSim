# 二、对 v0.11 实验的逐项判断

## 1. 世界与执行能力：实质进展成立

本轮确实不再只是模拟状态变化。模型已经实际执行过读取、采用、SQL 修改、构建、查询、提交和发布；四项目机制也使用了真实上游成果，而不是后台预制的正确结果。报告同时区分了程序机制通过与模型未完成，这个界限是正确的。:chatgpt-content-reference{index="1"}

代码中的执行能力将受管 SQL 和输入表交给独立 DuckDB 进程，返回实际结果、错误和可重建的逻辑表；独立业务计算则另用 Python 实现，没有调用工作人员生成 SQL 的逻辑。

因此，可以保留：

> **有限的可执行项目群已经成为 ProWorkSim 的实际工作载体。**

仍不能扩大为完整 dbt 环境、真实企业工作流或任意代码沙箱。Jaffle Shop 的虚构数据、我们增加的组织流程和真实 SQL 执行，是三个不同层次。

## 2. 历史评价与奖励：基本边界建立了，但不是 ID‑VTDO 的有效性层

历史 episode 将责任范围、起止状态、实际经历和具体提交固定下来，不再用后续成功为先前失败补分。代码也确实从封闭快照评价，而非重新打开当前世界取得“最新结果”。:chatgpt-content-reference{index="4"}

本次对奖励模块的独立检查确认了以下有限行为：可评内容失败保留为零奖励；格式失败不自动被排除；来源不可用和评价故障保持不可训练；继承交付不产生新信用；已公开的必要过程违规与未评正文分别记录。

但下一步必须把三个对象明确分开：

| 对象 | 回答的问题 |
|---|---|
| **奖励可训练性** | 这段经历是否有可信的回报？失败也可以是可训练的零奖励。 |
| **工作有效性 \(V\)** | 记录、权限、依据和交付是否满足声明的有效工作合同？ |
| **可重配资格** | 在有效性之外，是否能可靠映射类别、恢复该成员自身动作，并满足支持条件？ |

**`reward_eligible=true` 不能直接成为 ID‑VTDO 的正例准入。**反过来，零奖励也不能一律解释为无效：某些合法阻塞或带成本的结果，需要按具体合同判断。V1 对这几层有明确区分。:chatgpt-content-reference{index="7"} :chatgpt-content-reference{index="8"}

## 3. 主批 36 段全部零奖励：应当改变后续策略，而不是扩大同一种试跑

按报告加总，主批结果是：

| 后端 | 预算停止 | 格式失败 | 制度完成 | 独立正确完成 |
|---|---:|---:|---:|---:|
| DeepSeek | 11 | 5 | 2 | 0 |
| Qwen | 0 | 18 | 0 | 0 |

DeepSeek 的两个制度完成实例缺少确切文件依赖，独立内容合同失败；Qwen 则在当前单 JSON 协议下全部首先遇到格式问题。**36 个奖励为零的记录必须保留，但它们不支持“模型一般工作能力为零”。**:chatgpt-content-reference{index="9"}

主要有三类因素交织：

**接口因素。**严格动作包装、公开格式说明和工具参数要求，阻止了部分模型进入实质工作。

**呈现与预算因素。**完整观察不断进入历史，下一请求的保守预留又影响实际可用行动次数。名义上允许 120 次决策，并不表示模型实际获得了 120 次机会。

**工作因素。**模型能够修改和运行 SQL，但仍没有完成全部采用、来源和交付要求。后续三次校准已经表明，不能将所有失败都归于模型“不会 SQL”。:chatgpt-content-reference{index="10"}

因此，下一步不是降低交付标准、补写旧依赖或删掉失败，而是：

> **在开发阶段先消除主导测量的接口障碍，再冻结新协议，检查模型真正的工作瓶颈。**

这项调整属于运行协议 \(\Gamma\) 的变化，不能以后被归入 ID‑VTDO 调权收益。

## 4. 首决策训练：可以关闭接口冒烟，但不能继续当作算法进展

训练脚本确实执行了声明的损失、反向传播、一次 AdamW 更新、保存和重载；并且只对首个真实模型输出求导，其余行为固定。源码与报告的有限声明一致。

三条奖励都为零、常数 baseline 为 0.5 时，损失为：

\[
L
=-\frac13\sum_{k=1}^{3}(0-0.5)\log \pi_\theta(y_k\mid h_k)
=\frac16\sum_{k=1}^{3}\log \pi_\theta(y_k\mid h_k).
\]

**这个目标可以产生非零梯度，因此“零奖励还发生参数更新”本身不是实现错误。**它试图降低这些已采样输出的整体似然，但不自动提供更好工作方法的信息。

还应区别：如果在一个假设环境中所有动作的真实回报都相同，那么常数 baseline 项的期望 score-function 梯度为零；有限样本仍可能产生非零梯度。**不能把有限非零梯度当成已有学习价值，也不能仅凭这三条失败推断真实模型所有动作都没有价值。**

本轮已经诚实保留了概率不匹配、操作终止、内存增长及最终一次更新；没有提高容差或删除两条不通过的样本。这些记录应保留。:chatgpt-content-reference{index="13"}

但现在不建议继续为这三条历史输出投入更多反向步数。特别是，最终完整尝试使用约 99.35 GiB 主机内存，这种为复现历史批次与缓存路径建立的方式，**需要另外验证可扩展性，不能直接成为完整工作训练的默认路线**。:chatgpt-content-reference{index="14"}

**正确归档结论是：有限首决策策略梯度链路成立；基础多轮 MARL 与工作能力收益尚未成立。**

**当前不是已经有这个集合、只差运行优化器，而是还需要通过真实团队运行建立它。**无支持和单类别的块继续保留基础 RL，不转移预算、不删除困难情境，也不凭空给类别赋权。:chatgpt-content-reference{index="17"}

# 五、D0：先建立可用且固定的模型工作接口

## 要检验的命题

> 模型的工作结果主要反映实际信息处理与行动，而不是在进入工作之前被包装协议或重复观察消耗阻断。

### 三项优先修改

**动作协议。**可以选择原生工具、受约束单动作生成，或经过充分格式初始化的单 JSON 协议。重点不是统一成某个模型最不擅长的包装，而是将适配方式明确记录，并在后续方法间固定。

格式错误也可以在新协议中被定义为一次失败决策，返回公开格式反馈、消耗预算后继续，而非必然终止整个 episode。**这属于新协议，不能拿修复后的表现覆盖旧失败。**

**来源与交付反馈。**把已存在的公开要求变成容易发现、可检查的合同。可以提供只读结构预检，指出缺少哪些公开字段、引用或依赖；不能提供隐藏正确数值，也不能自动替模型选择、采用或补齐正确来源。

对于可信执行已经记录的真实 SQL 输入，可以明确表达其执行谱系；对于业务上采用了哪些口径，仍由工作人员实际选择和声明。**“实际工具输入”与“工作人员读过的所有文件”不能混成一份来源列表。**

**上下文。**将完整历史保存与本次模型输入分开。固定当前状态、增量事件和必要历史的呈现方式，保存每次选择记录。不能因为归档里还留着旧消息，就声称它仍在模型当前输入中。

这些修改均服务于 V1 的“实际局部输入可恢复”，而不是额外给模型全局信息。

### 实验安排

先在小型开发池中做成组比较，保持起点、模型和业务要求一致，比较明确的接口配置；运行顺序随机化，保留全部格式错误、预算停止和业务错误。

**通过条件不是 100% 成功，而是跨多个实例出现可重复的合法完整交付，并且失败已经能进入有意义的工作诊断。**

接口固定后再采算法材料，不能一边改提示、筛成功，一边估计同一 \(\Gamma\) 下的经验组成。

# 六、D1–D2：建立真实团队、信息依赖表示与支持

## D1：最小的信息不对称模型团队

建议先采用三个决策角色，至少两个具有真实可训练动作：

| 成员 | 局部信息与职责 | 需要实际作出的决策 |
|---|---|---|
| **资料／接口负责人** | 字段定义、变更说明或共享权力 | 查证、提供哪些依据、何时交接、是否确认 |
| **实现者** | 当前 SQL、已采用资料与工作目标 | 识别缺口、请求、修改、构建和交付 |
| **复核者** | 独立检查视角与发布条件 | 实际读取、定位差异、要求修复或接受回应 |

这些角色不必分别对应一个项目，也不要求立即并发多线程。继续使用固定调度和单写者即可。

这里有一项关键调整：

> **被列为学习成员的提供者，不能再由请求工具自动替它选择正确证据并完成业务回复。**

路由、送达和权限检查可以由程序执行；选择证据、回应和确认应由该成员真实决策。自动服务仍可保留，但不能把它的工作记作模型成员的学习经验。

### 同一情境允许多种有效方式

例如，在完全相同的初始信息与权限下：

**提供者主动交接**，或者**实现者发现缺口后请求，再由提供者回应**，都可以完成任务。

不得通过分别提示“请主动交接”“请等待请求”，然后把两批结果当成同一运行分布中的自然方法支持。程序见证可以验证两种方式可行，但不能计入当前模型的支持。

还应设置少量针对性控制：信息持有者交换、消息迟到、旧依据并存、必要信息不可得。全信息诊断可以存在，但它属于不同信息条件，不能并入受限信息池或用作算法收益。V1 正是要求区分这些信息状态及其真实后果。:chatgpt-content-reference{index="18"} :chatgpt-content-reference{index="19"}

## D2：联合轨迹、局部投影与 Mapper

建议新增三个逻辑对象，而不是另建一套世界：

**`TeamRollout`** 保存团队实际运行、情境、协议版本和最终后果。

**`MemberView`** 恢复该成员每次实际输入，以及它自己生成的动作 token。

**信息依赖图与 Mapper** 从真实记录中识别查询、获取、交接、采用、验证和修订，形成少量可核验的联合行为类别。

必须保持以下区别：

**发送者的消息是其动作；接收者看到这条消息是观察。**

**项目依赖图是预定结构；信息依赖图是实际发生的工作关系。**

**图中的依赖是可观察关系，不是已经识别出的因果关系。**

**同义改写和不同文件名通常不是新方法；主动交接与请求后交接则可能是。**具体等价关系需要在看结果之前定义，并用正反控制检查。:chatgpt-content-reference{index="20"}

### 支持诊断怎样采样

可以先从一个小型固定情境组重复采样。例如，作为规划算例：

\[
4\text{ 个基础情境}
\times2\text{ 种信息布局}
\times32\text{ 次联合运行}
=256\text{ 条团队 rollout}.
\]

**这不是已冻结规模，也不是样本充分性保证。**同一个 Jaffle Shop 家族不会因此变成八个独立来源，三成员投影也不会变成 768 个独立团队结果。

每个成员—情境块应报告：

\[
M_\xi,\quad n_{\xi iz},\quad
v_{\xi i},\quad b_{\xi iz},
\]

同时报告从全部原始运行出发的类别产出率、映射失败、成员参与和成本。不能只在成功池内计算比例，然后据此估计生成预算。

如果只有一个类别，该块没有组成优化自由度；若没有有效支持，就保持基础处理。**不能反复补采或改变类别定义，直到达到想要的配额。**V1 对这项支持瓶颈已有明确约束。:chatgpt-content-reference{index="21"}

# 七、D3：建立基础多轮 MARL，并先验证 \(Q=B\)

## 1. 不再把首个 response 当作完整训练对象

下一轮应覆盖所声明工作片段内，各目标成员真实产生的多轮动作。按照 V1 建议，选择一种现有 CTDE actor–critic／PPO 型基础配方，固定参数共享、优势、归一化、critic、熵与 KL 处理。

**第一阶段只重配 actor 经验，其他项保持基础配方。**这是 V1 的设计，而不是再发明一套基础多智能体 RL。:chatgpt-content-reference{index="22"}

没有必要坚持现有某一个模型必须成为最终训练对象。可以在开发池比较可训练候选，选定后冻结。但强 API 模型产生的成功轨迹不能被算作另一个训练模型的当前支持。

## 2. 基础学习信号需要先成立

当前三条零奖励输出的非零梯度，不足以证明可用学习信号已经建立。

应先检查：是否存在可信的结果差异、有效优势、完整动作掩码，以及训练后在未用于更新的检查情境中可解释的工作变化。

这里不要求先取得大规模显著收益才能进行算法预检；但也不能仅凭 loss、梯度范数或参数元素变化就通过“已经能够学习工作”的门槛。

必要时可以进行明确标记的格式或基础工具冷启动，所有后续方法使用相同来源与用量。**冷启动完成后应重新采样；Teacher 材料不计作当前团队自然支持。**

## 3. 权重物化先过恒等与保持检查

V1 的核心验收不是“权重确实改变”，而是：

| 检查 | 必须成立 |
|---|---|
| **\(Q=B\)** | 恢复原基础损失、归一化和规定更新，不能残留成功样本过滤 |
| **合格分支重配** | 使用 \(q/b\)，其余可训练失败保持基础权重 |
| **动作归属** | 同事消息、工具返回不成为接收者的生成目标 |
| **无自身动作** | 不为该成员制造 actor 梯度 |
| **支持边界** | 不给支持外类别正权重，不把无支持任务质量转移到容易任务 |
| **概率比区分** | \(q/b\) 与 PPO 的新旧策略比率分别计算和记录 |

V1 给出的“基线加组成变化”形式，就是这些检查的理论依据；它也明确承认，\(q/b\) 主动改变训练 surrogate，并不是无偏改善原始环境回报。:chatgpt-content-reference{index="23"}

数值方面，新在线训练应选择可扩展的采样与复算路径，记录温度、约束解码、实际 token 和概率，核查更新前概率差异。**不要求所有新训练永久复刻旧三条样本的批次与缓存路径，但不能忽略实际行为分布与训练概率的差别。**

# 八、D4–D5：从固定材料干预进入 ID‑VTDO 算法实验

## D4：Contribution 必须测量训练之后的团队效用

固定当前学习状态——包括 actor、critic 和优化器——以及同一批联合材料。对成员—情境块 \(j\) 的某类经验，沿

\[
d_{jz}=\delta_z-q_{j,t}
\]

做小扰动，以相同更新预算训练两个分支，再在配对开发情境中实际执行，估计：

\[
\widehat C(j,z)=
\frac{
\widehat F(Q+\varepsilon d_{jz})-\widehat F(Q)
}{\varepsilon}.
\]

**它不是该成员本次执行的功劳，也不是当前轨迹奖励，而是改变训练组成之后的团队学习效果。**探测完成后必须回到共同起点进行正式更新，不能累加有利分支。:chatgpt-content-reference{index="24"} :chatgpt-content-reference{index="25"}

先验证低成本梯度代理和低维信息图特征能否预测这些结果，不必立即实现大型图神经网络。

### 必须加入的对照

| 对照 | 要回答的问题 |
|---|---|
| 基础 MARL | 是否存在总体增量？ |
| 所有成员共用类别权重 | 成员条件化是否必要？ |
| 原始成员—轨迹元重加权 | 信息结构是否超出一般验证驱动调权？ |
| 不含信息依赖的特征 | 是否只是任务或角色标签在起作用？ |
| 结构化单成员配置 | 联合交互校正是否有额外价值？ |
| 同预算随机成员对探测 | 图引导选对是否值得？ |

历史锚和覆盖项再通过相应消融检验。**仅优于均匀权重，不足以支持 V1 的主要创新。**通用元重加权必须获得可比的验证信号和外层计算资源。:chatgpt-content-reference{index="26"}

## D5：联合交互与在线闭环另行冻结

单点贡献可估以后，再对发送—接收、复核—修订等成员对做四分支比较：

\[
I_{ab}=F_{11}-F_{10}-F_{01}+F_{00}.
\]

图引导与随机选对使用相同探测预算，并保留少量非邻接对。**没有信息边不代表没有学习交互，尤其在共享参数时。**

最后才进入完整在线闭环：各方法从相同初始化和情境分布出发，更新后各自重新采集。此时控制的是相同规则与可比预算，**不能再声称各方法始终使用逐字相同的经历**。:chatgpt-content-reference{index="27"} :chatgpt-content-reference{index="28"}

# 九、预算与规模：充足资源应投入哪里

这些记录提示：**当前问题不能仅通过提高 API 金额上限解决。**协议失败、重复观察、有效类别稀缺和训练数值路径，都可能比 API 单价更限制研究推进。

建议资源优先顺序是：

**接口开发与真实团队可行性 → 同情境支持密度 → 基础多轮学习 → 配对贡献校准 → 独立来源与结构测试。**

不要仅重复少数成功场景，也不要把所有资源继续用于历史三条失败的精确反向。

同时，ID‑VTDO 的总成本必须包含采样、正式更新、探测试训、探测开发执行及外层优化。只固定内层训练步数、却给新方法增加大量开发执行，只能作为机制研究，不能宣传为同总资源下的收益。:chatgpt-content-reference{index="30"}

训练、贡献开发和独立测试应先按来源及世界家族划分，再生成情境与信息布局。Jaffle Shop 可以支撑首个机制闭环；后续强泛化结论需要新增独立可执行来源，而不是仅更换实体名和数值。

## 最终推进判断

**v0.11 的成果应保留：模型确实进入了世界，SQL 确实执行了，历史评价确实固定了，有限参数更新也确实发生了。**不能因为没有取得成功率或学习收益，就否定这些已声明的接口成果。

但下一阶段必须停止用这些接口成果代替算法前置条件。

建议近期实际推进顺序为：

\[
\boxed{
\text{固定可用的模型工作接口}
\rightarrow
\text{建立信息不对称模型团队}
\rightarrow
\text{恢复联合与局部经历并普查支持}
\rightarrow
\text{基础多轮 MARL 与 }Q=B\text{ 验收}
}
\]

在此基础上，再进行：

\[
\boxed{
\text{固定材料贡献干预}
\rightarrow
\text{结构与成员配置对照}
\rightarrow
\text{联合探测和在线闭环}
}
\]

**下一轮最重要的成果，不是更多平台模块、更多调用，或者第二次参数更新，而是第一次明确建立：哪些真实联合经历可被哪些成员学习、它们具有哪些有效工作方式，以及基础学习是否能够利用这些经历。**这才是从 ProWorkSim 环境建设进入 ID‑VTDO 科学问题的实质转折。
