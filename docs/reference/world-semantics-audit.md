## 三、新发现的两个世界机制问题

### 问题一：工作依赖无环，不代表“工作—发布”系统可执行

**位置：`workflow.py::validate_workflow`。**

当前验证会检查工作 ID、依赖引用、发布组名称和普通工作依赖中的环，但没有联合检查：

\[
\text{工作激活}
\leftrightarrow
\text{发布组开放}
\leftrightarrow
\text{事件触发条件}
\]

之间的可达性。

本次用原函数实际确认，它会接受下面这个配置：

```text
工作 A：只有发布组 R 开放后，才可以出现。
事件 R：只有工作 A 已经 accepted，才开放发布组 R。
```

A 没有普通工作前驱，所以普通依赖图没有环；但 A 永远不能出现，R 也永远不能触发。

即使假设“任何已经激活的工作，都能被工作人员立即正确完成”，整个系统仍然没有可达的工作节点。复现配置保存在审计包的 `unreachable_workflow.json`。

#### 应当如何定级

这是一个**新配置准入缺陷**。

它不推翻已经成功运行的四种内置配置；但当前 `validate_workflow` 不能被当成自动合成新规格的充分可执行性门槛。

#### 建议修复

对当前有限规格语言，先做一个联合可达性检查即可：从 `initial` 发布组出发，交替扩展可能被执行的工作和可能触发的发布规则，直到不再变化，然后报告不可达节点及其原因。

这仍只是**结构可执行的必要条件**，不是专业任务可解性的充分证明。

同时，不要把修复做成“一律禁止所有回环”。真实审阅返工可以有可达入口和合法出口；需要拒绝的是无入口、无出口或相互等待的配置错误。

---

### 问题二：一次 scope 回复会清除不相关任务的阻塞

**位置：`kernel.py::World._drain_events` 的 `manager_reply` 分支。**

目前逻辑相当于：

```python
for item in work_items:
    if item.status == BLOCKED and reply.topic == "scope":
        item.status = OPEN
        item.blocker = None
```

回复没有与具体工作或阻塞记录绑定，而是遍历所有阻塞工作。冻结提交和当前 `main` 中，这个源文件的 Git blob 相同。

本次使用原始方法的 AST，在明确标记为单元夹具的事件回调中复现：

| 工作 | 回复前 | 唯一发生的事件 | 回复后 |
|---|---|---|---|
| `memo-1` | 等待经理确认情景假设 | 经理回复 scope | `open`，阻塞清空 |
| `note-1` | 等待客户补充受众要求 | 没有收到对应答复 | **也变成 `open`，阻塞清空** |

这里没有声称做过完整 WorkerSession 回放；但被执行的状态转换逻辑来自核对过字节的原始方法。

#### 为什么它对当前目标重要

在一个主任务的简单原型里，“所有阻塞都等口径”可能暂时掩盖问题；引入 fork 以后，不同工作会因为不同原因等待。

**世界应当能够区分“收到了一条消息”和“这项工作所缺的条件已经满足”。**否则模型做出的求助与回复没有准确的业务后果。

#### 建议修复

将阻塞从一个自由文本字段，提升为最小结构化对象：

```text
blocker_id
work_item_id
kind
requested_role
required_scope_version
status
resolution_ref
```

消息回复应解析对应请求或阻塞，而不是解除所有 blocked 工作。一个工作存在多个阻塞时，只有相关阻塞全部解决、其他前置条件也满足，才能重新开放。

**旧回复、错角色回复和不相关回复，都不应改变这项工作的就绪状态。**

这不需要先部署多个更强的模型；先把固定角色的工作语义做正确，反而更容易检验。

## 四、“四种拓扑”的表述需要校正，但不影响实例计数

我直接比较了 `make_workflow("continuous", "chain")` 与 `make_workflow("continuous", "coordination")`：

> **除 `topology_id` 外，两者生成的工作与事件规格完全相同。**

coordination 的差异由 `designer.py` 强制使用 clarification 信息配置体现；规则机制实验又额外对这一条件注入了旧 memo。

因此，更准确的记录应是：

**四种工作配置，三种不同工作图结构，另有信息获取方式与错误注入条件的变化。**

这不是文字挑剔，也不意味着 16 个世界要改成更少的世界。它关系到以后到底在覆盖什么。

建议分开记录：

| 维度 | 当前对应对象 |
|---|---|
| 工作图结构 | chain、fork、selective |
| 信息获取方式 | mail、clarification |
| 事件策略 | 发布新披露／假设、修改 brief |
| 错误注入 | 是否故意保留旧 memo |
| 布局 | standard、shifted |

另外，两项结果还应保持当前的有限解释：

**移动布局**同时提供了对应指南，支持“语义定位映射能够工作”，不是任意未见表格布局理解的证明。

**selective**明确告诉工作人员只改 note，并要求保护 model/memo，支持“按已说明的影响范围进行选择性更新”，不是自主发现全部影响范围的证明。相应要求确实写在工作节点生成逻辑中。

这些限定不削弱工程价值，只是帮助我们避免把不同能力提前合并。

## 五、本轮最值得继续研究的，不是上下文优劣，而是“工作依据”尚未完整进入世界

两个失败案例都很有价值：

- seed317/history 使用旧增长率 0.07，新要求为 0.09；
- seed331/reset_context 使用旧增长率 0.05，新要求为 0.07。

两者记录中都只有第一轮 scope 回复。

独立评价正确拒绝了这些成果；但两个世界的 freshness 记录仍全部为 `current`。

### 1. 这不等于 freshness 函数再次出错

当前 `model` 的必要依赖只有 `financials`；`scope` 没有进入模型的必要输入关系。freshness 的明确计算依据也是“声明依赖与必要边”，不是所有业务条件。

本次组件诊断中，仅推进 scope 版本而不改变 financials，model/memo 也仍然为 `current`。

所以这里应区分：

\[
\text{声明的数据来源版本未过期}
\neq
\text{所用工作依据仍然适用}
\neq
\text{成果正确}
\]

**不能因为错误成果显示 current，就直接判定 F2 修复失败；真正欠缺的是“已批准假设”这个业务对象及其依赖关系。**

### 2. 下一步应把批准依据变成一等对象

建议增加 `ApprovedBasis` 或 `AssumptionRecord`，记录：

```text
依据 ID 与版本
适用的工作／需求版本
确认者及其权限
适用期间与生效时间
可见的确认凭据
替代了哪个旧版本
```

工作模型不只依赖披露，还应能够绑定它实际采用的假设依据。这样，“数据没有变，但批准假设变了”才能成为世界内真正可表达、可传播的变化。

但要保留角色隔离：**不要直接给分析师读取经理私有 scope 的权限。**可以让经理通过授权邮件、确认文档或实际回复，形成分析师可引用的确认凭据。

### 3. 不要把解决方法退化成“每轮必须再问一次经理”

这会把工作机制重新压回固定脚本。

如果适用的确认已经存在于可读邮件或文档中，模型可以直接使用；只有信息缺失、版本不适用或权限不清楚时，才需要澄清。

因此，验收对象应是：

> **所采用的依据是否适用于当前工作。**

而不是：

> 是否调用过 `mail_send(topic="scope")`。

同样，不应把所有已读材料自动加入“实际采用来源”。访问、理解和采用是不同的对象。

### 4. 失败诊断也应沿依赖链归因

这两个案例的一处旧增长率，导致预测收入、利润、估值、EPS、备忘录指标等多项检查同时失败。公开失败项中可以看到这种传播。

**它们不应被简单统计成多个相互独立的能力缺口。**否则后续课程可能同时增加计算、报告、估值等训练题，实际上却没有处理最先出现的依据失效问题。

现阶段更有价值的工作，是记录：

\[
\text{依据失效}
\rightarrow
\text{输入沿用}
\rightarrow
\text{计算传播}
\rightarrow
\text{跨产物一致但共同错误}
\]

这既能改善世界建模，也能为将来的训练诊断提供更准确的对象。

## 六、当前离“较完善模拟工作世界”还差什么

目前的系统已经不只是一个固定顺序脚本，但仍属于**可配置的有限经营分析世界**。四种配置继续使用同一个合成经营模型族、预定义产物和固定环境角色；事件效果限定为发布披露、发布 scope、修改 brief。

我认为当前最重要的三个缺口不是规模，而是以下机制。

### 1. 工作过程中的变化，还弱于“完成后进入下一阶段”

现有发布规则主要由 `after_accepted` 驱动，适合模拟先完成一轮，再进入下一轮。

但更完整的工作世界还需要处理：

**分析尚未完成时需求变化；等待澄清时新版本到达；成果已经提交、尚未审阅时上游依据变化。**

这些情境不能全部被替换为“先结束当前工作，再开启新工作”。

下一步应明确需求过期、撤销、重新提交和新开工作项的规则。历史批准应继续保存，但不能自动被解释为对新版本的批准。

### 2. 工作人员有角色名称，还需要更完整的职责与工作后果

现在应优先提升的不是角色模型数量，而是职责的准确性。

经理需要知道自己在确认哪个工作、哪个版本和哪类问题；审阅者应检查被提交的具体成果，并区分自己能验证的内容与尚未确认的内容；客户需求应真实改变交付要求，而不只是改变一个字段。

例如，目前 note 的受众检查主要是与 brief 的 audience 字段匹配。它形成了有效的有限约束，但不能直接代表完整的“面向不同客户调整说明方式”的工作。

可以逐步为不同受众增加少量明确的内容要求，但不必立即引入复杂的主观质量总分。

### 3. 世界有效性不应由“模型做对了”代替

一个模型顺利完成任务，只证明某条路径可用；它不能证明世界在其他合法行动下仍然自洽。

世界建设阶段更需要检查：

**正确行动是否得到恰当结果，错误行动是否留下真实后果，信息不足是否能合理阻塞，无关消息是否不会推进工作，需求变化是否只影响该影响的对象。**

因此，不能只扩展更多成功世界，也需要覆盖等待、失败、局部完成、撤回和修订等状态。

## 七、建议将下一轮明确命名为“工作世界语义与生命周期完善”

不建议下一轮按报告末段直接扩大上下文样本，或者增加训练种子。先把下列工作完成，会更贴近当前课题目标。

| 工作包 | 主要实现 | 验收重点 |
|---|---|---|
| **W1：规格与阻塞语义** | 联合发布可达性、结构化阻塞、回复作用域 | 错误配置被识别，不相关回复不推进工作 |
| **W2：工作依据版本化** | 假设确认、适用范围、可见凭据及依赖边 | 仅假设变化也能产生准确的状态后果 |
| **W3：执行中的需求变化** | 进行中／待回复／待审阅阶段的变化规则 | 历史事实不被改写，新要求不误用旧批准 |
| **W4：角色与交付物语义** | 有范围的确认、审阅与客户要求 | 角色行为针对实际问题，而不是固定剧情 |
| **W5：世界机制验收** | 程序见证、错误策略、固定模型试跑 | 评价世界是否自洽，而不是训练 loss 是否下降 |

这里不要求立即实现通用字段级因果分析、完整办公 GUI 或多员工共同学习。可以继续使用当前产物级依赖与单目标分析师，把有限机制先做扎实。

### 下一轮最小验收情境

我建议至少覆盖下面这些情境，而不是先增加随机种子数量：

| 情境 | 应当出现的结果 |
|---|---|
| 两个任务因不同原因阻塞 | 只解除被实际回应的阻塞 |
| 工作与发布条件互相等待 | 构建时报告不可达，不让 Agent 无限等待 |
| 财务数字不变，仅假设修订 | 识别工作依据变化，不自动修改文件 |
| 仅受众要求变化 | 未受影响的模型和备忘录保持内容与适用状态 |
| 旧澄清回复晚到 | 保留历史，但不把旧确认应用到新需求 |
| 待审期间上游发生变化 | 批准绑定明确版本，当前适用性单独判断 |
| 关键信息确实无法取得 | 合理阻塞或结束，不虚构信息 |
| 正确完成且无实质变化 | 允许直接交付，不强制返工或重复操作 |

这些是**世界机制覆盖条件**，不是效果研究样本量。可以先用透明程序策略检验，再用固定模型验证交互是否自然、工具是否可用；目标模型此时仍是测试工作人员，不必同时成为新的训练对象。

## 最终推进判断

**本轮成果应保留：旧契约修复有实质实现，有限结构可运行，匹配上下文对照与参数训练接口也都有明确记录。新增问题不构成推倒重做的理由。**

但当前更合适的阶段判断是：

> **已有一个具备真实文件、版本、角色边界和有限事件规则的工作世界原型；正在补全工作依据、任务生命周期和协作语义，尚未到以学习收益为主要验收目标的阶段。**

下一轮优先修复**发布可达性与定向解除阻塞**，随后围绕**假设版本、执行中变更和角色职责**深化世界。训练冒烟可以归档，暂不扩展为新的 GPU 实验。

**当前最重要的标准不是模型做对更多题，而是世界中的每一次确认、修改、等待、审阅和需求变化，都产生合理、可解释、可验证的工作后果。**
