**看过原论文、官方运行代码和公开样例后，APEX 的实际任务构成，比“模拟公司里的员工完成完整项目”更具体，也更偏分析型：它主要让一个 Agent 在已有项目资料和工作产物中，完成一项有明确边界的专业委托。**项目背景可以很大，但单个任务可能只要求计算一个数、完成一组敏感性分析，或返回一份检查清单。:chatgpt-content-reference{index="0"}

这对我们的课题有直接影响：**应继承 APEX 的“丰富项目上下文＋明确工作要求”，但不能把它已经实现的能力，等同于我们计划增加的动态工作人员、连续项目推进和审阅返工。**

先说明材料范围：下文主体是**原版 480 题**，不是 1.1 的 240 题。原始 Hugging Face 文件目前设有访问条件，本次没有取得完整的 `tasks_and_rubrics.json` 和 `world_descriptions.json`，因此全量构成采用论文公布的统计，具体任务采用能直接核实的原论文与官方代码样例；当前官网的 1.1 样例另行标明，不混入原版统计。:chatgpt-content-reference{index="1"}

## 一、原版的基本单位：33 个项目世界中的 480 项任务

### 1. 职业与世界构成

原版的三个职业各有 160 题，但项目世界数、文件规模和交付要求不同。下表来自论文表 1。:chatgpt-content-reference{index="2"}

| 职业 | 项目世界数 | 任务数 | 平均每世界文件数 | 要求文件交付的任务 |
|---|---:|---:|---:|---:|
| 投资银行分析师 | 10 | 160 | 172 | 27，约 16.9% |
| 管理咨询顾问 | 11 | 160 | 165 | 11，约 6.9% |
| 企业律师 | 12 | 160 | 161 | 20，12.5% |
| **合计** | **33** | **480** | **166** | **58，约 12.1%** |

每个世界包含 8—20 个任务，平均约 14.5 个。世界是项目级背景，任务是从中提出的具体工作要求，**不是一个世界对应一个必须从头做到尾的大项目任务**。:chatgpt-content-reference{index="3"}

### 2. 世界是怎样形成的

构建阶段，专业人员先扮演项目中的不同角色，开展研究、沟通和成果制作，再据此设计任务。官方发布文章明确描述了专家在 Google Workspace 中模拟同事协作的做法。:chatgpt-content-reference{index="4"}

例如，论文给出的咨询世界是：一家咨询团队为健康消费品客户制定五年市场扩张战略，涉及需求、消费趋势、市场进入和产品机会。**这是世界的项目主题，不是一道要求 Agent 一次完成全部战略项目的题目。**:chatgpt-content-reference{index="5"}

对我们的参考是：

> **项目负责产生相互关联的材料与业务语境；任务负责指定当前需要完成的一项工作。**

这两个层次应该分别生成、分别保存。

## 二、最重要的构成事实：87.9% 要求文字回复，只有 12.1% 要求文件交付

原版任务的最终输出分布如下。数量来自论文第 3.2 节，比例按 480 题计算。:chatgpt-content-reference{index="6"}

| 最终交付形式 | 数量 | 占全部任务 |
|---|---:|---:|
| 控制台文字回复 | 422 | 87.9% |
| 新建电子表格 | 14 | 2.9% |
| 修改已有电子表格 | 16 | 3.3% |
| 新建文档 | 20 | 4.2% |
| 修改已有文档 | 2 | 0.4% |
| 新建演示文稿 | 5 | 1.0% |
| 修改已有演示文稿 | 1 | 0.2% |
| **合计** | **480** | **100%** |

文件交付任务进一步分为：**39 个新建任务、19 个修改任务**；按文件类型合并，则为 30 个表格任务、22 个文档任务和 6 个演示文稿任务。以上是对官方数量的加总。:chatgpt-content-reference{index="7"}

### 这个分布应该怎样理解？

**第一，文字回复不等于简单问答。** 最终只回复一个数，也可能需要先定位模型、理解参数口径、读取其他材料并进行计算。

**第二，不能反过来假设每道文字题都需要重建完整模型。** 有些题确实只是对既有成果进行受约束的读取与组合。题面的简短或冗长，都不能替代对实际依赖的分析。

**第三，文件输入、过程中的文件操作和最终文件交付，是三个不同变量。** 上表只统计最后要求交什么，不统计执行中读写过什么。

因此，我们的任务记录应至少分开标注：

\[
\boxed{
\text{输入材料复杂度}
\quad
\text{执行与状态修改复杂度}
\quad
\text{最终交付复杂度}
}
\]

不能把“最终输出是 Excel”当成高质量工作任务的必要条件，也不能因为输出是短文本，就把它当成普通静态 QA。

## 四、直接拆解能核实的原版任务

下面只分析公开题面能够确认的结构。所列依赖和执行环节是对任务要求的分析，**不是声称已经查看了完整工作簿、参考答案或实际 Agent 轨迹**。

### 案例 A：从既有模型与指定材料中计算一个指标

**来源：原论文第 3.2 节的公开例题。**

任务要求使用 DCF 模型中的隐含股价，以及日期为 2025-12-23 的年度财务材料中的摊薄 EPS，计算 KVUE 的市盈率，并保留两位小数。:chatgpt-content-reference{index="12"}

| 拆解维度 | 题面可以确认的内容 |
|---|---|
| 工作目标 | 返回指定口径的市盈率 |
| 输入对象 | 既有 DCF 模型、指定年度财务材料 |
| 来源约束 | 股价必须来自模型，EPS 必须来自指定材料 |
| 核心计算 | 模型隐含股价 ÷ 摊薄 EPS |
| 最终交付 | 一个经过舍入的数字回复 |
| 是否必须新建文件 | 题面没有要求 |
| 是否必须重建整个 DCF | 题面不能支持这个结论 |

它不是“去网上搜索 KVUE 当前 P/E”，也不是“随便找一个股价除以 EPS”。**正确性取决于选对两个带有业务限定的输入。**

对我们的启发是：一种有效工作任务可以很小，但应有**明确来源约束和输入依赖**。不必给每道题都附加多角色协作、长报告和文件交付。

---

### 案例 B：在已有并购模型中增加双对象敏感性分析

**来源：Archipelago 官方示例，World 221。**代码明确把默认任务标为：

`task_9ba58a6197114140877a1df1754d2993`。:chatgpt-content-reference{index="13"}

任务要求修改现有并购模型，分别计算 BBDC 与 TVPG 股东的增厚／摊薄结果，并建立两份敏感性分析。变化维度是出价溢价与现金对价比例，同时调整 EBIT 协同效应和交易后收购方股价下行情景参数。:chatgpt-content-reference{index="14"}

| 组成部分 | 实际要求 |
|---|---|
| 初始工作状态 | 已经存在一个并购模型 |
| 分析对象 | BBDC 与 TVPG 两方股东 |
| 敏感性维度一 | 出价溢价：10%、20% |
| 敏感性维度二 | 现金对价：10%、15% |
| 额外参数变化 | EBIT 协同效应提高 480 个基点；指定股价下行情景参数降低 210 个基点 |
| 输出精度 | 百分比，保留两位小数 |
| 交付要求 | 修改原模型，增加两份敏感性分析 |

按题面给定的组合计算，至少涉及：

\[
2\text{ 个对象}
\times
2\text{ 个溢价设定}
\times
2\text{ 个现金比例设定}
=
8\text{ 个结果位置}
\]

但任务不是“把八个数贴在回复里”就完成，因为它明确要求修改已有模型。:chatgpt-content-reference{index="15"}

**它最值得借鉴的地方是：任务复杂度来自已有模型中的依赖和参数传播，而不是来自一个很长的任务提示。**

对我们的模拟器而言，这种任务自然需要区分：

**基础模型状态、任务给定的参数变化、模型重算结果，以及新增的展示区域。**

不过，公开题面并不能告诉我们原始评分器是否充分检查了公式可重算性。**“要求修改模型”与“验证器确实检查模型语义”仍需分别确认。**

## 五、当前官方样例提供的补充：实际工作要求往往比职业名称更窄

以下三个样例来自当前 **APEX-Agents 1.1 官网**，仅补充任务形态，不能据此反推原版 480 题中的比例或原始措辞。

| 领域 | 当前公开样例实际要求 | 对任务设计的启发 |
|---|---|---|
| **投行** | 在股价设为 87 美元的条件下，寻找五类业务驱动因素使 IRR 降至指定临界值的位置；同时处理逐年 EBITDA 不低于 9,100 万美元的约束，并新建结果工作表。 | 不只是“跑几组参数”，还包含临界点搜索和约束优先关系。:chatgpt-content-reference{index="16"} |
| **咨询** | 先读项目经理邮件，再按照指定的数据质量／缺口记录执行 SKU 生命周期分析，返回四组前二项组合，以及两个最常见平台／应用。 | 任务要求可能藏在沟通记录中；最终只需紧凑的结构化回复。:chatgpt-content-reference{index="17"} |
| **法律** | 检查合资协议签署前的特定形式问题：顶层章节顺序、孤立编号、签字人姓名字段；明确排除部分其他问题和实质商业条款。 | 审阅质量不仅是找出更多问题，还包括不超出本轮委托范围。:chatgpt-content-reference{index="18"} |

这三个例子共同提醒我们：

> **专业任务不是“尽可能全面地发挥专业能力”，而是在当前业务委托内做恰当的工作。**

特别是第三个例子，模型即使发现了其他合同问题，也不能因此忽略用户明确限定的检查范围。对训练而言，“知道什么时候不扩展任务”同样是工作能力。

## 六、APEX 的任务包实际怎样组织：共享世界＋任务覆盖层

官方代码比抽象描述更有参考价值。

运行示例先加载世界数据，再按需加载任务专属文件；世界内部区分普通文件系统与应用数据。任务之间通过 `world_id` 关联到共同世界。:chatgpt-content-reference{index="19"}

| 组成 | 官方文件或对象 | 作用 |
|---|---|---|
| **世界描述** | `world_descriptions.json` | 按世界 ID 关联项目世界的描述与元数据 |
| **任务与评分要求** | `tasks_and_rubrics.json` | 提供题面、领域、世界关联及 rubric |
| **共享世界快照** | `world_files_zipped/<world_id>.zip` | 提供该项目世界的基础材料和应用状态 |
| **任务专属输入** | `task_files/<task_id>/` | 在共享快照之上补充或覆盖本任务需要的文件 |
| **文件型参考交付物** | `gold_files/<task_id>/` | 保存对应任务的专家参考文件 |

上述文件组织可由官方仓库目录和运行示例核实。:chatgpt-content-reference{index="20"}

### 1. 没有任务附件，不代表没有输入材料

代码先加载世界，再判断是否存在 `task_input_files`。因此，某个任务没有专属输入文件，仍然可能依赖世界中大量已有材料。:chatgpt-content-reference{index="21"}

对我们而言，这个设计比“每道题复制一套附件”更合理：

\[
\text{任务初始状态}
=
\text{共享项目状态}
+
\text{本任务的局部变化}
\]

这也为同一个项目产生不同任务情境提供了基础。

### 2. 运行时是工具环境，不要求完整 GUI 复刻

Archipelago 是通过 MCP 暴露应用能力的无界面环境，负责数据载入、工具访问和状态快照。它不是要求所有任务都通过浏览器点击来完成。:chatgpt-content-reference{index="22"}

因此，我们可以先实现文件、邮件、表格和计算的真实语义，不必先重建完整办公软件界面。

### 3. APEX 使用的是封闭项目资料空间

原版关闭 Web 搜索，必要资料预先放入世界；核心应用覆盖日历、聊天、代码、文档、文件、邮件、PDF、表格和演示文稿。:chatgpt-content-reference{index="23"}

这意味着，第一版参考 APEX 时可以优先解决：

**在可复现的资料空间中发现信息、理解既有产物并完成工作。**

开放互联网中的来源发现、实时数据漂移和外部服务不稳定，应视为后续额外维度，而不是默认已经包含在 APEX 范式中。

## 七、最需要纠正的理解：它不是在线多员工协作模拟器

这一点直接关系到我们前面设计的“各个模型充当工作人员”。

### 1. 专业人员扮演角色，主要发生在世界构建阶段

专家协作生成工作历史、邮件和交付物，是 APEX 的世界生产方法。不能据此推断正式评测时也部署了客户模型、主管模型和审阅者模型，与被测 Agent 持续互动。:chatgpt-content-reference{index="24"}

### 2. 原版基线要求 Agent 独立完成任务

原论文公布的系统提示明确要求 Agent 尝试独立执行，并且**不能请求帮助或进一步澄清**。:chatgpt-content-reference{index="25"}

所以：

\[
\text{读取已有邮件寻找口径}
\neq
\text{向一个在线主管询问并获得新回复}
\]

两者都可能重要，但不是同一种能力。

### 3. 同世界任务不自动构成连续项目执行

官方运行示例为一个任务启动新环境，加载世界快照与任务输入，运行 Agent，最后保存快照和评分；它并不是默认把上一任务的输出作为下一任务的输入，连续推进全部项目。:chatgpt-content-reference{index="26"}

因此，比较准确的定位是：

| 维度 | APEX 原版可核实的设计 | 我们计划增加的部分 |
|---|---|---|
| 工作环境 | 丰富的项目资料和工具状态 | 能持续推进的项目状态与事件机制 |
| 工作人员 | 专家构建角色历史；被测 Agent 独立执行 | 参数固定或可训练的在线环境工作人员 |
| 任务流 | 项目世界中的具体委托与工作类别 | 由实际行为、依赖变化和需求产生的新工作 |
| 反馈 | 完成后的 rubric 评价 | 世界内审阅反馈、真实修订，以及训练侧评价 |
| 跨任务状态 | 单任务快照执行 | 有控制的跨阶段状态继承 |

右栏是我们的拟议扩展，不应写成 APEX 已经提供的现成功能。

## 八、对 ProWorkSim 的直接参考：先定义工作操作，而不是先建“完整公司”

从上述统计与样例出发，我建议把第一版任务空间分成几个**可独立组合的轴**，而不是只使用“投行／咨询／法律”或“DCF／LBO”标签。

### 1. 业务内容与工作操作分开

以下是为我们提出的分类，不是 APEX 官方重新统计出的频数。

| 工作操作 | 需要模拟的核心机制 | 已核实的参考形态 |
|---|---|---|
| **定位与组合证据** | 找到适用来源，确认定义和期间 | KVUE 指定来源的 P/E 计算 |
| **改变假设并重算** | 参数变化沿已有模型传播 | 并购模型中的协同效应调整 |
| **情景比较与边界搜索** | 多组参数、临界点、约束切换 | 并购敏感性表；1.1 的 LBO 临界点样例 |
| **从材料中归纳统计** | 把邮件要求与半结构化数据连接起来 | 1.1 的 SKU 生命周期分析 |
| **限定范围的审阅** | 找问题，同时遵守审阅边界 | 1.1 的协议签署前检查 |
| **形成或修改交付物** | 真正写入文件，并保留可用结果 | 原版 58 个文件交付任务 |

同一个业务模型可以承担不同操作。例如 DCF 不只是“生成一个 DCF”，还可以用于读取结果、调整假设、验证来源、比较情景、检查错误或解释变化。

**这种分解比按业务名词生成整道大题，更适合控制覆盖、难度和训练需求。**

### 2. 为每个任务增加这六项标注

| 标注轴 | 建议记录的内容 |
|---|---|
| **业务对象** | DCF、并购、经营分析、市场研究等 |
| **初始工作状态** | 从零开始、已有可用成果、部分完成、需要更新、存在待审问题 |
| **信息获取方式** | 题面直接给定、文件可发现、通信历史可发现、必须实时澄清 |
| **核心工作操作** | 检索、组合、重算、比较、审阅、修改 |
| **最终交付形式** | 数值、结构化回复、分析文字、文件、多个相互依赖的文件 |
| **状态延续要求** | 单任务结束，或需要被后续工作继续使用 |

其中，**实时澄清和跨任务持续使用**应明确标为超出原版基线的扩展轴。这样才能比较：新增这些机制到底训练了什么，而不是让全部变化混在一起。

### 3. 第一阶段任务族可以更贴近 APEX 的主要构成

我建议优先选择：

> **已有分析模型上的假设调整、敏感性分析与结果解释。**

理由不是它一定最容易，而是它与原版投行任务的主要分布和官方实例直接对应，也容易形成清楚的输入、状态变化和输出要求。

在此基础上保留三种交付粒度：

**短回复任务**检验信息与计算链是否正确；\
**文件修改任务**检验工作是否真正落实到产物；\
**连续工作任务**检验修改后的产物能否支持下一轮需求、审阅和修订。

这里的三种粒度是逐步增强的实验条件，**不应一开始全部合并成“每道题都要邮件沟通＋模型更新＋长报告＋主管审阅”**。否则很难定位哪个机制带来了收益，生成成本也会提前上升。

## 九、最终判断：最值得继承的是什么，不能照搬的又是什么

**APEX 最值得继承的，不是“160 多个文件、9 个应用、几个员工名字”的表面规模，而是把一个具体委托嵌入已经有业务意义的材料、模型和沟通历史中。**它的公开任务已经说明，真正的工作难度可以来自来源限定、既有模型依赖、参数变化和交付边界，而不一定来自巨大输出。:chatgpt-content-reference{index="27"}

对当前课题，我会据此作三点调整：

**工作环境**首先围绕任务相关的证据、既有产物和真实工具语义构建，不追求无差别增加文件。

**模型工作人员**分成“用于生成背景历史的角色”和“执行时在线回应的角色”。后者是需要单独验证的新增机制。

**工作任务流**先实现有边界的专业工作单元，再通过状态、产物依赖和事件将它们连接成持续项目；不能把官方 workflow 标签直接当成可执行流程。
