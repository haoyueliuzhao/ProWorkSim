**v0.10 可以保留为“统一工作人员、声明式场景和分项评价已经接通”的阶段基线。现在适合开始接入 API，让模型实际承担工作，而不必继续等待更多内核功能或新模板全部完成。**

# 二、对本轮成果的判断

## 1. R0：原评价异常的修复可以保留

报告将 null 目标、null 行等合法 JSON 中的结构错误，与业务数值错误、来源不可用、目标未评和评价器内部故障分开。它没有用“捕获所有异常并记为员工失败”来掩盖问题。:chatgpt-content-reference{index="2"}

源码中的外层评价边界也保留了已经完成的检查、读取集合和被中断检查，且不捕获进程退出等 `BaseException`。这与声明一致。**原来的输入边界缺陷可以按本轮范围关闭。**

## 2. R1／R2：运行器与业务策略确实分开了

`StaffRuntime` 只向策略提供角色自己的工具、观察、记忆和上次结果，执行策略返回的动作；没有导入核对算法、报告生成或审阅答案。

这是本轮最有价值的架构进展：**模型可以替换“如何决策”，而不需要替换世界的执行与评价机制。**

实例绑定补修也有实质意义。新版本在调用策略前核对 world、instance、branch、actor 和项目范围，避免把旧世界记忆交给同名的新世界。本次局部检查确认异实例和异分支均在策略调用前被拒绝。:chatgpt-content-reference{index="5"}

但“可信 Python 策略只收到公开端口”仍不是恶意代码沙箱保证；本轮没有作这个扩大声明，应继续保持。

## 3. R3：声明场景已经能够替代部分专用实验编排

场景构建与事件控制通过真实工具产生效果；真实执行前缀、背景构造和正式运行分别记录。未达到前缀目标时保留不可构建结果，不补写不存在的审批或读取历史。:chatgpt-content-reference{index="6"}

源码也显示，控制器只按有限的声明条件执行事件，没有调用评价器来决定何时救场。

因此，**可以保留“现有情境已经具备统一运行入口”的结论**。八个场景仍属于有限配置覆盖，其中显示名变体不是新增工作结构，重复初始构建也不是新样本。

## 4. R4：分项评价方向正确，但还不是现成的 RL 奖励

制度进度、内容质量、独立目标、过程约束和运行问题分别输出，能够避免“上游错误、下游忠实”被简单合并为成功，也避免把已知 null 与目标未知混为一谈。:chatgpt-content-reference{index="8"}

**没有统一 `overall passed` 并不是缺陷。**诊断层应该保留这些区别；未来训练需要的是在其上增加一个明确、版本化的奖励合同，而不是反过来压平原始评价。

# 三、需要补修的问题：分项评价漏列工作条件

## 1. 具体原因

`assess_episode()` 选择条件记录时使用：

```python
if state["condition_specs"][cid].get("work_id") in selected
```

但真实请求创建的条件，以及条件投影使用的字段是：

```python
"work_item_id"
```

两者不一致。

## 2. 本次实际刻画

在符合实际字段结构的内存夹具中，设置：

- P 的工作有一个不可得条件；
- Q 的工作有一个无关条件；
- 评价范围只选择 P。

执行原条件投影函数摘录与原评价筛选表达式，结果是：

| 对象 | 结果 |
|---|---|
| 条件投影 | 正确保留 P、Q 两项条件 |
| 原评价筛选 | **空字典** |
| 按规范字段筛选的独立预期 | 仅包含 P 的条件 |

这说明，**世界中的阻塞条件可以真实存在，但分项报告遗漏了其具体依据。**

这是评价诊断问题，不是本次已证实的越权、错误批准或文件损坏。也没有证据表明它推翻了本轮四个固定 R4 条件的全部结果。

## 3. 最小处理

统一使用规范字段，并通过真实会话补充三个对照：

**选中工作条件应出现；无关项目条件应排除；没有条件时应保持为空。**

不应为迁就错误筛选，向基础记录额外补写第二个含义相同的字段。修复后重新评价相关副本即可，不需要因此重做所有无关实验。

# 四、架构已经允许 API 接入，但还差一层模型适配

我的判断是：**可以开始，而且应当开始。**继续只运行专门编写的规则工作人员，已经不足以回答“模型能不能通过这套世界接口真正工作”。

但当前需要补齐三处衔接。

## 1. 策略接口可替换，场景注册仍只允许三类规则策略

`StaffRuntime` 接受通用的 `policy.decide(context)`，这是合适的接入点；但场景注册当前只支持 `reconciliation`、`report_author`、`reviewer`。

旧的 DeepSeek `run --provider` 入口仍使用旧 `World` 和 `run_model()`，**不能直接当作新多角色场景的 API 接入已经完成**。

建议新增一个薄的 `ModelPolicy`：将真实公开观察与工具定义交给模型，把模型返回转换为一个行动决策，再由原运行器执行。**它不包含核对、报告或修复答案。**

## 2. 模型服务失败不能直接算策略能力失败

当前 `decide()` 内抛出的异常都会被记录为 `policy_error`。本次用一个抛出 `TimeoutError` 的离线策略夹具确认了这一行为，**没有实际调用网络**。

对现有规则策略，这不推翻实验；接入 API 后则必须分别记录：

**服务超时／限流、模型输出格式错误、真实业务拒绝，以及世界实现错误。**

有效但错误的模型动作不能被幕后重采样替换。服务重试可以有固定规则，但必须保存每次 attempt、请求内容、返回及实际 usage。

## 3. API 原始调用记录需要独立保存

现有经历记录保存的是公开工具、观察、策略决定和世界动作，不会自动保存 `decide()` 内部发出的完整模型请求、返回、模型标识和 token 消耗。

因此，需要在模型适配层增加调用记录，并与角色机会、模型调用和世界动作建立对应关系。

DeepSeek 官方工具调用协议本身就区分了“模型提出调用”和“客户端实际执行工具”。我们应保留这种区分：**模型返回一个工具调用，不代表世界已经执行了它。**:chatgpt-content-reference{index="16"}

首轮建议限定每次决策一个动作；若收到多个调用，按预先声明的协议处理并完整记录，不能静默丢掉其余调用。

# 五、在正式模型评测和 RL 前，还要固定 episode 的评价边界

这项不是本轮已复现的业务错误，而是**从当前状态报告走向训练奖励时必须补齐的合同**。

目前默认评价选择“当前世界中每项工作的最新固定提交”。CLI 会检查世界与场景身份，但仍用当前状态和所提供的经历进行评价。

本次对原选择函数的局部刻画表明：

```text
episode 结束时：默认选择 S1
世界继续产生 S2 后：默认选择 S2
显式指定 S1：仍能选择 S1
```

这与当前“最新提交”接口声明一致，不推翻 R4 在同一固定状态上的重复评价。但未来不能让：

> 第一个模型没有完成的工作，被后续工作人员完成后，反过来给第一个 episode 记成功。

建议新增一个最小的 **EpisodeManifest**，固定：

**起止世界状态、经历区间、责任工作范围、具体提交与产物、模型与场景版本，以及终止原因。**

要保存可重新读取的边界快照或事实引用，而不仅是一串哈希。当前世界报告可以继续存在，但**历史 episode 评价与当前进度查询应分成两个入口**。

这也解决另一个问题：模型说 `done`、运行器返回等待、场景边界到达、业务接受和任务正确，不能成为同一个标签。

# 六、下一阶段采用两条并行主线

## 主线 A：尽快完成真实 API 模拟

现有两个模板适合做接口校准，不必等公开项目群完全落地才开始模型试跑。

### A0：先做薄适配验收

用明确的模拟响应检查调用协议、角色上下文、错误返回、重试、预算和 checkpoint。模拟响应只算接口测试，不算模型实验。

模型输入应由**角色任务、公开观察、真实工具结果和该角色历史**构成。不要把全世界状态、控制器未来事件表、其他角色完整记忆或独立评价答案发给模型。

首轮也不建议让模型每轮重新生成整份 memory；可以由适配器保存真实对话。上下文整理必须留痕，不能事后重写成一段“更合理的历史”。

### A1：建议先运行 36 个开发 episode

这是一个可执行的起始规模建议，尚未冻结：

| 内容 | 建议配置 |
|---|---|
| 场景 | finance-direct、finance-route、report-direct，以及提交前／待审／接受后变更三个链式场景 |
| 模型后端 | 2 个 |
| 每个场景、每个后端 | 3 次独立运行 |
| 合计 | **36 个 episode** |
| 目标角色 | 每个场景只替换一个指定执行角色 |
| 其他角色 | 使用固定版本规则策略 |
| 用途 | 工具可用性、上下文、能力缺口与成本诊断 |

一个后端可以先沿用已有 DeepSeek 接入经验；另一个优先选择**后续能够取得相同版本权重、支持实际训练的模型服务**。具体模型和服务参数在执行前核实，不把返回别名视为不可变权重身份。

建议每个 episode 最多 **120 次目标模型决策**，单次输出上限可从 **8192 token** 起步，以实际模型支持和任务输出长度为准。环境角色机会、累计 token、HTTP attempts 和金额上限另外冻结。

这批不是正式泛化测评。失败全部保留，不通过换种子、追加预算或规则策略补交付获得“成功”。

### A2：随后再测试有限的多模型工作人员

在少量独立场景中，将作者与审阅者同时换成模型，观察真实协作是否成立。

但它应与“模型执行者＋规则审阅者”分开报告。**改变审阅者就改变了环境反馈，成绩不能直接当作执行模型能力增益。**首轮 RL 仍建议固定环境同事策略，只训练一个目标策略。

## 主线 B：让公开可执行项目群成为主要任务载体

**现有核对和有限句式报告可以保留为回归负载，但不应成为最终 Agentic RL 的全部任务空间。**

建议优先使用 `jaffle_shop_duckdb` 作为候选执行基础：它包含客户、订单和支付数据，以及可在本地运行的 dbt 模型、测试和文档。官方也明确说明其数据是虚构的，项目是自包含示例，并不覆盖完整企业 PR／CI 流程。:chatgpt-content-reference{index="19"}

我们增加的组织协作与事件属于研究设计，不能说成原仓库提供了完整真实工作流。

### 首个四项目组合

| 项目 | 实际工作 | 项目联系 |
|---|---|---|
| **P0：数据准备** | 核对客户、订单、支付输入，建立可发布数据与定义 | 提供共同输入 |
| **P1：经营指标** | 编写、修改 SQL/dbt 模型，运行测试并发布指标接口 | 与 P2 协调共同口径与粒度 |
| **P2：客户分析** | 使用共同数据和指标完成客户粒度分析 | 可以向 P1 提出接口或定义问题 |
| **P3：集成核验** | 读取 P1/P2 实际成果，核对一致性并形成交付 | 汇合前序项目成果 |

**并行交叉不能只是“P1、P2 都读取 P0”。**应当让两者对客户标识、统计期间或指标粒度存在真实协调需求。

同时，先提供一份可用的共同接口，让两项目能够启动；反馈跨版本发生，不把双方最终完成设置成相互等待的死锁。

### 这条主线最重要的实现变化

模型必须能够：

**编辑真实 SQL／配置，执行数据库查询，运行构建和测试，查看实际错误，再修改和交付。**

不能预先把查询结果算好放进 JSON，让模型复制字段，然后称为数据工程工作。

这些能力应在隔离工作空间中执行，隐藏验证器、控制区和 API 密钥不可见；代码、数据库和输出文件的变化需要进入世界版本及提交记录。**不能让终端绕过 WorldCore，随后又被恢复机制当作未提交文件覆盖。**

可以先限制为当前项目需要的文件、SQL、构建和测试能力，不必立即开放任意网络、宿主 Shell 或复杂生产数据库。

# 七、公开项目群如何建立模型能力基线

完成一个项目群的可行执行后，再扩大实例，而不是重复原教程的成功命令。

建议构造明确的新需求或受控问题，例如：

**订单状态口径变化、重复记录导致汇总膨胀、连接关系错误、客户粒度接口调整，以及发布后下游结果更新。**

公开要求应足以判断工作目标；隐藏测试只实现这些要求，不额外增加模型无从得知的条件。不同但等价的 SQL 和文件组织应允许通过。

一个后续主批的参考规模是：

\[
12\text{ 套需求／数据实例}
\times
2\text{ 种事件配置}
\times
2\text{ 个模型}
\times
3\text{ 次运行}
=
144\text{ 个 episode}
\]

这是**规模建议，不是功效保证或已执行预算**。它们仍来自一个项目家族，不能宣传成 144 个真实企业项目，也不能把同场景的重复调用当作独立来源。

主要评价应包括：

**实际业务结果、跨项目一致性、变更后的有效交付、合理求助与停止、工作恢复，以及调用和执行成本。**

静态与动态条件若改变了目标或工作量，需要分别报告；只有真正匹配的条件才能用于分析某个因素的影响。

预算充足时，优先增加**独立需求、不同错误机制和未见结构组合**，而不是只对少量场景反复抽样。

# 八、将分项评价转为可优化奖励，然后开展最小 Agentic RL

## 1. 保留评价分项，另定义奖励

建议增加 `RewardSpec`，将可评结果映射为训练信号，但不改变制度记录或原评价。

初始奖励应围绕：

> **完成明确工作目标、维持要求的一致性、满足必要约束，并控制不必要消耗。**

不要直接奖励批准次数、消息数量、关闭问题数量或反复提交。可恢复错误应允许发生，但“先制造错误再修复”不能比一次正确完成得到更多奖励。

奖励验收至少覆盖：空交付、只改标签、重复发布、篡改测试、始终等待逃避任务，以及后续 episode 成功被错误记到前一段。

**评价器故障不是模型失败奖励零分；真实模型失败也不能因为不成功就被过滤掉。**两者应分别记录、分别处理，并公开对应分母。

## 2. API 评测与参数训练必须分清

商业 API 可以用于能力基线和 Teacher 经历，但不意味着能够更新供应商模型参数。

RL 应使用可训练权重及相应推理后端，保存实际 token、掩码、策略版本和算法需要的行为概率。缺失字段保持缺失，不从最终文字伪造。

不必重新实现整套 RL 平台。Harbor 已提供容器任务训练接口及 SkyRL 对接，并明确要求 rollout 保存 token、mask 和奖励；可以将其作为候选适配基础，但 ProWorkSim 的兼容性仍需实际验证。:chatgpt-content-reference{index="20"}

## 3. 首轮研究对照应直接服务于核心命题

建议在相同起始模型下比较：

| 条件 | 用途 |
|---|---|
| 不进行新 RL | 基线 |
| 独立工作任务上的 RL | 一般任务训练收益 |
| 串并联项目群上的 RL | 持续状态、交叉依赖和工作后果的增量价值 |

尽量匹配业务目标组成和训练预算，并保留未见需求、项目关系组合及后续不同仓库的测试。

**参数变化和训练 loss 下降只能证明训练发生，独立项目上的工作结果改善才支持学习收益。**

---

# 九、建议的执行顺序与预算使用

建议近期按以下顺序推进：

\[
\boxed{
\text{诊断补修与 API 薄适配}
\rightarrow
\text{36 次真实交互开发试跑}
}
\]

同时：

\[
\boxed{
\text{公开项目执行基础}
\rightarrow
\text{四项目组合与模型基线}
\rightarrow
\text{奖励校验}
\rightarrow
\text{最小 Agentic RL}
}
\]

不需要把第二条线完成，才启动第一条线；也不应因第一条线的有限模板表现不错，就停止建设真正可执行的项目群。

预算方面，先用开发批的实际输入、输出、缓存、失败和重试成本估计每个 episode 的分布，再确定主批上限。**“预算较充足”可以支持增加覆盖，但不能替代模型、调用数、累计 token 和金额停止条件。**原计划书中的拟议金额不应直接当成此次已经批准的额度。

真实金融工作流材料继续作为后续校准支撑，不设采集数量门槛。近期重点是利用公开代码与数据，让模型真正工作、让结果能够验证。

---

## 最终推进判断

**v0.10 已经提供了开始真实模型模拟所需的架构接缝。现在应当接入 API，而不是再做一轮只有程序工作人员的模块展示。**

本次发现的条件诊断遗漏需要局部修复；API 传输记录和 episode 固定评价需要补齐。但这些都是边界明确的接入工作，不应变成新的长期延期理由。

下一阶段应形成两类实质成果：

**一是模型确实通过统一工作人员接口，在动态世界中检索、行动、等待、修订和交付；二是公开项目群确实要求模型编写和运行代码、协调跨项目依赖，而不只是填写预制结果。**

**有了可信的模型评测与可优化奖励，就应进入有限范围的 Agentic RL。内核继续由真实工作与训练需求反馈完善，而不是以“先完成一个无限通用的世界”为训练前提。**
