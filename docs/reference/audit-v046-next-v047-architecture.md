**我的判断是：应该先做你提出的对比，并把它作为下一轮的优先实验。**先弄清楚“增加成员名额、采用自由组织或人工架构，究竟换来了多少任务完成度、消耗了多少 token”，比继续单独追踪容量效应，更能帮助我们选择后续学习实验的执行基线。

对 v046 的审计结论是：**可以接受其以技术中断封存；18,432 的有限资格通过，但正式四对比较仍未完成。**目前既不能说扩容有效，也不能说扩容无效。

我已完成报告、逐槽机器方案和证据包。建议的新先导为：**先做 28 槽架构／名额比较，再做 16 槽事前指定的预算比较；最多 44 槽、1,500 万实际模型 token。**以下说明审计发现、为什么这样设计，以及结果应如何解读。

## 一、v046 审计：主要报告成立，未知必须继续保留

本次核对了固定版本的最终报告、机器 JSON、协议、准备及启动记录，并审阅了容量绑定、费用清算、停止路径和组织接口。对摘要进行了 **190 项算术、库存、分母和保留约束检查，190 项通过，0 项失败**。

这个结论限于已核对材料的一致性及相关源码路径，**不等于独立重放了原始运行**。报告与 JSON 来自同一上游；本次没有重新执行模型、候选业务测试、私有验收或 GPU 诊断。

### 1. 四对结果没有形成容量效应估计

| 项目 | 审计后的状态 |

### 2. 费用账目正确，但必须保留两种口径

| 范围 | 完整回包 | 已开始 attempt | 已知实际 token | 含不确定预约的扣账 | 完整实际 token |
|---|---:|---:|---:|---:|---|
| 正式首槽 | 31 | 32 | 472,582 | 489,971 | null |
| 独立中性资格 | 1 | 1 | 16,412 | 16,412 | 16,412 |
| 本轮新增合计 | 32 | 33 | 488,994 | 506,383 | null |

第 32 次请求的准备输入为 15,341，加输出预约 2,048，共 17,389，能够装入 18,432。它已经开始执行，缺少完整回包，所以不是 context、fixed 或 shared budget 的执行前拒绝。

其中的 **17,389 是不确定调用的预约扣账，不是已知实际消费**。较晚账本的 489,971 与较早 runtime-state 的 472,582，反映的是不同保存时点。两份记录可以同时成立。完整实际费用仍然未知。参见[机器明细](https://github.com/haoyueliuzhao/ProWorkSim/blob/a5772ef6c8d923d5ba53cdf1677fb87fd09a0b1d/docs/experiments/software-organization-v046-final.json)及[账目清算实现](https://github.com/haoyueliuzhao/ProWorkSim/blob/8dc6e4ce90b8e50080a0ce0a7f0b4851bc1bc9fc/src/proworksim/team_budget_v033.py)。

新增 worker 占用约 **0.68935 GPU 小时**。31 次完整原生调用耗时已经包含在 worker 时间里，不能再累加一次。这个费用口径也应沿用到后续架构比较。

### 3. 过程证据提出了新的诊断方向，但没有补出业务失败

有三点会影响后续实验设计。

**第一，模型已经见过初态反例。**两名成员的首个完整请求都包含同一组初态诊断：7 个检查、4 个失败。因此，“没有看见恢复义务”不能作为完整解释。但这些初态诊断也不能算作模型对当前候选版本的新测试。

**第二，保存前缀没有形成当前版本的验证与提交链。**已有 16 次读取、9 次编辑，均修改 event_store.py；没有保存的当前版本 run_tests、固定提交或成果集成。静态候选把 restore／replay 另定义在 event_store.py，而公开调用仍进入 recovery.restore／replay。这使“接口定位及改动位置偏差”成为值得检验的解释，尚不能把它写成已验收失败。

**第三，新旧轨迹不是逐动作重放。**首个可见输入中的实例、分支和账本摘要标识已经不同；首次动作分歧出现在全队第 4 请求，早于原先设想的容量拒绝点。相同 seed 不能保证相同输入或后继动作。以上事实均来自[封存报告及其过程证据](https://github.com/haoyueliuzhao/ProWorkSim/blob/a5772ef6c8d923d5ba53cdf1677fb87fd09a0b1d/docs/experiments/software-organization-v046-final.md)。

因此，下一轮除了完成度和费用，还应观察：

> 已见义务 → 定位实际调用接口 → 修改明确版本 → 测试该版本 → 固定交付。

这比增加消息数、编辑数或读取数，更接近我们真正希望改善的工作能力。

## 二、为什么现在应先做架构效率比较

### 1. 旧 S1／F2／O3 还不能回答人数问题

源码中的实际定义是：

| 原制度 | 初始人数 | 最大同时存活 | 累计出生上限 |
|---|---:|---:|---:|
| S1 | 1 | 1 | 1 |
| F2 | 2 | 2 | 2 |
| O3 | 2 | 4 | 6 |

**O3 不是“三个模型”。**旧比较混合了初始人数、成员名额、出生退出和组织制度，因此不能直接画成 1／2／3 人数曲线。

同时，成员是拥有独立私史和工作区的逻辑会话，共用一个 owner.transport；“最多 3 resident”指并行 episode worker 上限，不是逻辑成员最多三名。采用四名逻辑成员，并不要求部署第四个 resident 模型。参见[制度定义](https://github.com/haoyueliuzhao/ProWorkSim/blob/8dc6e4ce90b8e50080a0ce0a7f0b4851bc1bc9fc/src/proworksim/software_organization_v045.py)及[共享运行时](https://github.com/haoyueliuzhao/ProWorkSim/blob/8dc6e4ce90b8e50080a0ce0a7f0b4851bc1bc9fc/src/proworksim/software_organization_runtime_v045.py)。

### 2. 首次提交费用补充，已经给出了比较效率的理由

旧 LA／LB 四个全部成功配对块中，各制度四槽的累计费用为：

| 制度 | 到首次固定提交 | 首次提交后 | 完整 episode |
|---|---:|---:|---:|
| S1 | 386,069 | 125,008 | 511,077 |
| F2 | 587,652 | 479,270 | 1,066,922 |
| O3 | 868,042 | 348,705 | 1,216,747 |

相对 S1，F2 和 O3 在首次提交边界已经分别多耗 **52.21% 和 124.84%**；完整回合分别多耗 **108.76% 和 138.08%**。所以，新增成本不能全部归因于提交后继续运行。参见[首次固定提交费用补充](https://github.com/haoyueliuzhao/ProWorkSim/blob/a5772ef6c8d923d5ba53cdf1677fb87fd09a0b1d/docs/experiments/software-organization-v046-final.md)。

但这里仍有两项限制：

- 这是特定成功子集，不能替代全体任务的成本比较。
- 首次提交当时尚待验收，不能称为“首次正确解成本”。

我们现在真正需要回答的是：**新增成员是否提高完成度；若提高，要付出多少全体实际成本；相同团队预算下，哪种组织方式更有效；增加预算后，谁能把余量转化为交付。**

公开的多智能体扩展研究也把架构、任务、模型和预算共同控制作为比较基础；它支持开展这种对照的思路，但不能替我们预先指定最佳人数或提升幅度。[arxiv.org](https://arxiv.org/html/2512.08296v1?utm_source=chatgpt.com)

## 三、建议的新先导：1／2／4 名额，七个配置

这里将“模型数量”定义为：**同一 9B 基座下，可用的逻辑成员名额**，不涉及参数规模或不同模型家族。

为了保留完整自由组织，D 从一名成员开始，自主决定是否增员。因而主比较是“提供不同名额时，整个组织策略的表现”，并同时记录实际使用人数。

### 七个配置

| 配置 | 初始／最大存活／累计名额 | 组织方式 |
|---|---|---|
| S1 | 1／1／1 | 单成员自行求解、测试、提交 |
| D2 | 1／2／2 | 自由增员、分工、交流、共享、退出 |
| D4 | 1／4／4 | 同上，最多四个累计名额 |
| I2 | 2／2／2 | 两个独立候选尝试＋有预算的最终选择 |
| I4 | 4／4／4 | 四个独立候选尝试＋有预算的最终选择 |
| P2 | 2／2／2 | 实现 → 复核兼修订 → 提交 |
| P4 | 4／4／4 | 实现 → 独立复核 → 修订整合 → 最终验证／提交 |

首轮先比较两种人工架构：**独立多尝试**和**固定复核流水线**。它们分别回答“更多独立搜索是否足够”和“预置工作流程是否有用”。集中协调者可以作为后继第三种对照，本轮不展开所有拓扑。

### 自由组织必须允许少用人

D4 如果最终只使用一名成员，这就是四名额条件下自由策略作出的选择。不能把这种运行删掉，再宣称比较的是固定四人的效果。

每槽需要同时记录：

- 累计出生人数；
- 至少实际调用一次模型的人数；
- 峰值存活人数；
- 每成员 token、调用和出生退休时序。

因此，本轮可以回答部署时“给多少名额、用什么架构”，**不能单独识别固定实际人数的纯因果效应**。这个边界应直接写进结果表，而不是在观察结果后重新定义人数。

### 人工架构必须是真正可执行的对照

**I：独立生成，然后计费选择。**

生成阶段隔离跨分支代码、报告和私史；之后由现有 member_001 兼任选择者，计入原来的 N，不增加隐藏模型。建议 70% 团队 token 给候选生成并按 N 均分，至少 30% 留给选择、测试和提交。

选择只依据合法共享的固定候选和公开证据。私有验收在最终候选锁定后运行，不能先验 N 份再挑正确答案，也不能把“任一分支成功”当正式成功率。

I 定义为选择一个已有候选，因此最终文件哈希需要绑定该候选。原 integrate_patch 是三方合并，不能默认当成切换到选中版本；取得、复原、测试、固定与提交都要按原生路径执行并计费。

**P：固定流程要包含修订和最终交付机会。**

P2 建议 token 比例为 **60%／40%**。P4 建议为 **35%／20%／25%／20%**。未用额度只能向后传递，不重新获得团队预算。

源码还有一个必须落实的提交门：**最终提交者必须对自己的精确当前版本执行公开测试，并固定该版本；前驱测试过不能直接代替。**测试须真实执行，但原提交门并不要求公开测试全部通过。参见[集成与提交接口](https://github.com/haoyueliuzhao/ProWorkSim/blob/8dc6e4ce90b8e50080a0ce0a7f0b4851bc1bc9fc/src/proworksim/software_collaboration_v027.py#L333-L388)。

所以阶段预留不能只留 token，还要保留其他共享配额：

| 配置 | token 比例 | 决定／attempt 配额 | 公开测试配额 |
|---|---|---|---|
| I2／I4 | 70%／30% | 88／40 | 24／8 |
| P2 | 60%／40% | 76／52 | 20／12 |
| P4 | 35%／20%／25%／20% | 44／26／32／26 | 8／8／8／8 |

I 的生成阶段、P 的前置阶段可以固定候选，但不能正式 submit；提交权只在最终阶段开放。这样才不会在选择或流水线尚未完成时，悄悄用前阶段提交取得正式结果。

这些比例是待冻结的人工策略，不是已证明最优的配置。本轮不根据成绩反复调比例、删除试跑。

## 四、实验规模：先 28 槽，再 16 槽

### 阶段 A：统一 250k，比较架构与名额

在原 LA、HA、LB、HB 四个 root 上，各使用一个新配对 seed，运行全部七配置：

\[
4\text{ 个任务块}\times7\text{ 个配置}=28\text{ 槽}
\]

每槽团队 token 上限 250,000，总上限 **7,000,000**。

这一阶段回答：

- 相同预算下，自由组织、独立多尝试、流水线谁完成得更多？
- 增加名额后，实际 token 是否增长，完成度是否随之提高？
- D 是否会选择增员，增员后是否形成有效工作？

### 阶段 B：预先锁定四配置，比较真实 500k 条件

对 **S1、D4、I4、P4**，在同四个 root、同配对 seed 下，从初态独立运行 500,000 预算条件：

\[
4\text{ 个任务块}\times4\text{ 个配置}=16\text{ 槽}
\]

总上限 **8,000,000**。名单现在就锁定，不根据阶段 A 的赢家、失败者或实际增员情况选择。

| 阶段 | 配置 | 每槽团队预算 | 槽数 | token 上限 |
|---|---|---:|---:|---:|
| A：架构／名额比较 | 七配置 | 250,000 | 28 | 7,000,000 |
| B：预算响应 | S1、D4、I4、P4 | 500,000 | 16 | 8,000,000 |
| 合计 | 稀疏两预算设计 | — | **44** | **15,000,000** |

各槽保持 18,432 容量、2,048 输出预约、原业务合同和验收口径，以及团队 128 决定、128 attempt、32 次成员测试上限。44 槽相应最多 5,632 决定、5,632 attempt、1,408 次成员测试。

### 固定预算需要真实运行，不能靠长轨迹截断替代

**“初态知道只有 250k”与“知道有 500k，事后截到 250k”是两个不同实验。**

预算会影响增员、分工、验证及提交策略；I／P 的阶段预留也随 B 改变。因此，两个预算应分别公开、分别从共同初态运行。高预算前缀可以作为过程描述，不能代替低预算处理。

本设计没有 N=2 的高预算点，所以不声称估计了全部人数×预算交互。

### 四个旧 root 足以先看方向，但不足以做总体结论

采用现有四个 root，能直接衔接业务合同和已知问题，符合“预先有一个大概判断”的目标。但它们只来自两个相关人工任务家族，已经被反复观察，而且易、难两端比较明显。

每配置只有四个任务块，一个结果就改变 **25 个百分点**。44 次运行不是 44 个独立任务。

因此，这轮以逐 root 配对结果、实际成本和工作路径为主。如果所有配置仍表现为易题成功、难题不交付，就应报告“当前面板未分辨出完成度差异”，随后另提独立中等难度任务确认，而不是继续追加 seed 直到出现优势。

## 五、启动先导前，只需处理一个明确的执行问题：时间关闭边界

v046 已经说明，原 40 分钟硬终止可能留下未回包和未知费用。仅把 token 上限降到 250k，不能保证这个问题消失。

**建议新协议采用：90 分钟停止发起新请求，另给 10 分钟有界关闭窗口，100 分钟硬截止。**这是新先导的工程提案，不追溯改写 v046，也不宣称这个时长已经被证明足够。

软截止后，只处理已经实际发往 transport 的在途请求：

1. 停止新请求和自动重试。
2. 结清既有在途请求、对应合法工具动作及费用。
3. 锁定最后固定提交的对象、版本和哈希。
4. 完成原生关闭、唯一候选验收及终态守卫。

关闭窗口不新增模型收尾、I 的选择阶段或 P 的后续阶段，也没有额外 token 额度。硬截止后仍有未回包或不明副作用，继续记技术未知，不自动重采。

这里有一个重要的统计区别：

- 如果行政软截止先截断了原本还能继续的模型工作，即使安全闭合、验收已知，也只得到 **共同 token 与时间策略下的结果** \(R_{\text{joint}}\)。
- 对“给定 token 上限 B，按正常资源条件运行到结束”的问题，\(R_{\text{token}}\) 仍是行政删失，保持 null。

不能删掉这些慢槽后只比较完成子集，也不能用已知 \(R_{\text{joint}}=1\) 回填 \(R_{\text{token}}=1\)：原生验收取最后提交，继续运行仍可能覆盖早先候选。

辅助业务得分 Q 也遵守同样边界。一个配置有 \(s\) 个已知成功、\(u\) 个未定结果、计划分母 \(m=4\)，token 完成率只能给出：

\[
\left[\frac{s}{m},\frac{s+u}{m}\right]
\]

这是未知结果下的识别区间，不是置信区间，也不是把未知算作失败。

前置工程只需覆盖新接口、阶段账目、完整合法提交路径和上述关闭流程。保持同一数值路径时复用现有 18,432 资格，不新增长度扫描或要求先试出业务成功。首个真实模型运行计入正式先导库存。

## 六、最终应看什么，而不是只看一张成功率表

建议形成两项主要比较。

### 比较一：250k 下的完成度—实际成本

七配置同时报告：

| 维度 | 主要口径 |
|---|---|
| 完成度 | 逐 root 的正式结果、正常未提交、验收失败、行政删失、技术未知、未启动 |
| 实际成本 | 所有成员的输入＋输出，包含成功和失败、提交后的活动 |
| 提交边界 | 首次固定提交费用、最终采用提交的费用，分别记录 |
| 实际人数 | 出生人数、调用人数、峰值存活、每成员费用 |
| 工作闭合 | 反例实际呈现、精确版本修改／测试／复验、固定交付 |
| 其他资源 | 测试／工具 CPU、worker 时间；嵌套时间不重复累加 |

核心是看：**有没有配置在完成度不低的同时更省 token，或者增加的完成度是否值得增加的成本。**

不能只比较成功案例的平均费用；提前退出、没有交付的低费用也不能自动成为“高效率”。没有首次提交的槽应保留事件缺失和终止成本，不能从首次提交均值里消失。

### 比较二：真实 250k→500k 的预算响应

对 S1、D4、I4、P4，比较两个预算点的：

- 完成度变化；
- 全体实际费用变化；
- 实际增员变化；
- 新增的有效验证和交付，还是更多重复编辑。

几类结果的含义可以提前约定：

| 观察 | 初步判断 |
|---|---|
| D4 同预算优于 I4 | 自由组织的作用超过这套独立尝试＋选择策略 |
| P 优于 D | 固定复核修订流程当前更能闭合工作，应作为强人工基线 |
| I 优于 D | 当前更多独立搜索与有界选择更有效，需要区分搜索和协作的价值 |
| 增员只增加成本，完成度不变 | 当前任务上新增名额未体现收益 |
| 500k 普遍改善结果 | 预算紧张可能比架构差异更关键 |
| 500k 主要增加重复编辑 | 所测策略没有有效利用额外资源 |
| 技术未知或行政删失较多 | 执行条件仍限制解释，不能强排架构冠军 |

44 槽结束即收口，不自动增加第三预算、更多架构或 seed。
