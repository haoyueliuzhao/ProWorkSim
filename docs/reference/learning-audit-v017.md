# 二、最重要的实现发现：合法 SQL 写法被误当成函数

## 1. 现在可以确认的是词法误分类

冻结执行器用下面的模式识别“函数”：

```python
r"\b([A-Za-z_][A-Za-z_0-9]*)\s*\("
```

然后与 `FUNCTIONS` 比较。因此，`NOT (` 会被识别成名为 `not` 的函数，而该集合中没有 `not`。**拒绝发生在 `connection.extract_statements(text)` 之前。**这段代码在 H1 和后继源中对应相同 Git blob。

本次局部结果如下：

| 输入 | 原检查函数行为 |
|---|---|
| `SELECT NOT (1=0)` | 拒绝：`allowlist: not`；数据库解析调用0次 |
| `SELECT NOT 1=0` | 到达解析分支 |
| `NOT (LOWER(TRIM(InvoiceNo)) LIKE 'c%')` | 在词法阶段拒绝 |
| `LOWER(TRIM(InvoiceNo)) NOT LIKE 'c%'` | 到达解析分支 |

用于检查控制流的数据库解析对象是明确的测试替身，不冒充真实 DuckDB。另在 SQLite 上用普通票号、取消票号、空值等人工数据验证了后两种谓词得到相同结果；**这项检查也没有被当作 DuckDB 重演**。DuckDB 官方文档本身明确说明，`NOT LIKE` 与 `NOT (string LIKE pattern)` 等价。:chatgpt-content-reference{index="3"}

因此，本次能够把报告中的候选解释推进为：

> **所测布尔否定写法被原函数当成未允许的函数调用而拒绝。这是执行器的词法边界问题，不是这些谓词本身的业务计算错误。**

但这仍然**不能证明两条原 H1 完整 SQL 其余部分正确**，也不能证明修复以后模型会成功。原记录中还有日期类型比较、未提交和其他工作问题，必须分别保留。

## 2. “所有模型共用同一执行器”不能消除这个影响

共同环境有助于控制条件，但不同模型或 harness 会以不同概率选择等价写法。

一个模型倾向于 `NOT (...)`，另一个倾向于 `NOT LIKE`，前者就可能多消耗一次构建和修复机会。因此，当前 H1 测到的是：

**模型＋harness＋这套具体受限执行器的表现。**

它不能直接解释成没有接口偏差的 SQL 能力或专业工作能力排名。**不能将受影响 episode 删除，也不能把修复后的重算结果补回原轨迹；应在原分母中另列执行器误拒暴露及后续实际恢复。**

## 3. 修复要窄，不必重新开发完整 SQL 平台

建议优先正确区分声明支持的布尔语法与函数调用，同时保留单条 SELECT／CTE、外部访问禁止、扩展加载禁止、写操作禁止及资源边界。

下一次验证只需围绕这个根因：通过真实公开工具路径比较两种等价谓词，覆盖括号、组合条件和 NULL，再确认原有危险或不支持操作仍被拒绝。

**不要直接关闭白名单，也不要让 harness 自动将模型 SQL 改写成某种“标准答案写法”。**前者扩大风险，后者隐藏了环境问题，并改变了实际执行与模型输出的关系。

# 三、四项目评价汇总：格式失败不应无条件变成未知

## 1. 问题不在 Decimal 验收，而在其后的覆盖逻辑

四项目采集器先调用：

```python
assessment = assess_project_episode(episode)
```

随后，只要某个角色终止状态属于包括 `model_format_error` 在内的一组状态，就执行：

```python
assessment.update(
    eligible=False,
    reward=None,
    completed=None,
    reason="model_or_environment_execution_incomplete",
)
```

这个分支把格式错误与服务、环境、身份等故障放到同一处理集合，没有进一步判断独立结果是否已经可信可评。

本次人工夹具确认了：

| 独立评估输入 | 后续状态 | 汇总输出 |
|---|---|---|
| 已知未完成，`reward=0` | `model_format_error` | `reward=null` |
| 已知完成，`reward=1` | `model_format_error` | `reward=null` |
| 已知未完成，`reward=0` | `model_budget_exhausted` | 保留0 |

**这是原条件的可复现行为，不是已经发生的四项目模型失败。**本轮四项目模型尚未提供已执行结果，不能将人工夹具说成真实世界反例。

## 2. 应当区分终止原因、记录完整性和结果可评性

有完整原始输出、确切拒绝和固定终态的格式失败，本身就是模型的真实行为。若它导致工作未完成，可以形成**已知失败**，不必改成未知。

如果工作已经完成，之后又出现格式错误，是否影响成果应由公开过程合同判断。即使合同规定因此失败，也应是**按合同得到的已知失败**，而不是自动不可评。

真正缺少关键返回、身份、版本或评价结果时，才应保持未知。V1明确区分真实业务失败、记录缺口与环境故障，并要求可信失败保留在基础处理里。:chatgpt-content-reference{index="6"} :chatgpt-content-reference{index="7"}

建议将三个字段分别表达：

**为什么停止；行动记录是否可信；当前固定结果能否独立评价。**

不要让一个终止状态名直接覆盖已经得到的业务评价。否则还可能通过后续“未知即停”的规则，令剩余预定案例不再执行，使缺失与模型行为相关，而不只是系统偶发故障。当前四项目执行设计确实规定了这类停止处理。

## 3. 这是四项目模型评价前的必要修订，不推翻现有程序验收

本轮关于“共同错误但差额为零”“混版本”“复制结果没有真实 build”“后补上游固定提交”的负例仍有价值，它们检验的是另一个层次。

下一步补一个有界端到端控制即可：真实 WorldCore，加明确的人工模型返回，产生格式拒绝、保留终态、独立评价，并确认其他角色和后续预定案例按合同继续。

**这不需要重做整个世界内核，也不需要把所有服务故障都强行记成零奖励。**

# 四、H2 有两项设计限制，应在学习结果出来之前处理

## 1. 复核标签与业务口径固定关联，客户隔离没有解决这一点

后继使用的零售目录，在 train、development、locked 三个池中都固定：

| 事实位置 | 公开业务口径 | 准备的提交类型 |
|---|---|---|
| f0 | 全期、`sales_only` | `correct` |
| f1 | 全期、`net_signed` | `wrong_count` |
| f2 | 半年、`sales_only` | `wrong_amount` |

期间名称也包含对应的 `f0/f1/f2`。这些关联可以直接从任务目录与准备逻辑确认。

本次只用 train 的“业务口径＋结束日期”建立一个查表规则，就能预测 locked 三种**预设提交类型**。

这项刻画的边界必须说清楚：

**没有证明模型已经利用这个关联；没有证明它不读提交就能通过完整复核奖励；也没有证明隐藏标签字段直接进入了 actor 输入。**

但它说明，未来复核成绩改善可能部分来自学习“哪类口径通常配哪种错误”，而不完全来自核验当前成果。**新客户和新发票，不足以排除这种任务构造捷径。**

建议在新协议中，让同一口径、同一来源切片分别出现正确、错票数、错金额的真实提交，错误类型跨口径组织。仅随机化编号不够，因为业务口径关联仍然存在。准备仍通过实际工具完成，不能把参考补丁或错误标签给模型。

一个可核算的新评价示例是：每次实现6例、复核9例、pair6例、chain6例，共27例；保留64个训练 episode，初始／最终合计54个评价，形成118例的新 pilot。**这与原112例不同，必须作为明确修订；不是本次已经冻结或授权的预算。**四类任务仍按各1/4计算宏平均，不能因复核例数增加而静默改变效用权重。

## 2. 当前 H2 不只是“可能没有支持”，而是无法形成两类达标支持

H2每任务的三个精确情境，当窗重复数为：

\[
M_\xi\in\{2,1,1\},
\]

采集器固定 `min_class_count=2`。

因此：

\[
|\mathcal S_{\xi i}|
\le
\left\lfloor\frac{M_\xi}{2}\right\rfloor
\le 1.
\]

即使所有轨迹都有效，每个块最多也只有一类满足门槛。四个窗口的参数发生变化，不能合并后称为同一当前策略的支持。

**这不妨碍 H2 做基础在线学习，但应明确称为 \(Q=B\) 的基础 pilot，而不是等待支持出现后自动启动 O4。**V1 对单类无组成自由度已有明确规定。:chatgpt-content-reference{index="14"}

后续进入 ID‑VTDO 时，需要另行安排当前同一 \((\theta,\Gamma,\xi)\) 的密度。例如两个有限联合协作情境各8次可以作为预算规划起点，但8仍不是充分样本量，也不保证多方法出现。没有支持就继续基础处理，不补采到凑齐类别。

# 五、H1 的正确收口方式：完整测量、保留限制，不重新解释旧 S1

## 1. 原 S1 的处理正确

27B的22个已知结果和14个未知结果应分开；18次 OOM 分布于14个 episode，不能算作18个独立失败样本。11个已知完整责任可以作为已确认成果数，不能用已知子集比例代替完整批次成功率。

将新 H1 的准入由“所有旧评分已知”修订为“原尝试已准确闭合、未知保留”，是合理的新实验路径。**不应让一个已经失败的旧资源配置永久阻止新配置研究，也不能因此追认旧选择器已经成功。**

## 2. 真实长请求通过，不等于所有容量已经确认

两条容量请求提供了有界证据，但27B实际只生成78个输出 token，9B生成586个；输出上限保持2048，不代表实际执行了2048长度，更不代表完成反向。原选择依据是渲染字符长度，也不是最大总 token 或最坏执行路径。

下一阶段只需补与实际迁移相匹配的代表性可微路径检查，不必展开无限容量认证。但不能凭推理容量通过，就默认4卡27B具备同等长度的训练容量。

## 3. H1结果仍应解释为有限运行组合效应

每组合12例来自六个开发情境，主要均值与四任务宏平均已经分开，这是正确安排。未知组合不自动进入H2，是可执行性规则，**不是证明未知组合的基础能力更低**。固定排序得到的是开发初始化选择，不是普遍能力认证。

终态报告建议保留原计划中的逐情境配对、岗位完整责任、成本和工作断点，并新增一项只读标注：**执行器误拒暴露**。不要剔除这些案例，也不要把修复后的环境表现与旧 H1 拼成完整臂。

“9B曾正确构建并提交”“27B使用了被误拒的谓词”“收到多调用反馈后改成单调用”，都可以如实报告；但这些早期片段不能给两模型或两harness作最终排名。

# 六、对已经部署的后继：不热改，但也不能把自动化当作科学决策

当前后继脚本会在 H1 结束后依次选择组合、启动迁移与四项目评价，再在迁移准入通过后启动 fresh pilot。脚本不根据部分成绩重采，这点应保留。

**但“执行图已经部署”不意味着新发现的问题必须一直带入训练。**

建议按实际阶段处理：

**运行中的 H1**继续保留冻结源，完成或按原规则停止，不修改SQL支持、提示和评分。

**尚未开始的四项目模型评价**，先修正格式错误覆盖可评结果的分支。

**尚未开始的正式主学习**，先处理 SQL 误拒和复核标签关联，在新阶段明确冻结。只读报告与原始选择可以保留为旧 \(\Gamma\) 下的证据。

**若后继事实上已经启动**，则保留它的源、真实行动和成本；不能声称本次建议已执行，也不能把其中已发生的结果删除后重新采样。

本次没有操作服务器。上述调整需要在真实调度边界由执行方实施，不能仅修改主分支文档，就假定独立冻结进程已经采用新规则。

# 七、下一轮实验建议

## E1：先完成两项窄修复，不再新增大型基础设施

第一项是 SQL 运算符／函数识别；第二项是四项目终止与可评性分离。

验收只围绕原反例、修后真实工具路径及必要负对照。**不增加新的多代理框架，不迁移训练后端，不扩大 LoRA，不同时改奖励。**

对于 SQL，原始模型完整 SQL 的隔离重演可以帮助判断：通过词法检查后还有哪些类型或业务错误。但它属于新的诊断，不能补成模型当时成功执行。

对于评价，应保留独立 assessment，将 collection termination 作为单独事实；只有确切证据表明目标不可判定，才把结果设为未知。模型可恢复或不可恢复的行为错误，不应自动等同于基础设施失败。

## E2：完成原 H1，并确定新阶段使用的候选组合

不必为了追求完美排名反复重开整个48例比较。

如果目标只是选一个有能力、可训练的初始化，原H1可以提供候选名单，在修复环境中做预声明的小型确认即可。**如果要声称“修复环境中四组合的完整排名”，则必须有对应的新配对证据，不能直接沿用旧排序。**

无论哪种路径，SDK都没有必须胜出的地位。近期应选择实际工作与训练成本合适的组合，而不是为框架名称寻找收益。

## E3：完成一个固定组合的直接在线学习 pilot

新的阶段从 fresh 公共基座开始。迁移依然是：

\[
4\text{ 个实际训练片段}
\rightarrow
\text{至多一次更新}
\rightarrow
4\text{ 个新策略开发片段}.
\]

迁移通过后，主 pilot另起fresh状态，迁移权重不接入。业务全成功不是准入要求，但必须有可信记录、实际概率与反向路径、明确参数更新和新策略交互。

**只采用terminal MC可以降低本轮因素数量，但不能称为它已经优于RTG。**此前RTG对过去交接信用的机制修订并没有被业务比较否定。当前MC还可能继续将有限读取／交接成果分配给后续无效动作，因此应保留轻量的岗位优势和成果诊断，而不必恢复昂贵的全部梯度分解。

训练记录要继续包含模型主动选择的 note、todo、检索与编辑；机械检查和工具返回不成为 actor 目标，一次编辑的两类日志不造成双计。概率复算只用当时实际输入，不把被last4移出的历史补回去。成员自身动作与同事消息的区分是 V1 的核心约束。:chatgpt-content-reference{index="20"}

最终测量是固定 \(\Gamma\) 下：

\[
\Delta_{\mathrm{learn}}
=
U(\theta_T,\Gamma)-U(\theta_0,\Gamma).
\]

工具修复、换模型或换harness的收益不计入其中。四次更新、一个训练种子可以形成有界 pilot；不能承担稳定学习收益或算法总体有效性的证明，也不能失败后追加到幸运成功才结束。

## E4：四项目先验证自主执行，再补训练投影

本轮将P1/P2独立质量、P3固定输入忠实性与整体目标分开，尤其保留“双方共同错误但差额为零”的拒绝，是重要进展。

修订评价汇总后，静态2例、一次变更2例仍可作为有限自主工作探针。但报告应分别回答：

**第一版是否完成；变更是否实际触发；哪些角色收到新义务；是否沿用原Conversation与预算；哪些后继完成；最终失败发生在哪里。**

变更情境要求先完成第一版才触发新事件。若模型没有走到触发点，不能解释为已经测得“处理变更失败”；它首先是初始交付未完成。

新义务再激活只应调度真实后继工作，不重置预算、不赠送采用和修订、不替模型执行。程序控制已支持这个方向，实际共享模型能力仍待四例运行回答。

四项目训练投影可以后续再接。**正式效用成立不等于已经接入 RL，但也不应让这一扩展阻断已经可评的短责任训练。**

---

# 八、ID‑VTDO下一步应怎样真正进入实验

当前最需要避免的是：每轮都记录“支持不足”，却始终采用不可能产生组成自由度的采样设计。

建议将两个目的明确分开：

**基础学习 pilot**检验模型能否在必要harness和可信工具下，通过真实失败与成果学习；不要求多方法支持。

**ID‑VTDO实验**则另外固定具有足够当窗密度的联合协作情境，检查当前团队确实产生了哪些有效方法、哪些成员具有自身动作，以及类内频数是否足够。

情境应允许不同合法获取、交接或核验路线，但不在提示中指定路线。构建不同正确／错误提交，是不同的初始情境，不能合并为同一 \(\xi\) 内的方法多样性；话术和笔记差异也不自动产生新方法。:chatgpt-content-reference{index="23"}

有支持之后，Contribution仍然通过共同 actor／critic／optimizer 起点、同一当前窗口材料和更新预算下的配置干预，再到开发世界实际执行来估计。**它不是某条轨迹的奖励、harness效果、工具修复效果或当前梯度大小。**:chatgpt-content-reference{index="24"}

这条路线不需要回到教师轨迹采集或SFT：目标模型继续在世界中工作，窗口内暂存经历用于在线优化，更新后重新进入世界。失败残余保留，\(Q=B\)恢复基础损失，只有已有合格分支内部组成发生变化。:chatgpt-content-reference{index="25"}

## 最终推进判断

**本轮不是方向失败，也不是学习成功。它已经进入能够暴露“真实模型行为与模拟工具之间不匹配”的阶段，这比继续增加纯程序通过数更有研究价值。**

但下一步不能只看执行器有没有继续运行。应优先保证：

**合法工作方式不会被工具误拒；可评的模型失败不会被汇总成未知；复核收益不能仅由任务标签关联解释；算法支持密度必须真正允许组成优化。**

建议收敛为：

\[
\boxed{
\text{原H1准确收口}
\;+\;
\text{窄工具／评价修复}
\rightarrow
\text{去关联的有限在线学习}
\rightarrow
\text{四项目自主工作验证}
\rightarrow
\text{有实际自由度的ID‑VTDO实验}
}
\]

**下一轮最有价值的成果，是完成一次“工具可信、评测不走捷径、模型真正更新并再次工作”的闭合实验，而不是再增加一层自动执行图。**
