## 一、课题命名与总体定位

建议当前课题命名为：

# **ProWorkSim：面向智能体学习的专业工作世界模拟与任务流合成**

英文工作名称：

**ProWorkSim: Professional Work Simulation for Workflow Synthesis and Agent Learning**

它的核心目标是：

> **构建由工作环境、模型工作人员和项目任务流组成的可执行工作世界，让目标模型在其中真实承担工作，产生可验证的交互经历、专业交付物和训练数据，并根据学习反馈持续扩展工作空间。**

第一阶段以**金融研究与分析**为应用领域，但不把架构限定为金融问答系统。

这个名称保留了你最关心的三个方面：**模拟工作世界、合成任务流、支持目标模型直接学习**。“自进化”作为架构中的闭环机制，暂时不放进主标题，避免在尚未验证持续改进效果时，让名称先于证据。

下面将这份方案称为 **ProWorkSim v0.1 初步架构**。它是当前设计建议，不代表具体模型、算法、任务规模和实验协议已经冻结。

## 二、最上层拆解：三个主体，两个支撑系统

你的拆解是合适的：

\[
\boxed{
\text{工作世界}
=
\text{工作环境}
+
\text{工作人员}
+
\text{项目与工作任务流}
}
\]

不过，需要把三者之间的职责边界进一步明确。

| 主体 | 回答的问题 | 核心内容 | 不应该承担的职责 |
|---|---|---|---|
| **工作环境** | 在哪里工作，有什么资料、工具与规则？ | 数据、文件、应用、通信、权限、时间、状态 | 不替工作人员决定正确解题路线 |
| **模型工作人员** | 谁在工作，知道什么，有什么职责，如何决策？ | 角色、模型、局部信息、记忆、行动策略 | 不随意改写世界事实和评分规则 |
| **项目与工作任务流** | 为什么需要做这些工作，工作之间如何关联？ | 业务目标、工作义务、依赖、事件、审阅、返工 | 不把业务过程变成唯一执行脚本 |

在这三个主体之外，再建立两个支撑系统：

| 支撑系统 | 作用 |
|---|---|
| **世界构建与合成系统** | 生成项目情境、角色配置、环境材料、历史过程及可执行任务 |
| **验证、学习与演化系统** | 检查执行和成果，编译训练经验，更新目标模型，并调整后续工作空间 |

**关键区别是：工作人员属于世界内部；生成器、训练器和独立评测器属于世界外部。** 不能把这几类模型都混称为“多智能体团队”。

从目标模型的强化学习视角看，其他工作人员可以被视为环境的一部分；但从系统设计视角看，仍应把他们单独建模，因为他们拥有自己的信息、职责和行为策略。

APEX 的原始构造方法为这个拆分提供了依据：专家先承担不同角色完成项目、形成沟通和工作产物，再从世界内部设计评测任务。我们要继承这种“先有工作世界，再有任务”的方法，并增加自动模拟和训练能力。:chatgpt-content-reference{index="0"}

## 三、第一主体：工作环境应该怎样进一步分解

这里的“环境”不是一个文件夹，也不只是几个工具接口。我建议拆成七个子系统。

| 环境子系统 | 管理的核心对象 | 第一版需要具备的能力 |
|---|---|---|
| **E1. 业务与制度环境** | 业务背景、组织规范、口径、权限规则 | 解释工作要求，明确谁有权决定什么 |
| **E2. 事实与证据环境** | 公开材料、结构化数据、来源、时间与定义 | 支持检索、引用、核对和重算 |
| **E3. 工作产物环境** | 工作簿、报告、备忘录、版本与依赖 | 支持真实修改、版本保留和跨产物一致性检查 |
| **E4. 应用与工具环境** | 文件、邮件、表格、计算、检索等工具 | 执行真实操作，返回真实结果和错误 |
| **E5. 通信与协作环境** | 邮件、消息、任务交接、审阅、批准记录 | 支持局部信息交换和有业务效果的协作 |
| **E6. 时间与事件环境** | 披露到达、需求变化、回复、截止时间 | 推进项目状态，产生新工作和返工 |
| **E7. 执行与隔离环境** | 沙箱、状态持久化、快照、分支与日志 | 支持重复运行、恢复、比较和训练采样 |

下面分别说明它们应当保存什么，以及最容易设计错的地方。

### 3.1 E1：业务与制度环境——定义工作为什么有这些约束

这一层描述世界中的业务背景与规则，例如：

某研究团队要为客户更新公司研究；团队采用特定指标定义；分析假设需要负责人确认；正式交付必须包含工作簿和备忘录。

建议将这里的内容分成两类。

**世界运行规则**由程序维护，例如权限、文件所有权、哪些角色可以正式批准成果。

**专业工作要求**可以通过任务、规范文件和沟通记录表达，例如采用哪个分析口径、需要解释哪些变化。

这两类规则不能混为一谈。

目标模型试图读取无权访问的资料，环境应该拒绝；但目标模型写错一个财务公式，环境通常应允许这个错误发生，再由检查和工作反馈暴露问题。

> **运行规则负责约束“能不能这样操作”，专业评价负责判断“这样做是否正确”。**

如果环境拒绝所有不正确的业务动作，就相当于后台已经替模型完成了判断。

### 3.2 E2：事实与证据环境——区分事实、材料中的陈述与角色的认知

这一层至少需要区分：

| 对象 | 含义 |
|---|---|
| **来源材料** | 财报、公告、演示材料、历史记录等原始证据 |
| **证据支持的事实** | 能够定位到来源、期间、单位和定义的数值或陈述 |
| **研究假设** | 用于分析的情景设定，不冒充已发生事实 |
| **角色认知** | 某位工作人员知道、相信或尚未确认的内容 |

尤其不能把“主管说过”直接等价为“金融事实正确”，也不能因为一份旧报告存在，就默认其中所有内容都仍然适用。

每项关键证据建议保留：

`source_id、原始位置、适用期间、公开可得时间、单位、口径、来源类型、版本。`

这里有两个设计原则。

**第一，世界后台不必宣称掌握现实世界的全部真相。** 对真实公开材料，后台保存的是有来源支持的事实、冲突和不确定性；只有完全由我们定义的模拟业务规则，才可以由后台明确给定。

**第二，不把后台全部事实直接交给目标模型。** 模型仍需通过有权限的文件、搜索和沟通获得信息。

材料可以有三种构造方式：有使用权的真实材料；完全合成的业务材料；真实公开事实与明确标记的虚构项目背景相结合。不能让合成邮件或假设冒充真实公司的内部记录。

### 3.3 E3：工作产物环境——不仅保存文件，还保存它们如何依赖

工作产物应至少包括三部分：

\[
\text{产物}
=
\text{实际内容}
+
\text{版本状态}
+
\text{依赖关系}
\]

例如：

一份备忘录引用工作簿中的利润率；工作簿中的利润率依赖收入与利润；这些输入又分别来自某份披露材料。

当输入变化时，系统应知道哪些成果可能受到影响，但**不应该自动替目标模型更新这些成果**。

建议为产物记录：

`artifact_id、version_id、owner、status、derived_from、引用的输入版本、review_status。`

需要特别强调：

> **世界自洽，不等于所有文件始终一致。**

“新资料已经到达，模型尚未更新，报告仍引用旧数字”可以是一个完全合理的项目状态。重要的是这种差异有可解释的时间和版本来源。

依赖关系可以先用普通结构化表保存，不必第一版就建设完整知识图谱。对暂时无法精确解析的依赖，可以标记为“可能受影响”，不能假装已经掌握了完整语义关系。

### 3.4 E4：应用与工具环境——操作必须真实发生

第一版建议优先支持四类工具：

| 工具类别 | 主要操作 |
|---|---|
| **文件与检索** | 搜索、读取、写入、查看历史版本 |
| **邮件与工作沟通** | 读取需求、询问口径、回复、提交成果 |
| **电子表格** | 读取数据和公式、修改输入、重算、检查引用 |
| **代码与计算** | 数值计算、数据转换、验证和产物检查 |

报告可以先通过文件工具生成，暂不要求实现完整文档编辑器；演示文稿、复杂 GUI 和全部办公应用可以后续扩展。

每次工具执行建议统一记录：

`actor_id、action_id、输入、实际输出、错误、读取/修改对象、前后版本、逻辑时间。`

模型说“已经更新了工作簿”，不构成更新；工具执行产生新版本才构成更新。

此外，要避免建立一个与应用真实内容平行、却悄悄保持正确的“后台工作簿”。**实际文件应该是交付物内容的权威载体，后台保存可重建的索引、来源和验证结果。**

### 3.5 E5：通信与协作环境——消息可以改变工作关系，但不能凭空改变事实

通信环境不是角色聊天的装饰。它需要支持真正的工作效果：

确认口径、分配任务、请求资料、提出审阅意见、接受交付或要求修订。

但自然语言表达与业务状态变更仍要分开。

例如，“这个方案看起来不错”不应自动被解释为正式批准；“负责人批准了版本 v3”应该对应有权限角色对特定版本的明确确认。

**收件人、时间、附件版本和消息可见范围**都应当进入通信记录。

另一方面，角色可以说错话、遗漏信息或尚未确认事实。第一版可以先让环境角色相对可靠，再引入经过控制的沟通噪声，而不是一开始就让所有角色自由产生矛盾。

### 3.6 E6：时间与事件环境——使世界能够继续产生工作

建议采用**离散事件驱动**，而不是让所有角色始终无休止地对话。

事件分成两类：

| 事件类型 | 示例 | 触发依据 |
|---|---|---|
| **外部事件** | 新披露到达、客户调整需求 | 预设或采样的事件策略 |
| **内生事件** | 提交触发审阅、询问触发回复、输入变化影响下游成果 | 实际行动与当前状态 |

尤其要避免“固定剧情式审阅”：无论目标模型交什么，都收到相同的修改意见。

审阅反馈必须针对实际提交产生。正确提交应有机会直接通过，而不是为了制造长轨迹强制返工。

时间也要区分：业务材料的时间、模拟项目时钟，以及模型运行消耗的真实时间。没有校准之前，不能把工具调用次数简单解释为工作了多少小时。

### 3.7 E7：执行与隔离环境——支持实验，而不是只支持演示

每个工作世界实例需要独立状态，能够：

从初始快照启动；保存中间状态；在指定节点分支；恢复继续执行；导出完整记录。

参考答案、隐藏验证器和后台生成材料应与工作者可访问的空间隔离。权限控制必须在工具和存储层生效，不能只写一句“请不要看答案”。

重复运行也要分清两种能力：

**恢复同一状态**可以通过快照和日志实现；**重新调用模型得到完全相同的行为**不能仅凭设置随机种子就保证。后者需要保留实际模型输出，才能准确重放已有经历。

## 四、第二主体：模型如何充当工作人员

### 4.1 “工作人员”不能只等于一个角色提示词

建议将一个工作人员表示为：

\[
\text{Worker}
=
(\text{角色},\text{模型策略},\text{权限},\text{可见信息},\text{记忆},\text{当前义务})
\]

其中，角色定义“负责什么”，模型决定“怎样行动”，权限定义“能做什么”，记忆记录“此前实际知道什么”。

同一个基础模型可以扮演多个工作人员，但各角色必须有独立的身份、上下文和记忆。不能因为共用模型，就共用全世界信息。

### 4.2 初步角色配置

建议先定义以下角色，其中资料负责人可以在第一版暂不独立运行。

| 工作角色 | 职责 | 主要信息 | 第一版是否训练 |
|---|---|---|---|
| **需求方／客户** | 提出业务目标、解释用途、调整需求 | 自己的需求与约束 | 否 |
| **项目负责人** | 分配工作、确认口径、协调交付 | 项目目标、团队规范和授权信息 | 否 |
| **执行分析师** | 搜索证据、分析、修改产物、检查并提交 | 经工具和沟通实际获得的信息 | **是，作为目标模型** |
| **资料负责人／同事** | 提供其掌握的材料、说明历史工作 | 被分配的局部资料与工作历史 | 暂不训练，可后续加入 |
| **审阅者** | 检查实际成果、提出修改要求或接受交付 | 被授权查看的提交物及相关证据 | 否 |

第一版采取：

> **一个可训练执行者，若干参数固定但能够条件响应的环境工作人员。**

“固定”不是每次都说同一句话，而是训练周期内不同时改变这些角色的模型版本和基本策略，以便识别目标模型的学习效果。

### 4.3 角色观察必须经过过滤

可以用下面的关系描述模型的行为：

\[
o_t^{(r)}=O_r(S_t)
\]

\[
a_t^{(r)}\sim \pi_{\theta_r}
\left(\cdot\mid h_t^{(r)},o_t^{(r)},\text{当前职责}\right)
\]

其中，\(O_r\) 根据身份、权限、时间和实际获取行为构造角色观察。

这意味着：

**可访问的信息，不一定已经被发现；已经进入角色收件箱的信息，不一定已经阅读；另一个角色掌握的信息，也不自动进入当前上下文。**

角色运行器应当保持这种区分，而不是在每轮提示中把所有重要资料整理好再交给目标模型。

### 4.4 世界内部角色与后台模型必须分开

后台还可能存在世界设计模型、示范 Teacher 和独立评审模型。

它们不是公司的“员工”，权限也不同。

尤其需要区分：

**业务审阅者**提供工作人员在真实任务中可以获得的反馈。

**独立验证器**检查事实、产物和任务效果，可以使用隐藏检查条件，但不把整套答案直接交给工作人员。

同一个模型可以承担两种后台功能，但必须运行在不同上下文和权限范围内。使用多个模型也不自动意味着评价独立、无偏。

## 五、第三主体：工作任务流如何建模

### 5.1 先统一五个概念

| 概念 | 含义 | 示例 |
|---|---|---|
| **项目** | 持续的业务目标及其背景 | 更新某公司的经营研究 |
| **工作任务流** | 使项目推进的工作义务、依赖和反馈结构 | 口径确认、模型更新、报告同步、审阅修订 |
| **工作任务** | 某角色在当前状态下承担的具体义务 | 将备忘录同步到最新版模型 |
| **行动** | 工作人员的一次实际操作 | 搜索邮件、修改公式、提交文件 |
| **执行轨迹** | 一次真实运行中的观察与行动序列 | 模型具体如何完成这项工作 |

**工作任务流不等于执行轨迹。**

任务流规定什么工作需要相互协调；执行轨迹由模型实际决策产生。我们不能用生成世界时的参考过程，要求目标模型逐步复现。

### 5.2 用工作原语组合项目，但不预设工具顺序

建议建立一组有业务意义的工作原语。

| 工作原语 | 典型前置条件 | 产生的结果或义务 |
|---|---|---|
| **确定范围与口径** | 存在需求，但部分条件尚需确认 | 经确认的范围、定义或待澄清事项 |
| **收集与核对证据** | 存在需要支持的事实或判断 | 可追溯的材料与核对结果 |
| **构建或更新分析产物** | 有输入、适用口径及待完成目标 | 新产物版本与变更说明 |
| **同步依赖成果** | 上游结果变化 | 更新后的报告、表格或相关说明 |
| **审阅与反馈** | 已提交特定版本 | 接受、缺陷说明或进一步要求 |
| **修订与重新交付** | 存在有效反馈或需求变更 | 修订版本及问题处理记录 |

这些原语描述业务功能，不规定“必须先调用邮件搜索，再调用表格读取”。

具体任务流应允许分支、并行和回环，而不是只支持一张无反馈的顺序流程图。

### 5.3 建议维护两种依赖结构

**工作依赖**表达“什么工作需要先得到什么结果”。

**产物依赖**表达“某个结论、表格或模型依赖哪些输入版本”。

二者需要关联，但不能混为一谈。

例如，备忘录是否需要修订，由产物依赖决定；修订后谁来审阅，则属于工作依赖。

这也是后续模拟“接手工作”“影响分析”“返工传播”的基础。

### 5.4 任务应该怎样产生

任务主要从三种来源产生：

**业务目标尚未满足。** 项目开始时需要完成建模、分析和交付。

**外部事件改变了工作条件。** 新资料、需求变化或假设调整使已有成果不再适用。

**实际行动产生了新的工作义务。** 提交触发审阅；发现信息缺口触发澄清；承诺提供资料形成后续交付。

因此，不必把项目中的全部任务在开始前枚举完毕。应当预设允许发生的机制，再根据实际状态实例化工作。

### 5.5 工作任务的最小数据结构

建议一个 `WorkItem` 至少包含：

| 字段 | 含义 |
|---|---|
| `project_id / work_item_id` | 所属项目与任务标识 |
| `origin_event` | 为什么产生这项工作 |
| `owner_role` | 当前责任角色 |
| `goal` | 要实现的业务目标 |
| `visible_requirements` | 通过任务或环境可发现的要求 |
| `inputs / dependencies` | 依赖的材料、版本与其他工作 |
| `deliverables` | 需要提交的成果 |
| `status` | 待处理、执行中、阻塞、待审阅、需修订、已接受等 |
| `acceptance_spec_ref` | 独立验证规范的引用，不直接暴露答案 |

“已接受”需要绑定需求和产物版本。需求改变后，可以产生新任务或重新打开相关义务，而不是把之前的历史状态抹掉。

同时，**业务角色接受了交付，不等于独立评价确认其正确**。这两个结果应分别保存。

## 六、工作任务流空间怎样合成

这一部分是项目最主要的研究对象。

建议把空间生成拆成五个阶段，而不是直接让大模型“一次生成整个公司”。

### 6.1 建立项目原型

从有使用权的专业工作描述、专家设计和公开业务流程中，形成少量项目原型。

第一类原型可以是：

> 新资料到达后，更新已有分析模型，并使下游研究报告与之保持一致。

原型需要明确业务目标、角色、产物类型、依赖关系和允许发生的变化。

它不是一份完整解题答案。

### 6.2 生成结构化项目定义

世界设计器选择具体信息结构和过程结构，例如：

口径是否已经确认、信息由谁掌握、模型影响几个下游产物、审阅在哪个节点发生、哪些事件可能改变需求。

这些变化不能独立随机拼装。需要澄清的任务必须存在有效沟通渠道；要求同步的成果必须确实依赖发生变化的内容。

### 6.3 构建一致的工作历史与实际产物

采用“结构化构造＋关键片段真实执行”的混合方式。

背景历史可以紧凑生成；对当前任务有决定性影响的模型、文件版本和修改过程，优先通过真实工具形成。

材料应当是项目事件留下的结果，而不是互相独立生成的一组附件。

### 6.4 从时间节点切出可执行工作情境

在某个项目节点保存环境快照，形成目标模型需要接手的工作。

切片时只提供该时刻可用的信息。不能先完成整个项目，再只删除最终报告，却留下已经引用未来结果的邮件、索引或摘要。

随后允许模型继续推动项目，而不只是回答当前节点的一道问题。

### 6.5 按结构扩展空间

建议主要控制下面五个维度：

| 空间维度 | 有意义的变化 |
|---|---|
| **信息分布** | 信息集中、跨应用分散、由其他角色掌握、需要澄清 |
| **产物依赖** | 单一输出、多输出共享输入、跨文件引用、局部或广泛影响 |
| **项目阶段** | 从零开始、接手半成品、更新、审阅后修订 |
| **组织关系** | 信息所有者、决策者、执行者和审阅者是否分离 |
| **事件结构** | 新资料、需求变化、假设变化、行动触发的反馈 |

需要分别记录**表面多样性、结构多样性和合法解决路径多样性**。换公司名称、重排文件名和改写提示有用途，但不能替代结构覆盖。

空间扩展也不应只追逐难例。建议区分代表性任务池和压力测试池，避免最后合成出一个“所有文件都冲突、所有同事都拖延、每次交付都返工”的失真世界。

## 七、完整的软件初步架构

建议先按八个逻辑模块组织。它们是职责划分，**不要求第一版部署成八个微服务**。

| 模块 | 主要输入 | 核心职责 | 主要输出 |
|---|---|---|---|
| **1. Project Designer** 项目设计器 | 项目原型、来源材料、覆盖目标 | 生成项目目标、角色关系和允许的事件结构 | `ProjectSpec`、`RoleSpec` |
| **2. World Compiler** 世界编译器 | 项目定义、证据、历史过程 | 生成实际文件、应用状态和初始快照 | 可运行的世界实例 |
| **3. Environment Kernel** 环境内核 | 工具动作、事件 | 执行权限、维护时间和状态、保存快照 | 观察、状态变化、事件记录 |
| **4. Staff Runtime** 工作人员运行器 | 角色配置、可见上下文、模型 | 构造角色输入、调用模型、提交行动 | 角色行动与交互记录 |
| **5. Workflow Engine** 工作流引擎 | 项目规则、实际事件、产物变化 | 生成和更新工作义务、依赖和交接状态 | `WorkItem` 与项目进度 |
| **6. Validation Service** 验证服务 | 任务要求、证据、轨迹、实际产物 | 检查来源、计算、交付、状态一致性 | 分项评价、缺陷类型、不确定项 |
| **7. Learning Bridge** 学习适配层 | 模型调用、轨迹、奖励、有效性结果 | 编译监督数据或交互训练样本 | 数据包与训练输入 |
| **8. Curriculum Controller** 课程控制器 | 开发集表现、失败诊断、生成成本 | 调整后续结构与任务分配 | 新一轮合成配置 |

### 7.1 谁负责改变状态

这是实现中最重要的一条：

> **所有工作人员都通过工具或明确的业务动作改变世界；环境内核负责提交和记录这些变化。**

模型输出只是行动候选，不能直接修改后台状态字典。

工作流引擎可以依据实际变化生成新工作、标记某成果需要复核，但不能偷偷把错误公式修正，再让模型获得完成奖励。

### 7.2 核心持久化对象

第一版可以围绕以下对象设计存储：

`WorldSpec`、`RoleSpec`、`ProjectSpec`、`WorldSnapshot`、`WorkItem`、`ArtifactVersion`、`InteractionRecord`、`EvaluationRecord`。

其中需要始终区分：

**世界规格**描述一类世界如何运行；\
**世界实例**保存一次具体运行的状态；\
**执行记录**保存这次运行实际发生了什么。

同一个世界规格可以产生多个实例，同一个初始实例可以产生不同执行分支。不能把不同分支的工具结果混成一条训练轨迹。

### 7.3 与 APEX 底座怎样衔接

Archipelago 官方代码已经区分环境、Agent runner 和 grading，支持 MCP 应用、容器化运行及前后快照比较。它可以作为环境运行与评估适配的起点。:chatgpt-content-reference{index="1"}

但不能假设它已经实现了我们的全部要求。其 README 中，基于轨迹和提取值的部分验证类型仍标为待实现；项目状态引擎、动态角色协作、产物依赖校验和训练桥接需要单独建设或验证。:chatgpt-content-reference{index="2"}

另外，APEX-Agents 1.1 当前以 Harbor 任务包交付。建议核心对象保持独立，通过运行适配层连接 Archipelago 或 Harbor，不让项目定义绑定某一版目录结构。:chatgpt-content-reference{index="3"}

这里的“基于 APEX”主要指**继承世界构造范式并复用适用的运行组件**。官方数据卡明确将 APEX-Agents 1.1 限定为评估用途，因此训练世界应独立构建，代码与材料的使用条件分别核对。:chatgpt-content-reference{index="4"}

## 八、用一个完整运行实例连接这些模块

以下是拟议的合成项目，不对应真实公司的内部工作。

### 项目目标

某研究团队需要在新一期材料发布后，更新公司 A 的经营分析工作簿和配套备忘录。

世界中已有旧模型、旧报告、公开材料快照和团队口径记录。

| 阶段 | 世界状态或事件 | 工作人员行为 | 系统真正记录的内容 |
|---|---|---|---|
| **项目启动** | 新材料到达，已有成果仍使用旧数据 | 负责人分配更新任务 | 新工作义务、可用材料时间 |
| **信息发现** | 指标口径分散在材料和邮件中 | 目标模型检索、比较、必要时询问 | 实际检索与沟通结果 |
| **模型更新** | 工作簿输入和公式需要调整 | 目标模型修改并重算 | 新文件版本、真实公式与输出 |
| **成果同步** | 备忘录可能仍引用旧结果 | 目标模型判断影响范围并修订 | 报告变更、引用版本 |
| **审阅** | 特定版本被正式提交 | 审阅者检查并接受或提出问题 | 针对实际产物的审阅记录 |
| **修订或交付** | 可能存在待修问题 | 目标模型继续处理，或完成交付 | 最终状态、成果及完整轨迹 |

假设目标模型更新了工作簿，却漏改备忘录中的一个比率。

系统不应自动补齐。审阅者可以基于自己能访问的工作簿和备忘录指出不一致，目标模型再定位并修正。

反过来，如果模型一次就完成正确，审阅者应允许通过。不能为了增加训练步骤而制造一个不存在的问题。

还可以增加一个合法的需求变化：负责人调整了情景假设。该变化应形成新版本要求，并影响相关计算和报告，而不是仅在聊天记录里出现一句话。

这个例子同时涉及：

**环境中的证据与产物、角色间的信息交换、工作流中的依赖与返工，以及目标模型的真实执行。**

## 九、如何把工作经历变成高质量数据和模型训练

### 9.1 数据产品不止一种

建议系统输出三类互相连接的数据。

| 数据产品 | 内容 | 用途 |
|---|---|---|
| **可执行工作情境包** | 世界快照、角色、任务、工具和验证规范 | 反复执行、评测、交互训练 |
| **完整工作经历包** | 实际模型上下文、行动、工具结果、版本变化和最终交付 | 行为研究、失败分析、恢复学习 |
| **编译后的训练包** | 合格监督目标、奖励、掩码、分段与权重信息 | SFT、偏好学习或多轮 RL |

同一段工作经历不必全部作为正向示范。错误可以保留在历史上下文中，有效修正可以成为监督目标；无法确定有效性的记录应单独保存，不能强行归入成功样本。

### 9.2 验证分为三个层次

**运行真实性**检查工具是否真实执行，产物是否真实生成，记录是否完整。

**业务与产物正确性**检查证据、期间、单位、公式、依赖和跨文件一致性。工作簿必要时应通过输入扰动后重算，检查它是否真正可用，而不只是缓存数字正确。

**专业交付质量**检查需求覆盖、解释是否有依据、假设是否清楚、结论是否恰当地表达不确定性。

FrontierFinance 的来源关联、细粒度研究要求适合借鉴到第三层和证据检查层，但需要扩展到实际文件和持续工作状态，而不仅评价最终文本。:chatgpt-content-reference{index="5"}

对于无法自动确定的专业判断，可以采用模型评审与专家抽查，但必须保存不确定性，不把评审模型的一致意见等同于事实真值。

### 9.3 内层训练循环

目标模型使用一个固定参数版本完成一批工作，随后根据有效经验更新，再进入下一批。

训练时只把目标模型实际生成的输出作为策略行为；其他角色消息和工具结果是观察，不能当作目标模型自己生成的内容。

需要保存真实上下文、输出 token、模型版本；RL 后端需要时，还要保存相应概率信息。不能仅凭事后整理的漂亮轨迹训练，却丢掉模型当时实际看到的输入。

Agent Lightning 的公开设计已经提供模型调用记录、rollout 管理和训练后端连接，可以作为学习适配层的候选，但与这套工作世界的具体兼容性仍需验证。:chatgpt-content-reference{index="6"}

### 9.4 外层空间优化循环

外层根据失败诊断调整下一轮合成：

模型能找数据但不会同步下游成果，就扩展不同依赖结构；模型不会判断何时澄清，就增加不同信息可得性和授权关系下的工作情境。

但应先区分失败来自：

**模型能力不足、角色模拟失真、任务不可完成，还是工具和验证器问题。**

第一版不要同时训练所有角色、修改评分标准、更新工具和改变课程。建议先固定角色策略、核心工具、评价标准和训练协议，主要更新目标模型；内层成立后再引入外层课程调整。

## 十、第一版应该怎样收敛

### 10.1 建议的 v0.1 范围

| 维度 | 第一版建议 |
|---|---|
| **领域** | 金融研究与分析 |
| **项目族** | 既有模型更新、报告同步与审阅修订 |
| **主要角色** | 需求方、项目负责人、目标分析师、审阅者 |
| **工具** | 文件与检索、邮件、表格、代码计算 |
| **工作变化** | 新资料到达、假设调整、真实审阅反馈 |
| **目标模型** | 先训练一个执行角色，不绑定具体型号 |
| **环境模式** | 优先固定证据快照，后续检验开放检索迁移 |
| **训练方式** | 先打通有效经验编译，再比较监督学习与交互 RL |
| **外层优化** | 先做可解释的结构配额调整，不急于训练复杂总控模型 |

第一版不需要完整虚拟公司、全 GUI、全部办公应用或所有角色共同学习。

但也不应退化为“给模型一份文档算一个数”。最小原型至少要保留：**信息分散、真实修改、跨产物依赖、角色反馈和状态延续**。

### 10.2 分阶段验证什么

**阶段 A：工作世界成立。**\
证明项目定义能够生成一致的材料和状态；角色权限生效；工具真实执行；事件能够形成合理的新工作。每类任务应存在可行解决方式，或者明确的澄清、阻塞出口。

**阶段 B：经历具有训练价值。**\
目标模型产生的经历能够被正确编译，训练后在未见工作情境中改善，而不只是熟悉文件名和输出格式。

**阶段 C：项目过程模拟具有独立价值。**\
在模型、工具、业务目标和预算相近的条件下，比较独立任务合成、失败定向扩展，以及持续项目过程模拟。

**阶段 D：闭环优于静态空间。**\
检验根据能力反馈改变工作结构，是否比预先固定配额更有效，并把生成、验证和反馈评估成本一并计入。

小规模原型通过阶段 A，只说明机制能够运行；不需要在此阶段承担规模化泛化证明。相应地，也不能把几个成功项目直接写成稳定训练收益。

## 十一、这份架构真正要检验的研究命题

Agent-World 等工作已经把环境与任务生成、多环境训练和能力反馈连接起来。因此，ProWorkSim 的贡献不应写成“首次把环境生成和强化学习接起来”。:chatgpt-content-reference{index="7"}

我建议将研究命题明确为：

> **相较于独立任务环境合成，具有持续状态、角色信息约束和跨产物依赖的项目过程模拟，能否产生更有效的专业工作学习经历？**

评价重点应对应这个命题。

| 评价对象 | 应观察什么 |
|---|---|
| **环境有效性** | 时间、来源、权限和状态是否一致，任务是否合理可完成 |
| **空间覆盖** | 覆盖了哪些信息结构、依赖结构和工作阶段，而不只是生成多少题 |
| **协作能力** | 是否在需要时寻求正确角色的信息或授权 |
| **持续工作能力** | 能否接手已有工作、处理需求变化、修复错误并承担先前行动的后果 |
| **交付物可用性** | 成果是否正确、可重算、版本一致，并在后续工作中继续成立 |
| **学习与成本** | 未见项目上的能力增量，以及生成、验证、训练的整体成本 |

同一项目的多个切片、同一报告改写出的多个任务不能被当成完全独立的泛化样本。训练与评价需要按项目来源、材料关联和生成谱系隔离，并专门保留未见结构组合。

## 当前架构结论

**ProWorkSim 的主体应该是一个“能产生工作、能被行动改变、能保留工作后果”的世界。**

工作环境提供资料、工具、规则和状态；模型工作人员在局部信息下作出决策；任务流把业务目标、产物依赖和角色交接连接起来。外围的合成系统负责扩展这些世界，学习系统负责把真实经历转化为模型能力。

因此，当前最优先定义的不是一个总控 Agent 的提示词，而是四个基础对象：

\[
\boxed{
\text{WorldSpec}
\quad
\text{RoleSpec}
\quad
\text{ProjectSpec}
\quad
\text{WorkItem}
}
\]

**先把“世界里有什么、每个人知道什么、工作为什么产生、完成后改变什么”定义清楚，再实现模型运行和训练闭环。** 这会使项目始终围绕你提出的“工作任务流空间”展开，而不是逐渐变成一个通用多智能体框架。
