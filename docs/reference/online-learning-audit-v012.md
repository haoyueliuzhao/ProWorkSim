## 审计结论

**v0.12 可以保留为“真实联合经历、成员局部动作与基础训练接口已经接通”的阶段基线，但尚未建立直接在线训练闭环。**本轮最有价值的结果，不是采样量增加，而是已经能够区分：模型实际做了什么、哪些工作有效、哪些动作可训练，以及哪些经历能够进入 ID‑VTDO 的重配置支持。报告也明确记录了本轮 actor、critic 均未更新，D4、D5 未执行。:chatgpt-content-reference{index="0"}

结合刚才确认的方向，下一阶段应当作一个实质调整：

> **不再以“先采到一批完整成功、多方法齐备的轨迹”作为全部训练的前置条件，而是在边界明确、反馈可信的工作情境中，让一个共享模型直接进行“交互—更新—再交互”。ID‑VTDO 的支持统计和配置机制嵌入这个在线过程，而不是先建设离线训练数据集。**

本次独立复现了一处 **critic 状态特征与世界实际枚举不一致**的问题；还从源码确认了一个与本轮大量失败相关的接口表达缺口。它们需要定向修订，但不需要推倒现有世界，也不应再次演变成长期的“先完善全部环境再训练”。

# 二、对本轮实验的主要判断

## 1. 三成员工作机制成立，但程序可行性、模型可行性和训练支持仍是三件事

本轮 manual route 已经要求真实成员读取并选择证据，环境只负责权限内送达，不自动替提供者回复。主动交接与请求后交接的程序见证也使用相同初始信息和角色说明。**这比把“同事”实现为固定答案服务，更接近我们的学习问题。**:chatgpt-content-reference{index="1"}

DeepSeek 的 16 条联合运行进一步说明，至少部分真实模型团队能够在这个机制下完成工作。但必须继续保持以下区分：

| 观察 | 本轮数量 | 能说明什么 |
|---|---:|---|
| 制度完成 | 6 | 工作记录达到规定的制度终点 |
| 制度完成且独立内容正确 | 5 | 相应交付满足有限内容合同 |
| Reward＝1 | 7 | 满足当时 RewardSpec 的目标，不自动等于完整工作有效 |
| 严格 \(V=true\) | 3 | 同时满足本轮声明的记录、权限、依据和交付条件 |
| 可重配的本地 actor 支持 | 0 | 尚不能据此开展规定的近策略 actor 更新与组成优化 |

三条有效经历分属不同精确情境，且商业 API 没有实际 token trace，不能拼成当前本地模型的训练支持。报告对此处理正确。:chatgpt-content-reference{index="2"}

不过，**Reward 与完整工作义务之间的差别，下一轮要从“诊断上区分”进一步变成“训练目标明确”。**如果希望共享模型学会完成包含复核在内的团队工作，不能只奖励实现者的正确内容，却让复核是否发生对回报没有影响；反过来，也不能仅凭批准动作就给完整成功奖励。

这需要新版本的任务／奖励合同，不是追溯改写本轮七个正奖励。

## 2. 新 Qwen 批次的主要瓶颈，在进入业务推理之前就大量发生

新本地批次的记录完整性有明显进展：952 次生成均有实际响应和可恢复动作，三名成员的完整 actor 轨迹都能形成。但其结果是 **868 次世界工具调用中 750 次被拒，拒绝比例约 86.4%**；没有成功的 `read_object`、`handoff_information` 或 `approve`。:chatgpt-content-reference{index="3"}

与此同时，14 次 SQL 确实执行成功，另外 3 次 build 请求是在执行前被拒。这说明不能把全批零奖励简单概括为“模型不会 SQL”。**当前大量失败首先集中在对象引用、工具参数、工作权限和交接入口。**:chatgpt-content-reference{index="4"}

首个预声明诊断实例更加具体：51 条拒绝后的转移都实际收到了错误反馈，其中 38 次仍使用完全相同参数。它支持“模型未能有效利用这些反馈”的判断，但只针对这个实例，不能直接外推到全部 16 段。:chatgpt-content-reference{index="5"}

**因此，继续把同一接口下的 16 槽扩大为 64 或 256 槽，现阶段很可能主要增加相似拒绝，而不是增加可学习工作方式。**优先事项是减少不必要的接口歧义，并让在线学习能够获得较短、真实且可判定的行动后果。

## 3. 数值修订支持工程候选，不能替代学习验证

小张量 profiler 和三条历史响应的概率比较，为新 attention 路径提供了独立工程依据；但它们没有产生新策略更新，也没有测量更新后工作能力。新采集又改变了公开结构说明和决策预算，不能把前后结果解释成 attention 修订的单因素效果。:chatgpt-content-reference{index="6"}

这里不建议继续增加大量历史响应的精密复算。应在新的在线训练入口中，核对**当前有效权重、实际采样分布与本轮更新前概率**，然后检验真实更新及新策略交互。

## 4. D3 按旧门槛停止是正确执行，但旧门槛不应成为永久训练条件

本轮四个固定槽完整恢复了 240 次生成与 14,669 个自身输出 token，但原 D0 未通过、四个回报均为零，所以按原协议停止。**这个决定没有问题，不能现在把旧 gate 改成 true 来补做一次“已获准训练”。**:chatgpt-content-reference{index="7"}

需要调整的是**下一版协议**：

**基础在线 RL 的准入**，应检查环境、记录、奖励、概率和优化是否具有明确语义；  
**ID‑VTDO 的准入**，还需要有效方法类别、成员动作和足够支持。

两者不能合并成“当前模型先能稳定完成整条工作链，并产生多类成功经历，才开始任何训练”。

PPO 的基本结构本来就是当前策略与环境交互，再利用这些经历更新策略，重复这一过程；不是等一个成功轨迹集建设完毕才启动。:chatgpt-content-reference{index="8"}

但这也不意味着应该对全零终局回报盲目执行更多梯度步。**没有真实差别信号时，随机初始化 critic 产生的优势差异，不能被当作已经获得有意义的工作学习信号。**应改善可学习情境和反馈，而不是人为制造“有梯度”的证明。

# 三、需要补修的具体问题

## 1. 已局部复现：critic 计数使用了错误的工作状态名称

训练脚本 `past_features()` 统计：

```python
["open", "active", "pending", "accepted", "blocked"]
```

但世界实际投影使用：

```text
in_progress
in_review
```

来分别表示进行中和待审，`WorldCore.observe()` 又直接保留这些状态，没有转换成 `active/pending`。  

本次在其他观察内容相同的条件下，将状态分别设置为 `in_progress`、`in_review`，原函数生成了**完全相同的 30 维特征**；预定的两个状态栏均为零。控制中的 `open` 与 `accepted` 则能够被区分。

**影响应限定为：critic 特征没有按预期表达这两种实际状态。**由于本轮根本没有执行模型训练，它不是本轮 Qwen 拒绝循环的已证实原因；也不推翻 CPU 上 \(Q=B\) 的算术恒等。

建议修复规范枚举或改用明确的公共状态谓词，版本化特征定义，并补一条“真实世界观察→critic 输入”的回归。**不需要因此重建大型 critic，也不应覆盖旧 prepared 材料来假装原特征正确。**

## 2. 源码确认：工具公开 schema 没有充分表达运行时的互斥要求

读取实现要求 `alias` 与 `object_id` **恰好提供一个**；但工具定义将二者分别列为可选属性，没有在机器可读 schema 中表达二选一。嵌套 `reference` 等对象的字段约束也比较粗。 

因此，即使生成了一份满足当前外层 JSON schema 的参数，也可能必然被底层拒绝。

**底层拒绝歧义引用是正确的；问题在于公开行动接口不够完整。**这与报告中反复同时填写 alias 和 object_id 的现象相符，但尚不能据此声称它是全部失败的唯一原因。

建议采用一种清楚的引用方式，或拆成“按别名读取”和“按精确版本读取”两个接口；对工作 ID、输入别名、对象版本和提交对象分别给出完整类型。

这里应守住边界：

> **完善语法与可见引用，不等于替模型选择正确业务依据。**

不能在后台猜测哪个版本正确、丢弃模型提供的一个字段、自动补采用或把两次操作合成一条隐藏的正确工作流。

若使用约束解码，约束只能依据公开语法与角色已经可见的信息；还必须保存实际约束后的行为概率，并让训练概率复算对应同一个条件分布。

# 四、下一阶段的架构中心：共享模型在线训练器

当前 D3 是一个**读取指定归档、验证固定 base、执行单窗口预检的脚本**。它对这次实验是合理的，但还不是反复更新和重新交互的通用入口：其中包括固定四槽选择、旧 D0 引用以及“未更新 base”的身份要求。 

下一步应当把已有模块连接为一个在线运行器，而不是另外建设一条轨迹数据生产线：

```text
初始化共享 actor、独立 critic 和优化器
    ↓
当前 θt 的多个角色实例直接进入训练世界
    ↓
真实查询、交接、修改、执行、复核和交付
    ↓
环境产生结果；训练器计算奖励与优势
    ↓
恢复成员局部动作，进行本轮共享参数更新
    ↓
所有目标角色同步 θt+1
    ↓
θt+1 产生新的行动与新的世界后果
```

这与 V1 的在线算法一致：窗口内暂时固定材料用于近策略更新与配置比较，更新后由新策略重新进入世界。**暂存经历和保存日志没有问题；关键在于它们是在线闭环内部的中间量，而不是一个先收集完成、再独立训练的固定数据集。**:chatgpt-content-reference{index="16"}

### 参数与角色应明确这样组织

**一套有效 actor 参数、一个共享适配器、一个 actor 优化器。**provider、implementer、reviewer 的职责、记忆和权限不同，但不分别训练三套岗位权重。

每个窗口内所有目标角色使用同一版本；更新后同步同一个新版本。原始 base 可以始终只读，但策略身份要包含**实际适配器权重**，不能要求第二窗口仍与未训练 base 相同。

critic 是训练辅助组件，可以使用允许的联合历史；actor 仍只接收当时本角色实际可见的输入。共享参数不改变动作归属：同事消息和工具返回是观察，不是接收者的生成目标。

另外，**用实际生成 token 复算 log probability，不等于进行 SFT**。区别在于更新目标来自环境奖励与优势，而不是把一份教师答案当作监督目标。

初版建议在完整短工作片段之间更新，减少策略陈旧处理的复杂度。后续引入长任务截断时，再明确区分自然终止与预算截断，以及 continuation、bootstrap 和版本切换。参数刷新后不能继续使用旧权重生成的 KV cache，但世界事实与合法会话历史必须保持。

# 五、不依赖 SFT，怎样让在线学习获得可用信号

我们需要避免两种极端：

**一端是要求模型先学会完整任务，才允许 RL；另一端是对当前长链全零失败反复更新，期待它自然解决全部接口与协作问题。**

更合适的方式是：**在训练世界中配置不同长度、都有实际工作目标的情境，并让模型直接在其中学习。**

| 训练情境 | 模型实际承担的工作 | 可验证的结果 |
|---|---|---|
| **证据取得与交接** | 读取资料、判断允许版本、向正确接收者交接 | 资料、版本、接收者与工作范围正确，实际送达 |
| **基于依据的实现** | 在合法起点上修改 SQL、执行、检查和提交 | 实际结果满足公开合同，依据绑定一致 |
| **复核与处理** | 读取真实提交与独立材料，确认或定位问题 | 对正确、错误交付采取有依据的处理 |
| **完整三成员链** | 自主完成获取、交接、实现和复核 | 整体业务目标、过程要求与交付均成立 |

**这些是环境任务，不是四份提供给模型模仿的标准轨迹。**模型仍需自己选择动作，错误真实发生，参数更新仍来自环境后果。

起点可以由可核验的场景初始化或实际执行前缀形成，但准备角色的历史要标明，不能成为目标模型自己的动作记录，也不能夹带未来正确答案。

### 奖励也要对应所声明的工作范围

短片段可以有自己的终局目标，不必等整条团队链完成才知道前面所有行动是否有用。但短片段通过不能计为完整团队成功。

若确需增加阶段性奖励，应绑定真实成果、责任与版本，防止反复发送、重新提交、先制造错误再修复等刷分。**不要按消息数量、批准次数或工具调用成功次数直接加奖。**

这是新的基础训练合同；在正式 ID‑VTDO 比较前，应固定其任务份额、奖励和预算，并由所有方法共同使用。它不是让 ID‑VTDO 同时优化课程，也不改变本轮旧 RewardSpec 的结果。

如果一个可训练初始模型连这些基础公开操作都长期无法进入，可以在开发池另选工具基础更适合的**统一检查点**。不必死守某个模型，也不应默认退回“先采 Teacher 轨迹做 SFT”的主路线。

# 六、建议的下一轮实验安排

建议将下一阶段命名为：

# **共享模型直接在线学习与工作接口验证**

## O0：只补齐影响在线执行的必要缺口

完成 critic 状态映射、工具引用 schema、模型参数刷新以及实际概率记录的定向检查。

模型侧用少量短工作片段检验：能否读取、交接、处理一次真实错误并继续。对接口版本进行比较时保持同一初始模型和工作条件，保留全部失败，不在后台修正动作。

**本组验收的是当前接口可用，不是要求所有完整项目均已成功。**旧 D0 结果继续保留，新接口另行冻结。

## O1：真正完成至少两个连续的在线更新周期

首先使用基础 RL，即 \(Q=B\)，在训练世界中执行：

\[
\theta_0
\xrightarrow{\text{实际交互}}
\mathcal B_0
\xrightarrow{\text{更新}}
\theta_1
\xrightarrow{\text{新交互}}
\mathcal B_1
\xrightarrow{\text{更新}}
\theta_2.
\]

必须确认：更新确实改变了共享模型；所有角色随后使用正确的新版本；下一窗口的动作与工具结果是重新产生的，不是重播 \(\mathcal B_0\)。

**没有有效重配支持不阻断这一步。**可信失败仍参与基础处理；只有记录或回报不可信的情况按预声明规则隔离。

也不必要求每一个窗口都出现不同终局奖励。若某窗口实际优势为零，要如实记录 actor 没有相应回报驱动更新，按固定探索和预算规则继续；不能补采到出现正例才公开窗口，或把 critic 初始化噪声当学习效果。

两个周期证明的是**在线工程闭环**，不是能力收益。

## O2：检验基础在线学习是否改善工作

在相同初始共享模型下，比较冻结模型与直接在线基础 RL。评价使用新的工作情境，检查：

**证据取得与交接、错误反馈后的行动调整、实际实现、独立复核，以及完整链条的有效交付。**

工具成功率、训练 loss、梯度范数和参数变化只作诊断。主要结论仍由工作结果决定。

训练按预声明窗口和资源预算连续运行，检查点选择只使用开发池。冻结模型是能力基线，不应因其没有训练成本就被包装成“同总预算算法对照”；正式算法资源比较后续另设。

## O3：在在线运行中同步统计 ID‑VTDO 支持

支持统计应随每个策略窗口产生，而不是另起“优质轨迹采集批”。

对每个 \((\xi,i)\) 记录真实分母、有效性、可映射类别、本人动作、类内数量以及 \(b_i\)。无支持、单类别和未映射块保持基础处理；不能把以前所有模型版本的成功轨迹无条件合并为当前策略支持。

**这一步可以与 O2 同时开展。**不必等整个支持目录完成后才允许基础模型学习，也不必为了凑够两类而改角色提示或跨情境合并。V1 明确要求在无重配支持时保留基础处理，且任务广度与类内密度不能相互替代。:chatgpt-content-reference{index="17"} :chatgpt-content-reference{index="18"}

## O4：达到条件后，再进行 ID‑VTDO 的在线窗口干预

当基础学习可运行、当前窗口确有相应支持时，再执行：

**共同 actor／critic／optimizer 起点 → 暂时固定本窗口经历 → 比较经验配置 → 在开发世界中实际测量训练后效用 → 回到共同起点完成正式更新 → 新策略继续工作。**

这仍然是在线训练内部的机制检验，不是转为离线 RL。

对照至少保留基础 MARL、所有成员共用权重、通用成员—轨迹元重加权，以及不含信息依赖的特征；联合探测再与相同预算的随机成员对比较。不能仅优于均匀权重，就声称信息结构与成员配置的贡献。:chatgpt-content-reference{index="19"}

# 七、泛化与多项目目标不能在“小闭环”中丢掉

当前 D1 是**一个构造 SQL 家族、一个项目、一个工作节点**。这样收窄有利于定位问题，但它只是最小学习载体，不能成为最终任务空间。:chatgpt-content-reference{index="20"}

建议分两步拓展，而不是现在同时增加大量新模板。

**先在当前短情境上完成真实在线学习闭环，再把同一个共享 actor 接回已有的四项目串并联环境。**并行项目之间继续保留指标粒度、资料定义和接口需求的交叉；下游必须消费实际上游成果，而不是只等待其状态完成。

与此同时，从现在开始划分训练、贡献开发与锁定测试的来源及世界家族。不能先在所有变体上训练，再随机留几条 rollout 作为“新项目测试”。同一来源的不同数值和信息布局能够检验有限适应，但不能替代独立来源。:chatgpt-content-reference{index="21"}

共享模型还应接受两类实用性评价：

**只部署一个实例，接手某个岗位；多个同权重实例，组成工作团队。**

两种情况下都冻结参数测试新事实、新信息安排和新项目关系。不能要求用户必须部署训练时的整套团队才获得收益，也不能利用模型已经记住的私有事实证明它会合法查询。:chatgpt-content-reference{index="22"}

如果目前只有一个来源家族，可以先形成该范围内的机制与学习结果；强泛化结论等独立项目家族实际加入后再报告。真实金融资料继续作为校准支撑，不设置采集数量门槛。

# 八、资源应投入到哪里

本次算术核对与报告一致：资源口径共 **1,917 次 HTTP、19,891,192 个已知采样 token**，其中包括 service-only 返回；52 个封闭 episode 与 1 个开放 episode 仍应分开。费用估计也不能代表未货币化的 GPU、CPU 和全部研究成本。:chatgpt-content-reference{index="23"}

新 Qwen 批次输入 token 占约 **99.42%**。这个比例不意味着输入都无用，但提示应优先减少每轮重复的工具规格和冗余观察，而不是仅增加决策上限；必要历史与证据不能被静默删去。原始请求仍需完整可恢复。:chatgpt-content-reference{index="24"}

下一阶段预算优先用于：

**当前接口的针对性验证、真实在线更新周期、独立开发情境，以及新来源上的冻结评测。**

不建议继续把主要算力投入相同冻结策略的大量重复拒绝，也不建议再次围绕历史少量输出建立复杂的专用反向回放方案。数值校验服务于新训练循环，而不是成为长期独立主线。

## 最终推进判断

**本轮没有完成在线学习，但已经具备启动它所需的大部分记录与执行基础。**应保留 D0 的失败、D1 的真实结果、D2 的零支持和 D3 的未执行；不需要为了推进而改写任何旧结论。

需要重新设计的是下一步的先后关系：

\[
\boxed{
\text{公开行动接口可用}
\rightarrow
\text{共享模型直接在线学习}
\rightarrow
\text{在线产生并诊断方法支持}
\rightarrow
\text{ID‑VTDO 配置干预}
\rightarrow
\text{未见项目验证}
}
\]

**不是“先让模型在全部项目上成功，再允许训练”；也不是“先积累足够成功轨迹，再做 SFT 或离线 RL”。**

下一轮最值得取得的结果，是同一个模型确实在世界中工作、受到真实后果反馈、完成参数更新，并以新策略继续工作；随后用独立情境判断它是否真正学到了可迁移能力。**内核、日志、支持统计和贡献估计都应服务于这个闭环，而不再成为无限延长的训练前置工程。**
