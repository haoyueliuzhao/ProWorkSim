# 二、对本轮主要成果的判断

## 1. 两个模板确实引入了不同的工作结构

### 财务资料核对：不再假定每项工作都有一个确定数值答案

当前合同允许保留冲突、不可比、缺失和歧义，并要求完整覆盖原始记录，而不是默默选一个来源、删除重复候选或把缺失补零。:chatgpt-content-reference{index="3"}

源码中的评价也确实检查了这些内容：按集合核对键组覆盖，保留候选记录的重复性，分别判断期间、定义、币种和单位，最后核对行级结果与汇总。它没有调用工作人员的 matcher 生成自己的答案。

本次局部复验确认了六类手工真值，以及漏组、重复组、不可比强算差值、缺失填零、实际比较值错误等负例。

**这项进展应保留：合理的不完备结果开始成为世界允许的工作成果，而不只是失败出口。**

### 报告审阅：检查的是实际正文，但仍然是有限句式

当前报告不仅检查 claim 元数据，还解析受检章节的实际正文；正确数字配错误期间、错误来源，或者 metadata 正确而正文写成 999，都不能仅靠元数据通过。:chatgpt-content-reference{index="5"}

不过，当前评价只接受两种公开的完整句式，额外语句不在相应语法内。源码也明确将开放论证、专业完整性和文风列为未评。

所以，准确表述仍然是：

> **具有正文语义约束的有限研究报告模板，而不是自由专业报告审阅系统。**

这是范围限制，不是要求本轮立即接入大模型评审或开放文本语义判断。

## 2. 共同问题关系的抽取是合理的

`issues`、`issue_responses`、`issue_decisions` 保存追加事实，`issue_views` 推导当前状态。提出问题、回应问题、接受修复或反驳，分别形成不同记录。

本次执行确认了几项关键性质：

**撤回和重新提交不会自动关闭问题；一个处理决定只解决对应问题；旧提交上的新意见可以保留为历史；重复同一决定不增加正式事实；错误对应关系会被拒绝。**

同时要继续保持报告中的边界：**处理决定绑定具体回应和提交，不证明未来所有版本都正确。**一个已解决问题之后再次出现缺陷，需要新的定位问题；不能把历史处理记录当作永久质量认证。:chatgpt-content-reference{index="8"}

这说明内核抽取的是可复用的**工作关系**，不是把领域评价器伪装成一个“永远正确的审阅者”。

## 3. 跨模板联动验证的是工作链，而不只是共享文件

X3 的重要之处在于：上游材料更正后，A 重新核对、交付并发布；B 再发现后继工作，采用新结果、制作报告并接受实际审阅。报告明确说明控制器没有直接修订 B、修改 B 文件或预填正确问题清单。:chatgpt-content-reference{index="9"}

三类质量结果也被合理分开：

| 情况 | 应如何解释 |
|---|---|
| A 核对正确，B 忠实并正确表达 | 有限总体目标达到 |
| A 错误但获批准，B 忠实表达错误接口 | A 质量失败；B 忠实性可通过；总体目标未达到 |
| A 正确，B metadata 正确但正文错误 | B 表达失败；实际修复后再判断 |

**下游忠实不等于上游正确，正式批准也不等于独立质量通过。**本轮保留了这些区别，而没有合并成一个“链条成功率”。:chatgpt-content-reference{index="10"}

不过，X3 的完整执行仍主要由你的实验记录支持，本次没有重新回放原服务器的全部跨模板动作。

## 4. 拒绝分类与开发失败的处理基本合理

新版不再根据异常文字猜测原因，而由知道违反哪项合同的边界提供分类；无法归因时保留 unknown。`tool_outcomes.py` 中确实实现了这一分离。

本次局部检查确认：同样的人类可读错误文字可以对应不同明确分类；没有结构化归因的错误不会自动被判成环境故障。

首次冻结后出现的非字典参数回归，属于本轮新增诊断路径的实现问题。报告保留原探针、补充四项检查并重新冻结、重跑，没有拿首次全通过替代遗漏路径的证据。这个处理应当保留。:chatgpt-content-reference{index="12"}

# 三、新发现：结构错误的交付可能使核对评价器异常退出

## 1. 本次实际复现

使用合法的核对合同和完整来源材料，仅将交付的核对部分改为以下两种形式：

| 交付内容 | 预期 | 实际结果 |
|---|---|---|
| `{"comparison": null}` | 返回交付结构不符合合同 | 抛出 `AttributeError` |
| `{"comparison": {"rows": [null]}}` | 指出某条结果行不是合法对象 | 抛出 `AttributeError` |

这里的 `comparison` 是该测试合同声明的结果路径；没有改变来源、匹配规则或评价目标。

原函数在确认目标对象和行元素类型前调用了：

```python
output.get("rows")
r.get("key", [])
```

而异常处理没有包含由这些调用产生的 `AttributeError`。

外层 `work_product.evaluate_submission()` 的异常列表也没有处理该异常，WorldCore 的评价入口则直接委托它。这部分是源码审阅结论；**本次动态复现发生在原始领域函数层，没有宣称已完成完整 ProjectSession 回放。** 

## 2. 应如何定级

这是一个**评价输入边界的健壮性缺陷**，两个触发属于同一根因。

它没有造成已证实的“错误交付获得通过”，也没有证明本轮六个固定核对场景被错判。但当工作人员不再是专门编写的程序时，输出形状错误是应当有明确结果的情况，不能让评价过程本身中断。

因此：

> **需要局部修复后再扩大非专用工作人员的接入；不应据此否定整个 v0.9。**

## 3. 建议的最小修复

先显式检查结果对象、`rows` 及各行的结构类型，再进入字段与业务判断。对不符合交付合同的内容，返回明确的结构性失败。

同时不要简单采用：

```text
捕获所有异常 → 一律记成工作人员失败
```

应继续区分：

**交付格式错误、来源本身不可用、目标未评，以及评价器实现故障。**

下一轮通过真实会话写入上述 JSON、建立合法来源绑定并提交，补齐端到端反例；正常及原有业务错误对照保留。修改评价版本并在新目录复验相关组即可，不需要因此重做无关的旧模型实验或全部故障矩阵。

# 四、现在适合转向哪些“其他模块”

本轮两个模板已经足以充当模块集成负载。**下一步不必立即再做第三、第四个行业模板，而应让这些工作摆脱各实验脚本的专门编排。**

从公开示例看，目前仍由主程序顺序调用作者的 `prepare/deliver`、审阅者的 `review`，再按结果调用批准。工作人员只能看到公开端口，这个边界是好的，但“谁何时工作、如何继续”仍主要由外层示例或实验代码安排。

建议启动两个主模块，配套一个最小支撑接口：

| 模块 | 主要作用 | 与内核的关系 |
|---|---|---|
| **统一工作人员运行模块** | 让不同角色以可替换的策略持续承接工作，管理各自上下文、行动机会和实际交互 | 使用内核提供的可见状态与工具，不替内核创造权限，也不替策略决定正确答案 |
| **场景构建与编排模块** | 将项目包、角色配置、共享关系和事件政策组合成可运行情境 | 向世界部署声明，不在运行中通过私改状态“推动剧情” |
| **评价与经历记录接口** | 汇总实际工作经历，分别评价制度进度、内容质量和过程要求 | 读取固定事实与交付物，不修改既有世界历史 |

这三个部分应围绕**同一条“核对—发布—报告—审阅”链**接起来，不各自发展成一个大型新工程。

# 五、模块一：统一工作人员运行

## 1. 它解决的不是“再写一个 Agent 类”

核心目标是把三件事分开：

**角色配置决定谁知道什么、负责什么；工作人员策略决定如何行动；运行模块负责让决策真实发生并保存经历。**

现有 `ReconciliationWorker` 和 `PublicReportWorker` 可以保留为规则策略，而不是废弃重写。但它们不应继续要求实验主程序理解每一步业务操作，才能把整段工作串起来。

未来换成模型时，也不能由运行模块暗中调用 `prepare()` 生成正确报告，再说是模型完成了工作。

## 2. 调度机会，不等于安排正确步骤

运行模块可以决定：

> 现在让哪个工作人员获得一次行动机会。

但不应默认替它决定：

> 现在必须读取来源 A，然后修复第二节，再同意第一项意见。

需要区分**运行调度**与**业务规划**。前者可以先采用透明的轮转或事件唤醒；后者属于工作人员策略。

同样，审阅者应根据自己实际读取的提交和证据提出意见。控制器不能因为独立评价失败，就把正确问题清单塞给审阅者。

## 3. 当前适合的范围

先统一规则工作人员的接入，保持单写者世界。每个角色具有独立的上下文、动作记录和工作进度；不同项目的会话由可信宿主绑定。

先不要求所有角色都换成模型，也不要求实现任意时刻的策略崩溃恢复。**一段完整行动返回后的继续执行**已经足以支持首版模块实验。

# 六、模块二：场景构建与编排

## 1. 从“脚本中的一个故事”变成“可声明的工作情境”

一个场景应当说明：

| 内容 | 回答的问题 |
|---|---|
| 世界与项目配置 | 启动哪些项目，使用哪些已有对象？ |
| 角色与信息分布 | 谁负责、谁知道、谁有权确认？ |
| 工作起点 | 从初始、部分完成、等待还是待审状态接手？ |
| 事件政策 | 什么变化可以在什么条件下发生？ |
| 共享与依赖 | 哪个成果被哪个工作采用，采用什么政策？ |
| 运行边界 | 何时算完成、合理阻塞或实验截断？ |

第一版可以复用现有项目包和有限事件规则，**不需要先让大模型自由生成世界代码，也不需要建设复杂的新规则语言**。

## 2. 场景必须约束变化，而不是固定唯一轨迹

例如，声明“资料更正到达后，持续维护项目需要形成后继工作”是世界规则；声明“执行者下一步必须调用哪个函数”则是策略脚本。

场景可以控制外部资料何时到达，但不能在看到模型快失败时临时补料、改变截止条件或取消本来应发生的事件。

**后台为了运行事件可以读取必要状态；工作人员能否得知这些变化，仍需经过角色可见性与通知规则。**

## 3. 不要立即追求大规模场景合成

先把 v0.9 已有情境迁入统一声明入口，再增加少量有意义的变化：信息分布、交付组织、事件发生阶段。

同时区分：

**表面变化**，例如文件名和人员显示名；  
**结构变化**，例如谁掌握资料、工作何时被打断、哪些产物受影响。

不能生成一百个名称变体，就声称覆盖了一百种工作流程。

# 七、配套接口：评价与经历记录，但暂不升级为训练系统

这个接口的近期价值，是让新模块的运行结果可解释，而不是尽快导出大量 SFT。

建议每次运行分别保留：

**工作人员实际看到什么；实际做了什么；环境发生了什么；控制器进行了什么干预；最终交付和评价依据是什么。**

评价至少分开以下对象：

| 对象 | 需要判断什么 |
|---|---|
| 制度进度 | 是否提交、是否被接受、哪些工作仍待处理 |
| 内容质量 | 有限领域合同是否成立 |
| 过程约束 | 是否发生明确不允许的正式动作，是否保持应保持的内容 |
| 不完备性 | 信息缺失、目标不可评和合理未解决项 |
| 运行问题 | 工具异常、评价故障、预算截断和不支持的能力 |

**不能把“材料未知”和“计算错误”都计为失败，也不能把“业务接受”和“独立正确”合为成功。**

本轮已经在多个实验中维护了这些区别，下一步要把它们变成统一接口，而不是每份脚本各写一套总结逻辑。:chatgpt-content-reference{index="17"} :chatgpt-content-reference{index="18"}

# 八、建议的下一轮实验方案

建议分两阶段，不一次同时扩张所有功能。

## 阶段 A：评价边界与工作人员运行

### R0：错误交付不会破坏评价过程

通过真实工具提交正常核对、结构完整但业务错误的核对、目标对象为 null、行元素为 null 等有限条件。

分别验证结构失败、业务失败和评价运行故障的表达，保留原文件、来源与提交。再加入一个明确的评价器内部异常负对照，确保它不会被错误包装成“工作人员数值算错”。

### R1：现有程序策略经统一运行模块仍保持语义

把现有两类工作人员接入新运行模块，覆盖：

**正确首交、两项问题分次修复、错误意见的有据反驳。**

与原有受控驱动比较的是实际来源、提交、问题—回应—决定关系、结果和历史保持，而不是强制要求动作数量与日志形状完全相同。

相等性之外仍需独立真值，避免两个运行方式共同犯错也通过。

---

## 阶段 B：角色协作与场景编排

### R2：工作人员独立运行，而非由主脚本传递答案

作者和审阅者分别从各自公开端口观察、行动。运行模块只提供行动机会，不在主程序里预填 findings 或修复后的正文。

重点检查：

| 情境 | 预期 |
|---|---|
| 正确交付 | 可以直接接受，不强制返工 |
| 两项独立缺陷 | 处理第一项不会关闭第二项 |
| 旧回复或旧意见晚到 | 保留历史，不影响无关当前义务 |
| 一名工作人员暂时等待 | 另一名工作人员仍可推进自己的合法工作 |
| 规则策略采取不合适行动 | 留下真实拒绝或错误后果，不由运行器代修 |
| 私有资料或独立评价答案 | 不进入无权角色的输入 |

可以先使用规则策略和明确标记的故障策略，不需要立即消耗模型预算。

### R3：同一场景由规格构建，而不是靠专用脚本补状态

将两个现有模板分别配置为独立场景，再配置一个跨模板联动场景。

首先验证相同规格能够形成一致的初始业务状态；再一次只改变一个明确维度，例如资料从直接可见改为需要合法请求，或更正从提交前改为待审期间到达。

**不要求不同条件产生相同轨迹，而要求它们分别产生合同规定的工作后果。**

无法构建的情境要报告缺失条件或不可达原因，不能自动替换为更容易的情境。由构造直接形成的背景历史，要与工作人员真实执行的前缀分开记录。

### R4：统一经历与分项评价可核对

独立捕获公开端口返回，与工作人员保存的经历逐项核对。对同一固定提交重复评价，应得到一致结果，且不改变世界业务事实。

特别检查：

**上游错误而下游忠实、metadata 正确而正文错误、合理未知、评价器自身异常。**

Episode 结束也不能清空世界和其他项目；否则新运行模块会重新把项目、世界与实验生命周期混在一起。

## 可选后续：一个角色的固定模型接口试跑

上述模块稳定后，可以另行冻结预算，只把一个执行角色换成固定推理模型，其他角色、场景与评价保持不变。

它首先回答：

> **非专用程序是否能够通过这套公开界面工作？**

不是立即测排行榜、训练收益或普遍泛化。失败后不能由规则策略补齐并计作模型成功，预录响应也不能冒称真实模型运行。本轮不因这份建议自动启动 API 或 GPU 实验。

# 九、哪些问题应反馈到内核

新增模块暴露问题后，仍应先判断所属层，而不是所有问题都继续进入内核。

| 发现的问题 | 优先改进位置 |
|---|---|
| 场景缺少必要资料或事件配置矛盾 | 场景构建与项目配置 |
| 工作人员不知道如何处理，但工具和规则已足够 | 策略或公开说明 |
| 文件定位、读取或编辑能力不足 | 应用适配层 |
| 财务定义、正文要求或判据不准确 | 领域合同与评价 |
| 相同事件在不同角色下产生不一致的授权、义务或历史 | 世界内核 |

下一阶段可能确实需要内核补充更统一的待办查询、可见事件或通知关系；但应由具体运行反例驱动，而不是先建设一个复杂的通用调度系统。

**真实金融工作流材料仍是后续校准支撑。**它们可以检验资料如何组织、角色如何交接、哪些变化引起返工；未观察的审批和时序继续保持未知或明确合成。不设置采集数量门槛，也不把历史轨迹强制为唯一合法路径。:chatgpt-content-reference{index="19"}

## 最终推进判断

**本轮已经证明：两个真正不同的有限工作结构，可以使用同一套世界规则并形成跨项目后果。这个成果足以支持开始建设其他模块。**

建议近期顺序为：

\[
\boxed{
\text{局部评价补修}
\rightarrow
\text{统一工作人员运行}
\rightarrow
\text{声明式场景编排}
\rightarrow
\text{统一经历与分项评价}
}
\]

保留现有两个模板作为集成负载，不急于新增行业、开放专业文本评价或启动训练。

**下一轮最重要的成果，不是又增加多少条规则，而是让“场景、工作人员、世界与评价”各自承担清楚的职责，并在不依赖专用实验脚本填入正确步骤的情况下，完整运行起来。**这样，ProWorkSim 才会从可靠的模板实验集合，进一步形成可扩展的模拟工作世界平台。
