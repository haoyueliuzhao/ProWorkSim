## 审计结论

**v0.15 可以保留为“真实来源已进入可执行世界、候选模型开始通过修正后的原生接口承担工作”的阶段基线。**但本轮仍是阶段快照：**三模型筛选尚未完成，主训练模型尚未选定，N0／N1和软件模型评价尚无已完成结果。**不能将已部署的自动执行图当作实验已经执行，也不能据9B的一条成功就完成模型选型。

# 二、真实来源接入：这次有实质进展，但仍是有界工作子集

## 1. UCI不是简单替换了数据名称

本轮保留了实际发票、数量、时间、单价、客户及取消编码，并使用真实 SQL 执行与独立 Decimal 验收。设计中明确区分订单与明细行、销售与净额、日期边界，以及原始来源和新增模拟政策。这比继续扩展原来的 `completed/pending`、金额倍数构造，更接近真实数据工作。

| 扫描541,909行 | 原始资料普查范围 |

**29个API输入不是完整兼容性证明。**它们支撑当前新需求的有限验收，不证明任意修改、任意输入或完整上游测试都正确。无需因此无限扩大本轮安全审计，但也不能扩大结论。

# 三、EOS事件说明：数值准入、正确运行与业务能力必须分开

## 1. 旧9B条件退出排名是正确处理

旧9B在 `im_end` 之后继续生成，造成虚构后续对话。这个条件测到的不是正常聊天协议下的工作能力。保留原输出、评分与成本，同时将整个错误条件退出能力排名，比裁尾重判或保留其中“看起来正确”的片段更合理。

这也揭示了一个重要经验：

> **生成概率可以准确复算，梯度可以真实产生，但被复算和训练的仍可能是一段错误协议下的行为。**

因此，S0不能只覆盖概率、反向和重载；模型原生的停止、角色消息边界和工具调用结构同样属于运行合同。

## 2. 修订发生在正确的位置

`candidate_runtime_v0151.py` 确实在真实生成器配置中设置双EOS，核对tokenizer与聊天模板，并保留原始输出及概率；检查并非仅在解析器中截断文字。

本次8项函数控制确认了：合法末尾EOS可以通过；EOS后继续、裁剪输出、篡改概率、长度不对应等情况不能伪装成正常校准。

不过，**三条短输出的通过仍然只是有限准入**。它不能替代计划大小窗口、更新后权重、较长工具交互和多卡反向的实际检查。没有观察到EOS的长度截断，也应按明确运行合同记录，不能一概解释为模型能力失败或基础设施故障。

## 3. 新架构的LoRA范围需要单独解释

本轮只在full-attention的q/v上放置LoRA，DeltaNet保持冻结，源码对此有实际模块数量检查。这个选择可以作为当前可控起点，但它并不等于“整个混合模型都在学习”，也不保证与旧架构相同rank具有相同适配容量。

后续应保存实际可训练模块与参数量。**暂时不建议同时扩大LoRA范围、换harness、改奖励、改精度**；否则即使取得改善，也很难定位原因。先选定能工作的组合，再针对明确瓶颈研究适配范围。

## 1. 现在还不能排名

归档快照中的状态是：

| 候选 | 已闭合、评分已知 | 完整责任成果 | 可以作出的判断 |
|---|---:|---:|---|
| 旧7B | 36／36 | 0 | 当前协议下仍主要取得读取与交接成果 |
| 修订后9B | 10／36 | 已观察1例 | 已出现真实完整实例，但不足以估计全批表现 |
| 27B | 0／36 | 未测量 | 不能计为失败或零能力 |

9B已经出现正确构建与固定提交，这比单纯工具调用成功更有意义；但已完成部分并非完整、平衡的任务样本，不能据此声称总体优于其他候选。

## 2. 选择器实现的是相对排序，不是“已经具备足够能力”的门槛

源码按完整实现＋复核数、完整双／三成员成果、分配设备秒排序，并将训练准入与业务分数分开。未完成条件不会被填成零，历史7B也不会自动成为新主模型。这个处理符合本轮声明。

本次用一个**完全人工的全零业务结果夹具**执行选择函数：当两个新候选均具有训练准入时，它仍会选取成本较低者并返回 `selected`。

**这不是新漏洞，也不表示现实候选已经全零。**它说明：

\[
\boxed{\text{相对最优候选}\neq\text{基础工作能力已充分建立}}
\]

不要在看到部分结果后追加回溯通过率门槛；但最终选择记录应同时保留**各岗位表现、跨事实重复性和仍未解决的短板**，不能只展示一个模型名称。

自动化是在部分开发结果可见后加入的，也应继续如实记录。指标和样本不变可以支持机械执行，却不能将所有后来补齐的细节都追认成完全事前注册。

## 3. 模型排名是依赖harness的

本轮实际比较的是：

\[
\widehat U_{\mathrm{dev}}(\theta_m,\Gamma_0),
\]

即候选模型在当前原生适配、工具呈现和工作循环下的结果。

换成新的工作harness \(\Gamma_H\) 后，表现和排序都可能改变。**因此，本轮筛选仍有价值，但得到的是当前运行系统下的初始化选择，不是裸模型的永久能力排名。**

V1本来就将harness纳入固定运行协议。开发阶段可以改进它；正式经验配置比较时，则不能让不同方法拥有不同的隐藏规划、记忆和工具支持。:chatgpt-content-reference{index="12"}

# 六、下一步最值得新增的，不是更多队列机制，而是实际可用的工作人员harness

## 1. 优先接入OpenHands SDK，保留现有世界和训练器

延续刚才的调研，我建议首个原型使用 **OpenHands Software Agent SDK** 的会话、事件和类型化工具；mini-SWE-agent保留为轻量对照或备选。暂不同时迁入多个完整编排层，也不同时更换Agent Lightning／rLLM训练后端。

OpenHands官方将Agent、Conversation、LLM、工具和Workspace分开，自定义工具具有Action、Observation和Executor接口，适合包装现有世界命令。:chatgpt-content-reference{index="15"}

但一个关键限制仍然是：**工具并不通过Workspace API执行。**只替换Workspace不能保证所有文件和终端操作都受WorldCore控制，必须接管对应执行器。:chatgpt-content-reference{index="16"}

建议先完成三个明确接点：

| 接点 | 近期实现目标 |
|---|---|
| **工作人员适配器** | 每个角色独立Conversation；一次模型决策后能够交还调度权，接收真实结果再继续 |
| **世界工具网关** | 读取、查询、编辑、构建、消息、提交仍由WorldCore或现有受管执行器产生后果 |
| **模型记录适配器** | 在实际调用边界保存原始token、停止、概率、角色和权重身份，可继续使用resident_direct |

这里的名称是建议接口，不是声称上游已经提供了ProWorkSim专用类。

**模型升级和harness完善应当相互配合，但不应同时暗中改变世界规则。**程序可以自动维护调用ID、哈希和实际执行谱系；选择业务依据、修改逻辑和作出复核判断仍由模型承担。

## 2. 第一版只提供必要支持，不增加隐形解题系统

建议优先提供：

**清楚的职责与待办、可检索的局部历史、角色私有工作笔记、固定提交浏览、方便的实际编辑，以及真实错误反馈。**

暂不引入后台强模型规划、自动选择正确来源、自动修补SQL、隐藏评价器反馈、默认子代理共享记忆或成功重采。

尤其要保留：

**角色笔记不是正式世界事实；能够访问的资料不等于已经查询；已读过的资料也不等于仍在本次模型输入中。**

这与既定的信息不对称和成员局部投影要求一致。:chatgpt-content-reference{index="17"}

## 3. 不要因开源框架默认工具而退化软件隔离

当前软件任务使用真实的 `read_source/search_source/replace_source/run_tests`，编辑由可信世界执行，测试代码进入受限进程。这条边界已经形成，首版SDK适配可以直接封装它，不必立即开放通用Bash。

mini的本地执行同样不能直接当作隔离环境；其环境后端需要与我们的权限和工作空间规则一起配置。:chatgpt-content-reference{index="19"}

**先让成熟harness使用现有真实工具，后续有明确需要时再扩展执行能力。**这样避免为了复用框架，反而绕过已经建立的版本、来源和安全边界。

# 七、建议的新实验：先做harness比较，再冻结在线学习组合

## H0：薄适配验收

在独立开发树固定上游版本，验证真实SDK会话、事件与执行器确实被调用，而不是只借用框架名称、实际仍运行手写替身。

必要检查限定为：角色权限与记忆不混合；一个角色暂停不取消其他角色；模型输出与实际动作对应；文件修改进入世界版本；停止与token记录保持；参数刷新后不继续使用旧缓存。

然后进行少量真实模型交互，覆盖读取、实际编辑、错误反馈后的继续执行。**这一阶段验证兼容性，不重新宣称“在线学习闭环首次成立”，也不要求移植框架全部功能。**

## H1：小型“模型×harness”开发比较

建议只比较两套harness：

**H0：当前有效原生接口；H1：SDK工作harness。**

等原S1完成后，再按明确规则确定两个可用候选。一个有界示例是：

\[
2\text{ 模型}
\times2\text{ harness}
\times6\text{ 新开发情境}
\times2\text{ 次运行}
=48\text{ 个episode}.
\]

六个情境可包含实现2、复核2、双成员1、三成员1。**这是方案示例，不是已冻结预算或统计功效保证。**若只有一个候选可用，就明确收缩为24例单模型harness诊断，而不是维持“双模型比较”的结论。

比较要保持相同业务目标、权限、工具效果、工作起点和合理预算。模型采用各自原生模板；如果harness同时加入多个支持功能，先报告组合效果，不将全部改善归因于某一项记忆或计划功能。

主要指标应是：

**完整责任、依据的实际使用、正确修改、有据复核、具体错误恢复和总成本。**

不只看格式正确率、工具ok或平均R。新情境使用开发用途的事实，不动软件锁定任务；原S1的部分成功也不能充当新harness组的结果。

## H2：固定组合后，继续直接在线RL

确定 \((\theta_0,\Gamma_H)\) 后，暂时保留现有learner和critic，不同时迁移训练框架、扩大LoRA、改奖励和数值精度。

在线过程仍然是：

\[
\theta_t\text{ 实际工作}
\rightarrow
\text{真实经历与后果}
\rightarrow
\text{共享参数更新}
\rightarrow
\theta_{t+1}\text{ 重新工作}.
\]

harness产生的额外调用、笔记、摘要或检索，都要记录真实输入输出与成本。不能把整理后的文本重新分词，冒充当时模型实际生成的token；也不能把同事消息算作接收者自己的生成目标。:chatgpt-content-reference{index="20"}

如果原N1已在旧harness完成，它是 \(\Gamma_0\) 下的独立实验；新harness不能拼接进它的四个窗口。下一轮应明确区分：

\[
\underbrace{U(\theta_0,\Gamma_H)-U(\theta_0,\Gamma_0)}_{\text{harness组合效果}}
\]

与

\[
\underbrace{U(\theta_T,\Gamma_H)-U(\theta_0,\Gamma_H)}_{\text{固定harness下的学习效果}}.
\]

前者不等于参数学习，后者也还不等于ID‑VTDO增量。

# 八、真实多项目与泛化，应同步推进但不成为新的无限前置条件

## 1. 下一次世界扩展应补“项目关系”，不只是增加更多单项目实例

当前UCI已经能够承载实际实现与复核，接下来可以复用现有资产形成：

| 项目 | 工作作用 |
|---|---|
| **P0：资料核对与发布** | 发布实际数据、字段说明和未解决项 |
| **P1：指标实现** | 编写、执行并发布指标接口 |
| **P2：客户分析** | 与P1并行，对期间和粒度提出实际约束 |
| **P3：集成复核** | 消费P1/P2真实成果，核对一致性并形成交付 |

先提供可用共同合同，让P1/P2能够启动；反馈通过后续版本发生，避免首次完成互相等待。环境负责声明的发布、授权和义务后果，不能替下游生成正确成果。

这项扩展可以先用有限程序见证检查可行性，再让共享模型实际接手；**不要求四项目全部自主成功之后才允许已有工作片段继续训练。**

## 2. 不要让harness开发污染软件迁移评价

Marshmallow目前是一个未用于参数更新或模型选型的软件来源，但仍只有一个需求、每节点三次运行。它适合做**窄范围迁移探针**，不能承担“广泛软件能力迁移”的结论。

如果后续根据这个任务的模型错误调整技能、提示或自动修复，它就参与了开发。应另建新的锁定需求或来源，而不是继续沿用“未参与优化”的描述。

UCI的客户隔离测试同样只是同源泛化。新harness的文件索引、搜索、记忆和检索范围也必须遵守划分，不能让训练角色通过通用文件工具读取全部原始XLSX或锁定资产。

# 九、ID‑VTDO如何接入：支持统计随在线训练发生，不另建成功轨迹工程

更好的模型和harness可能让有效实现、复核与协作开始出现，但**不能据此预设两类有效方法一定充足**。

每个窗口仍需固定 \((\theta,\Gamma,\xi)\)，分别统计成员动作、有效性、类别、类内数量和 \(b_i\)。harness升级后，旧轨迹不能不加区分地并入新支持池；自动检索或自动交接也不能被误标成模型自主选择的方法。:chatgpt-content-reference{index="22"}

没有支持或只有单类时，基础RL继续按原规则处理。有可用支持时，才在在线窗口内进行共同起点的配置试训、开发世界执行和正式更新。

**现在不应为了尽快运行O4而放宽有效性、跨情境合并或强制补出方法。**也不应把harness增加的能力、换模型的收益或更多计算预算，统称为经验配置收益。V1要求的是同一基础配方下，\(Q=B\)恢复基线，失败保留，配置只改变现有合格分支的训练组成。:chatgpt-content-reference{index="23"}

## 最终推进建议

**本轮值得保留的突破，是从构造素材转向真实来源，并开始认真区分“模型会不会工作”和“运行系统有没有正确使用模型”。**EOS反例正说明了后一项的重要性。

近期优先顺序建议为：

\[
\boxed{
\text{闭合当前有效筛选／准确保留未完成项}
\quad+\quad
\text{独立开发可复用harness}
}
\]

随后：

\[
\boxed{
\text{选定模型—harness组合}
\rightarrow
\text{直接在线学习与冻结评价}
\rightarrow
\text{真实多项目和新来源迁移}
\rightarrow
\text{有支持的ID‑VTDO比较}
}
\]

**不要在运行中不断更换基础设施，也不要因为已经部署了自动执行图就把它当作最终研究路线。**原实验按原合同保留，新设计独立冻结。

下一轮最有价值的成果，应当是：**一个具备基础能力的共享模型，借助必要且可解释的工作harness，在真实来源支撑的世界中完成实现、复核和协作；训练后的变化能够与模型升级、harness增强及环境修订分别归因。**这比再增加一批队列检查或重复失败，更直接地服务于我们的算法问题。
