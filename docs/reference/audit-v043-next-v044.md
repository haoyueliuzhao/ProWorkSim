# 二、最重要的源码发现：普通格式反馈没有退出当前上下文的机制

## 1. 它为什么会长期留下

冻结代码中的链路是：

**第一步，产生格式错误反馈。**  
`_format_rejection`将来源ID、hash、错误计数、限额说明、解析诊断和纠错合同包装为`public_format_feedback`，通过单独的user消息加入会话。

**第二步，选择SDK历史。**  
`select_context`只识别登记在`_observation_texts`中的正式观察，并删除较早观察和较旧工具回合。其他user消息被保守保留，因此上述格式反馈不受“四回合历史”限制。

**第三步，执行容量投影。**  
`protected_software_request`再删除可移除的旧assistant/tool对，但保留全部system/user及最新工具对，格式反馈仍在其中。

而模型后来合法执行时，只将连续错误计数归零，没有使旧错误消息退出工作上下文。

**因此，当前实现实际上把“错误必须留档”变成了“旧错误正文必须长期占用模型输入”。**这两者没有必要绑定。

## 2. 不能把它简单修成“删除所有旧错误”

本轮四个硬拒绝的超额分别为：

| 前缀 | prompt | 超出14,336硬界 |
|---|---:|---:|
| SB／member_002 | 14,484 | 148 |
| SB／member_001 | 14,583 | 247 |
| ST／member_001 | 14,605 | 269 |
| ST／member_002 | 14,461 | 125 |

它们都同时含有测试首页和格式反馈。三个被挡测试首页对应的旧格式反馈此前已经呈现；但**SB／member_001是在看过测试首页后产生了新的格式错误，新错误还没进入下一次生成。**

所以需要两项相互配合的修订：

1. **历史普通错误不永久占用受保护上下文。**
2. **最新错误保留必要的纠错内容，但不重复携带整套审计元数据和通用说明。**

只做第一项，不一定解决SB／member_001；只做第二项而仍无限累计，也可能在更长工作中再次遇到相同问题。

这两项组成一个新的反馈呈现协议，不能宣称是对模型行为没有影响的“纯文字清理”。

# 三、建议v0.44明确区分：错误留档、当前纠错、业务恢复

## 1. 给普通格式反馈定义生命周期

建议采用下表所示规则，**仅适用于有明确运行器来源的普通格式／公开参数拒绝**。

| 状态 | 当前prompt怎样处理 |
|---|---|
| 最新拒绝尚未进入真实生成输入 | 保留当前纠错正文，不能为了fit直接删除 |
| 下一次生成仍出现新的格式错误 | 前一反馈已呈现后，由最新拒绝承担当前纠错位置；旧反馈标为被替代，不叫已修复 |
| 随后产生通过原生解析与公开schema的调用 | 旧普通格式反馈可以历史化，不再强制重复 |
| 合法格式调用被世界业务条件拒绝 | 旧语法问题可以历史化，新的业务拒绝仍完整保留 |
| 权限违规、身份异常或关键记录失真 | 不套用普通格式反馈清理规则 |
| 来源或呈现时序不清楚 | 不猜测、不删除，保留诊断 |

这里的“已呈现”必须有实际selected请求与真实生成记录，不能仅凭SDK调用了`send_message`。

**格式已经合法，不等于原业务问题已经解决。**例如模型把错误的调用语法改对后，可能仍选错文件或违反版本要求；后者继续由真实世界反馈体现。

也不能依据任意user文本恰好包含`public_format_feedback`字段就删除它。必须绑定运行器产生的事件、成员、原call和时序，防止误删用户要求或伙伴消息。

## 2. 最新反馈要可操作，但不需要重复整份账本

建议将实际给模型看的最新普通格式反馈限定为：

| 应继续给模型 | 可保留在完整审计记录、不反复铺入prompt |
|---|---|
| 对应调用、拒绝状态、没有执行动作 | 原响应完整hash等重复审计字段 |
| 真实native与adapter错误阶段 | 重复版本标签、重复来源描述 |
| 原主要reason | 每次重复的整段通用格式合同 |
| 已知的字段位置、缺失项、预期／实际类型 | 未启用的旧格式退休门说明 |
| 有证据的解析位置 | 与当前纠错无关的冗余结构 |

原诊断模块已经把native失败与后续adapter失败分开，并只描述公开语法和schema；下一版应保留这些纠错依据，不能用最后一个JSON错误覆盖真正的原生解析错误。

**不自动改工具名、不补recipient、不生成正确参数或代码、不免费重试。**模型仍需在下一次真实机会自行纠正，旧错误输出和费用完整留存。

这种投影会改变模型看到的格式诊断内容，应明确登记为新Γ；不能因为原件还在，就说可见信息毫无变化。V1.3本来就区分了完整归档与实际输入。ID_VTDO_理论基线_自主组织完整修订稿_V1.3_202…

## 3. 测试反馈和初始信息暂不一起改

## 最终推进判断

**本轮不应再回退为“分页还不能被模型使用”，也不能前进到“分散信息改善了协作”。**实际情况是：部分反馈已经可达并支持个人交付；普通错误反馈的长期保留又在shared条件中挤占了下一次行动空间。

下一步应当修复这个已定位的机制，而不是扩大整个平台：

> **错误需要完整留档，但不必永久占据工作上下文；最新错误必须让模型有机会理解和纠正，旧错误则应有明确的历史化规则。**

只要这一有限执行条件建立，就应收口接口修订，回到真实任务组织与协作使用的观察。最终研究价值仍取决于这些经历将来能否被更有效地学习，而不是提示更短、页面更多或CPU检查再次全绿。
