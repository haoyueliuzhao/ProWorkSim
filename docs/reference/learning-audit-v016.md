## 审计结论

**v0.16 可以保留为“真实 SDK 工作人员已接入受管世界”的阶段基线。下一步应当完成已规划的 H1 比较，并将选定的模型—harness 组合接入直接在线训练，不需要再以增加框架功能或重复 H0 冒烟作为主要目标。**

# 二、对本轮主要成果的判断

## 1. SDK 接入是真实复用，不是只借用了框架名称

源码确实构造了独立 Conversation、Agent、类型化 Action／Observation 和自定义 Executor。执行器检查类型化参数是否改变了原始参数，再调用受管网关；得到观察后暂停，交回原来的角色调度。默认终端、编辑器、MCP、子代理和生成式摘要没有被隐式启用。

这符合我们之前确定的分层：

> **SDK 管会话和工具交互，WorldCore 管事实与行动后果，模型作出工作决策。**

不过，当前新工具、历史检索和四回合上下文策略主要由本项目适配层定义。因此，H1 即使取得改善，也首先支持**这一受管 SDK 组合**，不是证明完整 OpenHands 产品、某个上游默认规划器或某一项记忆机制有效。

## 2. H0 三例应继续按不同性质解释

| 片段 | 本轮实际证明了什么 | 没有证明什么 |
|---|---|---|
| **公开接口校准** | 模型能经过 SDK 接收错误、读取、显式编辑、写笔记和结束 | 自主完成业务；它本来就有公开指定步骤 |
| **真实实现** | 取得确切输入并完成正确实际构建 | 完整交付；没有固定提交 |
| **双成员工作** | 两名模型工作人员实际独立行动，拒绝和反馈被保存 | 有效交接与协作；provider没有发送依据 |

所以，既不应把三例合成“完整工作成功率0%”，也不能把实现例的 \(R=0.5\) 称为任务成功。**它是有价值的中间成果：模型已经做对计算，但没有完成责任闭环。**

双成员记录也已将一个具体解释排除：18次输出均可解析，8次拒绝都出现在同角色下一次实际输入中。provider始终拥有 `handoff_information`，却没有调用；implementer持续请求或读取尚未共享的依据。**这份轨迹不支持“最新错误被上下文处理丢掉了”，也不能被概括成“模型不会 SQL”——它尚未进入实现阶段。**

## 3. 四项目见证成立，但还差正式效用与真实模型执行

四项目确实建立了共同合同、并行可启动的 P1/P2、实际下游消费和后续版本影响。混合新指标与旧分析时，实际结果产生差异，之后通过显式更新恢复；世界没有自动重写下游产物。

这已经足以作为后续模型实验的环境基础。但应保留两个限定：

**第一，当前是程序安排的可行路径，不是模型自主协调。**

**第二，P2/P3 的独立核验仍在报告中，尚未形成可供训练稳定使用的正式奖励接口。**

此外，初版成果发布和集成后发生变更、终版才固定提交，不能扩大为已经验证了长期运行中任意已验收项目的维护。

# 三、需要澄清的三处问题

## 1. SDK 错误标记修复合理，但不能据此解释 H0 失败

H0 的 `GatewayObservation` 没有设置 `is_error`，导致它沿用默认 false；不过原始 `ok:false` JSON仍然传给模型，世界也没有把拒绝改为成功。后继 v0.16.1 修订的是 SDK 事件表达，不是原业务结果。

建议按已有做法保留 H0，不重跑、不回写，将修订绑定到新 H1 协议即可。

这里应形成三个独立判断：

| 层次 | 问题 |
|---|---|
| **标记一致性** | SDK 是否把世界拒绝标成错误？ |
| **内容传递** | 原错误内容是否进入实际模型输入？ |
| **反馈利用** | 模型是否理解并针对同一义务作出修正？ |

前两项成立，不保证第三项成立。

## 2. “harness 不替模型选来源”，不应写成“模型不能自主选来源”

SDK 默认 SYSTEM 中包含：

> `Never … choose sources automatically …`

而原生 ModelPolicy 的说明是使用公开要求与证据。这一表述存在语义歧义：**原本应限制后台自动补选的规则，被写进了对工作人员的指令。**

我们的研究恰恰需要模型自主判断：该查询什么、选择哪个合法依据、是否请求确认、怎样交接。合理的模型侧说明应接近：

> **根据当前公开合同和你实际取得的信息，自主选择允许使用的来源；缺少信息时检索或沟通，不臆造依据。**

禁止 harness 自动补选，则继续由执行器和信息边界保证。

**这不是已证实的 H0 失败原因，也不证明模型将原句理解为禁止所有选择。**但在 H1 尚未执行时，值得明确这条语义。若采纳修订，应显式登记新的提示与 \(\Gamma\)，而非把它当作无行为影响的文字勘误；两臂仍应具有相同的业务自主权。

## 3. 格式反馈已经送达，但可能没有暴露最有用的诊断

实现例的原生解析记录是：

`Native parameter does not match public JSON type`

SDK公开反馈记录的却是后续 JSON 解析错误：

`Expecting value: line 1 column 1 (char 0)`。

原始诊断没有从档案中消失，但**“档案里有具体原因”与“模型收到可操作的具体原因”仍然不同**。

建议后续保留结构化的两级解析结果：哪个解析器拒绝、违反哪项公开 schema、已知的字段位置和类型。没有定位依据时就保持未知，不猜字段，更不能返回正确业务参数或参考 SQL。

这项改进也不能解释 pair 的失败，因为 pair 没有格式错误。若要修改反馈，应在新协议中固定，不在 H1 运行过程中临时加强某一组。

# 四、当前四回合上下文策略，应作为待比较的工作机制，而不是默认最优设置

源码与本次10项控制一致：当前选择器保留最新观察、最近四个完整工具配对，并保守保留格式反馈；更早的观察和工具回合会退出实际输入。

这套策略是明确、可追溯的，但存在真实取舍：

**它减少重复输入，也可能移除之后仍然需要的依据；历史检索可以找回，但需要模型主动意识到缺口并消耗机会。**

因此，完整归档、当前输入和可检索历史必须继续分开。不能说“资料还在日志中，所以模型不会忘记”，也不能在没有实际请求证据时将失败归因于遗忘。

H1 中 SDK 新增的 note、todo、检索和编辑同样占用角色机会。这不是天然不公平，但意味着 H1 的问题是：

> **在固定工作预算下，这套辅助工具与上下文组织的整体收益，是否超过其使用成本？**

不是“给 SDK 不限次数，它最终能不能做完”。不要在看到结果后给 SDK 免费检索或额外机会，也不要将组合差异单独归因为记忆、规划或 SDK 引擎。

# 五、下一步首先完成 H1，但要把测量对象写清楚

## 1. 保留48例，不再扩大成新的框架筛选工程

当前计划：

\[
2\text{ 模型}\times2\text{ harness}\times6\text{ 情境}\times2\text{ 重复}
=48\text{ 个 episode}
\]

可以继续作为有限开发比较。原 S1 收口、真实模型身份和 H0兼容审阅按现有合同处理；**不自动把尚未完成的候选改成不可用，也不要求 H0 先取得完整业务成功才允许 H1。**

每个模型内部比较：

\[
\Delta_m=
\operatorname{mean}_{\xi,r}
\left[
U(\theta_m,\Gamma_{\mathrm{SDK}};\xi,r)
-
U(\theta_m,\Gamma_{\mathrm{native}};\xi,r)
\right].
\]

初始权重相同，工作目标和世界合同相同，但模型真实行动、后续输入和工具结果可以不同。相同 sampling seed 不等于逐字配对。

## 2. 主要分母是六个开发情境，不是48个独立项目

每个模型、每种 harness 实际只有12例：

| 任务 | 每臂、每模型的运行数 |
|---|---:|
| 实现 | 4 |
| 复核 | 4 |
| pair | 2 |
| chain | 2 |

这适合观察候选差异和工作断点，不适合凭小幅均分变化宣布普遍优越性。

还有一个容易忽略的口径：**H1 的实现、复核各占1/3，pair、chain各占1/6；原 S1 四类等份额。不能直接用 H1 均分减 S1 均分，声称能力提升。**若另报任务宏平均，应提前声明权重。

native→SDK→SDK→native 的顺序可以平衡部分时间影响，但不构成所有运行噪声已经消除的证明。H0使用过的情境继续保持 development 身份，不能称为完全未接触的锁定评价。

## 3. 在结果出来前，明确组合选择规则

建议优先看完整实现与有据复核，再看团队成果与成本；同时保留每个事实、重复和岗位的结果。

**不要预设必须选择 SDK。**如果 native 更可靠，就可以作为近期训练接口；如果 SDK 的收益不明确但成本更高，可以保留简单版本，同时继续利用它的工程组件。采用开源框架不是研究终点。

如果两套都只取得部分成果，则说明这个开发范围里的完整工作仍是短板。可以继续有界在线学习或定向诊断，但不能将“相对排名第一”解释成“基础能力已经充分”。

# 六、把失败诊断嵌入 H1 的只读分析，不再反复重跑 H0

下一轮最有价值的行为分析，是定位**工作在哪里断开**，而不是再统计更多工具成功次数。

| 观察问题 | 建议保存或提取的证据 |
|---|---|
| **正确构建为何没有转成交付？** | 首次正确 build 的机会位置、剩余预算、后续是否改坏或换版、是否尝试 submit、具体拒绝 |
| **提供者为何没有交接？** | 何时实际看见请求或义务、是否取得适用依据、可见供给能力、之后选择了什么 |
| **接收者是否根据反馈恢复？** | 原错误是否进入输入；是否针对同一义务修复；确切版本是否随后实际执行 |
| **工作辅助是否真的被利用？** | 笔记是否进入后续输入、旧依据是否通过历史查询找回、用了多少机会与 token |
| **完成与停止是否被混同？** | 正确构建、固定提交、独立复核、`staff_done`分别记录 |

例如，H0 实现例没有提交，可能与时间分配、接口理解、格式错误消耗或其他选择有关。**目前证据不足以直接说“模型忘记提交了”。**同样，provider有工具却未使用，不说明仅增加一个handoff工具描述就必然解决。

应先用原始记录定位。如果确有公开职责或参数说明不足，再设计一个小型开发对照。可以明确“你负责向哪个工作提供什么类型的依据”，但不要给出参考结果或固定动作清单；也不能由 harness 在正确 build 后自动提交。

# 七、H2 的重点：让工作辅助参与真实在线学习，而不是只留下更多日志

H1 选定 \((\theta_0,\Gamma)\) 后，可以继续共享模型直接在线训练。**不需要等整条团队链稳定成功、或两种有效方法都采齐，才允许基础 RL。**但也不能把 SDK 接通或日志完整直接当作学习准入已经完成。

## 1. 固定运行组合，避免同时改变所有变量

首版保持同一共享 actor／LoRA／优化器、独立 critic，以及明确的任务份额、奖励、数值配置和上下文策略。暂不同时扩大LoRA、迁移训练后端、增加隐藏规划模型。

MC／RTG若继续比较，作为两个基础配方另列。不要一次展开“两个模型×两个harness×两个信用方式×多个训练种子”，却没有预算完成评价。

旧 \(\Gamma_0\) 的 N0/N1 按原协议独立保留，不与新 SDK 窗口拼成一条学习曲线。

## 2. 私有笔记与检索，也是模型真正作出的行动

这是接入 harness 后新增的重要训练边界：

**`work_note`、`work_todo`、`work_history_search` 和 `work_history_read` 虽然不直接改变正式业务状态，却会影响后续输入。**如果它们是模型真实选择的动作，就不能仅因 `world_effect=false` 被静默从 actor 经历中删除。

相反，机械版本查询、系统上下文整理、工具结果和同事消息不是该成员生成的动作。一次 `work_replace_text` 同时产生 harness 记录和 world `write_object` 回执，**仍然只对应一次原始模型输出，不能重复计算训练目标。**源码已经分开了这两类执行记录，训练接入应保持这种区别。

这符合 V1：成员局部投影恢复实际输入和本人动作，共享参数不改变消息和动作的归属。:chatgpt-content-reference{index="16"}

## 3. 概率核验使用实际选择后的输入

SDK更新时必须使用模型当时真正看到的上下文，不能为了复算方便，把已被last4移出的历史重新拼回来。

需要完成一次有界的实际更新接入检查：当前窗口采样、原始概率与可微前向核对、共享更新、各角色使用新身份重新交互。**这是迁移验收，不必再包装成“在线闭环首次建立”。**

H2 主实验应当观察固定 harness 下的学习差：

\[
U(\theta_T,\Gamma)-U(\theta_0,\Gamma),
\]

而不是把更换 harness 得到的差异归入参数学习。

可以用四个窗口、每窗16例作为容量核定后的 pilot 起点，但这只是规模建议，不是学习充分性保证。独立评价额度需要同时冻结。若四次更新没有收益，就如实限定为该训练剂量和范围，而不是追加到某次成功才结束。

## 4. 仍然是在世界中直接学习

训练过程保持：

\[
\theta_t
\xrightarrow{\text{实际工作}}
\text{本窗口经历与后果}
\xrightarrow{\text{参数更新}}
\theta_{t+1}
\xrightarrow{\text{新的实际交互}}
\cdots
\]

H0/H1 的开发轨迹不应被悄悄改造成成功示范库。窗口内暂存材料是在线优化的中间量；更新后的策略必须实际产生新的工作行为与世界结果。这是 V1 的在线算法要求。:chatgpt-content-reference{index="17"}

# 八、四项目环境：下一步补正式评价，而不是再写一套求解器

建议与 H1 并行，将现有四项目报告中的 P2/P3 独立核验整理为固定提交上的评价合同。

最重要的一项负对照是：

> **P1和P2给出了相同但共同错误的数值，P3差额为零，仍然不能算整体正确。**

当前报告有独立 Decimal 对照，下一步应确保正式评价保留它，而不是只保留 P3 的一致性测试。

| 层次 | 应检查的对象 |
|---|---|
| **P1 指标质量** | 是否按本项目适用合同从真实数据计算 |
| **P2 分析质量** | 是否按其实际采用依据形成正确结果 |
| **P3 集成忠实性** | 是否真实消费双方固定版本，计算正确差异 |
| **整体业务目标** | 合同、版本、分支结果与交付是否共同成立 |

再加入混合版本、只改标签、结果缺真实构建、后续成果回填旧episode等有限对照即可。**不需要对所有可能错误穷举，也不能让模型反复调用隐藏评价器来取得答案。**

随后先让选定共享模型承担静态交付与一次明确变更，各做少量固定重复。程序只负责初始化、预声明事件和独立评价，不替模型补交接、SQL、采用或提交。

这一线可以与短责任在线学习并行：**四项目尚未全部自主成功，不应阻断已经可评的短任务训练；短任务有进步，也不能代替四项目能力证据。**

# 九、ID‑VTDO 与泛化如何衔接

## 1. H1不是方法支持普查，不必为了它扩大样本

H1每个模型—harness—精确情境总共只有两次，而且当前采集器分别登记窗口。若每类最低要求两条，要同时支持两类，最基本的必要数量就至少是四条；更不用说有效性与类别分布。**不能把 native 与 SDK、9B 与27B凑成一个支持池。**

这不影响 H1 做组合比较。方法支持应在后续当前策略的在线窗口中统计：实际 \(V\)、成员动作、类别频数、\(v_i\) 与 \(b_i\)，没有支持或只有单类时继续基础处理。:chatgpt-content-reference{index="19"}

同时，模型写了不同笔记、改变了措辞，不自动形成新方法；机械编辑的内部子步骤，也不能冒充成员自主交接。

有支持以后，Contribution仍然要通过共同学习起点上的配置试训，以及训练后开发世界中的实际团队效用来估计。**它不是H1中的harness效果，也不是工具成功率或某组梯度。**

## 2. 新客户是开发扩展，不是新来源泛化

12个客户与旧素材实体互斥，是有价值的隔离；但仍属于同一个 UCI 来源和同类合同。H0又已用于适配开发，H1只能承担开发比较。

后续应保持：

**harness选型开发池、在线策略训练池、贡献开发池、锁定测试用途清楚；检索索引与私有记忆遵守同样边界。**

Marshmallow的原锁定需求不能被用于不断调整业务技能或提示后，继续宣称未参与优化。纯接口连接测试可以使用另外的机械夹具。

主要泛化评价固定 harness、冻结模型参数，分别检验单岗位接手和同模型多实例团队；更换另一套功能充分的harness可以作为辅助稳健性检查，而不是删掉必要工具制造失败。

# 十、资源与下一阶段的收口标准

本次按报告复算，H0为 **33次生成、255,944个总token**，输入占约97.52%；显存采样峰约71.76 GiB。**这些都不是新harness更省或训练资源足够的证据。**没有native对照，且当前峰值来自推理，不包含实际反向的新增开销。

不建议按三个H0片段的平均时间，直接外推27B、48例H1或多窗口H2。应按实际角色机会、输入长度、设备分配、辅助操作和训练前向分别核定。

下一阶段建议只围绕三个成果收口：

1. **完成H1的有限比较，或对未完成项给出明确原因；不再停留于SDK接线证明。**
2. **固定一个模型—harness组合，完成有界直接在线学习和独立工作评价。**
3. **将四项目独立效用正式化，并获得少量共享模型自主执行记录。**

来源、框架、恢复和日志都服务于这三个目标，不再单独扩张成不断增长的验收工程。

## 最终推进判断

**本轮已经回答了“能否把真实SDK接入世界”，下一轮应回答“这套支持是否使模型更能完成工作，以及固定它以后能否学得更好”。**

建议顺序为：

\[
\boxed{
\text{闭合H1、明确运行组合}
\rightarrow
\text{共享模型直接在线学习}
\rightarrow
\text{四项目与新来源评价}
\rightarrow
\text{有真实支持的ID‑VTDO干预}
}
\]

**SDK不是新的研究终点，也不应成为必须胜出的候选。我们最终需要的是一个能够依靠当前证据完成实现、复核和协作的共享模型，以及一套帮助它工作、但不替它完成工作的可移植 harness。**
