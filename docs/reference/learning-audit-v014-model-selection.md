**v0.14 应当保留为“工作学习诊断与时间信用机制得到验证、数值失效获得有界解释”的阶段结果；预定学习对照仍然未完成，不能给 MC 与 RTG 排优劣。**六个正式运行都在概率一致性门停止，训练后的开发与锁定评价没有执行，因此这里不是“测得零收益”，而是**缺少原计划要求的收益测量**。

> **一条线用已修订的数值配置，完成规模较小但闭合的在线学习比较；另一条线把真实公开数据与代码接入现有世界，让训练不再长期局限于同一个构造 SQL 家族。**

# 二、对本轮实验的核心判断

## 1. 原六运行的停止处理正确，但原学习比较应正式标为未完成

主要分母核对一致：

| 对象 | 数量与解释 |
|---|---|
| 原计划 | 744 个槽 |
| 已闭合训练 | 144 个 episode |
| 已闭合评价 | 120 个，均为已执行的初始评价 |
| 未启动 | 480 个，不能记为零奖励 |
| 原正式 actor／critic 更新 | 各3次 |
| 全轮更新，含两个容量实验 | 各5次，不能全部归入正式比较 |

训练源码在行为概率门失败时直接返回，位置在实际反向与优化器更新之前，与报告中“失败窗口零新增 step”的解释相符。先前已经成功的更新继续保留，不能因后续停止而抹去。

因此应同时保留两个结论：

**在线训练不是没有发生；但预定长度的学习过程及其训练后评价没有完成。**

也没有必要为了补满原来的744槽继续旧运行。新数值配置应当对应**新的实验身份、起点、预算和停止规则**，而不是修补一份表面完整的旧结果。

## 2. MC／RTG 实现对准了原问题，但“去掉错误信用”不等于“产生有效学习”

源码中的区别是明确的：

\[
G_d^{\mathrm{MC}}=R,\qquad
G_d^{\mathrm{RTG}}=\sum_{k:\,s_k\ge s_d}r_k,
\]

其中 \(s_d\) 是实际决策开始的联合事件位置。账本只将可在发生时确认的读取、实际送达提前结算，其余依赖终态的成果在终点结算，并用补差保持原终局合同。

例如，整链只有交接获得0.2、后续没有成果时，RTG 可以使交接之后的动作不再获得那笔过去奖励；如果后来完成了新的交付，它仍应获得相应未来回报。若此前成果最终失效，负的终点补差也必须保留。

本次局部检查支持这套有限算术。报告中的真实梯度记录进一步支持：**候选确实移除了所测后送达阶段的过去交接信用。**

但是：

> **把后续错误动作从正优势变成零优势，只是去掉了一种不恰当强化，不代表模型已经知道正确 SQL、正确采用或正确复核该怎么做。**

本轮 RTG 的后送达零梯度，与“RTG 改善工作”之间还缺少真正的学习结果。不同轨迹、不同停止位置以及只在成功通过数值门的窗口上测到的梯度，也限制了比较。

此外，当前损失按成员自身输出 token 平均。**账本总和相同，不足以证明两套实际 surrogate 严格无偏等价。**代码已经保留这个限定，没有必要额外夸大，也不应将 RTG 当作 ID‑VTDO 的创新。

## 3. 真实梯度诊断有价值，但它测到的不是 Contribution

本轮短交接组与总梯度的有符号对齐份额接近1，配合实现、复核的零优势记录，说明**三个成功首窗的直接 actor 信号主要来自交接，尚未来自正确实现或有据复核**。

这里应继续保持三项区分：

**梯度对齐份额不是非负的“贡献百分比”**，不能把组范数相加；
**它不是 AdamW 更新后各岗位能力变化的分解**，共享参数可能产生迁移或干扰；
**更不是 ID‑VTDO 的 Contribution**，后者需要实际训练之后的开发团队效用。

本轮已经把这些边界写清楚，建议保留。下一轮不必继续增加大量类似诊断，重点应转为：**实现与复核是否开始产生对应工作成果，以及这些变化能否在冻结评价中重复出现。**

## 4. 上下文问题得到缓解，但不是主要业务瓶颈已经解决

E0 中，12k 条件的六例没有上下文拒绝，但回报逐项未变；正式大批仍出现4次上下文边界。因此可以保留“所测合理路径在12k内可容纳”的结论，不能扩展为所有实际轨迹都不再受限。

更重要的是，模型已经出现读取依据、改 SQL、执行新 SQL 和具体义务修复，但仍没有正确构建与完整提交。这说明问题已经不能只用“工具调用不通”解释。

下一步应围绕**依据取得之后的使用、真实代码修订和独立复核**开展学习诊断，而不是继续主要优化接口消息的字节数。

# 三、数值修订可以作为新起点，但应避免再陷入数值工程循环

## 1. 六序列诊断支持什么

固定原输入、输出和实际 actor 张量，`high` 缓存重演与原采样概率一致，而整序列重算重现失败；改用 `highest` 后，缓存与整序列差异明显下降。这支持**所检查失效点与数值计算路径有关**，排除了这些点上的简单日志错配解释。修订计划也明确说明，这是按失效点选择的诊断，不估计总体错误率。

PyTorch 官方文档说明，`high` 可以使用较低的内部乘法精度，而输出仍然是 float32；因此“模型权重是 FP32”并不意味着所有乘法都使用相同内部精度。:chatgpt-content-reference{index="11"}

同时，数学等价的浮点运算也不保证因批次、形状和运算顺序不同而逐位相同。**不能把所有数值差异都归结为记录错误，也不能仅凭这些诊断唯一定位到某一条底层 GPU 指令。**:chatgpt-content-reference{index="12"}

## 2. 下一步需要的是“足够稳定地完成研究”，不是无限精度认证

建议以已经通过有界检查的 `highest` 配置作为近期默认，固定生成、概率复算和反向的实际执行条件。重点补充：

**一个预定大小的真实窗口，以及更新后的下一个窗口。**

这比再次只测四例初始容量更贴近本轮真正的失效边界，但也不需要展开任意长度、任意硬件、任意模型的穷尽认证。

原概率门保持，不删除异常 token、不覆盖原行为概率。**不过，0.02／0.002 是本项目冻结的工程准入阈值，不是 PPO 的普适数学常数。**以后研究更快的数值路径，可以另行校准概率误差、surrogate／梯度偏差和实际代价；不能在本轮看到失败后仅调高阈值放行，也不能永久把“逐位一致”作为所有在线 RL 的必要条件。

## 3. 必须按新代价重冻预算

最高精度四例耗时约1172.64秒，按原公式外推，训练部分约39.09 GPU进程小时，尚不含评价。这个重新估计是合理的停止依据。

但四例 `high/highest` 的实际轨迹不同，**2.33倍的观测时长比不能被解释成纯精度设置造成的因果速度比**。未来预算也不能只按 episode 数线性推断显存和耗时：本轮正式峰值已经高于四例容量。资源数应继续区分进程时长、调度墙钟与实际硬件计算。

# 四、一个更本质的判断：当前任务与模型的学习信号仍然失衡

本轮没有正确实现或有据复核的成果，三个成功窗口又都是 critic 初始为零的首窗。由此可见的直接问题是：

> **已经会做的交接贡献了大部分可利用信号，真正希望改善的实现和复核仍没有提供足够的结果差异。**

这不能通过更复杂的 \(q/b\) 自动解决，也不能通过人为制造非零优势来证明“可训练”。V1 明确规定：无支持保持基础处理；零信号与探索不足不会因经验重配置而消失。:chatgpt-content-reference{index="13"} :chatgpt-content-reference{index="14"}

下一阶段可以保留完整链，同时增加**具有完整业务意义、但计算与协调长度受控的工作责任**，例如：

| 责任情境 | 模型必须真实完成的事 |
|---|---|
| 已取得合法依据的实现 | 读取适用规则，修正一处真实查询或代码，运行并交付 |
| 已有真实提交的复核 | 读取固定产物与独立依据，识别一个明确但不预告位置的差异 |
| 有限双成员交接 | 一方掌握必要解释，另一方必须获取并实际用于结果 |
| 完整多成员链 | 自主完成获取、实现与复核，不由控制器补齐步骤 |

这些不是教师示范，也不是要求先成功才能训练。**模型仍然从环境中自行探索并承受后果；调整的是可执行工作情境的长度与复杂度，而不是在后台给出答案。**

同时，不应继续默认“只要再多训几个窗口，完整成果自然会出现”。可以在开发阶段做有限的条件诊断，分开检查计算可行性、信息协调和状态依赖；正式方法比较前再冻结共同任务分布。这个拆分正是 V1 的建议。:chatgpt-content-reference{index="15"}

## 1. UCI Online Retail：直接复用当前 SQL 能力，但必须尊重真实字段语义

接入时最需要避免的是：

> **把现有构造任务中的 `completed/pending`、`amount_factor`、`order_id` 换个名字，继续声称在使用真实业务数据。**

建议保留原始文件和字段说明，在本地建立可查询表；按完整发票或关联实体形成有界切片，而不是任意抽几行。模型获得 schema、必要预览和查询工具，**实际修改 SQL／Python、构建结果，而不是读取后台预算好的答案**。

## 2. 首个真实数据项目群

| 项目 | 实际工作 | 串并联关系 |
|---|---|---|
| **P0：资料核对与发布** | 检查字段、记录和未解决项，发布可用数据 | 提供共同输入 |

| **P3：集成核验** | 读取双方实际产物，核对结果与口径 | 汇合前序成果并形成交付 |

并行交叉应来自**共同客户标识、统计期间、记录适用性和输出粒度**，不是两个人只是读取同一张表。先提供可用初始合同，让双方能够启动；反馈跨版本发生，不把首次完成设置成互相等待。

原数据没有记录的审批、角色沟通和需求变化，仍标为模拟。**真实素材提高的是工作语义与来源基础，不会自动把我们构造的组织流程变成真实历史。**

第一版可以先让共享模型接手其中一个有明确责任的工作片段并在线更新，再扩展到交叉项目。**不必等四项目全部自主成功才训练，也不必等旧 toy 的 MC／RTG 比较显著之后才开始接入。**

## 3. 软件来源：用于验证内核是否真的超出表格工作

**接口约定 → 实现修改、消费者适配并行 → 集成复核。**

# 六、建议的下一轮实验组织

## N0：计划规模的数值与资源桥接

用新冻结的最高精度配置，运行**一个计划大小窗口及其更新后的下一窗口**。任务和样本数事先固定，不按结果补采，不使用容量训练后的权重充当正式初始模型。

验收对象是：当前规模能否完成真实交互、概率核对、更新和下一窗口；失败时准确留下未执行项与状态。**不是要求所有任务成功，也不是要求把所有未来数值风险消除。**

同时完成真实数据源的 CPU 导入、工具和验证工作，两条线互不等待。

## N1：先完成一个较小的 MC／RTG 在线学习 pilot

相较直接重启六运行，我建议先采用：

\[
2\text{ 条件}\times1\text{ 个训练种子}
\times4\text{ 窗}\times16\text{ episode}
=128\text{ 个训练 episode}.
\]

这是**新设计建议，不是已冻结预算或功效保证**。三个训练种子的正式扩展随后另行登记，不能选择一个幸运种子冒充多种子结果。

评价也要在预算中明确保留。例如，一个可核算的 pilot 是：

| 评价位置 | 示例数量 |
|---|---:|
| 共同初始开发8例＋锁定12例 | 20 |
| 两条件在第2窗后各开发8例 | 16 |
| 两条件在第4窗后各锁定12例 | 24 |
| **评价合计** | **60** |

这样合计188个 episode。其用途是取得完整学习曲线和候选效应，不是证明广泛泛化。**单种子完成，比六个种子全部中途停止更能回答当前的工程与学习问题，但结论强度仍然有限。**

按旧构造家族的最高精度容量公式，这128个训练例约需13.03 GPU进程小时，含原25%裕量、不含评价。**这只是原家族的规划参照，不能直接用于 UCI 或代码环境的成本承诺。**

正式运行保持初始权重、优化器、工具、终局合同、任务份额及总预算一致。MC／RTG 只改变声明的时间信用。每次更新后重新进入世界，不能把同一批经历重复优化当作多个在线窗口。

## N2：真实来源上的直接工作与在线学习

这一组与旧家族的比较分开报告。先冻结新素材、任务合同、工具和奖励，再让同一共享模型直接交互和更新。

近期优先验证：

**是否读取并使用真实字段定义；是否修改实际逻辑；是否产生独立正确结果；是否依据固定产物完成复核；并行项目是否真的影响彼此的工作。**

如果模型仍只完成读取和交接，就准确报告这个边界。不能为了让新数据“看起来有效”，自动补采用、修 SQL、改变评分或用规则策略完成后续。

新来源不自动解决探索不足，但它可以防止研究一直围绕一个熟悉的六行交易世界做局部修订。**来源扩展与学习有效性应分别测量。**

## N3：支持统计同步进行，有条件再启动 ID‑VTDO

本轮54个成员块只有9个 provider 短交接块支持非空，且全部是单类，因而没有组成自由度。继续不执行 O4 是正确的。

其中“36个情境块”应解释成**窗口—情境记录**，不是36个独立来源或不同业务任务。短 provider 交接也不能替代多成员共同决策的协作支持。

新来源中，应有2–3个真实决策主体，在同一初始条件下允许不同合法获取、交接或核验方式；实际频数由当前模型产生。**不靠不同提示强制出两种方法，不跨权重拼接，不补采到配额齐全。**

达到支持条件之后，再在在线窗口内从相同学习状态做配置试训、实际开发评价和正式更新。没有支持时继续基础 RL。V1 对这一顺序和支持外不赋质量的约束很明确。:chatgpt-content-reference{index="21"}

# 七、泛化控制应在接入来源时落实

下一轮不能只有“新金额、新持有者、新规则”的内部锁定标签，还需要明确哪些来源真正没有参与训练和外层开发。

建议采用以下划分：

| 层次 | 能支持的判断 |
|---|---|
| 同一来源的新事实、需求 | 有限实例适应 |
| 同来源的新信息布局、项目关系 | 相应结构变化下的适应 |
| 未用于训练或调权的数据／代码家族 | 新来源迁移 |
| 不同工作类型、不同搭档 | 工作与协作迁移，需另外验证 |

同一表的不同月份、同一仓库的近重复问题、上游成果与其衍生下游任务，都不能简单随机拆分后称为独立来源。反过来，共用 Python、DuckDB 或测试框架也不必把所有项目合为一个来源；需要追踪的是**具体事实、目标代码、解法和派生产物的关联**。

旧锁定评价按本轮协议保留。**若下一轮据其逐案结果修改任务、提示或奖励，它们可以继续作为开发参考，但不能再次称为新方案从未接触的独立测试。**

最终仍应分别测试：一个模型实例接手某个岗位，以及多个同权重实例组成团队。公开项目可能已经被基础模型见过，因此还要通过新需求、信息重新分配和独立来源限制记忆捷径，不能保证预训练污染为零。

这与来源调研和 V1 的共同要求一致：**数据源提供工作对象，模型自己产生行动；评测要验证新工作，而不是熟悉项目上的重复完成。**:chatgpt-content-reference{index="22"} :chatgpt-content-reference{index="23"}

# 八、预算和阶段终点应如何收口

本次计数复算支持报告的主要资源结论：全阶段290个闭合 episode、5次 actor 更新，原正式运行仍只有3次更新；累计约7.1304 GPU进程小时，不等于纯 GPU 计算或并行调度墙钟。

下一轮资源应优先投入：

**一次能跑完的学习比较、至少一个真实来源的实际工作接入、冻结评价和有限迁移检查。**

昂贵的全量分组梯度可以只在事前指定窗口记录，其他窗口保留必要的优势、概率、回报、成员动作和状态。不能让诊断报告越来越完整，却始终没有预算完成训练后评价；减少诊断是否节省成本仍需实测。

下一阶段的完成条件建议只有三项：

1. **在冻结数值与资源条件下，完整执行一个有限在线比较及训练后评价，无论结果正负。**
2. **至少一个真实公开来源成为模型能够实际操作并在线学习的场景，另一类代码资产完成有界可运行验证。**
3. **分别报告来源准入、工作表现、基础学习、方法支持和 ID‑VTDO 增量，不互相替代。**

## 最终推进判断

**本轮不应被判成研究方向失败，也不应被包装成学习成功。它已经明确告诉我们：数值路径中断了效果研究，而已完成更新的有用信号仍集中在较容易的交接工作。**

接下来的重点应从“再做更大的同类试验”调整为：

\[
\boxed{
\text{稳定的有限在线执行}
\;+\;
\text{真实公开项目接入}
\;\longrightarrow\;
\text{完整学习与迁移测量}
\;\longrightarrow\;
\text{有支持的 ID‑VTDO 比较}
}
\]

**保留一个共享通用模型、仿真内直接训练和独立项目泛化这条主线。数值修复是运行条件，真实来源是工作载体，MC／RTG 是基础学习对照；最终科学对象仍然是：如何让同一个模型从不同工作位置的真实联合经历中，学到更可迁移的工作与协作能力。**
**我同意，而且这应当成为下一轮的优先调整：不再默认继续以 Qwen2.5-7B-Instruct 作为唯一主训练模型，而是先选择一份已经具备基本工作能力的开放权重检查点，再研究共享模型的在线学习与经验配置。**

我们的主要科学问题是：**怎样让模型从不同工作位置的经历中，学得更可靠、更善于协作、更能迁移到新项目。**不宜同时承担“基础工具协议学习、基础代码能力补课、长程协作学习、训练数值实现”四个难题，否则难以判断算法究竟有没有发挥作用。

但也要保持一个边界：**换模型是合理的实验起点调整，不代表已经证明现有全部失败都来自模型能力不足。**v0.14 的数值停止与实现、复核缺少正确成果，是两类不同问题；更强模型不会自动解决概率复算问题。

## 一、我们需要的“基础能力”，不是只会调用工具

建议以实际工作表现定义，而不是仅看参数量或综合榜单。

| 能力 | 应当观察到的行为 |
|---|---|
| **工具与合同理解** | 根据公开定义选择工具、填写引用，收到明确错误后能够调整，而非持续原参数重试 |
| **依据驱动的实现** | 读取当前规则，实际修改 SQL／代码，执行并获得正确结果，不只是运行已有错误程序 |
| **独立复核** | 读取固定提交和必要依据，区分正确与错误成果，提出有证据的问题 |
| **基本协作** | 发现信息缺口，向正确成员请求或主动提供资料，接收之后真正用于工作 |
| **持续执行** | 在多轮操作、版本变化和反馈之后，仍能保持目标与工作上下文 |

**选型不能只看交接成功率。**目前真正制约学习的是实现与复核；一个模型如果只把读取、交接做得更熟练，仍没有解决当前主要问题。

我们也不需要候选模型在全部长程项目上接近满分。合适的起点是：

> **基础工作在不同事实下能重复完成，复杂协作与动态维护仍有明确提升空间。**

这不是重新设置“先成功才能训练”的门槛，而是在有限预算下选择更有研究价值的初始化。可信失败仍进入基础 RL；只是不能期待经验重配置自动创造不存在的有效方法和学习信号。:chatgpt-content-reference{index="1"}

## 二、建议优先测试的模型

我核查了当前官方模型页面。建议首次只比较少量候选，**下面是试跑优先级，不是已经在 ProWorkSim 中验证过的能力排名**。

| 候选 | 建议定位 | 选择依据与主要限制 |
|---|---|---|
| **Qwen3.8-27B** | **能力优先的首选试跑对象** | 官方开放了后训练权重，采用 Apache-2.0；发布说明重点覆盖代码、专业工作、长程 Agent 和环境反馈处理。属于27B级稠密模型，但使用混合架构，现有训练代码不能默认直接兼容。:chatgpt-content-reference{index="2"} |
| **Qwen3.5-9B** | **较低资源档的候选** | 官方提供后训练权重、工具使用入口，采用 Apache-2.0。它可以检验“更合适的新一代小模型是否已经足够”，但不能仅凭代际更新就认定强于旧模型的实际工作表现。:chatgpt-content-reference{index="3"} |
| **Qwen3-32B** | **训练集成风险较低的备选方向** | 官方提供32.8B稠密、GQA结构的后训练模型，采用 Apache-2.0，支持思考与非思考模式。从结构上比混合模型更接近现有路线，但仍需真实验证前向、缓存、反向和 LoRA 接入。:chatgpt-content-reference{index="4"} |
| **现有 Qwen2.5-7B-Instruct** | **保留为历史与低能力基线** | 不删除已有实验，也不再因为已经适配它，就默认所有后续研究都必须围绕它开展。 |

**我的倾向是：先用 Qwen3.8-27B 与 Qwen3.5-9B，连同现有7B模型做一次有界的能力筛选；Qwen3-32B作为事先登记的集成备选。**

如果27B候选在实现、复核和协作上明显更可靠，而且在线训练代价可接受，就优先采用它，不必为了“小模型更省”继续消耗大量重复失败。反过来，9B候选若已经满足基本工作要求，可以把更多预算留给在线窗口、独立来源和贡献校准。

**应比较的是“完成有效工作和产生可用学习信号的总成本”，而不只是单次前向的成本。**

## 三、选后训练检查点，不等于改变直接在线 RL 路线

这里“基础模型”指我们的**初始策略检查点**，不必是模型厂商命名为 `Base` 的纯预训练版本。

建议使用已经具备通用指令遵循、代码和工具能力的后训练模型，然后：

\[
\text{选定共享初始策略 }\theta_0
\rightarrow
\text{在仿真世界中实际工作}
\rightarrow
\text{依据环境后果更新}
\rightarrow
\text{新策略继续工作}.
\]

**我们不需要先采集 ProWorkSim 教师轨迹，再为候选模型专门做一轮 SFT。**采用一个已经公开后训练的检查点，与“本项目在环境内直接进行在线 RL”并不矛盾。

同样，选型期间可以测试不同模型，但正式训练仍然是：

**一个选定模型、一个共享适配器、一个 actor 优化器，所有角色使用同一套有效参数。**

不是资料员用9B、实现者用27B、审阅者再用另一个模型。那会改变团队组织与最终部署目标。

## 四、先做一次短而有辨识度的选型实验

我建议不要直接给每个候选启动多种子长训练，而是先冻结一个**开发用途的工作能力筛选集**。

一个可执行的规划规模是：

\[
12\text{ 个开发情境}
\times3\text{ 次独立运行}
\times3\text{ 个模型条件}
=108\text{ 个 episode}.
\]

这是拟议规模，尚未执行或授权。十二个情境可以按下面组织：

| 类型 | 情境数 | 主要检查 |
|---|---:|---|
| 有合法依据的实现任务 | 3 | 是否真正修改并产出正确 SQL／代码 |
| 对真实提交的复核任务 | 3 | 正确接受、发现错误、避免无依据批准 |
| 双成员信息获取与反馈恢复 | 3 | 是否取得必要信息，并纠正具体工作问题 |
| 多成员或跨项目工作链 | 3 | 是否将上游成果用于后续工作，而非停在交接 |

至少一部分应来自正在接入的真实公开数据或代码，不能全部采用已被多轮调整的构造 SQL 案例。**来源准备属于环境构建，不是先生成训练示范。**

### 比较时，要给模型公平的工作条件

**业务条件一致，模型接口按官方格式适配。**不同模型可以使用各自的原生聊天模板和工具解析，但不能为某个模型额外给正确步骤、隐含依据或自动修复。

**不要把旧的512输出上限机械套给所有模型。**Qwen3.5与Qwen3.8默认包含思考模式，并提供关闭方式；模式、输出预算和历史保留策略必须事先明确。否则测到的可能只是输出被截断，而非工作能力。:chatgpt-content-reference{index="5"}

这也不意味着默认开放超长推理。可以在小型接口开发中选定一个可负担模式，再固定正式筛选配置。不同模式作为不同条件记录，不能失败后临时开启更多计算、只保留成功结果。

### 选型主要看什么

优先看**实现与复核的独立正确性、错误反馈后的有效恢复、团队完整成果，以及总运行成本**。格式正确率、工具成功率和平均奖励作为辅助。

不应只要求“出现过一次成功”就宣布通过，也不必设置某个未经测量依据的统一成功率门槛。更有说服力的是：

> **在不止一个事实或项目上，反复表现出已有基础工作能力，而失败主要位于我们希望通过在线学习改善的协调、维护和复杂性环节。**

模型筛选使用的环境属于开发资源；正式泛化测试另行保留，不能用同一批结果既挑模型、又证明新项目收益。

## 五、“会工作”与“适合训练”要分别核查

一个模型推理能力更强，不代表当前训练器已经能正确更新它。

### 1. 不要直接移植旧 attention 补丁

Qwen3.5-9B与Qwen3.8-27B采用 Gated DeltaNet 与注意力混合结构。旧模型针对 GQA、缓存和完整序列重算的专用处理，不应未经验证直接套用。:chatgpt-content-reference{index="6"}

建议优先使用该架构已有支持的实现，再验证我们实际需要的几个环节：**生成概率、可微概率复算、共享 LoRA 更新、检查点恢复和更新后重新交互。**

若候选能力很好，但训练接入需要大幅重写，应把它记作训练集成成本，而不是隐藏这项代价或把失败解释为模型能力差。

### 2. 资源评估不能沿用旧7B的配置推断

仅按27B语言参数粗算，FP32权重约108GB，BF16约54GB，**还没有包括其他模块、激活、缓存和训练状态**。因此，更大的模型可能需要新的精度或并行方案，不能声称现有单卡配置必然可用。

这不等于必须坚持FP32才能做研究，也不等于可以静默改成低精度。应当冻结实际数值路线，核查概率与梯度，并按真实成本选择。**v0.14的数值问题需要单独解决，不能指望升级模型名称就消失。**

### 3. 推理采样与训练概率必须对应

原生模板、思考模式、温度、截断采样、重复惩罚或约束解码，都需要纳入运行配置。不能在采样时使用一套分布，训练时却继续按“只除温度”的旧实现计算概率。

商业 API 可以用于初步能力参照，但最终训练对象需要可取得的相同检查点及完整训练接口；**云端别名的好表现，不能直接充当本地权重的能力与训练证明。**

## 六、对下一轮计划的直接修改

我建议把顺序调整为：

\[
\boxed{
\text{少量候选的实际工作筛选}
\rightarrow
\text{选定一个可训练的共享检查点}
\rightarrow
\text{重新测量初始能力}
\rightarrow
\text{直接在线基础 RL}
\rightarrow
\text{ID‑VTDO 对照}
}
\]

现有Qwen2.5-7B及v0.11–v0.14结果全部保留，但不再把它们当作必须继续投入的模型绑定。更早的实验已经明确提醒：特定协议下的失败不能泛化为模型全部能力不足；现在需要的是在可用接口下，对新候选做实际比较。:chatgpt-content-reference{index="7"}

选定新模型后，MC、RTG、基础MARL和ID‑VTDO都从**相同的新起点**出发。新模型比旧7B更好，是模型选择结果；训练后比自身初始状态更好，才是学习收益；ID‑VTDO比同起点、同预算的强基线更好，才是算法增量。

**我的明确建议是：先升级“研究起点的能力”，而不是继续要求当前7B同时学会基础实现、基础复核和复杂协作。我们应把主要训练资源用于提高已有工作能力的可靠性、协作效率与泛化，而不是长期消耗在尚未进入有效工作的重复失败上。**
