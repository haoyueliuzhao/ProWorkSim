# 二、三类失败不应被归为同一个“模型能力不足”

## 1. 9B：主要问题是完整合同保持

9B大多数槽能够形成固定提交，两个修复合同也都两seed通过。O1的主要缺口包括默认值与secret更新、未知字段处理、金额精度以及规定的Schema序列化路径。

这不是“完全没有合作”，也不是“完全不会编程”。它更接近：

**能够推进工作，但没有在最终集成中持续满足全部要求。**:chatgpt-content-reference{index="10"}

因此，9B后续最值得检查的是根需求保持、边界验证和集成后复核，而不是继续增加消息、计划或任务创建次数。

## 2. Devstral：交付接口与代码正确性共同影响结果

两个明确的失败槽已经固定patch，却连续生成：

```text
submit_integration({})
```

由于缺少必填`message`，在连续格式错误门下终止；主要反馈还被二次JSON解析的`Expecting value`遮盖。这是具体的接口障碍证据，不能把这两例简单概括成不会写代码。:chatgpt-content-reference{index="11"}

但Devstral唯一“提交后仍失败”的O1也存在金额精度和dump路径缺口。**因此，补好message反馈并不等于它一定能通过完整任务。**

## 3. SWE：主要测到了当前受管协议使用困难

SWE r2十二槽均未交付，错误集中在XML参数、空搜索、读行数越界、缺recipient、重复参数，以及保守token预约和等待终止。

v0.32第三条调用本身格式合法、概率和反向也通过，只是模型没有按要求调用`record_fact`。因此，需要区分：

**模型没有选对下一步**，与**执行链路不能可靠处理模型输出**，不是同一件事。:chatgpt-content-reference{index="12"} :chatgpt-content-reference{index="13"}

本轮不能证明SWE在熟悉的工作台中也一定没有能力；但也不能用其公开代码Agent定位，代替本项目的实际结果。**建议暂时停止SWE整批复测，保留其数值接入成果，避免继续围绕它的三条技术资格反复修订。**

# 三、有两项方法学问题，下一轮必须修正

## 1. 不能由单人简单题与双人复杂题，推断协作带来的损失

当前API、修复和O1是不同合同。O1账本同时包含金额语法、精度、去重次序、可复用Schema和集成输出；settings也包含部分更新、嵌套合并、默认值、原子性及敏感字段投影。

所以：

\[
\text{单人API／修复更好}
\quad\not\Rightarrow\quad
\text{双成员协作使能力下降}.
\]

可能是任务本身更难，也可能有协作负担，还可能是接口和预算共同作用。**缺少的是同一根目标的单／双执行比较，而不是更多不同题目的成功率。**原报告对此限制的说明是正确的。:chatgpt-content-reference{index="14"}

## 2. 技术资格、行为诊断和分配支持，不能长期合成一道门

原协议这样定义资格，按原门停止没有问题。但作为后续研究设计，应拆成四层：

| 层次 | 判断什么 | 不能被什么替代 |
|---|---|---|
| **执行可信** | 身份、实际输入输出、权限、工具结果与反馈可靠 | 指定三道工具选择题全答对 |
| **学习接入** | 原始目标、概率关系、完整梯度、状态恢复与有限容量 | 加载成功或短生成 |
| **工作行为** | 是否选对工具、恢复错误、完成交付 | parser合法、工具返回ok |
| **分配支持** | 新训练窗口中真实有效方法、本人动作和可辨识学习信号 | 开发池通过率或旧“入选”标签 |

v0.32第三条是明确的行为诊断失败，**不应在新的协议中被解释为已经证明的执行和可微能力全部失效**。反过来，数值路径通过也不应使其业务行为自动通过。

这里不是追溯取消旧资格，更不是现在绕过有效性直接训练。原`selected_candidate=null`保持。只是：

> **“某开发池每类至少2/4”是一次选型政策，不是ID‑VTDO的理论前提。真正不可跳过的是当前任务上的真实支持、可信学习与独立效果测量。**

V1.3明确要求避免把通用团队高成功率和反复工程资格作为算法研究的无限前置。

# 四、合同严格可以保留，但应减轻无关手续

## 1. 本次没有发现足以否定O1验收的隐藏义务

核对公开合同后：

- ledger事先要求精确金额、先验证后去重、Schema的load与dump；
- settings事先要求部分更新、默认值不覆盖已有值、未知字段忽略，以及通过Schema.dump隐藏token。

因此，**输出值相同但没有使用规定API，仍然可能按原合同失败**。不能仅因这类要求使成功率降低，就事后撤销。 

不过，必须继续分列“内容正确”“规定过程满足”“完整交付”。不能将未调用dump一律说成数值算错，也不能将公开少量测试绿色写成所有根要求已经验证。

未来的新任务应在开始前说明过程约束的工程意义；不要为了容易记录轨迹，不断增加与实际学习问题无关的手续。

## 2. 下一版接口建议只收口一次

| 建议修订 | 保持的边界 |
|---|---|
| 对本地模型统一使用实际选中请求的token计数预约 | 不增加总token额度，不改写旧账 |
| 原生参数错误放到反馈首位 | 原始坏输出和全部拒绝保留 |
| 核查`submit.message`的业务作用；若只是备注，明确改为可选 | 仍由模型主动提交，不自动补版本、补测试或宣布通过 |
| 普通可恢复格式错误消耗一次真实机会后继续 | 非法动作不执行，仍受总决定与token预算约束 |
| 权限、身份或关键记录失真单独阻断 | 不能把这类问题当普通可恢复业务错误 |

我建议在**新协议**中，不再额外因连续两次普通schema错误就永久终止角色，而是让它在共同总预算内接收反馈、尝试修正。这个改变必须公开、两模型及后续B/G/I一致使用；旧失败不回改，也不称为单因素修复实验。

这比继续增加“SWE如何填某个参数”的特殊说明更通用，也更贴近真实工作中的错误恢复。

# 五、下一轮核心实验：同一O1任务上的单／双执行诊断

## 1. 暂停模型扩容，只保留两个诊断对象

建议使用：

**当前9B端点＋Devstral-Small-2507。**

理由是两者已有完整工作和真实训练接入的分项证据，失败形态也不同，适合诊断；**不是宣布两者已通过旧筛选，更不是得到新的模型榜单**。

SWE不新增整批复测，也不再下载第四个候选。此前“更强代码模型可能更合适”的建议已经经过一次实际检验，没有得到O1优势，应据此收敛，而不是不断往更大或更新的模型搜索。

## 2. 16条有限诊断即可填补关键缺口

建议的新规模为：

\[
\boxed{
2\text{个模型}
\times2\text{个相同O1根目标}
\times2\text{种执行条件}
\times2\text{个固定seed}
=16\text{条经历}.
}
\]

旧两道O1题可以用于这次**开发复测**，但不能称为新来源独立确认。

| 条件 | 单执行者S | 双成员T |
|---|---|---|
| 根目标、代码、合同与验收 | 相同 | 相同 |
| 初始执行任务 | 空 | 空 |
| 任务与计划 | 模型自行形成 | 成员交流后自行形成 |
| 初始信息 | 团队合法初始信息的并集 | 冻结的局部条件 |
| 工作副本 | 一个 | 两个私有副本与显式发布／导入 |
| 参数 | 当前固定模型 | 两会话共享同一当前模型 |
| 总资源 | 统一总额度 | 同一团队总额度，不按人数翻倍 |

**资源必须按团队匹配。**不能单人64次、团队每人64次，却把分数差全部解释成组织优势。可讨论的设置是每个条件总计128次决定、500,000实际调用token，并匹配工具与测试资源；这属于新协议建议，不是已冻结额度。

双成员仍可集中完成、相互协助或重新分工，不预设任何岗位；运行器只公平提供机会。

## 3. 看什么结果，而不是只看有没有成功

| 新观察 | 下一步 |
|---|---|
| 单人和团队均能完成 | 有局部可行性，按事前规则选择支持采集载体 |
| 单人能完成、团队不能 | 有组织／局部信息／流程负担的线索，核查实际依赖断点 |
| 单人和团队均不能 | 不能只责怪协作；另设领域规则更少、但依赖真实的新根目标 |
| 团队能完成、单人不能 | 有有限互补或探索收益迹象，仍不作总体团队优势结论 |
| 格式和预约停止减少，内容仍错 | 接口改善与工作能力分开结论 |

两次seed不足以得到稳定性认证，但比继续跨不同题型猜测失败原因更有辨识力。

**这批只运行一次，不形成“改一句提示—重跑—直到达门槛”的循环。**全部团队结果仍为零时，不强行选赢家；应调整新任务的领域复杂度，而不是取消自主组织或给出正确分工。

# 六、如何避免又停留在载体诊断

这里需要明确一个结束条件：**已有局部工作可行性后，就应转向真实支持与配置，而不是等待模型在所有开发题上都稳定高分。**

## 1. 新训练任务可以缩小领域负担，但不能预写工作路线

初期根目标可以保留真实API—消费者依赖，或者两项共享模块的功能，但不必同时堆叠金额精度、嵌套默认覆盖、安全序列化、未知字段等全部规则。

这种调整要形成新任务、新合同和用途记录：

**减少问题本身的无关复杂度，不等于把任务拆好交给模型执行。**

参考实现继续留在环境验证侧；集中完成仍允许，双向协作也不被强迫。旧复杂任务和失败全部保留，后续可以作为迁移或难度扩展。

## 2. 当前开发成功不能进入训练支持

本轮36条都属于`model_interface_development`。无论之后怎样解释成功、修复接口或调整模型，都不能将它们改标为策略训练、贡献开发或独立确认。

选定载体后，必须在正式训练来源中重新采集：

\[
M,\quad n_{\xi iz},\quad n^+_{\xi i},\quad
v_{\xi i},\quad b_{\xi iz}.
\]

有完整有效工作，不一定有两类方法；有两类方法，不一定有足够频数；有频数，也不一定有可辨识梯度。最低必要条件逐项检查，但不把这些检查扩张为模型必须先具备通用工作能力。

# 七、首次分配实验与后续消融应继续沿V1.3推进

## 第一项真实规则比较

| 方法 | 本次作用 |
|---|---|
| **B：\(Q=B\)** | 基础学习对照 |
| **G-raw** | 同一合格原始成员分支的一般元重加权，不读专用图／类别 |
| **I-P** | 成员条件化类别配置，以实际试训估计C，采用详细基线的N与双锚 |

三者使用同一模型、完整学习起点、当前原始材料、优势和分母。失败残余保持基础权重，不把探测试训叠加成隐藏正式更新。

C只能来自**候选实际更新后**的贡献开发工作；独立确认不参与选权。新模型比旧9B成绩高，是载体变化，只有同模型内部的 \(I-B\)、\(I-G\) 才是分配增量。:chatgpt-content-reference{index="19"}

## 后续主线与消融优先级

| 研究层次 | 必须回答的问题 |
|---|---|
| I-P与I-S | 结构共享是否比局部估计更可靠或更省成本？ |
| 成员共用与成员条件化 | 对不同成员分别配置是否有额外价值？ |
| 一般特征／信息关系／完整工作关系 | 任务、责任与产物依赖是否超出一般统计和信息关系？ |
| 无C、无N及双锚消融 | 收益是否来自学习反馈，而不只是覆盖先验与正则？ |
| 单点／随机联合／图引导联合 | 联合探测与图选对分别有没有价值？ |
| 多窗口B/G/I-S | 新策略重新采集并再次更新后，相对增量是否保持？ |
| O3动态人数 | 共同总资源与动态基础测度下，自主成员组织是否仍受益？ |

成员支持不一致时不能直接复制共同q；\(q_t=r\)时N本来为零，不能用这种窗口评价N；只有一个联合候选对时也无法检验图比随机更会选对。

**单／双执行诊断与这些算法消融是两类实验。**前者解释载体，后者解释分配规则；不能让载体诊断永久替代算法研究。

# 八、成本与停止规则：有一项记账提醒

本轮唯一worker成本为约 **5.945 GPU小时**。报告另列的约 **1.402小时**是“显存预约就绪到child结束”的区间，可能包含child本身的worker时间。

因此，**不能直接把两者相加成总占卡成本**。总体占卡应按每张卡对预约与worker区间取并集，再单列“只有预约、没有模型”的时间。本次没有取得全部预约区间并重建该并集，不给一个猜测总数。:chatgpt-content-reference{index="20"}

之后真正昂贵的还可能是配置试训。例如一个块有8条合格经历、2类，完整方向比较G与I、共享B后有17次唯一试训，再加三次正式更新，共20次窗口更新，开发执行另计。

所以，需要在支持出现后按真实维度冻结可承担的探测方式。不能只看到冻结推理几小时，就启动几十次长窗口更新；也不能为降低成本，随意删除G方向或挑选有利轨迹。

旧累计时间上限已经撤销，本建议不自行恢复。但**取消累计时限不等于无限模型搜索或无限试训授权**。本次没有预约显存、停止进程或启动新队列。
