# 一、本轮审计：真正阻塞在哪里

## 1. 执行完整性成立，算法效果仍未被测量

| 对象 | 本轮事实 | 正确解释 |
|---|---:|---|
| 当前策略采集 | 8/8槽可评闭合，技术未知0 | 同一情境、同一策略的8次重复完成 |
| 固定交付 | 7份 | 已形成可核查版本，不代表完整正确 |
| 完整有效工作 | 0/8 | 没有完整合格方法进入重配分支 |
| 真实模型生成 | 478次 | 不是956条开始／结束事件对应的956次调用 |
| 上游与成员测试 | 62次，50次全绿 | 不能替代consumer独立验收 |
| B/G/I试训及正式更新 | 均为0 | 不是运行后零收益，而是未启动 |
| 独立确认 | 0 | \(I-B\)、\(I-G\)仍未知 |

本轮的停止处理是正确的：没有把失败改名成有效方法，没有降低频数门，没有补采到出现成功，也没有擅自追加无对照基础训练。**这一有限配置试验的停止，不等于完整在线算法以后可以删除失败经验。**:chatgpt-content-reference{index="3"} :chatgpt-content-reference{index="4"}

## 2. 七份交付失败在同一个正常调用路径，不是整个编程过程都失败

七份固定交付的结果非常一致：

| 检查 | 每份结果 |
|---|---:|
| 来源库API | 3/3 |
| 所选上游回归 | 5/5 |
| consumer空列表 | 1/1 |
| consumer非空输入 | 0/2 |
| 完整工作 | 不通过 |

报告中的实际断点是：模型将

```python
sqlparse.parse(expression)[0]
```

得到的`Statement`，直接作为`Comparison`判断，而没有正确访问内部比较节点，导致合法表达式在形成记录前就抛出异常。初始consumer桩没有预埋这段错误，它来自模型实际实现。:chatgpt-content-reference{index="5"}

因此，应当作两层判断：

**局部代码能力已经存在。**模型能够理解并修复所测库属性，保持有限上游回归。

**完整工作能力仍不可靠。**它没有把库、consumer、正常输入和最终验证连接起来。

`Comparison.left/right`调用为零，是提前异常造成的后果，不能再当成一个独立根因重复计算。无固定交付的support-4也不能拿临时工作区补做终局判断。

## 3. 可见测试覆盖和模型修复能力，都可能参与了失败

多数槽反复运行绿色上游回归，却没有验证consumer正常路径。这说明当前反馈容易使工作停留在“库测试通过”，而不是“根目标完成”。

但不能将全部失败归因于测试没有暴露错误：**support-6后期确实编写了consumer自测，连续四次看到同一异常，仍没有修复。**因此，反馈覆盖、API理解、错误后的行动选择及停止策略需要区分，不能只改一个测试入口就宣称根因已消除。:chatgpt-content-reference{index="6"} :chatgpt-content-reference{index="7"}

我的建议是：新协议可以增加少量**来自公开合同的正常路径检查和明确覆盖说明**，但必须保持以下边界：

> 让模型更容易知道“哪些要求实际验证过”，不是把隐藏参考实现或正确节点访问步骤告诉模型。

这会形成新的运行协议，所有候选和分配方法一致使用，旧0/8不回改。

## 4. 当前首先不是上下文、Mapper或最低频数问题

本轮最大实际prompt为12,967 token，预留2,048输出后仍有1,369 token余量；没有上下文停止或容量剪除。增加上下文不是当前证据指向的第一步。:chatgpt-content-reference{index="8"}

同样，当前阻塞发生在：

\[
V_{\mathrm{delivery}}=\mathrm{false}
\quad\Longrightarrow\quad
n^+=0.
\]

不是已经有两种完整方法，只差最低频数；也不是Mapper把大量已知成功都判成未知。**此时修改分类器、降低频数或扩大权重范围，都不会修好consumer。**

# 二、与V1.3仍有两处需要对齐

## 1. 当前仍是“领取预建任务”，不是自主形成任务

冻结代码直接提供`library_repair`和`consumer_export`，提示成员在这两项之间选择，任务表也由固定定义初始化。双方可以协商领取和转交，但执行分解已经由环境给出。

按V1.3，这属于 **O0b受限控制**。O1要求从共同根目标出发，成员自己创建、修订任务并形成责任，而不是只决定谁领取研究者写好的两张卡。:chatgpt-content-reference{index="10"}

下一轮应改为：

| 环境预先提供 | 成员自行产生 |
|---|---|
| 根需求、代码、兼容要求、验收标准 | 执行子任务及其拆分 |
| 合法工具、信息与资源边界 | 谁承担、是否转交、是否合作 |
| 身份、版本和任务变更规则 | 依赖安排、实现顺序、集成方案 |

可以继续固定两名启动成员，但**不能固定两项执行子任务**。暂时不需要增加经理Agent或开放无限人数；O3仍保留为最终动态组织面板，不必和这次模型选型同时完成。

## 2. 分配协议仍是旧变体，不能直接代表详细理论

本轮协议使用的是：

\[
N_z=\max(0,1-Kb_z),\qquad q_0=b,
\]

且G与I共享类别覆盖先验。这一变体已经明确登记，又未实际执行，所以不推翻本轮采集；但下一次正式理论比较不能继续把它等同于V1.3。

主理论版本应恢复对数N、历史锚与覆盖锚；一般基线也应区分：

- **G-raw：**不读取专用语义类别或工作图的一般成员—轨迹元重加权。
- **G-lift：**共享类别先验、但允许类内分别加权的辅助归并对照。

**更换模型解决载体能力，O1解决研究场景，公式与基线对齐解决算法对象。三者不能相互替代。**

# 三、模型是否应该换：应该做有限选型，但不要只挑更大的参数量

这里需要的模型，不只是能生成正确函数，而是能够：

**理解API → 检查真实返回 → 设计正常路径测试 → 根据错误修改 → 协商并集成 → 完成固定交付。**

所以，我建议优先考虑**代码Agent后训练检查点**，而不是仅根据“14B比9B大”选一个通用模型。

这些公开模型此前经过SFT或RL，不意味着本项目要改为离线训练。它们可以作为共同初始化，之后仍采用我们的当前策略在线工作与经验分配。

## 1. 推荐候选

|---|---|---|
| **Devstral-Small-2507，24B** | 软件Agent定位、工具与多文件编辑；官方BF16权重；OpenHands设置下发布者报告SWE-bench Verified 53.6% | **优先24B候选**，能力方向与现有工作台较匹配 |
| **SWE-Next-14B** | 基于Qwen2.5-Coder-14B-Instruct进行仓库级轨迹后训练；原论文报告其14B设置Verified 30.0% | **优先14B候选**，比只选普通代码Instruct更贴近完整仓库工作 |
| **Devstral Small 2 24B** | 发布者报告Verified 68.0%；官方发布为FP8 | **能力优先备选**，须先通过可微训练接入 |

这些数字来自各自作者或厂商的协议，**不能横向相减当成统一排名，更不能换算成本项目的成功率**。:chatgpt-content-reference{index="12"}

### Devstral-Small-2507：为何优先考虑它

它的优势不仅是24B，而是训练定位直接面向软件Agent，并有OpenHands使用基础；官方BF16权重也避免了第一步就必须研究FP8训练。官方配置为`MistralForCausalLM`。:chatgpt-content-reference{index="13"}

**我的建议是将它作为首轮24B路径，而不是立即回到27B多卡方案。**不过，它依然需要独立的原生模板、EOS、工具格式和学习概率核验，不能直接套当前Qwen的所有适配。

### SWE-Next-14B：比单纯回退原生Coder更值得测

这个检查点直接基于仓库级修复和恢复式调试轨迹进行后训练。其官方文件目录也已列出约29.6GB、六个权重分片；本次核查不是只看到了一个论文名称，但尚未下载验证完整张量。:chatgpt-content-reference{index="14"}

它值得测试的原因是**工作行为训练更贴近当前缺口**。但原执行格式与我们的受管SDK可能不同，必须先验证能否在不增加隐藏辅助的条件下使用现有工具。它的公开训练来源还需要与本项目拟用仓库和确认集检查重合。

### Devstral Small 2：能力更值得关注，接入条件也更严格

这是本次候选中不能遗漏的一项，但有一个关键事实：**官方版本是FP8，不是官方BF16版本。**模型卡的本地部署说明和68.0%结果，均不能证明当前A100上的LoRA反向、概率重算和完整窗口更新已经可行。:chatgpt-content-reference{index="15"}

若使用显式反量化后的BF16张量，应记录为新的数值profile；转换也不能恢复量化前的原始高精度参数。我的建议是：

> 先做有限训练接入判断；通过后可以替换首轮24B候选，而不是再增加一个完整筛选臂并无限扩展工程工作。

## 2. 有些“代码相关模型”并不适合承担所有成员

例如 **CodeScout-14B**专门进行代码定位，官方明确它不是代码编辑或完整issue解决模型。不能因为它来自OpenHands、在SWE相关指标上表现好，就把它当成整支自主工作团队的共同基座。:chatgpt-content-reference{index="16"}

# 四、单卡能否承载：需要区分“参数装入”和“在线训练”

本轮冻结协议针对的是 **A100 80GB**。仅按名义参数量计算，参数存储约为：

| 总参数 | BF16参数存储 | FP32参数存储 |
|---:|---:|---:|
| 9B | 16.76 GiB | 33.53 GiB |
| 14.7B | 27.38 GiB | 54.76 GiB |
| 24B | 44.70 GiB | 89.41 GiB |
| 27B | 50.29 GiB | 100.58 GiB |

这是参数量乘字节数的算术，**不是显存峰值**。还需要FP32输出头与LoRA、KV、激活、反向重算、优化器和各种缓冲。

所以，你此前27B需要多卡的实际情况应当保留；但不能概括为“27B天然必须两卡”。如果是全FP32，仅参数就已超过80GB，而BF16的情况不同。本次没有重测旧27B，也不建议为此重新开启多卡路线。

**14B与24B都值得做单卡准入；24B不能仅凭44.7GiB参数大小就承诺16K反向可用。**

普通密集Transformer在工程上可能比当前混合循环路径少一些专门适配，但这是选型理由，不是已经测出的数值稳定性或速度优势。LoRA也只是减少可训练参数及其状态，不会消除激活与反向计算。

# 六、O1和正常路径反馈应在这次筛选前统一冻结

## 1. 从根目标开始，不给预建的执行任务

新的主环境应当只提供：

**共同要求、代码与已有事实、权限、工具、总资源和验收合同。**

模型自己创建子任务、修改分解、领取或接受责任、声明依赖与协商集成。根要求依然包括库与consumer正确，但不再自动生成`library_repair`和`consumer_export`两张待领取卡。

这与V1.3一致，也使后续能够研究“经验分配是否改善任务形成和组织”，而不只是学习怎样执行既定流程。:chatgpt-content-reference{index="18"}

## 2. 不让测试工具的绿色结果掩盖未测部分

建议公开反馈至少区分：

| 状态 | 含义 |
|---|---|
| 上游回归通过 | 已执行的回归检查通过 |
| consumer公开正常例通过 | 实際正常业务路径通过 |
| 成员自测结果 | 成员自己创建的测试及执行结果 |
| 未测试 | 对应要求没有执行证据 |
| 固定提交 | 保存了待验收版本，不等于独立通过 |

新增公开用例应从公开合同构造，而不是抄隐藏验收。隐藏评价继续独立。

若为提交增加必测项，那是新合同，所有方法一致遵守；**不能把强制运行测试产生的发现，宣传成模型自主识别了旧验证缺口。**

# 七、选定模型后，研究重心必须立即回到B/G/I

模型选型不是新的长期主线。通过筛选后应固定一个共同模型、harness和数值配方，恢复如下路线：

\[
\boxed{
\text{O1当前策略工作}
\rightarrow
\text{完整有效方法支持}
\rightarrow
\text{B/G-raw/I-P选权与更新}
\rightarrow
\text{独立确认}
\rightarrow
\text{新策略继续工作}.
}
\]

## 首次配置实验必须保持的条件

**同一模型与完整学习起点。**不能B用9B、I用24B；新架构不能继承旧9B的LoRA或优化器。

**同一批当前经历。**不同模型、不同先手协议、不同接口的旧成功不能拼入支持。

**同一基础损失与失败残余。**只在真实合格分支内配置，可信失败继续基础处理；无动作成员没有伪目标。

**C来自更新后的实际开发工作。**未运行schema不能记成C=0；覆盖项让q变化也不能冒称发现高价值经历。

**独立确认不参与选权。**换模型导致绝对成绩提高，属于载体变化；只有同模型内部I相对B/G的差值，才支持分配增量。

最低频数和重复数应根据新开发产出率与估计精度事前确定，不再机械沿用“8条”。若新批仍无支持，有限配置试验可以依协议结束，但不能不断补到成功。

# 八、试训成本要先算清，不能只看到新模型单次推理更快

当前完整有限差分在一个块上的成本为：

\[
T_G=1+2(n^+-1),\qquad T_I=1+2(K-1).
\]

| 假设支持 | G试训 | I试训 | 共享B后的唯一试训 | 加三次正式更新 |
|---|---:|---:|---:|---:|
| \(n^+=4,K=2\) | 7 | 3 | 9 | 12次窗口更新 |
| \(n^+=8,K=2\) | 15 | 3 | 17 | 20次窗口更新 |
| \(n^+=8,K=3\) | 15 | 5 | 19 | 22次窗口更新 |

每份试训还需要贡献开发执行。**8条新工作经历不意味着只做8份计算。**v0.29的1.783 GPU小时只是采集阶段；冻结协议所引旧完整更新成本也只能作历史参照。

第一次模型训练资格就应记录完整长度分布下的实际更新成本。大规模G无法穷举时，事前确定有竞争力的可扩展元优化，而不是削弱一般基线或让“完整穷举”永久阻止实验启动。

# 九、与最终主线的衔接

| 阶段 | 核心研究内容 |
|---|---|
| **本次选型与O1对齐** | 找到能工作、能修复、能训练的共同载体 |
| **局部B/G-raw/I-P** | 第一次真实检验完整选权规则，而非仅权重接线 |
| **I-S结构共享与消融** | 成员条件化、一般特征／信息关系／完整工作关系、跨窗口校准 |
| **C/N与双锚、联合探测** | 无C、无N、历史／覆盖作用；单点、随机联合、图引导联合 |
| **O1多窗口主实验** | 各方法新采、选权、更新，比较独立效用与全部成本 |
| **O3动态组织面板** | 在共同总资源下由模型决定成员增减和重组，使用单独冻结的动态测度 |

这条主线不会因为更换基础模型而改变。**强模型的作用是让真实工作与有效经验更有可能出现，而不是替ID‑VTDO提供一个更强的实验组。**

资源方面，本轮报告已明确GPU0–7可用，不能再沿用旧GPU5单实例限制；但本次没有检查实时资源或启动任何新运行。下一轮仍需冻结候选、任务、诊断更新、贡献试训和独立确认数量，取消旧累计时限不等于无限搜索。

## 最终建议

**应该考虑更换模型，而且现在比继续重复当前9B的同题采样更有研究价值。**但更换应是一轮有明确结束条件的载体选择：

> **优先比较一个24B软件Agent模型和一个14B仓库Agent模型，先确认它们在同一O1环境中能够完成正常路径、利用失败反馈修复，并能在单卡执行真实更新；随后固定胜出组合，立即进入经验分配规则对照。**

本轮不应改的是0/8、无支持和未执行结论；下一轮最应该改的是**候选模型的工作基础、正常路径验证、O1任务形成和理论公式对应**。不能再用降低有效性门槛、改Mapper或增加读取次数，代替这些真正的阻塞点。
