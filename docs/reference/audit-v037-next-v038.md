# 二、为什么现在应该转向协作自由度，而不是继续围绕双类支持打转

**双类支持解决的是“能不能调整这两类经历的训练比例”，没有解决“当前团队究竟拥有多大自主组织空间”。**

目前的local／peer是有限产物路线：它们能够区分最终交付如何形成，但并不完整描述团队如何提出工作、协商责任、调整依赖、组织复核或决定人员数量。新协议也明确保留了旁支活动、重复编辑、弃用导入和提交后活动，不把两个类别解释成完全独立与必要协作。

因此，下一阶段不应继续追求：

> 再多接纳几条轨迹、再增加几个类别，然后立即恢复同一局部配置实验。

而应转向：

> **扩大模型能够自主决定的组织行为，同时保持根目标、权限、质量和资源约束可检查。**

这里还有一个重要的证据缺口：本轮报告充分呈现了支持和更新，但没有给出完整的组织行为总账。例如，多少任务经过协商形成、多少责任真正转交、多少请求被伙伴响应、多少冲突由重新分工而不是独自覆盖解决。**不能把v0.35的消息计数直接沿用到v0.36，也不能从4条peer推断已经存在丰富协作。**

暂停训练的直接作用，是让这些执行与测量问题不再和参数变化混在一起。它**不是**要求先训练出或搭建出一个“通用团队”后才能研究分配。

# 四、自由度怎么提高：不是预设更多角色，而是开放组织动作

## 1. 分三层推进，但不再把“两名成员”写成系统定义

| 层次 | 初始人员 | 模型可以决定什么 | 本阶段作用 |
|---|---|---|---|
| **O1：自主任务与职责** | 固定2人 | 提出和修订任务、接受责任、转交、协调、集成与验证 | 共同参照条件 |
| **O2：多成员自主组织** | 首轮固定4人 | 同O1，并允许自然形成临时协调者和子团队 | 检查多成员运行与组织变化 |
| **O3：自主人员组织** | 初始2人，有容量上限 | 是否增员、给新成员什么工作说明、何时等待、退出或替换 | 动态组织目标 |

O2首轮用4人，是为了与O3的容量形成清楚的参照，不意味着4人最佳；也不要求先把3人、4人、5人全部逐一做完才能进入O3。

**无需等待固定4人取得显著优势，才允许测试动态人数。**只要基础运行合同可靠，O3的小规模冻结模型实验可以紧接着开展。

## 2. 任务和职责继续由模型产生

共同根目标可以列出功能、输入输出、兼容和交付要求，但不能预先生成“接口开发”“消费者实现”“测试验收”三个执行任务，再等待模型认领。

建议使用下面这条边界：

| 系统规定 | 模型决定 |
|---|---|
| 哪些功能和质量必须成立 | 如何分解或集中完成 |
| 谁能访问什么、工具有什么副作用 | 需要向谁索取信息、共享什么 |
| 任务提案、接受、转交的操作语义 | 谁承担什么、何时改变责任 |
| 版本、冲突、测试和提交规则 | 哪个成果值得采用、谁来检查 |
| 成员容量与团队总预算 | 是否需要新增成员、保留谁 |
| 公平调用机会与真实事件送达 | 得到机会后工作、等待还是调整计划 |

这与详细理论中的定义一致：职责最初不预设，但经真实创建、接受和转交形成后，可以进入成员后续观察；禁止的是外部提前给出分工答案，而不是禁止模型记住已经形成的职责。ID_VTDO_理论基线_自主组织完整修订稿_V1.3_202…

任务板也不应变成新的手续负担。**允许模型不建立复杂任务图就直接工作，任务数量不是成绩。**同样，任务责任与文件访问权限需要区分，不能因为某文件跨越两个任务，就机械禁止合法的集成或修复。

## 3. 动态成员的最小合同

建议首轮O3采用以下**待冻结的有限设置**：

- 初始2名中性成员。
- 同时活动成员最多4名。
- 累计出生最多6名，包含初始成员。
- 全体共用一个episode预算，不随创建、退出或重建而增加。

累计出生上限与活动上限分开，是为了允许有限替换，同时避免通过不断重建会话取得额外资源。这不是最佳团队规模的假设。

| 事项 | 建议规则 |
|---|---|
| 谁能发起增员 | 任一当前成员，不预设永久经理 |
| 新成员能力 | 同一冻结actor、同一工具能力，不注入“专家权重” |
| 新成员职责 | 来自发起成员实际生成的说明，以及后续协商 |
| 初始信息 | 公共根目标、合法公共材料、明确授权的交接内容 |
| 私有历史 | 不自动复制整个团队或其他成员的私有会话 |
| 工作副本 | 默认公共基线；采用其他固定快照须有显式授权和版本记录 |
| 等待／退出 | 等待可由真实事件唤醒；永久退出不自动复活 |
| 未完成责任 | 保留为待处理义务，不因退出而消失，也不由后台自动分派 |
| 身份 | 出生ID不复用，历史动作不因转岗或替换改名 |

新成员初始化说明是发起成员的输出、新成员的输入，不能被算成双方都生成了一遍。活动人数、累计出生人数和真正产生过输出的参与人数也必须分别统计。详细线路已经给出了这些生命周期边界。ID_VTDO_实验线路与最终主线_自主组织修订版_20261…

## 4. 系统如何运转，而不偷偷加入一个强经理

运行器只做机械执行：

\[
\text{可运行成员集合}
\rightarrow
\text{按固定公平规则给予机会}
\rightarrow
\text{模型行动}
\rightarrow
\text{执行工具并记录后果}
\rightarrow
\text{更新成员、任务和等待状态}.
\]

它可以送达真实消息、显示已经发布的任务状态、唤醒等待成员；不能判断“这时应该派一个测试员”，更不能替团队补写方案。

首轮建议仍采用**单模型实例、多个独立会话、顺序调用**。这足以检验任务与人员组织，不需要为每名逻辑成员常驻一份模型。相应地，这一阶段不声称真实并行加速。

# 六、建议的近期实验：先24条组织开发，再决定是否扩展

## 阶段A：只读行为复核，不新增模型工作

## 阶段C：首轮24条冻结模型开发实验

直接复用本轮已经实际使用过的四个schema开发root，不挑掉0/4的`order-totals`：

- `sc-command-set-v035`

|---|---:|---|---|

=\boxed{24\text{条经历}}.
\]

这里必须重新运行共同参照组，不能用旧v0.36成绩对比新O2/O3：新执行入口、成员管理和可能的信息呈现变化，都可能影响结果。

### 共同预算

建议首轮继续沿用每episode：

\[
128\text{决定},\quad128\text{attempt},\quad
500000\text{实际token},\quad32\text{次run\_tests}.
\]

不按人数翻倍，不给新成员额外额度，不按人均硬拆份额。24条的库存上界为3,072次attempt、1,200万实际调用token、768次测试；这些是**计划上界，不是预计会全部消耗**。

先手使用预登记轮转表；同为初始两人的O1/O3保持配对，四人条件在整个面板中轮转覆盖。所有条件使用同一冻结actor、采样设置、公开合同和验收规则。

### 这24条怎样判读

**不要求O3得分最高才算这一阶段完成。**

应分别回答：接口是否可靠；模型实际行使了哪些自由；工作质量与成本怎样变化；哪些功能没有被触发。

例如，模型始终不增员可以是合法行为，但这批结果就不能声称已覆盖真实动态招募。不能为了“演示成功”给余下槽追加“请创建第三名成员”的提示；那会成为新的引导条件。

# 七、任务也要逐步增加组织空间，而不是只增加人数

首轮24条用于运行和行为观察，但四个小root未必能体现多成员组织的价值。后续任务应提高**依赖与协调难度**，而不是重新堆叠复杂领域规则，把失败又变成业务计算能力问题。

建议仍保持软件工程同域，形成三类根目标：

| 任务约束族 | 可以产生的组织选择 | 不应预置的内容 |
|---|---|---|
| **轻协作控制** | 一人集中完成、另一人检查或不介入；动态组可以不增员 | 强迫拆成多个任务、最低消息数 |
| **交叉功能与多消费者一致性** | 自行选择接口先行、并行探索、串行适配、临时协调和集成 | A负责上游、B/C分别负责消费者 |
| **验证与后继维护** | 自行决定谁调查变化、谁修改、谁检查、是否替换或增援 | 永久测试员、必定错误的初稿、必须返工 |

根目标可以要求多个功能共同正确，但不能把“功能要求”编译成研究者预写好的执行岗位。正确初稿允许直接核准；简单任务允许不招募；合法集中完成也允许成为好结果。

### 后继冻结执行面板的规划示例

完成首轮接口开发后，可以考虑：

\[
12\text{新root}\times
4\text{条件}\times3\text{seed}
=144\text{次执行},
\]

四个条件为单执行者、固定2人、固定4人、初始2人的动态组。三个约束族各4个root，来源谱系和用途事前确定。

**这只是规模示例，不是已有任务清单，更不是足够统计功效的承诺。**单执行者组用于领域能力与组织开销参照，不是团队能力的严格上界；动态组与固定2人的比较主要检验开放人员变化，动态组与固定4人的比较则同时包含不同初始人数制度，解释不能混同。

本轮已用过的schema任务适合组织开发。尚未执行的TextFSM确认池应继续保留，不拿来调试新成员协议或反复改提示；否则它将失去原来的独立用途。

# 八、评价与消融：测工作后果，不奖励“看起来很协作”

## 1. 主指标不变，组织过程单列

| 层次 | 指标 | 不能怎样解释 |
|---|---|---|
| 工作结果 | 预算内完整合格交付、固定提交、内容／过程分项 | 未提交不等于所有可变代码均错误 |
| 执行成本 | 全体实际调用、输入输出token、测试、worker时间 | 提前失败便宜不等于高效 |
| 组织过程 | 被接受的任务、责任修订、实际响应、产物交接、阻塞处理 | 消息多、任务多不等于合作好 |
| 人员过程 | 活动人数轨迹、累计出生、实际参与、退出和替换 | 用人少不自动是好结果，用人多不自动是能力提升 |
| 表示覆盖 | 哪些实际关系可恢复、哪些仍有歧义 | 类别更多或映射率更高不等于算法收益 |

记录“重叠编辑”和“重复测试”时应使用中性名称。必要冗余可能有助于发现问题；冲突也可能被有效处理。是否值得，应结合最终质量与全部成本判断。

当前仍以终态最后固定交付为准。**不因旧轨迹首个提交之后花了很多token，就改成首个提交后强制停止。**首个提交不等于已经通过独立验收。

## 2. 第一轮最重要的对比，已经包含在三组里

O1与O3比较“开放人员变化”；O2与O3比较“全部人员预先在场”与“由团队决定何时增员”。没有必要在第一轮再加十种工具消融。

后续确需解释机制时，可以只增加两类受限对照：

| 消融 | 保持什么 | 检验什么 |
|---|---|---|
| 允许增员，但不开放后续退出／替换 | 相同模型、任务、总预算与其他工具 | 连续人员调整是否具有额外作用 |
| 初次任务形成后限制责任转交／修订 | 不预设初始任务，保留编程与交流能力 | 根据工作后果重新组织是否有价值 |

这些只是受限比较条件，**不代表主系统退回固定岗位**。它们也不能删除权限边界、读取隐藏答案或给实验组附加更强协调者。

## 3. 不按实际组织结果筛选有利样本

动态组的实际人数、任务数和组织方式是执行后的结果。不能只挑“恰好用了3人”的成功轨迹与固定3人比较，再称为公平主效应；也不能只在成功子集比较耗时。

主要分析按预登记条件、全部root和全部seed保留。12个root各3次执行，仍然不是36个独立业务问题；少量来源簇下，结论保持局部，不用大量成员事件制造虚假的统计样本量。

# 九、与ID-VTDO主线如何衔接：保留研究目标，不要求立刻恢复训练

这次调整改变的是**近期实验顺序**，不是把ID-VTDO改成一个只研究任务调度的项目。

后续关系应是：

\[
\boxed{
\text{冻结模型的自主组织运行}
\rightarrow
\text{可解释的组织经历与工作评价}
\rightarrow
\text{具备代表性的学习场景}
\rightarrow
\text{另行决定何时恢复经验分配研究}
}
\]

恢复训练之前，不需要证明O3普遍优于固定团队，也不需要让每个工具都频繁出现。需要的是：当前执行空间确实承载了要研究的组织行为，记录足以恢复真实经历，评价能区分不同工作的后果，规模和成本可以规划。

与此同时：

**旧13条支持属于旧精确情境、旧两成员协议和旧当前策略窗口。**不能复制其 \(b\)、支持频数或缓存到新O2/O3，假装更开放组织已经具有相同训练支持。

**local／peer继续作为有限产物关系字段即可。**这一阶段先把任务、责任、人员和产物关系完整记录，不必立即将每种组织拓扑都变成新的训练类别，更不必追求每类达到频数门。

**O3的动态训练测度仍待后续单独确定。**现在只保存足够的出生、参与、原始输入输出和版本记录，不为暂未开展的训练增加一整套强制接入门。

# 十、具体推进决定

我建议将下一轮收敛为以下边界：

| 项目 | 下一阶段安排 |
|---|---|
| 26次剩余方向试训 | 继续暂停 |
| 3次正式更新、48条旧独立确认 | 继续暂停，不自动接续 |
| v0.37缓存生产验证 | 暂停，保存有限资格与失败记录 |
| 模型选择 | 固定现有9B原common，不再搜索新模型 |
| 首要工作 | 只读组织行为复核、动态成员运行入口和有限CPU合同控制 |
| 首轮模型实验 | 待确认的24条冻结actor组织开发 |
| 主动开放 | 任务与责任修订、多成员临时组织、有限增员／退出／替换 |
| 保持不变 | 根目标、质量验收、信息权限、团队共同资源 |
| GPU范围 | 仅物理GPU3、4、5、7；没有其他卡回退 |
| 启动状态 | 本次仅审计与设计，不恢复队列或启动新运行 |

不将已撤销的累计GPU／worker／统一墙钟上限偷偷恢复为旧默认；通过**有限任务库存和明确单任务资源合同**约束本轮工作，原内存、磁盘和产物保护继续保留。当前四卡限制与取消状态已有独立记录。

**最终判断：本轮不是“训练没跑通，所以退回做环境”。训练已经跑通；现在应停止重复验证这一点，推进真正属于研究场景的自主组织选择。下一项有价值的成果，应是团队在不预设职责、不预设执行任务的情况下，自行形成并调整组织，而这些行为能够被真实执行、清楚记录并以工作后果评价。**
