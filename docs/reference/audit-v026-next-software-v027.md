# 二、v0.26说明了什么：应更换主载体，但不是否定数据分析领域

## 1. 新载体已经比旧的一次转发更真实

v0.26让maintainer准备源视图，consumer消费固定源版本并完成自己的聚合，最后还有复核要求。它不再只是提供者转发basis后退出。**这项结构改进应当保留。**

但实际结果仍在很早的位置停止：源端6次SQL执行成功，其中两份固定提交的表名、列名、行值和单位正确；消费端只有一次构建尝试且失败，提交和批准都是0。

所以，当前问题既不是“模型完全不会计算”，也不是“工作都完成了，只差一次批准”。**双方真正消费彼此成果、推进联合交付的行为仍然没有闭合。**

## 2. 严格合同与机械操作，正在遮蔽协作问题

两份内容正确的源提交仍不满足DOUBLE类型和显式SQL元数据关系要求。原要求公开且冻结，因此原评分应保留；但**没有在SQL里显式引用某张元数据表，不等于模型没有利用读过的规则**。这是当前规定的表示合同，不能推广为判断信息使用的通用标准。

另一个明显问题是运行余量：程序合法路线的最大prompt加输出预留后，仅剩4个token。实际32个角色终止中，26个达到决策上限，6个达到上下文上限。存在性路线通过，不能代表模型正常探索有足够空间。

我的判断是：

**当前实验同时在测业务计算、对象引用、请求绑定、表示格式和长链条闭合，却难以分辨协作组织的学习价值。**继续加几条SQL、几个强制引用或更多审批步骤，很可能使载体更复杂，而不使算法问题更清楚。

这不是“数据分析天然不适合协作”的结论，而是**当前具体载体的投入产出不再适合作为主线**。旧载体保留为历史结果、低结构复杂度控制和后续迁移对象，不再优先扩展。

## 3. 两个通信条件都为零，不支持继续研究哪种通信更好

normal与single_pass各0/8存在明显地板效应。它们还保留了共享产物和正式复核，single_pass并非没有任何协作。

因此，这轮能够支持载体与行为诊断，**不能证明通信条件等价、额外交流无用，也没有检验训练分配的作用**。恢复后的16槽与原中断尝试还应继续分开，不将恢复结果改写成原协议从未中断。

# 四、数据更换：采用软件工作素材，但不要把单人SWE题直接套成多人任务

| **接口生产者—消费者变更** | API、数据结构或异常语义共同约束两边代码 | 先协商再并行、上游先行、通过原型差异再协调 |

## 3. 用途划分必须先于任务派生

先区分接口开发、策略训练、贡献开发与独立确认，再构造需求组合和信息条件。按仓库、commit、issue、目标补丁及测试派生关系检查重合。

# 六、新的后续实验：软件迁移与分配器实现并行推进

建议将下一阶段暂称为 **“软件协作中的在线经验分配实验”**，按四个相互衔接的阶段执行。

## 阶段A：一次有限的载体开发，而不是新一轮通用模型训练

首批可采用 **4个开发情境、每个2次固定重复，共8条冻结参数联合经历**。这是建议的开发规模，不是效果研究规模或已授权运行量。

它只回答：

**模型是否真正读、改、测、交付；任务是否允许有后果的分工与依赖选择；这些行为能否回到原始成员动作。**

程序见证用于排除合同矛盾和必要步骤不可达，少量全信息单人诊断可以帮助区分编程瓶颈与协作瓶颈。**不要求团队必须先超过单人，也不要求模型达到稳定高成功率。**

先复用现有9B运行器。若连小型仓库的基本工作都不能完成，才单独比较一个代码适配候选，然后固定共同模型；不恢复无限模型搜索或无目标基础RL。

这一阶段同时完成软件有效性、工作依赖Mapper和一般配置接口，避免等待模型表现很好以后才开始写算法。

## 阶段B：当前模型产生真正可配置的训练窗口

正式采样前，根据开发阶段的产出与成本固定情境、重复数 \(M\)、频数门和预算。**不再把8或16视为天然足够，也不事后补采到凑齐。**

每个精确情境单独统计：

\[
M,\quad n_z,\quad n^+,\quad
v=\frac{n^+}{M},\quad
b_z=\frac{n_z}{n^+}.
\]

方法类别应反映实际的分工、依赖处理和集成路线，而不是某条消息有没有填写ID。不同初态、不同错误类型、不同参数窗口和程序路线不能拼池。

有一个真实可配置块，就可以研究局部作用，其他块和可信失败继续基础处理。**全部没有自由度时，这项有限配置试验按计划结束，不默认追加昂贵Q=B训练。**完整在线研究中的基础处理规则则保持不变，两类实验合同不能混淆。

## 阶段C：直接比较三种分配规则

| 方法 | 保持相同的部分 | 实际变化 |
|---|---|---|
| **B：基础 \(Q=B\)** | 当前经历、学习起点、基础损失与工作条件 | 不加组成干预 |
| **G：一般成员—轨迹元重加权** | 同类开发反馈、残余处理与可比外层预算 | 依据原始成员经历选择权重 |
| **I：ID‑VTDO第一阶结构化成员配置** | 同样的基础条件 | 利用工作类别、依赖和成员位置估计价值并选配置 |

第一轮先在相同合格分支与权重约束下比较G和I，避免“结构差异”与“允许重配的范围差异”混在一起。一般方法必须采用合理的候选与优化方式，不能故意让它在更高维空间里使用无效搜索。

各方法从相同actor、critic、两个optimizer和规定随机状态出发，用同一批当前经历更新。配置由预先定义的规则和开发反馈产生，不能由研究者看独立测试后手工挑选。

**首版ID‑VTDO不必先有大图网络。**可以用少量可解释类别、低维结构特征和有限配对试训；没有跨窗口校准标签时，就明确采用有限差分，不宣称已经有可靠的结构贡献预测器。

同时把C与N落实为可检验选择：

- **C**：移动训练比例对更新后开发工作效用的影响；
- **N**：当前真实支持中的覆盖不足，不是价值或不确定性的替代；
- **约束**：保持任务与成员份额、失败残余、比例界及相应锚。

旧两类别原型可以作为测试参照，但不直接解除所有硬编码、再称通用算法已完成。新接口需要明确输入、候选、探测预算、未知处理、求解和回退。

# 七、怎样防止下一轮再次偏离主线

## 1. 不把“软件任务成功了”当成分配成功

需要分别报告：

| 层次 | 实际问题 |
|---|---|
| 功能与交付 | 两项需求和组合行为是否正确，是否形成固定补丁并保持回归？ |
| 协作过程 | 责任怎样形成，伙伴信息是否被使用，依赖和冲突怎样解决？ |
| 学习结果 | 更新后是否做得更好？ |
| 分配增量 | 是否比相同条件的B和G做得更好？ |

消息数、任务领取速度、测试次数和早停只作诊断。一个团队少做工作却失败，不能称为高效；一个团队多做必要回归，也不能因此受罚。

同样，**串行服务两个会话能够研究分工和依赖，不自动证明真实并行加速。**

## 2. 先证明第一阶规则，再逐项验证复杂机制

优先两项消融：

**所有成员共用权重，对比成员条件化权重；只有信息关系，对比加入任务、责任和产物依赖。**

之后才研究联合探测、图选对与随机选对、去N或对应锚。不能用越来越复杂的机制掩盖主比较没有增量，也不要求第一轮一次完成所有消融。

## 3. 总成本与正式更新次数分开

固定材料、相同正式更新预算，适合检验配置机制；要声称学习效率，还要计入采集、候选试训、开发执行、正式更新和外层计算。

基础组省下外层成本，可以按预定规则做更多有效训练，不应被要求空等。**上一轮SQL推理只用了2.47 GPU小时，也不能推断软件训练会便宜：代码搜索、测试、上下文和反向成本都会改变。**

因此，不建议现在直接给一个新的“总56例／72例／144例”来替代旧计划。先完成有限软件开发验证，再以实际任务清单和单窗口成本冻结正式分配实验规模；独立评价预算必须预留。

## 最终推进建议

**现在应当结束“不断增加载体复杂度、但仍没有真正配置对照”的循环。**v0.26说明双方承担产物还不够：若运行负担和固定手续占据主要行为，任务仍可能无法提供有辨识力的协作经验。

下一阶段应围绕一个小而完整的目标：

> **在真实代码与测试上，让模型自行分工、处理依赖和集成；由当前经历形成有效方法支持；再由完整分配规则选择权重，与基础分配及一般元重加权比较更新后的独立工作表现。**

软件工程是为了让协作差异更容易落到实际后果上，**不是新的研究终点**。最终要证明的仍是：**我们的分配规则是否比强基线更有效地利用这些经历。**
