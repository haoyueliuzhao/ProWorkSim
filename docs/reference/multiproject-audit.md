## 审计结论

**v0.5 可以保留为“单世界、单写者、有限工作语义下的状态一致性与恢复基线”。但我确认了 E2 中一处测量缺陷：正式确认的两种引用表示被直接比较，导致合法确认被显示为 false；两个模板共同误测，仍然通过了相等性检查。**这需要修正 E2 的相应结论，但不应因此否定 K1–K3、其他实验或推倒现有内核。

结合刚才的讨论，下一轮的主线应调整为：

> **从“两个模板共用内核”，推进到“一个先于项目存在的世界，能够装载、运行和结束多个项目”。**

真实金融工作流数据应作为后续的**领域校准、项目实例化和设计反馈依据**，不是另起一个采集工程，也不应成为当前世界核心解耦的前置阻塞条件。

# 二、对 v0.5 各组实验的判断

## 1. K1：阶段回执的语义已经得到实质修正

当前 `execute_transition()` 确实分别计算：

\[
\Delta_{\text{Apply}},\quad
\Delta_{\text{Derive}},\quad
\Delta_{\text{Net}}
\]

不再仅按字段属于基础区还是投影区，反推变化发生在哪个阶段。失败阶段也保留 `failed_phase`、`attempted_delta`，没有把尚未完成的阶段伪装成空变化。

本次实际检查了两个关键例子：

**Apply 修改投影、Derive 不修改**：回执正确记录为 Apply 有变化、Derive 无变化。

**Apply 修改后被 Derive 改回**：两个阶段均有变化，但净变化为空。

因此，上一轮提出的回执口径问题可以关闭。报告进一步说明“阶段快照不等于最终持久化状态”，也避免了新的混淆。

## 2. K2／E1：指定视图的缓存无关性，有对应实现与实验依据

`derive_condition_view()` 从条件历史和原始回复推导，`derive_current_work_view()` 从工作定义、提交、审阅、替代关系及条件视图推导；兼容 blocker 不再反向决定条件状态。

原始回复保存接收时相关事实，重建时重新匹配，而不是把过去缓存的 PASS 当成不可质疑的真值。

我在独立夹具中执行了正常、删除、改坏和重复重建四种条件，结果一致；也检查了后来替代工作不会反向改变先前回复到达时的满足关系。

**这支持的是指定派生视图可重建，而不是任意字段丢失后都能恢复世界。**E1 归档明确限定了缓存路径、检查点和比较范围，因此其 48/48、288/288 应按这个边界保留。

## 3. E3：有界探索比增加手工样例更进一步，但不是完整状态空间证明

报告中的数字加总一致：

\[
2+11+39+110+284=446
\]

\[
58+340+1229+3512=5139
\]

\[
914+738+3487=5139
\]

独立参考模型使用另一种 ledger／tuple 表示，没有通过被测的工作状态查询函数计算期望结果，这一点可以从脚本核实。

一个需要继续保持精确的表述是：

> **446 个状态是参考比较投影下的可达代表，不是包含所有原始消息和观察历史的完整世界状态穷举。**

脚本按参考模型投影去重，并在该范围内展开出边。被排除的文件系统、新请求创建、更多角色和更长序列，也明确写入了实验边界。

当前没有必要仅为了“更强证明”就把深度扩到 6 或 8。**下一轮增加多项目作用域后，再针对新增关系设计有界探索，比机械增加原状态机深度更有意义。**

## 4. K3／E4：提交与确认失败的区分是正确进展

`journal.py` 已经绑定操作身份、主体和请求摘要；同一身份不同负载会显式冲突。工具运行器也将已提交命令与随后发生的事件错误分开返回。

开发期发现的“事件已提交，却用旧状态恢复文件”问题，在冻结实现中已有针对性处理：提交后异常重新加载已提交状态，不再恢复提交前文件。

这正好说明，**进程退出与普通异常是两类不同的故障路径**。报告把十个 `os._exit` 切点与额外的 ValueError 探针分开，处理得合理；归档也保留了 `event_committed=true` 和确认错误记录。

不应由此继续追加断电、跨机和任意插件事务作为当前通过条件。

## 5. E5：七个语义负对照有价值，但不能替代测量函数自身的检查

按照报告，七个变异都实际激活并触发了预先指定的断言，而不是因导入或夹具异常退出。它们支持：

> 验收对这七种明确违反合同的行为具有敏感性。

但本次 E2 反例说明，**“被测内核会不会错”与“测量函数能不能正确读出世界事实”是两个层次。**后续负对照应补充针对测量层的小型检查，而不是只在内核实现上植入错误。

# 三、新发现：E2 的正式确认字段存在共同误测

## 1. 具体问题

`semantic_projection()` 使用了：

```python
bool(attestation) and attestation.get("reference") == ref
```

但两边引用的表示不同：

```python
# 正式 attestation 中的引用
{"object_id": "policy", "version_id": "v1"}

# 适配器提供的引用
{"artifact_id": "policy", "version_id": "v1"}
```

二者语义上指向相同对象版本，直接比较字典却不相等。这个表达式确实存在于冻结实验脚本中。

公开 E2 的 `ConfirmGrant` 比较结果也出现了：

```text
formal_confirmation = false
coordinator_signed = true
worker_has_exact_version = true
```

而比较仍被标为通过。

## 2. 本次实际复现

我使用原始 `confirm_credential()` 创建合法确认，再执行 E2 的原比较表达式，得到：

| 检查 | 结果 |
|---|---|
| 内核 `registered_applicability` | **PASS** |
| E2 原 `formal_confirmation` | **false** |
| 经 `VersionRef` 规范化后比较 | **true** |
| 改成错误版本的负对照 | **false** |

这说明：

**正式确认事实并没有丢失；错误发生在实验如何读取和比较这个事实。**

E2 的跨模板通过条件是“两侧投影非空且相同”。因此：

\[
\text{共同误测为 false}
\Rightarrow
\text{两侧相等}
\Rightarrow
\text{比较通过}
\]

但：

\[
\text{相等}
\not\Rightarrow
\text{正确测到了正式确认}
\]

该通过条件可直接在实验脚本中核实。

## 3. 定级与影响

我把它定为：

> **E2 正式确认维度的测量缺陷，需要修正复核；不是整个内核失效，也不推翻其他比较维度。**

原来的 31/31 是当时脚本实际输出，应保留；但不能再不加限定地将其解释成所有预定制度关系都已正确测量。

## 4. 最小修复方案

先规范化精确引用，例如使用 `VersionRef.from_mapping()`，但不能放宽成只比较对象名。

随后，在相等性之外增加**独立预期条件**：

| 情况 | 预期 |
|---|---|
| 合法签发、对象版本与登记一致 | 正式确认存在 |
| 缺少 attestation | 不得显示为已确认 |
| 对象相同、版本错误 | 不匹配 |
| 签发关联不一致 | 不匹配或不可确认 |
| 历史确认已不适用于新工作 | 正式历史仍存在，当前适用性另行判断 |

优先对原检查点副本重算投影，再在新目录复验相同的四条适配器轨迹。**不需要重采样模型，也不需要因这一脚本修复重做所有无关实验。**

# 四、结合刚才的讨论，当前首要缺口已经不是“恢复还不够强”

v0.5 回答的是：

> 在现有世界结构中，同一事实能否获得一致解释？

但它还没有回答：

> **这个世界是否先于项目存在，能否持续承载多个项目？**

代码中，`WorldSpec` 仍然强制包含单个 `ProjectSpec`，并直接携带经营领域的 `facts` 和 `assumptions`；运行观察返回单个 `state["project"]`。

对象写入也仍要求对象已经注册：

```python
artifact = state["artifacts"][artifact_id]
```

它提供的是新版本写入，不是通用的运行中对象创建接口。

因此，当前应准确定位为：

> **具有共享内核的两个单项目世界实现。**

不能直接升级为：

> 一个可持续运行、可以装载多个项目的世界核心。

这是架构扩展尚未完成，不是对 v0.5 已声明实验的反例。但**它应当决定下一轮开发方向**。

# 五、建议下一轮主线：World Core 与多项目承载

下一轮不建议新增第三个行业，也不建议继续把大部分精力投入更深状态探索或更多故障切点。

建议聚焦一个明确命题：

> **在同一世界中，项目可以独立加入和结束；人员、对象、时间与历史持续存在；项目之间只通过显式的共享、授权和工作关系产生影响。**

## 1. 先分开四种生命周期

| 对象 | 生命周期由什么决定 |
|---|---|
| **世界** | 运行器启动、暂停、快照与恢复 |
| **项目** | 业务目标、当前义务、归档或结束条件 |
| **工作项** | 执行、等待、提交、审阅、替代 |
| **Episode** | 某次评测或训练选取的起止边界 |

尤其不能继续默认：

```text
项目完成 = 世界完成
项目归档 = 删除其对象与人员
episode 结束 = 清空世界历史
```

世界没有活动项目时可以处于空闲状态，之后仍能装载新项目。

## 2. 建议新增的核心对象

| 对象 | 最小职责 |
|---|---|
| **WorldSpec / WorldState** | 世界身份、主体、应用、对象注册表、时间与事件政策；允许项目集合为空 |
| **ProjectInstance** | 项目目标、参与者、工作空间、义务、交付要求及项目生命周期 |
| **WorkContext** | 世界、项目、工作、需求版本、用途和期间的完整上下文 |
| **ObjectRegistry / Workspace** | 世界级对象身份与项目内别名；支持运行中创建产物 |
| **ScopedGrant** | 主体在项目、工作或对象范围内的访问权与制度权力 |
| **ProjectPackage** | 将领域材料、任务合同和局部事件部署到世界，而不是重建一套世界机制 |

这不意味着立即引入微服务、新数据库或复杂规则语言。可以继续沿用现有 JSON 状态、不可变文件与单写者提交协议。

## 3. 不能只把 `project` 改成 `projects`

真正需要解除的是下列耦合。

**身份与项目分开。**同一个人在 A 中执行、在 B 中审阅，仍是同一个主体；不能因为切换项目就自动获得另一种权限。

**对象身份与文件名分开。**A 和 B 都可以有 `report.json`，但它们不能指向同一个底层对象，除非明确共享。

**读取与共享分开。**跨项目采用一个成果，不代表能够访问上游项目的全部私有资料。

**项目状态与世界状态分开。**A 完成后，B 的未到回复、共享文件和合法历史不应被清空。

**当前版本与采用政策分开。**同一数据更新，可以要求 A 更新，也可以不影响明确固定历史快照的 B。

其中，现有授权函数主要按主体、权力、主题和工作节点判断，没有显式项目参数。多项目接入时，应使用完整作用域或无歧义的世界级工作引用，而不是继续依赖容易重复的本地 `work-1`。

## 4. 保留“可执行错误”，不要把核心做成审批流水线

多项目扩展后，模型仍应能写错公式、提交不充分的草稿，或者选择一种不优但合法的解决方式。

内核负责身份、引用、作用域和正式效果；领域与独立评价负责内容正确性。

而且，并非所有工作都需要经理批准。**是否需要确认、什么内容可以自行假设、哪些工作只需交付，不应被统一写成所有项目必须经过的审批链。**

真实金融工作流后续接入时，恰好可以帮助我们校准哪些制度约束是真实必要的，哪些只是当前模板的方便设定。

# 六、下一轮实验方案

建议先采用**一个世界、两个项目、少量共享对象、单写者交错执行**。只在生命周期实验中动态加入第三个项目。模型、GPU 和训练仍非必要。

下面是拟议实验，不是已经冻结或执行的结果。

## M1：世界独立存在与项目装载

### 要检验什么

> 世界可以先启动；项目启动和结束不会隐式重建或销毁世界。

### 实验过程

从零项目世界出发，建立主体、文件服务和一份世界级材料；装载 A、B；完成或归档 A；继续推进 B；最后在同一世界中加入 C。

| 应检查的对象 | 预期 |
|---|---|
| 世界身份、主体身份、逻辑时间 | 保持连续 |
| B 的工作与事件 | 不因 A 完成而丢失 |
| A 的历史提交和共享成果 | 继续存在并按权限可引用 |
| C 的启动 | 不依赖重新编译整个世界 |
| 非法项目包 | 整体拒绝，不留下半个项目或残留授权 |

**项目结束不等于撤销它产生的一切事实。**哪些待处理义务取消、哪些成果继续共享，需要有明确项目合同。

---

## M2：跨项目名字、职责和访问隔离

### 要检验什么

> 相同名称不导致对象混淆；同一主体的不同职责不导致权限串用。

故意让 A、B 使用相同本地任务名和显示文件名，例如都包含 `work-1` 与 `report.json`。

同一个工作人员在 A 负责执行，在 B 负责审阅。成对测试：

| 正向情况 | 对应反向情况 |
|---|---|
| A 的负责人确认 A 的工作依据 | 同一确认不能应用于 B 的同名工作 |
| 明确分享某个版本后能够读取 | 未分享前拒绝访问 |
| B 的审阅者批准 B 的提交 | 不因在 B 有权就批准 A 的工作 |
| 相同命令重试返回原结果 | 不同项目的新命令不被误认作原命令 |

命令摘要需要覆盖实际工作上下文，作用域由可信会话检查，不能由模型随意填入一个项目 ID 就扩权。

同时要避免不现实的承诺：**同一人员已经合法获得的信息，不会因为切换项目自动遗忘。**技术权限、上下文展示和人员保密规范应分别建模。

---

## M3：共享输入、不同采用政策与定向影响

### 要检验什么

> 同一世界事件可以对不同项目产生不同的合理后果。

建议建立一份世界级资料：

- A 按“当前适用版本”使用；
- B 按“固定版本／指定时点快照”使用。

资料发布新版本后，A 可能出现更新义务或不适用标记；B 的历史分析则可以继续成立。

再分别测试：

**只改变 A 的批准依据**，不能使 B 的无关工作失效。

**只改变某个交付的受众要求**，不能自动重写共同模型。

**没有共享关系的局部修改**，不应传播到另一个项目。

本组应明确区分：

\[
\text{事件发生}
\rightarrow
\text{关系或义务变化}
\rightarrow
\text{通知送达}
\rightarrow
\text{工作人员实际修改}
\]

前面三步可以由环境机制产生，最后一步不能由后台代做。

对于无法确定的影响，允许记录“需要检查”或 unknown，不要求内核凭空完成领域判断。

---

## M4：运行中创建工作产物与合法解决方式

### 要检验什么

> 项目不是让工作人员填写编译器预制的几个文件，而是允许其实际组织工作并创造对象。

项目只规定产物角色、类型和要求，不预先列出所有中间文件名。工作人员通过合法工具创建一个新数据表、草稿或分析文件，形成版本、引用和提交。

应至少验证：

| 情况 | 判断原则 |
|---|---|
| 创建事先未列名的合法产物 | 允许，并进入统一版本与权限体系 |
| 一份文件与两份分拆文件均满足合同 | 不因路径不同而强制只有一种通过 |
| 额外中间草稿 | 不自动视为错误 |
| 覆盖另一项目的私有文件 | 拒绝 |
| 冒用对象身份或伪造确认 | 不产生正式效果 |

**这一组对摆脱狭窄模板特别重要。**否则世界即使拥有完整审批和恢复机制，仍可能只是一个可靠的“预制产物填空器”。

本轮不必开放任意宿主机路径或完整代码执行。动态对象创建可以先限定在受控工作空间、明确文件类型和现有工具能力内。

---

## M5：多项目交错与有限恢复

### 要检验什么

> 项目可以共享世界演化，但不相互污染；新增共享关系仍遵守已有提交协议。

安排 A 等待回复时 B 继续工作；期间出现共享输入更新或 A 的需求修订；旧回复随后到达。

重点检查：

**A 的旧回复不解除 B 的条件。**

**B 已完成的正式结果不因 A 的修订被回滚。**

**一个 episode 结束不清空另一个项目。**

**同一人员切换后仍绑定正确工作与需求版本。**

恢复测试只新增与多项目变化直接相关的少量切点，例如共享变化提交前、提交后但结果尚未返回。没有必要把原十个切点机械乘以所有项目与模板。

恢复后应比较项目注册、作用域授权、对象别名、采用关系和原始观察，而不只比较最终 `complete`。

# 七、真实金融工作流数据怎样支撑后续设计

这一部分应当保留，但不能反客为主。

**不建议把下一轮改成爬虫、访谈、数据规模或标注流程建设。**当前应做的是保留合适的接入合同；后续有实际可用、可授权的金融工作材料时，用它们校准世界。

## 1. 接入的应是工作证据，而不仅是金融数字

例如，未来取得一个模型更新工作包，可能包含：

**业务委托、原始模型、修改版本、适用材料、口径确认、审阅意见和交付要求。**

但如果只有财报和最终工作簿，就不能据此编造“经理曾在某日批准”“分析师曾因某事返工”等未观察到的过程。

原型本来就明确区分了合成经营模型与真实投行 DCF/LBO 的专业复杂度；后续真实材料的作用是校准和完善，而不是把原有合成模板重新命名为真实工作。:chatgpt-content-reference{index="19"}

## 2. 建议的接入路径

\[
\text{真实工作材料}
\rightarrow
\text{对象、角色、事件与要求的映射}
\rightarrow
\text{项目包}
\rightarrow
\text{可观察后果的检验}
\rightarrow
\text{设计缺口修订}
\]

这里需要区分三类改动：

| 发现的差异 | 应优先修改哪里 |
|---|---|
| 文件布局、字段表达、材料格式不同 | 渲染和工具适配层 |
| 财务定义、期间、单位、计算或交付标准不同 | 金融领域模块与评价合同 |
| 多项目共享、角色授权、工作交接无法表达 | 通用世界核心 |

**不能为了适配一份真实模型，就把该模型的特定公式塞进通用内核。**

## 3. 保留真实、推断与合成的边界

后续工作包至少标记：

- 哪些内容与事件由原始材料直接支持；
- 哪些是工程重建或业务解释；
- 哪些是为了模拟而增加的情境；
- 哪些关系仍然未知。

真实轨迹也不应成为唯一合法解法。它可以证明某条过程曾经发生、某些约束存在，却不自动证明其他顺序和方法都不专业。

**数据的价值在于约束和纠正模拟器，而不是要求模拟器复刻一条固定历史。**

# 八、建议的推进顺序与本阶段完成标准

| 顺序 | 工作 | 通过后意味着什么 |
|---|---|---|
| **G0** | 修正 E2 引用投影，增加独立预期条件 | 该维度测量重新可信 |
| **G1** | 零项目世界、双项目装载与结束 | 世界不再依附单一项目 |
| **G2** | 项目作用域、动态产物和显式共享 | 多项目共存具有真实机制 |
| **G3** | 定向影响、交错与少量恢复检查 | 新增关系仍服从同一内核 |
| **后续校准** | 接入实际可得的真实金融工作材料 | 检验外部合理性并完善实现 |

其中，真实数据接入不是采集数量门槛；模型训练和更大规模评测也不是 G1–G3 的验收依据。

当前主要风险已经不只是“某个状态字段可能错”，还包括：

> **持续把一个单项目模板做得越来越可靠，却始终没有形成能够容纳新项目、新对象和共享工作关系的世界。**

因此，应把 v0.5 的一致性工作沉淀下来，而不是继续无限延长它。

---

## 最终推进判断

**本轮最需要修正的是 E2 的测量缺陷；最需要调整的是下一轮的架构重心。**

不必因为 E2 一项共同误测而否定整个阶段，也不应因为 247 项测试和五组实验满足既定条件，就认为世界核心已经足够通用。

下一轮应集中证明：

\[
\boxed{
\text{世界独立存在}
+
\text{项目动态装载}
+
\text{对象运行中生成}
+
\text{跨项目作用域与共享后果}
}
\]

真实金融工作流后续进入这套结构，用来校准对象、规则和工作过程，而不是替代世界核心建设。

**这样，ProWorkSim 才会从“有可靠内核的窄场景模拟器”，走向“能够承载不同专业项目、支持动态能力评测与后续学习的工作世界基础”。**
