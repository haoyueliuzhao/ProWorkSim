# 二、这些反复出现的问题，其实指向同一个架构缺口

回看历次问题，它们并不是互不相关的工程漏洞。

| 已出现的问题 | 背后缺失或不明确的底层语义 |
|---|---|
| 指南允许的引用被评分器拒绝 | 工作要求及其解释应有一致来源 |
| 正文依赖正确、元数据依赖错误 | 内容声明、采用关系和实际来源不是同一对象 |
| 一次回复解除所有阻塞 | 行动效果应有明确作用域 |
| 工作与发布相互等待 | 任务状态与事件条件需要联合演化语义 |
| 最新 basis 被当作适用 basis | “最新”是版本关系，“适用”是带上下文的关系 |
| 无批准时仍使用隐藏假设算目标 | 后台存在某值，不代表业务上已经确定该值 |
| 新需求影响旧批准 | 历史事实与当前制度效力需要分开 |

我的推断是：

> **目前我们更多是在为具体情境补充“正确行为”，还没有统一规定一个工作世界中，哪些对象存在、哪些关系成立、哪些事件能够改变它们。**

这正对应你提出的物理引擎类比。

物理引擎不能靠“物体 A 碰到 B 时的特殊处理”“物体 C 落地时的特殊处理”无限扩展。它需要先有状态、作用、约束和演化规则。

同样，ProWorkSim 不能主要依赖：

```text
遇到 scope → 特殊处理
遇到 memo → 特殊处理
进入第二阶段 → 特殊处理
出现 unavailable → 再特殊处理
```

而应让这些现象由更少、更稳定的规则组合产生。

# 三、模拟工作世界的底层核心是什么？

我的建议是把它定义为：

# **工作世界语义内核**
**Work-World Semantics Kernel**

它的核心不是“安排工作步骤”，而是：

> **定义工作对象及其关系，并规定有身份、有权限的主体采取行动后，世界中什么会改变、什么必须保持、谁能观察到变化，以及这些变化具有怎样的业务效力。**

可以将它概括为三个相互连接的部分：

\[
\boxed{
\text{对象与信息的因果语义}
+
\text{组织行为的制度语义}
+
\text{角色观察的信息语义}
}
\]

### 1. 对象与信息的因果语义

例如，修改工作簿会产生什么版本；计算依赖哪些输入；输入变化会影响哪些成果；哪些文件内容不会自动改变。

它回答的是：

> **做了什么，实际改变了什么？**

### 2. 组织行为的制度语义

例如，谁有权确认假设；什么行动算正式批准；批准针对哪个版本；需求变化以后，什么义务需要重新履行。

它回答的是：

> **这个行动在组织中算作什么，产生什么责任或效力？**

### 3. 角色观察的信息语义

例如，谁可以看到材料；收到旧版本回复是否能访问新版本；一个角色已经读过什么；某个尚未确认的条件是否真的可得。

它回答的是：

> **谁在什么时刻，可以根据哪些信息行动？**

**三者缺一不可。**只有文件与工具，是办公沙箱；只有流程与权限，是流程管理系统；只有角色对话，是故事模拟。我们需要把它们连接成一个有明确状态变化规则的工作世界。

## 四、物理引擎的类比成立，但不能照搬成“社会物理学”

建议用这个类比来确定分层，而不是假设专业工作存在一套完全统一、已经被掌握的自然定律。

| 模拟物理系统中的概念 | ProWorkSim 中的对应物 |
|---|---|
| 物体及其状态 | 数据、产物、需求、凭据、工作义务及其版本 |
| 作用与事件 | 编辑、读取、询问、回复、确认、提交、撤回、需求变更 |
| 状态演化规律 | 行动前置条件、直接效果、派生影响和默认保持 |
| 约束 | 身份、权限、对象一致性、版本与时间约束 |
| 传感器与观察 | 各角色可见的文件、消息、工具结果和状态 |
| 控制策略 | 模型工作人员的决策 |
| 场景与目标 | 项目实例、任务委托与交付要求 |
| 测量与评分 | 世界外的独立评价 |

这里最容易犯的错误是把“专业人士通常应该怎么做”，写成“世界只允许这样做”。

例如：

**没有权限的分析师不能创造正式经理批准**，可以是系统必须维护的规则。

但：

**分析师可能忘记检查假设，可能写错公式，可能过早提交**，这些必须能够发生，否则模拟器已经替工作人员完成了判断。

因此，底层核心需要区分：

\[
\text{行动能否执行}
\neq
\text{行动是否合规}
\neq
\text{结果是否正确}
\]

一个可以运行的错误公式，应该产生真实错误结果；一个有权审阅者，也可能接受数值错误的成果。世界负责记录后果，评价器负责判断相应质量。

# 五、底层内核与领域、组织、任务之间必须分层

我不建议把所有规则都塞进一个“通用内核”。更合适的是以下结构：

\[
\mathcal W
=
\operatorname{Instantiate}
\left(
K,\ D,\ N,\ S_0,\ \Pi_{\text{staff}},\ E
\right)
\]

这是建议的形式化，而不是仓库当前已经实现的接口。其中：

| 层次 | 应当包含什么 |
|---|---|
| **通用内核 \(K\)** | 身份、对象引用、版本、行动效果、事件顺序、信息可见性 |
| **领域模型 \(D\)** | 业务对象、计算关系、量纲、产物语义、领域约束 |
| **组织制度 \(N\)** | 谁能够确认什么、批准什么，授权范围与工作责任 |
| **初始世界 \(S_0\)** | 当前材料、人员、需求、历史工作与未完成义务 |
| **工作人员策略 \(\Pi\)** | 如何检索、询问、分析、编辑和提交 |
| **外部事件过程 \(E\)** | 材料到达、需求变化等事件的生成条件与分布 |

独立评价 \(Q\) 另外定义，不直接决定世界应该产生什么结果。

### 对当前代码的具体含义

`growth_delta` 属于经营分析领域，不应该成为通用需求修订的核心参数。

“只有名为 `manager` 的角色可以确认”是当前组织配置，不应该成为所有工作世界的普遍规律。

`model/memo/note` 是当前领域产物角色，不应该成为通用工作节点能够交付的全部对象。

这些限制目前确实存在于 `basis.py`、`lifecycle.py` 与 `workflow.py` 中。**在单一有限模板内它们不算错误；但要建设稳定底层，就应逐步把它们从通用机制里移出。**  

此外，**模拟规则内部自洽，并不自动说明其金融含义符合专业实践。**当前经营模型既然明确标为合成教学式模型，就应继续按这个范围使用；领域真实性需要另外校准，不能由内核正确性替代。

# 六、建议优先构造的七条底层规则

这里不是要求先建立庞大的定理证明系统，而是先明确那些不应因场景变化而反复改写的语义。

## 规则一：行动具有显式效果，未受影响的对象默认保持

每种行动需要定义：

**直接修改哪些对象，可能引发哪些派生状态变化，以及哪些对象必须不变。**

例如，回复一项 scope 请求，可以改变对应消息、访问授权和阻塞状态，但不应改变另一个任务的阻塞，也不应修改工作簿数字。

可以用一个受限的保持条件表达：

\[
S'|_{\overline{F(a)}}=S|_{\overline{F(a)}}
\]

其中 \(F(a)\) 是该行动明示的业务影响范围，包括允许的派生影响。

日志、时钟和由时间推进触发的事件应单独计算，不能简单写成“失败动作不会改变任何状态”。

**这一条能统一解释定向阻塞、选择性更新和不自动改写下游文件。**

“动作改变什么、其余事实怎样保持”本身就是行动表示中的经典问题；情境演算相关研究已经围绕状态变化与保持建立形式化方法，可以借鉴，而无需把每种工作情境重新写成例外。:chatgpt-content-reference{index="11"}

## 规则二：事实、主张、假设与批准不是同一种对象

例如：

```text
财报记载收入为 X
分析师认为明年增长率为 g
经理批准使用 g 作为本次情景假设
工作簿实际使用了 g
工作簿计算正确
```

这五句话表达五种不同关系。

经理批准一个假设，只使它获得**当前工作中的制度效力**，不会使它变成已发生事实；工作簿声称采用新依据，也不证明单元格真的更新。

这正是 `old_basis` 与 `relabel_only` 两类错误需要分开的原因。v0.3 已经在向这一方向实现，下一步应将区分提升为通用类型，而不是仅用于 `basis` 文件。

## 规则三：正式效力只能由具备相应权力的行动产生

底层应表达：

\[
\operatorname{CanConfirm}
(\text{actor},\text{subject},\text{scope},t)
\]

而不是：

```python
actor == "manager"
```

“确认假设”“批准交付”“提供资料”“转交工作”分别需要什么权力，由组织制度配置。

同时，应区分**技术访问控制**与**行为规范**。系统能够禁止无权限者签发正式批准；但“审阅者应当认真检查所有内容”通常是评价其行为的规范，不应被模拟器自动执行成完美审阅。

否则我们会得到一个不会犯错的组织，而不是可用于学习工作的环境。

## 规则四：可访问、已观察、相信、采用与得到支持必须分开

建议至少保留：

\[
\text{可访问}
\neq
\text{已观察}
\neq
\text{声明采用}
\neq
\text{验证支持}
\]

至于模型是否“相信”某件事，不能仅凭读取日志就判定。

世界内核可以记录模型实际被提供了什么、调用了什么；它不应声称已经掌握模型内部认知状态。

访问授权也应针对具体对象与版本。收到 basis v2 的旧回复，不应顺带获得 basis v3 的访问权。

这方面可以借鉴 W3C PROV 对实体、活动、责任、使用和派生关系的区分。该规范还明确指出：一个活动使用过某个实体，并不充分说明其输出一定由该实体派生。:chatgpt-content-reference{index="12"}

## 规则五：适用性是带上下文的关系，而不是一个全局标签

更基础的表示应是：

\[
\operatorname{Applicable}
(c_v,\ q_v,\ \text{work scope},\ \text{purpose},\ t)
\]

即某个凭据版本 \(c_v\)，相对于某个需求版本 \(q_v\)、用途和时刻是否适用。

这样才可以自然表达：

**旧凭据对旧工作仍有效；新凭据不影响其他工作；相同数据可以支持不同情景；受众要求变化不必使分析假设失效。**

当前 `freshness.py` 已按工作要求检查批准，并明确选择共享产物对应的最近分析阶段。这适合当前有限模型；若以后一个产物同时服务多个有效工作，就不宜继续只返回一个脱离工作对象的全局结论。

因此，建议底层提供关系查询，界面需要时再生成 `current/stale/unknown` 摘要。

## 规则六：回复是一种事件，满足工作条件是另一种判断

收到消息并不等于问题解决。

回复可能提供了正确材料，也可能提供旧版本、来自无权角色，或者明确告知暂时不可得。

建议把状态演化拆成：

\[
\text{回复送达}
\rightarrow
\text{关联请求}
\rightarrow
\text{检查其满足什么条件}
\rightarrow
\text{更新对应义务}
\]

而不是“topic 对了就开放任务”。

当前 `blockers.py` 已经建立了这种方向上的匹配。下一步应将其从三种固定 blocker 类型，提炼成可扩展的“条件—回应—满足关系”。

还应注意：**某个角色目前无法提供信息，不等于世界永远不可能获得信息。**在当前不可得情境里结束 episode 是合理的；未来引入其他提供者或后续到达事件时，需要另行定义恢复机制，而不是直接把所有 unavailable 当成永久终态。

## 规则七：未知不等于错误，拒绝不等于世界失败

建议底层检查至少保留：

```text
PASS
FAIL
UNASSESSED
NOT_APPLICABLE
```

并区分三个层次：

**规格不可执行**：例如无入口的发布死锁，应在构建时拒绝。

**工作当前无法完成**：例如确认确实不可得，合理结果可以是阻塞。

**工作人员采取了不合适的行动**：例如明知没有适用批准，仍提交依赖该批准的正式成果。

v0.3.1 的 unavailable 补修，已经将这三类判断分开了一部分。尤其是，不再使用隐藏 scope 替业务上尚未形成的确认补答案，这是应当提升为内核原则的修复。

但这不意味着以后所有缺信息情况都禁止分析。某些任务可以明确允许条件化分析或自定假设；是否允许，应该由任务与组织契约说明，不能由评分器事后决定。

---

# 七、底层核心应如何驱动工作流，而不是被工作流绑死

这里需要对之前的架构作一项重要调整：

> **工作流图不再是世界的最高权威，而是项目目标、工作义务与依赖关系的一种组织方式。**

一个工作世界的演化可以分成：

\[
\text{真实行动}
\rightarrow
\text{对象变化}
\rightarrow
\text{关系与适用性变化}
\rightarrow
\text{新义务或原义务失效}
\]

例如：

```text
经理签发新假设
→ 新凭据及适用范围成立
→ 使用旧依据的当前交付不再满足要求
→ 产生修订义务
→ 工作者决定如何定位、修改和重新提交
```

这里不需要预先写死：

```text
下一步必须先读邮件，再读工作簿，再改 B4。
```

同时，也不意味着完全抛弃工作流图。已有 DAG、发布组和生命周期规则，可以继续表达固定前置关系；只是不应让它们代替全部世界语义。

这与 artifact-centric 的建模方向有可借鉴之处：GSM 将业务实体的信息模型与生命周期结合，用条件、事件、阶段和里程碑表达推进关系，并提供明确的操作语义，而不只描述一条活动顺序。:chatgpt-content-reference{index="16"}

**我们的增量需求是：再把模型实际行动、角色局部观察、允许发生的业务错误和可验证交付物接进来。**这不能只靠选定一个流程框架就自动获得。

---

# 八、一个具体的底层行动合同：`Reply`

为了避免“内核”停留在抽象口号，建议每个核心行动都有明确合同。以回复为例：

```text
Reply(request_ref, response_kind, evidence_ref)
```

| 合同部分 | 应明确的语义 |
|---|---|
| 输入 | 实际存在的请求、回复类型、可选证据／凭据引用 |
| 执行条件 | 身份被绑定；请求存在；允许向该接收者发送这些内容 |
| 直接效果 | 保存回复、关联请求、记录送达 |
| 授权效果 | 仅按规则开放明确的凭据版本 |
| 条件效果 | 只有满足对应工作条件，才解除相关 blocker |
| 保持范围 | 无关工作、无关阻塞、其他版本权限、模型与报告内容不变 |
| 失败或不足 | 错版本、无权确认、不可得等分别记录，不伪装为满足 |

如果这是一条旧回复，那么“记录历史”和“开放旧凭据”可以成立，“解除新需求的阻塞”则不成立。

如果回复是 unavailable，那么它可以使“请求已得到回应”成立，却不能使“所需资料已取得”成立。

**一个行动同时产生哪些事实、不产生哪些事实，才是内核应该负责的内容。**

同样的定义方式可用于：

`Read`、`CreateVersion`、`Request`、`Confirm`、`DeclareAdoption`、`Submit`、`Withdraw`、`ReviseRequirement`。

不需要一开始设计几十种行动。先将当前确实使用的少量行动定义清楚，比增加更多主题情境更有价值。

# 九、后续实现方案：先做“内核化”，不做功能竞赛

## 第一阶段：先写清语义规约，而不是立即重构全部代码

建议先形成三份短而明确的规格：

| 文档 | 必须回答的问题 |
|---|---|
| `CORE_SEMANTICS.md` | 有哪些基本对象、关系与不可混淆的概念？ |
| `STATE_OWNERSHIP.md` | 每个状态字段由谁产生、哪些行动可修改、哪些只是派生结果？ |
| `ACTION_CONTRACTS.md` | 每个行动的前置条件、效果、保持范围和观察是什么？ |

这里特别需要明确**基础状态与派生状态**。

实际文件版本、实际消息、正式确认、实际提交属于基础记录；`freshness`、当前可执行工作列表、当前适用性等通常是派生结果。

派生结果应能由其依据重新计算，不能成为第二份独立、随意修改的“真相”。

## 第二阶段：从现有实现抽出一个窄内核

建议保留存储、文件工具和历史格式，逐步形成：

```text
core/
    types.py
    references.py
    transitions.py
    visibility.py
    rules.py

domains/
    operating_toy.py

policies/
    organization.py

adapters/
    files.py
    spreadsheet.py
    communication.py
```

这里的目录只是职责建议，不要求立即拆成服务，也不要求新建一种复杂规则语言。

核心的状态推进可以抽象为：

\[
S_{t+1}
=
\operatorname{Commit}
\left[
\operatorname{Derive}
\left(
\operatorname{Apply}(S_t,a_t)
\right)
\right]
\]

其中：

**Apply** 执行真实操作或明确的领域模拟，产生直接变化。

**Derive** 计算适用性、阻塞与工作义务等后果，不能偷偷修正文件。

**Commit** 维护身份、版本、引用等系统一致性，不以“模型业务答案是否正确”作为所有写入的硬门槛。

已有 `basis.py`、`blockers.py`、`lifecycle.py` 不必全部删除。可以先作为兼容适配，逐个迁移它们共有的机制。

## 第三阶段：把验收从“十个故事”提升为“规则及其组合”

保留当前十个情境作为回归，同时增加少量跨情境属性：

| 属性 | 核心检查 |
|---|---|
| 局部性 | 回复某项工作，不改变无关工作 |
| 历史保持 | 新批准和新需求不改写旧提交事实 |
| 版本隔离 | 授权一个版本，不开放其他版本 |
| 适用性 | 全局较旧的凭据，仍可能对特定工作有效 |
| 不可评边界 | 无适用确认时，不借用隐藏数值目标 |
| 幂等性 | 重复处理同一个已完成回复，不重复推进工作 |
| 组合一致性 | 需求变更、旧回复和撤回组合发生时，状态仍有明确解释 |
| 角色替换 | 更换员工标识、保持其权力配置，不需要修改核心分支 |

对互不影响的行动，可以比较不同执行顺序下的业务状态是否一致；对共享对象的冲突，则必须有明确排序或冲突规则。

不需要现在证明任意并发过程都正确。先覆盖当前允许的有限动作组合，但不要把每一个测试都写成实现代码的翻版。

## 第四阶段：用一个极小的第二模板检验抽象边界

主线仍保留经营分析世界。

另外可以构造一个非常小的“文稿审阅与发布”配置，复用同样的版本、授权、批准、回复和修订机制。它的用途仅仅是检查：

> **底层是否已经摆脱 `growth`、`model/memo` 和特定角色名称？**

这不是立即扩张成第二个 benchmark，也不需要大规模 API 试跑。

如果新增这种简单配置仍然需要在内核中加入“如果是文稿”“如果是另一个主管”的专用分支，就说明所谓通用核心还只是原模板的重新命名。

# 十、当前不应推进什么，以及什么才算这一阶段完成

当前不建议继续增加训练步数、扩展上下文效果实验或推动角色共同学习。这些接口已经有归档记录，暂时不应继续牵引架构。

同样，不建议优先追求更多文件、更长对话或更多行业名称。它们可能增加表面复杂度，却未必增加底层表达能力。

**这一阶段的完成标准，应当是：**

> 在一个明确限定的工作子域内，读取、修改、请求、回复、确认、采用、提交、撤回和需求变化，都具有一致、可组合的语义；正确与错误行动都能产生合理后果；新增情境主要通过对象、初始条件和规则配置表达，而不是修改内核。

这里还需要两种不同的检查：

**内在有效性**：这个模拟世界是否遵守自己声明的规则，是否自洽。

**外部合理性**：这些领域与组织规则是否合理代表目标专业工作。

前者可以大量通过程序检查；后者需要业务依据或有范围的专业审阅。**内核测试全部通过，不等于工作世界已经足够真实。**

---

## 最终判断

本轮修订已经提供了一批有价值的底层语义雏形，尤其是：

**批准不等于正确，最新不等于适用，回复不等于解除阻塞，最终合理终态不抹去先前错误，未知目标不应被当作已知答案。**

这些不应再被视为几个特殊情境的补丁，而应进入统一的内核定义。

所以，我建议保持 **ProWorkSim** 的总体名称，将当前阶段明确为：

# **工作世界语义内核构建**

先回答：

\[
\boxed{
\text{什么对象存在}
\quad
\text{谁能做什么}
\quad
\text{行动改变什么}
\quad
\text{哪些东西保持不变}
\quad
\text{谁能观察到什么}
}
\]

再在此之上生成项目、工作人员策略和工作任务流。

**真正值得优先构造的，不是更多“工作的故事”，而是能够让这些故事合理发生、持续推进并留下真实后果的底层规则。**
