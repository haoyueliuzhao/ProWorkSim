# 三、新发现：嵌套 JSON 冲突可能被文件顺序掩盖

## 1. 问题位置

`domains/work_product.py` 的 `_equal()` 对直接的布尔值和数值进行了区分：

```python
_equal(True, 1) == False
```

但对于字典和列表，最终使用 Python 容器的相等判断，因此：

```python
_equal({"margin": True}, {"margin": 1}) == True
```

评价器随后合并多文件 JSON，后写入的字段覆盖先前值。**如果前面的冲突判断漏掉了嵌套类型差异，最后一个文件就可能决定通过结果。**

## 2. 本次实际复现

建立一个已明确的来源接口：`source/v2` 中的 `rate` 是**数值 1**。

要求交付中的 `metrics.margin` 与该数值一致。两份实际 JSON 文件都正确引用、声明依赖并采用同一个精确来源版本：

```text
文件一：metrics.margin = true
文件二：metrics.margin = 1
```

其他工作范围、来源版本和采用快照均正确。

| 提交顺序 | 评价器记录的冲突 | 最终结果 |
|---|---|---|
| 布尔文件在前，数值文件在后 | 空 | **通过** |
| 数值文件在前，布尔文件在后 | 空 | **失败** |

这两个结果不应由文件顺序决定。**两份文件对同一路径给出了不同类型的内容，应当都被识别为冲突。**

本次同时验证了两个对照：相同嵌套数值可以通过；不同嵌套数值被拒绝。反例的实际文件、采用快照、两种顺序和完整评价结果均保存在审计包中。

证据层级是：**原始完整评价模块＋实际 JSON 文件＋显式状态夹具**，不是完整 ProjectSession 回放。WorldCore 的评价入口直接委托这个模块，没有额外的嵌套冲突检查。

## 3. 影响范围

这是一处**内容评价缺陷**，需要阻断“多文件嵌套字段冲突已被可靠检查”的扩展性结论。

但公开 N3 使用的是顶层 `margin/source_ref` 条件。本次反例**没有证明原六种策略条件均被错判，也不应将整个 N3 或 v0.7 改判失败**。

## 4. 最小修复

建议采用类型感知的递归 JSON 比较：

**对象逐键比较，数组按序比较，布尔值与数值始终分开；数值之间的等价政策沿用当前明确合同。**

同时要求冲突判定与提交顺序无关。不要借修复顺便引入未声明的深层合并、浮点容差，或者“挑一份正确文件即可通过”的新规则。

补修后，通过真实项目会话创建、提交两份文件作正反回归；保留原评价结果，新增评价版本。没有必要因此重跑旧 API 或所有无关恢复实验。

# 四、下一阶段的关键问题：新能力能否与既有生命周期真正组合

目前，世界已经能够生产一个成果，并让另一个项目消费它。下一步应当检验：

> **当成果发生变化、当前工作被修订或替代时，项目是否能够继续工作，而不是需要控制器重新装载一个“已经整理好”的情境。**

这里有两个优先检查的衔接点。

## 1. 项目别名与工作采用关系，不应是同一个可变对象

当前采用声明按项目别名保存，并绑定一组 `work_ids`；提交只收集覆盖当前工作 ID 的采用快照。需求修订则会创建替代工作 ID。

这意味着，下一轮需要优先验证：

**原工作已经采用 `input`，修订后新工作是否仍能在同一公开别名下合法建立新的采用关系？**

不能只测试“没有修订时把 v1 换为 v2”。也不能直接把旧采用记录改写成新工作的历史。

我没有在本次执行完整的修订后采用链，因此**不将它列为第二项已复现缺陷**；但从当前结构看，它是最值得先检验的组合边界。

建议分开四个对象：

| 对象 | 作用 |
|---|---|
| 项目内别名 | 指向一个世界对象，方便发现和使用 |
| 工作采用绑定 | 某项工作、某个需求版本实际采用了哪个版本 |
| 政策目标 | 当前合同允许或要求采用的候选目标 |
| 提交快照 | 本次提交当时采用的版本及要求，保持历史 |

这样，同一个项目可以有两项工作使用同一对象的不同版本，而不必不断创造新别名或修改旧记录。

## 2. 发布变化与工作义务之间，还需要明确规则

当前发布主要产生版本授权、通知和 `review_required` 标记，并不等价于已经形成一个可执行的新工作义务。源码中的 `_publish_shared()` 体现了这一有限职责。

下一阶段应明确：

**什么变化只需通知，什么变化需要修订当前工作，什么变化会在持续维护项目中产生后继工作，什么变化不影响固定历史任务。**

这些规则由项目或领域合同配置，内核负责一致执行。不能一律规定：

```text
出现新版本 → 所有下游工作失效 → 自动重开
```

同样，v0.7 已提交成果的目标是按提交时固定的。**单纯出现后续发布，不应追溯改判旧提交；只有明确的新需求或维护义务，才形成新的工作要求。**:chatgpt-content-reference{index="22"}

# 五、后续实验方案

建议采用两阶段推进，继续以**一个世界、两个项目、单写者交错执行**为基本范围。不增加行业，不恢复参数训练，也不先建设数据采集体系。

## 阶段 A：评价补修与工作绑定

### P0：多文件内容评价的顺序无关性

**命题：同一组交付内容的冲突与正确性，不由文件枚举顺序决定。**

覆盖嵌套 `true/1`、`false/0`、相同值、不同数值、数组，以及合法单文件和拆分交付。以明确预期判断，不只比较两个顺序是否相等——两个顺序共同误判也不能算通过。

本组先修复并回归相关 N1／N3 内容检查，不扩展其他工具。

### P1：需求替代后的采用与信息路线

**命题：工作被替代后，旧历史保持，新工作仍有明确、合法的资料获取与采用路径。**

建议成对检查：

| 条件 | 核心期望 |
|---|---|
| 未修订，只出现新发布 | 按原采用政策处理 |
| 新需求仍允许使用旧版本 | 不强制更新 |
| 新需求要求新版本 | 新工作能建立新的采用绑定 |
| 旧请求晚到 | 保留旧回复，不替新工作取得未授权凭据 |
| 相同来源别名用于新工作 | 不因旧采用记录而进入无法推进的状态 |
| 错工作或错项目更新采用 | 保持拒绝 |

信息路线也要区分**可重复使用的路线定义**与**针对某个工作版本的具体请求**。新工作不能只能使用旧请求，也不应为了取得相同类型的材料而重新安装项目包。

如果合同明确要求 `current_published`，工作人员不能仅通过自行声明 `fixed` 回避该要求；如果合同允许选择政策，则应尊重选择。**这项权限与合同关系要预先说明，不能由评分器事后补定。**

## 阶段 B：从状态变化到持续工作

### P2：事件驱动的工作义务

**命题：同一来源变化在不同工作阶段产生恰当后果，而不是始终进入固定的“第二轮”。**

从相同基础条件出发，分别在以下位置引入一次声明事件：

**读取前、读取后、产物完成但未提交、待审、已接受后。**

不要求这些条件最终状态相同，而是分别验证：

| 工作关系 | 合理后果 |
|---|---|
| 仅订阅更新通知 | 产生通知或需检查标记，不自动改文件 |
| 当前工作被正式修订 | 创建替代义务，旧提交历史保留 |
| 项目合同要求持续维护 | 产生明确后继工作 |
| 固定历史任务 | 不因无关新发布而重新打开 |
| 同一事件重复交付 | 不生成重复义务 |

建议先使用有限的项目规则：来源选择器、受影响工作范围、触发条件、效果政策和去重身份。**不要求自然语言模型临时判断所有影响，也不把“生成 work-2”写死在通用内核。**

### P3：多源成果与局部更新

**命题：一个工作能够组合多个输入，而不只是把单一来源值复制到 JSON。**

可以让 B 使用 A 发布的一个中间接口，以及一个保持固定的本地输入，完成一项明确的有限计算或比较。新增的是**输入汇合与局部变化关系**，不必新增复杂金融模型。

随后只改变一个来源，检查：

- 应处理的工作得到明确提示或新义务；
- 未变化来源及无关项目保持；
- 环境不替工作人员更新结果；
- 实际更新后，内容、采用版本和贡献文件依赖一致。

期望值使用预先声明的标量或独立参考计算，不调用被测表格引擎生成答案。至少保留两种合法文件或计算组织方式，避免把参考路径变成唯一解。

评价继续分开**上游正确性、下游忠实性和总体业务目标**。一个上游错误传播到多个结果，不应直接统计为多个独立的能力缺口。

### P4：公开会话中的等待、切换与继续

**命题：工作人员可以从公开界面承接多项有限工作，在等待、变更和切换之后继续执行。**

先用透明、有限的程序工作人员或规则调度器验证，不要求通用模型自主规划。它只使用 `tools/observe/call`，但不再限定为恰好一项当前任务。

本组应明确区分四类结果：

| 结果 | 含义 |
|---|---|
| 工作人员等待 | 策略决定暂不继续 |
| 世界条件阻塞 | 内核确实保存了未满足条件 |
| 预算耗尽 | 实验截断，并非任务不可完成 |
| 环境错误 | 工具、规格或运行机制有问题 |

关键情境是：**A 等待资料时 B 可以继续；新资料或新要求到达后，工作人员能回到正确的工作和版本。**

缺路线时可以报告能力缺口，不能虚构请求；有合法恢复路线时，应验证信息到达后的继续执行，而不只验证第一次退出为 `waiting`。

本组保存实际观察和工具返回，不能在事后根据最终世界重建工作人员“当时应该知道什么”。

# 六、实验边界与完成标准

建议先冻结并完成 **P0／P1**，再冻结 **P2–P4**。这样可以避免底层绑定语义尚未稳定，就同时增加事件与工作人员逻辑。

恢复实验只针对新增机制增加少量有代表性的检查，例如一次工作绑定更新或事件生成后继义务的提交边界；不把所有工具、项目和切点做笛卡尔积。

各组在运行前明确：

**允许的动作、合法替代路径、拒绝或等待出口、比较范围及独立期望。**断言数量由合同决定，不先设一个必须达到的总测试数。

这一阶段的完成标准应是：

> **一个变化事件能够沿明确关系产生恰当工作义务；工作人员通过公开界面取得资料并继续工作；新采用与新提交有清楚的工作上下文；旧文件、批准和观察保持；无关项目不受错误影响。**

这比“最终文件又算对了一个数”更接近当前要完善的世界核心。

# 七、真实金融工作流材料如何继续支撑
