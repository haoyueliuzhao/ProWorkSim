# 二、最明确的问题：不存在的工具名，不应自动等于执行完整性丢失

这是本轮需要优先修正的具体设计问题。

## 1. 源码确认了技术未知是怎样产生的

冻结`harness_sdk.py`中，在工具名不属于当前schema时，当前错误政策直接执行：

```python
self._fail(
    "model_permission_error",
    "Tool is outside this role's authorized gateway"
)
```

普通`model_format_error`有返回反馈后继续的路径，而这个错误会重新抛出，经运行器使整条episode被完整性边界阻断。**检查发生在实际执行该工具之前。**

本轮`work_done`的原始输出、身份、314个输出token和先前固定提交均已保存；工具不在授权列表中，因此没有产生相应世界动作。报告没有显示实际越权、隐藏信息泄漏或固定交付被破坏。粘贴的 Markdown (1)(10)

因此应区分：

> **“模型提出了错误动作，系统成功拒绝”与“系统执行边界已经失效”不是一回事。**

旧runner遵守原协议停止，是执行事实；但把这类普通模型失误一律定义为不可恢复的技术未知，会让可靠的工作记录丢失评价资格，并使后续干净槽受到连带影响。

## 2. 建议的新错误政策

| 情况 | 执行处理 | 新协议中的含义 |
|---|---|---|
| 工具名不存在、普通参数不合法，原始记录可信且执行前拒绝 | 不执行；保留输出、费用和拒绝；下一机会返回反馈 | **可恢复动作错误** |
| 明确的禁止能力或越权请求被成功阻断 | 权限不开放，保留违规事件 | 按冻结合同判定过程是否违规；不必自动等于记录未知 |
| 未授权效果真实发生，或身份、记录、结果、世界状态不可信 | 停止相关执行 | **真实完整性故障或不可判定状态** |

这不是放松权限。**不应把`work_done`自动改成`staff_done`，不做模糊匹配，不调用隐藏fallback，更不能让成员使用controller工具。**模型必须根据拒绝反馈，在新的真实机会中自行选择合法动作。

已生成错误输出仍消耗原机会与token；不是免费重试。普通拒绝也不能重置预算或抹掉过去的错误。

V1.3本来就明确区分：允许的工具输入错误与恢复，不天然使完整经历无效；实际读取隐藏答案、篡改评价器等禁止过程，则可能不能被最终成功补偿。ID_VTDO_理论基线_自主组织完整修订稿_V1.3_202…

## 3. 修订应当很窄，不再做一轮大规模资格

用原`work_done`输出做程序反例，检查：零工具执行、文件和提交不变、拒绝日志与费用保留、下一输入可见反馈。再覆盖提交前／后的未知名字、禁止controller调用、真正的越权效果、合法done及预算不重置即可。

**不需要再加载9B证明同样的错误分类。**也不要顺手放松tool-call身份错配、实际权限泄漏等其他边界。

原v0.39未知、停止和两个未启动槽不回改。新政策下的继续工作本来可能产生新行为，不能据当前固定树通过，就推定“若继续也一定成功”。

# 三、当前瓶颈已经从“有没有接口”转到“有没有形成协作策略”

本轮主实验没有任务、认领、责任转交或工作消息；没有成员主动增员；22条已执行经历全部出现多人修改相同生产路径。这些事实说明，当前主要行为仍是**多个私有会话各自推进整个问题**，而不是已形成清楚的互补组织。粘贴的 Markdown (1)(10)

但不能进一步解释为“模型不愿合作”或“没有合作能力”。目前有三个需要区分的假设。

### 假设一：软件模块有依赖，不等于成员有互补信息

当前交叉任务要求两个消费者使用共享API，但任何成员都能看到相同公共代码、拥有相同工具并实现全部模块。

这保证了任务不预设岗位，是正确的；同时也意味着**代码结构上的依赖，并没有自动转化为成员之间需要交流的信息依赖**。定向任务文档也明确，两消费者通过不能推出必须由不同成员完成。

### 假设二：每个会话都把目标理解成“我完成整题”

当前成员说明的开头是完成共同根合同，随后列出允许的组织行为。这给了自由，却不保证模型会主动形成团队层面的工作安排。

在接口诊断里，目标明确是创建、回信、替换，模型做到了；在业务任务里，组织动作只是可选工具，模型没有调用。这提供了**任务定位影响行为选择**的线索，但尚不是因果结论。

### 假设三：新增会话主要分走了有限执行深度

主实验每次实际调用平均约11,928输入token、12,160总token。外生七名成员合计使用78次调用、915,217 token，全部来自原共同预算。

新成员没有免费算力、专家权重或私有知识。它的潜在价值是独立上下文、专注调查或验证；代价是重新阅读、执行与整合。**如果没有分工与成果复用，单纯增加会话可能只是在重复解整题。**这是待检验机制，不能由聚合平均直接证明其造成失败。

# 五、建议v0.40：检验互补信息与共同工作定位，不再重复外生增员组

我建议保持人员自由度，但把实验变量从“再多一个人”改成**“成员是否拥有可复用的互补发现，以及是否明确理解共同交付”**。

## 1. 共同设置保持不变

所有新条件继续使用原9B的3/3完整common，冻结模型；初始两名中性成员，允许自主增员，活动上限4、累计出生上限6。

没有永久经理，没有预建执行任务，没有固定谁实现或验证。成员可以集中完成、交流、建立任务、重新分工，也可以始终不增员。

\[
\text{新反向}=0,\quad
\text{actor更新}=0,\quad
\text{critic更新}=0,\quad
\text{Contribution试训}=0。
\]

**不再加入X3外生出生，不重复已有birth／replacement诊断。**这并不是关闭动态人数，而是不再把“是否出现第三人”当成唯一研究问题。

## 2. 两个开发任务改为“承接已有工作”，而不只是又换一组空桩

建议基于已用的`record-views`、`record-catalog`准备两个具名的**承接态开发变体**：

公开根要求继续保留，初态不再全部是待实现空函数，而是一份存在少量真实兼容缺口的现有分支。世界准备阶段执行两组公开、可重复的检查，形成两份诊断，例如不同调用方对同一记录表示的冲突，或者目录更新与查询／报告的一致性问题。

必须明确：

**预置代码、原有缺口和初始诊断都是环境准备事实，不是当前模型已经完成的工作。**完整参考解留在验收侧，诊断只给实际失败与版本，不给正确补丁或分工方案。

这样更接近“接手共同项目中的已有工作”，而不是每个新成员都从相同空桩重新解整题。

不过，这仍是已有来源上的开发变体，**不是独立benchmark或新来源泛化测试**。初态变更也需重新命名和冻结，不能与旧root绝对成绩直接作收益比较。

## 3. 两个实验因素

### 因素I：初始技术证据的位置

| 条件 | 设置 | 要检验什么 |
|---|---|---|
| **I-shared** | 两名成员都获得两份公开诊断 | 共同完整初始事实参照 |
| **I-split** | 每人初始获得其中一份；归属按预定表轮换 | 互补发现是否引出索取、共享、复用或重新检查 |

两组的根要求、代码、工具权限和可运行测试相同。I-split中的信息**不是永久隐藏的答案**：成员可以通过消息取得，也可以自己运行公开检查重新获得。

这不是给A接口职责、给B测试职责。**初始掌握什么信息，与最后承担什么任务分开。**任何成员仍可集中解决全部问题，或者基于交流调整工作。

信息布局会改变初始prompt长度和取得信息的成本，这些都是条件效果的一部分，应全部报告，不能宣称只隔离了“纯交流收益”。

### 因素G：工作定位说明

| 条件 | 设置 |
|---|---|
| **G-base** | 现有任务与工具说明，仅统一必要错误政策 |
| **G-team** | 额外明确团队共同交付，以及由成员自行选择分担、复用、核查或集中完成 |

G-team可以采用如下语义：

> 最终评价的是团队共同交付，而不是每个人分别完成一份。请自行判断是否需要分担、共享发现、交叉检查或增员，并形成你们认为合适的工作安排。集中完成也合法；不要求任务、消息或成员达到某个数量。所有活动共享同一预算，系统不会替你们安排职责。

这没有提供“正确计划”，也没有强迫首轮发消息。但它比G-base更直接地引出组织意图，**所以必须称为明确的提示干预，不能冒充毫无引导的自然行为**。

如果只有G-team出现合作，只能说明该说明下行为被唤起，不能称为模型经过训练获得了协作能力。

# 六、怎样评价，才能知道协作真的产生了作用

建议保留**完整合格交付为主指标**，另设一个预定义的组织诊断：是否出现至少一条可核查的跨成员工作使用链。

这条链应包括：

\[
\text{具体事实或产物}
\rightarrow
\text{实际分享／发布}
\rightarrow
\text{伙伴实际输入}
\rightarrow
\text{相关修改或验证}
\rightarrow
\text{可检查的工作结果}.
\]

与最终固定交付闭合时再单列标识。只有消息到达、代码相同、任务ID或补丁引用，都不足以自动认定使用，更不是唯一因果贡献。

| 记录层 | 应当记录的事实 |
|---|---|
| 初始准备 | 哪些代码、诊断和测试结果由世界事先提供 |
| 成员工作 | 实际提出了什么、修改了什么、验证了什么 |
| 信息取得 | 哪条消息或版本进入了哪个实际selected输入 |
| 成果使用 | 后续动作与取得内容有什么可核对关系 |
| 最终结果 | 是否形成当前版本的完整固定交付 |
| 组织成本 | 全体调用、token、测试、重复探索及人数变化 |

特别注意：**环境提供的初始诊断不能算成成员自主发现缺陷；成员对它的分享、解释和据此行动，才是本轮行为。**

不需要立即重新设计一个庞大的Mapper，也不需要将每种组织拓扑都变成新类别。这一阶段先记录事实和有限关系；歧义部分保留未知，不统计训练支持 \(n^+\) 或 \(q/b\)。

# 七、对照结果应该怎样决定下一步

| 新观察 | 应当怎样解释 |
|---|---|
| G-team增加消息，但没有实际成果使用 | 组织表述被唤起，业务协作尚未建立 |
| I-split出现真实分享并影响后续工作 | 互补信息在当前场景中提供了协作作用空间 |
| 只有G-team下出现有效闭环 | 当前模型需要较明确的共同工作定位；不是参数学习 |
| 使用关系增加，但完整交付没有改善 | 下一问题是实现、验证与集成深度，不是继续增加消息或人数 |
| 集中完成更好、成员不增员 | 合法结果，不应按“缺少合作”判失败 |
| 多组仍无实质协作 | 保存当前模型和场景的负证据，不继续逐句改提示直到合作 |
| 某组出现可重复有效协作 | 在新开发root上预登记复验，再扩大结论 |

两个因素还可以分别报告配对效应与交互，但这里只有两个root，不能用16条就给出总体稳定性认证。实际人数、是否通信和是否成功都是执行后的结果，不能只挑“用了三个人的成功槽”比较成本。

**这一设计的目的不是让某个提示获胜，而是辨别组织行为究竟缺少什么条件。**它允许结果告诉我们：当前小任务集中解决更合适，或者仅靠提示还不能形成有效合作。

## 最终推进判断

**v0.39已经取得足够证据，结束“工具能否被调用、新成员能否工作”的重复验证。**它尚未证明团队会自发组织，而原未知工具分类又造成了本可避免的整批缺失。

下一轮最值得完成的是：

\[
\boxed{
\text{修正普通错误与完整性故障的分类}
\rightarrow
\text{引入真实、可复用的互补工作证据}
\rightarrow
\text{对照共同工作定位}
\rightarrow
\text{观察实际协作链与完整交付}
}
\]

**不再把“多一个人”当成协作本身，也不把“多说几句话”当成组织能力。**应当让模型在有实际作用空间的任务中，自行决定是否分担、如何复用伙伴工作，以及什么时候根本不需要增员。
