# 二、初版已经实现了什么：不是空架构，但仍是一个固定项目族

## 1. 最值得保留的是“真实状态链”，而不是八个模块名称

代码已经建立了以下实质关系：

**工作人员通过工具修改实际文件 → 文件形成新版本 → 提交绑定指定版本 → 审阅检查真实产物 → 后续事件产生新的工作。**

尤其是，`submit` 记录的是产物版本；提交后再次修改待审产物，会使原提交失效。审阅读取对应提交版本，而不是笼统检查“工作目录里现在看起来正确的文件”。这一点是真正的工作流基础，不是界面包装。

同时，业务审阅与独立评价已经分离。业务审阅主要检查可计算性和交付一致性，独立评价进一步检查数值、来源、依赖与扰动后的重算结果。**“审阅接受但独立判错”是当前设计允许的情况，不应当把它本身当作缺陷。**

## 2. 按课题的三个主体看，当前成熟度并不相同

| 主体 | 当前真实实现 | 审计判断 |
|---|---|---|
| **工作环境** | 真实 XLSX/JSON、版本、权限、邮件、逻辑事件、快照恢复 | 已形成可用的机制底座 |
| **工作人员** | 目标分析师可接真实模型；经理、审阅者和客户为固定条件策略 | 符合初版范围，尚不是多模型组织模拟 |
| **工作任务流** | 三种交付粒度、两种信息配置、固定的连续两阶段 | 是最小任务流实例，还不是一般的工作流空间生成器 |

源码中，`designer.py` 主要根据种子抽样财务数值和少量假设；`compiler.py` 根据交付粒度形成任务；第二轮由 `kernel.py` 中专门的 `requirement_change` 分支创建 `work-2`。

因此，当前准确的描述是：

> **一个可以真实执行、具有角色隔离与连续状态的合成经营分析项目族。**

还不能称为：

> 任意专业项目过程生成器，或者已经能够系统覆盖工作任务流空间的世界模型。

这属于**当前范围限制**，不是否定阶段 A 的理由。但它会决定下一版应该优先实现什么。

# 三、三个需要先修复的实质缺陷

## F1：可见指南允许两种引用，评分器只接受其中一种

### 代码中的不一致

`compiler.py` 生成的可见指南写的是：

```text
values.revenue or values.operating_margin
```

也就是备忘录可以引用收入或经营利润率的位置。

但 `validation.py` 的 `memo_citations` 检查实际要求：

```python
required=[("financials", "values.revenue")]
```

因此，经营利润率引用虽然位置合法、来源版本正确，仍不能满足这个检查。

### 实际复现

我通过原始工具完成模型更新、备忘录写入、提交和审阅，仅把备忘录引用设为：

```json
{
  "artifact_id": "financials",
  "version_id": "v2",
  "location": "values.operating_margin"
}
```

结果是：

| 项目 | 结果 |
|---|---|
| 工作簿数值与重算检查 | 通过 |
| 备忘录版本与指标一致性 | 通过 |
| 业务审阅 | 接受 |
| 独立评价 | **失败** |
| 唯一失败项 | **`memo_citations`** |

收入引用的正常对照通过。

### 为什么它是当前阻断项

这不是“专业质量要求太高”，而是**工作者看到的任务契约与后台判定不一致**。

进入训练后，它会造成：

\[
\text{合规行为}
\rightarrow
\text{错误负反馈}
\rightarrow
\text{数据误筛或课程误诊断}
\]

而且，上一轮已经修复过“额外要求模型引用”的同类问题；当前的回归测试保留了收入引用，因此没有覆盖“仅经营利润率引用”这一合法变体。:chatgpt-content-reference{index="11"}

### 建议修复

不要继续分别在指南和验证器里手写两套要求。新增一个结构化的证据契约，例如：

```text
CitationRequirement
  allowed_artifacts
  version_binding
  required_all_of
  required_any_of
  allowed_locations
```

**同一个契约生成可见要求，也配置验证规则；参考答案与隐藏结果仍然不暴露。**

当前 memo 按已公布的二选一要求做兼容修复；short 任务中“模型股价位置＋指定披露 EPS 位置”的同时必需条件保持不变。

如果未来决定收入、利润率必须同时引用，那属于**新的任务要求**，不能只改后台评分器后追溯判旧交付不合格。

## F2：备忘录正文与依赖元数据可以矛盾，却仍被判为正确

这是对“持续工作世界”更关键的问题。

### 当前存在两份依赖记录

备忘录正文有：

```json
"source_versions": {
  "financials": "v2",
  "model": "v2"
}
```

产物版本元数据中另有：

```json
"derived_from": [...]
```

目前，备忘录评价检查了前者，却没有检查后者是否与其一致；而环境的陈旧状态传播使用的是后者。

### 实际复现一：清空元数据依赖

通过合法的 `write_file` 工具写入内容正确的备忘录，同时传入：

```json
"dependencies": []
```

结果是：

| 检查 | 结果 |
|---|---|
| 正文 `source_versions` | 正确绑定 financials v2、model v2 |
| 版本元数据 `derived_from` | **空列表** |
| 业务审阅 | 接受 |
| 独立评价 | **全部通过** |

随后，再通过工具修改实际模型输入，股价确实由：

```text
25.93957 → 25.955941
```

发生变化，但该备忘录的：

```text
possibly_stale = false
```

仍未改变。正确记录依赖的对照备忘录，则被标为陈旧。

### 实际复现二：普通省略参数也会出问题

这不只需要显式清空依赖。

`write_file` 省略 `dependencies` 时会保留旧版本的依赖。于是可以出现：

```text
备忘录正文：financials v2 / model v2
版本元数据：financials v1 / model v1
独立评价：通过
```

这一普通遗漏变体也已复现。省略参数保留旧依赖是现有 `_dependencies` 的行为。

### 为什么它是当前阻断项

问题不在于“工作者能够错误填写依赖”——工作环境应该允许真实错误发生。

问题在于：

> **评价确认的是一套依赖，后续项目运行使用的是另一套依赖，而两者矛盾的产物仍获得完整通过。**

如果据此筛选训练数据，模型可能学到：只要正文把版本写对，就不必维护真正影响后续状态的依赖记录。

这直接削弱了课题最重要的对象：**交付物能否在后续工作中持续使用，先前行动是否留下正确的工作后果。**

### 建议修复

对当前模板，最低限度需要：

**模型**验证适用披露版本；
**备忘录**验证适用披露版本和本次提交模型版本；
**正文版本绑定**与上述必要依赖一致。

同时区分三种不同信息：

| 信息 | 含义 |
|---|---|
| 工作者声明的依赖 | 工作者声称成果使用了什么 |
| 工具读取历史 | 工作者实际访问过什么 |
| 验证确认的依赖 | 产物满足任务所必需且可核实的输入关系 |

**读过一个文件，不代表成果一定使用了它。**不要为了补齐依赖，就自动把所有读取对象写成“真实使用来源”。

错误依赖可以继续作为工作者错误被保存，但不能通过完整交付检查。修正后的依赖应驱动后续失效传播，且仍不能自动改写下游文件。

## F3：百分号通过字符串替换处理，破坏公式优先级

### 代码原因

`Spreadsheet.value()` 将百分号后缀直接替换为：

```python
parts.append("/100")
```

然后交给 Python AST 解析。这个转换没有保留“百分号作用于前一个操作数”的结构。

### 实际复现

我通过原始表格工具写入并读取以下公式：

| 公式 | 应有结果 | 当前实际结果 |
|---|---:|---:|
| `=2/50%` | 4 | **0.0004** |
| `=2/(50%)` | 4 | 4 |
| `=10%^2` | 0.01 | **0.001** |
| `=(10%)^2` | 0.01 | 约 0.01 |

例如，第一行被转换成：

```text
2 / 50 / 100
```

而不是：

```text
2 / (50 / 100)
```

### 为什么它是当前阻断项

初版明确声明支持百分号和幂，因此这不是要求它实现尚未承诺的完整 Excel 功能。:chatgpt-content-reference{index="17"}

同时，工具观察、缓存写回和多项验证都依赖这个计算器。其错误可能使正确公式得到错误观察或反馈。

### 建议修复

**继续保留受限表达式计算器，但需要真正解析受限表达式结构。**

将 tokenizer 输出转为带有后缀百分号节点的表达式树，显式处理括号、幂和算术优先级，而不是继续增加字符串替换。

验收只需覆盖声明的子集，包括等价式测试、跨表引用、ROUND 边界和显式错误处理；**不需要因此引入完整 Excel 引擎作为本轮通过条件。**

## 三类缺陷对历史结果的影响，必须逐项判断

以上反例证明当前实现存在缺陷，**不证明历史 43 次模型调用或 37 条候选 SFT 记录全部失效**。

例如，公开的真实备忘录同时包含收入和经营利润率引用，因此 F1 不直接推翻这个公开样例。

是否受 F2、F3 影响，需要检查对应提交的依赖元数据和实际公式。当前公开 manifest 只包含部分成果的版本与哈希，不能替代完整历史状态。

正确处理方式是：**保留原交付字节和原评价，在修复后新增评价版本进行复核，而不是重新让模型生成一遍后替换历史。**

# 四、哪些地方不应判成初版失败

## 1. “28 项测试通过”不能证明没有上述缺陷，但也不必否定测试价值

已有测试确实覆盖了真实文件修改、错误公式、硬编码扰动、权限、旧备忘录返工、待审版本失效等关键机制。

本次反例说明的是：**测试没有覆盖契约的等价合法表达与跨表示一致性**，不是整个测试套件毫无价值。

后续应补的是这类反例，不是单纯追求更高测试数量。

## 2. 固定经理和审阅者，是合理基线

当前的经理回复和审阅策略虽然简单，却有明确的可见信息与权限边界。这有利于判断目标模型的行为变化。初版也没有把这些规则角色描述成已经训练的智能工作人员。:chatgpt-content-reference{index="21"}

不建议下一步立即让所有角色改用模型并共同训练。那会同时引入任务分布、反馈质量和沟通行为的变化，使实验更难解释。

## 3. 经历编译已经实现，但还不是完整训练链路

`learning.py` 确实筛选业务接受、独立通过的区间，保留原请求与响应，将历史消息设为零监督权重，并排除规则基线和测试 fixture 的正向 SFT。

但这仍是**结果条件化的候选监督选择**，不是每个中间决策都已被证明正确。缺失的 token IDs 和行为概率没有被伪造，RL 导出也明确标为尚不能直接进行严格 on-policy 训练，这个边界是正确的。:chatgpt-content-reference{index="23"}

因此，当前不应说“训练模块没做，所以阶段 A 失败”；同样也不能说“导出 37 条记录，所以阶段 B 已经完成”。

## 4. 简单金融模型不等于金融专业训练数据

本轮应沿用作者明确声明的合成计算模型，不将它升级为完整 DCF/LBO 审计。:chatgpt-content-reference{index="24"}

不过，下一阶段需要明确训练目标：当前材料首先适合检验**工具使用、版本维护和连续工作机制**。要声称金融专业能力收益，还需要独立核验领域口径，而不能只因为文件名包含估值，就把其中的计算关系当成规范金融知识。

# 五、后续实现的主轴：不是扩增种子，而是让“结构”成为可生成对象

当前课题最重要的下一步，并不是再生成几千个不同数值的世界。

源码中的课程标签有六类，但其中 `scenario` 与 `recalculability` 都映射到相同的 `file/mail` 配置；这些标签主要改变抽样配额，并没有自动产生新的工作结构。代码也明确说明没有额外注入新的压力机制。

所以，下一版应从：

```text
种子 + 交付类型 + 信息模式
```

推进到：

```text
项目结构 + 产物依赖 + 信息分布 + 事件规则 + 实例数值
```

## 1. 保留现有底座，抽出五类结构对象

| 新增对象 | 解决的问题 | 建议内容 |
|---|---|---|
| **`WorkflowSpec`** | 当前工作顺序写死在代码里 | 工作节点、依赖、终止条件 |
| **`WorkNode`** | 工作义务与特定 `work-1/work-2` 绑定 | 责任角色、前置条件、目标、交付要求 |
| **`EventRule`** | 后续工作只靠专用事件分支生成 | 触发条件、状态约束、允许变化、需求修订 |
| **`ArtifactContract`** | 验证规则固定在 `model/memo` 名称和字段上 | 语义角色、必需依赖、期间／单位／一致性约束 |
| **`LayoutMap`** | 业务语义与 `Inputs!B2` 等位置耦合 | 语义字段到文件、工作表、单元格或 JSON 位置的映射 |

这些先用 dataclass 和 JSON 即可，不需要微服务、复杂数据库或自由执行代码的生成器。

尤其应区分：

> **共用任务契约，可以防止要求与评分漂移；共用同一套答案计算实现，则不能证明独立正确性。**

不能为了减少重复代码，把生成、执行和验证都变成同一个函数的不同包装。

## 2. 环境内核不再直接理解“第二轮财务任务”

建议形成这样的代码边界：

```text
kernel.py
    身份、权限、工具动作、文件提交、状态持久化

workflow.py
    工作节点状态、依赖满足、交接与新增义务

events.py
    受约束的事件处理器

domain/operating_toy.py
    当前经营分析模板与计算语义

contracts.py
    证据、产物、交付与评价要求

renderers/
    依据语义和布局生成实际文件
```

当前模板通过兼容适配保留下来。这样，新增项目结构主要改变规格和模板，而不是不断向 `_drain_events()` 添加新的 `if revision == ...`。

## 3. 首批只增加少量“真正不同”的结构

我建议优先实现下面四类，而不是立即追求几十个行业场景。

| 结构 | 与初版相比，新增的本质要求 |
|---|---|
| **链式更新** | 披露 → 模型 → 备忘录，作为现有机制基线 |
| **分叉同步** | 同一模型影响两个交付物，需要分别维护一致性 |
| **选择性失效** | 一个变化只影响部分成果，需要判断更新范围，不能全部重写 |
| **信息协调与真实返工** | 口径缺口或版本冲突需要正确角色确认；审阅依据实际成果而非固定剧情 |

这里的关键验收不是“又多生成了四组题”，而是：

**改变依赖结构，所需工作会随之改变；只改公司名和文件名，任务的业务含义不应改变。**

对于每种结构，保留透明的工具层可行性见证，但不把它作为唯一合法路径，也不把它的成功率当成目标模型能力。

---

# 六、工作人员和工作环境应怎样继续扩展

## 1. 先统一工作人员接口，再增加模型角色

建议抽象：

```text
StaffPolicy
  observe(role_visible_state)
  decide()
  propose_action()
```

第一种实现继续使用当前确定性策略。后续增加模型版本时，只替换表达与决策策略，不让模型绕过权限或直接修改后台事实。

需要保持三个边界：

**角色能知道什么，由环境决定。**
**角色能批准什么，由权限决定。**
**角色如何表达和选择行动，才由模型决定。**

这样可以单独比较规则经理与模型经理，而不是连任务口径和审批语义一起变化。

## 2. 不应优先增加文件数量和自由对话长度

当前环境的小规模不是首要缺陷。更重要的是增加**有业务意义的信息分布与依赖**。

例如，把一个必要口径交给另一个有权确认的角色，比随机增加五十封邮件更有研究价值；增加一个真正依赖模型结果的下游成果，比复制一份无关报告更有意义。

## 3. 上下文优化可以做，但应作为运行框架变更单独记录

`run_model()` 会持续附加完整观察，而观察又包含项目和工作记录；这会使连续项目上下文不断增加。

可以改为“初始全量观察＋后续增量事件与版本通知”，并增加按需读取接口。

但应保留两个限制：

**不能事后把旧请求重写成更短的请求，再说那是模型实际看到的上下文。**
**减少 token 是否影响成功率，需要单独测量，不能用当前单谱系试跑直接估计一般收益。**

实现说明对当前上下文成本也已经作了类似限定。:chatgpt-content-reference{index="28"}

# 七、真正接入训练前，应补齐什么

## 1. 将“一个完整工作经历”作为明确对象

建议新增 `EpisodeRecord`，至少记录：

```text
初始世界快照
项目／任务／需求版本
目标模型 policy_version
实际模型调用与工具动作
提交及其绑定版本
全部评价与业务审阅结果
最终状态、停止原因、预算消耗
```

进一步把当前容易被一个 `passed` 混合的状态拆开：

| 状态 | 回答的问题 |
|---|---|
| `artifact_valid` | 数值、文件与依赖是否满足已验证要求？ |
| `business_accepted` | 世界内部审阅是否接受？ |
| `explanation_assessed` | 专业解释是否真的经过评价？ |
| `supervision_status` | 哪些模型输出可以作为何种训练目标？ |

这样，即使技术检查通过，也不会把明确尚未评估的专业充分性自动升级为金标。

## 2. 先做训练适配的最小实证

下一阶段不能只增加一个 `train.py` 文件。至少需要完成：

**真实 tokenizer 渲染 → token 级 loss mask → 有效 loss/backward → 参数变化 → checkpoint 保存与加载 → 新模型再次进入同一工具环境。**

这个结果只能说明训练链路成立，尚不是泛化收益。

同时，DeepSeek API 返回一个模型名称，不代表当前工程拥有该模型的可更新权重。应选择具有训练权限的目标权重，并分开实现 `ModelBackend` 与 `TrainerBackend`，不要把推理接口和训练后端混为一谈。

## 3. 保留候选监督边界，处理项目权重

当前一条 SFT 记录对应一次模型输出，不是一个完整项目。公开摘要中 continuous 的候选调用比 short/file 多，反映的是不同工作量与轨迹长度。

后续训练必须明确：优化目标按项目、工作项、调用还是 token 加权。

否则，“连续项目数据有效”可能只是因为它在训练中贡献了更多监督权重。

没有必要现在宣布某一种权重必然最优；**先冻结一种与实验问题一致的规则，并记录实际消耗。**

## 4. RL 接入不应跳过行为记录契约

现有 RL 导出保持 `on_policy_training_ready=False` 是合理的。

进一步训练需要明确策略版本、采样设置、真实 token 与行为概率，以及环境消息与目标模型输出的边界。不能凭现有 JSONL 就宣称完成了严格的在线策略优化。

有限的自生成成功轨迹训练可以先做；如果目标模型没有足够成功支持，可以增加明确标记的指导数据，但不能伪装成目标模型独立探索所得。

# 八、后续实验必须避免的一个关键混淆

**当前 `short/file/continuous` 不能直接作为“连续项目是否优于独立任务”的对照。**

它们同时改变了：

- 工作义务数量；
- 备忘录交付要求；
- 文件修改与持续状态；
- 模型调用和上下文长度。

这些差异来自当前任务定义，不是一个孤立的连续性因素。

后续至少区分两个问题。

### 问题 A：历史上下文是否有帮助？

保持第二阶段的实际世界快照相同，比较保留历史上下文与重新开始上下文。

这测的是**上下文继承的作用**，不是完整项目过程模拟的全部价值。

### 问题 B：项目过程产生的训练经历是否更有价值？

匹配来源、工作目标、交付物、工具与预算，比较连续项目经历与拆开的独立任务经历，并明确独立条件的起点如何形成。

这才逐渐接近课题的核心命题。不能简单拿两道短题与一个包含额外报告和返工的长项目比较，然后把差异全部归于“连续工作流”。

此外，当前种子谱系划分只能防止同一实例的变体跨组，**不能证明未见工作结构的泛化**。下一版应同时记录来源、模板、拓扑、布局和角色信息配置，并分别设置实例保留与结构组合保留条件。当前 `lineage_split` 本身只根据种子派生谱系进行划分。

# 九、建议的实施顺序与验收条件

| 阶段 | 核心改动 | 本轮应证明什么 | 暂不要求什么 |
|---|---|---|---|
| **v0.1.2：契约修复** | 修复 F1/F2/F3；评价版本化；补反例测试 | 已声明语义不再被具体反例推翻，原机制矩阵仍成立 | 新任务族、更多角色、训练收益 |
| **v0.2：结构化任务空间** | 抽出工作网络、事件规则、产物契约和布局映射 | 新结构主要通过配置生成，而不是修改内核；依赖变化产生真实工作差异 | 任意虚拟公司、无限自由生成 |
| **v0.3：经历与训练适配** | EpisodeRecord、token 级编译、最小参数更新 | 数据被真实消费，模型能保存、重载并继续工作 | 稳定泛化、闭环优越性 |
| **后续效果研究** | 匹配的连续／独立、静态／反馈课程对照 | 新机制带来可归因的学习收益 | 所有角色同时自进化 |

还建议在近期补两项较小的运行记录改进，但不把它们与三个已复现缺陷混为一谈：

**工具调用完成判断按 `call_id + tool_call_id` 定位。**当前 `_finish_tools` 使用整个历史中的裸 `tool_call_id` 判断是否已回复，后续接入不同后端时应避免跨响应 ID 重用导致跳过动作。这里是静态审阅发现的风险，本次没有把它计为已动态复现的缺陷。

**区分逻辑模型调用与底层请求尝试。**当前重试发生在后端内部，成功返回后才保存 call；失败与重试尝试应单独记录，避免以后把完成调用数当成全部请求数或完整成本。未知消耗保持未知，不估造。

## 最终推进判断

**这版不是需要重写的失败原型，而是已经建立了真实工作状态链、但尚未封闭关键数据契约的机制原型。**

本轮可以确认：

> 当前模板中的真实文件操作、角色边界、版本绑定、条件审阅与两阶段连续工作能够运行。

当前还不能确认：

> 通过现有验证器的所有交付，都具有一致的来源依赖和正确的受限公式语义，因此可以直接作为可靠的训练正例。

所以，**第一优先级是修复三个已经复现的契约问题；第二优先级才是把固定的 `work-1 → work-2` 转成可生成、可组合、可独立评价的工作结构。**

这比立即扩增种子、增加模型角色或接入大型 RL 框架，更直接服务于你的核心研究问题：**怎样模拟一个能够产生真实学习经历的专业工作任务流空间。**
