# v0.19：执行吞吐优化与独立世界双副本采集

依据用户在 v0.18 部署后要求“调整优化”。原 H1 的执行源、48 槽和成绩保留。2026-09-27 11:59 后已核对 v0.18 后继仍在等 H1 且 jobs 为空，只停止该等待观察器 PID3702577；没有停止 H1 或任何已启动后继模型。原 v0.18 迁移、118 例 pilot、四项目均未开始，新的执行配置在这个真实边界冻结。

## 先测瓶颈

9B 完成24例实际313次请求，其中308次生成、5次上下文前置拒绝；实际生成输入共2,602,622 token、输出112,224 token，调用时长约占总墙钟95.2%。一条原8444输入请求、明确诊断上限64输出的 profiler 中，aten::mm 自身设备时间占75.83%、bmm9.70%、depthwise卷积0.365%。这是该请求的局部剖析，不把开profiler的耗时作吞吐基线，不据此宣称所有任务比例相同。

当前2/4卡为单请求连续层分片，没有独立案例批处理；每个新调用完整prefill。卷积快核的当例收益上限小；安装FLA会改变具体数值路径，不能把dtype仍FP32当成highest等价。因此本轮不升级Torch/Transformers、不安装新算子包。

## 执行配置的明确变化

计划采用显式 `candidate-runtime-v0.19`：权重及LoRA仍FP32；matmul由highest改为high，CUDA TF32状态如实记录，CuDNN TF32仍关闭。原0.02最大/0.002平均概率差门完全保留。旧7B/high失败仍是旧配置的真实结论，新候选的局部通过不能回填旧实验，也不保证未来所有动作通过。

同actor、同精确前2048个token的混合缓存可复用，容量最多8个。仅保存独立prefix forward得到的状态，每请求深拷贝后处理后缀，完整实际输入IDs、输出IDs及实际采样logprobs仍记录；不同actor权重/身份清空，反向前清空，学习始终重算完整原输入。缓存不能裁切hybrid recurrent终态、不能增加别的角色的不可见输入。

已执行开发诊断在9B两条真实8.4k/14.3k提示、各64输出上：highest基线约10.83/17.13秒；high约4.83/6.99秒，同seed所测输出相同。high全输入重算最大差约0.00173/0.00064，均过原门；8.4k真实backward有限且非零，0 optimizer步骤。highest+2048前缀热请求约8.70/14.54秒，单独缓存也有小幅收益。这些只是开发数据；正式配置还要检查原2048输出上限、更长实际输出、27B以及双副本，不能把64输出诊断当完整容量证书。

## 双副本只采集，唯一学习器更新

同一在线窗口的独立世界固定分到两组GPU，父进程保留唯一共享actor/critic/optimizer，子进程只加载相同基座和真实adapter快照，不构造critic或optimizer。两组各保持9B两卡或27B四卡的原逻辑分片。唯一全窗声明及准备屏障之后才调用模型；每槽原seed与内部角色顺序不改，每个slot目录只有所属进程写入。

按 `rank=(global_slot_index+1-slot_count)%2` 固定分配，最后逻辑槽在父进程，合并严格回到原槽顺序。复制的是真实tensor而不是policy_version文字；副本最终实际hash、源、零更新与退出记录必须成立后父学习器才可更新。缺失或失败槽保留，子进程失败不由父进程接管/补采，不能把只有一侧的guard声称为全部通过。

不引入多optimizer、梯度平均或新的分布式训练后端。首次实现按窗口启动副本，加载/准备成本单独计入，同时报告生成阶段吞吐；不能只呈现热请求加速而隐藏加载。双副本占用全部8卡的27B方案与四项目有资源冲突，因此本轮四项目安排在学习链结束后，不能把延后评价写成已完成。

## 预算和准入

迁移8、主pilot118（64训练＋27初始＋27最终）、四项目4以及另列的密度16均不增加。复核交叉、四任务宏权各1/4、MC、角色预算、温度、输出/上下文上限、LoRA和学习率保持。初始/最终均使用同一新Γ；旧H1只提供候选，不将执行加速或新数值结果算作学习增益。Q=B及无自动O4保持。

性能清单在 `examples/throughput-v19/probe-inventory.json`：每候选固定3条原始实际请求（声明时可见的中位提示、最长提示、最长原输出），同新种子、原2048输出上限，基线与优化后分别保存原生成、热/冷耗时、全输入概率与实际backward。原H1请求只读，不回算评分。该清单不是未来任意长路径容量证明。

新的正式后继必须读取 `harness-optimization-admission-v0.19` 实测报告，严格绑定clean执行源提交、候选/基座manifest、完整runtime profile，并要求prefix概率、全输入概率、backward、真实双副本和吞吐5项证据通过。每项原证据文件均绑定hash。没有报告或某候选不通过就停止，不能静默回退、改门或切换候选。正式迁移和每个学习决定仍继续执行原概率门。

部署前做新增边界的必要CPU/实际GPU核验，再冻结源；H1完成后按原排序选择，选择不读性能试验业务成绩。代码实现、性能控制、真实模型工作和学习收益分别报告。
