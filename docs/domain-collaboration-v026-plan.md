# v0.26 相互依赖协作载体与冻结参数验证

依据[本轮审计](reference/audit-v025-next-v026.md)，本阶段先检验经验配置所依赖的工作载体。旧 v0.25 的真实更新、2/12 更新后确认与两次恢复按原范围保留；其未执行非单位 q/b，也没有参数学习增量识别。本阶段不再将支持不足自动转成另一轮无对照基础训练。

用户已要求按审计修订并开展后续实验，项目长期授权允许本地模型/GPU及提交推送。本轮限定 C0 只读证据、C1 小型冻结参数载体验证；C2/C3 的后继条件与公平对照同步更新为设计，不能仅凭 C1 消息增加而启动学习。以下预算为本次明确有限执行范围，旧未用预算不挪用。

## 1 C0 从旧经历区分协作证据层次

仅读原支持 16 条，保留原 V 与 Mapper，不重评分。每条信息/产物标记继承或当前模型来源，分别核对写入、送达或访问权限、首次进入接收者实际请求、首次进入有实际生成的请求、后续精确执行使用和对方验证。

“进入一个请求”与“模型完成处理”不等价：旧 B 的有效 issue 可以进入随后被上下文门拒绝的请求。issue 出现以前的代码修改不能被倒填为反馈修复；未完成的轨迹只能增加诊断标签，不能升级为方法支持。详见[只读证据表](experiments/collaboration-v026-c0.md)。

## 2 一个项目内的两个相互依赖工作项

复用 WorldCore 的对象版本、权限、采用、真实 DuckDB、固定提交和有据复核。保持现有共享 Qwen3.5-9B、原数值运行 profile 和完整 actor/critic=3/3 端点。新建的是一个明确版本化的工作载体及公开工具协议 Γ，不改旧记录，不把不同 Γ 轨迹并池。

| 成员 | 初始私有信息 | 自己完成的真实工作 | 对方工作如何进入自己的工作 |
|---|---|---|---|
| 数据维护者 maintainer | source_contract 模拟导出接口单位，原来源语义 | 根据实际 demand 与原始行编写 m_code，执行并固定提交 m_result | 必须取得消费者当前需求选择来源行；最终读取消费方固定代码/结果并独立复核 |
| 分析消费方 consumer | demand 当前期间及 sales_only/net_signed 用途 | 消费维护者已固定源视图，编写 c_code，执行并提交 c_result | 必须读取、采用维护者真实版本及 interface_meta，正确换算与核验 |

初始 m_code/c_code 不提供解答 SQL，结果为空；双方成果都必须由当前角色实际 SQL 执行。没有预制正确提交，也没有自动补 SQL、选择依据、采用版本或替模型回复。

源视图为 invoice_view(CustomerID,InvoiceNo,amount)、customers(CustomerID)、interface_meta(amount_unit)，消费结果为 metrics(CustomerID,revenue_pence,invoice_count)。原 raw 与原 UnitPrice GBP 语义不变；GBP/pence 是明确的模拟**输出接口**要求，不是伪造 UCI 原企业字段含义。

维护者的工作为 delivery_only，消费方工作由维护者复核，避免双方互等核准。中间草稿与结果按声明权限可读，以允许样例和查询探索；完整判定要求消费方实际使用维护者已经固定的确切版本，再由维护者读取消费方固定成果完成验证。业务产物通道本身可以传递信息，不要求只通过自然语言交谈协作。

## 3 四个反事实情境

两份新真实 UCI 材料，在模型运行前划分为 C1 开发用途。排除此前各阶段和 v0.25全部预留材料的客户、发票与原始行，不根据模型表现选取。两份共四名客户、十二张完整发票、二十六个原始行；来源清单与精确字节固定在 `examples/reciprocal-data-v026/source-manifest.json`。

| 原型 | 两个私有条件 | 区分信息前应相同的局部输入 | 正确执行应有的变化 |
|---|---|---|---|
| demand_pair | consumer 持有 sales_only 或 net_signed | maintainer 的初始实际模型请求相同 | 根据需求选取的源视图和最终指标不同 |
| unit_pair | maintainer 持有 GBP 或 pence 模拟导出合同 | consumer 的初始实际模型请求相同 | 上游 amount 与单位变化，消费方按元数据换算后最终 pence 指标应一致 |

反事实条件、case_id、来源用途与原型标签只在 host 归档，不进入角色任务/观察。配对世界保留不同真实 instance/branch，但模型可见非业务标识使用原型与配对 seed 的中性 namespace。对应反事实与两通信臂使用相同重复 seed，两次重复 seed 不同。

区分信息尚未可见时不能从模型输入的任务编号或运行 ID 猜条件；取得差异以后，通用、正确的参数化 SQL 也合法，不要求生成文本或程序字符串一定不同。反事实资格核对的是实际业务依赖及输出关系，不是刻意增加对话或强迫先犯错。

## 4 两个通信条件与公平性范围

C1 预定 4 情境 × 2 条件 × 2 重复＝16 个 episode，零参数更新。

- `normal`：双方按权限使用 request_information、handoff_information，自行选择证据及解释；公开 reply_options 只整理已经可见的真实请求范围字段，不选择证据或自动答复。
- `single_pass`：全 episode 仅允许 consumer 一次转交原 demand v1 精确引用，正文仅为固定非业务头部 `Original demand document.`，无额外自定义解释、请求或交接；该限制在受管世界命令内部执行，失败为可信工具拒绝。

两条件都保留完全相同的业务产物读写、真实 SQL、采用、固定提交、检查及正式问题/复核工具，角色权限、总机会、上下文、输出上限相同。**该对照的准确含义是“一次原件资料交接＋正常产物与正式复核流”，不是删除所有后续跨成员信息流。**m_result 的实际接口元数据可以正常进入消费者，c_result 可以被维护者再检查。

这样避免因为封死必要需求或产物读取而制造一个定义上不可能完成的对照。必须先取得 single_pass 的真实程序完成见证。若这个条件足以完成且 normal 没有可靠改进，应报告为低额外交流需求的控制情境；不增加最低轮数来改变结果。

## 5 判定与 CPU 资格

独立 Python/Decimal checker 从固定原始行、私有需求及源接口合同计算期望，不给角色暴露答案。保留三项分值：维护者实际正确固定源交付0.35、消费者实际正确固定交付0.35、双方执行依赖与后续验证0.30。完整职责要求全部成立，没有消息数量奖励。

双方 build 必须由当前成员实际执行，code/result、exact adoption、execution_provenance 与固定版本相符；私有信息或对方产物必须实际进入随后执行所依据的成员输入。导出模型还须通过实际保存SQL的关系依赖检查：用DuckDB解析各模型直接关系，并仅从真实export递归追溯到必需的源表；未被导出使用的中间模型、无用CTE或独立test不能替常数结果充当消费证据。CPU开发已实际复现“读取和采用完整但metrics写成正确常数”的假阳性，现作为负例保留。这个检查证明关系级执行引用，不证明列级血缘、唯一因果必要性或模型理解。声明 dependencies/sources 数组、工具ok、test通过、approve写入分别不能代替这些条件。未知服务/环境或证据损坏单列，可信业务失败按原判定保留。

模型前必要资格包括：

1. 四情境各完成 normal 的“约束先行”与“合法样例/查询先行”两条程序路线；四情境 single_pass 也完成。使用真实 native parser、compact输入、官方tokenizer、16384上下文/2048输出预留和两角色各24机会，无GPU模型或教师标签。
2. 配对目标角色的初始完整实际请求相同；隐藏条件改变产生声明的业务差异。原始输入与预处理记录均保留，不通过删除业务字段实现相同。
3. 少量必要负例：越权读取、未实际执行的伪产物、错误或过期对方版本不能取得完整资格；单次条件不得偷偷通过自由交接绕过，旧profile和精确回执核对保持。
4. 参数跨源码恢复显式保留旧 marker/source 引用，核验未改的数值模块、旧完整状态digest、actor身份与3/3计数；新世界/接口 Γ 单独记录，不伪改旧检查点身份。

两通信臂使用同一v0.26紧凑视图：当前观察中完全相同的两工作公共合同只保留一份并以显式引用连接；成员自己的相同role_task与visible_requirement同样去重。仅移除行动史中不供业务使用的审计digest/索引/空字段，历史工具消息逐字保留。v0.26核准回执保留固定引用与审阅状态，重复完整合同通过显式read_full_inspection检索。原始观察及变换记录均归档，旧profile不回改，context/output仍为16384/2048。

CPU程序只证明可达性和约束，不是目标模型已会协作，也不进入训练支持。若某条必要程序路线或上下文资格没有通过，应先记录其具体原因；不把失败写成全部准入，不通过临时增加模型预算掩盖。

## 6 冻结模型执行与预算

两个独立 episode worker 可并行，各绑定一张空闲或已授权共享的 A100、8个固定槽。同一 world 内两个角色仍顺序使用同一个共享参数实例，各有独立真实局部历史；不是训练 sampling replica，也不是一个world内多写者。

| 限制 | 本轮上限 |
|---|---:|
| 新世界 episode | 16，一次固定目录，不补采 |
| 新训练/反向/优化器步 | 0 |
| 外部模型 API | 0 |
| 并发 resident | 2，总共最多2卡；每world 1实例 |
| 单 worker GPU时间 | 2小时，两worker合计4 GPU小时 |
| 单 episode / loading / boundary | 20 / 15 / 10分钟，保留退出余量 |
| 单 worker RSS / 显存 | 64 GiB / 32 GiB |
| 新产物总量 | 12 GiB，包括临时文件 |
| 临时目录 | 本项目data1下各worker独立目录，至少1 GiB可用储备 |
| 总墙钟 | 6小时，包括等卡 |

普通可评分业务失败不截断固定分区；环境/服务未知或资源越限停止该worker，保留未知与未运行。所有失败和加载成本计入，禁止自动再尝试、自动扩窗或转训练。针对所用GPU保留原5秒查询和连续120秒遥测宽限。历史R1/R2费用不会因本轮另计预算而抹去。

C1 主描述量为同 case/seed 下 normal 与 single_pass 的完整职责配对差；同时报告两当前产物、实际进入输入、执行使用、反馈后的修订和再验证。它只能回答本载体/该端点下额外交流是否改变观察到的工作，不是经验分配或参数学习的效果估计。只有两个来源材料、两个原型和两个重复，不报告显著性或广泛因果泛化。

## 7 C2 与 C3 的后继门

C2 须在新训练材料、固定新 Γ 下，依据 C1 观察到的完整方法产出与成本事前冻结同情境重复数。不能缺哪类补哪类，不能将 C1 开发轨迹、旧 Γ 或程序见证拼池。**若没有任何可配置成员块，本次有限配置研究就在支持报告处停止，不再默认追加一次昂贵的Q=B更新和单端点评价。**有支持时，其他成员与可信失败仍保留共同基础损失及原分母。

C3 的核心是同一完整学习状态、同一当前原始经历、相同正式更新预算下比较基础Q=B、一般成员—原始轨迹元重加权、ID-VTDO结构化成员配置。一般元重加权获得同类贡献开发反馈和可比外层计算。算法必须实际产出配置；独立确认不参与选权，不以人工挑中的有利权重代替算法。

初始模型评价可作为辅助，但主量是两种分配规则更新后的独立工作差，而不是再次用通用训练前后对照取代配置对照。多成员共同图特征与联合效应须再跨信息结构窗口验证，单块成功不能一次证明所有主张。

C2/C3 尚无可执行新目录与GPU任务，本C1监督器的 `automatic_successors=[]`。本轮结束后依据真实载体证据再冻结后继，而不以消息增加、图有更多箭头或某条未闭合轨迹为准入条件。
