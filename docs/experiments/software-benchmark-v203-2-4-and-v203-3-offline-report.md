# 测试链验收与历史组织需求分析报告

日期：2026年11月16日；阶段：v203.2.4、v203.3-A。

**研究方向已按审计调整，已开展零 API 工程实验和历史分析。** 修复后的真实SDK、隔离Actor、测试、复核和交付已连续闭合；生产分块协议也已通过有限控制。当前仍不能宣布整个正式部署准入，更不能宣布动态组织有效。

本轮未调用外部模型、未消费旧余额、未重跑旧候选。新建的8个诊断容器均已清理，未使用GPU，未修改共享服务器配置、挂载、网络或既有服务。每次最多一个非root容器，2 CPU／4 GiB、network=none、drop ALL、无宿主挂载／端口／新卷。

## 1. 修订后的研究主线

上下文和通信管理作为Harness配套。接下来依次回答：工作产生了什么协作需求，现有组织能否处理，改变组织是否改善合法交付，再研究策略能否通过跨任务反馈改进。

后续不继续扩大K0／K1／K2。拟采用O0固定REVIEW2、O1强事件驱动、O2项目图与组织图联合驱动；先保持两名成员、相同权限、预算及同版本独立复核要求。完整条件、合法动作边界和后续阶段见[研究修订方案](software-benchmark-v203-3-research-revision.md)。O1／O2目前为准备协议，尚未实现或启动在线组织策略。

## 2. 真实执行链实际测到了什么

使用真实OpenHands SDK与原受管工具，响应由确定性脚本提供。在小型仓库中，先让错误代码产生真实pytest断言失败，再继续实现、发布候选、伙伴采用、复核和合法提交。最后锁定唯一候选并同步给隔离Actor。

最新协议控制有**26次脚本化响应，其中1次摘要、25次成员响应；2个私有会话；4次成员公开测试，其中1次失败、3次通过**。随后独立注入一次测试框架启动故障，使用正确代码检验技术未知。脚本记账只是机制控制数据，不是供应商usage或模型能力成绩。

| 控制 | 已取得证据 | 结论边界 |
|---|---|---|
| F1 缓存键 | `load_base()`与显式None在删除私有源码后仍返回预加载对象；CPU另测显式路径 | 规范化缓存修复有效 |
| F2 封存后测试 | 私有上传源码被删除后，非root PID1仍连续执行真实pytest | 没有回头读取已删除脚本 |
| F3 反馈进入请求 | 4条原测试回执逐一匹配正确成员后续实际wire中的报告ID、原件哈希、版本、计数和通过状态 | 证明已呈现这些字段，不证明模型理解；完整结果保留并按原接口分页 |
| F4 连续执行 | 真断言失败后，修改与测试继续；独立复核和提交成功 | 负例不会被误当永久通道故障 |
| F5 技术与代码分开 | 错代码得到1个失败断言；正确代码＋非法测试启动选项得到执行设施失败、测试计数未知 | 不把未知计数填0，不把设施失败当已测代码失败 |
| F6 故障停止 | 锁定后的真实Actor拒绝经生产RPC传回，RPC进入failed；原错误帧的CPU补充验证确认r5 guard阻止下一机会 | 此处没有新增模型调用；并非一次新的自主模型恢复实验 |
| F7 版本绑定 | 合法交付、锁定最终树、Actor最终同步树一致 | 仍使用预定member_001最终候选，不在成员间择优 |
| F8 不重复动作 | 相同键及相同载荷返回已有回执，Actor执行次数不增加；已锁定对象拒绝新写入 | 已知完成请求的幂等控制；不声称解决未知提交后的自动恢复 |

F7最终树哈希为 `2d8d43fa5667900a63074b173796325d232a7db74de6a8fb8cfc1a4ae2c9c13f`。22个生产RPC回执覆盖预同步、分块上传、4次公开测试、环境失败控制、最终同步与终态拒绝。

**工程结论为限定通过。** 真实SDK／执行器／分块协议组合控制已通过；本轮使用诊断启动器、Docker附着流和私有管道，未运行正式服务完整FIFO调度部署，亦未逐一准入未来基准任务解释器。正式付费实验Gate保持未通过，不能以本控制替代正式部署的零模型预检。

## 3. 诊断过程中发生的修订

8个诊断容器并非8个付费实验回合，均没有真实API调用。各轮材料保留，避免只留下最后成功记录。

| 诊断 | 实际问题与处理 |
|---|---|
| r1—r3 | 新诊断包漏子包、漏既有纯Python依赖、归档隐式子目录属主错误；均在SDK任务执行前退出，逐项修正 |
| r4 | 诊断缩短硬时限却未同步软时限，SDK拒绝装配；修正诊断时限顺序 |
| r5 | 主机fixture声明的解释器与容器实际解释器不同，原版本／argv校验拒绝测试回执；统一声明，未放宽校验 |
| r6 | 真实SDK已合法交付，但诊断错误地要求启动失败的tests_run等于0；修正为保留None／未知 |
| r7 | 归档桥接的完整链控制通过；4条测试回执与后续实际输入逐一核验 |
| r8 | 接入生产ManagedRPC和分块接收器后完成交付与同步；预期的终态拒绝是ValueError子类，诊断只捕获RuntimeError导致入口非零退出。保留原退出，不重做世界动作，只重放该错误帧验证failed状态和guard；修正以后使用的诊断异常分支 |

最后一项是**诊断代码的异常捕获遗漏**，没有将r8原退出码改写成0。综合验收引用r8实际链证据和单独错误帧控制，不冒称一次原入口全程零错误返回。新代码另通过5项必要CPU测试，包括缓存复现／修复、停止门及组织需求判断边界。

## 4. 历史材料中的需求与现有能力

本次重新对齐了原v203.2.1十二题中的32条产物、冲突和复核链。题目已有曝光，且包含既有环境故障；这里只做过程分析。时间取自原始控制器采集时间，不是活跃工作时间，也不是因果收益。

| 可直接观测的需求区间 | 区间数／题数 | 观测到结束 | 已完成区间中位数 | 范围 |
|---|---:|---:|---:|---:|
| 候选发布→伙伴集成操作 | 16／10 | 16 | 29.70秒 | 10.02—107.37秒 |
| 集成冲突→恢复到精确原候选内容 | 4／4 | 3；另1未见恢复 | 145.11秒 | 142.32—174.41秒 |
| 候选发布→同版测试支持的独立复核意见 | 12／8 | 11；另1版本不匹配 | 266.17秒 | 133.40—625.92秒 |

“集成操作完成”不表示内容已无冲突：原16次中12次干净集成、4次产生冲突。未恢复或版本不匹配的区间保留右删失，不能用最后日志时间充当解决时刻。上述起点是可见候选／冲突出现，不声称完整识别了潜在需求最早形成时刻。

这说明原有职责和普通操作确实能承接部分工作需要，但不能推出所有任务都无需动态组织。原108窗的既有AI辅助参考仍为**97个ABSENT、11个UNKNOWN、0个确证阳性**；不是新增独立审阅，也不能据此估计自然失配率为0。当前**失配持续时间保持未定**，没有用上表协作耗时替代它。

## 5. 旧11回合的故障前后边界

对每条原SQLite日志只读定位首次真实执行器 `FileNotFoundError`。在此之前仅选成功且来源哈希可核验的协作操作，不把更早的无效选择器拒绝当作设施故障。

| 项目 | 核验值 |
|---|---:|
| 原受损回合 | 11，涉及4个不同任务 |
| 故障前可保留的协作回执 | 10：8次消息、2次角色声明 |
| 全部响应usage总量 | 54,670,031 Token |
| 首次故障后响应usage总量 | 50,045,483 Token，占91.54% |

91.54%是故障之后发生的成本，不是可保证节省的成本；其中还可能有正常代码工作。它清楚说明本批轨迹大部分发生在失效反馈条件下，不能用于正常协作策略效果评估。故障前10条也只可用作过程材料，不能替代组织适配实验。
