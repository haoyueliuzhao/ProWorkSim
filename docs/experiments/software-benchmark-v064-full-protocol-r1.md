## 两种条件如何理解

两者均建立在OpenHands上，均只有一个实际Agent，不挂项目训练适配器，也不启动训练。

- **REF**：原生OpenHands五工具及原生会话，启用v062已形成的思考内容保留、公开Python环境说明、统一需求验证提示、有限停滞纠正与结束自查。
- **PROJECT**：OpenHands上承载ProWorkSim真实S1受管执行层；保留成员权限、版本化源码、任务／证据记录、分页、固定产物及合法交付规则。接入已修正的工具参数、空游标、仓库搜索和交付状态提示，并移除S1无合法伙伴可用的协作入口。

这些项目规则原本服务于多智能体协作：隔离各成员的探索版本、明确产物和责任归属，并用同版本测试与固定提交留下可核验的交付记录。本轮只有`member_001`，没有伙伴沟通、招募或跨成员合并，也没有团队协作收益可供宣称；测量的是单个Agent进入这套组织环境后的表现与成本。任务板仍可选，不能把未发生的成员沟通或任务维护解释成已观测开销。

本轮将PROJECT的计算容量与REF对齐，不把旧的18,432／2,048、50万成员预算、128次机会或最近4轮历史裁剪留作隐藏门槛。两条件都使用131,072总上下文、98,304最大完整输入、32,768单次输出，整题最多512次模型尝试／Agent决定，6小时软期限和6.5小时硬期限。PROJECT公开测试次数上限为512；单动作受管暂停机制保留，它不是整题只有两轮。真正的tokenizer／提供方计数继续负责准入，不能仅凭配置数值声称容量已对齐。

PROJECT先保留完整历史，在容量不足时按权限和版本规则移除可丢弃的旧观察及完整旧工具回合；REF继续使用原生会话及摘要机制。这些历史组织、工具粒度与交付机制仍是待测接口差异。PROJECT只运行预先确定的公开仓库测试入口，未增加不受管shell；REF可使用原生terminal定位和验证。不能把最终差值全部归因为某个单独API、某一条规则，或只归因为模型本身。

Qwen保持原始BF16检查点`c202236235762e1c871ad0ccb60c8ee5ba337b9a`、vLLM0.32.0及原思考／采样配置。DeepSeek采用`deepseek-flash`、思考high和top_p=0.95，省略思考模式无效或不支持的采样参数。官方文档当前将其映射为DeepSeek-V4.1-Flash-1017；商业API别名不是可验证的不可变权重哈希，应保存实际响应model与fingerprint。其服务端容量更大，本实验在客户端限定为上述共同容量。[DeepSeek官方说明](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)

## 评分与证据

三档预算和两种接口使用同一个官方评分标准。问题原文不改写为人工合同，公开工具不接收参考补丁、隐藏测试或官方评分反馈。每次从独立干净仓库开始，生成结束后锁定唯一最终工作树；评分与生成异步，评分不返回模型，不择优选中间补丁。

每组报告代码正确率。PROJECT额外报告最后合法提交的交付率，并记录其是否与最终代码同树、是否为同一受测版本。合法提交与最后工作树不同时分别评分；完全同树时可以复用该回合自己的代码评分，合法性仍需独立证据。没有合法提交的交付端点为0，REF的交付端点不适用。不能把两项均值之差无条件称为流程损失。

新评分路径包含v063对两处非语义git-diff日志解码的修复，原始字节完整保存；不修改候选、官方测试或resolved判定。不同slot及端点具有独立评分身份和run ID，避免旧缓存误命中。公开环境资格、接口覆盖限制、模型正常结果、提供方协议偏离、评分故障和实际用量未知分别记录。

## 实际消耗如何统计

十二组各自保留500题分母，分别汇总实际输入、输出、总token、推理token、缓存命中／未命中输入、调用数、墙钟时间、停止类型和API费用。每次已结算模型调用按唯一身份计入一次，包括重复发送的历史提示、原生摘要、自查、纠正，以及受管回读后发起的模型调用。推理token已经属于输出，缓存命中和未命中token已经属于输入，不再次相加。内部文件分块、CPU公开测试和官方评分不是模型token；PROJECT的代码及交付两个评分端点也不重复计算同一批生成消耗。

设第`g`组第`i`题的所有实际调用累计为`T[g,i] = 输入token + 输出token`。正式全组每题均值是`sum(T[g,i], i=1..500) / 500`，输入和输出均值也分别以500为分母。只有500题都已入场、生成达到终态且用量完整时，这三个全组均值才有确定值；代码评分仍未知并不必然使已完整结算的用量未知，不能因评分结果不理想或技术未知就剔除该题费用。

进度和最终报告同时区分以下覆盖口径：

- **完整计量回合均值**：仅在已经终态且usage完整的`n`题上计算，明确标为`n/500`；包含有完整用量的技术异常回合，不只选正常成功闭合题。另报正常闭合子集和成功／失败子集时，也列各自分母。
- **已入场已知消耗下界**：汇总所有已入场题已收到的完整usage，包括运行中和异常题已经发生的调用。除以已入场数或500得到的只是当前下界，不能命名为完整任务的平均消耗。
- **未定部分**：分别保留未开始原因、已入场但usage未完整的回合、未结算调用数及其预约。没有记录或没有开始不能填0；只有明确证明没有发出调用且回合用量记录完整时，实际0才成立。预约用于阻止超支，不加入实际token或实际费用。

推理细项、缓存细项或费用未被提供方完整报告时，各自列已知值及缺失调用数，不推造0或通过本地重分词补成提供方原始数据。输入和输出总数已知时，缺少这些细项不妨碍总token统计。全组用量均值与全组代码正确率的完备条件独立判断；只要某项仍未定，就保留该项空值与覆盖说明，不用500万／750万／1000万上限、各次预约或十二组混合均值代替实耗。

环境控制、程序化CPU测试及中性API准入单列，均不分摊进500题平均值。中性API费用仍占用同一1500元现金上限。统计定义及边界控制见[题单与用量验证](../../artifacts/software-benchmark-v064/plan-usage-validation-r1/validation.json)。
