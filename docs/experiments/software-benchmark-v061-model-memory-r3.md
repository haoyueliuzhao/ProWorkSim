## 已完成的工作与等待原因

此前的 CPU 亲和修订和原生工具部署诊断已经完成。七个任务各一项 gold／empty，共 **14 项评分环境控制已通过**；从原终态快照恢复的 `scikit-learn__scikit-learn-14894`／500万（原 slot163）也已经取得官方 `resolved=true`。这些是已完成的实际结果，不因本次显存修订重跑。

剩余 13 项属于需要重新生成的恢复回合。旧配置使用 `gpu_memory_utilization=0.8`，并要求至少 **66,560 MiB** 空闲显存。当时可见 GPU 虽有较多剩余容量，却未满足这项较高预约门，因此协调器处于等待状态，尚未加载新驻留或进入这 13 项。

修订前只停止了已核实属于本批、正在等待容量的协调器，原记录保留；没有停止他人进程或为本实验腾空整张显卡。原范围仍允许在剩余容量满足要求的共享 GPU 上运行，不要求整卡完全无人使用。

## 为什么可以提出较低预约比例

v056 原驻留引用的容量凭据来自同一原始模型、BF16、131072 上下文、`max_num_seqs=1` 的实际启动。其日志记录如下：

| 历史实测项目 | 数值 |
| --- | ---: |
| 显存预约比例 | 0.8 |
| CUDA 可见总显存／预约量 | 79.25／63.40 GiB |
| 权重加载显存 | 16.71 GiB |
| 已消耗显存（权重及非 Torch 部分） | 19.03 GiB |
| 峰值激活／CUDA graph | 2.09／0.02 GiB |
| KV 缓存显存 | 42.28 GiB |
| KV token 容量 | 1,364,813 |
| 每请求 131072 token 时的缓存并发容量 | 10.41 倍 |

运行实际只允许一个序列，历史缓存容量明显大于一个完整上下文所需。固定 vLLM 0.32 源码中，预约比例用于计算本实例请求的显存，再减去非 KV 消耗以分配缓存；该比例不参与缓存配置的计算图结构哈希。显式指定131072时，启动还必须通过至少一个完整请求的缓存容量检查，容量不足会拒绝启动，不在本方案中自动缩短上下文。

按照历史剖析值推算，0.6 对应约 **47.55 GiB** 总预约、约 **26.43 GiB** KV 缓存，缓存并发容量约为一个完整上下文的 **6.5 倍**。这些数值是基于旧日志的**部署预测，不是新配置实测**；新环境剖析和共享 GPU 上其他进程的用量变化仍可能影响实际可用容量。

原始日志、继承关系及对应源码引用见 [historical-capacity-evidence.json](../../artifacts/software-benchmark-v061/model-memory-r3/historical-capacity-evidence.json)。本次没有重新哈希全部模型权重，也没有根据任务成绩改变该资源参数。

## 本次改变与保持的条件

相对于已经通过部署诊断的 v061 配置，本次只改变模型缓存预约与对应的启动容量门：

| 项目 | 原配置 | r3 接续 |
| --- | --- | --- |
| `gpu_memory_utilization` | 0.8 | **0.6** |
| 空闲显存准入门 | 66,560 MiB | **50,176 MiB** |

50,176 MiB 按80 GiB卡的60%加1 GiB余量设置，作为启动前的保守容量门。准入仍按 GPU UUID 和本项目资源锁检查；这不是独占整卡，也不允许干预其他使用者。

以下设置保持：原始 Qwen3.5-9B 检查点、BF16、无训练适配器、上下文131072、单次输出上限32768、`max_num_seqs=1`、关闭前缀缓存、原思考与采样、原题及原 seed、原生单 Agent REF 工具和历史摘要规则。13项的累计输入＋输出预算总上界仍为 **89,000,000 token**，每题原预算及调用／时间边界不变。

CPU 亲和池、主机内存／PID约束、最多两个模型驻留、容器及卷数量、评分规则和候选锁定方式也不扩大。仍不修改共享服务器的 mount、namespace、驱动、用户管理器或既有服务配置。显存预约修订应作为部署版本记录，不将“计算图哈希不包含该字段”解释成已经证明跨启动逐 token 完全一致。

## 实际容量与中性验证：正式派发前必须通过

新驻留即使已经响应 `/v1/models`，也不能直接获得正式派发资格。每个驻留还需完成：

1. **实际启动容量核对。** 捕获本驻留 stdout／stderr 当时的前缀，保存前缀字节数、SHA256和独立副本。解析 vLLM 实际容量行，必须同时满足：报告上下文为131072、KV容量不少于131072 token、完整上下文并发容量至少1。缺失、冲突或不足均保留失败凭据并拒绝准入。日志后续可以继续追加，不改变已经冻结的前缀证据。
2. **一次有界中性请求。** 先用 `/tokenize` 核对固定中性输入的完整 token IDs、精确数量及上下文，再执行一次固定 seed 和原采样的短生成。该准备请求的输出上限为128；输入＋输出预约和实际用量每驻留均不得超过2048 token，两个驻留合计最多4096。128仅是中性准备调用的上限，正式任务输出上限仍为32768。
3. **完整账单核对。** 实际 `prompt_tokens` 必须与精确计数一致，`total_tokens` 必须等于输入与输出之和。只有收到完整、有效的响应并通过用量核对，才写入通过标记并允许任务开始。HTTP失败、响应不完整或计量不一致均保存原错误及不确定预约，不自动重试，也不写成 ready。

每个本轮驻留有唯一的中性验证占用记录，不能通过换输出目录重复调用。准备内容不使用任何基准题目，不读取候选评分反馈。中性验证检查的是服务与计量路径，不是模型能力分数。
