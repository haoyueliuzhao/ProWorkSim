# v057 无其他机器条件下的重新评估

日期：2026-10-24。用户暂无其他机器，要求在不干预共享服务器的前提下重新分析。本记录更新此前以异机为主的建议；当前所有实验暂停状态保持，不把候选办法写成已完成修复。

## 先拆开三个问题

1. **宿主恢复**：此前已确认的挂载可见性恢复；历史binfmt handler和事故期间其他任务的业务影响仍不能完整确认。显式Python已是本项目入口的实际做法，没有为项目补改全局handler的必要。本轮没有重复挂载检查。
2. **模型执行修订**：响应字段、公开运行指南与有限stuck纠正已在v057实现并做过CPU控制；这些不是剩余Requests评分网络问题的原因。没有新模型结果可证明分数收益。
3. **16项Requests补评**：四题各四档原候选；旧离线r2中2931、5414的参考修复已完整通过，1921、1766仍未通过。原候选保持，不需要因评分环境问题重新生成模型答案。

## 优先方向：按固定镜像分开准入，先解决有证据的8项

建议把原“四镜像全部准入后才处理16项”的批次依赖改为**逐镜像资格**：每个任务必须同时有同版本、同环境下的参考修复成功、空补丁因目标测试失败、可信退出记录，才能处理该任务的四份原候选。两题已有控制证据，对应8份候选；另8份保留技术未知。

这是待实现的评分调度／资格修订，不能直接绕过现有全局硬暂停。分组依据是环境控制结果，不是模型补丁得分；计划分母16保持，正式汇总保留两个环境修订及所有未知项。旧全局资格false与旧评分均保留。

要复用旧r2，还须确认其精确源码、依赖与控制记录一致，以及实际调用链不进入未准入的r3宿主NAT helper。不能只看到两个gold通过就宣布入口安全。本轮并行源码／控制细节检查被安全系统以`Potentially unintended activity`拦截，因此这一点未完成核验，未执行评分、未解锁入口。

离线容器的`network=none`只有loopback，因此服务可以在容器内提供，但固定外部地址的连接超时测试不能由此自动成立。旧r2已有独立超时夹具；其重用仍属于上述待核验范围，不在宿主补路由或用模拟异常替代真实测试。[Docker官方说明](https://docs.docker.com/engine/network/drivers/none/)

## 另8项：证书问题不能靠泛泛升级依赖解决

Requests官方说明指出，prepared-request路径可能不读取`REQUESTS_CA_BUNDLE`。公开历史v2.0.0与v2.2.1的`requests/certs.py`均直接返回仓库内`cacert.pem`；v2.0.0的adapter在`verify=True`时使用该默认CA路径。因而“安装新版certifi或设环境变量即可解决”不是可靠结论。[Requests说明](https://requests.readthedocs.io/en/latest/user/advanced/#prepared-requests)、[v2.0.0源码](https://github.com/psf/requests/blob/v2.0.0/requests/certs.py)、[v2.2.1源码](https://github.com/psf/requests/blob/v2.2.1/requests/certs.py)

这些公开tag用于解释机制，**尚未在本轮与两道任务的精确基线逐行对应**。剩余调查应逐项确定实际CA选择、测试服务版本与官方fixture入口，再判断能否仅调整评测依赖。若只能修改候选仓库的证书、客户端实现或官方测试才能通过，就超出了原冻结补评规则，应保持技术未知，或另建明确标识的兼容性诊断；不能混成原官方评分。

## 当前机器的备选条件：只查元数据，未启动资源

| 项目 | 普通用户只读结果 | 判断 |
| --- | --- | --- |
| QEMU | PATH未找到`qemu-system-x86_64`、`qemu-img` | 不能作为现成虚拟机路径 |
| KVM | `/dev/kvm`不存在 | 不加载内核模块、不修改设备权限来补齐 |

| 资源快照 | MemAvailable约942.79GiB，项目盘普通可用约673.16GiB | 仅采样值，无资源预约；容量不是当前首要阻碍 |

Rootless Docker降低守护进程的宿主权限，但官方仍要求UID映射工具及subid配置；不能以rootless名义临时补装特权组件或更改现有系统Docker。[Docker官方条件](https://docs.docker.com/engine/security/rootless/)

纯软件QEMU TCG也不应被当作无条件安全替代：QEMU将受支持的虚拟化安全边界与硬件加速、指定机型绑定，并明确要求管理宿主资源峰值。只设置guest内存和vCPU不足以证明共享宿主不会受影响。本轮没有下载、安装或启动QEMU。[QEMU安全说明](https://www.qemu.org/docs/master/system/security.html)

## 当前结论

比立即迁移或重建整套运行时更有针对性的下一步，是核实并复用已有两套离线环境，另立逐镜像补评资格；另一半继续定位精确TLS／服务兼容问题。**这是一条可审查的推进路线，尚不是已经验证可运行的方案。** 两项并行深入检查被拦截后，仅继续了公开资料分析和普通用户只读能力核验，没有以其他工具重做被拦截的源码／控制检查。

本轮没有主机配置写入、容器／namespace／VM创建、系统服务操作、评分或模型调用。此前8项全局环境准入门和项目硬暂停均未改动；不存在自动恢复队列。
