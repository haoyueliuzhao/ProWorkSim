# v142：审阅提案与源码冻结工具

`tools/seal_role_pilot_v142.py` 只准备可审阅的本地源码索引和运行范围提案，不写 `approved`，不创建 API 账本，不调用 Docker、systemd、网络或模型。400 元是用户已授予的三组共同 API 预算；具体 root 等效 Docker 对象范围仍与该现金授权分开。

`--inspect` 只列出必要准备文件是否存在，不生成源码 seal。`--seal` 仅在全部作者收口后使用：它要求新账本、运行授权、用户具体资源批准、资源预约、启动意图和正式执行记录均未存在；已冻结或已进入的身份不能重新封存。

冻结内容包括新 v141／v142 的角色、测试、环境、评分、主控、API、调度、启动及激活源文件，以及静态递归依赖；还包括题单、每回合配置、最终 bundle、真实成员 schema、普通用户服务规格和必要 CPU 证据。只读核验保留的证据，不重新运行旧测试。最终 source index 不纳入动态账本、网络探测结果或执行／清理状态，避免把运行过程中正常追加的记录误作源码漂移。

较大的 bundle archive、pytest 离线 wheel 和 baseline pyproject 作为独立 payload 引用封存：准备时核对字节、大小及 SHA，实际上传前仍需核对，不在每次 API 授权检查时重复读取全部 payload。pytest 原依赖计划及来源说明的 JSON 本身进入静态源码索引。正式评分端的候选、gold/empty、网络和环境准入仍由各自原有证据门控制，单有离线 wheel 不代表该题已通过真实评分环境验证。

提案明确列出 40 题×S1／FREE2／REVIEW2 共 120 回合、每队共享 5M token、合计上限 6 亿 token；三组共用一个 400 元账本，不能变成三份 400 元，也不保证现金可完成全部回合。最多 568 个容器、124 个专用卷、16 对生成、2 路评分、4 路启动，资源总预约上限 112 CPU／840 GiB。只新增一项有独立限额的普通用户协调服务，不新增系统 slice，不修改共享主机、挂载、网络、驱动或其他用户对象。

授权后的激活顺序与实际 `activate_role_pilot_v142.py` 一致：受限直连 httpbin 探测、冷评分准备、启动唯一普通用户协调器。协调器内部仍必须先完成四个零模型诊断和来源环境准入，再初始化新 API 账本。两个 TLS 来源未准入时保留局部未定，不伪造地址或把其失败扩散为全队列停止。

本工具新增 11 项纯 CPU 控制通过，覆盖实际准备对象形状、共同现金范围、禁止系统 slice、错误成员／资源／计数器配置、源依赖闭包、已消费身份拒绝、过期源码证据拒绝，以及激活入口在无授权时先于任何外部动作拒绝。检查没有执行真正 seal；应等待最终 P0、host 和 grading 汇总收口后，由主任务执行一次冻结并向用户展示具体资源提案。
