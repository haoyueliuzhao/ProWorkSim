# SymPy-19954｜已有复核人时，额外分派诊断职责有什么作用？

在 Sphinx 上，项目图显示的是连续两次修复失败。在 SymPy 上，公开测试已通过，但当前版本还在等独立复核。这里考察的是后一种现场：团队已配备复核人，策略会不会调整分工，以及调整后能否完成真实复核与交付。[Sphinx 的配对结果](v233-repaired-osa-pair.md)

## 实验怎么比

KEEP 沿用原分工，001 负责实现并交付，002 负责独立复核。OSA 从同一保存点重新调用策略模型，可维持原图，也可让 002 额外承担诊断和证据交接。两组都使用修复后的同一套工具、T1 上下文、DeepSeek Flash 非思考模式及官方评分器。每组团队总额 500 万 token，原前缀已用 1,151,467，各余 **3,848,533**，其中 OSA 的策略请求也占本组额度。每组只运行一次，该题此前已在其他条件下出现。[冻结方案](../../artifacts/software-benchmark-v234/sympy-a4-r1/protocol.json)

**策略看到了什么。** OSA 收到的异常名称说明“当前版本缺少独立复核”，组织图也列出了已有的复核人为 002。它看到的 E1 证据仅写明交付就绪检查执行成功。对照当时的原始检查回执，可以看到 001 的 v3 已通过公开测试，同时还缺“完成工作包”和“独立复核”，最终树也未固定。这些具体缺项和已通过的版本没有随 E1 提供给 OSA。执行检查成功与满足交付条件是两个不同的事实。

**实际选择。** OSA 选择给 002 增加诊断交接职责，001 继续负责实现。策略理由引用了 E1，并认为新增职责可以保留现有的实现／复核分工。单次选择无法判定补全 E1 后模型会怎样选择。

## 实验结果

| 保存点后新增的实际用量与结果 | KEEP 维持分工 | OSA 追加诊断 |
| --- | ---: | ---: |
| 官方代码评分／合法交付 | 通过／通过 | 通过／通过 |
| 实际输入＋输出 token | 1,794,987 | 1,911,101 |
| 其中输入／输出 | 1,786,740／8,247 | 1,902,379／8,722 |
| 请求数 | 27 | 28（含 1 次策略调用） |
| API 费用 | ¥3.0935 | ¥3.3223 |
| 从恢复到锁定候选，含公测 | 4 分 33 秒 | 30 分 22 秒 |

**决定后发生了什么。** KEEP 中，001 发布补丁，002 测试同一版本并正式接受，001 完成交付。OSA 中，002 先检查工作区差异，尝试发出正式诊断。其引用未获校验通过，随后成功登记阻塞原因。002 仍保留原复核职责，最后同样打开补丁、完成同版本测试、给出正式接受，001 随后提交。两臂均出现“独立复核通过”，OSA 的新增诊断职责停在“已报告阻塞”。

**两份代码是否不同？** 两组送入评分的补丁和文件树哈希完全一致。复核与提交也都绑定到保存点上已有的 v3 文件和元数据。这一现场主要考察团队能否把现成的正确代码复核并交付。现有复核分工做到了这一点；额外委派诊断在本例没有带来新的代码或交付收益。

**为什么 OSA 用时更长？** OSA 组的 001 自主运行了全仓公开套件，耗时 1,542 秒，报告 9,059 项通过、7 项异常，未超时。该版本最新公测因此被记为未通过，首次完成工作包被拒。其后 001 运行定向测试通过，002 再对已发布补丁测试并接受。KEEP 三次公测合计约 12 秒。两组总时长相差约 1,550 秒，其中绝大部分可定位到这次全仓测试。单次运行不足以判断额外诊断是否会系统性诱发全量测试。

**为什么原观察器仍显示“未知”？** 本现场触发异常的是 002，原观察器只读取这名成员的行动；最终提交由 001 执行。评测侧分别查到 002 对同一补丁的接受、其本人在相同文件和元数据上的通过测试，以及 001 对该版本的提交。由此可确认实际交付版本具备独立复核证据。原观察器的未知值保留，不能据此判断复核缺失或估计全程复发次数。

OSA 比 KEEP 多用 116,114 token（6.47%），其中策略调用本身占 917 token。按事前效用公式，OSA 相对 KEEP 的单例差为 −0.00232228，来自用量差。两个成功交付都按原规则计分。共享账本一次追加 ¥37 后，上限为 ¥181.37466640；本对实际支出 ¥6.41588824，余额 ¥55.30747752。在途预约为零，两组生成和评分环境已清理。[逐臂轨迹、复核版本、官方回执及账目](../../artifacts/software-benchmark-v234/sympy-a4-r1/results.json)

## 和 Sphinx 放在一起看

Sphinx 的持续修复失败触发了可以实际使用的诊断：伙伴给出意见，负责人读取并登记采用，但两组都未修好目标问题。SymPy 的代码在决策前就已就绪，团队真正缺的是同版本复核。在这个现场，额外诊断未完成，两组都依靠原有复核流程交付了相同代码。两个例子说明，**组织图可以改变成员的行动；要判断这种调整有没有价值，还要看新增职责是否对应现场真正缺少的工作。**

进一步验证时，优先在同一批决策前回执上比较两种输入：一种只显示异常名称与检查已执行，另一种同时说明已通过的版本、还缺的工作包步骤及现任负责人。先观察 OSA 是否改变选择，再用配对续跑比较后果。以上两题均为开发性探测，C/N 参数更新次数仍为零。[Sphinx 配对报告](v233-repaired-osa-pair.md)
