# 未完成回合恢复与新回合现金准入规则

2026年11月9日，用户追加50元，并明确要求已经开始运行的任务不因金额上限中断。本轮名义累计预算变为550元，550元用于新回合启动准入；已启动回合继续完成，累计费用可以超过这一数值。所有实际请求及超额均继续记账，不删除历史费用，不把在途支出转移到另一个账户。

## 恢复范围

恢复13个生成中断回合，另核验2个已锁定候选的评分分类。13个生成回合包括6个此前因观测器故障中断的回合，以及7个因现金预约不足中断的回合。它们按原题、seed、条件和初始仓库各独立运行一次，旧上下文、补丁、失败记录和费用保留；新尝试不冒充原会话续接。

仍为DeepSeek Flash非思考、REVIEW2双人、每队5M输入加输出token，包含执行Agent、历史摘要和通信压缩成本。新增输入加输出上限65M；每队512次物理请求、原上下文和输出限制以及时间限制均保留。只恢复列明身份，不因代码低分重复采样，不自动追加更多独立尝试。

按上一批14次恢复的实际账本均费估算，13次新恢复约需108.67元。这是估计，并非固定费用；本次50元增额不保证累计费用停在550元。已开始回合继续完成的例外可能产生超额，报告将单列超出准入线的金额。

## 金额门槛怎样执行

1. 队列取得真实运行和环境启动资格后，在启动环境前原子登记该回合的现金准入。单纯在排队列表中不算已经启动。
2. 新回合只有在550元门槛内仍能预约一次最大请求时才能登记；并行启动的初始预约也一并计算，避免同时读取同一笔余额。
3. 已登记且进入运行的回合，后续Agent、摘要和压缩请求继续执行，不再以全局现金余额不足为理由截断。每队token、请求次数、实际资源及时间限制继续生效。
4. 若尚未创建环境、未发生API调用便因资源不足退回队列，释放其启动预约，保留事件记录；下次进入仍须重新通过现金准入。
5. 已有真实API调用的身份不能作为新回合重新登记。旧账本的请求、usage、费用及500元历史政策均不改写；新政策通过独立的追加记录生效。

新状态中`cap_CNY=550`表示启动准入线，`over_start_threshold_CNY`记录超额，`initial_team_start_holds_CNY`是尚未发出首个请求的启动预约。三组读取同一SQLite账本，不能把三份视图的550元相加。继续采用冻结峰值单价的保守计费口径，供应商usage是token权威；这些金额不是供应商发票。

## 两项评分分类结案

Astropy14369的C1恢复候选和Seaborn3069候选原来被本项目列为评分技术未知。两者已有真实官方测试执行和官方`resolved=false`结果；官方`infra_failure`属于附加诊断，不改变该布尔结果。日志中的pip网络错误触发了诊断，但实际测试还明确显示候选自身错误。

- Astropy候选将必需的`CDS`类改名为`Cds`，未改动的模块仍导入`CDS`；pytest实际发生ImportError。
- Seaborn候选新增`field(default_factory=list)`却未定义或导入`field`；pytest在候选修改的第158行实际发生NameError。

本次核验绑定了原评分请求、候选锁、实际送入评分器的补丁字节、应用成功日志、测试日志及已合格环境，并核实旧交付记录均为无合法交付。两题据此结案为**已确认的候选执行失败**，代码和交付结果均为false。

没有重新调用模型、重新执行测试、修改候选或改写官方原报告；这是对项目侧“技术未知”分类的纠正。原网络诊断、没有逐测试状态的事实和全部费用都保留，不伪造一份正常解析的逐测试报告。

因此，在新13题恢复结果产生前，已有57份正常官方代码评分及2份由真实测试确认的候选执行失败，共59个明确结果；13个恢复回合仍需正常完成并评分。
