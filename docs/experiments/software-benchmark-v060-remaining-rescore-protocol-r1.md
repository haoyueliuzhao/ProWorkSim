# v060：1766／1921 原候选补评

日期：2026-10-25。最终状态：用户明确授权后，4 项环境控制通过，8 份原候选全部补评通过；12 个容器均已清理，授权已关闭。实际结果见[补评报告](software-benchmark-v060-rescore-results-r1.md)。以下保留准备阶段的范围和判据。

## 目的与范围

本轮只处理 `psf__requests-1766`、`psf__requests-1921` 在 500k、2M、5M、10M 四档预算下已经生成的 8 份候选。补丁、候选锁、题目版本和官方评分规则保持原样，不调用模型。2931／5414 已完成的 8 项 v058 补评不重跑、不覆盖。

目前这 8 项的旧评分记录仍保留，但因环境未通过验证，在分析中属于环境未知，不能计为模型失败。v058 完成后的完整 200 回合状态为 78 成功、100 未通过、22 未知；其中 14 项是既有生成未知，另 8 项就是本轮环境未知。上述数字来自 50 个不同任务的四档预算实验，不是 SWE-bench Verified 完整 500 题成绩。

## 为什么需要新的运行路径

v059 已分别在两题的原始客户端中验证：保留仓库原 CA 和 TLS 校验时，可以通过真实 `httpbin.org` 完成 HTTPS 请求，四次探针均返回 HTTP 200。不过，两次旧 `Session.send()` 探针在转发连接收尾时记录了 `ConnectionResetError`，而且单连接诊断不支持完整测试的连续请求。它证明原 CA 可以验证该服务，不等于两题已经取得正式评分资格。

1921 另有独立于 TLS 的旧环境问题：本地 httpbin 的 Cookie 过期测试未通过。因此 v060 将 HTTP 和 HTTPS 都限定转发到真实 `httpbin.org`，不再用本地服务替代这两题的响应。

v060 使用新版本的有界连接转发器处理连续及并发请求。容器内只监听自身回环地址；宿主普通用户进程通过既有 Docker exec 通道转发 TCP 字节，不监听宿主端口，不终止 TLS，不生成或替换证书。固定公开目标、连接次数、并发连接数、转发载荷和运行时限；超限或可信性不足保留为技术未知。

客户端重置、正常 EOF、外部连接失败分别记录。客户端主动关闭连接可能出现在正常 Requests 测试中，不能一律当作整个转发服务崩溃，也不能将重置伪记为完整双向 EOF。新转发器的 CPU 检查只证明受测协议和约束行为；真实容器兼容性与官方测试结果必须由后续控制运行确认。

## 评分顺序与判据

先执行两题各一项官方参考补丁（gold）和未修复基线（empty），共 4 项控制。每题必须独立满足 gold 被官方评分器判为 resolved、empty 在目标 FAIL_TO_PASS 测试上失败，并具备环境身份与清理证据，才派发该题的 4 份原候选。另一题不合格不自动阻止已合格题；未合格题保留完整身份和未知状态。

每份候选使用新的 run ID 和输出目录，保留原评分。转发、容器、测试或清理异常不会填成正常代码错误，也不在本轮自动重新生成补丁。公共范围或资源状态不明时停止新增容器；所有清理只针对本轮确证拥有的对象。

## 共享服务器边界

原 `v057-shared-server-hold.json` 保持 `hold=true`。已完成的 v058、v059 授权不重新打开。新授权仅涉及计划内的既有 Docker 管理接口操作和受限出网；不启动或重启守护进程，不执行宿主挂载、网络命名空间、NAT、slirp 或系统配置修改，不操作其他容器，不使用 GPU。

具体资源上限、题单、原候选哈希和 21 个入口／依赖文件已封存在 [本轮提案](../../artifacts/software-benchmark-v060/rescore-authorization-r1/proposal.json)。最多创建 12 个容器、并行 2 个，每个 4 CPU／16 GiB／512 PID；drop ALL，仅添加容器内 NET_ADMIN 和 NET_BIND_SERVICE。每容器最多 512 次 TCP 连接、同时 16 条连接、64 MiB 转发载荷，全部容器合计最多 6144 次／768 MiB；这些是硬上限，不是预计消耗。仅允许一次既有 DNS 解析后冻结的 `httpbin.org` 公网 IPv4 的 80／443 端口。容器生命周期最多 3600 秒，测试及转发最多 1800 秒；父进程额外留出清理时间，3900 秒后结束未响应的子进程。不能取得可信清理证明时保留占用记录并停止相应通道新增任务。

由于 Docker 管理接口具有 root 等效能力，用户最新 AGENTS.md 的“未经授权严禁使用 root 权限的相关操作”要求本轮取得具体授权。此前仅用于 TLS 诊断的授权已经完成，不能用于正式评分。

固定 SWE-bench 评分器的清理路径会直接调用 Docker CLI，而不是容器包装器的 `stop()`。新版本在该清理入口前先收尾本轮传输、保存 CA 与执行退出证据，再调用原清理函数，并在结束后恢复入口。因此存在明确的容器生命周期适配；官方测试、补丁应用与 resolved 判定没有修改，不称为完全没有修改 harness 的运行方式。

准备证据见 [validation.json](../../artifacts/software-benchmark-v060/rescore-authorization-r1/validation.json)。90 项 CPU 检查覆盖转发协议、范围与次数限制、评分接入、准入身份、结果回写和执行器；原 8 份请求另用固定 Python 3.12 的普通用户启动器完成检查。准备阶段未连接 Docker、未进行 DNS／公网访问、未运行模型或官方评分。

## 结果解释

若补评取得可信结果，只更新这 8 项对应的评分，并保留原记录与环境修订分层；其他 192 项保持原状态。14 项生成未知不会因评分修复消失。若环境控制或候选评分仍有未决，报告继续给出完整计划分母和未知数量，不只统计成功闭合的子集。

真实外部服务存在随时间变化的响应与可用性，因此本轮属于明确记录环境修订的补评，不将其与原离线环境描述成完全同质的实验。准备完成不等于补评完成；实际容器数量、连接和载荷、控制结果、候选结果及清理状态在运行后单独记录。
