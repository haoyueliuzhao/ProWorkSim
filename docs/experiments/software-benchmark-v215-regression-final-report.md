# 组合工作回归实验总结

2026年11月18日。本报告以v213六回合真实评测为主，单独列出v212比较结果及v214性能验证。报告分析没有新增模型调用、评分或预算。

## 1 主要结论

**本轮5/6回合的最终代码通过官方测试，但只有1/6完成合法交付；组合组仍为0/3交付，未达到后续开发准入门槛。**

与“接口完全走不通”相比，本轮已有更具体的进展：独立候选复核已被真实模型使用，Matplotlib组合组完成了伙伴代码的复核和无冲突合入；SymPy组合组的三个工作包均已完成并取得复核接受，却没有正式提交。瓶颈已进一步落到剩余工作完成、合并后的证据更新和最终结束流程。

**资源问题需要分开处理。** 六回合都触及5M Token预约边界，输入占实际Token的99.64%；唯一成功交付的回合，提交后仍消耗37.5%的总Token。与此同时，本地状态处理造成了明显墙钟开销。v214已将固定热路径基准加速约9.6倍，但不会自动减少模型输入Token或替模型完成交付。

## 2 实验条件和统计口径

三个历史回归任务：SymPy-19346、Astropy-14995、Matplotlib-25775。每题各运行以下两种初始方案。

| 条件 | 直观解释 | 不应混淆的边界 |
|---|---|---|
| SINGLE 单包起点 | 整题先作为一个工作包，由001负责实现、002独立复核，001最终交付 | **仍是两个实际Agent，不是单Agent基线** |
| COMBO 组合起点 | 按公开需求拆成三个工作包，指定各包负责人、验证人、协作和必要依赖，再由001集成交付 | 名字表示初始方案，不表示模型必然完整遵循或一直保持该安排 |

共用DeepSeek Flash非思考模式、原生OpenHands SDK上的真实受管接口、每队5,000,000输入加输出Token，两个私有工作区，001为唯一最终导出身份。上下文131072、输入上限98304、单次输出上限32768、temperature=1、top_p=1。全部533个已结算响应均记录`deepseek-flash`及同一fingerprint，详见数据摘要；API别名不等于独立核验了供应商权重文件。

本轮共同采用v213合同：未开工工作可由双方明确调整；代码和证据工作分别完成；固定候选可在不覆盖复核者私有树的情况下独立测试；最终交付仍需显式集成、同版本测试、固定和提交。官方评分不回传模型。

本报告分列三个端点：

- **代码正确**：回合结束后锁定的001最终工作树，经官方评分通过。
- **正式提交存在**：实际调用正式提交并通过项目合同检查。
- **合法交付正确**：最后合法提交的版本，经官方评分通过。

没有正式提交时，交付记未完成，不能将最终代码的通过替代为交付通过。工具拒绝、公开测试失败不自动等于技术未知。本轮六条生成均正常闭合，评分全部明确，无技术未知或现金截断。

## 4 逐题分析未交付原因

### SymPy

**SINGLE完成了正确交付，但没有及时结束。** 首次正式提交时累计307.51万Token，费用上界5.06元；之后又消耗184.59万Token、约3.21元和9.1分钟，占全回合Token的37.5%。其中002消耗146.31万、001消耗38.28万Token。全回合只有一次正式提交，该提交与最后合法提交身份一致。

这说明提交后的团队结束流程仍有可优化空间。但本轮费用全部保留，不能因为事后评分通过就按首次提交时点追溯截断。

**COMBO已具备工作包闭合证据，却没有正式提交。** 三个工作包均局部完成，最终只读检查表没有缺项。002对同一`patch-1`记录三次`accept`，实际只对应一个不同候选版本的接受，不能当作三份独立候选复核。001随后对自己的补丁执行了一次无冲突集成，最终没有调用`submit_integration`。

还需保留一个语义边界：该组合候选的复核公测记录为880通过、2错误，`passed=False`；三次`accept`均保留这一实际记录。合同允许“实际检查后明确接受”，不把接受等同于全部公测通过。这些不是三次全绿复核。最终代码另由官方评分确认通过。

**真正的中途责任调整仍未发生。** 本轮修正了v212提前暴露未来方案的问题：触发后提案确实进入001的11次实际请求、002的10次请求，但没有对应`offer_joint_arrangement`或`accept_joint_arrangement`。这证明信息被呈现，不能证明被理解或采用。不能再把“发出了提案”当作“组织已经改变”。

### Astropy

**SINGLE代码正确，停在复核接受之前。** 工作包已完成；002已打开固定候选并实际运行8项通过的公测，但未记录`org_review_patch`接受，也未进入正式交付。001消耗88.03%的团队Token，002仅11.97%。

该回合有21次`diff_workspace`调用，其中18次带分页cursor，主要对应约5.1万字符的大差异。不能将它们全部称为反复重复检查：这里既有较大差异内容，也有受管分页带来的行动和后续输入成本。

**COMBO复核路径已走通，但最终合并仍失败。** 双方两个代码候选均取得对方接受，其对应公测分别179项和190项通过；另一个“不改代码”的包已成功创建证据。因此，不能说新复核接口或证据完成入口从未执行。

随后001合入伙伴补丁产生一个实际冲突，最终预测补丁仍含冲突标记，官方测试出现`SyntaxError`。证据包又绑定在更早的版本，与整合后的树不一致；`adopt_evidence`和`review_evidence`因此被拒绝。这里的拒绝防止了错误版本背书，不应直接判为权限bug。待解决的是冲突返修、证据更新和最后交付组成的完整流程。

### Matplotlib

**SINGLE在预算耗尽前形成正确代码，但尚未完成工作包和独立复核。** 001用了94.85%的团队Token，002仅5.15%；已发布候选，却没有局部完成与接受复核记录。

**COMBO已经完成伙伴贡献的真实复核和集成。** 002负责的Text接口与Annotations两个包都完成；001通过新只读候选视图实际复核，公测92通过、8跳过，并将伙伴补丁无冲突合入最终工作树。官方评分确认最终代码正确。

剩余的drawing工作包没有局部完成及对应复核，最终也没有提交。这是“正确代码未转成合同认可的完整交付”，而不是“伙伴补丁从未进入最终工作树”。

门控JSON中的`partner_code_adopted`是“在已正式交付回合中满足伙伴采用”的复合条件。其false不能用来否认上述实际集成事件；本报告直接依据工具回执和世界事件列出机械动作。最终准入失败不变。

## 5 Token消耗的含义

全批实际29,744,694 Token，其中输入29,638,632、输出106,062；输入占99.64%。缓存命中5,417,600，占输入18.28%。所以“每回合接近500万”主要是多轮请求反复带入上下文，不是生成了500万字或500万输出Token。

COMBO平均Token只比SINGLE低约0.17%。**六条都触及5M预约边界，这个均值不能证明组合更省，也不能估计其真正完成工作所需的预算。** 预约需要同时容纳下一次输入与最大输出，因此结束时可以略低于精确5M。

目前能直接观察到的成本包括：实现和定位提前消耗大部分队内资源、分页回读、同一候选的重复接受、交付后继续活动，以及未完成的合并／证据更新。它们同时包含模型行为与接口组织成本，不能全部归为通信费用。

本轮没有可靠完成“通信输出＋接收端输入”的来源分账，因此**不提供通信占总Token的比例**。尤其不能把COMBO相对SINGLE的总Token差直接当作通信成本。

## 6 哪些修复有效 哪些问题仍存在

| 项目 | 本轮证据 | 可支持的结论 |
|---|---|---|
| 固定候选独立复核 | 全批7次打开、7次真实候选公测；组合组6条接受记录，去重为4个actor—候选版本 | 新路径被真实模型使用，复核与主工作树集成可以分开 |
| 失败公测解释 | 同版本失败现在明确返回`work_test_failed`，没有继续伪装成缺版本证据 | 报错语义已修正；检查范围选择及失败处理仍有额外开销 |
| 中途提案呈现 | 真实工作及测试后才进入模型请求 | 提前暴露问题已修复；模型未实际执行调整，动态适配未验证成功 |
| 不改代码的证据完成 | Astropy组合实际完成一份证据 | 入口可执行；随最终合并更新证据的闭合尚未完成 |
| 正式交付与结束 | 5条正确代码、仅1条合法交付；成功回合提交后又花37.5%Token | 最终工作完成和结束流程仍是核心问题 |
| 合并冲突 | Astropy组合最终补丁保留冲突标记，官方语法错误 | 独立候选各自通过不保证整合树正确，最终合并检查不能省略 |

这轮证明了若干工程路径可执行，**没有证明组合组织有净收益，也没有证明预算只要加大就能解决所有问题**。

## 7 性能优化单独报告

v213完成后续评分期间，v214完成本地执行性能修订；v213六条真实生成没有中途切换到v214。

旧版每次提交后清空状态缓存，下一次观察重新解析368MB级状态，同时重复解码122MB级仓库版本及编码审计数据。新版保留受文件身份保护的提交快照，缓存不可变版本解码及JSON字符串编码，权限、事务、哈希与落盘格式不变。

同一固定热路径两轮基准由71.18秒降至7.40秒，约9.62倍；只看第二轮为8.63倍。最终状态字节与规范哈希相同。CPU等价、私有版本权限、失败回滚、提交后重试和真实SDK新进程续接／公测／交付控制均通过。

**该结果不是完整模型实验的端到端加速，也不是Token压缩收益。** 新版已接入后续运行入口，尚未产生新的真实评测成绩。[性能优化详情](software-benchmark-v214-runtime-performance.md)

三个任务是已反复使用的定向回归题，不是独立确认集。本报告中的百分比只是这三题面板结果，既不是完整SWE-bench Verified分数，也不足以给出稳定性、显著性或总体能力结论。
