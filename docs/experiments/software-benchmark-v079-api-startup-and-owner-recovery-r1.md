# v079：API启动补位与故障拥有者恢复

本版本仅准备新的API协调器，不修改正在运行或已封存的v076源码，不控制Qwen模型、任务或GPU。真实执行须由主操作方在原孤立对象和费用全部核清后启动。

v076实际监测中，DeepSeek多数时间约30—38题并行，主机CPU和内存都有余量；四个同时启动名额长期占满，派发到SDK就绪的中位数约78秒。v079把这一启动上限改为8，目标仍44、最多48题，逐任务CPU／16 GiB容器限额、模型、思考、工具、种子及5M token预算保持。API任务继续共同受原 `proworksimv076api.slice` 的224 GiB硬上限保护，不重建或修改父组。

随后原API协调器发生已确认的16 GiB cgroup OOM。该上限覆盖管理进程、导出压缩和host评分子进程，不能解释成单纯API客户端用量。新API协调器为4 CPU／64 GiB、swap0、pids512，保留三条评分线程；启动必须有至少384 GiB真实可用内存。Qwen由独立v080处理，新API读取其资格和进度。Docker评分容器的16 GiB限额仍独立计量，不能因为host评分程序在协调器cgroup内就把Docker容器内存从总账移除。

新监控器分别报告主机、API Docker父组和API协调器自身三个层级。协调器剩余内存低于24 GiB暂停新actor及host评分准入，达到32 GiB恢复；低于8 GiB通过现有局部停止事件回收本项目API回合，不停止Qwen或父资源组。自身探针缺失、读失败或上限不符时停止新增，不把主机空闲充足误当成自身单位没有OOM风险。

新资源实现另接入v080的安全就绪探针：正在写入的空／部分JSON视为尚未就绪，不因一次瞬态解析错误停止整个队列；完整就绪文件仍须满足既定身份和SDK条件。Qwen缺少正常工作席位时，API暂缓新增补位；既有回合不会因此取消。

若Qwen自身协调器已停止或失败，API在原库存全部环境资格已是可信终态、资格引用通过校验且新cursor未改变这些资格时可独立继续；此时不再为无法派发的Qwen固定预留四席。缺资格、资格变化、引用损坏仍拒绝，API自己的源、费用、资源和清理保护保持。这一隔离不允许无条件忽略共享数据完整性故障。

## 两种交接入口

正常交接只把旧API并发目标设为0，等待其生成、评分、请求及资源自然收口。两次相隔至少3秒的新鲜静止证明后，通过pidfd结束确证的旧API主PID，保留父资源组；不对Qwen发送任何信号。新API单位可在后台等候，最多8小时，管理进程临时多占64 GiB且记入实际容量账。旧API退出后它成为唯一API协调器。

此次旧拥有者已OOM退出，**不能使用“自然收口完成”冒充故障恢复**。`--recover-dead-owner`入口只接受主操作方独立完成的证据：原退出与cursor、保留原终态的行政cursor、全部API对象静止／清理证明、保守费用核对、原辅助预约释放。工具再次核验旧单位inactive、API物理预约为空、原账本reserved为0、父组无子cgroup，才封存新的库存。清理、费用恢复本身不由该入口执行。

任何已派发、已有物理创建身份、API请求或部分候选的任务均排除重放；缺终态者继续为技术未知，不能填成模型失败或零用量。旧生成／补丁／评分／费用记录不改写，原1000题分母与1500元唯一账本保留。待评分任务只接未消费的原评分身份；已经消费而未取得可信评分的项目保留技术未知。

部署顺序：先 `prepare_api_startup_v079.py --bootstrap` 封存文件；故障恢复证明齐备后执行 `--recover-dead-owner PROOF_JSON`；待新Qwen已发布可信cursor，再用 `launch_api_startup_v079.py --launch` 启动API。这些命令在本次实现工作中没有执行。

## 必要验证

新增9项CPU控制覆盖：API静止条件、拒绝对未静止任务发信号、故障cursor历史完整性、禁止重放已消费身份、私有runner不改旧全局变量、新单位4CPU／64 GiB、实际物理余量准入、只释放自有预约、信号后不伪回滚。初次有一项测试对字节码导入名的位置断言不正确，修正测试后只重跑这一项；其余八项未重复。限定Ruff通过。

另外新增2项Qwen故障隔离控制、2项API自身内存控制；私有runner绑定随新增分支做针对性复查，不重跑整个旧套。合计13个不同控制覆盖当前增量。

资源侧的启动竞争、Qwen补位和部分JSON控制另见相应v079／v080验证凭据。配置44不等于实测44，须在真实运行中记录actor数量、请求并发、启动中数量、父组内存和逐题完成速率。
