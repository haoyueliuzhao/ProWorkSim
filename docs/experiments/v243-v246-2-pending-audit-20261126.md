## 1　如何读这些实验条件

执行者是两名修题成员。**KEEP** 让他们沿用当前分工。**OSA** 是另一个专管组织决策的 Agent，可以维持分工，或改变某个工作包的负责人、诊断人、复核人和相应的行动顺序。成员负责读代码、修改、测试和交付。以下在线实验使用 DeepSeek Flash 非思考模式和 T1 上下文策略（主要重发有变化的信息）。完整任务从原始仓库和空白会话起步；中途配对从同一个已保存现场分成两支。每支或每个团队共享 500 万输入加输出 token，中途续跑的上限包含此前历史，费用表只算新增实际用量。

**代码通过**指任务结束时的最终工作树通过官方评分。**正确交付**指项目收到合法提交，且该提交版本也通过官方评分。两者可以不同。成员运行中只得到公开测试反馈，最终官方结果在结束后产生。脚本决策、同题重复、没有可恢复保存点的历史事件均单独记账。

## 3　项目图如何实际改变组织图

**规则与离线验证。** 项目图把公开测试回执连接到成员、工作包、测试目标和被测代码版本。相同目标在两个不同代码版本上失败，或同版本三次实际测试仍失败，就进入重评；三次失败落在互不相同的目标时，也可记录为工作包测试持续受阻。读取同一回执不会累加。OSA 看到异常及当前交付要求，决定是否让伙伴独立诊断、移交工作或维持分工；控制器记录实际生效的分工和下一次行动。后续新证据仍可触发，单题没有固定决策次数上限。用 v245.4 的五条历史轨迹回放，有四题出现触发证据；其中 Django-12663 出现在第 43、52、59、75 次行动机会。真实 SDK 的零 API 脚本控制连续执行了维持、移交、指派诊断三次决策，产生两次实际改组。[规则、逐轨迹触发及控制](v246-project-failure-replanning.md) · [控制结果](../../artifacts/software-benchmark-v246/failure-graph-control-r1/results.json)

## 附录　当前 OSA 实际使用的提示词（v246）

OSA 要回答的是：**继续原分工，哪项工作会卡住？如果调整，谁能为谁提供什么新产物？出现什么证据后应当重新判断？** 核对本批 7 道已评分任务的全部 10 份 OSA 请求，7 次例行判断使用同一段英文系统提示，3 次异常重评在其末尾追加一段指令。

每次请求还包含一条随现场变化的 JSON 消息。项目图给出公开事实和回执；工作义务图给出该工作包还欠哪些产物、哪些动作已经可以执行；组织图给出成员和分工。模型同时看到本次可选的行动路线、分工变更、工作指令和剩余 token。异常重评时，项目图还会带上触发重评的测试目标、失败回执引用及已有决策。模型通过一次 `activate_organization` 工具调用提交选择、证据、理由和重新判断的条件；这里的“一次”指每次决策的输出，单题可以再次唤起 OSA。[基础提示源码](../../src/proworksim/software_osa_prompt_v245_4.py) · [异常重评请求构造](../../tools/run_full_osa.py)

### 例行判断使用的系统提示原文

> You allocate work between two workers. Use only the public facts in project_graph. A delivery checklist shows what is currently owed; by itself it cannot establish repeated failure or stalled progress.
>
> 1. What would stall if the current owner continued? Cite the receipt IDs in basis. Classify repeated failure on the same target (A1), a dependency blockage (A2), an integration conflict (A3), a verification gap (A4), or repeated readiness without delivery (A5). Use STABLE for evidenced progress and UNKNOWN when the facts do not distinguish these cases.
> 2. Compare KEEP with the routes actually listed. For a change, name who will produce what, for whom, and why it addresses the observed gap. The actor takes the first action; the assignee may produce the added product later. A pending ordinary edit alone gives no reason to move it. An optional review can add value for a specific risk. Assigning a verifier does not certify a review. Explain the trade-off in reason and name one observable event in reconsider_after that would change the choice.
> 3. Read the dimensions as effects on work. D0 fixes team membership at two. D1 changes a role (e.g. a partner diagnoses a specific failure and returns evidence).
