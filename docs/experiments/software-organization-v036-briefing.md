# 从空任务板到实际协作：任务与职责如何自由形成

**v0.36 同一根任务的代表性轨迹汇报材料**  
日期：2026-10-09。配套：[逐节汇报稿](software-organization-v036-speaking-notes.md)。

本材料面向分工协作机制说明，仅摘录关键行动，不展示完整对话、代码或测试日志。案例均来自已结束的P2支持窗口，没有新增模型调用、重跑验收或恢复实验。

## 1. 核心观点：组织形式由成员行动形成

> **当前机制允许自主组织，也允许重复工作、集中完成或先执行后登记。**

这里的“自由”是在固定根合同、工具权限和共享预算内，成员自行决定执行任务、负责人、协作对象及交付路径。

必须区分三个层次：

| 层次 | 由谁确定 | 本轮观察 |
|---|---|---|
| 根目标与验收边界 | 实验预先给定 | 同一SQL inventory合同、指定API与两个生产模块 |
| 执行任务与正式负责人 | 模型创建、认领等动作，经环境校验后记录 | 初始任务板为空；创建者可以不是负责人 |
| 实际工作与最终交付 | 成员真实编辑、测试、发布、整合和提交 | 可以重叠实现、后置登记、职责标签反转或集中交付 |

**本轮“集中完成”的证据边界：** 机制允许一名成员覆盖整个根目标；本窗口实际能展示的是“完整产物或最终交付集中于一名成员”。16个槽中双方都编辑过两个模块，因此不能把案例说成“另一人完全没有工作”。

## 2. 共同起点：同一任务，没有预设执行岗位

所有案例的根目标均为 `sp-script-inventory-v035`：

- `reader.statement_records(script)`：调用真实sqlparse API，生成按顺序排列的语句记录。
- `report.summarize(script)`：消费reader结果，返回记录、三类语句计数和总数。

A、B使用相同模型参数和初始业务材料，各有私有工作副本及会话；A固定先手，成员共享团队预算。初始执行任务、补丁和交付记录均为空。“实现者”“验证者”不是预先分配的岗位。

任务的状态变化可以概括为：

```text
根合同 + 空任务板
      ↓ 成员自行选择行动
创建执行任务（owner为空） → 某成员认领（owner=A或B）
      ↓                                  ↓
可继续创建/调整任务              编辑、测试、固定发布、显式整合、提交
```

模型也可先编辑、测试，再补建任务。创建者与负责人分别记录；普通消息不会直接改变owner。机制提供委派、退回和依赖调整，但本轮是否使用要以真实事件为准。

**职责记录与文件权限的关系：** owner约束任务修订、依赖操作和关联补丁发布；任务描述不把文件编辑权自动切成专属岗位。成员仍可编辑自己副本内的全部可编辑文件，私人改动通过固定补丁和显式整合才进入伙伴副本。

**仍然存在流程门：** 编辑、测试可发生在任务登记之前；固定补丁发布要求关联至少一个自己负责的任务。自由组织指任务内容、形成时机与责任方式可由成员决定，不表示可以绕过全部交付条件。

## 3. 先看全窗口，再选择案例

统计口径：16条同根目标、不同采样种子的联合轨迹；以下为成功落库的世界事件，不包含被拒绝的工具调用，也不把模型自述当实际完成。

| 全窗口现象 | 观察值 | 能说明什么 |
|---|---:|---|
| 初始任务表为空 | 16/16槽，两成员视图均为空 | 分工没有在启动前填好 |
| A、B均编辑过reader和report | 16/16槽 | 重叠实现普遍存在；没有纯单人工作的样本 |
| 建过任务的槽 | 15/16 | 另一个槽全程没有任务登记 |
| 首次生产编辑早于首次建任务 | 15/15个建过任务的槽 | “先执行后登记”在本窗口是普遍模式 |
| 创建／认领／工作消息 | 21／20／2次 | 主要使用创建与认领形成责任记录 |
| 委派、退回、修订、依赖增删 | 成功事件均为0 | 不能宣称本轮验证了复杂任务重组 |
| 补丁整合 | 14/16槽，各1次，均记录两生产文件冲突 | 存在真实整合，也存在协作摩擦 |
| 提交成员分布 | 9槽仅一人提交，5槽双方提交，2槽未提交 | 交付可以集中，工作参与仍可能分散 |

据此选取槽00、05、13、14、12，分别展示职责方向变化、重叠登记、集中交付和未登记仍行动。**这些是按说明目的选择的案例，不是组织方式的随机样本或效能对照实验。**

阅读约定：A/B对应 `member_a/member_b`；槽号从0开始；`W#n`为该槽的世界事件序号，不能跨槽比较或当成模型轮次。连续或相关动作合并为一个展示步骤。

## 4. 同任务对照：实现／验证标签可以反转

### 案例A｜槽00：A登记实现，B登记验证并最终交付

seed：`202610070101`。**前置事实：** A在W#4/#6、B在W#9/#10都已编辑reader/report；此时任务板仍为空。

| 关键片段 | 实际行动与责任状态 |
|---|---|
| W#11 → #13 | A创建并认领 `member_a_reader_report_impl`；owner由空变为A |
| W#15 | A发布覆盖两个模块的patch-1 |
| W#18 | B整合patch-1；两个模块均出现冲突 |
| W#21–#24（压缩说明） | B修改冲突后的两个模块并取得公开检查通过；成员自测未执行 |
| W#27 → #28 | B此时才创建并认领 `member_b_verification` |
| W#29 → #30 | B发布patch-2并提交最终delivery-2 |

**结果：** R=1；原冻结Mapper识别为有证据的同伴产物交付。它支持有限产物保留关系，不证明伙伴产物对成功具有因果必要性。

**汇报重点：** “验证”是B在已有实现、冲突修复与测试之后登记的职责；不应画成B从一开始就只负责验证。

### 案例B｜槽05：B认领实现，A另建验证任务并最终交付

seed：`202610070106`。**前置事实：** A在W#4/#8、B在W#5/#10都已编辑reader/report；首次建任务为W#14。

| 关键片段 | 实际行动与责任状态 |
|---|---|
| W#14 → #15 | A创建 `task_complete_sql_inventory`，B认领；创建者A、负责人B |
| action-25（被拒调用） | A随后也尝试认领同一任务，环境返回“Task has already been claimed”；owner仍为B |
| W#17 → #19 | A另建并认领 `task_a_verify_implementation` |
| W#21 → #22 | B发布patch-1；A整合后两个模块冲突 |
| W#27–#29（压缩说明） | A修改两个模块并测试 |
| W#30 → #31 | A在“验证”任务下发布覆盖实现与测试文件的patch-2，提交最终delivery-2 |

**结果：** R=1；原冻结Mapper识别为有证据的同伴产物交付。

**汇报重点：** 责任通过真实认领与拒绝规则逐步形成。A的后续新建任务发生在认领被拒之后；这里只说明可观察的顺序，不推断未记录的内部动机。

### 两槽并列结论

| 同一根目标 | 登记的实现负责人 | 登记的验证负责人 | 最终交付者 |
|---|---|---|---|
| 槽00 | A | B | B |
| 槽05 | B（任务由A创建） | A | A |

两槽均由双方先后提交；表中列的是原评估采用的最后一次固定交付。早先提交保留在原事件中，本材料仅展开决定所选案例含义的片段。

两槽初始规则相同，登记职责与最终交付方向不同；同时两槽都先发生了双人重叠实现。“自由组织”在此体现为运行中形成责任记录和交付路径，**并未展示干净的事前专业分工**。

## 5. 槽13：先执行后登记，还可以出现同范围的重复任务

seed：`202610070114`。

| 关键片段 | 实际行动与责任状态 |
|---|---|
| W#5 → #6 | A先编辑两个模块；责任快照为空 |
| W#10 → #11 | A创建 `implement_sql_inventory`，B认领；创建者与负责人不同 |
| W#12/#13/#17（压缩说明） | B也修改两个模块并发布patch-1 |
| W#18 | A整合B的补丁，两个模块冲突 |
| W#25 → #26 | A另建 `my_sql_inventory_task` 并自行认领；两个任务描述相同，各有负责人 |
| W#27 → #28 | A发布自己的patch-2并提交最终delivery-2 |

**结果：** R=1，但原Mapper保持unmapped：已解释的弃用导入不足以证明最终保留了伙伴产物。`included_patch_ids`非空不能直接当作有效伙伴贡献。

**汇报重点：** 机制允许成员先做事、后登记，也允许同一工作范围出现两个任务。任务数量或负责人数量不能直接代表有价值的专业化分工。

## 6. 槽14：完整产物和最终交付可以集中于一人

seed：`202610070115`。

| 关键片段 | 实际行动与责任状态 |
|---|---|
| W#6–#9 | A、B分别修改自己的reader/report；任务板仍为空 |
| W#12 → #13 | A创建 `task_001`，描述仅提reader实现；B认领 |
| W#14 | B在该任务下发布覆盖reader和report两个模块的patch-1 |
| W#15 | A在自己的副本整合B的补丁，两个模块出现冲突 |
| W#16 | B提交完整的本地版本delivery-1，未包含伙伴补丁 |
| W#19 → #20 | A继续修改自己的冲突副本；没有形成第二份提交 |

**结果：** R=1，本地产物交付；本槽只有B提交。

**汇报重点：** 接受的完整交付可以由一名成员覆盖整个根目标，任务文字的名义范围也不等于实际文件操作范围。准确表述是“B集中交付”，不是“B是唯一劳动者”或“本地类代表没有协作”。

## 7. 槽12：没有正式任务登记，也能持续行动，但不保证交付

seed：`202610070113`。

| 关键片段 | 实际行动与责任状态 |
|---|---|
| W#8 → #10 | B编辑reader/report；责任快照为空 |
| W#13 → #15 | A也编辑reader/report；责任快照仍为空 |
| W#17/#18/#34（节选） | 双方执行测试；任务板仍为空 |
| 全槽终态 | 0创建、0认领、0工作消息、0固定补丁、0提交；共13次编辑、6次测试 |

**结果：** 未提交，R=0；未提交的工作区没有隐藏内容验收。不能把此结果解释为已证实所有代码内容错误，也不能只凭单例将未交付归因于没有任务登记。

**汇报重点：** 任务登记不是编辑和测试的强制前置流程；开放的行动空间也包含没有形成有效交付的路径。

## 8. 汇报落点：把机制允许、实际行为与效果证据分开

| 重点 | 本轮可讲的事实 | 保留的边界 |
|---|---|---|
| 自主组织 | 空任务板出发，成员生成任务并认领；创建者与负责人可不同 | 根合同、工具和预算仍由实验固定 |
| 重复工作 | 16/16槽双方均编辑两模块；槽13出现同描述双任务 | 不等于证明重复工作全部无价值 |
| 集中完成 | 槽14完整产物与最终交付集中于B；9槽仅一名成员提交 | 本窗口没有纯单人工作的样本 |
| 先执行后登记 | 15/15个建任务槽都先发生生产编辑 | 不把后置标签包装成事先规划 |
| 真实协作 | 槽00/05发生伙伴补丁整合、冲突处理及最终交付 | 不据此宣称最优分工、因果必要合作或训练收益 |

**建议结论：** 当前系统已经能承载并记录成员自行形成的任务与职责。这个固定窗口展示的主要模式是“先重叠实现，后登记、整合与交付”；后置责任标签和交付方向存在变化。开放机制允许多种工作路径，但高效、稳定的专业分工仍需要进一步证据。

实验继续保持“取消后续试训、等待审计”。本材料不讨论恢复执行，也不将组织案例当作B/G-raw/I-P效果对照。
