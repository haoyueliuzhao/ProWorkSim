# v089：DeepSeek 增补预算后的独立恢复回合

本轮依据用户“DeepSeek 组增补两百预算，完成后对技术未知进行处理”开展。现金总上限从 1500 元增至 **1700 元**，沿用同一个账本；旧实际费用、未定费用预约均保留，不退款、不重置。本文件记录恢复设计与 CPU 核验；实际启动及结果以 `runs/software-benchmark-v089/budget-recovery-r1/` 的执行回执为准。

## 1. 为什么需要独立恢复身份

v088 已没有未消费的生成库存。其原 1000 个 DeepSeek 5M 逻辑槽终态为：722 正常闭合、249 技术未知、29 未进入。最近 61 个原库存已全部进入协调器，其中 44 个在唯一 `cash_exhausted` 事件之后结束：43 个为协调器预算退出取消，1 个为派发前预算停止。其余 205 个历史生成未知属于后续异常处理阶段。

不能将 44 项称为“继续尚未开始的题”。当前没有可核验、可跨进程恢复整个模型会话和容器状态的完整检查点：REF 的会话持久化文件不足以证明外部执行状态可精确续接；PROJECT 声明 `model_can_resume=False`；冻结 episode 路径会创建新 actor/controller。因此，44 项分别获得 **一次从原初态开始的独立恢复回合**，保留同题、同 seed、同模型、同 5M 配置。

新操作身份为原 `slot_id` 加 `:recovery-v089-r1`，物理索引固定为 6000–6043。原 ID 由 `original_slot_id` 显式关联，原配置只改操作身份与物理索引；原首轮结果、目录、资源 claim 和 API 请求保持原样。独立恢复不是首轮改写，也不能描述为每题合计只用过一次 5M。

## 2. 事前固定范围

| 项目 | 本轮范围 |
| --- | --- |
| 恢复面板 | 全部 44 个预算行政中断，REF 21、PROJECT 23 |
| 筛选依据 | 原现金截止事件、取消原因、结束时间及原对象已清理证据；不看分数 |
| 每恢复回合上限 | 原输入＋输出合计 5,000,000 token |
| 新增生成上限 | 220,000,000 token；不是预计消耗 |
| 现金上限 | 所有旧费用与本轮共享 1700 元，不保证一定能覆盖所有回合 |
| 新资源身份 | 44 actor、44 controller、44 专用卷、44 代码评分、最多 23 交付评分 |
| 新模型驻留 / GPU | 0；不操作 Qwen 生命周期 |
| 评分 | 原官方评分规则与已合格环境控制；候选先锁定，评分不反馈模型 |

44 项不含 Requests 任务，本阶段不新增真实 TLS 通道或评分出网。原模型输入、工具、任务信息、公开测试和隐藏评分隔离保持；没有修改冻结的 v064–v088 源文件。

## 3. 执行和故障边界

新普通用户协调器使用原 CPU 168–175 片段，8 CPU、MemoryHigh 32 GiB、MemoryMax 64 GiB、swap 0、FD 16384。API 请求目标上限仍为 48，批量启动上限 16；实际并发继续受父组、CPU、物理内存和磁盘约束。API actor/controller 使用原获授权的同名 224 GiB、swap 0 父组的新生命周期；该父组由独立模块检查原生命周期释放证明后创建，不修改其他共享服务。

所有新资源与在途 Qwen 继续共用原 `resource-claims/allocation.lock`。独立新 authority 精确列出 44 项及其原逻辑映射；不把新物理身份伪装成原 6000 个身份之一，也不重用已消费 claim。原资源范围之外的模型、环境控制和历史候选不能由此计划创建。

复用 v088 的 poll 通道、FD 关闭策略和本地初始化故障隔离。生成、评分准备、官方评分与交付验证保持异步；评分准入不依赖已结束的 API 父组。管理进程与有界评分子进程使用相同的封存恢复评分 manifest，避免不同资源包装器被误判为评分器变更。

真实共享完整性、费用或清理状态未知仍须止损；单题已证明局部故障独立入异常集合。此修订没有宣称所有历史未知已修复。

## 4. 结果记录与后续顺序

新恢复结果单独报告 REF 21 / PROJECT 23 的闭合、代码正确性、PROJECT 交付及实际 token 使用。完整恢复组的平均 token 仅在全组用量已知时提供；否则报告已知用量下界、可确定用量子集均值及分母。原 1000 题首轮状态与得分不覆盖，旧费用不会重复累加到恢复 token 小计，现金总账仍包含全部旧费用。

44 项终态形成后，协调器写出 `after-recovery-technical-worklist.json`，包含：205 项历史生成未知、原评分未知，以及本阶段新产生的未知。该待办只建立处理顺序，不会自动再次调用 205 个模型或重复评分身份。后续需按剩余现金、可恢复原候选及具体故障证据制定单独阶段；不能按失败成绩挑题。

## 5. 必要核验

CPU 控制覆盖：原配置只允许改变操作身份、预算截止面板固定、资源计划只有新身份、实际私有 claim 使用共享锁且旧 claim 不变、重复身份拒绝、poll / 局部故障绑定、新评分 identity 与管理/子进程 manifest 一致、普通用户服务资源边界。七项最终通过；早期测试夹具缺少 source index 与官方包占位，修正夹具后仅重跑相关失败项，未由此产生模型或容器调用。Ruff 通过。

另外读取真实 v088 原件，核验 44 个精确映射，并分别以 REF 和 PROJECT 代表项调用冻结 controller 输入投影和原评分资格验证。两项均通过；PROJECT 夹具按原 episode 规则补上公开测试 entry 后通过，产品配置未改变。记录见 [只读核验](../../artifacts/software-benchmark-v089/recovery-inventory-readonly-r1/summary.json)。以上 CPU 证据不冒充真实执行成功。


准备后不热改已封存源码；部署出现问题应保留原回执并使用明确的新修订处理。
