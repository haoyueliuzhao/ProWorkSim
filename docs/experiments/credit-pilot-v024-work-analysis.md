## MC 三个成功实际包含什么

**一例当前真实实现交付，另外两例是对继承正确产物的当前独立核准。**后两例合法且有实际复核证据，但不是成功修复错误初稿。

| episode | 直接记录 | 支持的结论 |
|---|---|---|
| MC eval-01-0 | 提供者交接 seq30；实现者读取依据 seq42、数据 seq65；采用依据 seq88、数据 seq134；写代码 seq176；正确 build seq189；新 submit seq241 | A 的当前完整实现交付。保存事实同时具有 `current_actor_build=true`、正确当前构建及新固定交付 |
| MC eval-02-0 | `initial_correct=true`；固定产品仍为初始 submission-1/code v2/result v2；reviewer inspect seq18，data read seq41，audit read seq87，code read seq110，result read seq133，approve seq156 | 继承正确产物，当前有充分独立复核并合法核准；`current_actor_build=false`、`current_repair_build=null` |
| MC eval-02-1 | 同一正确初稿情境的另一重复；reviewer inspect seq18，data seq41，audit seq87，code seq110，result seq132，approve seq150；固定版本不变 | 同上，是第二条合法核准经历，不是第二种修复方法 |

在这 12 槽上，MC 相对 θ0 出现了完整职责改善，不能把结果退回为“仅参数更新接通”。但三条成功只覆盖两个独特情境，并且两个 B 成功来自同一个正确初稿情境。错误初稿 B 和两种维护条件均无完整职责成功。

## 没有完成的部分工作也应保留

**交接仍然稳定，但不能代表后续闭合。**三 checkpoint 的四个 A 均完成合法依据送达。θ0 和 RTG 的 A 都仅取得该 0.2。MC 有两个 A 继续取得依据用于正确构建；其中一个完整提交，另一个未完成固定交付。

MC `eval-01-1` 的实现者先在 seq18 发出信息请求；提供者 seq30 的实际交接没有绑定 `request_id`。实现者随后读、采用并于 seq187 正确构建，但 seq213、252 的 submit 均被真实世界拒绝，原因是工作尚未开放提交。seq226 试图将信息条件当 issue 响应也被拒绝。已有依据送达与正确构建得到原 R=.5，未闭合请求阻塞了完整交付；不能因为数值正确而补给完整职责。

**RTG 有一条正确的新固定替换，但完整修复链仍不合格。**`eval-03-1` 从错计数初稿开始，实现者 seq122 真实 withdraw，seq145 改代码，seq168 build，seq191 提交新的 submission-2/code v3/result v3。保存的 `final_fixed_build` 非空且 `current_actor_build=true`，说明不能将 RTG 的 0/12 解释为“没有任何有用修正”。但实现者当前调用记录没有读依据 basis；冻结评分要求的当前源读取证明未满足，`current_repair_build=null`。reviewer seq202 才对已撤回的旧 submission-1 提 issue，实际结果 `active_at_creation=false`，保存判断 `valid=false`；之后只 inspect 新提交，没有完成当前独立最终核准。原 R=0、Y=0 保持。

MC `eval-05-1` 和 RTG `eval-05-0` 均完成了数值不需变化的维护独立核准，取得 R=.7，但均未满足实现者当前完整检查证据，Y=0。这不是完全没有检查尝试，也不是独立核准无效；缺失的是完整维护责任要求的另一部分。

## 复核与失败类型

下表只计实际成功存储的正式 `approve`/`raise_issue`，并沿用保存的独立有效性判断。`approve` 工具返回成功不等于业务核准有效。未出现成功存储的正式判断不等于完全没有读取、思考或被拒绝的判断尝试。

| 指标 | θ0 | MC | RTG |
|---|---:|---:|---:|
| 有复核职责 episode | 8 | 8 | 8 |
| 无成功存储的正式判断 | 2 | 4 | 2 |
| 有效 approve | 0 | 3 | 1 |
| 无效 approve | 1 | 1 | 4 |
| 其中缺充分读取证据的 approve | 1 | 1 | 3 |
| 其中读取证据完整但业务错误的 approve | 0 | 0 | 1 |
| 有效 raise_issue | 2 | 0 | 0 |
| 无效 raise_issue | 3 | 0 | 1 |

- θ0：对正确 B 初稿的两次正式 issue 均无效；错计数 B 的两次 issue 有效，但没有完成后续修复。数值变化维护没有最终正式判断；不变维护分别出现无效 issue、无充分证据的 approve。
- MC：正确 B 的两次当前核准都有效；错计数 B 两次没有正式最终判断。数值变化维护两次没有合格重建与最终复核。不变维护一次无充分证据核准、一次独立核准有效但实现者检查证据不足。
- RTG：正确 B 一次无充分证据核准，另一次重新提交继承产物但无最终核准；错计数 B 一次无充分证据核准，另一次发生上述正确新替换但最终复核未闭合。数值变化维护一次在读取证据完整后仍核准旧不适用产物，另一次没有最终判断。不变维护一次独立核准有效但实现者检查证据不足，另一次核准证据不足。

“无效 issue”本身不唯一识别数值判断、引用位置、当前性或证据哪一项错误，不能把所有无效 issue 重命名为“内容错误”。保存的 `final_fixed_build` 也结合内容与真实构建来源证明，并非另行计算的纯内容指标；B 的通用 `current_correct_build` 字段本就不使用，不能据其为空断言没有新正确产物。

## 结论边界

本次有限工作比较不支持 Handoff-RTG 优于 MC。MC 的完整职责观察增加是真实工作结果，主要由一次当前 A 交付和同一正确 B 情境两次独立核准构成；未形成成功错误修复或维护的完整示范。RTG 改变时间信用后的训练机制结果应与上述工作终点分别报告，不能用机制变化、loss 或工具次数替代 Y。

这仍只有一个训练起点/seed、每臂两个窗口、六个同来源情境各两个重复。共同首窗数据被两分支分别消费，第二窗各自重新采样。观察到的有限样本差异不足以证明“提前结算交接必然损害工作”或解释其因果机制，也不能从 v0.23 与本轮不同材料/剂量之间直接相减归因。没有外部模型评价，也没有 ID-VTDO 配置干预。
