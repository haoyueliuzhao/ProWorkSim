# v145：21项API技术未知的根因核查与修复边界

核查日期：2026-11-07，北京时间。对象为v142题单、v143实际部署的40题×S1／FREE2／REVIEW2共120回合。本文读取原记录与账本，不修改原实验结果。停止候选补评已执行，结果见[修复与补评汇总](software-benchmark-v145-repair-and-rescore.md)；用户随后授权的完整独立恢复见[v146](software-benchmark-v146-independent-recovery-plan.md)。两类结果分开，不把停止补评当作正常回合完成。

## 1. 已核实的故障规模

全批7396次请求中7375次正常结算、21次未定，请求级异常比例为**0.284%**。但每次请求异常都终止所在团队回合，造成**21/120＝17.5%**回合技术未知。原主队列于18:01:46结束，99回合正常闭合并评分；21回合清理证明完整，原停止工作树与账单记录保留。

| 条件 | 正常请求 | 未定请求 | 正常回合 | 未知回合 |
| --- | ---: | ---: | ---: | ---: |
| S1 | 2049 | 0 | 40 | 0 |
| FREE2 | 2710 | 11 | 29 | 11 |
| REVIEW2 | 2616 | 10 | 30 | 10 |

21项包括11次HTTP 500、8次HTTP 503和2次无HTTP状态的`ValueError`。每个受影响回合恰好1次未定请求，没有自动重试。未出现HTTP 429，因此没有证据把本次故障解释成达到API并发配额。

官方把500归为服务端错误、503归为服务过载，并建议短暂等待后重试。这支持对19项5xx的分类，但不能从响应状态反推出供应商内部哪个组件故障。[DeepSeek错误说明](https://api-docs.deepseek.com/quick_start/error_codes/)

21个受影响回合此前已有535次成功调用，合计**23,437,749个已知token、19.98978688元已结算费用**，另保留**7.252874元未定预约**。这些已完成工作因整队停止而没有正常最终评分，不能将其token或费用删除，也不能把未定请求记成零消耗。

## 2. 为什么不能归因于“双人协作更容易报错”

S1最后一次API调用在14:21:36结算；21个未定请求的预约时间均在15:02—16:07。故障时S1已经结束调用，两组双人成员仍在运行。**条件与运行时段混杂**，因此本轮未知集中于双人组不能证明协作本身造成API错误。

这21个请求的输入预约上界中位数为36,007 token，成功请求为53,941 token；异常请求范围为11,856—97,414。没有证据表明只有大上下文或接近上限的请求才失败。21项都是agent调用，输出预约均为32768，但正常请求也几乎全部采用该输出上限，不能据此推断输出上限为原因。

账本保存的是预约时间，未定请求没有结算时间；上述时间窗口不能当作服务端报错的精确时间。故障有明显时间聚集，本文不使用独立同分布假设外推回合失败概率。

## 3. 已定位的本地系统性放大机制

**第一，一次可恢复的服务错误直接升级为整回合终止。** `software_benchmark_deepseek_api_v105.py`的直连传输遇到非200就抛出异常，500／503没有有限退避。v142客户端将其记为未定，再抛出`APIUncertainFailure`；团队账本拒绝该队后续请求，SDK以“One SDK transport attempt did not complete”结束整队。保持未定费用预约本身是必要的，但把“账单尚未确定”和“必须放弃整个任务”绑定起来，造成了上述放大。

**第二，冷却机制不适合并发下成功与失败交错的情况。** 当前采用全局连续3次错误触发冷却，而任何成功响应都会把连续错误计数清零并删除冷却。并发期间，其他任务的一次成功可能抵消正在出现的服务故障信号。源码证实这一机制存在，但历史记录没有逐次冷却事件，不能声称本次从未进入冷却。

**第三，错误证据过少，妨碍根因追踪和可靠恢复。** 当前异常记录只保留类型、HTTP状态和统一原因；传输丢弃非200响应体，包装又丢弃底层错误阶段与正文。保密应通过字段白名单与脱敏实现，不能把诊断信息全部压缩成`ValueError`。

代码位置：[直连传输与结算](../../src/proworksim/software_benchmark_deepseek_api_v105.py)、[本批团队客户端](../../src/proworksim/software_benchmark_deepseek_api_v142.py)、[历史未定记录与冷却](../../src/proworksim/software_benchmark_deepseek_api_v055.py)、[SDK异常闭合](../../src/proworksim/harness_sdk.py)。本次修复应置于新版本，不能热改原冻结部署后把新旧结果混为一体。

## 4. 两次ValueError仍有哪些不确定性

两次分别位于10094（FREE2，seaborn-3069）和10107（REVIEW2，pylint-4604）。账本没有错误正文和失败阶段；所有21项未定请求均没有`response_observations`，全批没有`provider_protocol_events`，没有可追回的权威响应usage。已有证据不能唯一判断是传输对象重复使用、响应字节边界、JSON对象形状等哪个分支，也不能直接把这两次归为供应商故障。

官方说明非流式请求可能通过空行保活，流式请求则使用SSE注释；10分钟内仍未开始推理会断开连接。现有`json.loads`接受JSON前后的空白，因此**没有证据认定正常空行心跳就是这两次错误的原因**。未来需要保留解析阶段、状态和字节计量，才能区分空行后正常正文、仅心跳后关闭、非JSON错误体和正常响应。[DeepSeek连接与心跳说明](https://api-docs.deepseek.com/quick_start/rate_limit/)

## 5. 修复与恢复应满足的约束

1. 在新版本中，对已完整收到的500／503引入有限次数退避；每次物理请求有独立身份、次数、时间、费用预约与错误记录，成功响应仅执行一次，不重放已执行工具动作。
2. 未定费用不清零，未知token采用明确保守占用；重试同时受现金、团队token、次数和总时间约束。不能宣称供应商5xx必然不计费，也不能因恢复而突破原400元上限。
3. 采用不会被任一成功请求直接抹掉的冷却期限或滑动窗口，并分别记录请求故障与整队结果。
4. 保存脱敏错误代码、错误阶段、HTTP状态、响应字节数／摘要、请求标识、重试谱系及结束时间；不保存认证头。
5. 对旧21项，先锁定唯一停止代码候选进行独立补充评分；这不能补造合法交付、正常SDK闭合或完整用量，也不是模型续跑。若以后新增独立模型尝试，应单列身份和成本，不能覆盖旧记录。

新版本必要CPU控制应覆盖：500后成功、503连续失败及次数边界、成功响应仅返回一次、取消与总时间边界、预算不足拒绝继续、错误证据保留，以及并发成功不会提前清除既定冷却。正式恢复状态和补评结果由本轮执行记录更新，本文仅给出核查事实与实现要求。

机器可读逐项证据与统计见[根因核查摘要](../../artifacts/software-benchmark-v145/api-rootcause-r1/summary.json)。摘要保留原账本路径、原结果摘要、源码身份和21项请求明细，不含密钥。
