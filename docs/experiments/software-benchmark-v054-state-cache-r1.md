# v054 S1 已提交状态读取缓存：实现与必要 CPU 对照

本修订仅为 `software_benchmark_world_v054.SoftwareCollaborationWorld` 安装 `CachedStateStore`，减少同一已提交 `state.json` 的重复读取与 JSON 解析。全局 `Store`、原子持久化、事务锁、恢复、工具 schema、分页、Γ1、模型与预算保持原实现。没有启动模型、GPU、公测或官方评分，也没有修改已完成回合的世界。

## 证据与收益范围

使用已完成 Django `django__django-11276` 的 PROJECT 槽 6，源状态文件 91,426,372 B，SHA256 `a0277054e10afe853cd87f94d8ce1cc3490b76bf20d7c7010aa899164229ecb3`。在实际控制器使用的私有 Python 3.12.3 CPU 环境中，仅对独立临时副本测量。临时目录在控制结束后删除，正式源文件身份保持不变。

先做分阶段基线，三次暖文件读取分别为 1.041、0.999、1.055 s；`deepcopy` 为 0.0662、0.0667、0.0662 s；原 `json_bytes` 为 1.090、1.121、1.138 s。一次完整 `atomic_write`（含真实 `fsync`）为 0.125 s。`cProfile` 显示读取中包含文本解码与 JSON 解析；写入仍包含完整序列化和 fsync，不应把所有耗时都称为磁盘等待。原始基线及 profile 见 [基线回执](software-benchmark-v054-state-cache-baseline-r1.json)。

新实现的三对交错暖读取结果：

| 读取方式 | 三次耗时 / s | 中位耗时 / s |
|---|---|---|
| 原 Store | 1.13382、1.09089、1.09289 | 1.09289 |
| 缓存命中后 deepcopy | 0.08809、0.08523、0.08334 | 0.08523 |

该局部读取耗时减少 92.20%。首次未命中为 1.27641 s，仍须从真实 JSON 读取并复制；每次保存后缓存失效，下一次读取再次走完整读回。不能把缓存命中的数字推广成整个 PROJECT 的提速。

另对两份完整独立世界副本各执行一次真实 `read_task` 事务，事前均读取一次以代表 `observe → action` 的同版本再次读取。未触发测试、模型、隐藏评分或源码修改。

| 项目 | 原 Store / s | 新缓存 / s |
|---|---:|---:|
| 完整 read_task 事务 | 6.29511 | 5.63270 |
| 事务内 load（各 1 次） | 1.08699 | 0.06818 |
| 原 recover（各 1 次） | 0.36513 | 0.35817 |
| 原 save（各 1 次） | 1.28816 | 1.39839 |

原事务中 `load + recover + save` 占 43.5%，其中读取占 17.3%。这一对动作总耗时观察到约 10.5% 减少，存在 CPU 调度与文件缓存噪声；仅有一对，不能据此给总体性能保证。公测数百秒等待和其余动作开销未被此缓存解决，也未声称已归因于状态读写。

## 语义与持久化

缓存只有一个槽：一个磁盘文件身份和一个从原 `Store.load` 得到的 JSON 规范值。文件身份为 `(st_dev, st_ino, st_size, st_mtime_ns, st_ctime_ns)`；读取与拷贝前后都核对身份。命中也始终返回 `deepcopy`，调用者不能通过未提交的修改污染下一次读取。文件改变则重新读盘；读期间发现文件变化时不安装该读值的缓存。

`save` 直接调用原 `Store.save`，保存前后都清空缓存，包括异常退出。没有把输入对象作为缓存：原 JSON 往返会将 tuple 转为 list、将键规范为字符串、打断对象别名；NaN 等非法值仍在原序列化路径报错。原 `json_bytes` 排版、原 `atomic_write`、权限 0600、真实 fsync、原子替换、事务锁和完整恢复均保留。原世界构造器先完成原有 schema 与恢复检查，再替换成 v054 专用 Store，并保留原 fault hook。

完整事务字节对照只固定显式 `request_key` 与用于 `wall_seconds` 的时钟值；实际性能测量使用未替换的 `perf_counter`。两版工具输出 SHA256 同为 `e30d6cee1508fd0666ad5c58111d3bb36d65b75351aeddece44a54443f646a8c`，提交后状态 SHA256 同为 `2c05d816f201689c49099fd7997487b29afdd94b06ae5b35e8247296b1d72bc5`。正式运行继续记录真实 `wall_seconds`，因此不声称不同耗时的实际回合会有相同时间字段或相同整份文件哈希。

## 必要控制与边界

[控制回执](software-benchmark-v054-state-cache-control-r1.json) 的 16 项均通过，包括独立 load 返回、未 save 异常隔离、JSON 别名与类型规范化、原字节及 fsync/权限保持、同长度同 mtime 外部原子替换失效、可观察 ctime 变化失效、读中替换、失败 save 不污染状态、实际 read_task 输出与事务字节一致、原世界未改动。

缓存依赖现有单写者锁及原子提交协议。初次小型控制额外试验了绕过协议的同 inode、同长度、同一个时间 tick 内原地写入并人工恢复 mtime，观测到 ctime 也可完全相同；纯 stat 缓存无法识别这种元数据相同的外部改写，初次该项断言失败。该失败发生在小型语义夹具阶段，尚未执行大文件 benchmark 或真实世界动作。随后保留诊断并明确范围：授权 `Store.save` 始终原子替换，S1 也不能任意写控制状态，因此该非协议写入不是缓存的保证；本实现不提供通用防篡改检测。不增加整文件重复 hash、inotify 或其他依赖来掩盖此边界。

本轮没有重跑原 UID、三组 CPU、模型容量或官方评分控制。改动仍须随新的运行源码版本冻结；已经完成的回合保留原源码身份。
