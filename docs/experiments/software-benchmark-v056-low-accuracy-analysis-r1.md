# Qwen REF 正确率偏低的进一步分析

日期：2026-10-24。分析对象仍为 v056 的50题、四档预算、200回合。未重新运行模型；新增的3次CPU评分仅用于官方参考修复的环境对照，不并入模型成绩。

**本次最重要的新发现是：现有评分环境不能让三题的官方参考修复通过。因此，低分既包含预算与模型执行问题，也混入评分环境失效，不能把全部“官方未通过”解释为模型修复能力不足。** 原始分数继续保留，但在环境修复和原候选补评前，不应把它视为已经排除环境因素后的模型正确率。

## 1. 预算不足解释了低档，但不是大预算组的主要停止方式

| 原始评分中未通过的回合 | 预算截止 | SDK stuck | 正常结束但未通过 | 合计 |
| --- | ---: | ---: | ---: | ---: |
| 四档全部 | 59 | 24 | 31 | 114 |
| 仅500万与1,000万 | 7 | 17 | 25 | 49 |

50万档88%的回合被预算截断，扩大预算确有必要。但大预算组49个原始未通过回合中，只有7个因累计预算停止；另外42个已经因为其他原因结束。继续提高总token上限，不能自动解决这些问题。

这张表按**终止方式**划分，不是因果贡献分解。正常结束、stuck等回合仍可能受到评分环境影响，不能把25个正常结束失败全部称为模型逻辑错误。

## 2. 评分环境问题已经得到阳性对照验证

四个requests任务在四档下共16回合全部记录为未通过，日志均有网络错误。为排除“只是模型补丁写坏了”的解释，选取三种明确故障案例，用固定数据集中的**官方参考修复**在评分端独立执行。镜像、基线、官方harness、4CPU／16GiB、禁网和测试上限均与原评测保持一致，参考修复未交给任何Agent。

| 官方参考修复对照 | 官方结果 | 实际失败证据 |
| --- | --- | --- |
| requests-2931 | 未通过 | 目标修复测试通过；2个既有连接超时测试预期超时，实际立即报`Network unreachable` |
| requests-1921 | 未通过 | 5个目标测试和38个既有测试未通过；测试日志出现`httpbin.org` DNS失败 |
| requests-5414 | 未通过 | 目标修复测试通过；4个既有连接超时测试因`Network unreachable`失败 |

三份参考补丁均成功应用，三个评分容器均已清理。2931／5414日志另见httpbin fixture递归等问题，5414还缺少trustme；这些也是环境诊断信息，但不能把每条错误都当成一个独立失分原因。

对应三题的12个原模型回合中，**10个的目标／既有测试未通过集合与官方参考修复完全相同**；另外两个50万回合还额外未通过目标测试。第四题requests-1766只有日志疑点，本次没有执行参考修复对照。

据此可以确定：当前固定评分环境与这些任务的测试要求不相容。**不能将这些false全部归因于模型，也不能反向把这10个模型回合直接改判成功。** 模型补丁在修复环境后是否完整通过，仍须对原锁定候选重新评分。不得简单删除requests题目、缩小分母，再对外报告一个更高分数。

原报告的72个通过、114个未通过、14个生成未知保持原始记录。先前完成率范围只处理14个生成未知，未包含此次发现的评分环境有效性问题，因此不能继续当作校正后正确率的完整范围。

## 3. 长回合中存在反复执行、无法输出有效行动的问题

全部26个SDK stuck回合中，23个被记录为重复动作和反馈，3个为连续仅思考、没有正文或工具行动。500万与1,000万档的18个stuck中，17个原始评分未通过。

这些回合往往仍有大量预算。例如1,000万档：

- **xarray-3677**只用了约21.5万token，就连续4次读取同一文件的同一行段。
- **astropy-13579**只用了约31.1万token，反复执行同一段报`too many values to unpack`的脚本。
- **pytest-7490**还剩约779万token，仍反复调用think。
- **pytest-7571**还剩约866万token，末尾连续3次没有有效行动；最后一次输出32,768 token全部用于思考。

这说明一部分任务缺的是从反馈转向有效行动的能力，单纯增加累计余额没有解决它。23个动作循环具体包括：重复文件查看7个、think循环6个、其他terminal重复5个、重复等待／中断2个、重复失败脚本3个。它们是已有轨迹中的现象，不意味着停滞检测器的每次判定都错误，也不应直接取消检测器来延长无效运行。

另有165次明确的原生工具拒绝，其中140次是terminal拒绝多条未正确串联的命令。这个计数来自11,303次远程工具RPC，不是165个任务，也不等于165次测试失败。这属于本轮**REF原生工具的使用约束**，不是PROJECT多智能体协作规则造成的成本。

## 4. 真实修复中存在需求覆盖和验证覆盖的缺口

31个“正常结束但原始评分未通过”回合覆盖15个任务。逐题取最高预算的一个代表进行诊断，共12个1,000万档、3个500万档；它们是事后故障分析样例，不是新的随机评测集。

有明确代码和测试证据的例子包括：

- **Django-15957：需求语义偏差。** 需求是每个父对象分别取前几个关联对象，候选却对全部关联对象整体切片。它通过了116项公开测试，但官方逐父对象结果断言仍失败。
- **Seaborn-3187：遗漏另一条接口。** 题目同时提到objects与scatterplot，候选只修objects路径。公开159项测试通过，另一条绘图接口的图例仍错误。
- **SymPy-15017：相关约束没有一起修复。** 修改了rank-0数组的长度和迭代，但`array[0]`仍抛出索引越界。
- **pytest-7432：修复伴随另一行为错误。** 改善了skip定位，却破坏`--runxfail`的行为。

这些证据更支持“只覆盖部分需求、局部修补没有保持整体约束、验证没有覆盖新边界”，而不是笼统地说模型完全没有测试。部分案例确实运行了不少公开测试，但既有测试通过不等于新需求被完整满足。

测试入口选择也有摩擦：SymPy-15017在正确的testbed Python中调用`python -m pytest`，该环境没有pytest，而仓库实际入口是`bin/test`；之后主要依靠手工Python检查。Django-13807多次使用不正确的测试模块／settings路径。现有证据不支持将它们称为忘记激活环境或整个环境无法运行测试；更合理的方向是让Agent能取得并正确使用仓库公开测试入口。

另外两个pylint代表因官方测试收集时所需符号缺失而停止，相关符号在原基线和最终候选中都不存在，文件也未改变。这可能涉及支持API未实现或测试契约问题，尚不能直接归为候选删除代码、一般环境bug或多项独立断言失败。

## 5. 还有适配与单次输出问题，但其分数影响尚未量化

已确认本地模型响应中的`reasoning`没有映射到SDK使用的`reasoning_content`。用实际响应做CPU转换对照，8,440字符思考字段在原路径中丢失，规范化字段后可以保留。**这是明确的适配遗漏，但还不是已量化的分数损失。** SDK对空回应和仅思考回应使用相同的纠正规则，不能据此宣称修复字段就会挽救前述3个无行动stuck。

14,048个已记录完整响应中，27次显式标记`finish_reason=length`，涉及13回合；另按实际用量统计，共61次达到32,768单次输出上限，涉及24回合。部分达到上限的响应被标记为tool_calls，所以二者不能混作同一个计数。增加累计预算不会提高这条单次输出上限；但出现输出上限也不自动说明最终修复失败。

相比之下，已记录请求的最大输入为65,044 token，最大实际输入加输出为83,141；没有观察到可信闭合回合因总上下文、512次共同上限或6小时期限终止。因此，当前证据不支持优先靠继续扩大总上下文或调用上限解决低分。109回合发生过历史摘要、共380次摘要响应；没有硬context拒绝也不代表摘要完全保留了信息，摘要损失仍需单独消融，不能凭长轨迹直接归因。

## 下一步优先级

1. **先修评分有效性。** 在评分端补齐任务所需的依赖／服务／网络条件，要求官方参考修复对照通过，再补评原锁定候选；保持Agent禁止联网获取答案的边界。
2. **再处理可确认的执行问题。** 修复reasoning字段适配，改善公开测试入口信息与工具错误反馈；对重复动作、只思考不行动做有针对性的诊断。
3. **最后用可信评分判断模型能力与预算。** 重点看需求分解、跨接口覆盖和修复后的回归验证。500万可保留为较宽松预算候选，但现阶段不应凭受环境影响的分数宣布其最优，也不宜仅靠继续增加token推断会追平外部成绩。

本轮只测REF。上述公共执行／评分环境与本地模型适配问题，不能直接归因于PROJECT的多智能体权限、通信或交付规则；这些规则的额外影响仍需要同题、同预算的MATCH↔PROJECT比较。
