## 1. 修复的范围

原执行层把一次500／503与不可恢复的传输未知一起升级为整队停止。本版本拆开“本次响应能否恢复”“费用与token是否已知”“整个团队是否还能在预算内继续”三个状态。

| 情况 | 新行为 | 计量方式 |
| --- | --- | --- |
| 完整收到429、500、502、503、504响应 | 同一逻辑请求最多3次真实HTTP尝试，采用有限指数退避、抖动与受限Retry-After | 每次独立请求身份；失败继续保留现金与token预约上界，成功仅记录权威usage |
| 超时、断连、截断响应、JSON解析或结构未知 | 不盲目重试，保留阶段与诊断证据 | 不把未定预约记成零，也不填成实际消耗 |
| 已知usage但输入／输出边界或finish_reason不合格 | 结算已知费用，明确协议异常，不把响应交给模型继续执行 | 原始usage保留，不因错误重复扣账或重试 |
| 单次成功与其他请求错误交错 | 共享60秒滚动失败窗口，3次可恢复错误触发30秒冷却；成功不会清空窗口 | 冷却和退避不持有HTTP并发槽 |
| 重试前现金、团队token、次数或时间不足 | 在新HTTP前停止，保留此前尝试 | 已发送过HTTP的逻辑调用不会被错误标成“完全未调用” |

同一逻辑请求的正文、工具schema、user_id和采样设置保持；成功响应最多返回一次，没有重放已经执行的工具动作。每队真实HTTP尝试合计仍最多512次，已知token加未定token预约上界不得超过5M。SDK继续按权威响应计算已知用量，外层账本额外守住保守预算；两者不能混成“实际token”。

网络仍使用普通用户直连官方TLS主机，无代理、重定向或联网搜索入口。诊断持久化包括错误阶段、受限错误代码、HTTP状态、响应字节数／哈希、Retry-After和时间；不保存认证头或完整错误正文。已知JSON、响应形状、传输争用及结算校验错误使用具体分类，避免再次只留下一个无法解释的ValueError。

## 2. 实现和宿主适配

[新客户端与账本](../../src/proworksim/software_benchmark_deepseek_api_v145.py)建立独立v145账本，不打开旧账本写连接。`group_api`接收冻结题单与现金授权引用，绑定组别、成员、逻辑请求、用途和逐次HTTP身份。

[新宿主适配](../../src/proworksim/software_benchmark_host_api_v145.py)使用实际受管工具schema、成员权限、原官方token计数及请求摘要校验。`HostTeamTransport`将每次真实HTTP的并发槽交给客户端管理，所以退避期间可让其他团队继续使用API。`runtime_for`只构造运行对象，不启动监听、容器、服务或模型；实际启用仍由另一个冻结部署的scope guard决定。

现金授权明确绑定**唯一子账本绝对路径**，三组必须共享同一现金授权、子账本与policy。不能给每组分别复制49.19元账本，否则会叠加超出原400元。宿主会在创建客户端前拒绝跨组路径或policy不一致。
