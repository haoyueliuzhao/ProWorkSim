# 四人组表现下降：简要分析

**基于既有28次四人运行｜整理日期：2026年10月23日**

**主要问题集中在资源分散、候选选择和成果交接。**28次运行中，4次成功，24次失败均未完成最终合法提交。未提交不代表代码全部错误，部分轨迹已有成果，却没走完验证和提交。

| 策略 | 具体组织方式 | 成功／运行 | 主要瓶颈 |
| --- | --- | ---: | --- |
| 固定四人自由组织 | 不预设岗位，成员自行分工，共享总预算 | 1/8 | 各自实现，验证和修订不足 |
| 四人独立候选 | 人工预设：4人分别生成方案，再由原成员1选择并提交 | 1/8 | 候选未完成，或选择者反复读取 |
| 四阶段协作 | 人工预设：实现 → 复核 → 修订 → 验证提交 | 2/12 | 成果未交接，后续调用被阻断 |

**1. 自由组织：人多了，每人能推进的工作反而少了。**

同为50万团队预算，双人变四人后，每成员平均模型调用从20.1次降至10.5次；各8次运行的测试总次数从40降至18。多条分支停在API错误未修复、未测试或修改后未复验，未汇成一个可交付版本。这支持资源分散削弱修订深度的解释。

**2. 独立候选：生成不完整，选择也可能停滞。**

25万预算被切分后，16个生成者均只调用3次就触及各自额度，没有形成可供选择的固定候选。提高预算后，一次运行已有3个候选，选择者却花20.76万token连续13次读取同一文件，直到预算不足，仍未采用或提交。两种失败需要分别解决。

**3. 四阶段协作：前人的成果没有自然传到最后一人。**

成员必须显式发布和采用成果，最终验证者又无权修改代码。原8次架构对照中，只有1次最终验证者采用了候选。全部10次失败的最后停止原因是：7次上下文超限、3次团队预算不足；此前还存在交接缺失和权限误用。

**结论：优先把“形成成果 → 交接 → 验证 → 提交”做完整，再评估增员收益。**

减少重复输入后，四阶段在两题上从0/2恢复到2/2，说明流程可执行性确实重要。但同期单人也为2/2，token消耗仅约四阶段的三分之一，尚未显示四人的净收益。

上表混合了不同任务、预算和输入条件，仅用于汇总。样本较小，不能认定统计显著或推断四人普遍更差；各因素的独立贡献仍需对照实验验证。
