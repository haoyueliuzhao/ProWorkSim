# v227 真实任务中的异常与分工调整

本轮想回答一个问题。两名开发成员遇到具体困难时，由独立的组织策略 Agent 提议调整分工，能否比维持原安排或由开发成员自己提议取得更好的结果？

## 两个开发窗口

每道题都从原始仓库状态开始，由两名 DeepSeek Flash 非思考模式的成员在 ProWorkSim 中正常修复。观察程序只读取指定成员有权看到的工作回执。首次观察到预定情况，且尚有足够的提案预算时，保存当时的代码、成员对话、责任和已用 token。

| 窗口 | 任务 | 在新运行中等待的证据 |
| --- | --- | --- |
| 第一窗 | Astropy-14182 | 同一公开用例在同一工作包的两个不同修改版本上持续失败 |
| 第一窗 | SymPy-16450 | 合并工具报告实际冲突，或同一用例在合并前通过、合并后失败 |
| 第二窗 | scikit-learn-13496 | 当前版本的验证证据缺失或失效 |
| 第二窗 | Xarray-3095 | 不同版本上的公开检查提供稳定证据，当前没有未解异常 |

历史上出现过的问题只用于选题。若新运行正常结束或耗尽任务预算而没有观察到指定情况，照常锁定最终代码和合法交付并评分，同时记录没有形成相应的分工比较。

## 同一现场比较三种安排

第一种是维持原分工。第二种由正在工作的成员结合自己已经看过的对话和当前证据提议。第三种由独立的组织策略 Agent 只看获准的异常证据和工作归属，提出局部调整。后两者都可以建议维持原分工。提案先冻结，执行效果相同的方案合并，保留每个来源。每个不同候选从同一保存点续跑，成员可以接受、推迟或拒绝。每个分支只在首次合格现场分配一次方案，便于把后续行为与这一次建议对应起来。

代码是否通过官方测试、是否合法交付、异常是否得到解除分别记录。例如，判断持续修复失败是否解决，需要新版本通过原失败用例，并检查决策前已经通过的其他公开用例。回归检查按用例名排序取前两个，候选共用。必要证据不足时单列未知。一次建议、一次接受以及一次成功执行分别计数。

## 策略更新与经费

同题全部可比较分支结束后，用合法正确交付和实际 token 计算各方案相对贡献 C，再估计当前策略对同类响应的覆盖不足 N。两道不同任务均形成可区分且评分完整的比较，才更新策略并进入下一窗口。两窗完成后冻结初始策略、两轮更新策略及只用 C 的诊断策略，独立确认使用另外四道题。第一窗缺少有效比较时保留原结果，策略维持初始值。

每条逻辑分支最多 500 万输入加输出 token，包含共享前缀、两份建议和本分支续跑。物理费用按实际请求结算，共享前缀只支付一次。开发获批 100 元，准备 15 元，独立确认 75 元。启动时共享账本已有 893.13154392 元结算额，累计上限 1,100 元。每题的全部有效分支一起核算后准入。当前题单和代码摘要已在首次真实调用前封存。[实验题单](../../artifacts/software-benchmark-v227/window-r1/candidate-tasks.json) · [冻结记录](../../artifacts/software-benchmark-v227/window-r1/freeze.json)
