## 已确认的两类停止

2026-10-29 11:38:41，Qwen协调器保存了`coordinator_error/JSONDecodeError`并退出。旧摘要没有文件名或完整堆栈，因此不能唯一锁定原错误读的是哪个文件。代码中已确认一个可复现竞态：生产者创建`controller-ready.json`后才写入，消费者可能读到空／部分JSON，原准入器未捕获这种情况。v080将这类暂态视为该环境尚未完成准备，记录诊断并继续独立任务；最终可信初始化校验仍保留。

11:39:27，API拥有者的unit日志明确记录OOM kill，随后没有完整run-summary。该协调器原上限16 GiB，宿主归档、导出及评分子进程也在同一unit内；不能仅凭主机空闲内存充足判断这个unit安全。日志包含zstd与多个ld-linux子进程，但未保留所有命令行，不能把每个ld-linux都断言为评分器，也没有证实唯一触发OOM的分配点。记录见[退出证据](../../artifacts/software-benchmark-v081/dead-owner-recovery-r1/exit-evidence.json)。

## 已实施的恢复

- Qwen：32 GiB协调器、4个生成任务、1个宿主评分线程；复用四个原模型PID，没有重载。导入267／275／277三条原技术未知及原用量，不重跑。
- API：64 GiB协调器，启动名额由4增至8；保留每容器16 GiB、原CPU片段、API专用父组224 GiB及1500元唯一账本。Qwen需要补位时优先让出启动机会。
- 新增API协调器自身内存门：余量低于24 GiB暂停新增，达到32 GiB恢复；低于8 GiB时只对本进程注册的API回合请求局部停止。主机和Docker父组的压力保护同时有效，探针失败不按零占用处理。
- 资格已可信闭合且引用不变时，Qwen自身停止不再让API无限等待；API自身来源、账单、资源和清理保护保持。

宿主评分进程和Docker评分容器必须区分。Docker评分容器仍各16 GiB，不能因为宿主评分子进程位于协调器内就从总账删除这64 GiB。新保守上界为：模型384＋Qwen环境128＋API父组224＋协调器32／64＋最多四个Docker评分器64＝896 GiB。它是限额上界，非实际占用；真实主机余量门与自身压力门继续控制派发。API父组及其他用户的资源组没有变更。
