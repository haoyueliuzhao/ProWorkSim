# v062 单 Agent 有界恢复与终态自查协议

日期：2026-10-26。当前结论仅为新实现及 CPU 协议控制通过；没有运行新的模型回合或官方评分。旧 v056/v061 源码、模型轨迹、成绩与终态均保持不变。

## 修改目标与比较含义

v061 的 5M/10M 档出现较多正常结束后未通过、SDK 停滞后未通过，且冻结响应转换没有采用已实现的 reasoning 字段映射。以上是修订动机，不是新协议有效性的证据。本模块把推理字段保真、固定通用覆盖提醒、最多两次停滞恢复与一次终态自查组合为新的执行条件。计划中的同期原冻结 REF 5M、新修订 5M、新修订 10M 比较，衡量的是完整修订协议与累计预算的联合表现，不能把分差单独归因于其中某一项。

自查是同一 Agent 在同一工作区里的下一次用户消息。它要求重新从原问题和公开契约检查预期行为，不是第二名 Agent、独立初态重采、候选择优、奖励反馈或官方测试反馈。即使今后该条件提升成绩，仍不能据此宣称已测到模型的普遍能力上限。

## 公开 SDK 能力与状态转换

固定 OpenHands SDK 1.49.6。本地已安装的 `LocalConversation.send_message` 对 FINISHED/STUCK 接收新用户消息后改为 IDLE；`run` 从 IDLE 进入执行循环。原生 `StuckDetector` 依据最后一条用户消息后的近期事件判断重复，因此新用户消息提供原生支持的有界继续机会，无需替换检测器或改写私有状态。依据为[官方固定版本源码](https://github.com/OpenHands/software-agent-sdk/blob/v1.49.6/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py)以及本地同版本源码；本地源码 SHA 保存在验证回执中。

新模块不修改第三方包，不写 SDK 的执行状态，不清空历史、检测器或已结算账本。保留原五工具、官方模板和原摘要参数；保留同模型、131072 总上下文、32768 单次输出、既定采样。公开测试入口及解释器事实由独立 public-context 模块准入后以文本传入；本模块不读取任务映射、参考补丁、评分文件或隐藏测试内容。

## 执行边界

`initial_message` 原样保留问题文本，追加固定的需求清单、公开测试和验证证据提醒，再追加已经准入的公开环境文本。该完整初始消息与所有后续消息按原数值适配器的完整请求实际计账，不增加免费模型调用。

`create_conversation` 直接复用 v057 `build_llm`，完整保留 `reasoning → reasoning_content` 规范化、原响应归档与原用量结算，以及 Agent/condenser 共享的不可清除故障保护器。它同时复用原五工具原生构造器，不创建额外模型或 Agent。

`run_controlled_conversation` 的固定规则如下：

1. 只接收一次新鲜 IDLE 会话，初始调用、决定和实际 token 均为零。同一会话不能第二次进入协议。
2. 原生 STUCK 最多发送两条固定恢复消息。两次机会跨全部执行段共用；自查后再次停滞不会获得新的停滞额度。
3. 第一次 FINISHED 在原余额和时限允许时最多发送一条固定自查消息。第二次 FINISHED 直接结束，不再要求额外自查。
4. 因而一次回合至多包含初次执行加三次继续，即最多四次 `run()`。四次都共享同一个会话状态、Agent、检测器、适配器、账本、初始工作区与绝对截止时刻。
5. 每段 SDK 最大迭代数设为原累计决定余量。每条消息发送前和每段执行前检查原累计 token、调用、决定以及绝对时限；真实下一请求仍由原适配器执行完整精确输入加输出预约准入。粗检查不代替真实 token 计算。
6. ERROR、暂停、确认等待、异常、未知用量、未决预约以及投影故障均不自动继续。异常保留原异常链交由 controller 归类；没有传输重试或重新采样。
7. 不评估中途候选，也不恢复先前工作树。最终评分对象仍是停止并证明静止后锁定的最后生产工作树。首次 finish 后的自查可能修改工作树；不因先前 finish 认为已有成功结果，也不按后续评分选择是否保留修改。

逐段事件记录原累计调用、决定与 token；准备消息事件保存完整固定提示及 SHA，发送成功事件记录 SDK 的终态→IDLE 转换。消息可能已发送但在下一段开始前触及时限，此时保留 `run_not_started` 及原消息，不声称发生了模型消费。controller 必须继续使用独立宿主的全局时限约束，并在认可最终候选之前再次检查同一投影故障保护器。

## 必要 CPU 控制与实际观察

18 项新增纯 CPU 合同控制通过，覆盖两次停滞总额度、一次自查总额度、先停滞后自查与先自查后停滞、原累计计账、单次入场、其它 SDK 终态不续、预算/调用/决定/时限拒绝、未知账目拒绝、吞掉的投影异常拒绝、原异常透传以及账本替换拒绝。

另外一次真实 SDK CPU 控制通过，使用现成私有 Python/SDK bundle 的普通用户 loader，不启动 Docker、namespace、Actor、服务或 GPU。实际装配生产五工具工厂；三个远程工具由禁止调用的 RPC 对象绑定，程序化响应只调用原生 Think/Finish。Agent 和 condenser 实际共享同一 v057 guard。所有输入与原响应归档，23 份投影回执均保留完整 reasoning 字段。

| 程序化路径 | 返回段数 | 程序化响应 | 最后 SDK 状态 | 停滞恢复/自查 |
| --- | ---: | ---: | --- | --- |
| 停滞、恢复后再停滞、恢复后 finish、自查后 finish | 4 | 10 | finished | 2 / 1 |
| finish、自查后停滞、两次恢复后第三次停滞 | 4 | 13 | stuck | 2 / 1 |

两个路径的分段起始已计费调用分别为 `[0,4,8,9]` 与 `[0,1,5,9]`，各段迭代上限为 `512` 减去已有累计决定。后继请求实际包含对应完整提示；账本通过同一原 `reserve/settle` 接口逐次累计。控制中的输入单位按完整序列化请求计算，是合成单位，不能当作真实 tokenizer 费用或推理性能。

实际模型调用、远程工具调用、官方评分均为 0。Python audit 记录网络尝试、模型权重打开、GPU 设备打开均为 0。所新增三个 Python 文件的限定 Ruff 检查通过。

首次真实 SDK 控制已经完成第一条路径的 10 个程序响应，但 checker 误把 SDK 的 `content` 文本块数组按字符串比较，因此结果为失败；失败回执保留。修正 checker 的文本提取后仅重跑受影响真实 SDK 控制。期间另一次指定 pytest basetemp 的父目录不存在，在进入 fixture/导入 SDK 之前失败；随后创建项目内新目录完成最终控制。以上均不属于模型运行失败，也没有删除原失败回执或把第一次控制改记为通过。
