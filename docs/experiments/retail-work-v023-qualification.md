# v0.23 小型材料、有限维护与完整职责可达性准入

本专项的结论是：**28 个事前声明的唯一情境，在真实 WorldCore、native 单动作接口、v0.22 compact 呈现、现有 Qwen3.5-9B 官方 tokenizer 和完整角色期限下，分别存在一条实际完成职责的有限程序路线。**六个负控保持已知失败，28 个独立进程重复初始化的业务内容与静态工作人员策略身份相同。它支持开始参数学习与初末评价，不构成模型工作成绩、模型稳定成功率或学习收益。

所有程序均为 CPU 控制。模型生成、GPU 调用、API 费用和参数更新均为零。详尽逐情境回执与 token 长度见 [机器可读准入记录](retail-work-v023-qualification.json)，原始总汇在 `runs/retail-work-v023-qualified/report.json`。与该结论不同的旧候选失败保留在原目录，未用新协议重新给旧实验评分。

## 1. 先分来源用途，再派生任务

从已固定的 UCI Online Retail XLSX 读取完整发票，先排除 v0.15、v0.16 和 v0.22 所有旧切片涉及的客户、发票与原始行：54 个客户、162 个发票、777 原始行。排除完整客户实体意味着旧客户的其他未选发票也不能进入本轮。

最终材料是同一来源中的 56 个新客户、168 张完整发票、366 原始行，共 28 组，每组两个客户。每客户取两个完整正常发票与一个完整取消发票，正常发票每张 2—3 行、取消发票每张 1—3 行；价格保留原始两位以内小数，取消发票至少含一条正价格负数量行。没有改写原始交易数值、删除已选发票内部行或伪造交易。

选择规则为：在实体排除与有限大小条件之后，按 `SHA256(collaboration-v023:CustomerID)` 排序，取前 56 客户，连续两人形成一组；首先把前 12 组分配给冻结配对评价，余下 16 组分配给训练，然后才派生任务、准备质量、窗口和种子。任务及种子重复均继承相同来源用途。`case_id` 包含对应材料 SHA256，不能把替换原始材料后的案例继续作为同一精确情境。

当前 pin 为 `examples/retail-collaboration-v23/source-manifest.json`，SHA256：`429ee6dbf3dc05e5b475a4b2888942f22f668e7df5cc36934b0e663501a9ef80`。这是**同一来源内的小型材料 pilot**，不称为新独立企业来源或跨来源泛化。

## 2. 冻结的职责、质量和重复

评价包含 4 个 A、4 个 B、4 个维护情境，每情境两个固定种子；初末沿用同案例、同种子和相同 canonical 业务初态。两个随机重复不算两个独立任务。

每窗训练按 `A0、B0、实现、复核、A1、B1` 顺序安排 6 个 episode，A0/A1 是同一个精确 A 案例，B0/B1 同理；每窗只有四组唯一新材料。四窗之间使用不同材料。每个 slot 的种子在 catalog 中固定，不依模型成绩替换材料或改顺序。

| 用途 | 事前固定准备质量顺序 |
|---|---|
| 评价 B，4 个唯一情境 | 正确、错计数、错金额、正确 |
| 训练 B，窗口 1—4 | 正确、错计数、错金额、错计数；各窗同案例重复两次 |
| 训练单岗位复核，窗口 1—4 | 错金额、正确、错计数、正确 |
| 评价维护，4 个唯一情境 | 应更新、应更新、无需数值改变、无需数值改变 |

普通实现、复核和 A/B 沿用 v0.22 的固定材料结果职责与奖励。角色上限保留实现 12、复核 12、A 的 provider 6 / implementer 16、B 的 implementer 24 / reviewer 28；维护采用 B 的 24 / 28。温度、16384 总 context、2048 单次输出、compact 算法均未因程序路线结果而更换。公开合同继续要求复核固定 result 的实际零基行/单元格位置，以及已读的精确 data 和 audit 引用；正确工作允许直接有据批准。

程序路线不进入训练材料。CPU 控制器的动作序列、公开事实计算器与后验评分不会注入模型提示或标签。B/复核/维护的任务起点本来包含程序准备的固定 SQL 与产物，这些**继承工作**仍按公开工具可读；其准备阶段不记作当前模型工作，更不记作模型先前成功。

## 3. 有限维护合同及实际触发

维护起点先通过真实工具形成旧政策下的正确固定 pending 交付。随后客户端 operator 实际写出 basis v2 与 audit_basis v2，provider 实际读取并经既有合法路线交付 v2，世界时钟实际触发送达。完成这些事件之后才开始模型的当前 episode。合同明确告诉工作人员应读取当前 v2；事件回执、旧交付和来源版本都保存在 preparation 与 episode 起点中，不靠给当前模型记一次不存在的前项成功来声称维护已发生。

两例应变把政策从 `sales_only` 改为 `net_signed`，新材料中真实取消交易保证旧结果实际需要改变。两例无需数值改变仍真正发布 v2 与新 audit，但政策规则重申，不制造缺陷。host 的“应变/无需变”标签不进入工作观察，成员须从当前政策和真实产物自行判断。

当前维护职责为：implementer 重新 inspect 旧固定交付，读旧 code/result、data 和新 basis；若值需改变，实际撤回、推进当前 basis 采用、执行并形成新固定交付；若值仍正确，保留旧固定结果。reviewer 必须独立 inspect 当前固定提交，并实际读 code/result、data 与 audit v2，之后才能有据批准；真实 issue 还须有真实处理。奖励权重保持 B 的 `0.4 + 0.3 + 0.3`，分别对应当前政策的独立复核、当前政策正确固定产物、有效维护响应。旧正确交付、事件本身以及仅凭继承状态停机都不能赚取完整职责分。

这是一次触发后的有限维护责任。尚未声称已经覆盖先前正式验收/发布、任意外部变更以及长期持续项目生命周期。

维护还暴露了一个真实公开接口缺口：原职责采用 `fixed` basis，既有内核正确禁止原 work 上推进该采用；v0.14 的 implementer 工具白名单又没有公开已有 `adopt_version`。本轮只为维护声明 `current_applicable` basis，准备阶段也实际用该策略采用；维护 implementer 显式取得既有 `adopt_version`，精确提供 work、alias 与 version。普通训练 A/B/实现/复核保留原工具集合，reviewer 没有新增写工具。没有自动换版、自动改 SQL、代提交或代批准。

新 profile 的 compact 回执同样经过原始 command digest、actor、project、真实参数和原始回执再投影绑定；两条真实 inspect/submit compact 回执通过，伪造为 reviewer profile 均被拒绝。没有以忽略回执身份来迁就新接口。

## 4. 实际 tokenizer 和角色机会证据

28 条正向程序路线通过真实 ModelPolicy、WorkInterface 和 WorldCore，使用实际 Qwen 官方模板及现有 non-thinking / single-call 参数呈现输入。CPU transport 严格执行 `prompt tokens + 2048 <= 16384`；超限实际返回同类 `context_length_exceeded` 本地 400，不伪造生成或让超限动作继续执行。真实程序输出的工具调用文本也按 tokenizer 计算并核对 2048 上限。

| 职责 | 唯一情境数 | 必需业务动作最大 prompt tokens | 程序路线最大请求机会，包含被拒的额外停机请求 |
|---|---:|---:|---|
| A | 8 | 10068 | provider 3；implementer 9 |
| B | 8 | 13203 | implementer 10；reviewer 15 |
| 实现 | 4 | 9402 | implementer 6 |
| 复核 | 4 | 10937 | reviewer 7 |
| 维护 | 4 | 14065 | implementer 11；reviewer 15 |

所有必需业务动作最大 `14065 + 2048 = 16113`，在现有 context 内；所有成功请求（包括程序控制请求）最大 prompt 为 14217。角色请求数均未超过原公开上限。B 的这条存在性路线是 implementer 先真实自检与修复，reviewer 在固定有限等待后独立查看最终固定交付，不要求先看完错误版本再看一遍修复版本。等待只消耗 reviewer 自己的机会，不传递其他角色的隐藏记忆；模型仍可选择其他合法工作路线。

必须保留一个限制：**共有 14 次完成职责之后的额外 `staff_done` 请求被真实 context 规则拒绝**，分布于 12 个情境，最长 prompt 15619。所有这些请求都未执行，未提供业务动作或追加分数；episode 因实际期限/上下文边界关闭时，此前的固定交付或正式批准已经成立。因此本准入不声称每条路线的所有收尾对话都装得下，也不保证模型的自由探索、错误恢复和其他合法路线装得下。它只排除了“必要职责在协议下必然不可达”。

## 5. 负控与重复初态

| 真实负控 | 辅助回报 | 完整职责 |
|---|---:|---|
| A 仅送达依据、不消费实现 | 0.2 | 未完成 |
| 已读完整证据但错误批准错稿 | 0.25 | 未完成 |
| 正确稿未经本轮证据读取就批准 | 0 | 未完成 |
| 维护应变时保留并批准旧错误数值 | 0 | 未完成 |
| 无需数值变化却不必要地替换固定交付 | 0.7 | 未完成 |
| 维护仅继承旧正确交付、当前无动作 | 0 | 未完成 |

六例均为可核对的已知结果，没有把环境异常填成失败零。它们说明部分奖励与完整职责分开：错误批准即使已有阅读仍不能算有效复核，不必要返工即使产物正确也不算本合同的有效保留响应。

全部 28 个情境另在独立 CPU 进程重新建立起点；业务内容、不可变文件字节与角色 policy identity 逐一相同。这里发现并修正了一个旧 fingerprint 表示问题：准备提交的 `requirement_snapshot` 由集合遍历生成，跨进程 JSON 键插入顺序不同，使原 `digest(json_bytes(...))` 不同，实际字典内容没有差别。

v0.23 的 prefix 因而使用现有 `canonical_digest(initial_business_state(world))`，只规范键序，不额外删除业务字段、逻辑顺序、采用、回执或文件字节；原 `initial_business_state` 已明确排除的实例标识、交互 wall time 和 receipt 状态摘要仍按其原定义处理。旧顺序敏感 hash 单独保留。28 条业务路线不重做、不回填分数；用其已保存 start 快照与另进程副本只读比较并重算 canonical hash。该序列化修订与已完成业务控制的关系记入 JSON，旧 v0.22 hash 定义没有改写。

## 6. 保留的前置失败与核验范围

1. `runs/retail-work-v023-initial`：初稿 CPU 控制存在重复 adopt 已有 fixed 绑定的程序错误；维护 operator 的 write 错带 owner edit context，也被真实工具拒绝。修正程序与公开维护契约后重新运行。不是模型失败。
2. `runs/retail-work-v023-corrected`：维护动作已成功，但新 profile 未同步注册 compact 回执核验，被历史评估拒绝；补齐严格注册后重试，原记录保留。
3. `runs/retail-work-v023-tokenizer` 与 `runs/assets/uci-collaboration-v023-initial-max10`：早先每完整发票最多 10 行的材料，以及先读旧错稿再读修复稿的程序路线，会在必要动作之前超过实际 context；该候选在模型运行前被舍弃，非“仍使用原数据”。旧 PIN/catalog 在该目录的 `preflight-source-max10` 保存。全量预检在确定必要调整后主动停止，未把其部分结果写成完整通过。
4. 同轮维护 no-change 评分草稿曾错误地用 reviewer 判断位置核对 implementer 的消息消费。修为 implementer 本人后续实际 native request 中含其读回执，且发生在正式批准之前；28 正控和负控在修正后才形成最终业务结果。
5. 最后的 canonical 初态修订只影响表示与绑定，按实际已保存副本核验，无需重复业务控制或运行模型。

两个新增定向测试通过（0.19 秒），覆盖来源用途/重复/质量冻结以及维护工具授权边界；相关 Python 静态检查通过。真实动作、回执、tokenizer 和历史结果由上述专项 CPU 实验承担，不用镜像实现的单元测试重复代替。模型初末变化与四窗学习结果须另看主实验报告，本专项没有这些成绩。
