# v0.1 实验记录：机制验证与真实模型试跑

## 1. 结论适用范围

实验于 **2026-09-22** 在项目服务器执行。第一版完成了可执行世界、实际文件修改、连续任务、条件审阅、独立验证和经历编译的工程验证。结果不构成训练收益、跨项目泛化或连续过程优于静态任务的证据。

本轮没有执行 SFT/RL 参数更新，没有使用 GPU 训练，也没有同时优化环境角色、评分器与目标模型。规则基线和 DeepSeek 真实模型实验分别统计。

## 3. 必要自动验证

最终测试套件 **28/28 通过**，耗时 **2.77 秒**。`ruff check src tests scripts` 通过，安装依赖检查无冲突。

测试针对以下机制，而非逐行复写实现：

- 三种交付粒度与两种信息配置可通过实际工具完成，正确交付不强制返工。
- 故意漏改的备忘录触发针对实际内容的意见，修订后的版本能够通过。
- 经理私有材料、未来披露、隐藏评价引用和宿主机路径不能从分析师工具获得。
- 邮件列表、实际阅读、各角色的访问记录分开；分析师不能批准自身交付。
- 无效编辑回滚；有效编辑改变 XLSX 字节及缓存，旧版本和下游陈旧状态保留。
- 错误业务公式可以写入；业务审阅可能接受，但独立验证会拒绝。
- 把正确结果硬编码可以通过当前值检查，但不能通过实际输入扰动检查。
- 快照恢复保留未到期事件；分支独立；篡改状态校验和会被拒绝。
- 修改待审文件使原提交失效；中断后恢复不重复已经提交的工具动作。
- 真实请求上下文、工具错误与返回字段保留；环境消息不成为目标模型策略行为。
- 失败前缀、继承分支、规则基线和测试 fixture 不进入正向 SFT；来源谱系不能跨组。
- 测试集和无效评价不参与课程反馈；建议配额能实际生成训练谱系世界。
- 非有限输入返回可记录错误，ROUND 的半数边界行为有检查。

测试 fixture 只用于验证接口与掩码，不计入真实模型实验或实际 SFT 数量。

## 4. 规则基线机制矩阵

配置为：`seed ∈ {11, 29}` × `delivery ∈ {short, file, continuous}` × `information ∈ {mail, clarification}`，共 **12 个世界实例、2 个来源谱系**。

基线仅使用分析师的工具接口。连续模式下，第一次提交故意保留旧备忘录，检验真实返工；其他模式不注入错误。基线没有读取隐藏规格或独立参考结果。

| 结果 | 数值 |
| --- | ---: |
| 世界实例完成 | 12 / 12 |
| 每项工作的最后提交通过独立验证 | 12 / 12 个世界 |
| 实际工作义务 | 16 |
| 实际提交 | 20 |
| 收到实际修订要求 | 4 次 |
| 数据来源谱系 | 2 |

精确时延和各配置动作数以 [v0.1-mechanism.json](v0.1-mechanism.json) 为准。矩阵的两个 short 信息配置都无需实时澄清，它们不能作为两个不同的协作难度条件。

这项实验说明当前模板存在可行工具路径、状态和反馈机制可运行。由于基线具有预先实现的求解策略，12/12 不能解释为目标模型成功率，也不能代表未知项目的覆盖率。

复现命令：

```bash
.venv/bin/proworksim experiment runs/reproduce-matrix --seeds 11 29 --workers 4
```

## 5. DeepSeek 真实模型实验

使用 seed=101 的同一来源谱系，分别编译三个独立世界。short/file 使用历史邮件；continuous 使用实时澄清。每个世界启动新分析师上下文，continuous 的两轮任务则在同一个世界和上下文内继续。

| 粒度 | 模型调用 | 业务接受工作数 | 独立验证通过工作数（修正后） | 可用 SFT 调用记录 |
| --- | ---: | ---: | ---: | ---: |
| short | 5 | 1 / 1 | 1 / 1 | 4 |
| file | 9 | 1 / 1 | 1 / 1 | 7 |
| continuous | 29 | 2 / 2 | 2 / 2 | 26 |
| 合计 | 43 | 4 / 4 | 4 / 4 | 37 |

三种交付均在 50 次调用预算内结束。连续模式读取了实际口径回复，更新并提交工作簿与备忘录；第一轮接受后读取第二轮披露与假设变化，继续修改已有产物。没有用规则基线替真实模型补齐交付。

**三个世界共享一个来源谱系，不是三个独立泛化样本。** 该谱系按当前稳定分组规则属于 train；本轮只是开发过程中的可运行性试验，没有把它包装成保留测试集表现。

## 6. 首次连续评价失败与评分修订

首次评价的原始结果为：short 通过、file 通过、continuous 两轮均只在 `memo_citations` 检查失败，业务审阅均已接受。原始结果完整保存在 [v0.1-live-original.json](v0.1-live-original.json)。

调查原始文件后发现：

1. 可见 `guide` 要求 `source_versions` 绑定 financials 和 model，`citations` 示例给出披露来源位置。
2. 模型实际在 `source_versions` 绑定了正确 model 版本，并引用披露的收入和经营利润率。
3. 初始验证器在上述要求之外，额外强制 citations 中出现单独的 model 引用。这个附加约束没有公开给工作人员。

因此，将这两个失败归因为**可见要求与验证器不一致**，不能当作模型能力缺陷。修订后的 finance-v0.1.1：继续严格检查模型版本绑定、数值一致、来源版本与有效披露位置，但不再要求未公开的冗余模型引用。短回复仍必须引用指定的 `Outputs!B6` 和 `values.diluted_eps`，不会把任意同文件位置当作正确来源。

修订新增了对应回归测试。随后使用**完全相同的原交付字节重新验证**，没有重新调用模型、补写引用或修改工作簿。三种粒度全部通过。修正后明细见 [v0.1-live-corrected.json](v0.1-live-corrected.json)。本地世界保留两个评价版本；课程读取每项提交最新的评价，避免重复计算被修订判据产生的失败。

这次修订是原型开发中的评价契约修复，不能宣称初版评分标准被冻结后得到 100% 成功率。后续正式比较必须先固定可见要求和评价器版本，再在独立谱系上采样。

下表为 API 返回的 usage 逐次求和。多轮历史会反复计入输入 token，缓存命中计入输入总量，因此数值不是唯一材料长度。

这里的秒数为各模型调用记录的耗时之和，不是三个并行试验的总墙钟时间，更不是模拟业务工时。未查询账单，因此不报告人民币或美元实付金额。API 真实尝试的 usage 与完整消息保存在本地调用记录中；没有用 token 数估计训练 GPU 消耗。

连续世界的上下文成本明显更高是这三次运行的观测事实。但不能据此估计一般连续任务的成本倍数，原因包括单一种子、任务义务数量不同和本版逐轮附加观察的实现方式。上下文增量化是后续可优化项，而非本轮已测得的性能收益。

## 8. 经历编译与样例

## 9. 尚未回答的研究问题

本轮没有回答：

- 训练后是否在未见项目、来源或结构组合上提升。
- 连续项目过程是否优于独立任务合成、静态配额或失败定向扩展。
- 经理和审阅者换成模型后是否保持可靠、成本是否可接受。
- 专业解释是否足够全面、哪些不确定性必须由专家评价。
- 当前简单经营模型的结论能否迁移到 DCF、并购、债务或更复杂办公文件。

下一阶段应首先冻结角色策略、工具与评价协议，扩展来源和结构保留集，再接入真正的参数更新流程。任何关于训练收益或泛化的判断，都需要新的对照实验。
