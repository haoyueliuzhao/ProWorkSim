# v082：API 生成补位与评分准备解耦

本修订只增加 API 队列实现；不改变冻结的 v066、v079、v080 文件，不运行模型、评分容器或真实 API。真实部署与运行统计由独立的后继运行器记录。本文中的通过结果来自 CPU 模拟，不能据此声称实际吞吐已经提高。

## 问题与改动

旧队列虽将官方测试放到评分线程，但主线程仍执行 `prepare_score` 和 `delivery_disposition`。PROJECT 的交付核验会读取、解压并校验控制器归档；主线程执行这些操作时不能及时收取完成的生成任务并补位。已经生成的候选、公开测试及官方评分本身不需要改变。

v082 将完整评分工作交给三个线程：固定候选的原始准备校验 → 官方评分 → 清理证据校验 → PROJECT 原交付判定。存在独立合法提交树时，交付判定产出的同一个 `scoring_request` 进入三个评分线程的队列，仍独立评分，不重建候选、不选择更有利版本。准备失败只记录该槽的技术未知；无法证明已运行评分资源清理完成时仍停止新派发。

生成执行器保留 48 个线程的能力上限。实际准入继续由运行器提供的 `generation_limit`、资源父组、内存与 CPU 守卫、资格状态及 API 人民币预算共同决定。v082 不提高这些限制，不管理 Qwen 驻留服务，不提供新增 Docker 权限。

非准入用途的用量记录、统计文件更新和每 60 秒的活跃槽 SQL 用量读取移到一个串行统计线程，避免统计 I/O 阻塞生成补位，也避免多个线程同时修改统计记录。请求级现金预留及 `budget_status` 仍使用原权威账本；异步统计不授予消费额度。

主循环等待执行完成的最长轮询间隔为 0.2 秒。独立心跳默认每 1 秒发送最近状态，并报告 `scheduler_cycle_age_seconds`、`scheduler_stale`；超过 5 秒未完成主循环时明确标记过期，不能用仍然跳动的心跳伪装调度正常。外部提供的准入、游标、日志及进度回调需要保持短小；这一实现不保证任意外部阻塞调用都能在 5 秒内返回。

## 不变的实验语义

- 仅允许 DEEPSEEK 原任务；不接收新的环境控制任务，不自动重放已消费的生成。
- 原任务、配置引用、唯一最终候选、完整归档验证、官方评分身份及 PROJECT 合法交付规则保持。
- 评分与交付结果均不反馈给模型；不因异常重新选择补丁。
- API 账本错误、人民币耗尽、鉴权故障保留原停止准入语义；局部评分准备错误不扩大为全实验停止。
- 评分线程包含准备阶段，最多三个完整评分作业在途；不能将排队准备误报为三个额外官方容器以外的资源名额。

## 持久化与恢复合同

`factory(job_root, heartbeat_sink=None, heartbeat_interval=1.0)` 返回与原队列关键字参数兼容的执行函数。直接调用 `execute_queue` 时传入 `job_root` 即可。此路径必须属于本次新运行器，不能修改旧评分产物。

每个原槽和端点使用唯一目录 `<slot_index>-code` 或 `<slot_index>-delivery`。准备开始前封存 `job.json`，包含原始任务行、生成结果引用、端点和候选或已准备请求引用。相同身份再次出现必须完全同值；不允许换候选。原评分请求准备完成后再保存 `prepared-request.json`，执行前保存 `execution-intent.json`，最终保存 `outcome.json`。文件锁防止同一描述符在两个工作线程同时执行。

游标的 `active_grading_jobs` 和 `pending_grading_jobs` 存放描述符引用。`active_grading` 只含已经真正形成的请求引用；尚在解压或验证的任务不会伪装成准备完毕。旧版 `pending_scores` 在此队列中为空。恢复时将两个描述符列表合并到 `initial_state['pending_grading_jobs']`，并使用相同 `job_root`。原格式 `pending_score_jobs` 四元组也可导入，随后立即转为本地描述符。

`execution-intent.json` 仅证明尝试执行，不证明已经创建资源。恢复必须额外核对原全局资源 claim、`capacity-claim.json`、`started.json` 等消费标记。已消费且没有可信完成记录的身份禁止重放；准备完成但从未消费的请求可继续。已有官方 `completion.json` 必须绑定同一个请求并通过原清理核验，随后只恢复交付判定和队列记录。此规则同样适用于从旧运行器转入、没有本地执行意向文件的请求。

可选 `external_poll()` / `external_pending()` 支持旧运行器结束后的封存交接。交接检查在独立单线程执行，主循环约每秒取回小结果；旧运行器的停止、资源核验、封存及允许交接的槽集合由调用者负责。返回结构为 `{generation, scores, deliveries, pending_score_jobs}`。生成记录仅可更新已预留的 `external_*` 槽占位；既有最终结果只接受同值重传。交付记录另允许原始的 `waiting_for_own_code_score`、`requires_separate_official_score` 两种非终态向后推进；已形成的独立交付评分请求必须完全同值。非终态记录与同一个待执行请求可以同时交接，不能把它误认为已经完成的评分。冲突不覆盖旧结果，记录 `external_handoff_requires_review` 并继续本队列其他生成。交接不能增加生成白名单，也不能把旧任务再次运行模型。

若同时传入 `progress_sink` 与独立 `heartbeat_sink`，主循环仍调用前者写入真实进展，心跳另写后者。没有独立心跳接收器时，两者共享原进度接收器。两个文件的用途和陈旧状态分开记录。

所有测试只写临时目录并使用线程和内存事件，不调用网络、GPU、Docker、共享服务器配置或实际实验资源。实际性能收益仍须由新运行器在部署后观测生成完成速率、补位延迟、主循环间隔与官方评分积压；暂不提供未经实测的加速倍数。
