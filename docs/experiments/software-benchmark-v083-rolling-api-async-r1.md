# v083：API 滚动交接及异步评分

本修订只接续原 DeepSeek 思考模式 REF／PROJECT、每题 5M token 的两个 500 题组，不增加题目、seed、生成重试、API 总预算或模型条件。Qwen v080 的进程、显卡、源码和派发器不在操作范围内。本文件说明实现及 CPU 验证；不把代码准备完成表述为已经部署或已经提速。

## 原因与修订

旧 API 主循环同步执行 PROJECT 归档验证、评分准备和交付证据检查，可能数分钟不能补充生成。另一个已经观测到的问题是：API 管理进程的 `memory.current` 包含大量文件缓存，原有 64 GiB 管理边界按总占用触发暂停；即使宿主和 224 GiB 容器父组还有余量，也可能停止新增生成及评分。

新派发器使用 v082 队列：三名评分线程负责候选验证、准备、正式评分、清理证据与交付分析；一个统计线程更新费用和实际 token 报表。主线程保留权威 API 预算准入、任务身份检查和快速调度。心跳明确区分线程仍存活与主循环最近推进时间。

v083 管理进程准入改用保守工作集：

`working_set = memory.current - max(0, min(inactive_file, file) - file_dirty - file_writeback)`。

原始占用、完整 `memory.stat`、可回收估计和工作集同时记录。只扣除非脏的 inactive file 缓存，缺字段或读取异常即停止新增准入，不将未知当成空闲内存。原 24／32 GiB 暂停／恢复滞后门和 64 GiB 内核硬上限保留；宿主实际内存与容器父组保护也保留。该估计不意味着文件缓存回收没有性能成本，仍需部署后观察吞吐。

## 不等待全部旧任务结束的交接

1. 精确核对旧 v079 API 服务与进程身份，将其派发控制设为 0；只暂停新增任务。
2. 等待一条时间新鲜、位于控制修改之后、`configured/effective_generation_limit=0` 的确认。冻结旧调度事件、游标和所有已消费身份。
3. 新库存排除所有旧已调度、已申请资源、已请求 API 或已有环境的原身份。旧在途槽标记为 `external_running`；它们不计作完成、模型失败或新库存。
4. 启动独立 v083 API 服务。旧已开始的任务继续自然执行。两个服务共享原唯一 1500 元账本、资源锁、224 GiB 容器父组与全局 48 个 API actor 上限。
5. 旧端生成归零后，后台监视器检查旧身份的全部活跃资源租约和未结 API 预约。已开始的正式测试必须完成。只允许接管从未领取资源／从未开始的评分，或已有精确 completion 与清理证据的评分；后者只导入结果，禁止重跑。
6. 旧服务 cgroup 必须仅有原主 PID。监视器持有共享资源分配排他锁，在信号前再次验证游标未变、旧资源与 API 预约为零，然后通过 pidfd 仅结束旧主 PID。这避免旧正常退出路径错误清理新旧共用父组；不取消活跃模型或官方测试。
7. 将旧最终结果及未开始的固定评分请求封存为独立 `historical-results.json`，释放旧管理进程自身租约。新异步评分线程接管固定请求，完整 1000 题的历史与新结果按任务 ID 合并一次。

旧线程在暂停后尚未领取 actor 的生成 future 也计入保留额度。新生成 future 上限同时扣除旧实际 actor 和旧未领取资源的 future，防止两个管理服务各自取得 48 题。仍采用全局最多 8 对同时启动、Qwen 4 题优先补位和原 CPU 片段；不修改单容器 CPU、内存或网络条件。

## 管理资源与边界

新普通用户服务为 `proworksim-v083-api.service`，4 CPU、64 GiB、swap 0、512 进程，使用既有允许 CPU 集合中的第 164–167 项。旧 v079 管理线程使用第 168–171 项，两者不重叠；actor 仍使用原共享片段。

滚动期额外保留一份 64 GiB 管理上限，理论组合上界可暂至 960 GiB。它是最大配额之和，不代表实际占用。启动必须满足实际宿主可用内存至少 384 GiB，并通过原物理容量门；运行期间继续观测宿主、API 父组和本管理 cgroup。旧管理进程退出后释放其精确预约。不开新父 slice，不改共享主机挂载、网络、驱动、既有服务或他人任务。

尚未证明结束的旧任务在新报告中保持 `external_running`。新旧结果不能通过拼接回合列表重复计数；新完成的交付评分也不能被旧的等待交付状态覆盖。旧运行时可变的 usage 报告在交接库存中复制为不可变快照，避免旧端继续写入使新端引用哈希失效。

## 准备与运行入口

以下命令由负责运行的主协调者在最终核验后依次执行。本实现阶段没有执行它们。

```bash
.venv/bin/python tools/run_offline_scorer_v058.py tools/prepare_rolling_api_v083.py --bootstrap
.venv/bin/python tools/run_offline_scorer_v058.py tools/prepare_rolling_api_v083.py --gate
.venv/bin/python tools/run_offline_scorer_v058.py tools/prepare_rolling_api_v083.py --inventory
.venv/bin/python tools/run_offline_scorer_v058.py tools/launch_rolling_api_v083.py --launch
```

`--inventory` 在旧端尚未确认暂停时返回等待状态，不生成可运行题单。授权、源码索引、题单和服务启动记录只写一次；不可通过重复启动复用已消费身份。旧端交接异常会单独记录，独立的新库存可继续执行，Qwen 不受其生命周期操作影响。共享账本、源码、评分清理等完整性门仍然有效，不将异常转换成普通失败掩盖。

若尚无新服务 `launch-intent.json`／`execution-started.json`，可执行同一 prepare 入口的 `--rollback-before-launch`，只在旧服务身份及暂停控制仍完全相符时还原原派发控制。新服务已有启动意图后禁止重新打开旧派发器，防止新旧库存重叠。旧主 PID 已结束而记账封存中断时，监视器依据不可变 `signal-intent.json` 核对旧服务确实不活动，只续作历史封存及旧租约释放，不再次发信号。启动时重新检查旧暂停仍存在且调度集合没有增长；回退后的旧库存不能继续用于启动新派发器。

Qwen refill 提示读取 v080 当前状态：其协调器失败或结束时目标为 0，不因旧失败游标永久暂停 API。全局 API 48／Qwen 4 的实际 actor 硬边界保持；后续 Qwen 新版本的优先补位提示应独立接入。本次不等待该可选接入，也不尝试恢复 Qwen。

## 有限验证

CPU 检查覆盖库存互斥及外部在途状态、全局并发额度、工作集扣减与未知字段拒绝、暂停确认的新鲜度、历史去重、禁止重放已开始评分、精确已完成评分导入、独立用户服务 CPU／内存规格、旧任务未静止时拒绝发信号，以及信号后仅续接记账、启动后拒绝回开旧库存。v083 共 13 项，连同 v082 的 19 项，联合 32 项通过（4.98 秒）。该控制不调用 Docker、模型、外部 API、systemd 或 GPU，也不验证真实吞吐提升。
