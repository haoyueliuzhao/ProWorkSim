# v0.26 相互依赖协作载体：本轮实验结案报告

日期：2026-10-01。时间均为北京时间。范围为旧经历 C0 审计、CPU 资格控制、冻结参数 C1 真实模型实验及其资源恢复；不包含 C2 新支持采集、C3 配置对照或新增训练。

**实验已结束。恢复后 16 个逻辑槽全部可评分，完整职责 0/16；normal 与 single_pass 均为 0/8，平均分均为 0。** 实际发生 17 次业务尝试，包含一个仍保留为 unknown 的原中断尝试。最后模型于 **21:47:36.354** 退出，累计消耗 **2.468925 GPU 小时**，包含最初加载失败及中断成本。原始不完整实验和恢复后的描述性结果分别保留。

零分需要结合工作内容解释：恢复后 16 个逻辑槽中，源端有 6 次 SQL 执行成功，其中 **2 份固定提交的源产物在表名、列名、行值和单位上正确**，但没有满足整套冻结接口合同；消费端仅尝试 1 次构建且失败，提交 0 次。因此，本轮没有完整双向交付与复核，也不能说所有源端计算都错。CPU 程序路径能够完成任务，尚未转化为当前模型配置的完整工作成果。

本报告只整理归档与做独立算术诊断，没有启动新模型、SQL 执行、历史重放、评分或参数更新。原 reward 和缺失状态保持不变。[精简机器记录](collaboration-v026-summary.json)、[业务轨迹附录](collaboration-v026-work-analysis.md)、[资源附录](collaboration-v026-resource-analysis.md)分别提供数值、逐动作证据和资源恢复依据。

## 1. 研究问题与执行边界

[审计意见](../reference/audit-v025-next-v026.md)指出，旧载体主要是一次资料交付后的个人计算及未闭合复核，仅增加样本数不足以证明相互依赖协作。[v0.26 方案](../domain-collaboration-v026-plan.md)因此先核对旧经历，再建立双方各自产出、消费精确版本并承担复核义务的载体。

C1 比较正常交流与一次原始需求交接，考察固定参数下的工作表现。它改变的是通信协议，**没有改变参数，也没有执行经验配置算法**。该比较不能估计参数学习收益、非单位 q/b 的贡献或 ID-VTDO 相对基线的增量。C1 材料是开发材料，不是训练支持池；C2/C3 均未执行。

原协议为 16 槽、4 GPU 小时和 32 GiB 单进程显存保护。运行过程中，用户先将等卡范围指定为 GPU 0/4/5/7，最终等卡期限延长到 **10 月 2 日 00:00**，再授权扩展累计运行预算至 8 GPU 小时、开放显存保护至物理卡容量 80 GiB，并恢复未完成槽。这些是有记录的运行修订，不能把恢复结果写成原协议下从未中断的完整实验。

## 2. C0：旧协作证据审计

[C0 报告](collaboration-v026-c0.md)只读核对 v0.25 的 16 条联合经历，未重判旧 V、Mapper 或 reward。原归档有 302 次模型请求、283 次响应、258 次世界动作；旧标准下唯一完整有效主动交接仍是 `train-00-5`。

34 个本轮代码/结果版本中，6 个版本标识进入过对方实际输入，但没有一个新产物的完整内容经读取进入对方实际请求；此统计不排除另行发送的依据正文。8 次当前交接、5 次信息请求中仅 1 次有绑定请求的响应；4 次正式问题仅 1 次有效。有效问题发生于 `train-01-3` 的事件 #179，后续请求 #185 包含该问题，却因上下文停止而没有生成；更早的 #145/#168 修改不能归因为这次反馈。

这些证据支持“旧经历尚未形成持续双向产出和反馈修复”的载体诊断，不能据此改变旧阶段已经归档的成功、失败或训练结果。

## 3. 新载体、材料与冻结配置

### 3.1 工作合同和两种通信条件

maintainer 持有原始零售数据与私有源接口说明，consumer 持有私有需求。双方从空代码、空结果开始，分别承担以下工作：

| 角色 | 当前工作与产物 | 对另一角色的依赖 |
| --- | --- | --- |
| maintainer | 准备并固定提交 `invoice_view(CustomerID, InvoiceNo, amount DOUBLE)`、`customers`、`interface_meta` | 获取 consumer 的日期/发票口径需求；最终复核消费产物 |
| consumer | 使用固定源版本，构建并提交 `metrics(CustomerID, revenue_pence, invoice_count)`，金额为整数便士，发票去重计数 | 读取固定 `m_code/m_result`，采用 `m_result` 与 `demand`，完成自己的聚合业务 |

合同区分可访问、实际读取、精确采用、SQL 执行依赖、固定提交与复核。源 `invoice_view` 必须实际引用 `retail`、`demand_meta`、`source_meta` 的关系依赖；仅把输入列在采用清单中，或在未使用的 SQL 模型/测试里读到它们，不满足此项。它是本次公开操作合同，不能推广为判断所有程序是否在语义上使用信息的唯一标准。

normal 允许工作人员自行请求和交接信息。single_pass 仅允许 consumer 一次发送原始 demand v1，交接正文固定为 `Original demand document.`；仍保留双方相同的产物读写、采用、SQL、提交和正式复核工具。single_pass 不是无协作条件，也不是整个流程只有一条信息边。两臂没有预制正确源产品，不要求先犯错或达到最低交流轮数。

最终评分的三部分为：当前正确源交付 0.35、当前正确消费交付 0.35、双向消费与再验证 0.30。完整职责要求整套合同闭合；单次工具成功或源 SQL 数值正确均不能直接替代它。

## 4. CPU 资格与实际输入控制

[CPU 资格报告](collaboration-v026-qualification.md)的最终批次 `native-complete-07` 通过 12 条正路径、2 条错误逻辑负控、6 组反事实检查及 4 组公平性检查。正路径均完整成功，负控均未完成完整职责；共 510 次程序化请求（正路径 440，负控 70），没有模型调用、GPU 调用或训练。CPU 控制只使用 `202610040000`、`202610040100`，未覆盖正式模型 repeat=1 的两个 `+1` seed。两条程序路径是可达性见证，不能作为模型学会的两类方法。

最大实际 prompt 为 14332 token，保留 2048 输出后距 16384 上限仅 **4 token**；控制程序最大输出 402 token。资格证明限定于这些程序路径，不保证任意模型行动序列的容量。前期超长、开发中断和结束动作仍超长的批次均保留。准入前对重复公开合同及仅审计历史字段作了精简，没有修改历史工具正文或扩大 context/output 上限；亦修正了只在未使用模型/测试中读取元数据却能伪造依赖的检查缺口。

真实运行中，恢复后的 **8/8 私有事实反事实初始请求对**完整请求字典序列化一致。这 8 对是“2 原型 × 2 通信条件 × 2 重复”，不同于“4 情境 × 2 重复”的 8 对通信条件结果。原 R2 只有 4 对可核对、4 对缺失；不以恢复数据覆盖这一事实。原中断槽和恢复槽的两个角色首请求也分别一致，但没有据此宣称后续逐 token 重演。

## 5. 运行、中断与恢复后的结果

首次 C1 的 GPU 4/5 均在加载时 CUDA OOM，未启动业务；R1 只等待、没有模型加载，后为延后等卡期限而主动停止。R2 于 10 月 1 日约 20:00:47 在 GPU 0/4 开始。GPU 0 于 20:35:15 被原 32 GiB 保护停止；当时进程显存 33866 MiB，高于 32768 MiB，而设备仍有 47279 MiB 空闲，**这是监督阈值停止，与首次 CUDA OOM 不同**。

## 6. 工作进展、错误与未闭合位置

### 6.1 调用与停止

| 口径 | 请求 | 响应 | 工具调用 | 外层拒绝 | 上下文停止 | prompt tokens | output tokens |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 恢复后 16 逻辑槽 | 760 | 754 | 751 | 247 | 6 | 7,916,598 | 140,419 |
| 全部 17 实际尝试 | 806 | 799 | 795 | 259 | 6 | 8,406,926 | 148,655 |

token 数来自已保存响应的 usage 累加，不补估未返回请求或中断时未持久化的生成。16 槽的 32 个角色终止中，26 个达到 max_decisions、6 个达到 context_length_exceeded。没有正式问题、回复问题、裁定、preflight 或 approve 调用；9 次 sql_query 全被拒绝。因此失败不只是缺少最终审批，消费执行更早就没有完成。

247 次外层拒绝中，225 次标为 `unclassified_exception`。对照完整消息及冻结实现，它们均是明确的 ValueError 输入/状态校验，主要为未共享精确版本 98 次、无效提交引用 75 次、重复采用 18 次。其余为 single_pass_communication 21 次、公开参数结构拒绝 1 次。粗粒度错误标签不能解释成 225 次内部崩溃，也不能据此证明整个接口实现无缺陷。

另有 **20 次内层 SQL 执行错误**，与外层拒绝分开：源端 19、消费端 1。工具 `ok=true` 只表示成功保存构建回执，可能同时返回 `execution_status=execution_error`。源端 7 次成功提交中，5 次固定了成功 SQL 结果，另 2 次分别固定执行错误结果或尚未构建的初始结果，不能称作 7 次正确产品交付。

### 6.2 两份内容正确的源产品与合同限制

报告阶段用 Python 标准库和 Decimal，从同一尝试实际读回的 raw 行及固定事实独立计算期望，与六次成功 SQL 的归档表比较；没有重执行 SQL 或评分。详细实际/期望行见[业务附录第 8 节](collaboration-v026-work-analysis.md#8-追加内容诊断数值正确与原合同合格分开判断)及其 JSON。

| 已保存产物 | 内容诊断 | 其他已知限制 |
| --- | --- | --- |
| R2 `c1-02-normal-0` | 发票 GBP 金额正确；interface_meta 为空 | 仅传 raw，采用缺 source_contract，amount 为 DECIMAL |
| R2 `c1-01-single_pass-0` | net_signed 错按 sales_only；漏两张取消发票 | 需求已经进入实际请求；amount 为 INTEGER |
| R2 `c1-03-normal-0` | 金额以 GBP 计算却声明 pence，少乘 100 | amount 为 DECIMAL |
| R2 `c1-03-normal-1` | 10 条明细没有聚成 4 张发票，且单位缩放错误 | amount 为 DOUBLE，但正式请求未闭合，提交被拒 |
| R3 `c1-00-normal-1` | **全部表名、列名、行值及单位正确，并有固定提交** | amount 为 DECIMAL；没有所需元数据表关系引用 |
| R3 `c1-02-single_pass-0` | **全部表名、列名、行值及单位正确，并有固定提交** | amount 为 DECIMAL；没有所需元数据表关系引用 |

六份成功 SQL 的 invoice_view 均未同时引用 demand_meta/source_meta。后两份确实已经读取、采用并传入三份输入，模型可把读到的规则写成常量；缺少 SQL 关系引用不等于没有利用信息。显式依赖和 DOUBLE 类型要求属于本次冻结合同，数值正确与合同未合格可以同时成立。这项 **2/6 源产品内容诊断不能替换 0/16 完整职责，也不是新增成功评分或方法支持**。

### 6.3 代表性阻断点

业务附录保留精确事件序号、参数及实际入模请求摘要；以下是不同失败位置，而非单一根因的排序：

- R2 `c1-00-normal-0`：maintainer 请求需求后，又试图自己充当该需求的手工提供者，遭权限/谱系拒绝；后来拿到交接，构建却只传 raw，SQL 读取 source_meta 时出错。信息可达不能自动补足构建输入。
- R2 `c1-01-single_pass-0`：写代码前的请求明确含 net_signed，生成仍过滤负数量和 C 开头发票。消费端随后把 `models` 写成映射而非 `{name,sql}` 列表，唯一一次消费构建报 `Code needs one to eight models`；不能将它归因为源 DECIMAL 类型。
- R3 `c1-02-single_pass-0`：源产品内容正确、成功固定提交，consumer 随后采用、检查并读取固定代码与结果，最后达到上下文上限，始终没有写消费代码或构建。没有数据证明只延长一步便能完成。
- R2 `c1-03-normal-1` 与 R3 `c1-02-normal-1`：consumer 交接需求时漏 `request_id`，资料已可读，但正式请求未关闭。公开观察明确 `status=blocked`、缺少可执行提交动作；4 次源提交被拒。请求绑定是本载体真实的交互负担，不能把全部后果单归于通用业务计算能力。

现有证据同时包含模型实施错误、对象/状态引用错误、严格接口要求和有限决策/上下文容量。没有独立消融确定它们各自的因果占比；也没有证据支持把 0/16 全归为平台故障或模型完全不会计算。
