# v076：按实际余量提高 DeepSeek 并发

状态更新（2026-10-29）：用户已明确授权独立父资源组，创建及内核限额核验已完成。旧队列已暂停新派发，在途自然收口；计划中的新primary服务已作为后台交接器运行，完成后自动接续Qwen并启动API。本文中的44是新调度目标，不是已经达到的实际并发。实际记录见[部署快照](../../artifacts/software-benchmark-v076/runtime-rollout-r2/snapshot.json)。

用户明确要求按 CPU 整体余量调度，并将 DeepSeek 提高到40以上。因此，前一版仅把预约832 GiB改为896 GiB、最多提高到10并发的 v075 草稿不部署；其源码和控制记录保留，不能当作运行过的实验配置。

官方当前公布 `deepseek-flash` 的账户并发请求上限为2500；新任务目标低于这个上限。[DeepSeek官方并发说明](https://api-docs.deepseek.com/quick_start/rate_limit/)。任务环境并发、实际API请求数和已完成任务数是不同指标，必须分别记录。

## 共享服务器保护

本机总内存约1007.6 GiB。40个环境若同时达到各自32 GiB上限，不能仅凭当前空闲内存多就声称安全。新方案采用API专用的硬聚合内存边界，而非只靠反应式监控。

最大内存账为：四个模型384 GiB＋四个Qwen环境128 GiB＋两个协调器32 GiB＋最多四个评分器64 GiB＋全部API环境共同224 GiB＝**832 GiB**。该算式不代表实际已占用832 GiB；它保留可审计的项目总体硬上界。API任务之间共享224 GiB，压力升高时暂停新增，并通过每个任务已有的局部停止事件回收本项目API回合。被压力中断的回合单列为部署技术未知，保留原候选及用量，不自动重跑。

实际Docker使用systemd cgroup v2，父边界必须是system manager下的独立slice。新slice采用无连字符的名称，避免隐式创建多层祖先。它只接纳本轮新API容器；不移动旧容器、不改变原模型、Qwen、评分或其他用户的cgroup。只读验证父级MemoryMax、swap及实际容器祖先路径后才允许新API派发；没有合格父边界则拒绝启动新API。父级剩余内存低于64 GiB暂停新增、达到96 GiB恢复，低于16 GiB触发本项目API回收，与主机余量保护取更严格者。

创建这个全新的system manager对象涉及新增root等效管理操作，区别于已授权的普通用户协调器与既有Docker容器路径。精确命令和清理条件见[父级授权提案](../../artifacts/software-benchmark-v076/aggregate-parent-authorization-r1/proposal.json)；在该范围获准并验证之前，不开始真实队列交接。创建必须证明同名对象不存在，采用 `StartTransientUnit` 的 `fail` 模式；结束时只有原分配锁下无任何API预约、子cgroup或进程才允许清理该独立父级。

## 交接与结果连续性

先暂时撤回四个模型的发现标记、暂停旧API新派发，在途任务继续使用已有模型连接。必须等待生成、控制、评分及资源全部达到可核验的静止边界，保存原cursor与待评分清单，再只结束两个已确证的协调器主进程。旧Qwen的普通退出路径会卸载全部模型，所以这里不能对它发送会执行该退出逻辑的TERM/INT；交接使用pidfd绑定的精确主PID并跳过旧卸载逻辑，模型服务是独立单位。恢复原字节发现标记后，新协调器接续原库存。

原Qwen3000题与DeepSeek5M1000题计划分母不变。任何已生成、曾派发或已消费物理创建身份均排除重放；旧异常保留。已完成评分导入，未消费评分移交，不能把生成闭合等同于答对，也不能将历史技术未知补成普通失败。新Qwen和API协调器均支持可读的并发控制文件，后续降低目标只停止新增，不阻塞评分回收。

已做的必要控制包括：实际容量与原分配锁竞争、批量启动门、CPU／内存／watchdog拒绝路径、三类消费者一致绑定、压力回调的任务归属、bootstrap失败释放、交付评分复用、自然排空与PID复用拒绝、库存去重与禁止重采。各项凭据保存在 `artifacts/software-benchmark-v076/`。不重复运行无关旧测试。

## 已执行的授权与自动交接

用户明确回复“授权上述限定范围”后，只创建了 `proworksimv076api.slice`；实际内核 `memory.max=240518168576`、swap=0、pids=32768。未修改其他系统资源组或已有服务。创建命令只提交一次。

旧API原先没有并发控制文件，使用程序默认目标32、实际8；交接前先将同值默认配置显式记录，再暂停新派发。旧模型仅暂存发现标记，在途继续使用原连接。一次启动工具审批超时未执行，按工具提示只重试一次，随后成功启动本项目普通用户 `proworksim-v076-primary.service`。

自然收口可能超过一个交互回合，因此在新primary第一次正式执行前增加自动交接入口。原未执行的准备源码、授权和两项unit规格已完整[归档](../../artifacts/software-benchmark-v076/bootstrap-preparation-r1-archive/archive-map.json)，重新封存后才启动；没有改写已运行的旧实验源码、父资源组提案或模型配置。该进程临时4 CPU／16 GiB预约计入旧共享账，最长等待8小时，每15秒检查一次；必须有两次相隔至少3秒、且晚于暂停时间的静止证据。完成交接后释放临时预约，同进程进入正式Qwen调度，并自动启动API。

超时或发出协调器停止信号前失败时，恢复旧派发；停止后若发生问题则保存边界并报告，不能假称旧进程可恢复。最后的在途任务可能因模型自行结束而提前收口，当前不能给出确定切换时刻。更详细的自动流程见[交接说明](software-benchmark-v076-automatic-handoff-r2.md)。

资源并发提高也会增加共享CPU片段上的排队，实际测试耗时与端到端时限可能因此变化。运行记录保留部署版本、实际成本与技术异常，不能把吞吐提升直接解释成模型能力提高。

## 第一阶段实测与剩余瓶颈

2026-10-29约11:01，旧任务及评分已全部自然收口。旧API的可变调度checkpoint仍残留一个已经完成的任务，导致交接等待；依据原closed结果、事件和三对象清理证明，先归档原checkpoint再补齐终态，原补丁、评分、费用和运行源码均未修改。该[独立记录修复](software-benchmark-v078-idle-api-cursor-reconciliation.md)完成后，后台自动接续两条队列，四个模型未重载。

11:04:57—11:38:04的只读观测中，API真实actor并发最高38，**尚未证实达到40或44**。约33分钟新增37题正常生成闭合、36份评分及2项局部技术未知，描述性速率约67题/小时；旧队列前一小时基线为24题/小时。任务混合和启动阶段不同，不能将两者比值当作受控因果提速倍数。Qwen同期增加3题正常闭合并继续补位，没有因API扩容停止。

主机CPU约15%—27%、可用内存最低约839 GiB，API父组最高约80/224 GiB，没有压力回收或全局暂停。API协调器60秒平均使用2.59核，没有持续占满四核的证据。61个已就绪环境的派发到SDK-ready时间代理中位78.3秒、均值104.6秒；它包括环境物化与排队，不是纯CPU导入时间。四个启动名额长期占满，是实际并发仍低于目标的直接限制。

详细数值与边界见[监测摘要](../../artifacts/software-benchmark-v076/throughput-observation-r2/summary.json)。它明确区分会话观测摘要与完整原始序列。后续仅提高API启动补位上限的v079修订另行记录；本阶段不能报告44并发已完成。
