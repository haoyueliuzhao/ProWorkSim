# v203.3.5：降低过高现金预约并恢复原队列

2026年11月16日，依据用户“预约金额显然过高”修订。原16条续跑安排、4个保存状态、KEEP／REASSIGN条件、原剩余Token与时钟、模型、工具和评分不变。只修改新回合的现金准入规则，继续同一80元账本，不重新调用已结束的6个身份。

## 旧预约为何过高

旧实现将剩余输入加输出Token全部乘以最高输出单价8元／百万，因此每条约需38.8元预约。实际截至修订前：25,450,465输入Token、85,625输出Token，输入占99.6647%。不能把全部输入按输出价计算预期费用。

5个正常续跑实际峰值费用上界分别为8.56945648、8.46010376、8.57705608、8.55691424、8.51233592元。旧预约为实际费用的约4.5倍。原队列在实际累计44.72335848元、尚余35.27664152元时停止新准入，是预约策略导致，并非已经用完80元。

## 修订后的规则

每条新回合预约**9.5元**。计算规则为：已完成正常回合费用最大值×1.10，再向上取整至0.5元。使用费用而非通过率计算，不读取评分来选择回合或改变顺序。该估计冻结用于剩余原10条身份，不因某组分数调整。

启动准入计算：历史已结束回合费用，加每个在途回合的max（9.5元预约，已知费用及未定请求占用），再加新回合9.5元，必须不超过80元。已支付部分包含在预约中，不重复相加；结束后释放未使用预约。未定请求保留占用，不能当作零费用。

沿用用户已明确的“已开始任务不因金额上限中断”要求：80元为**新回合启动线**，新预约是估计而非最高费用保证。已开始回合继续受原Token和时间限制，不因实际费用超出估计而中途停止；如果估计不足，总额可能越过80元，必须如实报告并停止新准入。没有增加名义预算，也不宣称改成估计后仍能数学保证绝不超额。

原每请求Token预约、实际usage结算、原始响应及未知保留规则不改。旧slots/requests记录及旧meta的80元值不重写；新cash_admission_revisions表按新槽位单独记录版本和估计。修订前账本已备份。

## 验证和恢复

3项必要CPU测试通过：实际费用不与预约重复计数且结束释放余量；费用超过估计时不切断已入场回合、但拒绝新的准入；未知请求保留占用及禁止同身份重复启动。

仅恢复原尚未调用的10个身份，最多2路生成、1路异步评分。复用已经通过的4题gold／empty及同一评分实现，不重复环境控制，不重跑历史异常。旧生成和评分已经排空，不修改在途程序。普通用户服务及隔离Docker的CPU、内存和权限范围与上一轮稳定运行配置相同，不修改共享服务器。

当前剩余额度按已完成回合约8.5元均费，预计支持约4个额外回合，不保证完成全部10个。保留原顺序；现金准入不足的身份继续单列未启动，不能填成模型失败。
