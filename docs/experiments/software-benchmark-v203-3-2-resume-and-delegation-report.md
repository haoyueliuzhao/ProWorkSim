# SDK续接验收与真实诊断委派实验协议

日期：2026年11月16日；版本：v203.3.2。依据用户提供的v203.2.5／v203.3.1审计修订。

**本轮完成零API的检查点续接准入。** 连续运行与新进程恢复KEEP、两个KEEP副本、KEEP／REASSIGN三组控制均通过，并走到测试—反馈—复核—合法交付。旧测试链未重复验收，本轮没有新增Docker容器、GPU任务、外部模型调用或API费用，也未修改共享服务器配置。

**研究仍未进入效果证明。** 本轮用真实SDK和受管世界、确定性模型替身及真实pytest验证恢复行为。它不证明诊断委派提高完成率、降低真实Token消耗，或系统已经会自主选择委派时机。

## 1. 本轮验证结果

保存点包含两个真实私有SDK会话、已经发生的2次历史摘要、1次公开测试、任务所有权、成员工作台、版本、团队预算和调度状态。不是只有两次读取的空白对话，也不只保存Git树。

| 路径 | 是否从新进程恢复 | 续跑脚本化请求数 | 最终诊断负责人 | 受管交付 |
|---|---|---:|---|---|
| CONT 连续运行 | 否，保存后在原进程继续 | 14 | 001 | 完成 |
| KEEP-A | 是 | 14 | 001 | 完成 |
| KEEP-B | 是，独立于KEEP-A | 14 | 001 | 完成 |
| REASSIGN | 是，增加预定委派指令 | 18 | 002 | 完成 |

这里是**一个受控起点、四条执行路径**，不是四道独立软件任务。请求数是替身协议调用数，不是外部模型调用；控制用量为人为设定的usage，不能当作真实Token效率。没有运行官方隐藏评分，不报告基准正确率。

### 连续与恢复KEEP

从同一保存点发出的下一次全局请求，其消息、工具定义、采样及输出设置一致。只排除供应商归属字段 `user_id`：每个物理分支需要不同身份。没有删除任何模型消息、观察、预算或工具字段来制造一致，也没有添加“继续任务”提示。

两名成员的原SDK事件文件均逐字节保留。第二成员在第一成员已经完成一次新调用后才行动；此时团队账本的来源哈希可能因新物理响应ID不同而变化，不能再把这当成“同一未执行状态”的下一请求。该差异保留在原件中，未通过改写提示或去掉合法信息来消除。

### 双KEEP隔离

KEEP-A和KEEP-B各有私有持久化目录、工作区、账本、运行命名空间与新请求ID。新请求集合不相交，父检查点哈希在全部分支结束后仍一致；各分支结束后的世界状态与自己的结果文件一致。

逻辑前缀中的原会话、事件和旧世界操作标识不改写；新的物理执行、请求和记账由外层分支命名空间区分，逻辑标识只在该分支内解释。正式评分还须使用独立 `run_id`，不能因同题复用其他分支的评分缓存。

执行环境对各次启动采用独立PID命名空间，因此日志中的本地PID都可能为6；没有据此误判为同一进程。四次独立Python启动由保留的执行会话记录区分。

### KEEP与REASSIGN

干预前恢复同一前缀；REASSIGN只向001加入预定的委派要求，由替身通过原工具实际执行offer、002接受并承担诊断。没有直接写owner。干预后的请求允许不同，不能为了字节一致抹去转移结果。

001仍实现并交付，002仍进行同版本复核。002参与诊断的知识积累和判断倾向是委派流程的一部分，不宣称其独立于诊断过程。控制分支中没有由002编写最终实现再经001重发来伪装独立复核。

本控制由确定性替身给出诊断和修复动作，**仅用于续接验收**。它不能复用为真实模型实验中的诊断答案或脚本化修复。

## 2. 预算、时钟和重复计费

保存点的团队模型用量和测试次数完整继承；测试额度已用1次，恢复后仍是1次，而非重新获得512次。两次摘要的已用额度也保留。旧账目作为只读前缀，不触发新的提供方调用；新请求从分支独立身份开始记账。

时钟采用事前固定规则：保存、复制和新进程装配的暂停时间不消耗分支执行时限，准备过程本身另计实验开销；每支从相同的已保存剩余软／硬时限继续，干预工作从恢复后的预算中消耗。本控制各恢复支第一次新调用的软时限剩余约21,582.55—21,582.61秒、硬时限约23,382.55—23,382.61秒，均不超过保存值，未重发完整时长。

内部团队usage和请求身份机制已验证；真实供应商账单、缓存与服务标识仍需在获批的真实分支中验证。本轮没有创建新的付费账本，旧130元账本及31.25543296元余额不转用。

## 3. 恢复中实际修复的问题

官方文档给出的接口基础是按会话ID和持久化目录恢复基础状态及事件；它不替项目恢复外部团队资源与世界状态。本轮使用本地冻结SDK行为核验，而非仅凭当前文档宣布通过。[OpenHands持久化文档](https://docs.openhands.dev/sdk/guides/convo-persistence)

| 缺口 | 修订 |
|---|---|
| 摘要器是函数内局部类，SDK拒绝反序列化 | 为原缓存类提供稳定模块标识，不改变摘要方法、阈值或既有摘要事件 |
| 旧动态Action／Tool类型在新进程不存在 | 按原注册身份和同一schema重建类型与可信执行器，不重写旧事件 |
| 测试次数账本在世界状态之外，初版恢复误补额度 | 将原测试账本纳入新版本检查点；未补齐的旧保存点不静默修补 |
| 替身新响应ID与前缀重复 | 新运行／请求／响应使用分支独立命名空间，保留原重复身份拒绝机制 |
| SDK持久化元数据仍指向父目录 | 显式绑定分支目录并移除初始化时未使用的空会话；历史事件保持原字节 |

早期失败控制保留，未把它们写成通过。最终验收以新版完整检查点和独立恢复结果为准，没有从后续工作反推早期缺失状态。

**对本轮冻结SDK、已结算机会边界、含摘要的REVIEW2路径，检查点工程事项可以关闭。** 不扩张为任意崩溃、在途请求或任意后端的恢复认证。下一阶段只验证真实模型后端和实际任务环境的变化部分。

## 4. 首轮真实实验究竟研究什么

研究对象为：**对同一个真实、尚未完成的诊断工作包，分配“尝试委派给002”的方案，相比保持001负责，有什么质量和成本差异？**

首轮不让O2自动选择时机，也不增加成员、工具权限或新上下文算法。两组固定原模型、非思考模式、上下文131,072、单次输出上限32,768和REVIEW2规则。具体服务版本及缓存情况按实际请求记录。

| 条件 | 实际要求 |
|---|---|
| KEEP | 001继续当前诊断，不增加无意义管理动作，不额外插入恢复提示 |
| REASSIGN | 只加入一次冻结的委派要求；模型通过原offer／accept及必要信息交接尝试转移，之后自行诊断与实现 |

不得替未接受的模型直接改owner；不得写死诊断结论、测试结果或修复；失败后不追加未注册的人为指导。真实模型拒绝、没有完成、重复确认或越界修改均保留，其实际动作和代码来源另报。

本轮不假定并行收益：如果001必须等待002结果，关键路径并未自动缩短。可能收益来自002已有知识、不同诊断视角或减少重复探索；也可能增加回读和确认成本，或使诊断与复核判断过度一致。首先归因于完整委派流程，不拆称为单一“负载均衡收益”。

上一轮脚本增加5个工具动作，本轮控制增加4个脚本化请求，均不是未来固定成本常数。真实账目按实际输入、输出、摘要、转移、回读、测试及返工记录。

## 5. 真实状态的取得方式

首轮采用**共同准备起点**，与自然自发形成的状态分开解释。分支前仅建立最小诊断契约与初始001负责人，双方获得相同公共任务事实；不附参考修复、精确答案或隐藏测试。准备工具、CPU及所有模型调用成本都记入实验。

拟定最多8个候选，目标取得4个合格状态、尽量覆盖至少3个仓库。每个前缀最多50万输入＋输出Token、24个团队Agent机会；在至少8个机会后的首个已结算边界，若事前事实审阅确认有真实未完成诊断且两分支合法，则保存。达到上限仍不合格就记录原因及成本，不无限试题。

候选ID和执行顺序须与新现金预算一起在首个真实前缀前锁定，当前尚未填入真实题单。此前四个小型类比不能替代真实面板。已曝光的Verified仍只作开发探测材料，不称独立确认集。

资格判定区分三类：

- **仍有诊断对象，转移可能有帮助：** 如002已掌握相关证据，但不预先判定获胜。
- **仍有诊断对象，转移可能不值得：** 如002缺少相关信息、诊断简单且责任清晰，可进入配对比较。
- **诊断已经完成：** 没有可转移对象，作为拒绝干预的准入负例，不强行增加一段诊断来凑对数。

新增准入函数实现这些明确排除条件，但不会将非空字段当成事实证明；真实“未完成”仍须引用截止前可核验材料并接受审阅。没有已知永久环境故障、版本来源完整和续接资格是必要条件。

## 6. 4状态×2分支×2重复的预算与终点

目标为16个真实续跑，只有4个起点。候选不足时报告不足，不替换成小型类比。执行顺序按预定seed配对交错，避免总是先KEEP；首两条相反条件分支属于主计划与分母，放行后续依据是接线和账目完整性，不依据官方成绩。

每支继承同一检查点的剩余Token、机会与时间，不重新发放500万。转移、回读和信息返回从分支开始即扣账。原团队上限拟保持500万，前缀花多少，续跑就相应少多少。该设计保留实际闭合机会，主终点不在结果不利后改成局部诊断成功。

账目明确分开：

1. **实验实际消费：** 所有尝试过的前缀各计一次，加全部续跑、环境与评分；未达保存点或不合格前缀也计入。
2. **某个方案完整执行任务的成本：** 该前缀成本加该分支续跑成本，不能将前缀视为免费。

额度未定前不启动付费前缀或分支，旧余额不自动转用。Token上限不是预期消费或现金保证。

## 7. 主分析与未知结果

采用按分配条件的主分析，即ITT。拒绝转移、交接失败、未完全回读、越界行为及KEEP更好的分支不剔除。是否offer、accept、实际呈现、回读、由谁诊断及谁写代码作为依从性与机制结果。

主终点是**最后合法提交的相应版本通过官方验收**；锁定最终工作树的代码正确率单列。工作树通过不能替另一个提交版本通过。技术未知保留未知及范围；已确定正常闭合但没有合法提交时，交付端点为0。未知费用也保留未定与已知部分，不填0，不阻塞其他结果汇总。

展示每个状态两次配对的完整质量、费用和执行记录。不把8个配对当8个独立来源，不作正式非劣或稳定性认证，不补样直到出现正收益。

后续只有观察到可解释的状态条件差异，才实现自动选择的O1／O2；参照应包括“只要合法就始终委派”和“只在任务初始选择一次分工”。跨任务更新须与冻结策略及等候选数、等验证预算的普通搜索比较，且还需从任务初态验证全过程，不能仅在旧检查点上选规则就声称在线进化。本轮不训练模型权重。
