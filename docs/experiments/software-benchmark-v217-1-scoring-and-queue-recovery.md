# 评分误分类修复与确认队列恢复

日期：2026年11月19日。用户要求处理异常并增强健壮性，避免少数任务阻塞整体实验。此修订只改变评分分类与队列恢复，不改变模型、题目、候选生成、图特征、C/N公式或已完成的生成轨迹；累计API额度仍1100元。

## 中断原因

第一轮开发6个合格状态、11条续跑全部评分完成，完成第一次更新。第二轮5个合格状态、8条续跑的模型工作也全部结束，但SymPy-16450 KEEP被评分封装列为技术未知，触发了全队暂停，第二次更新及确认均未启动。

核验原件发现：模型补丁实际已应用，官方测试脚本也确实启动；最终候选的`sympy/simplify/simplify.py`第274行仍有`<<<<<<< working-copy`冲突标记，导致导入时SyntaxError。官方结果保留`resolved=false`、`infra_failure=false`，但其`patch_successfully_applied=false`与实际应用日志不一致。旧封装把该字段作为“结果可判定”的必要条件，误把候选代码失败当成设施故障。

此次用原锁定候选、原应用日志、测试起止和退出码、实际语法报错路径及行号交叉绑定，并对原候选源码只做语法编译。状态改为`candidate_execution_failed / false`，原始报告和原technical_unknown记录不覆盖；没有修补候选，没有新模型调用、容器或重新评分。未知若缺少这些证据，仍保留未知。

## 恢复范围

第二轮规范记录另存，纳入上述明确失败后，用原第一次更新参数和原5个完整面板完成第二次更新。没有重算第一轮，也没有使用确认数据。随后从从未调用的16个确认题继续，沿用2个固定确认备用题及所有原预算约束。

开发实际为6＋5个任务状态，三个不合格前缀使用了两个固定开发备用，仍少于原计划12个状态；不再看成绩后补题。当前19条开发续跑代码通过13条、正确交付5条；它们不是19个独立任务。

## 新的故障隔离

- 普通代码失败、预算耗尽、未交付不暂停队列。
- 单题生成、准备或评分异常进入独立异常清单，其他题继续。模型已经调用的回合不自动重采；未定结果不填0。
- 对没有官方结果的评分设施异常，允许同一锁定候选使用新评分身份再试一次；明确候选失败不为追求通过而重评。有官方结果但解释仍不清的情况保留供集中核查。
- 同一任务的多次错误不会充当多题证据。只有至少三个不同任务出现相同类型及标准化原因的设施错误，才触发疑似共同故障暂停新准入；既有健康任务仍完成。
- 单个工作线程异常不再让整个窗口的结果收集失败；已完成候选立即记录。
- 无法读取账本、源封存不一致等协调器自身完整性故障仍停止，不能在结果或费用不可核查时盲目放行。

评分有未定候选的面板不进入完整候选加权分析，也不会被当作全失败。报告保留原计划分母、全部未知身份及费用，不能只报成功闭合子集而隐藏缺失。

四项CPU检查通过：严格区分候选冲突与超时／未应用／未绑定错误；不同任务的共同故障计数；原SymPy锁定候选恢复；一个工作线程抛错时其余任务仍完成。不重复旧评分镜像、缓存或SDK的整套验收。
