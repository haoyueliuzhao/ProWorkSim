# 对齐评测：补评后的阶段结果与通过率差异分析

状态：2026-11-04，**阶段报告，尚未完成全部恢复**。本报告使用 v113 原运行记录，合并 v114 两份原候选重评，另列两份停止工作树补充评分。Requests 1766、1921 在 REF／PROJECT 下的四个原回合尚未调用模型；v116 环境修订已准备，新增四项环境控制等待明确授权。

当前最明确的问题是：**PROJECT 的输入历史较重，同样的累计 token 预算容纳了更少的模型决定。** 但已观察到的分差同时包含定位与工具操作负担、修复不完整、错误的完成判断及公开测试环境问题，不能全部归因于预算或接口。交付闭合已明显改善：本轮 PROJECT 已通过的27份代码均有合法同版本交付。

## 1. 两组到底比较什么

两组都建立在 **OpenHands** 上，使用同一 DeepSeek Flash 非思考模型，均为一个实际 Agent。REF 采用原生终端与文件工具；PROJECT 在 OpenHands 上接入项目的受管工具、版本和权限规则、观察组织、公开测试入口与显式交付流程。这些规则服务于后续多智能体协作，本轮没有真实跨成员协作。

本轮已对齐一次结束自检、同预算历史摘要及 pytest／Django／SymPy 选择性公开测试。共同上下文为131,072、输入上限98,304、单次输出上限32,768，每回合累计输入＋输出最多5,000,000 token，保留512次尝试／决定及6小时／6.5小时边界。缓存命中的输入也计入累计 token 预算。

对齐公开测试入口不意味着执行能力完全一样：REF 的终端命令可组合操作并执行自定义脚本；PROJECT 仍通过受管动作和声明的测试选择执行，不额外开放不受管 shell。分页、来源版本、工具参数与最终交付语义也仍有区别。因此测量的是两套执行条件的整体差异，不是一个孤立 API 的因果效应。

题目是固定的50题、12仓库校准面板，不能称为完整500题 SWE-bench Verified 分数或新的独立确认集。

| 已实际调用模型 | 48 | 48 |
| 已确认代码通过 | 33 | 27 |

66%和54%目前是确认成功下界，**不是已经完整确定的点估计**；上述范围也不是置信区间。REF的4项未定包括两份异常停止回合和两道未运行Requests题；PROJECT的2项是对应Requests题。

已完成的两份原锁定候选重评为：Sphinx10614未通过、Pylint6528通过。它们修正的是评分路径，原候选未变。另两份REF停止工作树（Matplotlib22865、Xarray4687）补充评分均未通过，但它们不是原正常闭合边界下的候选；原生成异常标记保留。若单看包含停止树的补充代码端点，REF为33通过／15未通过／2待运行，仍须与严格原回合口径分开。

两组共同严格可评的46题中，25题都通过、12题都未通过、8题仅REF通过、1题仅PROJECT通过。这个共同子集只能用于配对诊断，不能替代完整50题分母。纳入两份停止树补充端点后，共同可评48题，成为25／13／8／2；这一变化本身说明异常端点口径会影响分差判断。样本按仓库聚集且已用于开发校准，不据单次显著性检验宣称总体接口损失已被准确估计。

## 3. token差异主要来自输入，而非输出

以下均以各组全部48个实际调用回合为分母，包括失败和生成异常；累计计入Agent与摘要调用，不只统计成功题。评分不产生模型token，两份停止树补评不重复记账。

| 实际平均消耗／题 | REF | PROJECT |
|---|---:|---:|
| 输入token | 2,095,019.56 | 2,861,763.00 |
| 输出token | 20,776.81 | 9,007.46 |
| 输入＋输出token | **2,115,796.38** | **2,870,770.46** |
| 输入占总token | 99.02% | 99.69% |
| 每次Agent请求平均输入 | 25,214.84 | 64,102.46 |
| 每题平均Agent决定数 | 82.58 | 44.40 |
| 全部输入缓存命中比例 | 95.48% | 84.98% |
| 每题平均API费用 | 0.21775元 | 0.51457元 |

PROJECT每题平均多用约75.50万token（**+35.68%**），其中输入多约76.67万，输出反而少约1.18万。Agent单次输入约为REF的2.54倍。这说明当前额外消耗主要发生在反复输入信息，而不能解释为模型写出了更多内容。不同工具的一次决定可完成的实际工作不同，82.58与44.40也不等价于两组操作能力的精确倍数。

摘要调用本身只占总token的REF 0.69%、PROJECT 0.64%，不是额外消耗的主要来源。PROJECT缓存命中更低又放大了人民币费用；缓存优惠降低付费金额，但不会返还被冻结的累计token机会。

现有已调用回合合计239,355,208 token，正式调用费用35.15132252元；另有本批中性准入1,212 token／0.001596元，单列而不摊入任务均值。原累计350元账本仍保留前轮费用与5.24288元未定预约，当前未用额度195.65182408元；后续四个首次回合费用仍计入同一账本。

## 4. 已观察到的系统性负担

**重复观察与任务说明。** 对每个已调用回合按固定规则抽取中间一次实际Agent请求，48个PROJECT样本都含重复的相同`role_task`，平均保留约10条受管观察。其user内容平均198,353字符，REF为6,642字符；REF另有独立tool内容，不能只比较user字符就推导全部输入差异。PROJECT重复观察包含任务、合同、资源／执行条件、版本与状态信息。具体例子中，第15次请求累积了15份约18,550字符的user观察，摘要之后仍可能保留大量观察文本。

这些字符证据定位了重复内容；上表的供应商实际token统计证明输入负担确实更大。**字符不是token，尚未做删除重复内容的单因素评测，因此不能把全部75.50万额外token或全部分差精确归到某个字段。**

**工具选择与参数恢复成本。** PROJECT记录到56次“无工具正文不等于结束”的格式反馈、17次`Unknown published patch`、11次路径不在对应来源版本、7次测试分页cursor错误、8次替换文本不唯一等。它们说明模型与当前schema、来源和分页规则之间仍有摩擦，但不意味着这些拒绝都应取消；不唯一替换、跨版本cursor等拒绝本身有保护作用。应改善可选参数、来源入口与可恢复反馈的清晰度，再测实际收益。

**预算确实截断了部分任务，但不是全部失败。** 正常终止分类中，REF有5题、PROJECT有8题因累计预算停止。另REF Xarray4687在预算末尾输出截断后触发历史解析错误，仍归生成异常，不把它藏进正常预算分类。八道REF独有成功中，三道PROJECT达到预算停止；其中Matplotlib20826的71个已执行动作全部是读取／搜索，没有编辑或测试，预算在定位阶段已用完。这是定位和信息成本值得优先修复的直接例子，仍不能断言多给预算就必然成功。

## 5. 逐题证据还显示模型修复与验证问题

以下例子来自公开问题、实际轨迹与最终候选；对照的是另一组成功候选，不把它冒称官方参考解，也不据此虚构隐藏测试断言。原因可能重叠，不能相加当作互斥失败比例。

- **pytest7490、pytest10081：修改循环没有闭合。** PROJECT分别执行8次、6次公开测试，均返回非零，最后仍有明确行为回归，直到预算停止。工具足以修改与跑选定测试，但模型没有完成修复；接口额外成本可能压缩机会，尚未证明是唯一原因。
- **Django15103：边界条件判断错误。** PROJECT仅用约93万token便结束且合法交付，其补丁使用`if element_id`，而成功REF使用`is not None`，对空值ID语义不同。该题不能归因于预算耗尽或未提交。
- **pytest7432：代码未实质改变，却宣称修复。** PROJECT最终补丁只更改注释，77项已有测试通过，但缺少对应issue的回归验证。合法交付的是功能上未完成修复的代码，属于可见的完成判断／验证错误。
- **Matplotlib23476、Pylint4970：已有测试通过不等于覆盖问题。** 前者通过182项已有pickle测试，但未覆盖报告中的反复反序列化DPI行为；后者自检宣称覆盖各调用路径，最终补丁仍表现出路径覆盖差异。结束自检已执行，却不保证其判断正确。
- **Requests2931：公开测试环境与执行入口共同干扰。** 实际测试出现httpbin fixture错误，模型通过pytest执行新复现又遇到收集／断言／类型错误；最终只修复部分调用路径。这是已观察到的公开反馈质量问题。v116只修另两道题的评分侧CA，不能据此宣称本题生成时的公开测试反馈也已修好。
- **Xarray6461：PROJECT也有独有成功。** PROJECT补充了标量输入回归测试并成功执行选定测试；REF做出另一种未通过的属性继承语义选择。因此不能描述成所有受管限制对每题都只有负面作用。

## 6. 哪些解释目前不成立

公开测试CPU时间不是当前已观测的主要消耗：PROJECT共176次`run_tests`调用，168次实际执行（165次选择性、3次完整），合计约773秒，无超时，同版本同选择重复执行仅2次。REF终端测试只能按命令文本作启发式统计，缺少同口径耗时，不能据此声称两组测试机会完全相同。

本轮也没有观察到“代码已通过但没合法交付”的新损失：27个PROJECT成功候选均有同版本合法交付。固定、测试、提交仍占用动作，但不能用历史批次的交付缺口解释本轮全部分差。单人条件没有实际成员通信和任务交接，不能归因于大量真实团队沟通成本。

## 7. 修复状态与下一步边界

两项原候选评分路径修复已用实际控制和评分完成验证。两个异常停止回合的SDK历史解析修复已做CPU控制，但没有用于重采原回合，也不改变剩余四个首次回合的冻结模型策略。两道Requests的当前IP和评分CA修订进入v116准备，真实环境资格尚待新的gold／empty控制，不把离线通过写成运行已通过。

本轮收口后，最值得单独验证的是：在保留最新状态、来源权限与交付证据的前提下，减少重复任务／静态观察进入历史；其次改善来源入口、分页和精确替换的失败恢复说明。再分别观察实际输入、有效动作和逐题代码结果，避免同时改预算、工具和提示后把提升全归因于某一个因素。本报告没有自动启动这些新消融。

后续四个原回合若获得合格环境，将合并其真实用量和评分，再更新本报告；两份停止树仍单列。所有旧结果与失败证据保留，不重采已调用回合，不调整题目分母。
