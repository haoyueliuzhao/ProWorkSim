# v050 r4：统一取消共享显存余量终止，并接管已预占的GPU2

## 1 用户授权与本轮目标

2026-10-15用户先要求恢复任务、固定高显存占用、放宽资源限制，并取消任务并发数限制。在原GPU2任务再次停止后，用户进一步明确“取消共享显存余量限制，继续任务”，随后要求“尽快占用GPU2”。本轮执行这些授权，恢复原Q+与Q−的同一学习分支，以及原16条从未启动的开发评估。

不增加训练材料、seed、方向、业务任务或optimizer更新次数。原40条已闭合生成槽、B更新、S*/B开发结果和全部停止记录保留。旧26试训/3正式更新/48独立确认、v046库存和缓存生产队列不恢复。

本轮独立源码为 `artifacts/software-learning-v050/resume-r4-source`，分支 `v050-resume-r4`，从r3的 `f5886b46a196f7f57c49ba173f16e48f4a135b2e` 建立。正式模型工作只在本协议、变化部分CPU控制和源码提交推送后开始；已授权的资源预占先行，事实和费用单列。

## 2 GPU2停止的已证原因与覆盖缺口

2026-10-15 22:29:20（北京时间），原r1监督器PID465916以 `shared_device_free_memory_reserve` 主动终止原Q+ PID3124120。22:29:13的GPU2空闲36453 MiB，22:29:20另一进程新增占用32234 MiB后空闲降至4214 MiB；Q+自身仍为44686 MiB。旧6144 MiB门因此触发。worker记录signal 15，22:29:24.952937退出，返回码−2；这次发信号来源明确。

这不是成功更新终态，也没有证据将其写成模型抛出OOM或外部进程直接发信号。r3资源修订仅用于新任务，原Q+仍由旧r1监督器持有，因此GPU2没有获得取消共享余量门的保护。这是上轮实施覆盖范围的缺口。本轮不再保留一个仍使用旧共享余量终止规则的在途Q依赖，而是在统一新监督器下管理两个恢复分支。

停止时Q+确认完成345/643条反向，原生前向989次已开始、988次完成；第346个梯度前向在途。actor/critic optimizer均0，完整状态步数仍4/4，只有更新前 `shared-before.pt`，没有可恢复的累积梯度/RNG/游标组合或更新后checkpoint。该进程已退出，不能把内存中的345条梯度当作可续接状态。

r3于22:29:31观察到原Q+失败并按冻结依赖门停止。其17个worker全部attempted=false，模型调用与GPU worker费用均0；r3预留的170001秒没有被消费。这个旧停止和未开始事实保持，不回写为成功或运行中。

## 3 已实际执行的GPU2资源预占

用户要求尽快占用GPU2后，已启动资源持有进程PID2111917，独立根为 `runs/software-learning-v050-gpu2-reservation-r4`。其原始启动命令、PID/start_ticks、GPU UUID、bootstrap源码SHA、实际显存采样及状态在该目录保存。申请时GPU2空闲81154 MiB；本进程一次成功建立73728 MiB（72 GiB）native CUDA allocator缓存，实际nvidia-smi占用约74142 MiB，预占后设备空闲约7003 MiB。

预占通过未初始化uint8分配后释放张量引用完成，live reservation tensors=0；缓存由同一个进程持有并可直接用于模型。该阶段没有加载模型、没有生成、没有反向或参数更新。资源进程保持运行，不能为了恢复而先释放显存、再开新进程争抢。

原始bootstrap已运行，不能热改或冒称另一个命令。它等待 `handoff.json`，只允许接入固定r4源码根、固定r4运行根和 `update-Q_plus`；核对冻结源码HEAD及监督状态中的本PID后，切换工作目录/导入路径，清理旧项目模块，保留已建立的torch/CUDA allocator，再直接调用r4 worker。资源模块沿用r3已验证代码，数学模型路径在接管时才装载。

bootstrap旧字段 `model_started=true` 表示已经转入worker入口的意图，不是实际模型调用的证明。实际模型加载、首次native请求、反向和optimizer仍分别以正式worker的独立凭据为准。

## 4 同进程接管的所有权与成本

新监督器先确认该资源进程的PID、start_ticks、GPU UUID、实际bootstrap哈希、原生解释器、缓存目标和当前状态，再登记本进程为Q+ worker；写入真实bootstrap启动命令与单独的逻辑worker入口，不能伪装成一次新的 `python -m ... worker` Popen。

只有正式计划、源码、CPU控制及GPU/任务绑定通过后才写handoff。监督器状态与派发凭据先落盘，bootstrap随后核对所有权并进入模型代码。接管代理依据精确进程身份、退出回执及worker终态判断，不把PID重用、失联或无回执死亡判为成功。其停止权限只限本次明确接管的资源进程及新启动的本项目worker；不信号其它项目任务。

直接进入worker时安装与普通CLI相同的SIGTERM处理，保留受控异常和终态回执；真正SIGKILL或无法确认的终止仍按未知处理。原Q+旧PID和监督器不恢复、不再使用。

预占前置时间、正式worker时间及训练区间分开记录。GPU实际占用从资源进程开始计，前置预占和随后模型阶段的区间不能重复相加；训练区间144小时上限按原定义只计训练入口至结束，预占等待与装载成本另外披露。

## 5 统一资源政策

所有r4新任务，包括接管GPU2的Q+、新Q−和16条开发槽，统一取消：共享设备空闲低于6144 MiB的强制终止、原56 GiB本进程显存上限、最多3个resident限制和额外60秒稳定等待。共享空闲量仍记录为诊断，不能单独杀死正在计算的本任务。

GPU0—7全部可用，按实际空闲量优先派发；GPU2由已接管的Q+持有，其余任务等待其它卡满足容量。每卡一个本项目resident，由实际容量和依赖决定并发，无额外人为数量上限。

新进程装载前最低实际空闲46080 MiB，缓存目标固定为 `min(73728 MiB, 空闲−1024 MiB)`，最低45056 MiB。GPU2沿用已经取得的73728 MiB目标。预占后装载资格仅加回精确同PID/UUID的自身缓存，不借用外部进程显存。临时预占张量在模型调用前释放，native allocator缓存供模型复用；启动占位峰单列，加载前重置监测峰值计数。

只有模型加载前的资源取得可以等待/重试，不重新执行已开始的模型计算。真实OOM、设备/进程身份错误、费用或记录不确定、磁盘/RSS越界等仍如实处理；不通过降低精度、改RoPE/attention、截断原输入或删除训练行来迁就资源。
