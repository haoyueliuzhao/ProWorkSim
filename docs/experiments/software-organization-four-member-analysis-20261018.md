# 四人组结果下降：实验结果与轨迹原因分析

**ProWorkSim｜分析日期：2026年10月18日｜仅分析已有运行，未启动新模型或补做验收**

快速阅读：[简要分析](software-organization-four-member-analysis-brief-20261023.md)。

现有证据指向三个不同问题：**固定四人自由组织把有限资源分散到多套未完成的实现；四人独立候选受到生成子预算和选择行为阻断；四阶段协作经常没有完成成果交接，并在最后被权限、上下文或预算限制挡住。**

最重要的共同事实是：**28次实际四人运行中，4次成功，另外24次失败全部没有形成最终合法提交。**因此，成功率下降首先表现为交付未完成；未提交工作区没有统一补做私有验收，不能进一步推断它们的代码全部错误或全部正确。

这里的“下降”描述观测成功数变化，不等同于已经证明统计显著。各同条件比较只有2、4或8次运行，且不是所有四人条件都下降：50万预算的四候选与同期单人成功数相同，修订输入表示后的四阶段与同期单人也同为2/2。

## 2. 固定四人自由组织：分支变多，验证修订没有相应完成

### 2.1 同一总预算被分到更多独立工作分支

固定双人与固定四人都没有人工指定岗位，每次团队预算均为50万token。各8次运行的过程指标如下：

| 过程指标 | 固定双人 | 固定四人 |
| --- | ---: | ---: |
| 总模型调用 | 322 | 336 |
| 每成员平均模型调用 | 20.125 | 10.500 |
| 每成员平均完整token | 24.44万 | 12.32万 |
| 成功读取事件 | 134 | 162 |
| 成功修改事件 | 64 | 62 |
| 已接受的公开测试调用 | 40 | 18 |
| 固定成果事件／正式提交事件 | 4／4 | 1／1 |
| 格式拒绝输出 | 36 | 47 |

事件统计按各8次运行求和；人均分母分别为16、32个成员会话，包含提前退出者。测试调用是整次测试运行，不是断言数量；测试失败也计入。格式拒绝已经包含在模型调用中，不能重复相加。

**观察到的变化是每个成员推进得更浅：**总模型调用近似不变，单成员调用约减半；修改事件没有增加，测试却从40次降至18次。四人7次失败的28个成员中，17个没有实际测试，6个当前版本公开测试未全过，5个最新修改后没有复验。

四人失败槽没有工具级工作消息或成果整合记录，未形成把多个分支连接到一个已验证交付的证据。这里有“预算分散、各自实现、验证修订未闭合”的过程证据，但没有控制实验能证明把某个成员的额度转给另一人必然成功。

### 2.2 代表性配对轨迹

| 任务 | 四人组实际轨迹 | 同任务双人对照 |
| --- | --- | --- |
| job-policy，seed尾号102 | 003、004分别消耗131,820和129,419 token，没有成功编辑或测试；001唯一一次测试报 `cannot import name 'Int' from 'schema'`，之后没有修复复验，全队无固定提交 | 002完成“测试失败 → 修订 → 测试通过 → 固定 → 提交”，提交时团队累计280,540 token |
| room-bookings，seed尾号101 | 多人各自实现；测试先后出现不存在的 `min_len`、`Int`、`strict` 参数或属性；两人未测试，所有人无固定提交，最后触及共同预算 | 002完成“测试失败 → 修订 → 测试通过 → 固定 → 提交”，提交时团队累计355,449 token |

这些是明确的代码/API错误和缺失复验，不能将失败仅描述为最后缺一个提交动作。共同预算确实结束了运行，但“预算耗尽”只是停止条件，前面的工作没有收敛到可交付版本才是需要解释的过程。

**反例也必须保留：**room-bookings另一seed中，四人成功、双人失败。四人组的003第一次输出便声明done退出，001随后独立实现并成功提交；002整合001补丁产生的冲突没有进入最终交付。它不能证明退出有益，但足以说明“成员退出”或“合并冲突”不是本批四人失败的统一解释。四人组仅2次硬context拒绝，也不足以解释7次失败。

## 3. 四人独立候选：低预算产不出合法候选，高预算仍可能卡在选择

### 3.1 人工预算切分阻断了实际生成路径

该架构将团队预算70%用于生成，四人均分，另外至少30%留给原成员1选择。生成分支不能互借额度，余额只能向选择阶段流转；选择阶段不能编辑或合并代码。

| 团队预算 | 每个生成者初始额度 | 生成阶段实际推进 | 合法生成候选 | 最终成功 |
| --- | ---: | --- | --- | ---: |
| 25万 | 43,750 token | 16个生成分支全部在3次模型调用后遇到子预算拒绝 | 4次运行全部为0 | 0/4 |
| 50万 | 87,500 token | 每个生成者5或6次调用 | LA有3个；LB有1个；HA/HB为0 | 1/4 |

例如低预算LA的001已用36,118 token，剩7,632；下一请求需要13,784输入＋2,048输出预约。它符合单次上下文容量，但超出分支余额，因而无法继续。不能把这个拒绝误归为context超限。

低预算四次运行的生成阶段共花610,389 token，没有生成阶段固定候选；随后选择阶段又花366,089 token。空候选池和选择阶段不能修改代码的组合，使后续余额无法继续完成原来的生成工作。对照双候选在同样25万总预算下，每个生成者有87,500 token；其LA两名生成者完成5、6次调用，其中一人形成候选并被采用后成功交付。

这支持分支额度压缩候选完成机会的解释，但不证明三次调用在理论上绝不可能产出候选，也不证明增加额度必然成功。

### 3.2 已有代码进展，却错过候选登记阶段

低预算LA的真实顺序是：

> 生成阶段结束，候选池为空 → 选择阶段公开测试通过 → 此时才固定patch-1 → 提交被拒 → 尝试采用patch-1也被拒 → 结束，未提交。

原反馈分别要求：

- 提交必须等于已明确选择的固定候选：`Final I files must exactly equal the explicitly selected fixed candidate`。
- 只能选择生成阶段冻结的候选：`Select only a frozen generation candidate`。

所以问题不是选择阶段完全没做工作，而是成果形成时机与人工阶段协议不匹配。公开测试通过仍不等于私有完整验收通过，本次没有补验或改写原失败结果。

原证据为 `org47-A-r0-I4-B250000/experience.jsonl` 第397、420行，事件序号396、419；完整路径保存在专项证据JSON中。

### 3.3 产生候选之后，选择行为也能单独阻断交付

高预算LA已经有3个合法候选，四名生成者的公开测试均有通过记录。随后选择者：

- 花费 **207,579 token**，连续13次读取同一个patch-1的 `event_time.py`。
- 每次都从第1行开始，完整文件只有23行；首次最多读50行，后12次最多读30行，均覆盖同一完整文件。
- 13次工具返回均成功；首段、末段两处实际输入抽样也包含完整23行反馈，下一次生成仍重复读取。
- 没有采用候选、没有选择阶段测试、没有提交，最终团队预算不足以继续调用。

这是已经观察到的行为停滞，不能用“没有候选”或“读取工具一直失败”解释。模型为何重复读取仍未被独立识别，可能的策略或输入进度保持问题应另行验证。

唯一成功的高预算LB完成了“生成固定候选 → 选择者采用 → 本人测试 → 固定当前版本 → 正式提交”，最终完整验收通过。I4的7次失败中，**6次生成候选池为空，1次有候选却重复读取到预算结束**；8次均进入选择阶段，没有提前永久退休或硬context拒绝。

详见[四候选完整轨迹分析](four-member-analysis-20261018-assets/i4/findings.md)及[阶段费用、原动作和反馈证据](four-member-analysis-20261018-assets/i4/evidence.json)。

## 4. 四阶段协作：交接没有自动发生，最后阶段又缺少修补能力

### 4.1 人工架构放大了交接是否完成的重要性

四人职责和预算固定为：

**成员1实现（35%） → 成员2复核（20%） → 成员3修订整合（25%） → 成员4验证提交（20%）。**

成员1、3能改代码但不能正式提交；成员2、4能采用和测试候选，却不能编辑或合并。各人有自己的初始工作区，前驱修改不会自动传给后继，必须发布并显式采用；阶段只能向前推进。

在原8次架构比较中：

- 只有3次运行发布过固定候选。
- 只有1次最终验证者采用了候选；其余7次最终验证者末态仍是初始版本v1。
- 8次均没有最终提交。

一个典型轨迹是低预算LA：

> 实现者写好代码、公开测试通过并发布patch-1 → 尝试提交，被阶段权限拒绝 → 复核者采用patch-1 → 修订者却从初始树重新实现，测试通过但未发布 → 最终验证者测试自己的初始树失败 → context拒绝，结束。

这说明有多个成员工作不等于成果按阶段累积。双阶段LA对照中，第二人拥有修改和提交权限，实际完成了“修改 → 测试通过 → 固定 → 提交”；但该例也是第二人重新实现，不能据此声称前后分工本身带来了协作收益。

12次四阶段运行共有10次架构权限拒绝，例如最终验证者试图修改 `migration.py` 被拒；修订表示的两次成功运行也有4次权限拒绝。因此权限与行为不匹配是真实阻力，但不是一出现就必然失败的充分条件。

### 4.2 最后停在哪里：7次context，3次团队预算

四阶段10次失败中，最终验证者有7次因硬context拒绝结束，3次因团队token预约不足结束。**这个7／3是最后的资源停止分类，不代表更早没有候选缺失、权限误用或重复工作。**

同一50万预算也可能尚有大量余额，却不能再发一次请求。增加团队总token无法解决单次输入超过上下文容量的问题。

| 代表轨迹 | 最终阶段实际发生了什么 | 直接阻断 |
| --- | --- | --- |
| LA，原50万架构对照 | 采用patch-1 → 公开测试通过 → 无最终提交 | 输入16,816＋输出预约2,048＝18,864，大于容量18,432；团队尚余128,918 token |
| LA，原表示机制对照 | 采用patch-1 → 公开测试通过 → 后续生成未发生 | 输入16,485＋2,048＝18,533，超出容量101；团队尚余228,474 token |
| LB，原表示机制对照 | 先测试初始树失败 → 采用patch-1 → 未对采用后树复验或提交 | 读取后输入16,796＋2,048＝18,844，超过容量18,432 |

LA是“采用后测试已通过，但未能继续提交”；LB是“采用后还没复验”。二者不能混写为相同过程。

### 4.3 已有与成功交付相同的代码，也可能因为流程未完成而失败

LB原表示运行中，最终成员采用后的整文件树，与修订表示运行最终成功交付的文件树哈希完全相同：

`0b57edcdcdb36e0169d50390e7421e40407a98c7a6073a6fe2970e464bf20fe6`

原记录分别位于 `software-organization-v048-final.json#/slots/5/exact_candidate_applications/0/files_sha256` 与 `#/slots/4/final_fixed_submission/submission/files_sha256`。

但原表示运行没有采用后的本人测试，也没有固定提交，原R=0应当保留。这是静态同字节证据，**直接说明至少有一条失败包含“代码已经取得，交付流程没有完成”的问题**，没有进行新的反事实验收。

严格同值引用修订输入后，两次P4运行的硬context拒绝从6次变为0次，两次都完成：

> 采用成员3的固定候选 → 本人同版本测试 → 固定当前版本 → 提交 → 完整验收通过。

成功从0/2恢复为2/2，是输入表示影响该流程可执行性的较强局部证据。但不同表示也改变后续模型动作，不能将其说成同一条确定轨迹的简单重放。修订后仍有重复实现、错误权限尝试和额外交接；P4平均消耗43.06万token，同表示单人14.39万，双方都2/2成功。

## 5. 原因判断与后续优先级

| 原因判断 | 证据程度 | 适用范围 |
| --- | --- | --- |
| 固定总预算下，更多独立分支挤压了单分支验证修订深度 | 人均调用、测试次数和配对轨迹直接可见；对成功率的独立贡献尚未识别 | 固定四人自由组织，部分阶段架构 |
| 生成子池不足，候选冻结为空，后续选择者又不能继续编辑 | 有实际预算拒绝、候选池状态、采用／提交拒绝记录 | 低预算四候选最明确；高预算HA/HB也无候选 |
| 有候选但选择者重复读取，不进入采用和提交 | 原动作、成功返回及实际后续输入有证据；重复行为的模型内因未定 | 高预算四候选LA |
| 前驱成果未传到最终成员，权限限制又不允许最终成员自行修复 | 原版本、采用事件及权限拒绝有证据 | 四阶段协作 |
| 单次context容量直接阻断测试后的固定提交 | 原请求长度、拒绝及反馈中断有证据；表示修订配对提供局部支持 | 四阶段协作，不能推广到无context拒绝的I4 |

**优先改进应围绕完成交付路径，而不只是增加人数或总预算。**以下是待验证的设计建议，本次没有实施，也不声称收益已经成立：

1. **先使成果可以按阶段传递。**明确生成／实现阶段结束时必须留下什么可采用成果；单独定义空候选池和未发布成果时的后续处理，避免继续消耗无从交付的阶段预算。
2. **调整资源分配与成员使用方式。**比较固定四人同时各做一套、先形成一条完整解再展开其他分支等策略；对独立候选单独检验生成份额和候选登记时机，而不是把总预算翻倍当作充分修复。
3. **改善选择阶段的进度保持。**针对已经完整读取同一固定候选却反复再读的行为，独立验证进度提示或重复动作处理，并观察是否真正进入采用、验证与提交。
4. **让最终负责人能完成必要收尾。**在新协议中比较允许受限修订、返回修订阶段或合并修订与验证的安排；保持可执行的输入表示，保留本人同版本测试和固定提交证据。

现有记录支持“组织制度与模型实际行为没有顺畅接上”的解释，其中包含代码/API错误、有限预算、候选登记、交接和输入容量多方面因素。它不支持把下降统一解释为四人本身降低了能力，也不足以确定哪一种重设计必然最优。
