# v230 实验报告｜减少重复输入，给新负责人留下行动机会

2026 年 11 月 24 日。本轮完成了历史回放和本地双 Agent 运行测试。四个案例的 346 次真实历史请求，在保留相同历史动作、工具和权限的条件下，优化后的本地分词输入合计减少 **36.78%**。Sphinx-9591 的历史记录也解释了伙伴为什么没有执行新职责。新调度器在真实 OpenHands SDK 中通过了确定性复验。本轮新增付费 API 调用 **0 次**，没有产生新的任务分数。[上轮审计材料](v229-dev1-audit-report-20261124.md)

## 1. 历史 token 花在了哪里？

逐笔核对了 v228、v229 的供应商响应、用量文件和各自的费用账本。下表的费用按历史账本的冻结费率复算，两个账户分别核算。缓存命中和未命中之和就是实际输入。供应商没有单列这批请求的推理 token，因此该项记为未知。[分账及逐请求档案索引](../../artifacts/software-benchmark-v230/engineering-r1/token-replay.json) · [DeepSeek 缓存计量说明](https://api-docs.deepseek.com/guides/kv_cache/)

| 历史批次 | 已结算请求 | 实际输入 token | 其中缓存命中 | 实际输出 token | 账本计费（元） |
| --- | ---: | ---: | ---: | ---: | ---: |
| v228 | 646 | 37,436,951 | 6,941,440（18.54%） | 153,262 | 62.4948 |
| v229 | 785 | 44,288,363 | 8,399,232（18.96%） | 162,709 | 73.4159 |
| 合计 | 1,431 | 81,725,314 | 15,340,672（18.77%） | 315,971 | 135.9107 |

**输入占实际总用量的 99.61%。** 为了解内容构成，我们用冻结的分词器逐字段计数。项目状态约 2,184 万、组织状态与工作约束约 1,951 万，两项占本地完整输入的 **50.67%**。工具定义约 947 万，工具返回约 678 万。能直接识别的伙伴消息输入约 117 万，占 **1.44%**。这项只计算直接呈现的消息，交接记录、工具参数及重复呈现的其他组织信息各归其来源，不能据此估算协作的全部开销。

基于这一分布，优先改的是每次请求都携带的项目与组织状态。例如同一题内，文件列表和任务负责人均未变化，只有一个新测试结果。现在保留该成员可见的首份完整状态，后续发出发生变化的字段、删除项及前一份状态的位置。摘要造成历史截断后，从当前请求中仍然可见的第一份状态重新开始。

输入分项是估算。历史完整输入按本地分词比供应商少 114,724 token，模板和分字段切分的差额单列。输出另外统计正文、工具参数和组织决策参数，分项未覆盖的格式开销保留在供应商输出总数中。[九类来源及输出分项](../../artifacts/software-benchmark-v230/engineering-r1/token-replay.json)

## 2. 同一条历史请求，实际缩短了多少？

**T0 原始输入**沿用当时请求中的完整观察和工具返回。**T1 优化输入**保留同一成员的系统说明、工具定义、动作顺序和证据权限。相邻观察只发送变化，同一条伙伴消息可以引用其第一次出现的位置。较长的公开测试页面保留版本、结果和诊断，并给出取回原页的工具参数。组织策略 Agent 仅接收其可见的异常证据和合法选择，执行成员接收与其职责相关的工作和依赖。完整原件在模型输入之外保存。

下表在四个审计指定案例上，用同一个历史请求分别构建 T0、T1，再用同一分词器计算完整输入。Astropy 包含 v227 的 49 次共享前缀请求，已在案例中计一次，这些请求没有再次计入上节的 v228 账本。

| 案例与历史范围 | 请求数 | T0 输入 token | T1 输入 token | 降幅 |
| --- | ---: | ---: | ---: | ---: |
| Astropy-14182，共享现场和 W0／W1 两条续跑 | 129 | 7,460,776 | 4,649,547 | 37.68% |
| Sphinx-9591，共享现场、策略请求、维持／调整分工 | 103 | 5,903,930 | 3,748,663 | 36.51% |
| SymPy-19954，共享现场、策略请求、维持分工 | 50 | 2,700,196 | 1,652,785 | 38.79% |
| Sphinx-10449，自然完成并正确交付的长轨迹 | 64 | 3,653,714 | 2,414,455 | 33.92% |
| 合计 | **346** | **19,718,616** | **12,465,450** | **36.78%** |

2,957 份成员观察均能还原，其中 2,637 份用增量表示。同一消息重复呈现转为引用 42 次。21 次长测试页呈现均按原成员、报告号、版本及游标核回原文。这些是呈现次数，一份材料在不同请求重复出现会分别计数。四案中满足严格相同内容和大小条件的重复文件结果引用为 0，因此这部分没有贡献表中降幅。

按原始请求中的对象核对，**39 次异常提示、9 项策略证据、119 次工具错误和 233 次带版本的测试回执**均保留，共 **400/400**。该比率衡量这些已定义对象的保留程度。它不能度量模型读懂证据的概率，也无法证明所有具有任务价值的信息都已列入分母。

同一成员、同一角色相邻请求有 312 对可比较。T1 可复用的共同前缀合计从 3,662,143 降到 3,526,622 token，缩短 **3.70%**。因此实际费用可能与输入用量按不同幅度变化，仍需观察在线的缓存命中、输出、工具回读和任务步数。[完整回放结果](../../artifacts/software-benchmark-v230/engineering-r1/token-replay.json)

## 3. 为什么 Sphinx 的新负责人没有行动？

Sphinx-9591 调整分工后，001 保留实现职责，002 新增独立诊断职责。当时还剩 **970,203 token**，但 002 仍处于等待。第 68 至 81 次机会连续选中 001。第 82 次才选中 002，这时只剩 **38,675 token**，原运行器因预算边界结束。这一次 002 有调度记录，却没有实际发出模型请求。历史证据支持“新职责没有及时变成行动机会”；它没有回答“如果 002 及时参与，能否修好代码”。[逐机会及预算证据](../../artifacts/software-benchmark-v230/engineering-r1/trajectory-replay.json)

新调度器在职责生效前检查能否给新负责人、验证者和最终交付者各留出一次调用机会。在当前上下文和输出上限下，每次按 131,072 token 的保守上界计算，合计 393,216。实际消耗仍按用量结算。授予新职责时，等待中的成员收到版本通知并优先执行；其余时间继续使用原有轮转调度。资源不足会留下拒绝理由，已永久停止的成员保持停止。一次机会允许成员自行选择动作，无法保证它完成验证或交付。

**在两种输入条件下，各跑了一次真实 OpenHands 双成员 SDK。** 使用本地脚本产生确定性的模型响应。002 自行进入等待，控制器发出诊断决定，随后 002 立即获得首个新机会并成功读取文件。两组均观察到新负责人、验证者和交付者依次得到预留机会；两组均在预算不足的控制中拒绝了改组。每组实际执行 5 次成员请求、1 次独立控制器请求，控制器的 281 个脚本用量从同一团队额度扣除。临近交付的场景在脚本中显式设置剩余额度。这里验证的是机会和扣账，脚本没有证明修复成功。[SDK 运行凭据](../../artifacts/software-benchmark-v230/engineering-r1/sdk-control.json)

## 4. 轨迹能还原到什么程度？

四个案例共 11 个历史片段，包含共享前缀、策略提名和后续分支。按检查点身份接回原前缀；按成员、调度机会、调用号、供应商响应号、工具调用号及实际世界动作号连接记录。时钟只用于比较相邻请求的前缀，因果关联使用原生身份。

- 346 次物理请求均有响应和用量。328 次调度机会中包括等待和预算拒绝。331 项成员工具意图中，287 项对上了项目执行回执，其中 12 项明确拒绝。其他 44 项没有项目工具执行回执，包含 SDK 的等待、私有工作台或派发前处理，不计作真实项目操作。
- 302 个项目事件可以直接回连到这些工具操作。继承自共同前缀或初始化等其他事件单列并保留原件。四次受控组织图激活均保留版本；自然运行阶段使用原世界记录，不补造受控版本号。
- 保留原评分。Astropy 两分支、Sphinx-9591 两分支均未通过代码和交付；SymPy 的维持分工分支、Sphinx-10449 的自然运行均通过两个端点。上述是旧运行结果，本轮没有改变候选或重新评分。[分支及评分凭据](../../artifacts/software-benchmark-v230/engineering-r1/trajectory-replay.json)

实现把原始输入、实际呈现输入及其清单绑定到同一个请求身份。物理调用前留存，响应已返回而观测写入失败时保留返回结果并标记轨迹不完整。同一身份在响应不确定时不能再次派发。只读文件缓存仍逐次检查调用者权限、版本和路径，每次读取产生独立回执。写入、测试、提交不走只读缓存。[运行接线](../../src/proworksim/software_graph_execution_v230.py) · [记录与派发](../../src/proworksim/software_trajectory_v230.py) · [回归测试](../../tests/test_token_execution_v230.py)

## 5. 下一轮可以检验什么？

已登记 v231 的三个历史保存点，每个现场各跑 T0、T1 一次，共六条续跑。两组复用同一现场和已记录的组织决定：Astropy 和 Sphinx-9591 使用独立诊断，SymPy 使用维持分工。两组共用相同的双成员、模型设置、职责调度、工具权限、5M 团队上限和官方评分规则。共享前缀及控制器的实际用量先扣除，配对分支获得相同余额。这是针对历史场景的机制试验，不能用于估计整个基准的平均收益。[三个检查点及各对余额](../../artifacts/software-benchmark-v230/engineering-r1/next-paired-design.json)

v231 的主要判据是每题的**实际输入、总费用和正确交付能否同时改善**，另报缓存命中、输出、调用次数、证据回读、总时间以及技术未知。当前证据支持进入小规模在线配对；实际缓存、费用、任务时间和正确交付率的变化仍待测。本轮按审计保留为零 API 工程实验，旧账本余额未转入新试验。
