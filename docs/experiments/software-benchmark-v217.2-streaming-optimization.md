# v217.2 实验提速与调度交接

2026-11-19。此次只调整执行效率，不修改任务、候选、选择器、模型设置、评分或累计1100元预算；不增加模型尝试。

## 为什么慢

确认阶段原调度器有两层等待：先等整批前缀与候选准备完成，再开始续跑；一个任务的生成槽还要等该任务全部候选评分结束才释放。早已准备好的任务曾等待约69–71分钟。提高名义并发不能消除这两种等待。

18个确认前缀累计模型循环14917.4秒，其中API请求1089.7秒（约7.3%）、公开测试回调153.4秒（约1.0%），其余13674.2秒在本地执行路径。后者不是完整CPU剖析，不能全部归为序列化。

大仓库的状态处理确有显著开销。例如sklearn-9288前缀总计约52.2分钟，最终状态738139283字节，约704 MiB；旧编码缓存命中率约0.56%，且状态大于512 MiB会转入较慢的读取路径。

## 已实施的优化

1. **生成与评分分离。** 新调度器按续跑分配槽位，生成结束立即释放，评分进入独立队列。上限18路生成、2路评分、6路环境启动；接管前仍存活的子进程也计入容量。单任务错误独立记录，只有多任务重复的同类基础设施故障才暂停新准入。
2. **大状态缓存。** 编码缓存上限384→1536 MiB，产物缓存256→768 MiB，原生JSON读取阈值512→2048 MiB。保持原规范编码、保存格式、哈希、权限判断和业务类不变。增加内存占用有明确上限，仍受普通用户服务与主机余量准入约束。
3. **不重启模型的交接。** 只暂停旧协调器派发，不向模型或评分子进程发信号。新协调器采纳已有结果、等待已有子进程，并复用账本预约。只有此前未启动的task16两条及task28、29各一条使用缓存优化版。旧子进程全部结束后才退休旧协调器。

本次确认的候选池已经全部准备完成，因此此前的整批准备等待无法追溯消除。本次上线直接解决后续生成与评分互相占槽的问题，不把它描述为已修复所有未来阶段的准备屏障。

## 验证结果

在同一个已闭合的704 MiB真实状态上，测量读取、三次哈希、验证、保存及缓存读取：

| 本地操作 | 旧版秒 | 优化版秒 |
|---|---:|---:|
| 冷读取 | 12.108 | 5.259 |
| 三次哈希 | 9.247 | 3.969 |
| 状态验证 | 2.273 | 0.170 |
| 保存 | 3.400 | 1.459 |
| 缓存读取 | 0.026 | 0.029 |
| 合计 | 27.054 | 10.886 |

该基准约加速2.49倍。规范哈希、保存字节哈希完全一致，原数据未修改。它是单个已闭合状态的局部基准，存在缓存与系统负载影响，不代表整轮实验加速2.49倍。

第一版试验曾改用原生紧凑JSON计算哈希，该路径更慢，最终未采用；对应基准原件保留。4项状态、权限、公开测试、合法交付及故障恢复控制，加2项队列控制通过。接管r1曾因继承资源租约刷新时嵌套非重入锁卡在调用模型之前；核实其子进程数为0后终止，仅修订协调器为r2，并增加1项真实容量锁回归检查。共7项CPU检查通过。原模型不受这次协调器启动故障影响。

## 当前部署与统计口径

有效服务为`proworksim-v217-streaming-r2.service`，输出在`runs/software-benchmark-v217/streaming-r2`。它接管13个合格状态、22条续跑：18条已有身份，4条尚未开始的身份。已有回合结果仍在`confirmation-resume-r1`，新汇总按`adopted-plan.json`映射读取，不能只统计新目录。

运行快照已证实4个未启动回合进入环境准备，已有回合同时进入独立评分队列。快照时容量登记11路生成（含7个旧进程、4个新启动）、1个评分；这是瞬时状态，不是承诺持续18路。缓存优化仅对4个新回合有效，旧慢回合不会因为调度交接自动加速。

新服务64核等价CPU、320 GiB内存硬上限、288 GiB高水位、禁用swap；不修改共享服务器配置、既有挂载或他人任务。累计账本上限仍1100元，快照已结算584.1848848元，尚余515.8151152元；预约不当作实际支出。
