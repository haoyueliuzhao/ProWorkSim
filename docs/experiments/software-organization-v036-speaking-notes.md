# 任务与职责如何由模型形成：逐节汇报稿

日期：2026-10-09。对应材料：[任务与职责如何由模型形成](software-organization-v036-briefing.md)。

讲述范围为已结束的 v0.36 P2 支持窗口。预计约 7—9 分钟，备答不计入；这是时长估计，尚未实际计时。以下为汇报者讲述稿，不是模型原话。章节与主材料对应，原始事件和统计依据见主材料的证据索引。

## 开场：机制说明

**当前实验中，任务由模型成员在合同范围内自行拆分，职责通过认领、转交等工具操作形成。** 今天讨论的是已经结束的 v0.36 P2 窗口，所有案例和数字都来自这一批记录。

这里的“合同”，就是预先规定的根目标、模块和 API，以及验收要求。A、B 使用相同的模型参数和业务材料，各有独立会话和私有工作副本。开始时任务表为空，没有预设“实现者”“测试者”等岗位。A 固定先行动，之后调度器轮流给可运行成员行动机会。

成员调用 create_task，自己填写任务描述、编号和父任务，新任务暂时没有负责人。任一成员可以调用 claim_task 认领，系统才把正式负责人设为该成员。所以，创建者和负责人可以不同。

如果要转交职责，当前负责人可以调用 delegate_task，把任务交给伙伴；接收任务的伙伴也可以用 return_task 退回，任务会清空负责人、恢复待认领状态。有权限的成员还可以修订任务、声明或移除依赖，环境检查版本和依赖环等约束。

这些操作的参数由模型生成，环境负责校验和保存。成员也可以通过消息协商，但消息本身不会修改正式负责人。

**机制允许自主组织，也允许重复工作、集中完成或先执行后登记。** 任务负责人不会获得文件专属编辑权，双方仍能修改各自副本中的同一批文件。因此，任务归属不能直接当作实际贡献。下面用五段真实轨迹，说明这些机制在任务中怎样表现。一个“槽”就是一次双成员运行，编号从 0 开始。

## 共同任务：完成语句提取与汇总两个模块

这 16 次运行完成的是同一个 SQL 脚本清单任务：输入一段 SQL 脚本，先整理出其中各条语句，再生成一份汇总。

reader.py 提供 statement_records，要求调用真实 sqlparse API，按顺序生成语句记录；report.py 提供 summarize，使用 reader 的结果，返回记录、三类语句计数和总数。

例如合同中的脚本先查询 bins 表中的 label，再更新 flag。预期结果应当包含两条语句记录，SELECT 和 UPDATE 各计一次，DELETE 为零，总数为二。

这些要求预先给定，但谁实现 reader、谁实现 report、谁做验证，都没有事先分配。双方都能修改自己副本中的两个模块。

私有副本意味着：A 写好的代码，不会自动出现在 B 那里。A 需要发布固定版本的补丁，B 再显式整合，才能把改动带进自己的副本。如果双方已经修改同一处，整合就可能发生冲突。

## 第13号槽：先执行后登记，也允许重复工作

这段轨迹主要体现，成员可以先做实现、后登记任务，同一工作范围也可以出现重复实现和重复任务。

最开始，A 已经修改了 reader 和 report，但任务表仍然是空的。之后，A 创建了一项实现任务，由 B 自行认领。于是，创建者是 A，正式负责人是 B，而 A 的实现工作已经发生。

B 认领后，A 又发消息，请 B 认领任务并发布补丁。这里，正式认领早于这条消息；消息没有产生新的责任转移。

随后，B 发布了自己修改两个模块后的补丁。A 整合这份补丁时，两个模块都发生了冲突。B 也曾提交过自己的版本。此时，双方已经形成了两份范围重叠的实现。

之后，A 又创建并认领了一项新任务。新任务与 B 持有的实现任务描述完全相同，任务表中因此有两条同范围任务，分别由 A、B 负责。

最后由 A 发布并交付自己的版本，原完整验收结果为通过；原有产物判定规则未确认最终版本有效保留了伙伴产物。

这条过程对应两个具体机制：编辑不要求先登记任务；认领任务也不会锁住对应文件或排除别人创建同范围任务。因此，自主组织的过程中可以出现先执行后登记，也可以出现重复工作。

## 第00号槽：验证职责可以在工作之后登记

这段轨迹主要体现，“验证”职责可以在编辑、冲突修复和检查已经发生之后才登记。

开始时，A、B 都先编辑了两个模块。之后，A 创建并认领实现任务，发布了自己的补丁。

B 整合 A 的补丁，两个模块发生冲突。B 修复冲突并通过公开检查之后，才创建并认领验证任务。

随后，B 发布自己的补丁并形成最后一次固定交付。原完整验收通过，原判定规则也确认了有限的伙伴产物保留关系。这一槽双方都曾提交，这里讲的是最后由 B 交付的版本。

因此，任务名称中的“验证”记录的是执行中登记的职责。机制允许编辑和检查早于任务登记，不能从这个名称倒推 B 一开始就被分配了测试岗位。

## 第05号槽：创建者与负责人可以不同

这段轨迹主要体现，任务创建者不会自动成为负责人，负责人由成功认领的成员确定。

A、B 都先编辑了两个模块。A 随后创建实现任务，B 认领。A 再尝试认领同一任务时，被系统拒绝，因为该任务已经有负责人。

之后，A 另建并认领了一项验证任务。任务表中的安排变成 B 负责实现，A 负责验证。

接着，B 发布补丁，A 整合时发生冲突。A 修改冲突副本并测试，随后发布和交付自己的版本。原完整验收通过，原判定规则确认了有限的伙伴产物保留关系；这一槽双方也都曾提交，最后交付者是 A。

与第 00 号槽相比，实现、验证标签对应的成员不同。这些安排都由运行中的创建和认领形成，没有发生正式转交。create_task 只新增未分配任务，claim_task 才确定负责人；任务已有负责人时，另一成员不能直接再次认领。

## 第14号槽：一名成员可以集中完成并交付

这段轨迹主要体现，一名成员可以形成覆盖两个模块的完整产物，并独自完成本槽的固定交付。

双方先编辑了两个模块。A 后来创建的任务只描述 reader 实现，由 B 认领。

B 发布的补丁却同时覆盖 reader 和 report。A 整合这份补丁时发生冲突，B 随后提交了自己的完整本地版本，通过原完整验收。

A 之后继续修改自己的冲突副本，但没有形成第二份提交。所以，本槽只有 B 交付，并不表示 A 没有工作；这里的集中完成，指完整产物与固定提交集中在 B 一方。

这对应任务归属与文件编辑权限的关系：任务描述不会自动把文件范围锁住，成员可以在自己的副本中完成多个模块，再发布和提交完整版本。

## 第12号槽：没有登记任务也可以编辑和测试

这段轨迹主要体现，即使任务表一直为空，成员仍然可以执行编辑和测试。

这一槽从始至终没有创建或认领任务。A、B 都修改过 reader 和 report，全程累计进行了 13 次编辑、6 次测试。

之后也没有出现固定补丁或提交，最终原结果记为零分。未提交的工作区没有接受隐藏内容验收，因此这个结果不能解释为所有代码都已被判错。

这里体现的是编辑、测试与任务登记之间的具体关系：编辑和测试可以直接进行；发布固定补丁则要求关联至少一项自己负责的任务。记录显示成员确实开展了工作，但本次没有形成可验收的固定交付。

## 这些轨迹体现了怎样的机制

把这五个例子放回完整窗口，现象也一致。全部 16 个槽，A、B 都编辑过两个模块。15 个槽建立了任务，这 15 个槽全部先发生生产文件编辑，后创建第一项任务；另一个槽始终没有登记任务。

全窗口成功保存了 21 次任务创建、20 次任务认领和 2 次工作消息。转交、退回、任务修订和依赖调整的成功事件数都是 0。因此，这批运行中的正式职责主要通过创建和认领形成，其他调整工具虽可使用，但本窗口没有成功落库的使用记录。

最终有 14 个槽通过原完整验收，另 2 个槽没有提交。

这些轨迹具体展示了：机制允许自主组织，也允许重复工作、集中完成或先执行后登记。模型可以自己创建和认领任务，环境校验这些操作；成员同时保有私有副本中的编辑空间，职责记录不会替代实际工作和最终交付。

是否形成有效分工，还需要结合编辑、消息、补丁整合和最终产物继续审计；这些记录本身不足以证明分工高效、解释模型动机，或证明参数训练带来了收益。

## 备答

**为什么选这五个槽？** 它们分别展示先执行后登记与重复工作、后置登记验证职责、创建者与负责人不同、集中交付，以及空任务表下的编辑和测试。总体情况仍使用完整 16 槽统计。

**先做后登记，是不是只为满足发布条件？** 发布固定补丁确实要求关联自己负责的任务。记录能确认操作顺序，但不能仅凭顺序判断模型动机。

**通过验收，是否就说明协作有效？** 验收回答最终交付是否符合要求；协作效果还要看伙伴成果是否保留、重复实现和整合成本。
