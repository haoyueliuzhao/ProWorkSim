# v0.36 实验中的任务与职责如何形成 逐节汇报稿

日期：2026-10-09。对应材料：[v0.36 实验中的任务与职责如何形成](software-organization-v036-briefing.md)。

按材料第1—5节讲述，约5—7分钟；备答不计入时长。以下是讲述稿，不是模型原话。案例取自已结束的P2阶段历史记录，详细统计和原始事件定位见主稿附录。

## 1 实验开始时给定什么

先说这次汇报的核心：任务由模型成员在合同范围内自行拆分，职责通过认领、转交等工具操作形成。

这里的“合同”，就是预先规定的根目标、模块和API，以及验收要求。实验给出要完成什么，但不预先写好执行任务，也不指定谁是实现者、谁是测试者。

本次案例使用同一个SQL inventory任务，要求完成reader和report两个模块：reader解析SQL语句，report根据解析结果汇总记录和计数。后面说的一个“槽”，就是两个成员共同完成这个根目标的一次运行；槽从0开始编号，所以第13号槽对应slot-13。

A、B使用相同的模型参数和初始业务材料，各有独立会话和私有工作副本。初始任务板为空。A固定先行动，之后调度器轮流给可运行成员行动机会。

因此，起点只有共同目标和约束，具体任务与负责人要在行动中形成。

## 2 任务和负责人怎样形成

可以把正式分工理解为一张由成员自己填写的任务表。

成员调用create_task，填写任务描述、ID和父任务，系统便新增一条任务。这时还没有负责人。任一成员调用claim_task，认领成功后，系统才把owner，也就是正式负责人，设为这个成员。

所以，谁创建任务和谁负责任务是两件事。A创建的任务可以由B认领，后面的案例就发生了这种情况。

如果要转交职责，当前负责人可以调用delegate_task，把任务交给伙伴。当前负责人也可以通过return_task退回任务：这会清空owner，回到待认领状态，并不会自动退还原委派者。

任务还可以调整：当前负责人，或任务尚未认领时的创建者，可以修订任务；依赖的声明和移除由当前负责人操作。模型生成这些操作的参数，环境检查权限、版本和依赖环等约束，并保存合法操作的记录。

成员也可以发消息协商，但消息本身不会修改正式负责人。说一句“请你负责”，并不等于任务表里的owner已经改变。

还要说明一个流程要求：编辑和测试可以在没有任务时发生；发布固定补丁时，必须关联至少一项自己负责的任务。因此，机制允许先做事、后登记。任务归属也不会授予文件专属编辑权，双方仍能修改各自副本中的同一批文件。

## 3 第13号槽实际发生了什么

用第13号槽看这套机制，比只看工具名称更直观。

第一步，A先修改了reader.py和report.py。当时任务板还是空的。

第二步，A创建了一项实现任务，B随后认领。于是，创建者是A，正式负责人是B，但A在认领发生前就已经做了实现工作。

第三步，B也修改了这两个模块，并发布了自己的补丁。A尝试整合B的补丁，发生冲突。这时双方已经各自实现了重叠的内容。

第四步，A又创建并认领了一项新任务。新旧两项任务的描述相同，也就是说，同一个实现范围出现了两条任务和两个负责人。

第五步，A发布自己的版本并完成交付。

这条轨迹说明，实际过程未必是先分工、再执行。新增任务也未必意味着把工作拆得更细，它还可能记录已经发生的重叠工作。

这一槽最终通过验收，但原判定规则没有确认最终产物有效保留了伙伴的成果。因此，不能仅凭A尝试过整合，或者提交记录里出现了伙伴补丁ID，就认定合作整合成功。任务负责人、实际编辑和最终产物来源，需要结合起来看。

## 4 其他运行展示了哪些工作方式

其他几个槽补充了不同情况。

第00号槽中，A登记并负责实现任务，B后续登记验证任务，最后由B完成交付。第05号槽的方向相反：A创建的实现任务由B认领，A另建并认领验证任务，最后由A完成交付。两槽都通过验收，原判定规则也都确认了伙伴产物的保留。

但这不能理解成从一开始就分好了实现和验证岗位。两槽中，双方都在第一项任务创建之前编辑过两个模块。任务板上的实现、验证标签，是执行中形成的责任记录；这里说的交付者是最终交付者，两槽此前也有另一方提交的记录。

第14号槽展示了交付集中于一人的情况。A创建的任务只描述reader实现，由B认领；B实际发布的补丁却覆盖reader和report。A尝试整合并继续编辑，但本槽只有B形成提交，最终验收通过。这说明任务文字不会自动限定文件操作范围，也说明只有一个人交付，不等于另一个人没有工作。

第12号槽则从始至终没有登记任务。双方累计进行了13次编辑、6次测试，最后没有发布固定补丁，也没有提交。它说明没有任务登记仍可以编辑和测试，但持续行动不保证完成交付。这里的未成功来自没有形成提交，不能说隐藏验收已经判定所有代码都错误，也不能只凭这一例断言没有登记任务导致了失败。

## 5 这些记录能够说明什么

把案例放回完整的16个槽，结论会更清楚。

16个槽中，A和B都编辑过reader和report。15个槽创建了任务，而且这15个槽全部先编辑、后登记。这个窗口中，实际出现的普遍过程是双方先进行重叠实现，随后才登记职责。

工具提供了转交、退回、修订和依赖调整的能力，但这16个槽没有这些操作成功落库的事件。因此，我们可以介绍机制允许什么，不能据此声称这些复杂调整已经在本窗口得到验证。

另外，14个槽发生过补丁整合，这14次整合全部出现冲突。最终有9个槽只有一名成员交付，5个槽双方都交付，2个槽没有交付。这些结果显示交付路径存在差异，也保留了重叠工作与协调成本的证据；它们还不足以证明已经形成高效、稳定的专业分工。

所以，判断是否形成有效协作，要同时看任务登记、实际编辑、消息、补丁整合和最终交付。owner表示正式责任，不能直接当作文件作者或实际贡献。这里的案例说明组织过程，不构成参数训练收益或某种方法更优的证据。

## 备答

**为什么选择这些槽？**

先查看完整16槽，再选择能说明不同现象的案例：13展示先执行后登记和重复范围；00、05展示职责标签与最终交付方向的变化；14展示集中交付；12保留未交付的情况。总体发生率使用全窗口统计，不用精选案例代替。

**相同模型为什么会形成不同职责？**

A、B共享模型参数，但各有独立会话和私有副本，行动次序、可见事件和采样结果都会影响后续过程。记录证明轨迹确实不同，不能单独把差异归因于某一个因素。

**后置建任务是否只是为了满足发布条件？**

发布固定补丁确实要求关联自己负责的任务。记录能够确认先编辑、后登记的时序，但不能仅凭时序推断模型的动机；是否主要为了完成发布流程，应作为待审计的问题。

**通过验收是否等于合作成功？**

验收检查最终交付是否符合要求。合作是否有效，还要看伙伴成果是否被保留、重复实现和整合成本等。第13号槽通过了验收，但原规则未确认伙伴产物的有效保留，所以两者需要分别表述。
