# v074：等待原 model-5 的合格显卡

本次新增一个最多运行六小时的普通用户监控器。它只等待原未消费的 model-5，不重新加载已经启动的 model-4，也不停止、重启或发送信号给任何已有任务。

监控器每 60 秒读取 v068 主协调器的状态。只有主队列仍处于正常阶段、没有共享故障、心跳不超过 180 秒，并且还有 Qwen 生成库存或在途任务时，才调用已封存的 `v073.launch([5])`。显卡选择、UUID 排他、剩余显存、共享资源和原模型设置全部由 v073 与原驻留实现复查。没有合格卡则保留未消费身份等待下一次；一旦身份消费，监控器退出，不把启动失败的身份当作可重试身份。主队列结束、共享故障或六小时到期也会退出；心跳暂不可确认时只等待，不启动模型。非容量类启动错误单列并结束监控，不盲目重试。

监控器使用唯一用户服务 `proworksim-v074-model5-watcher.service`，限定一个 CPU（原 CPU 池的 `[172:173]`）、4 GiB 内存、无 swap、64 个任务、`Restart=no`，并由 `RuntimeMaxSec=21600` 限制服务运行时长。其 1 CPU／4 GiB 在原共享 `allocation.lock` 下显式预约，计入原 152 CPU／832 GiB 总上限，不额外扩张资源池。正常退出与收到终止请求时，`finally` 只释放经过精确字节核对的自身预约；不删除其他租约。若服务启动结果不明确，保留预约和原回执，须先核实实际退出后才能回收，不能凭超时推定没有服务。

`--prepare` 只封存新源码、原 v073 源码和授权、用户单元规格，不查询 GPU、不接触用户服务管理器、不预约资源。`--launch` 先确认原 model-5 未消费、主队列正常、目标用户服务不活动，再预约自身资源并请求启动。实际模型就绪仍由原驻留的完整上下文缓存和中性准入判定，启动请求成功不等于已开始处理正式任务。

实现：[watch_additional_qwen_v074.py](../../tools/watch_additional_qwen_v074.py)。五项必要 CPU 控制通过：每分钟只尝试 model-5 并在消费后退出；主队列健康和六小时截止；非容量错误不重试；共享账本准确预约并只释放自身租约；用户服务的固定 CPU、内存、swap、任务数、时长和禁止重启约束。Ruff、差异检查通过。测试均为注入夹具，无真实 GPU、模型、API、容器或用户服务调用；实际准备、启动与运行结果由主流程另记。
