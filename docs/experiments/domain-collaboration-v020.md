# v0.20 本轮实验：同领域来源准入与单卡初始化确认

日期：2026-09-27。依据[审计后的新方案](../domain-collaboration-v020-plan.md)，本轮完成研究目标与预算结构修订、真实来源CPU准入，以及用户单独恢复的有界单卡P1。原H1、v0.19失败及暂停记录保留；没有恢复原27B双副本或118例后继。

**结论：新来源的有限可执行路径与用途隔离检查得到支持；两种9B单卡低存储配置都能完成实际生成，但均在首条自身概率重算门失败。因此本轮未形成可进入训练的初始化，业务确认、反向与参数更新均未执行，基础学习和ID-VTDO增量仍未检验。**

[机器报告](domain-collaboration-v020.json)保留计划、原调用、实际dtype、源、成本及SHA；它不是训练准入证书。

## 1. 研究方案如何改变

研究中心改为同领域协作：结构化数据分析与数据工程中的信息获取、交接后实际使用、独立复核、针对性修复及维护。一个共享actor/LoRA和actor优化器顺序服务具有不同权限与局部历史的角色；critic仍为独立辅助组件。没有新增岗位专属权重或采样副本。

后继设计改为四窗×24训练：联合情境A重复8、联合情境B重复8、单岗位实现4、单岗位复核4，共96训练；初始/最终各24评价，共144。M=8、每类最少2条只是允许多类支持出现，不能保证实际支持；本轮实测支持仍为空缺，不跨θ/Γ/精确ξ拼池。P3有限共同起点分支、P4三方法及同总资源比较分别登记，不自动启动。

该144例方案的具体新来源、复核反馈修复合同、项目维护评价适配和资源预算尚未完成，JSON明确`launchable=false`、`resource_approved=false`。它是替换旧恢复计划的实验设计，不是已批准或已执行episode。V1理论未改，旧H1的27B＋SDK仍是旧排序结果，新P1的9B＋native只是独立资源配置确认。[结构化设计](../../examples/id-vtdo-v20/study-proposal.json)

## 2. P0：真实数据库来源与谱系

固定官方Six-Gym-SQLite 5000条/13库与BIRD-Critic-SQLite 500条/15库的公开元数据。数据库ID及发布SQLite SHA没有交集，但实际出现22个规范化题面指纹、10个错误SQL指纹、3个题面＋错误SQL联合指纹重合；3个联合指纹对应5个跨源任务配对。不同DB ID不足以保证独立。

`TRAIN_86/210/303`作为预定接口开发案例，在同一`book_publishing_company`原SQLite及WorldCore受管DuckDB路径上实际执行，3例共33项控制通过，CPU实验4.46秒。原问题、合法错解与host修复见证能够区分；真实构建与复制结果JSON也能区分。原数据不变，参考SQL、上游Python测试和独立期望值留在host，测试代码未exec。SQLite宽松聚合与DuckDB的实际差异分别保存，未宣称全数据方言等价。

静态审查发现的`TRAIN_100`日期方向矛盾、`TRAIN_120`零书目出版商覆盖歧义均保留为未准入，没有悄悄修正参考后按它评分。这些选择是合同/接口准入判断，不基于目标模型成功率。

三例都只是同一数据库的程序见证：0模型调用、0训练示范、0协作成绩；Six其余数据库尚未分配正式研究用途，Critic缺完整官方评分资产。详见[来源实验](sql-source-v020-p0.md)与[原始归档引用](sql-source-v020-p0.json)。

用途检查另将实际精确重复故意声明成训练/锁定两用途，传递闭包正确拒绝；三个联合指纹因共同`six:hockey`数据库联结成两个冲突组件，而不是三个独立来源。UCI与TeamBench Online Retail派生候选也被明确标为已知同源冲突。上述是负控，不是把这些材料实际投入训练或锁定测试；未知谱系仍为未解决。[用途与密度控制](study-v020-p0-controls.json)

## 4. P1授权、配方与停止规则

用户明确恢复小型P1：最多一张A100，物理GPU2–5优先、6备用；累计最多1 GPU小时，每任务最多15分钟，主机RSS最多64GiB，两次运行新增产物累计最多5GiB，模型API调用/费用为0。P2没有自动恢复授权。

首配置为9B、native、单常驻、无prefix和只读副本；真实BF16冻结基座，FP32 LoRA、critic与概率归约，FP32 matmul为highest，full attention采用声明的BF16 QKV/efficient-only后端。单卡启动free至少40GiB，自身GPU离散采样超过40GiB即停止。以上资源门不构成容量通过保证。

P1先安排三条固定开发prompt的新采样、完整原token复算和过门后的诊断反向；仅全部通过后才做四个真实UCI开发世界（实现、复核、pair、chain）。原2048输出上限、16384上下文、温度0.7及max0.02/mean0.002概率门保持。旧H1输出不作训练示范，也不回填奖励。

原配置在首条失败后，只读核查发现LM head产出BF16 logits后才转FP32。作为单个候选机制，只额外预声明一次v0.20.1：BF16主干＋真实冻结FP32 LM head，输入在head乘法前升FP32、输出保持FP32，其余不变。这不是输出后float，也不是容差校准。后继绑定原launch SHA，扣除原46.314569秒，剩余3553.685431秒；旧源/旧目录不修改，新源/新目录分别冻结。不再展开第三种配置。[首配置CPU准备](runtime-v020-storage-preparation.md)、[唯一补修配置](runtime-v0201-fp32-head.md)
