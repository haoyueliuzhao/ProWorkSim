# v202 实验报告：语法事实提取与项目图动态维护

日期：2026-11-12。规范结果：`offline-results-r2`。设计、实现边界和文献核对见[设计说明](software-benchmark-v202-project-graph-design.md)。

## 1. 本轮结论

本轮按 v201 审计完成了工程修订和离线实验，没有启动新模型任务。

1. **修复了多行表达式在提取阶段被截断的问题。** A2 的 24 个完整源码控制目标全部提取；Pylint-4604 原遗漏的赋值右侧和两个分支都已进入事实候选。原读取属于部分文件，仍保留 Partial 标识。这里只证明提取修复，不能改写 v201 的留出成绩。
2. **项目图可以随已观察的工程事件更新，并保留版本和测试边界。** PG2、PG3 在 456 个历史事件及 24 个合成事件检查点均与逐事件全量重建一致；故障回滚、旧验证不继承、补丁采用不等于测试通过等控制通过。
3. **增量维护降低了当前实现的 CPU 成本，但双图协同收益尚未验证。** 历史回放中 PG2 比 PG1 少用约 71.46% 图更新 CPU 时间。组织侧仅完成候选与同步接口的 CPU 控制，没有真实调岗、消息发送或团队实验。

当前主要缺口已从“表达式漏提取”转为“足够完整的项目材料与语义依赖”。77 份不同历史源码材料只有 5 份完整；其余均为局部片段。当前跨文件影响分析基于静态 import 候选，没有实现完整调用图或 def-use 分析。因此不能将图一致性解释为程序依赖完整性，更不能据此宣布协同进化有效。

## 3. 实验 A：表达式是否完整进入候选池

### 3.1 条件与结果

A0 是 v200 沿用的旧源码片段提取组件；不重新执行完整 F1。A1 提取 LibCST 完整语句／定义，A2 再拆出表达式结构，A3 使用 Tree-sitter 节点。

24 个完整源码控制的目标包括语句、NamedExpr 和 Decorator，不全是赋值语句。为了避免因空白边界不同不公平地低估旧方法，同时报告“精确节点范围”和“一个事实包含完整目标”。

| 条件 | 完整目标被单一事实包含 | 精确目标范围 | 部分／异常控制没有完整性误报 | 本批输出事实次数 | CPU 秒 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A0：旧片段提取 | 10/24 | 0/24 | 6/6 | 1,954 | 0.064 |
| A1：LibCST 完整节点 | 22/24 | 22/24 | 6/6 | 1,336 | 3.361 |
| A2：LibCST＋结构化子项 | 24/24 | 24/24 | 6/6 | 5,010 | 3.252 |
| A3：Tree-sitter 节点 | 24/24 | 24/24 | 6/6 | 3,438 | 0.137 |

“事实次数”累计了 108 份输入 × 对应条件，不能当作不同语义事实数。A0 的精确范围为 0 不表示它完全没有提取有用代码；包含口径保留了它实际覆盖的 10 个目标。A1 的两个缺项是预定的 NamedExpr 和 Decorator 子节点，其选取类型不覆盖这两类。

四条件合计 **11,738 次事实输出的源码字节、范围、哈希、成员和版本核对均无不一致**。这证明输出能定位到来源，不证明事实在 Issue 中必要或语义正确。

CPU 数据是本轮固定顺序、单次运行的进程时间，未做独立性能基准或显著性检验。工作进程累计峰值 RSS 为 48.19 MiB；各条件共用进程，不能把该数字视为各方法独立内存用量。A3 本次明显更快，但只测 Python，不能据此外推多语言能力。

数据：[逐次提取结果](../../artifacts/software-benchmark-v202/offline-results-r2/syntax-trials.json)、[提取汇总](../../artifacts/software-benchmark-v202/offline-results-r2/syntax-summary.json)。

### 3.2 Pylint 已知回归

旧提取没有生成完整的局部赋值：

```python
is_type_annotation_import = (
    imported_name in self._type_annotation_names
    or as_name in self._type_annotation_names
)
```

A1、A2、A3 均保留了完整目标；A2 另有赋值目标、Boolean 表达式和两个 Comparison 分支，父子结构与来源范围可核查。上面的代码仅为便于阅读的排版，逐字原文及实际缩进保存在[回归证据](../../artifacts/software-benchmark-v202/offline-results-r2/known-regression.json)。

重要边界：该输入只是一段文件读取，所有事实完整性仍为 Partial，限定作用域未知。没有把局部闭合语句变成完整文件声明；也没有重新渲染 F1 卡片或运行模型，因此不能报告“v201 已从 33/34 提升至 34/34”。

## 4. 实验 B：项目图能否正确更新

### 4.1 历史事件回放

PG0 在首次换版后冻结；PG1 每个事件重分析全部当前可见材料；PG2 缓存文件子图；PG3 在 PG2 上计算保守的潜在影响范围。

| 条件 | 与 PG1 完全一致的检查点 | 图更新 CPU 秒 | 图更新墙钟秒之和 | 文件重分析次数 | 完整文件树解析次数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| PG0：初始静态图 | 166/456 | 10.674 | 11.716 | 159 | 19 |
| PG1：逐事件全量重建 | 456/456 | 13.524 | 14.037 | 689 | 58 |
| PG2：文件增量维护 | 456/456 | 3.860 | 4.361 | 125 | 5 |
| PG3：增量＋潜在影响 | 456/456 | 3.826 | 4.324 | 125 | 5 |

PG2 CPU 降低 **71.46%**，PG3 降低 **71.71%**。两者之间的小差异不足以判断谁更快；PG3 多做影响计算，本次微小反向差异可能来自缓存与测量波动，没有重复性能测量支持。

历史事件更新墙钟中位数／P95：PG1 为 2.28／152.48 ms，PG2 为 0.95／56.86 ms，PG3 为 0.99／56.42 ms。这里的墙钟之和是逐调用相加，不是并行批次结束时间，更不是模型完成任务的时长。

**实际提速主要来自避免重复分析文件。** 历史材料没有同一完整文件的可验证连续编辑序列，所以 PG2/PG3 的 5 次完整树解析中，真正使用旧树编辑的次数为 0。不能把这批历史提速全部归因于 Tree-sitter 增量算法。旧树编辑机制由下面的受控连续修改验证。

### 4.2 合成事件与更新故障

合成事件流包含接口修改、调用文件调整、测试失败／通过、固定产物、定向发布、接收者采用、提交、重命名、删除、错误语法和修复。

| 条件 | 与全量参考一致 | CPU 秒 | 文件重分析 | 完整树解析 | 使用旧树编辑 |
| --- | ---: | ---: | ---: | ---: | ---: |
| PG0 | 11/24 | 0.275 | 24 | 24 | 0 |
| PG1 | 24/24 | 0.283 | 69 | 66 | 0 |
| PG2 | 24/24 | 0.051 | 12 | 9 | 4 |
| PG3 | 24/24 | 0.050 | 12 | 9 | 4 |

另外的 CPU 语义控制确认：

- 同一测试报告分页回读不增加 TestRun；不允许同一报告被改成另一个版本或相反结果。
- 新工作区版本不能继承旧版本有效测试状态；公开测试只验证实际 selector。
- 补丁采用保留作者，接收者形成自己的版本，不继承作者测试通过状态。
- 只拥有部分文件时保留局部事实，但不创建完整限定符号；未知修改不能沿用旧代码事实。
- 重命名、删除和语法错误使对应旧图结构失效；恢复合法语法后能重新构建。
- 在状态归约后、图计算后分别注入失败，旧状态、旧树、事件日志和快照均保持不变；随后可正常提交该事件。
- 相同事件内容重复提交幂等，事件 ID 被不同内容复用会拒绝。

### 4.3 边分类与陈旧状态

下表统计历史 456 个检查点中边的累计出现次数，同一边跨快照会重复计数，不能当作不同依赖数量。

| 边类别 | PG1 参考出现次数 | PG2／PG3 匹配 | 解释 |
| --- | ---: | ---: | --- |
| 代码结构及来源 | 45,201 | 45,201 | 含语法事实、来源、文件与版本；不全是跨文件依赖 |
| 测试验证 | 657 | 657 | 测试定义、执行版本和失败证据 |
| 任务关系 | 456 | 456 | 历史 S1 只有 root Task→Issue，没有真实跨成员任务依赖 |
| 成果来源及交付 | 72 | 72 | 固定产物和提交记录 |
| 组织责任 | 不混入上述 PG 分母 | 单独 8 项 CPU 控制 | 原历史材料没有真实两人协作 |

PG2/PG3 的节点和边对参考均无多余、缺失或属性不一致。PG0 的历史边中，67.33% 为相对当前参考的陈旧／额外边；参考边中 25.70% 未被 PG0 正确表示。这是“首次换版后冻结”的预期后果，不是 PG0 运行报错，也不能当作真实软件依赖识别错误率。

陈旧／额外率 = `(实际边数－完全匹配边数)/实际边数`；缺失／变化率 = `(参考边数－完全匹配边数)/参考边数`。同 ID 属性改变也按不匹配处理。参考本身只覆盖已观察材料，未观察到的程序依赖不在分母中。

最终快照审计检查了 PG1–PG3 共 **1,440 个快照、64,320 次事实出现**，源码和权限范围无异常；393 次有效测试边和477 次旧版失效边的版本判定一致。这些是跨方法、跨快照的检查次数，不是新测试执行次数。来源中实际有 19 个历史 TestRun；另有合成 TestRun 3 个。

数据：[图维护汇总](../../artifacts/software-benchmark-v202/offline-results-r2/graph-summary.json)、[快照审计](../../artifacts/software-benchmark-v202/final-audit-r1/summary.json)。

### 4.4 影响范围能说明什么

PG3 仅在已观察文件之间，沿变化前后静态 `may_import` 候选边反向传播。预定合成控制的接口变化应影响 core、client、test_client 三个文件，实际 3/3，Precision／Recall 均为 1。

**只有这一项明确预期的影响集合；不是现实项目影响范围准确率。** 静态 import 存在并不说明某次执行一定经过该路径。当前没有函数调用别名解析、完整数据流、动态导入或真实根因链。历史回放也没有独立影响集合金标准，因此不报告其 Precision／Recall。

## 5. 最小双图桥接：完成了什么

8 项控制均通过：跨 owner 显式依赖生成 AddHandoff；已有交接不重复生成；普通修改不自动改派；持续阻塞及多个下游形成 Reassign 候选；无所需工具的接任者被拒绝；Merge 缺少完整责任计划被拒绝；私有事实不向伙伴路由；具有定向发布证据的事实才出现在伙伴同步计划中。

所有结果都保持 `proposal_only`；没有执行责任迁移。同步的 `sent/presented/read/used` 全为 false，没有调用发送或上下文更新工具。这个原型能说明约束接口可运行，不能说明模型理解了同步信息，也不能给出实际交接率、组织调整收益、协调成本或任务正确率。

各触发阈值是预先编写的工程启发式，没有基于本轮任务成绩搜索。“三条 blocked 记录”不等于统计上证明该任务长期阻塞；“反复同路径修改”也可能是合理合作，后续需要用真实任务反馈判断候选是否值得执行。

数据：[组织与同步控制](../../artifacts/software-benchmark-v202/offline-results-r2/organization-controls.json)。

## 6. 资源、异常与可复现性

本轮规范离线测量墙钟 **31.26 秒**，最多两个 CPU 工作进程；这是已完成开发、依赖准备和测试后的测量时间，不是本次全部工程用时。图回放工作进程峰值 RSS 为 **283.50 MiB**，为进程累计峰值，不是共享服务器总内存或并发进程内存之和。

新增被测模型 API 请求、输入／输出 token 和 API 支出均为 **0**；未使用旧实验现金余额。Codex 开发／审阅的 token 与费用无法独立取得，不声明为零。没有新容器、GPU、训练、系统资源组或共享主机配置修改。

r1 在测量前被 Python 3.14 forkserver 的监听端点权限阻止。保留[原异常](../../artifacts/software-benchmark-v202/offline-results-r1/execution-error.json)，r2 仅把子进程启动改为不监听端口的 fork；实验材料、算法和阈值未变。r2 的 432 次提取及 1,920 次图事件更新全部完成，执行异常 0。6 条历史不完整 JSON 与本次执行异常分开计数。

封存后的实验源码哈希均未变化；v200 F1 与旧实验原件保持不变。46 项 CPU 控制日志见[测试记录](../../artifacts/software-benchmark-v202/cpu-controls-r2/pytest.log)。每个快照保存在本地 `runs/software-benchmark-v202/offline-results-r2/`，逐事件指标及来源清单在版本化 artifacts 中。

## 7. 准入判断与下一步

| 审计要求 | 本轮状态 | 适用边界 |
| --- | --- | --- |
| 多行表达式及来源范围 | 通过本批控制 | 不是所有 Python 语法或 Issue 语义的完备证明 |
| 版本、TestRun、Artifact 身份分离 | 通过 | 不宣称公开测试等于官方验收 |
| 增量与全量一致、失败可回滚 | 通过 | 针对已观察材料；共同解析缺陷仍可能一致存在 |
| 图维护成本可记录 | 已完成 | 单次工程测量，不是服务器吞吐基准 |
| PG→组织候选及同步约束 | 原型控制通过 | 没有真实组织重构或通信 |
| 完整调用／数据流依赖 | 未完成 | 当前只有语法结构与静态 import 候选 |
| 团队正确率、交付率、token 净收益 | 未测量 | 不作能力增益或非劣效结论 |

**v202 的限定工程门通过，可以进入 v203 的离线责任映射验证；还不能启动或宣称完整双图自进化评测。** 下一步应优先补齐真实修改后完整源码的受管捕获、可核验的调用／数据依赖和实际责任交接，然后再比较组织方案。继续增加事实卡或扩散更多未经验证的图边，不会弥补这些缺口。

真实模型阶段需要另行冻结任务、运行条件和预算，并将正确率、合法交付、团队实际 token、通信回读及图维护成本一起评价。本轮没有产生可替代这些指标的新分数。
