# v203.1 实验报告：依赖可观测性与真实组织失配参考

日期：2026-11-12。依据用户提供的 v203 审计开展；本轮不启动被测模型、真实 SWE 任务、训练或通信压缩。

## 1. 结论

**本轮改善了选材、证据分类和迁移执行基础，但仍未建立足以证明动态组织有效的阳性参考。**

1. 建立不以成功交接、认领或测试为条件的 **36个不同任务**材料池：开发24题、任务级留出12题，覆盖五种组织模式和12个仓库。25题没有显式成功交接，31题不满足v203旧筛选规则，补入了此前排除的材料。
2. 区分了“没有显式记录”“没有实际行为”和“执行中断”。134个无显式交接的旧回合中，**至少11个实际采用了伙伴固定补丁**；不能据此判断未合作。56个无控制器汇总的身份中，49个无API记录，7个确实调用过模型且留下中断记录。
3. 两路独立AI审阅、第三路仲裁及共同定义补核后，当前前缀得到 **23例No-Change、13例证据不足，0例足以支持结构性组织调整**。这是有限前缀的AI参考，不是人工金标准，也不是“整个任务不需要组织调整”的证明。
4. 新依赖观测契约禁止模型自我确认、禁止把采用或策略反馈升级为依赖证明。实际Harness控制中，依赖声明被记录为候选；即使声明产生的协议门槛随后得到满足，候选仍未自动升级为真实任务必要依赖。
5. **20个多文件迁移场景、1项相同请求幂等控制及17项证据／拓扑控制通过。** 完整包回读、不同文件和版本、多个产物、旧测试失效、拒绝与恢复得到限定工程验证；完整动态组织下的最终交付仍未验证。

因此，v203.1的材料和工程工作完成；**G2独立失配识别、G5组织增量仍未通过**。本轮没有把无阳性的数据用来计算一个虚假的高准确率，也没有启动真实模型对照。

## 2. 新材料如何解决旧选材偏差

### 2.1 选择规则

来源仍为v131原50题、250个组织身份。46个不同任务至少有一份控制器记录。新规则只要求控制器文件存在，不要求成功修改、显式任务板、认领、handoff、采用、测试、现金闭合或官方成绩。

先按固定种子、仓库轮转选定12个验证任务，排除v203已审阅的12题；再从剩余身份选24个开发任务。每题只取一个历史回合，按组织模式已有数量和固定哈希平衡，不以表现选回合。开发和验证任务互不重复。

| 项目 | 实际值 |
| --- | ---: |
| 不同任务 | 36 |
| 开发／任务级留出 | 24／12 |
| CHIEF／PIPELINE／REVIEW／SPRINT／MATRIX | 7／7／7／8／7 |
| 仓库 | 12 |
| 整个所选回合没有成功显式handoff | 25 |
| 所选回合不满足旧v203主样本规则 | 31 |

这修正了成功交接筛选，但仍存在**文件可用性、原50题面板及历史策略**的限制。缺失控制器的任务没有被伪造为完整样本；本批也不是组织模式随机分配实验，不能据它估计各模式完成率。

### 2.2 信息边界与独立性

审阅对象统一为**前40次实际派发工具动作**，不足40次则取现存全部前缀。审阅包含任务、冻结组织约束、实际成功／拒绝回执和来源，不包含之后的动作、官方终局评分或O4输出。

这个固定早期窗口可能遗漏后期交接、集成和验证瓶颈。因此，本轮“未找到充分阳性”只适用于这些前缀，不能外推整段任务。后续应在看标签前固定更多工作阶段锚点，并按任务保留层级，不能把同一任务的多个窗口当成独立新任务。

验证集覆盖11个仓库；这些仓库也都出现在当前开发集。相对v203主样本新增Django、Matplotlib、Seaborn、Scikit-learn四个仓库，但它们更早均有研究曝光。**本轮只有任务级分离，没有仓库级隔离，也不是整个研究历史的新任务确认集。** 本批材料已打开，后续不能重新包装成未见确认集。

准备时，r1仓库重叠汇总的集合运算误用了空集合；在审阅前修为[summary-r2](../../artifacts/software-benchmark-v203-1/panel-r1/summary-r2.json)。题目身份、分组和前缀没有变化，原汇总保留。规范选择规则见[plan.json](../../artifacts/software-benchmark-v203-1/panel-r1/plan.json)。

## 3. “没有合作”还是“没有记录”：来源核对

### 3.1 原194份控制器记录

| 观察 | 数量 | 正确解释 |
| --- | ---: | --- |
| 无来源绑定的显式handoff | 134 | 不等于没有合作 |
| 上述回合中存在实际伙伴补丁采用 | 11 | 固定产物可以直接采用，无需先发handoff |
| 无终态明确负责人的任务 | 100 | 不能直接判为责任缺口 |
| 完全没有任务板条目 | 57 | 项目允许直接修复，不能把可选任务板变成强制条件 |

11个直接采用案例是明确反例；其余没有采用记录的回合仍可能有消息、读取或其他协作，不能自动填“无合作”。这里是共享已发布的固定产物，不是多人自动写同一私有工作树。

### 3.2 原56个无控制器汇总身份

通过五个旧API账本的只读查询区分：

- **49个**没有API调用记录，也没有控制器汇总。
- **7个**有调用记录，合计295条请求；原结果分别记录6个`Native/model transport failed`和1个协调器取消。七个失败归档仍在，本轮只核对小型结果元数据，没有解压大归档或重采。

这7项不能当作正常组织失败，也不能说全部原始历史丢失。原错误概括不足以继续断言都是网络、内存或观察器本身的问题，本轮没有猜测更深层根因。

### 3.3 36题原始模型响应交叉核对

核验2386份原始供应商响应文件的哈希及大小，没有缺失引用或哈希错误。在这些响应的实际函数调用中：

| 工具 | 模型请求 | 实际派发 | 成功 |
| --- | ---: | ---: | ---: |
| declare_dependency | 0 | 0 | 0 |
| offer_transfer | 0 | 0 | 0 |
| accept_transfer | 0 | 0 | 0 |
| return_task | 1 | 1 | 1 |

因此，对这36个原回合，显式依赖声明和责任转交缺失**不是仅仅被聚合观察器漏数**：现存原始模型响应里就没有请求这些工具。但这仍不代表不存在隐式工程依赖；自然语言中的提议也不能冒称执行成功。

该核对使用完整旧回合，仅用于记录完整性诊断；其结果没有提供给审阅者，也没有倒灌为前缀预测特征。

证据：[可观测性审计](../../artifacts/software-benchmark-v203-1/observability-r1/summary.json)、[缺失汇总与只读查询](../../artifacts/software-benchmark-v203-1/source-gaps-r1/summary.json)、[7项中断来源](../../artifacts/software-benchmark-v203-1/source-gaps-r1/interruption-causes.json)。

## 4. 独立AI审阅与共同定义核查

两名独立AI审阅者分别检查36个前缀，不读取彼此标签、分组身份、组织策略实现／输出或未来结果。第三名AI处理22例注册字段分歧。没有专业人工审阅，全部记录均标记`human_gold=false`。

| 初始判断 | 一致率 | κ，Unknown单列 |
| --- | ---: | ---: |
| 是否存在真实组织失配 | 75.0% | 0.518 |
| 是否需要改变组织 | 66.7% | 0.349 |

这些一致性结果说明问题仍有相当解释空间，不能隐藏分歧只报告最终标签。第一名审阅者曾将2例标为失配；第二名没有确认阳性。仲裁保留了材料的未知，而非用多数投票制造确定性。

另外，A/B共同给出Confirmed的4例也经过定义补核。OBS012、OBS014、OBS024只证明产物消费或阶段推进，被修为Inferred；OBS030的真实`review_required`拒绝能确认一个限定的提交前置条件，保留相应参考。原始意见和第一次汇总均未覆盖。

最终有4个“Confirmed”参考，范围均为**原协议准入条件**：

- OBS008：任务认领先需要当前revision的组织授权；拒绝、授权补齐和成功认领形成对应链。
- OBS011、OBS021：认领需关联有效目标／提案；既有协议补齐后操作恢复。
- OBS030：当前候选提交需要同版本独立接受；拒绝证明门槛存在，但不证明它后来已满足。

这些是AI基于实际回执形成的限定参考，**没有自动写成运行时Confirmed任务依赖**；也不证明代码任务必须跨成员分工，更不证明应该调岗。

### 4.1 规范参考结果

| 分组 | 任务数 | 支持No-Change | 干预判断证据不足 | 足以支持结构性组织调整 |
| --- | ---: | ---: | ---: | ---: |
| 开发 | 24 | 15 | 9 | 0 |
| 任务级留出 | 12 | 8 | 4 | 0 |
| 合计 | 36 | 23 | 13 | 0 |

No-Change表示当前前缀支持保持原组织、继续工作或恢复现有协议，不等于代码已修好、组织完全无问题。InsufficientEvidence保留未定，不能当成正确负例。

单独看“是否已经证明存在真实失配”，17例否定、19例未知、0例确认。它与“是否应立即改变组织”不是同一问题，因此分母和标签不能混用。

证据：[最终逐题参考r2](../../artifacts/software-benchmark-v203-1/reference-r2/per-task.json)、[一致性与分组汇总](../../artifacts/software-benchmark-v203-1/reference-r2/summary.json)。

### 4.2 为什么没有计算O4准确率

本轮没有足够的正向干预参考，不能计算可靠的干预召回或比较O4与O3的收益。23个No-Change也不满足建议的30个负向独立场景；同仓库相关性和未知仍需处理。

作为样本量说明，若把场景暂按独立二项试验处理，全对时双侧95%精确区间下界分别为：7/7约0.590、30/30约0.884、36/36约0.903。这里没有计算模型成绩；这些数字仅解释为何旧7/7不足以支持“真实准确率达到90%”。实际任务／仓库聚类会使独立假设更弱。

本轮没有用这36题调O4，也没有把原32个合成控制重新当确认集。**G2、G5继续未通过。**

## 5. 依赖观测契约与防循环证据

新增[依赖证据模块](../../src/proworksim/software_dependency_evidence_v203_1.py)，区分软件、任务和组织关系，保存实体、来源指针、版本、有效时间、提出者、核验者与候选／确认／失效状态。

关键约束如下：

- 代码实体关系不能直接填成任务实体依赖。
- Agent声明、Harness记录、独立核验分开；模型自我确认、成果采用或组织策略反馈不能完成确认。
- 确认必须来自独立检查入口，引用已注册的原始见证、适用版本和明确核验范围；缺字段、错版本、无见证拒绝。
- 阻塞原因分开保存；环境故障、预算、正常等待不自动成为组织失配证据。
- 版本变化使旧关系失效，保留旧状态和原证据，不用新状态改写过去。
- Presented、Read、Adopted、Rejected需要各自的来源和接收者／版本绑定；发送成功不能替代实际请求输入证据。

独立检查器是一个明确的受信任实现边界，不是任意Actor可调用的“确认”工具。字段验证本身也不能证明检查器已经解决所有软件语义；本轮没有给真实依赖发现算法盖章。

本轮确认门的单元控制使用CPU构造的检查见证，尚未部署能够自动核验真实SWE任务必要依赖的语义核验器。新模块是证据准入协议，不能称为已经完成的真实依赖发现算法。

### 5.1 原Harness中的实际声明控制

补充控制实际执行了任务转交、`declare_dependency`、因声明前置条件未满足而拒绝固定补丁，以及采用上游产物后恢复固定操作。

这个例子刻意防止循环论证：**协议能够执行Agent声明的条件，并不独立证明这个条件对解决软件任务必不可少。** 因此最终依赖仍为candidate、verifier为空，没有因操作成功自动升级。

控制没有启动模型或SWE任务。原始回执及事件见[观测器控制](../../artifacts/software-benchmark-v203-1/live-observer-control-r1/summary.json)。

## 6. No-Change及更完整的静态拓扑基线准备

No-Change成为显式结果，并另设`abstained_for_insufficient_evidence`，使“有证据保持原组织”和“证据不足，暂不干预”可以分别统计。不会把未调岗自动计为失败。

新增[静态拓扑基线](../../src/proworksim/software_static_topology_v203_1.py)原型，包含任务依赖映射、区域划分、工具／固定所有权约束、独立复核、跨区域交接和记忆可见性。它只使用已确认的任务依赖；代码依赖或推断边不直接参与任务分区。

该原型先约束负载再减少跨区域边，避免把所有任务交给一个成员以获得最低通信边数。未发布私有事实不会因责任分区免费迁移。搜索仅适用于固定两人、最多256种分配，即最多8个任务；超过上限明确退出，不冒称通用生产调度器。

这是ToCoMAS思想的有限适配，不是原论文完整复现。本轮仅做结构、权限与可行性控制，没有运行新的O0–O4能力比较；O4的模块消融和正式强基线比较保留到正负参考充分之后。

证据与拓扑部分17项CPU控制通过，见[日志](../../artifacts/software-benchmark-v203-1/cpu-contract-r1/pytest.log)。

## 7. 多文件责任迁移补充验证

新增[多文件迁移观察器](../../src/proworksim/software_multifile_transfer_v203_3.py)，继续调用原REVIEW2 Harness，不改变成员数、工具权限或固定交付人。

迁移包中的每个必需事实绑定文件、精确源版本、字符区间和UTF-8内容哈希；接收者必须实际恢复完整包，再逐项读取原文。分页可累积，但不同版本不能拼接。所有必需产物均显式采用后才能RESUMED。后续编辑使旧验证失效；任务revision变化使旧迁移包过期。

| 控制范围 | 覆盖情况 |
| --- | --- |
| 多文件／跨模块 | sample与helper实际相互引用，接任者独立测试 |
| 多任务 | 只转移指定任务，另一任务仍归原负责人 |
| 多产物 | 两个固定产物必须全部采用 |
| 信息完整性 | 预览不足、漏文件、分页读取、不同版本、篡改回执 |
| 权限与责任 | 未发布拒绝、已发布允许读取、私有事件隔离、错误接收者 |
| 生命周期 | 拒绝、过期offer、竞争offer、接受后revision变化 |
| 验证与恢复 | 旧测试不能验证新版本、失败后修复重测、读取失败后恢复 |
| 幂等性 | 新请求重复接受被拒；同一请求ID重放不重复生成世界事件 |

20场景矩阵全部通过，记录277条调用回执，执行7次微型本地pytest，含预定失败及恢复测试。另加1项相同请求ID幂等控制通过。它们是工程控制，不是21道新的模型能力任务。

竞争与版本变化采用确定性的操作交错，没有宣称真实多线程竞态测试。没有测试无限大小迁移包、所有语言或任意复杂三方冲突。当前仍未验证迁移后整个REVIEW2组织总能闭合法定最终交付，固定交付人和独立复核职责的连续性需要单独检查。

证据：[20场景日志](../../artifacts/software-benchmark-v203-1/migration-matrix-r1/pytest.log)、[相同请求幂等日志](../../artifacts/software-benchmark-v203-1/migration-idempotence-r1/pytest.log)。完整受管回执保存在本地`runs/software-benchmark-v203-1/migration-matrix-r1/`。
