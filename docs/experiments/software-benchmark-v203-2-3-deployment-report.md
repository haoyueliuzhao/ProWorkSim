## 已完成的实现与准入

K1/K2已经从历史PROJECT观察中真正删除可选字段的默认呈现，再集中呈现选中的完整字段卡；K0保持原输入。原先只追加卡片的准备版本保留为失败设计，不用于正式模型比较。真实SDK三组各25次脚本dispatch验证了请求与计量一致、K2角色排序生效、交付仍属REVIEW2且组别分别为K0/K1/K2。该验证不调用真实模型；本地Token计数不当作供应商账单。

三组共享修复后的公开测试取证接线，框架原始journal与stdout在actor退出清理前导出。Astropy、Requests、Flask在各自任务解释器中通过严格警告、嵌套会话与缺失finish控制。SymPy首次pytest诊断因环境无pytest失败，该失败保留；另用原生`bin/test`完成独立准入，没有向任务环境安装pytest。

Requests的原固定IP不可达，新gold控制45次连接超时且无应用载荷，empty受控取消，两者均清理并保留技术未知。有限新DNS／HTTP／严格TLS探测后固定新地址。新gold取得合格官方结果；新empty虽得到预期官方负结果，却有一次上游idle timeout，严格传输门仍判未知。原传输只存汇总字节数，不能证明完整HTTP响应，故不修改判定；采用同源gold、同IP／CA及原规则，为empty建立独立重试身份。此修复不改变求解侧网络权限或提供官方测试反馈。

调度已将该题三个身份单列pending。其余九个已准入身份可先执行；只有冻结资格严格通过后，Requests才进入主机API白名单。异步迟到或失败均不改变12回合计划分母，也不按模型成绩换题。

## 首次启动失败与独立恢复

首次r1用户服务确实启动，但九个已准入回合在实际执行器的旧CPU检查处失败：底层`_run`硬编码要求CPU池至少176核，和本轮32核上界、24核实际角色分配不符。执行日志及账本证明：**0个controller、0个任务容器、0个provider请求、0元API费用**。九个现金准入记录已关闭，全部自建资源清理；这九项是进入模型前的部署失败，不能填成模型代码失败。

独立r2部署保留原题目、seed、K条件和同一130元账本，使用新的物理资源身份。新CPU检查验证冻结池中的24核角色分配、范围、互斥及上界，不把协调器自身8核affinity误当全部可用资源。正式和诊断路径执行同一检查，九项CPU控制通过；源码和r1失败记录保持原状。

r2必须再经一次真正的actor/controller零模型诊断，覆盖实际`_run`、包展开、ready、RPC及清理后才能调用API。只有证明旧账本全局请求为0、九个旧准入无费用且所有旧对象静止，才备份并恢复这些零请求准入。恢复不增加130元额度，也不将已调用模型的回合重新采样。最终实际启动及用量以本批运行回执为准。

上述真实诊断已经通过：实际CPU检查、actor/controller ready、SDK初始化、双成员私有会话与计量均完成，model_calls=0，actor、controller及卷全部清理。账本备份及九项零请求准入恢复留有独立审计，随后才启动r2。旧账本路径不变，没有另开第二份130元额度。

Requests新地址下的单empty独立重试再次出现同一连接的idle timeout，官方负控结果仍符合预期。相同字节总量和重复位置不能证明HTTP响应完整，本轮保留未知；后续仅在新修订和新实证中核对协议边界，不放宽已运行r2的规则。
