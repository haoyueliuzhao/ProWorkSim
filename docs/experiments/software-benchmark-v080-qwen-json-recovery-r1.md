# v080：Qwen 调度 JSON 故障恢复

本修订只接续原 Qwen 六组3000题中的未消费身份，不重跑已进入模型的回合、不改变任务、seed、模型、token预算或受管工具。新的普通用户协调器为 `proworksim-v080-primary.service`，复用四个原模型驻留，4个生成任务与1个异步评分线程。

## 已知故障与归因边界

旧v076主协调器于2026-10-29 11:38:41以`coordinator_error/JSONDecodeError`停止，保留了完整summary；错误正文为`Expecting value: line 1 column 1 (char 0)`，没有文件名或堆栈，因此不能唯一断言旧错误发生在哪一次读取。

源码中存在可复现的竞态：episode使用`write_new`写宿主`controller-ready.json`；该函数先`open('xb')`创建路径，再写正文和fsync。资源观察器并行读取这个路径，但旧`pending_pairs`只捕获文件不存在，没有处理已创建但内容为空或尚未写完的情况。该路径能够产生同类JSON错误并传播至整个协调器。新修复消除这一已证实缺陷；它与历史故障一致，但不补写不存在的旧堆栈证据。

新观察器把不存在、暂不可读、空/部分JSON以及不合格状态标记为该任务“尚未取得就绪证据”，并在进度中附原因。只有完整字典、原协议版本、SDK初始化完成、model_calls=0才进入就绪缓存；执行器原有的最终初始化检查和时限均保留。未能读取一个任务的状态不再使整个队列停止，缺失或错误状态也不会被当作就绪。

## 库存、费用与资源

旧summary记录214个终态；另3个已派发任务267、275、277已有原始technical_unknown结果，分别含50、25、74次调用及完整清理证据。准备器导入这些原结果和用量，不覆盖原件、不重放回合。所有曾派发、存在物理claim或候选目录的身份均排除重复生成。已闭合候选缺评分时，先查原评分身份是否已消费；已消费而缺完整结果的评分单列未知，不重用其身份。

新Qwen协调器MemoryMax为32 GiB，最多1个宿主评分线程。这个上限同时覆盖协调进程及其host scorer／压缩子进程；Docker grader的16 GiB限额位于另一cgroup，不能从整体账中省掉。与API新64 GiB协调器、四模型384 GiB、Qwen任务环境128 GiB、API父组224 GiB及最多四个Docker评分器64 GiB合计，新理论上界为896 GiB。真实可用内存、CPU、磁盘及压力准入仍保留；不能将理论上界当作实际已占用量。

新资源观察器同样采用8个启动槽，并保留全部单容器限额。CPU测试仅覆盖新增解析竞态、错误标记不准入、旧模块不变、原结果归属/清理、单评分线程及私有runner绑定，未运行模型、容器或服务。原受取消任务和技术未知不会被填成模型失败或零token。

准备入口：`tools/prepare_qwen_recovery_v080.py --prepare`；启动入口：`tools/launch_qwen_recovery_v080.py --launch`。在本说明准备时没有执行这些入口；真实部署与资源清理由主代理另行记录。
