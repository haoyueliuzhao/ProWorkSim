# 十二组预算实验的异常隔离与续跑

2026年10月28日，用户要求修复导致整批停止的问题并恢复原十二组实验。本次只接续原6000个逻辑任务身份，不启动六种固定组织的评测，不改变模型、任务、seed、提示、工具、上下文、输出或每题token上限。原始记录保留，部署修订单独标识为v066。

## 停止原因

旧队列于北京时间04:08:26停止。当时30个回合已进入运行，17个正常完成生成并取得代码评分，13个为技术未知，5970个尚未开始；109题通过环境资格，3题未通过。API已核算费用上界15.12547528元，原总限额1500元。

直接触发是原slot 27的PROJECT控制器触及4 GiB容器内存上限，Docker回执为`OOMKilled=true`、退出137。它在建立受管世界期间退出，尚未发送模型请求。模型桥的请求、计数和生成计数均为0，线程及容器也已静止。

旧宿主在放行控制器前把状态标成“可能已派发”；异常回收没有依据完整零请求证明收紧这个状态。协调器随后将“没有控制器账本”升级为`missing_qwen_usage_reservation`全局故障，取消了其他在途任务。问题包括环境容量不足，以及本来可以独立隔离的故障被扩大到全部十二组。

## 修订范围

| 部分 | 新行为 |
| --- | --- |
| 控制器内存 | REF和PROJECT控制器统一由4升至16 GiB；actor仍16 GiB，每对真实预约32 GiB。 |
| 总资源门 | 仍为152 CPU、832 GiB，保留128 GiB安全余量。并发按实际预约自动降低，不靠扩大整机额度解决单容器OOM。 |
| Qwen请求记录 | 每次转发前持久保存请求身份和精确输入／输出预约；收到响应先保存实际usage，再转发给控制器。控制器日志缺失时可用独立宿主账本恢复。 |
| 零生成证明 | 启动意图、实际转发、完整零请求证据分开。只在证据和静止证明齐全时标记可恢复零生成，不凭缺文件推断0。 |
| 单题异常 | 有界的断流、控制器退出、候选导出或评分失败进入该题异常集合，其他独立任务继续；未知用量不填0，也不自动重采已调用模型的题。 |
| API异常 | 鉴权、余额、限额或账本故障隔离至DeepSeek；Qwen不随之停机。原唯一1500元SQLite账本继续使用，不重开额度、不重复中性API验证。 |
| 真正共享故障 | 源码／任务身份不一致、无法证实清理、共享资源安全门等仍可全局停止，不能靠删掉完整性检查追求表面不停机。 |
| 进度保存 | 新cursor记录未开始、在途、闭合引用及provider状态；旧结果按原引用导入，不覆盖原故障或评分。 |

这些是故障处理和部署容量修订，不是提高模型推理预算，也不是算法收益。保守预约只是未知消耗的上界，不冒充实际token。

## 原库存如何接续

独立核验确认25、27、29三个旧尝试为零模型生成且已完整清理；其中25／27是初始化OOM，29在入模前取消。仅这三个身份允许从相同初态重新准备。其他27个已入模尝试不重新采样。

原17份代码评分、7项交付端点和109份有效环境资格保留。评分复用逐题通过原资格验证器，并检查官方评分实现、镜像、测试材料、资源限制及环境行为等价；新旧运行目录和评分ID分离。三项旧环境失败继续单列，未据此换题。

当前允许接续5937个原任务身份，原有预算上限合计44,530,000,000输入加输出token；这是剩余任务的最大额度，不是预计消耗，更不是重新授权一套6000题预算。新环境控制776项，其中包括一项因旧全局取消而未完成的gold控制；它是评分环境控制，不是模型重采。

只创建续跑批次自有资源：两次准备修订合计最多5941对actor／controller及对应专用卷（5937正式＋4对零模型诊断）、5937个代码评分、2970个交付评分备用身份、776个环境控制、6个普通用户模型驻留和1个协调器。r1已使用并清理2对诊断；r2只剩2对诊断，不再设置备用，最多创建5939对actor／controller。实际创建还受CPU／RAM／显存／磁盘门限制。所有actor／controller网络为none、drop ALL、无宿主目录绑定；仅原四个Requests评分任务保持既定私有评分能力和限定httpbin通道。共享服务器挂载、网络、驱动、守护进程、linger及他人资源均不修改。

## 验证和运行记录

已完成有针对性的CPU检查：宿主请求先记账再转发、断流留有界预约、零请求证明、API独立停止、旧结果不重采、资格等价、实际32 GiB预约与组合容量门。全部原v064源文件与归档保持原字节。

r1的REF零模型检查通过。原触发OOM的scikit-learn PROJECT已在16 GiB下完成SDK初始化，容器没有OOM，但完整回环超过原180秒诊断时限，仍保留为失败，未据此启动正式任务。其原始结果、清理证明和源码字节已独立封存。r2采用新目录与新包，只将独立诊断时限延至600秒；正式生命周期24000秒、软／硬期限21600／23400秒，以及工具、模型参数全部保持。四个入口经机械AST对照；新版包CPU导入验证没有联网、模型或GPU操作。

r2的两项真实部署诊断随后均通过且完整清理。启动时发现Python 3.14与3.12的`ast.dump`默认空字段格式不同，使同字节源码的派生摘要不同；当时仍未进入正式模型。r3显式统一AST序列化，并将启动路径改为读取已封存计划，不在运行时重复准备。两项部署资格经原结果、正式限额、任务绑定和相关执行代码字节一致性检查复用，未再创建诊断容器。

r3已推进Qwen与环境评分。DeepSeek初始化另出现旧账本规范字段兼容错误：规范调用记录有`prompt_tokens`和`completion_tokens`，没有`total_tokens`。该故障被限制在API provider，未停止Qwen。随后以独立v067 API协调器修复为两项相加，原准备成本仍为747＋52＝799 token，不重新调用API验证。独立协调器不管理Qwen生命周期，只使用原未消费API身份及同一资源分配锁，新增4 CPU／16 GiB协调开销也纳入原152 CPU／832 GiB总预约；原1500元账本继续共用。

当前主队列的API暂停标记属于保留的故障记录；实际API进度以v067为准。汇总只取v066主队列的Qwen六组、v067的DeepSeek六组，避免将交接状态与真实结果重复计数。[合并进度脚本](../../tools/report_continuation_progress_v067.py)按原6000个逻辑身份读取两个状态源。

正式运行状态以独立回执为准，本说明不把准备完成说成任务完成，也不承诺任意故障都能自动恢复。普通单题异常在队列中隔离，影响共享完整性的故障仍需修订后续跑。
