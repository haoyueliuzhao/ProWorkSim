# v232.3｜诊断是否进入接收者的实际模型请求

**结论。接收预算已经转化为真实行动机会，但完整正文仍未进入接收者请求。** 两次后续请求均能核到消息 74 的前 500 个字符，原件有 1,934 个字符。001 随后固定了已有补丁并完成工作包；其修改和通过公开测试均早于诊断送达。当前证据可以确认预览呈现，无法确认诊断促成了代码修改。[逐请求观测和官方评分](../../artifacts/software-benchmark-v232-3/recipient-r1/results.json)

上次在 Sphinx-9591，002 向 001 的诊断已获项目接受，消息号为 78。001 随后触及预算边界，没有再发起模型请求。本轮要检验从“正式送达”到“接收后行动”的这一步。[v232.1 对照记录](v232-1-handoff-audit.md)

## 实验设计与判据

从同一个异常保存点新增一条续跑。沿用原始 D1 分工，001 负责实现，002 负责独立诊断并向 001 交接。原前缀 4,027,970 token、原组织决策 1,910 token 均计入逻辑上限，成员仍共用 **970,120 token**。模型、T1 观察、工具权限、交接语法和两个正式评分端点沿用上轮设置。

本次同时启用两项预算保护。第一，采用 v232.2 的待纠错预留：诊断仍待交接且成员还可以行动时，普通请求不能花掉留给一次合法纠正的额度。第二，在相同团队总限额内，新增一份只用于接收者的完整请求容量，保守预约为 131,072 token。新职责、验证、交付、可能的纠错、可能的接收合计按五次完整调用准入。新预留压缩了交接前自由行动的空间。与上轮比较时，两项变动和独立生成波动都应考虑。[冻结方案](../../artifacts/software-benchmark-v232-3/recipient-r1/protocol.json) · [调度实现](../../src/proworksim/software_handoff_receive_v232_3.py)

只有项目把该职责置为已交接，并为指定收件人登记了消息序号时，才唤醒并优先调度收件人。保留原生收件箱。审计顺序为正式消息回执、随后收件人的物理请求、该请求内的消息序号和正文哈希、模型实际返回、项目实际执行的动作。正文在请求中出现可以证明呈现；要进一步说明成员采纳了诊断，还需有与具体发现对应的后续行动证据。

**零费用控制。** 在真实 OpenHands SDK 上分别运行首次发送成功、首次填错后改对、连续两次填错三个脚本。前两种各有一次正式交接和一次接收者请求，均在实际请求中找到同一条消息，随后有工具动作；第三种只有一次纠错，没有正式交接，也没有触发交接后的专用接收机会。三个脚本的外部 API 调用均为零。[SDK 回执](../../artifacts/software-benchmark-v232-3/recipient-r1/sdk-control.json)

**在收到什么内容上有直接证据。** 第 77 次机会，002 首次调用合法，引用本人的证据事件 69，系统将职责登记为已交接。第 78 次机会立即轮到 001；第 80 次机会，001 再次发出请求，第 82 次机会因预算不足未派发。两次物理请求中的收件人、发送人和消息序号均匹配，逐字符核对得到连续的前 500 个字符，占原文约 25.9%；两次都没有完整正文。原生收件箱对消息体固定取前 500 字符，因而在本地短消息控制中表现为全文可见，在实际长消息中只呈现预览。[收件箱截取规则](../../src/proworksim/software_benchmark_world_v054.py) · [消息曝光与响应凭据](../../artifacts/software-benchmark-v232-3/recipient-r1/results.json)

**在收到后做了什么，也能按版本核对。** 第 75 次机会，001 已修改代码形成 v8；第 76 次机会，该版本的两个公开测试通过。第 77 次机会才发生正式发送。看到预览后，001 在第 78 次机会对同一 v8 执行了 `fix_patch`，形成 `patch-1`；在第 80 次机会对该补丁执行了 `complete_work`，两项动作均有成功回执。模型随后未调用针对消息 74 的原文读取工具。不能把先前的修改和测试归功于稍后才出现的诊断，也不能把固定补丁或完成工作包当成正式集成交付。最终官方代码评分未通过，未取得合法提交，原异常的解除及复发情况均因后继证据不足而未知。

**全文是否可取？** 生成与评分结束后，用归档状态和原接收者身份执行只读回放。`read_work_event(sequence=74)` 返回 1,934 个字符，哈希与正式发送正文完全一致。这验证了现有原文入口；本次在线的 001 没有使用它。下一项可单独检验的改动是，在被截断的正式交接旁显示“已展示 500／1,934 字符”和本条消息的原文读取参数，然后观察成员是否主动回读，以及回读后是否有内容对应的实质动作。[回放与在线结果](../../artifacts/software-benchmark-v232-3/recipient-r1/results.json)

本轮三项 SDK 控制和原文读取回放均为零 API。线上只新增这一条成员续跑，实际结算 **889,724 输入＋2,335 输出 token，1.54323392 元**；同一账本累计 **110.29865160 元**，余额 **34.07601480 元**。未结算请求为零，执行环境已清理，评分端未报告清理错误。本次首次发送即成功，线上没有触发格式纠错。单个历史现场、每组一次生成，只能据此判断执行链条和本次可见内容。
