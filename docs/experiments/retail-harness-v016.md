# v0.16 独立开发情境与四项目 CPU 见证

本记录报告新增世界与执行关系的有限可行性，不报告模型能力或训练收益。当前 v0.15 三模型筛选、后续学习执行图与 Marshmallow 锁定需求均未由本工作修改。harness 的真实 SDK 与模型比较结果另行记录，不能用下述规则见证代替。

## 独立开发数据

扫描固定 UCI XLSX 的 541,909 行，排除旧 train/development/locked 全部客户和发票后，固定六个片段，共 **12 个新客户、36 张完整发票、164 行原始记录**。新六片段间也实体互斥。每片段含 2 客户和 6 发票，大小 23–32 行。

这里仍只有一个 UCI 来源；数据为**开发用途**，不是新的独立来源或锁定集。所选发票完整，客户完整历史没有建立。筛选偏好小发票、可表示的两位小数和取消记录，不能将本素材当作总体分布。原始缺客户异常不在这个有界子集中。来源 SHA、每片段 SHA、旧排除实体和确定性选取规则见 [固定清单](../../examples/retail-harness-v16/source-manifest.json)，合同及接口见 [设计说明](../design/retail-harness-v016.md)。

准备命令：

```bash
.venv/bin/python -m scripts.import_retail_harness_v016 \
  --source runs/assets/uci-online-retail-v015 \
  --output runs/assets/uci-retail-harness-v016
.venv/bin/python -m scripts.retail_harness_experiment_v016 \
  --output runs/retail-harness-v016-cpu
.venv/bin/python -m pytest -q tests/test_retail_harness_v016.py
```

六个世界均通过真正的 WorldCore、StaffRuntime 轮转、文件版本、SQL 构建、固定提交及既有 Decimal 历史奖励评价。准备前缀不归于当前 actor。结果：

| 责任 | 样本 | CPU 完整责任 | 实际 R |
|---|---:|---:|---|
| 实现 | 2 | 2 | 每例 1 |
| 复核 | 2 | 2 | 每例 1 |
| 双成员 | 1 | 1 | 1 |
| 三成员 | 1 | 1 | 1 |

另执行 3 个有界负例：错发票数 SQL 得 0.2，无依据批准错提交得 0.25，指向没有差异的 CustomerID 单元格得 0.25。六正例加三负例共 **9 个闭合 CPU episode、79 次规则决策**。两项新增边界测试通过，确认实体排除、完整发票、旧 registry 数量保留及新 manifest/case 拒绝篡改；新增文件 Ruff 通过。没有重跑旧全量测试。

程序策略只用于可行性见证；正确 SQL 没有注入模型任务、SFT 或 RL 采样。原始记录为 `runs/retail-harness-v016-cpu/`；摘要为 [九路径结果](retail-harness-v016-cpu.json)。

## 四项目的真实发布、消费与反馈

另外使用 f0 开发片段建成一个 P0/P1/P2/P3 世界。它与六情境分开，不能增加 H1 样本数或独立来源数。

- P0 真正读取并发布原始资料、字段和未解决项，固定资料交付。
- P2 初始合同可发布；P1/P2 都真实读取并采用它和 P0 资料。二者输入不依赖对方结果，因此可以在同一合同下启动。
- P1/P2 分别真正执行指标和客户分析 SQL，发布实际结果。P3 读取并采用两条结果与合同，执行按客户 FULL OUTER JOIN 的集成 SQL。
- P2 随后写入并发布 v2 合同，将全期 sales_only 改为截至 2011-07-01 的 net_signed。发布产生有限义务修订，但没有自动更新采用或成果。P1/P2/P3 的后续读、采用、写、构建与提交均是显式工具动作。

最终运行 `runs/retail-projects-v016-cpu-r4/` 共 **97 次真实工具调用、7 次实际 SQL 执行、5 条维护影响**，包含两版完整结果和一次真实混合版本错误。所有期望金额由宿主 Decimal 读取原始数据与公开合同计算，未调用 SQL 结果作为真值，也未反馈数值答案给项目。

| 客户 | 初版金额/票数 | v2 金额/票数 | P3 最终差额 |
|---|---|---|---|
| 14298 | 37,830 便士 / 2 | 37,830 便士 / 2 | 0 |
| 14834 | 49,705 便士 / 2 | −1,445 便士 / 1 | 0 |

在 P1 更新、P2 尚未更新时，P3 真正执行旧分析与新指标的组合。客户 14834 出现 **−51,150 便士和 −1 发票差异**，本地可编辑测试真实返回 `tests_failed`。独立报告也从结果行与两条来源版本核对不一致；没有把旧分析静默替换为新分析。P2 后续显式构建并发布 v3 分析，P3 再读、采用、执行，两个客户均恢复一致；错误集成 v3 被保留，未当正确成果提交。

六个机制控制通过：两个版本中 P1 构建不改变 P2 产物、草稿写入不重建下游、发布不重建下游、被替代义务拒绝旧工作提交、混合版本实际产生差异。报告另保留发布前旧采用，不将“发布”与“采用”混同。

证据为 [最终项目见证](retail-projects-v016-cpu.json)。它保存实际版本、SQL 输入、义务修订和最终固定提交。运行命令：

```bash
.venv/bin/python -m scripts.retail_projects_experiment_v016 \
  --output runs/retail-projects-v016-cpu-r4
```

以上命令均要求全新输出目录；重现时应更换目录，不覆盖原记录。

## 开发失败与解释边界

四项目程序开发经历按 [尝试登记](retail-projects-v016-attempts.json) 全部保留：

| 尝试 | 实际结果 | 修订解释 |
|---|---|---|
| 初次 | 首次跨项目读取报 Unknown object | 程序错误地假定 `P0::data` 是对象 ID，改用内核 canonical object_identity |
| r1 | 对同一工作重复 adopt 被拒绝 | 程序先检查并复用实际绑定，版本变化再显式 adopt_version |
| r2 | 两版正常路径完成 | 预备可行性结果；尚未加入混合版本负例 |
| r3 | 混合版本产生真实 tests_failed 后程序中止 | 通用见证 helper 原本只接收 success，补上仅该预声明负例允许 tests_failed；没有改模型、世界或 SQL 判定 |
| r4 | 两版完成，混合版本错误与恢复全部记录 | 最终有界见证 |

初次/r1/r3 的闭合记录中保留了开发 helper 异常；它们不是模型失败或学习零收益，也不被后来成功覆盖。r3 的 SQL 失败是预期负例，程序中止属于见证 helper 不接受该预声明状态；此区分没有回写到旧原始 episode。

四项目当前为 **CPU 可行性**：程序显式安排步骤，尚未测共享模型的自主多项目成功率，也未做真实并发速度测量。P1 已用既有零售内容检查；P2/P3 的独立内容核验仍在本报告内，未注册成训练奖励。初版产物发布并集成后再发生反馈，终版才固定提交；没有声称验证已验收项目的无限维护链。

这些实验支持“资料、并行可启动合同、后续版本反馈和真实接口消费已在有限世界中运作”。它们不支持 harness 带来多少收益、参数学习是否改善或 ID-VTDO 获得了有效方法支持。上述问题须分别依据新冻结组合的实际模型 episode 与在线窗口统计。
