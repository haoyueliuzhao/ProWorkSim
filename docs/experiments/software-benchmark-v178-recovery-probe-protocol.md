## 首轮发现的测量问题

v177的40次API调用均正常，实际219,502 token、峰值费用0.23440912元。原严格评分为4/12，但这不能直接解释为8次模型恢复失败：

- r02问题同时要求`passed`计数，评分却期待布尔整轮结果；模型给出通过数1，并明确说明整轮失败。
- 多个“下一步”枚举语义重叠；恢复旧版本后选择另一安全措辞，被单一字符串相等误判。
- r06读取了含目标版本与测试状态的必要片段，评分却要求7354字符整段全部读完。
- “找到了含null的记录”与“知道具体计数”混在status中；`unknown`文本与JSON null也没有清晰区分。
- r11确有一条需要纠正的引用问题：未读取原文却引用不存在的消息0。事实回答未知不能掩盖这个问题。

## 修订

1. 明确`overall_passed`布尔结果与`passed_count`整数；提供不含答案的字段类型。可空字段在已知与未知案例中使用相同类型说明，不通过schema泄露未知答案。
2. 用可判定的布尔结论替代互相重叠的安全动作枚举，例如“旧测试是否验证当前快照”“零用例是否算通过”。同时保留42项精确事实，不能只靠回答否定结论通过。
3. 按必要事实的原文字节区间核查实际读取，不要求展开无关整段；相同原文的直接观察引用同样有效。
4. 每个引用必须存在，且与实际读取范围相交；额外编造引用同样拒绝。不存在隐藏评分观察时，不允许把摘要伪装为消息0。
5. 保留12例相同原材料，使用新物理调用身份及澄清后的问题。每例仍最多9次请求／8次读取，独立记录费用和结果。

4项CPU控制覆盖必要片段读取、虚假引用、布尔与计数／null区分，以及schema不泄露未知答案。模型仍只使用原文读取工具，原始历史不可修改。

通过标准仍是12例全部满足事实、读取证据、引用、范围及决策检查。由于修订利用了首轮错误，这属于开发性功能验证，不是独立统计确认，也不证明完整编码任务中的自主恢复能力。
