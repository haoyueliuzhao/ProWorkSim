# DeepSeek v055：输出越界隔离、预算策略 r4 与控制隔离事故

记录日期：2026-10-22，时间按北京时间（UTC+8）。本文区分已经观察到的事实、由旧代码分支可推出的结论、尚无法恢复的信息，以及修复后的预期行为。预算策略资格通过不代表性能提升已经发生，也不代表正式任务已恢复。

## 共享停顿的原因与已知边界

09:52 左右，`PROJECT-thinking / astropy__astropy-13236` 的第 24 次 API 请求触发旧账本的 `provider_usage_exceeded_authorized_request_bound`。共享协调器随后停止新派发并等待在途工作闭合。这不是 2000 元总预算耗尽，也不是 API 的 64 并发上限已经用满。

该请求明确发送 `max_tokens=2048`，原预约为 2.113536 元。旧结算分支先验证输入用量不超过 1,048,576、缓存用量分区一致等条件，再判断 `completion_tokens > requested_max_tokens` 或峰值费用超过预约。由此能推出该请求的完成用量超过 2048：如果完成用量不超过 2048，峰值费用至多为原预约金额，不可能进入这个分支。这是由已记录请求与代码路径作出的推导，不是取回了原响应。

旧代码在这个分支只保存失败原因；响应文件又只在 `complete` 成功返回后写出。因此原响应的准确 `completion_tokens`、响应身份、响应哈希和实际费用均不可恢复。本文不将“越界”推断成某个具体超出值，也不假设仅多出一两个 token。另一条历史不确定请求为 `PROJECT-nonthinking / pytest-dev__pytest-7490` 的第 19 次调用，两条都保持原不确定状态，不重放调用或任务。

停顿审计：[原始只读审计](../../artifacts/software-benchmark-v055/budget-policy-r4/original-halt-readonly-audit.json)。审计采样为 10:19:13；其中 `migration_not_executed=true` 只陈述该时刻的状态，不能用于描述后续事故后的账本。

## r4 的费用约束与异常范围

新策略保持模型、思考开关、温度、请求 `max_tokens`、Agent 工具、上下文、任务 token/调用/时间上限、直连 HTTP 传输、自动重试禁用和 2000 元总上限。REF 请求输出上限仍为 32768，MATCH/PROJECT 仍为 2048。现金预约改为模型文档绝对输入上限 1,048,576 与绝对输出上限 393,216 的峰值合计：

`1,048,576 × 2 / 1,000,000 + 393,216 × 8 / 1,000,000 = 5.242880 元/在途请求`。

这个金额是保守预约，不是预计或实际收费；393,216 是提供方文档的模型界限，不是给 Agent 放宽的输出上限。约束和价格依据沿用已查阅的 [官方接口文档](https://api-docs.deepseek.com/api/create-chat-completion/) 与 [官方价格/模型边界](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)。未来文档变化不能自动修改本批冻结策略。

新结算先记录响应的用量、身份、哈希和结束原因，不保存响应正文到公开证据。若费用与绝对模型界限均有效，仅完成用量超过本次请求上限，则按真实用量记账、扣住该响应不交给 Agent、把该任务记作技术异常，并让其他任务继续。不会截短响应后假装正常，也不会把越界内容用于修复。异常调用保持唯一请求身份，不能自动重放。

下列情况仍停止共享派发：绝对模型界限被突破、用量分区或身份不可信、重复提供方响应身份、费用超过现金预约、总承诺超过 2000 元，以及原策略中的鉴权/账户硬错误。将一般任务异常隔离不等于取消财务或完整性闸门。

两条历史未知请求各保留原 2.113536 元预约，另在独立 `budget_adjustments` 中补 3.129344 元，合计补充 6.258688 元。原请求行不改写，未知用量不填成已知费用。补充预约计入总承诺和剩余预算。

## 10:27 的控制隔离事故

首次迁移 CPU 控制存在隔离缺陷：迁移工具原来的 `connect(path=LEDGER)` 在函数定义时捕获正式账本路径；控制仅替换模块变量 `LEDGER`，未改变已经捕获的默认参数。于是本应在临时 fixture 里执行的迁移实际于 **10:27:46** 写入正式账本。控制里模拟的 `require_drained` 也随之进入了正式迁移证据。这个执行不符合预定“控制先通过、根协调器再接受并迁移”的顺序，不能称作正常人工审核后的迁移。

实际写入内容为：建立 r4 扩展表、添加两条补充预约、把元数据策略切换到 r4、在迁移历史中保存旧策略和旧 halt、清除该已识别 halt。原迁移事务内部检查请求行哈希前后一致、请求数一致、总承诺严格等于预算方案和上限不变后才提交。正式任务没有因这次误迁移自动恢复，调度停止状态仍保留；事故观察记录当时也未发现新正式请求。

临时目录随后被失败控制的清理逻辑删除，其中的迁移前 SQLite 备份、计划和收据没有保留下来。迁移历史中仍有这些文件曾经的路径/哈希，但那些引用目前不可访问。**不能据此声称具备独立保留的迁移前后请求行哈希对照，也不能声称有可用的迁移前完整备份。**

现有证据的强度是：

- 执行源码含事务内请求行完整哈希相等断言，事故执行版本已本地封存。
- 事前独立只读审计记录 22,745 条已结算、2 条不确定，结算合计 123.80074136 元，不确定原预约 4.227072 元。
- 事故后独立保留的请求表有 22,747 行，SHA-256 为 `3857188de594171c0e000e73ae05dc101dace2506d1d5e0cd07696f42658af60`；请求原承诺 128.02781336 元，与上述汇总吻合。
- 追加预约 6.258688 元后，总承诺为 134.28650136 元；没有在途预约，预算上限仍为 2000 元，并发上限仍为 64。金额是该静止快照的保守承诺，不是提供方账单。
- 事故后的 SQLite 备份已保留在本地，SHA-256 为 `89d5fb21369be23023e09e799fcc87216df52f87f7050011e9c55398c7558cac`。这是**事故后**备份，不能冒充事故前备份。

## 控制隔离修复与必要资格

修正后的迁移连接函数必须显式传入路径，消除了默认参数捕获。修正后的 CPU 控制另外在底层 `sqlite3.connect` 拦截所有连接，只允许临时 fixture 根目录内的数据库；访问真实账本路径在打开数据库之前即抛错。这是独立于模块变量替换的第二道边界。控制明确验证拒绝真实路径后，才操作 fixture。

已完成的隔离控制包含八项必要断言：22,747 条 fixture 行迁移保留和两条补充预约；旧客户端拒绝新策略；正常请求体不变且按绝对边界预约；越界响应准确记账、保留证据、扣住响应且不停止其他任务；绝对边界/用量/身份/现金异常仍共享停机；64 在途与 2000 元约束包括历史补充预约；原 `complete` 与异常类型身份保持；全部 SQLite 连接被限制在 fixture 内。修正后控制明确记录正式账本写入、真实 API、模型调用、GPU 加载、正式 claim 和服务变更均为零。

独立 all-arm 路由控制以 mock 客户端检查六条件及原生 condenser 的 10 个调用：请求体保留、所有调用进入新客户端、PROJECT 继续原项目 controller、REF/MATCH 继续已验证的 r3 controller、三个 arm 的未来 worker 配置/argv 均选择新入口，原阶段/双盘调度 tick 不变。该路由控制没有创建真实账本对象、迁移、启动 worker 或发 API 请求。

证据文件分别为 [隔离预算控制](../../artifacts/software-benchmark-v055/budget-policy-r4/isolated-budget-control.json)、[六组路由控制](../../artifacts/software-benchmark-v055/budget-policy-r4/all-arm-routing-control.json)、[组合资格](../../artifacts/software-benchmark-v055/budget-policy-r4/qualification.json)。本次整理直接使用已通过的必要控制，没有重复跑测试。

资格 `passed=true` 仅适用于上述 CPU 行为与路由；它不替代根协调器对事故后正式账本的独立只读接受，不宣称已经恢复、没有历史证据缺失或已提升吞吐量。

## 冻结身份与恢复边界

独立 r4 API 源文件 SHA-256 为 `96c7f36e672a913fb58ba6f3f8b9710d20e8f5be345446e0492a30cbaaf1b989`。资格文件 SHA-256 为 `e40b7a3682a37d536d53889cf14cdae18fbac3887c8b9bc519921d87848b251f`。其余新 source、controller、episode、迁移工具与控制的完整 refs 在资格 JSON 内；旧冻结 API/controller 文件未改写。

未来恢复只面向原清单中的 pending 槽。既有异常、已进入的回合、请求身份、旧补丁、评分和费用保留；既有进入回合不自动重跑。必须先由根协调器确认事故后真实账本与封存证据一致，再启动引用新客户端的独立 host 版本。旧客户端会因策略身份不匹配而拒绝打开新账本，不能直接重启旧 host。

费用策略及异常处理变化应在后续结果中按 runtime revision 标识。原来因全局停顿进入技术未知的任务不会被重写成模型失败，也不会因为未来恢复而自动获得第二次抽样机会。吞吐量比较需要从实际恢复后的观测窗口单列，不能把共享停顿时段当作优化后的稳定速度。
