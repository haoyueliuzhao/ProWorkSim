# v229 首窗补充开发｜继续寻找可对照的真实工作现场

## 原首窗为何没有产生 Q1

原首窗 4 题全部评分，Sphinx 和 scikit-learn 正确交付，Django 和 pytest 均未通过且没有合法提交。3 题未采到预定异常，Django 有验证缺口，但只有维持原图一个合法选项。完整配对为 0，Q0 保持初始值。原批累计 301 次请求，消耗 17,049,695 token，费用 28.09638104 元。[原首窗结果](../../runs/software-benchmark-v229/dev1-r1/window-result.json)

Django 的现场可以区分“有人还没完成工作”和“需要改变分工”。001 已经完成工作包并固定了补丁，002 已经担任独立复核者。清单要求 002 打开对应补丁、运行复核测试并作出复核结论。旧程序在见到该异常时就保存并停止寻找现场；候选菜单又会跳过已经完成的工作包，最后只剩 KEEP。为取得组间差异而重复指派已有复核者，无法产生实质不同的组织图。[现场回执与合法选项检查](../../artifacts/software-benchmark-v229/dev1-extension-r1/historical-check.json)

## 补充批次怎么做

沿用原审计的四个合格工作状态要求。对只有 KEEP 的现场记录成员、工作包、异常、证据、首次和末次观察位置，工作成员继续自然修复。只有真实出现异常且当时至少存在一种合法局部变换，才保存共同现场并邀请独立策略 Agent 提名。提名者仍可选 KEEP，不能将“可选”计成“已采纳”。若冻结提名确有实质变化，才从同一保存点运行固定原图与执行变更两臂。相同的计费、评分、5M 团队逻辑额度和交付规则继续适用。

题目从已通过环境控制的任务中选择，排除原 v228 八题以及 v229 已冻结的 16 个任务身份。使用 16 个候选身份的集合查找历史工作回执，共检查 23 条匹配轨迹。3 个身份检出带实际工作包的历史异常。排序优先考虑有异常记录、能补充尚未覆盖的异常类型和仓库，再用固定哈希确定顺序。历史回放只用于提高开发现场采集机会，未读取历史候选的官方评分。每个真实运行仍从头开始，单独核验当前成员有权看到的证据与合法变换。原 4 题不被替换，第二窗口和确认题单仍然封存。[筛选证据及范围](../../artifacts/software-benchmark-v229/dev1-extension-r1/recruitment.json)

| 顺序 | 补充开发题 | 可用的历史线索 |
| --- | --- | --- |
| 1 | Matplotlib-24570 | 持续修复失败、验证缺口 |
| 2 | Django-13417 | 验证缺口 |
| 3 | Astropy-7606 | 验证缺口 |
| 4 | pytest-10356 | 所查轨迹未检出符合条件的历史异常 |

补充批次存在历史暴露和按异常富集的选择偏差。用于验证受管机制并为 Q0 搜集开发对照；不能用来估计一般任务的自然异常发生率。补充批次四个不同状态均有合格配对才拟合 Q1；否则按类型报告已有证据和缺失项。第二窗口和确认实验不自动启动。

## 经费与核验

用户批准在同一个 130 元独立账本中最多增加上述四题。启动前已结算 28.09638104 元，余 101.90361896 元。逐题先预约完整一对的最坏费用 80 元，分支前的历史和提案物理上只付一次。如果结算后余额不足以再保证完整配对，停止新准入并保留余下题目身份。没有为补充批次新增现金额度。[资金凭据与源码冻结](../../artifacts/software-benchmark-v229/dev1-extension-r1/freeze.json)

零付费控制验证了多次遇到同一单选现场时继续观察、同时存在另一项可行异常时能采到正确现场、已经解除或无法绑定工作的节点不启动分支，以及现有预算预约与评分路径。4 项检查通过。Django 原现场在新规则下记为继续观察，历史 Astropy 真实现场则具备发起提名的条件；这两次离线判断均未重采模型或改写旧评分。[CPU 核验](../../artifacts/software-benchmark-v229/dev1-extension-r1/cpu-tests.txt)
