# v222 任务中途协作调整新增实验审计

**审计日期：2026年11月20日。范围：此前v217至v221审计之后新增的v222完整试跑，以及关联的v222.1性能修订。**

本报告不重复计入v216及v217至v221已经汇总的结果、运行次数和费用。现有汇报材料中的“维持分工／接受模型方案”采用的是历史v216.2数据，不是本次新增对照。这里保留v222真实的L/G条件名称，避免将不同实验换名或合并。

## 一 审计结论

**执行完整性可按本批范围通过；组织调整的收益尚未得到证明。**

4题、8条主运行全部结束并完成官方评分，无生成完整性故障或评分未定。L/G均为代码正确1/4、正确交付0/4，8条全部在Token预算边界结束。共同前缀、方案生成和续跑的Token已经对账，629个实际API请求全部结算。

机制证据比总分更有限：4题中只有2题生成了调整候选；只有scikit-learn观察到L/G不同的实际组织调整。SymPy虽然提出不同安排，G的责任转交没有落实。不能把8条有评分结果，等同于8条都有效检验了组织变化。唯一代码通过的Django题，两组均保持原安排；4条选择尝试调整的运行均未通过代码评分。

图信息已真实进入方案生成请求，但没有独立的必要关系参考集，因此不报告语义依赖的准确率或召回率。G续跑没有调用新增的图定位工具；当前证据更接近“关系辅助提案”的验证，不能称已验证交互式图检索提高定位效率。

## 二 本轮到底比较什么

模型为DeepSeek Flash非思考，基础框架为OpenHands，使用ProWorkSim真实双成员接口。每条完整逻辑任务共享500万输入＋输出Token，包括共同前缀、该条件的方案生成和后续执行。

| 条件 | 向模型提供的信息 | 如何采用分工方案 |
| --- | --- | --- |
| L 常规检索与任务记录 | 原始题目、全局代码检索、任务分工、进度、已登记依赖和可见工作历史 | 按模型返回顺序，采用首个通过检查且有实质结构差异的方案；没有则保持原安排 |
| G 增加项目关系辅助 | 相同基础信息，另将工作与代码、补丁、测试版本等关系交给生成器；定位工具可用关系辅助排序 | 与L相同 |

同题两组恢复同一检查点。实际请求抽样核对覆盖4题×两成员×两条件，同成员L/G工具Schema哈希一致，均57项工具。模型、权限、系统说明主体、测试入口和交付合同相同，后续补丁与评分不互相反馈。

本轮同时改变了关系信息的呈现和检索排序方式，允许L/G生成不同方案；它不是“同一候选集合上的选择器比较”，也不是“维持／接受”的独立分组。选中方案后仍需要成员明确尝试，并通过原有操作规则执行；控制器不直接修改负责人。

协议规定：达到“修改后执行过公开测试且有剩余工作”，或者24次行动机会、累计120万实际Token中的任一边界，就保存进度。每个条件仅在这个保存点生成提案，最多允许一次格式或合法性纠正；不是同一任务反复生成和更新组织方案。

题单依据固定顺序的公开题面选择，排除了近期v217/v218题单，没有按本轮得分换题。任务池有历史接触，不是未曝光确认集。

**需要审查的设计问题：** 提案生成边界与责任转交的执行条件不完全一致。SymPy和scikit-learn提案出现时尚未满足“实际修改后测试”的转交要求；三条尝试转交的续跑首先被正常拒绝。该规则保证已有执行约束未被绕过，但也增加无效尝试，限制了本轮检验组织调整的效率。

8条均没有合法提交记录，因此交付为0不是“提交版本评分失败”的混合统计。Django两条是正确工作树已经形成但未完成交付；另外六条还存在具体代码问题。评分执行成功不代表求解过程中的所有工具调用都成功。

“原通过测试失败”提示修复可能破坏既有行为，需回到对应代码与测试轨迹核验。以上为观察结果，不能从一次L/G配对直接断定图信息造成回归。

## 五 从提案到实际组织动作

| 任务 | L合法且不同于保持方案的候选数 | G候选数 | L实际调整 | G实际调整 |
| --- | ---: | ---: | --- | --- |
| Django 13516 | 0 | 0 | 保持原安排 | 保持原安排 |
| SymPy 13615 | 1 | 1 | 将验证相关工作交给伙伴，实际接受并继续工作 | 提议转交核心实现，但没有成功转交 |
| Astropy 14369 | 0 | 0 | 保持原安排；发生补丁集成 | 保持原安排；改变责任的尝试被拒绝 |
| scikit-learn 25102 | 1 | 2 | 伙伴接受验证工作 | 保留负责人，实际新增通用处理到组合验证的依赖 |

这给出三层不同结论：两题形成L/G不同提案；一题双方都执行了不同组织安排；最终代码和交付结果没有改善。补丁集成本身不一定表示分工改变，不能与责任转交混为一个调整次数。

scikit-learn的G提案引用了代码中的静态关联和成员消息，并说明增加依赖可能减少返工、同时也可能使工作串行。这支持“关系进入提案依据且动作落地”，不证明新增先后关系是必要或有益的。

### 候选生成仍存在限制

8次方案生成均使用了两次API调用，共16次。诊断中有18条可解析候选记录，其中7条通过编译检查，去重后为5份不同调整；另有3个响应未形成可用于候选统计的结构。重复修正记录不是独立方案，未解析响应的候选数也不能填成0。

编译通过只证明结构和声明规则满足检查，不等于执行条件已满足，更不等于成员实际执行。因此，本报告不把7/18直接称为“合法且可执行率”，也不把过滤后的候选全部不同称为“多样性100%”。

L的基础任务记录没有来源事件编号，但沿用的提案规则要求引用所呈现关系允许的事件；本轮L共有4条候选记录因事件引用被拒绝。另有纯补设置不算结构调整、同负责人不能改变权限模式、额外字段和JSON格式问题。这些是信息设计与生成器交互中的实际负担。没有生成出可用候选，不能证明该状态不存在合理调整。

## 六 图信息呈现与质量边界

16个实际生成器请求均核对到与保存输入一致的内容，所引用图身份可以追溯。这证明信息实际进入请求，不证明模型理解或采用了每条关系。

| 任务 | L关系数 E1／E2／E3 | G关系数 E1／E2／E3 |
| --- | --- | --- |
| Django | 3／0／0 | 8／8／4 |
| SymPy | 3／0／0 | 4／11／5 |
| Astropy | 3／0／0 | 9／0／5 |
| scikit-learn | 3／0／0 | 6／9／5 |

E1为实际工作或台账记录，E2为静态源码候选，E3为成员声明或假设。这里是生成器输入快照中的记录数，不能当成经独立验证的真实工程依赖数量，也不应把不同等级直接相加作为图质量指标。

后续求解阶段，L成功调用`locate_work`一次，G为零次。共同前缀统一使用L路径，生成器会事先获得一次自动检索结果。因此，本轮G的可观察作用主要发生在提案输入，而不是后续反复使用图定位工具；模型仍可通过普通搜索和读取定位代码。

生成器索引冷构建耗时6.36—14.37秒，估算Python对象内存163.42—228.89MiB。两组都建立基础索引，不能把这项全部费用只归给G；对象估算也不是进程RSS。L生成器共用74,934 Token，G为107,166 Token，多32,232 Token，约43.0%；这只是方案生成阶段，不是团队总成本增幅。

目前没有独立于生成图的“必要工程关系”参考集。本次不填写语义关系准确率P_edge及必要关系召回率R_edge；来源可追溯、语法可核验与语义正确必须区分。此前合成权限/版本检查保留为工程证据，不能替代真实关系质量审查。

## 七 新增Token与费用对账

**本节仅计v222本批新增调用，不重复加入以前已经汇总的费用。**

| 阶段 | 请求数 | 实际输入＋输出Token | 费用峰值计价上界元 |
| --- | ---: | ---: | ---: |
| 4个共同前缀 | 90 | 3,714,662 | 5.72608904 |
| 8次条件方案生成，含修正 | 16 | 182,100 | 0.28774248 |
| 8条主续跑 | 523 | 32,219,207 | 54.43622792 |
| 合计 | 629 | 36,115,969 | 60.45005944 |

实际输入35,957,087、输出158,882，输入占99.56%，这不是通信内容占比。缓存命中6,497,536是输入的子集，不额外相加。供应商usage是Token总账依据；人民币金额按冻结峰值费率计算，是费用上界，不是供应商发票核销值。

8条逻辑任务合计39,830,631 Token，其中共同前缀在L/G各计一次。扣除物理上只执行一次的重复前缀3,714,662，恰好等于实际36,115,969 Token。前缀和生成成本没有在分支恢复后重置。

本批没有因为现金不足中断任务，320元整批预约已释放；8条结束原因均为任务Token边界。现金预算与任务Token上限是不同约束。

## 八 执行健康度与关联性能修订

8项官方环境控制均合格：4份参考修复通过、4份空补丁失败。8份正式代码候选均取得官方报告，执行完整性字段均无故障；8份交付端点均明确为没有合法提交。629个API请求全部结算，无保留中的请求。

依据本批清理回执，12个生成侧actor已删除，未记录传输清理错误；环境控制和正式评分回执未记录容器清理错误；协调器最终资源租约为空。本次审计没有再次创建容器或修改服务器配置。

轨迹中仍有正常工具拒绝：提前转交、访问无权限的测试报告、测试选择不合法，以及指向未包含在已测试版本中的检查文件。标成`unclassified_exception`的几次返回分别是无实际变更的替换或检查路径不存在，不能仅凭分类名称把整条运行改成技术未知。

v222.1性能修订已经单独形成报告，本次只引用其版本边界：它未接入这8条冻结运行，也没有新增模型回合。因此，不在本报告重复汇总其局部性能数据，更不能用该修订解释本轮L/G结果。

## 九 审计判断与下一步

| 审查项 | 当前判断 | 主要依据或缺口 |
| --- | --- | --- |
| 运行、评分和账目是否闭合 | 通过本批检查 | 8/8评分明确，629请求结算，预算和逻辑Token可核对 |
| 图是否进入真实请求 | 有直接证据 | 16次方案请求与保存输入匹配 |
| 关系是否正确且覆盖必要依赖 | 尚未完成 | 没有独立必要关系参考集，记录数不能代替质量 |
| 图是否改变实际组织行为 | 局部观察成立 | scikit-learn有不同真实动作；SymPy的G提案未落实 |
| 是否改善代码或交付 | 未观察到改善 | 两组均1/4代码通过、0/4交付，且预算全部截断 |
| 是否已验证持续动态调整 | 否 | 每条件只有一个生成方案的决策点 |

建议先完成三项针对性审阅：提案的关系依据是否足以支持其安排；提案产生时是否已有执行机会；交接后的验证与集成为何没有转化为交付。尤其应避免“先生成暂不能执行的方案，再消耗额度满足其前置条件”，并检查是否仍有足够独立的工作可供真实调整。

如后续直接比较“维持分工／接受模型方案”，应在同一任务状态冻结一个具体调整方案，与保持条件配对执行，保留拒绝和未落实结果，不只统计成功接受的子集。这是新试验的设计要求；本次审计没有启动新模型实验或自动使用余额。
