## 2. 此次修复了哪些问题

**来源在产生位置绑定。** System／工具模板、任务、自己历史、伙伴消息、产物、工具反馈、摘要和按需回读分成八类；实际JSON字节位置、事件ID、成员和版本引用保留。SDK按事件顺序与转换关系映射，不搜索相同文字后猜来源。旧历史静态去重会移除字段，本版沿其已验证投影保留来源，不把正常转换误报为未知。

**摘要遵循原算法但保留自身来源。** 原SDK用事件字符串渲染摘要输入，包含既有的展示摘录规则；本版未修改这些规则。动态ManagedAction不能从旧JSON直接重建，现优先使用当前私有会话的原事件对象，并逐项核对冻结来源。摘要被呈现不等于其父原文全部被看到。此前r2／r3的缺口记录保持，最终r4才达到当前字节覆盖结果。

**复核与测试状态分开。** 修复了v155的accept与test_pass混同，分别记录test_executed、test_pass、review decision和版本是否仍当前。作者改版不会继承旧接受。嵌套Pytest沿用已修订的父子session、去重、零测试及超时判定；未通过调整测试标准提高成绩。

**请求与恢复有真实身份。** 采集层覆盖每次物理HTTP及内部重试，保留请求原件、response ID、model/fingerprint（未提供则标unavailable）、usage和异常。共享池阻止重复派发或把已结算请求换目录再调用；失败预约不会伪装为实际费用。

**观测错误不再改写已知账目。** 响应已返回后，即使原件／侧录写入失败，仍把原body交给账本结算，或保留原异常的重试分类；缺口会阻止相应准入，不重放已执行请求。压缩预算不足与账本完整性故障分开，只有前者可以正常回退原文。

## 3. 为什么精确token门仍未通过

本次只读核对了3条历史真实请求，没有为校准重新调用模型。完整请求的canonical字节与原HTTP账本哈希一致，响应ID和usage对账通过；旧记录没有单独raw-wire文件，因此这一步明确记为可核验重建。

| 历史请求 | 官方recipe本地输入计数 | API实际输入 | 差额 |
|---|---:|---:|---:|
| v142／10000／001，第1次 | 10,994 | 11,041 | +47 |
| v142／10000／001，第43次 | 94,170 | 94,217 | +47 |
| v146／10209／002，第1次 | 11,769 | 11,825 | +56 |

三条样本的128-token预约余量覆盖了差额，但不能把它当作通用精确修正。不能固定加47，也不能把差额按比例分给八类来源；差异机制尚未单独识别。[真实历史计量审计](../../artifacts/software-benchmark-v156/tokenizer-audit-r1/summary.json)

官方也将离线计数作为估算，并以API usage为准；公开recipe提供请求转换、渲染与本地编码，但这不自动证明与每个线上请求逐token一致。[DeepSeek计量说明](https://api-docs.deepseek.com/quick_start/token_usage/)、[官方recipe文档](https://github.com/deepseek-ai/deepseek-recipe/blob/main/docs/tokenizer.md)

因此当前可以报告：**输入原件及字节来源可追溯、来源级token可估算、全队实际usage可对账。不能报告：供应商每一个输入token已被精确分配到来源。** 分片单独编码还存在边界效应，其合计也不能冒充完整API提示计数。

## 4. 准入判定

| Gate | 本次结果 |
|---|---|
| G0-1 请求原件／usage或明确异常 | CPU及真实SDK脚本控制通过；真实HTTP边界适配已单独验证 |
| G0-2 payload本地来源估算 | 正常SDK样本100%覆盖，达到本地估算阈值 |
| G0-2 供应商精确来源 | **未通过，不伪称达到98%** |
| G0-3 用量／缓存对账 | 控制通过；按物理账本作总账，分析子账不重复相加 |
| G0-4／5 生命周期与observer | CPU状态语义控制通过；无完整证明的业务channel仍保守unknown |
| G0-6 版本／权限 | 控制通过；实际publication身份与文件／metadata摘要绑定，消息内容hash不冒充代码树hash |
| G0-7 模型身份 | 采集available／unavailable状态；不声称权重严格冻结 |
| G0-8 幂等／恢复 | 控制通过；独立物理ID、无重复派发、异常partial保留 |

[根准入审计](../../artifacts/software-benchmark-v156/p0-admission-r1/summary.json)区分了本地估算与provider-exact门。[独立审阅](../../artifacts/software-benchmark-v156/independent-gate-review-r1.json)结论为：**工程控制分域通过，P1不准入。** 根报告的独立审阅待办是审阅前快照，独立报告已完成，不需要再次重复审查。

[最终状态](../../artifacts/software-benchmark-v156/final-gate-decision-r1.json)明确独立审阅已经完成，但没有将其转换成模型启动授权。

正常SDK只有presentations具备本次完整覆盖证明，其他业务channel不因正常退出自动标为完整。信息“被使用”的判断仍需真实引用、采纳或版本证据；混合摘要及复合代码中的伙伴贡献不作比例分摊。此类未知不能填成0或模型失败。
