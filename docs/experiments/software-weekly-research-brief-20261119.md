# 项目图与组织图驱动的协作策略阶段汇报

**汇报范围：2026年11月16日至20日，包含最新v222结果。**

我们在研究一件事：**两个Agent一起修代码时，能不能根据实际工作情况调整分工，并从过去的结果中学会怎样分工更好？**

目前已经做到：记录代码和工作之间的关系、提出不同分工、让成员实际调整责任，以及根据结果更新方案的选择概率。还没有证明这些调整能提高最终交付成功率。

## 一 先说明团队怎样工作

所有近期主要实验都使用DeepSeek Flash非思考模式。每队有两个Agent，共享500万输入加输出Token，**不是每个成员各有500万**。底层仍使用OpenHands，ProWorkSim在其上增加私有工作区、责任交接、独立复核和正式提交规则；本轮不训练模型权重。

开始时，成员甲负责总任务和最终提交，成员乙可以参与调查、实现或复核。模型根据原始问题自行拆分工作，再决定各部分由谁负责、谁检查。两个成员按调度轮流行动，并不意味着同时进行两路模型推理。

我们分别看两个结果：

- **代码正确**：最后留下的代码通过官方测试。
- **正确交付**：团队按项目规则完成复核和正式提交，而且提交的那版代码通过官方测试。

因此，代码修好了但没有正式提交，会出现“代码正确，交付未完成”。

## 二 项目图与组织图的构建和更新

### 项目图 连接工作与代码证据

项目图将公开需求、具体工作、代码位置、补丁、测试和版本联系起来，记录：

- 每项工作涉及哪些文件和功能，以及可能存在的代码引用关系；
- 哪个成员实际读取或修改了相关代码；
- 工作形成了哪份补丁，伙伴是否已经采用；
- 哪次测试检查了哪个代码版本，后续修改是否使旧测试失效。

我们先从读取、修改、发布补丁、集成和测试等真实事件建立这些联系，最近又加入公开源码中的文件、符号和引用关系。

图会随工作更新。例如代码再次修改后，旧测试记录仍然保留，但不能继续证明新代码已通过。源码里存在引用，只能作为可能相关的线索，不能直接证明两项工作必须按先后顺序完成；成员提出的依赖也会保留为待验证的判断。

### 组织图 描述谁做什么以及怎样配合

组织图把成员和工作连起来：谁实现、谁复核、谁接收伙伴成果、哪些工作需要等待、最后由谁集成提交。它沿用同一批任务身份，随着责任接受、复核和交接等实际操作更新。

项目图帮助回答“这些工作有什么联系”；组织图回答“面对这些联系，我们怎样安排人和顺序”。例如两项工作共用一个接口时，可以安排一人实现、另一人验证，也可以保留负责人并调整先后顺序。哪种更好，需要实验检验。

责任转交必须由成员提出、接收者接受后才生效。调整后的阅读、修改、合并和测试，又会产生新的项目图信息，形成一个循环：

**实际工作产生证据 → 项目图整理联系 → 提出新的分工 → 成员执行 → 新证据更新项目图。**

## 三 从项目图提出协作方案 再用C/N学习选择

模型根据项目图中的代码联系、成员已做的工作和待完成的验证，提出最多两种调整方案，并保留“继续原分工”作为参照。每个方案都要明确：**剩余工作怎样拆分、由谁负责、谁复核、哪些工作先做，以及需要交接哪些成果。** 例如，两项工作共用一个接口，可以考虑集中由一人实现、另一人验证，也可以保留负责人，只调整实施顺序。

对提案分三方面判断：

- **有无依据：** 是否引用了当前可见的代码或工作记录；推测的依赖不能当作已证实事实。
- **能否执行：** 是否保留已有成果、符合成员权限，是否造成循环等待，以及是否与原安排有实质差异。通过提案检查后，实际调整仍须满足当时的工作条件，并完成必要的责任接受。
- **是否值得尝试：** 说明预计能减少什么问题，例如负担不均、等待或验证遗漏，同时估计新增交接、集成和Token成本。这是事前判断，不是已经取得的收益。

**项目图帮助提出有依据的方案，实际运行检验方案是否有效。** 接下来用C衡量方案相对当前选择的实际收益，用N为选择机会偏低的方案保留探索空间，再据此调整后续任务中各类方案的选择概率。

### C 看采用这个方案之后结果是否更好

我们让不同方案从同一个已保存的工作进度独立继续，然后记录正确交付和Token消耗。当前得分为：

**方案得分＝正确交付得1分－0.1×实际Token／500万。**

**C＝这个方案的得分－按当前选择概率计算的平均得分。**

例如，一个方案正确交付且用了400万Token，得分是0.92。如果它高于当前通常会选到的方案的平均表现，就得到正向C。C评价的是整个分工方案，不是个人贡献，也不奖励消息多或修改多。

一个方案通常只执行一次，所以这只是带有随机波动的估计。特别是，当所有方案都没有正确交付时，C只能反映谁花的Token更少；提前失败可能显得“省钱”，却不代表分工更好。代码是否正确、交付是否完成、成本多少必须分开看。

### N 避免过早只选一种方案

当前N的含义是：**某个合法方案获得的选择机会，是否低于均匀选择的参照。**

比如有三个方案，均匀选择时各占33.3%。如果某方案被压到20%，N就给它探索补偿；已经达到或超过33.3%时，不给这项补偿。具体计算是参照概率与当前概率之比的对数，负值按0处理。

所以，N不是评价代码有没有创新，也不是简单数历史上试了几次。刚开始各方案等概率时，N为0。

### 更新概率以后 仍要由成员实际改变分工

我们先根据C/N调整方案的选择概率，再学习“什么工作情况下更适合哪种安排”。学习使用成员负担、工作依赖、待验证内容和成本等信息，不记住题号，也不训练底座模型。

下一题出现类似情况时，新的选择规则会影响采用哪个方案。但**选中方案不等于自动改负责人**：成员仍可以尝试、保持或拒绝，转交和接受仍需真实执行。

当前做法是：用一批任务学习，再在另一批任务上停止更新、检查效果；不是每次读文件或发消息后都重新学习一次。

## 四 我们做了两类不同的对比实验

### 第一类 已有几种分工时 怎样选择更好

这是v217至v219主要比较的问题。

每题先保存同一份工作进度，再准备“保持当前分工”和最多两个调整方案，把可用方案分别运行到底。之后，比较以下五种选择方法：

| 条件 | 用什么信息判断 | 怎样选择 |
| --- | --- | --- |
| 保持当前分工 KEEP | 不用学习来挑选 | 总是继续原安排，仍正常修复、复核和提交 |
| 各方案等概率 q0 | 不根据方案特点偏向任何一个 | 本题有几个合法方案，就等概率选择 |
| 分工与进度记录＋C/N | 当前分工、进度、已登记的先后关系、资源使用等摘要 | 根据过去结果和探索补偿学习选择 |
| 项目图＋C | 在上述基础上，利用工作与代码、补丁、测试版本之间的联系 | 只根据相对收益学习选择 |
| 项目图＋C/N | 与“项目图＋C”使用相同种类的信息 | 同时根据相对收益和探索补偿学习选择 |

五种方法面对同一组已经生成的候选方案，差别在于选择依据和学习方式；求解Agent的代码访问权限相同。本轮主要检验方案选择，不单独检验图对方案生成的帮助。

比较的含义是：

- 分工与进度记录＋C/N 对 项目图＋C/N：增加项目关系，是否更会选？
- 项目图＋C 对 项目图＋C/N：增加N，是否有额外帮助？
- 学习后的方法 对 等概率选择或保持分工：学习是否值得？

五种方法共用各候选实际跑出的结果，不是各自重新跑五套任务。举例说，两个方案一个成功、一个失败，各有50%机会被选中，那么这种选择方法在该题的预计成功率就是50%。报告按这种方式计算，再让每道题占相同权重。**这类概率加权成绩，与实际独立跑出的成功题数有所不同。**

### 第二类 给出项目关系后 会不会提出并执行不同分工

最新v222比较的是这个问题。4题来自4个仓库，每题分别跑L和G，共8条运行。

| 要比较的内容 | L 普通检索＋任务记录 | G 普通检索＋任务记录＋项目图 |
| --- | --- | --- |
| 原始问题和保存的工作进度 | 相同 | 相同 |
| 搜索、读写代码、运行公开测试的能力 | 有 | 相同能力与权限 |
| 当前负责人、进度、已登记依赖等记录 | 有 | 同样有 |
| 是否额外整理工作与代码、补丁、测试版本的联系 | 不用这条额外处理路径；模型仍可自行阅读和判断 | 将这些联系交给方案生成器，并用于辅助代码检索排序 |
| 如何采用提案 | 选择首个通过合法性检查且确实改变分工或顺序的提案；没有则保持原安排 | 同一规则 |
| 是否用C/N学习选择 | 不使用 | 不使用 |

两组的工具、代码访问权限和任务初态相同，后续独立运行。差异限定为是否额外整理项目关系，供代码定位和分工提案使用。

这一轮让L/G分别生成方案，检验“定位和方案生成一起改变后的效果”；前一类实验则在同一候选集合上比较“谁更会选”。两类结论不能混为一谈。

两类实验的500万Token都包括开始的共同工作、方案生成和后续执行，不是在每次换阶段时重新发放500万。v222还规定到一定工作步数就保存进度，所以部分提案出现时，团队尚未满足立即转交责任所需的代码修改和测试条件。

## 五 实验结果及其含义

### 学习选择分工的结果

v217完成两次选择规则更新，v218和v219各增加一次，共四次。后两次学习所用的新运行都没有正确交付，因此新增C信号主要来自成本差异。

| 选择方法 | v217正确交付率 | v217平均Token | v219正确交付率 | v219平均Token |
| --- | ---: | ---: | ---: | ---: |
| 保持当前分工 | 53.85% | 408.06万 | 25.00% | 477.64万 |
| 各方案等概率 | 51.28% | 411.98万 | 25.00% | 448.23万 |
| 分工与进度记录＋C/N | 51.35% | 411.97万 | 25.00% | 449.80万 |
| 项目图＋C | 51.31% | 411.97万 | 25.00% | 448.45万 |
| 项目图＋C/N | 51.31% | 411.97万 | 25.00% | 448.33万 |

这是上一节解释的概率加权结果。v217用于检验效果的任务有13题，各方法代码正确率均为69.23%；但8题只有“保持分工”可选，真正能比较选择优劣的只有5题。v219用于检验的任务有4题，各方法代码正确率均为25%。两轮任务不同，不直接相减或合并成绩。

**项目图＋C/N尚未显示优势。** v217没有超过保持分工或分工与进度记录＋C/N；v219比保持分工少用约6.1%Token，但没有提高正确交付率，也没有比等概率选择更省Token。

### 最新L/G两组的实际运行结果

| 条件 | 代码正确率 | 正确交付率 | 平均完整任务Token |
| --- | ---: | ---: | ---: |
| L 普通检索＋任务记录 | 1/4，25% | 0/4 | 498.69万 |
| G 加入项目图 | 1/4，25% | 0/4 | 497.07万 |

这张表是8条真实运行的结果，无技术未知；两组均只有Django代码通过。4题中，2题的L/G提出了不同分工，另外2题都保持原安排。

scikit-learn题可以直观看出差别：L把一部分验证工作交给乙，乙实际接受；G引用通用输出处理与组合组件的代码关系，保留原负责人，实际增加“先完成通用处理，再完成组合验证”的要求。**项目关系确实进入了提案依据，并对应到不同动作；但这道题两组都失败，不能据此说G的安排更好。** SymPy题虽然也提出了不同方案，G却没有实际完成责任转交。

8条运行全部在Token预算边界结束，包括已经修对代码的两条。预算限制了继续工作，但没有证明加预算就能解决问题。全批实际消耗3611.60万Token，费用峰值计价上界60.45元；实际账单中共同工作只付一次，不能把表中每条完整任务的成本直接相加。

## 六 目前能下什么结论

**已经做到：** 用真实工作建立两张图；让项目关系进入分工建议；让成员实际执行部分调整；让C/N依据结果改变以后选择方案的倾向。

**尚未证明：** 项目图能让分工更合理，或者C/N能提高正确交付率。这些任务样本少且有历史接触，不能代表完整SWE-bench Verified水平。

下一步先查清“关系判断是否正确、方案为什么没执行、代码修好后为什么没交付”。然后分别检验：在同样的备选方案中，图信息是否帮助选得更好；有了可比较的结果后，C/N更新是否比不学习更有效。不同时改动多个条件后，把所有提升都归给项目图或C/N。
