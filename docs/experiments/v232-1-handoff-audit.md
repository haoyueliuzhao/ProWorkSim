# v232.1 交接复验｜一份合法示例和一次纠错机会

本轮追问上次 Sphinx-9591 实验中的一个具体问题。002 当时完成了诊断，向正确的收件人发出了以 `DIAG 74` 开头的工具调用，但多填了公开工具不接受的 `recipe` 字段。SDK 在语法校验阶段拒绝调用，002 随后用尽预算，001 没有收到这份意见。[上轮决策与拒绝记录](v232-osa-first-pair-audit.md)

## 实验怎样比较

在同一保存点新增一次续跑，与上轮已完成的 OSA 分支对照。原 OSA 的提名和证据原样复用：001 继续实现，002 独立诊断并向 001 交接。两次运行的原始检查点、组织图、DeepSeek Flash 非思考模型、T1 上下文、工具校验与官方评分相同。共享前缀是 4,027,970 token，原 OSA 决策是 1,910 token，两次执行成员都从 **970,120 token** 开始。本次实际付费仅包括新的成员及其历史摘要请求。[冻结条件和原决策身份](../../artifacts/software-benchmark-v232-1/handoff-r1/protocol.json)

修订包含两个同时生效的改动。

1. 002 完成首项可引用的证据工作后，在自己的会话中收到一次最小参数示例。示例使用本次实际的收件人、任务号和本人事件号，提示它以自己能支持的具体发现替换正文占位符。号码是否支持实际发现仍由成员判断。
2. 激活诊断时，在原团队上限内为一次纠错另留一个完整请求上界（131,072 token）。新职责、验证、交付三项原预留继续保留。只有 SDK 确认对当前待办任务的单个诊断消息调用因公开参数约束被拒，才把一次机会调给同一个成员。新请求由模型针对原反馈自行生成，再走原有校验。交接完成会释放未用预约；若一直未触发，原有优先机会已消耗且不足以保留两次完整调用或已无普通可运行成员时，释放预约供团队收尾。[实现](../../src/proworksim/software_handoff_v232_1.py)

进入真实实验前，使用真实 OpenHands SDK 和本地确定性响应重复三种情况。首次填写正确时，一条消息获项目接受，无纠错调用；首次多填 `recipe` 后自行改对时，获一次纠错并成功交接；两次都错时，仍只有一次纠错，项目接受消息为零。三项控制均验证了资源不足时拒绝激活，新增 API 费用为零。[SDK 控制凭据](../../artifacts/software-benchmark-v232-1/handoff-r1/sdk-control.json)

## 在线结果

**修订版的首次正式交接获项目接受。** 示例中使用了当时可引用的事件 68；002 后来选择自己的事件 75，向 `work_root` 的收件人 001 发送了 2,300 字符的诊断。调用只含 `recipient`、`task_id`、`body`。项目登记消息 78，并将诊断职责更新为 `handed_off`。原 OSA 和本次修订版都只产生一次正式发送意图，各自从同一现场独立生成。[调用、消息序号、接收者请求与评分凭据](../../artifacts/software-benchmark-v232-1/handoff-r1/results.json)

交接发生在第 80 次行动机会。001 随后的第 81 次机会触及预算边界，未能发出模型请求。因此可以确认诊断已经写入项目消息记录，尚无证据表明 001 读到、采用了诊断，或因此修复了代码。本轮每种条件只有一次生成，两项修订同时生效，不能从这一次成功推算成功率，也不能把它单独归因于参数示例。

**预留窗口暴露出一个边界问题。** 修订版在第 78 次机会结束时因剩余资源触及原定下限而释放了尚未触发的纠错预留。实际交接晚于释放；如果这次同样多填了字段，当时已没有专用纠错机会。线上验证了合法首次交接，格式拒绝后的恢复目前仅有 SDK 确定性控制证据。

据此增补了独立的 v232.2 调度修订：当只有未用纠错额度且诊断仍待交接时，普通调用继续扣除预留金额再计算可用量；临近边界，优先给有证据、可行动的诊断成员一次普通机会。公开参数约束、总预算和一次纠错上限继续生效。该修订通过了上次真实释放点（剩余 237,240 token）的回归检查，以及正确、改对、再次填错三条 SDK 路径。v232.2 尚未开展付费续跑。[预算保护实现](../../src/proworksim/software_handoff_v232_2.py) · [边界与 SDK 回归检查](../../tests/test_handoff_reserve_v232_2.py)

本轮新增 **889,440 token、1.54075296 元**，原账本累计 **108.75541768 元**，余额 **35.61924872 元**。所有请求已结算，执行环境和评分环境均有正常清理回执。下一次机制验证应同时检查“发送失败后有机会修正”和“发送成功后接收者有机会读取”，再看交接是否改变后续工程行动。
