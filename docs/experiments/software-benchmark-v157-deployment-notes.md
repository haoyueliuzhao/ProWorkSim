# v157 通信试跑的部署与环境边界

本文件记录执行层实现和准备过程，不报告模型分数。实验任务仍采用 v156 已获用户确认的 24 题、C0/C1/C2 各一次，共 72 个独立团队回合。Flask 1 题、Requests 3 题、其余 10 个仓库各 2 题；题目、seed、条件顺序和两波划分保持原冻结清单。每组始终是 REVIEW2 两名实际成员。三个条件仅改变通信呈现，`organization_id=REVIEW2` 与 `group_id=C0/C1/C2` 分别存储。

## 一、执行身份和预算

正式 slot 使用 `v157:<instance_id>:REVIEW2_Cx:<seed>`，保存原 `source_preparation_slot_id`，条件 ID 为 `DEEPSEEK_NT_REVIEW2_Cx_V157_B5000K`。本批固定整数索引 15700–15771；不同条件拥有独立的 episode、候选、官方评分请求和缓存身份。旧结果不作为本批生成或评分结果。

正式配置保留原 REVIEW2 的角色、私有历史、权限、公开测试入口、128K 级上下文和输出限制。每个团队共享 5,000,000 输入加输出 token，成员、历史摘要、压缩服务及真实 HTTP 重试共同计入；整批独立现金上限 500 元，由单个新 SQLite 账本管理。API 实际模型别名记录为 `deepseek-flash`，非思考；不宣称服务端权重版本可固定。此前准备元数据中沿袭的 `deepseek-v4-flash` 文本已在任何 API 调用前修正。

API provider usage 是总账；来源分项是明确标注的估算，不通过比例缩放冒充供应商精确分账。压缩服务不是第三名自主成员。

## 二、运行隔离与调度

最多 16 个生成 pair、4 个并行启动、2 个异步评分；每个 pair 含 4 CPU/16 GiB actor 和 2 CPU/32 GiB controller，评分容器 4 CPU/16 GiB，评分宿主子进程另有 4 GiB 地址空间限制并共用相同 4 核。普通用户协调服务 8 CPU/32 GiB、MemoryHigh 30 GiB、无 swap。全批并发预留上界 112 CPU/840 GiB，同时按实际可用内存、CPU负载和磁盘余量准入，不要求共享服务器完全空闲。

不新增 system slice，不修改共享挂载、网络、驱动、既有服务或他人对象。所有实际求解容器为 `network=none`、`cap_drop=ALL`、无宿主绑定、监听端口或 GPU。容器和卷只由当前批次持有并清理；异常不能清理他人的对象。

两波各 36 回合，调度入口按预先冻结的跨条件行顺序准入。生成和评分分别排队；每题错误进入异常记录，独立题继续。共享身份/账目冲突或无法证明写入及清理停止才暂停相关准入。第二波以第一波的真实请求原件、账本及 observer 完整性审计放行，审计函数不接受或读取模型分数；缺少证据时进入等待工程门，不把旧 CPU 控制结果当作第一波实测。

## 三、跨版本接口问题修复

旧执行器把组织名与实验分组视为同一字段，旧闭合器也只接受 `v142` 前缀。这会令已完成生成在导出时被误标技术未知。新闭合器独立核验任务、seed、通信条件与 REVIEW2 成员，不再借用旧 slot 身份。合法交付仍要求原来的同版本独立复核和提交证据；统一代码候选仍取结束时锁定的 member_001 工作树。

实际 controller、容器桥脚本和宿主 pump 均绑定新的 v157 FIFO。`/team-budget` 是独立计数的只读元数据路由；`/compressor-tokenize` 属于 count-only 路由；二者均不消费 512 次真实生成尝试。真实 HTTP 重试仍在统一账本中计数。帧大小继续受 32 MiB 上限约束。新增路由具备实际本地命名 FIFO 控制，部署 CPU 测试还检查实际被执行的 bridge 代码路径，不仅检查模块表面别名。

三个实际 Docker 零模型诊断与正式模型启动分开授权：分别验证 C0/C1/C2 的真实 SDK 导入、actor 操作、公开测试协议、私有成员注册和导出身份。诊断明确禁用真实 provider 账本绑定且不调用模型；正式执行必须启用共享 provider 账本。诊断通过不代表正式模型或通信效果已通过。

## 四、环境资格及发现的问题

本批 24 个任务的公开问题、base commit、actor image ID 和公开测试元数据均与 v156 清单逐项一致。22 题已有可核验的同镜像、同官方测试及基线 gold/empty 证明；继承需要重新检查原控制身份、结果和清理证据。Requests1142、1724 缺少对应资格，因此安排必要控制，不按模型表现换题。

本批 Requests 是 1142、1724、6028，不是前轮使用 httpbin TLS 修订的 1766、1921；pytest 是 5631、7521，不是以前做过离线 wheel 修复的 6197、10081。不能按仓库名自动套用旧环境修订或联网能力。

第一次控制启动被调用工具的文件系统/网络沙盒拒绝连接 Docker Unix socket，4 项均证明未创建容器。原错误、容量预约和清理证明已封存在 `environment-preconnect-recovery-r1`；在用户已有权限范围内，以可访问现有 Docker 接口的执行通道完成了首次实际容器控制，没有修改宿主配置。

首次实际 4 个控制容器全部完成清理，但尚未取得合格测试环境：Requests1142 在官方镜像初始工作树检查发现非干净状态；Requests1724 的任务解释器是 Python 2，旧隔离观测代码调用仅在较新 Python 提供的 `os.sched_getaffinity`，导致测试前失败。这是环境/观测问题，不能计为模型失败。后续恢复以新控制身份处理，原控制记录保留。总控制预留仍为 48：将 4 个已经精确复用且从未进入的控制预留改为这两题各 gold/empty 的独立恢复身份。

Astropy7336、Pylint6528 的既有官方测试路径 reset 修订也必须绑定到实际执行器，并按具体版本核验控制资格；不能只在安装说明中列出模块而让真正的 scorer 仍调用原始路径。最终环境资格以独立恢复记录为准，此文不提前宣称修复通过。
