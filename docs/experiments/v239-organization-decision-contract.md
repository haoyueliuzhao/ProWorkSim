# v239｜把「由谁负责」和「先做什么」分开，能否改善组织决策？

2026 年 11 月 25 日。**新合同能约束第一步的执行顺序，但整套决策的可靠性仍低于原分栏提示。** 在 28 次主测中，原方案有 22 份完整有效，新方案有 11 份。新方案这 11 份全部选对了第一步、执行人和工作包，但 14 个现场中有 13 个由程序只开放一个立即动作。该结果支持程序控制先后顺序，尚不足以证明模型自己学会了排程。v240 的真实 Worker 配对未放行。

## 改了什么

P0 直接使用 v237.1 的分栏提示。模型填写现有分工与备选分工，分别列出当前义务、后续检查和下一步，再决定是否改组。P1 保留同一个 OSA 和两个 Worker，把工作拆成四步。

1. **从回执建立任务依赖图。** 程序读取当前工作包、测试、合并、依赖和就绪记录，将工作标为可开始、被阻塞、进行中、已完成、证据过期、开放或未知。例如，工作包缺完成记录和独立复核时，两件事都尚未办完，但只有登记完成可以立即开始。
2. **由 OSA 作组织选择。** 模型比较原分工和可行的改组，选择维持、改组或等待证据，指出当前义务、唯一第一步、预期新增产物和重评条件。模型只需选择已列明的改动，无需再抄一份整图。
3. **把所选改动落实为版本化补丁。** 统一组织图登记 D0 成员、D1 角色、D2 工作归属、D3 协作、D4 依赖协调、D5 验证、D6 集成交付、D7 资源调度。注意新版 D1 是角色，D2 是工作分配，与旧编号的含义对调。本轮只开放原执行器已经支持、且当前预算满足的操作。追加诊断职责可以保留原工作包负责人；调度机会另计。D0 已登记，本轮固定两名 Worker。项目图保存依赖事实，组织图通过工作包和行动关联执行责任。
4. **校验后只释放一个动作。** 控制器核对原图版本、成员权限、测试证据、工作包和前置条件，按新分工解析执行人。在现场或图版本改变时，旧决策需要重新评估。此轮实际运行到动作释放检查；后续 Worker 是否真的履责仍待成对续跑。[组织合同实现](../../src/proworksim/software_organization_contract_v239.py) · [历史现场和 CPU 控制结果](../../artifacts/software-benchmark-v239/contract-r1/cpu-replay.json)

## 现场、参照和预算

计划 16 个现场，实际使用 **14 个真实现场、13 道题、8 个仓库**。已检索归档范围内的 205 个分支没有自然发生的「同版本反复就绪却未交付」案例；这次核对该范围没有更新。A5 的两个名额留空。已使用的现场均来自历史开发面板，对泛化能力的检验有限。另设一个明确未执行测试、工作包状态未知的模拟探针，单列结果。[现场与回执来源](../../artifacts/software-benchmark-v239/contract-r1/panel.json) · [A5 检索范围](../../artifacts/software-benchmark-v237/structured-decisions-r1/a5-inventory.json)

两名独立 AI 审阅者只读匿名现场材料，分别列出可接受的义务集合、第一步和分工决定。双方对首步的可接受集合在 14/14 个现场一致，义务集合在 9/14 个一致，分工选择集合在 13/14 个一致。第三名审阅者在调用模型前依据同一材料裁定，保留有依据的多个答案。q02 的冲突处理人依据观察者工作树推断，回执没有独立记录实际操作者。这是该项执行人标注的一处不确定性。[审阅一](../../artifacts/software-benchmark-v239/contract-r1/ref-one.json) · [审阅二](../../artifacts/software-benchmark-v239/contract-r1/ref-two.json) · [逐项裁定](../../artifacts/software-benchmark-v239/contract-r1/agreed-reference.json)

每个现场各运行 P0、P1 两次，第二次交换该现场的调用顺序。两组均用 DeepSeek Flash 非思考模式，单次输出上限 2,048 token，计费预约上限 8,192 个输入加输出 token。主测 56 次，探针 4 次，均已结算。整批最高预约 ¥3.93216，无重采。指标以每组 28 次为分母，无效回答在行动与义务指标计零。两次重复衡量同现场波动。[冻结协议与费用上界](../../artifacts/software-benchmark-v239/contract-r1/protocol.json)

## 为什么失分，修复了什么

**首要工程问题是解释文字限制。** 17 份无效主测答复中，14 份解释超过 650 字符，1 份重评条件超过 240 字符。已实现独立的接入修订，保留原文和 2,048 输出 token 上限，移除这两个字符门槛，所有行动、权限及图补丁校验保持原规则。对未改动的原始回答做零 API 回放，完整有效从 **11/28 升至 23/28**；首步及其执行人、工作包均正确也为 **23/28**。其余 5 份仍被拒：2 份选择等待却要求执行普通工作，3 份将已经完成的动作列为未履行义务。此回放保持原费用和原模型答案，不能覆盖正式成绩，也不能预测新表单下的生成行为。[修订入口](../../src/proworksim/software_contract_explanation_transport.py) · [回放结果](../../artifacts/software-benchmark-v239/contract-r1/transport-replay.json)

**义务判断仍是独立问题。** 放宽文字长度后，当前义务只从 7/28 升至 **12/28**。例如对连续失败的修复，审阅认为「查明原因、修复目标」是未履行工作，第一步是诊断。模型选对了诊断，却把修完后才需要的新版本验证也列为当前义务。任务依赖图能阻止提前执行；它并不会自动让模型正确区分当前欠缺的产物和未来验收。下一次真实验证值得优先检验这一点，并加入确实有多种就绪行动、非空改组能带来独立新增产物的自然现场。
