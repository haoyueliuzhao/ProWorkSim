## 3. 两个新合同及依赖证明

两目标使用原固定Marshmallow revision `c7b559a1fa3aba57ca6dba0ab336841c5038a782`，属于同一真实库的新开发合同，不是两个独立仓库或训练来源。

| 目标 | 共享库行为 | 应用消费关系 |
|---|---|---|
| directory | RecordSchema去name首尾空格，quantity转声明范围内的整数 | catalog输出有序规范records与整数total_quantity，保持重复、空输入及原输入 |
| name-index | NameSchema对声明ASCII名称去首尾空格并小写 | find_matches返回有序索引，export_names输出有序且保留重复的规范名称，保持空输入及原输入 |

完整声明范围与公开例子随工作区可见，独立输入在控制器侧。范围外输入、额外字段和未声明异常形状没有暗加验收。没有预置执行任务卡、责任分配、强制通信或强制双方编辑。

每个目标实际执行原始、只改Schema、只改消费者、联合参考四种程序，共8个变体。前三种未完成根目标，联合参考通过公开／独立完整验收。API跟踪记录Schema.load／dump实际调用和返回值，并把规范值与消费者结果逐项比较。四条真实SDK／WorldCore脚本路线分别执行集中完成和分支发布／导入，最终均有固定交付且R=1；实际决定数9、10、14、14，各实际run_tests一次。参考代码不进入模型提示、教师标签或训练材料。

验收将业务内容、规定过程满足、过程观测完整性分别记录。缺失API观测表示未证明满足，不改写成确定没有调用。收尾控制发现Python普通数值相等会接受整数位置上的浮点数，已改成保留JSON标量类型的比较，公开与独立验收使用同一类型规则；新增反控制拒绝float／bool冒充integer。输入保持判断同步采用该规则，防止把调用方整数原地改成等值浮点数后仍报“未变”。已有8个程序变体和4条路线的原始观测经新比较器离线复核后结论不变，未为此重执行它们；输入修改另有实际反控制。

## 5. 必要检查、失败历史及继承范围

合同去重6项CPU控制通过。新目标初始4项控制通过，但第一次SDK全窗口测试的脚本错误读取patch.actor_id（实际公开字段是author），在首条分支路线停止；前两条集中路线已通过，第四条未开始。修正的仅是CPU路线脚本。由于该固定四槽collector没有子库存／恢复入口，重新运行一次SDK全窗口时前两条也重新构建；最终4条全部通过。这些初始失败和重复CPU前缀如实保留，不合并冒充更多独立目标或模型证据。

类型比较与公开反馈修订仅增加对应控制和已有观测的离线重解释。公开反馈控制核对真实世界返回、原事件保存、版本guard、通过／失败诊断及成员调试输出。第一份native容量失败保留。公开反馈初版的94步通过记录另存；成员自测完整保留修订后，仅24个变化输入重新编码，70个输入的请求SHA逐项相等并复用前置证据。输入保持修订未改变纯反馈函数，最终helper函数hash和全部派生输出再绑定。差异计量曾在输出归档时遇到相对路径引用校验错误，未覆盖前置报告；修正归档路径后的通过回执与该失败历史分别保留。没有重做旧16样本审计、GPU资格、近16K训练压力或SDK世界路线。

控制器复用原数值实现、原common和既有实际学习接入证据；9B为原3／3步骤，Devstral为原0／0步骤。本轮未重新证明反向或增加更新，继承证据与新CPU检查分列。新控制器锁定2模型×2新root×2seed的8条T经历、原128／500000／32预算和四槽全量成本排序；技术未知不补成业务0。P2／P3须等实际结果后另冻训练用途来源、支持和公平探测清单。
