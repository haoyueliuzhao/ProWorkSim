# v223逐轨迹审查：为何只得到两题配对，后续应修什么

审查日期：2026年11月21日。范围仅为v223，不重复汇总旧轮次。此次只读取现有请求、工具回执、候选和官方评分，做了4次测试目标的静态编译检查；没有调用模型、重新评分或修改运行条件。

**结论：本轮执行与评分链路正常闭合，也观察到一次真实责任转交；但有效样本只有两题，且触发原因都是普通复核设置缺口。不能据此证明独立组织会话改善了任务结果，也不能把两题未准入简单归因于预算太小。检索、测试入口反馈、方案交接和冗余纠错均有明确改进点。**

## 1. 结果与实验条件

两名工作成员从相同的真实中途状态继续。W0以工作成员身份、带已见历史提出安排；W1由不带成员私有历史的独立组织会话提出安排。两组使用同一项目图、动作空间和官方评分，各自500万逻辑Token包含公共前缀、Graph审阅、方案生成和续跑。独立组织会话只提案，不能替成员修改代码或执行转交。

| 任务 | W0：工作成员提出安排 | W1：独立组织会话提出安排 | 审查结论 |
| --- | --- | --- | --- |
| Django-14792 | 未进入配对 | 未进入配对 | 接近200万前缀上限时，唯一测试调用被目标检查拒绝，没有执行测试 |
| SymPy-23950 | 未进入配对 | 未进入配对 | 接近200万前缀上限时，刚完成首个修改，没有调用测试 |
| Astropy-14182 | 选调整方案，真实转交并集成伙伴补丁；代码和交付均失败 | 选KEEP；代码和交付均失败 | 有决策及真实协作差异，未取得正向结果证据 |
| scikit-learn-13496 | 选KEEP；代码、交付均通过 | 选KEEP；代码、交付均通过 | 普通设置、实现和复核即可完成，不需要强行调整结构 |

有效配对中两组代码通过率和合法交付率均为**1/2**。另外两题保留为未取得合格中途状态，不能填成代码失败，也不能把有效子集的50%称为全部4题完成率。

两条Astropy续跑均触及预算边界；两条scikit-learn续跑均以合法提交结束。全部343个物理请求已结算，4条续跑均有明确官方代码评分，没有评分技术未知或执行完整性错误。

## 2. 两题为什么没有完成前缀准入

### Django：先定位和反复修改，测试发起较晚，目标错误后没有足够余量纠正

实际前缀40次API请求，消耗198.60万Token，其中输入197.96万、输出0.65万。按工作轨迹计有21次代码读取/检索，3次修改，1次测试调用。

第一处修改出现在累计约158.28万Token之后；测试调用时累计已达182.04万，只剩约17.96万。其目标为：

- `tests.utils_tests.test_timezone`
- `tests.db_functions.test_datetime`

接口将Django标签首段解释为`tests/`下的测试应用，因此前一个标签被映射到不存在的`tests/tests`。它返回通用的“所选路径不在当前源树中”，没有指出多写了一层`tests.`。后一目标也与真实代码目录不符：仓库中存在`tests/db_functions/datetime/test_extract_trunc.py`，不存在`tests/db_functions/test_datetime.py`。

零执行静态复核确认：`utils_tests.test_timezone`及`db_functions.datetime.test_extract_trunc`可以通过入口检查。也发现检查器只核对Django标签第一段，`db_functions.test_datetime`这个不存在的内层模块仍会通过静态检查；不能把“检查通过”说成测试一定能运行。

**归因：模型选错目标是直接原因；入口反馈不具体、标签检查不完整是可复现的接口缺陷；较晚才测试和累计输入消耗使纠错空间不足。不是Docker未能启动，也不是测试进程卡死。**

### SymPy：搜索分页未继续、符号定位偏离、两人重复探索，修改也没有解决核心行为

前缀38次API请求，共199.93万Token，其中输入199.34万、输出0.59万。23次动作是问题读取或代码检索，3次输出未满足单工具格式，只有1次代码修改，未调用测试。

关键链路：

1. 两名成员分别搜索`class Contains`，都得到“当前页无匹配、搜索尚未完成、附继续游标”。两人没有继续该游标，而是转向其他搜索或导航。
2. 两次`locate_work`分别返回6项和8项结果，首项都为`Boolean.as_set`；直接定义`Contains`的`sympy/sets/contains.py`均不在结果中。两人随后重复查看`boolalg.py`及邻近区域。
3. 代码级原因可以定位：当前导航只给含下划线或内部大小写变化的查询词额外“完整标识符”权重。`as_set`得到这一权重，单首字母大写的`Contains`没有。因此不能声称完整类名已获同等优先处理。这里证实的是本例检索遗漏，不是所有查询都失效。
4. 后期成员002提出接手剩余工作；成员001在尚无修改后测试证据时发起转交，被`joint_progress_required`正确拒绝。
5. 首次修改出现在累计196.75万Token时，只剩约3.25万。修改仅扩展了已有`NotImplementedError`的说明文字，没有实现`Contains.as_set()`的集合转换行为。

补充核查：初始分派用的`assign_work`、`offer_transfer`和`accept_transfer`在实际工具列表中可见；并非所有初始责任转交都要求先完成公开测试。本例选用了受中途进度门限制的`offer_joint_arrangement`，说明还需要把两种入口的用途解释清楚。

**归因：检索接口的分页/排序负担与模型没有正确使用分页共同造成定位浪费，口头协商也未变成合法接任；模型最后的修改本身没有解决问题。提高前缀额度可能给测试留下空间，但不能保证改对代码。**

### 为什么“200万Token”实际只支持几十次行动

Django和SymPy平均每次请求分别输入约4.95万、5.25万Token，最高达到9.18万、9.78万；输入分别占总量的99.68%、99.70%。每次读取、协商、修正格式都会重新带入上下文，而非只花一条简短工具指令的输出量。

按“这次请求最终返回什么动作”分组，Django的读取/检索请求合计约124.12万Token，SymPy约122.16万。这包括这些请求的完整历史和工具说明，**不是检索工具本身的净成本，也不能当作通信Token占比**。

因此预算确实形成了约束，但当前直接把上限调高，会连同定位和反馈问题一起放大成本。更合适的顺序是先减少无效行动，再单独比较是否需要增加前缀额度。

## 3. 两题有效配对实际发生了什么

### Astropy：转交成功，不等于协作修复成功

W0的候选把测试工作交给成员002。真实工具记录包含`offer_joint_arrangement`、`accept_joint_arrangement`、成员002修改测试并固定补丁、成员001集成补丁，因而不是只改了一条分工记录。

但W0后续的5次普通公开测试均失败；其中同一测试文件在修改后的不同版本反复执行，不能全部称为“重复测同一版本”。成员001另有2次测试报告游标错误。最终官方评分确认：新增的多行表头往返测试失败，原有正常写表测试也出现回归。后者表现为边框缺失和行首尾空格不符，属于实际代码错误。

W1选择KEEP，却在第一次`select_arrangement`中同时声称“保持分工”与“将测试工作转交”，后续两次转交均被`kept_arrangement_frozen`拒绝。这是模型执行意图与所选方案冲突，冻结规则本身没有失效。最终W1使现有9个公开测试通过，也完成了一个固定候选的独立复核，但官方新增的多行表头往返测试仍失败：类型说明行被当作数据转换，出现无法将`float64`转换为数值的错误。它不是单纯“代码已经正确但没有提交”。

两组都没有修好这一新增功能，W0还引入原有功能回归。单题不能证明转交导致回归，也不能证明OA避免了回归；能确定的是两条实际轨迹和失败版本不同。

评分日志仅用于本次事后审查，没有反馈给原工作成员，也不据此换题或改原候选。

### scikit-learn：两组都保留分工，完成了实现—测试—复核—提交

两组均保留成员001负责实现、成员002复核，补齐剩余工作的验证/协作设置，增加或修改公开测试，再完成合法提交。官方代码和交付均通过。

这说明当前受管接口具备完成完整交付的能力，也说明“有一项尚未设置复核者”不必然要求改变组织结构。由于两组选择了同一个KEEP，不能把该题成功归功于独立OA或组织结构进化。

## 4. Token差异主要来自哪里

以下平均只计算两题有效配对，包含共享前缀和Graph成本；未准入前缀费用另计。

| 阶段，平均每题 | W0 | W1 | W0减W1 |
| --- | ---: | ---: | ---: |
| 公共前缀＋共享Graph审阅 | 111.97万 | 111.97万 | 0 |
| 方案生成及合法性修正 | 16.21万 | 2.40万 | 13.82万 |
| 两成员后续求解 | 320.77万 | 319.13万 | 1.63万 |
| **合计** | **448.95万** | **433.50万** | **15.45万** |

两题合计差30.8962万Token，其中27.6302万、即**89.43%来自方案生成阶段**。W0带有工作成员已见历史，首个方案请求输入分别约9.00万、6.84万；W1分别约1.59万、1.42万。W0两题都进行了第二次纠错，W1只有Astropy进行了第二次纠错。

还发现一笔可明确定位的冗余：Astropy W0第一次已经生成有效首选，只是另一个方案不符合“实质结构变化”的要求。程序仍因这个次选错误发起第二次生成，消耗**92,919 Token**；最终选中的方案与第一次有效首选完全相同。该调用改善了未选方案输出格式，但没有改变实际选用方案，后续可在已有足够有效候选时停止生成。

这说明W1本轮更省Token主要是规划输入更短及纠错次数不同，**不是已经证明其工作分配使两名成员明显更高效**。缓存命中仍计入输入Token，已包含在上述数量中，不重复相加；现金价格会因缓存而不同。

全批物理消耗为1,939.4885万Token（输入1,931.5290万、输出7.9595万），峰值价格账本金额32.04676272元。四条逻辑续跑合计1,764.8892万，扣去重复计入的共享前缀和Graph223.9361万，再加两条未准入前缀398.5354万，恰等于物理总量。不能把四条逻辑总量与全批物理成本混成同一分母。

## 5. 项目图和组织推理的证据边界

**图确实持续变化了。** Astropy两条续跑分别有21、19个机会产生关系变化，scikit-learn分别13、13个；记录中也出现测试版本关系从当前转为历史的变化。一次真实转交和伙伴补丁采用有回执支持。

**但没有观察到新的复杂失配触发。** 两个合格保存点的`new_demand_ids`均为空，都是前面已经存在的`verification_gap`，在完成编辑及测试后才满足执行窗口。随后四条续跑没有新需求触发。它证明了“需求存在”和“允许动作”已分开记录，不能证明系统已经根据新的依赖阻塞、负载变化或冲突主动改组。

还有两项需要改进：

- **位置单位丢失。** 图把文件读取范围存成`start/end`，原含义是字符位置。scikit-learn的Graph解释却把4315–7236写成行号。引用编号校验通过，但解释仍不准确。该内容保留为E3假设，没有升级为事实；应在图中保留明确的字符/行号类型，并检查说明中的单位。
- **OA理由没有完整交接给执行者。** 生成器单独保存了OA对KEEP的具体解释，但候选包里的KEEP原因是通用模板，续跑只接收选中候选。工作成员仍保有先前的转交意向。执行指令已经明确KEEP不得改owner，所以不能说规则缺失；不过丢失具体选择理由可能不利于纠正旧意向，是否影响成功率需另做对照。

两次Graph审阅共生成9条E3解释，来源编号和工作引用合法；这不等于9条解释的语义全部正确。本轮没有独立标注集，不能给出关系或需求识别准确率。

## 6. 问题分类与下一步

| 分类 | 已确认问题 | 建议处理 |
| --- | --- | --- |
| 接口与实现 | Django错误不指出具体目标及标签根目录；内层标签静态校验不完整 | 给出失败目标、合法格式和公开目录依据，先用CPU例子验证；不提供隐藏测试入口 |
| 接口与实现 | 完整类名没有获得相应精确匹配权重；未完成搜索的空页容易被当成无结果 | 增加定义级精确定位，突出搜索未结束及继续入口，保持资源上限与权限 |
| 接口与实现 | 测试报告初始正文仅47字符，却并列大量逐测试证据，Astropy报告需17–23页 | 默认突出失败测试和错误摘要，完整证据按需读取；不是移除真实测试证据 |
| 接口与实现 | 有效首选存在时仍为无效次选追加纠错 | 满足已冻结候选需求即停止；保留无效次选记录，不重新采样已闭合回合 |
| 观测与交接 | 图位置缺少单位；KEEP具体理由未交给工作成员 | 采用有类型的证据位置；将选定方案、理由及当下允许动作一起交接 |
| 模型行为 | 忽略继续搜索游标、重复定位、错误测试标签、KEEP后仍想转交、修改未解决功能 | 记录为真实执行行为；不能全部归成系统bug，也不能宣称修接口必然消除 |
| 实验设计 | 前缀要求先形成编辑/测试证据，但初始任务集中于成员001；两个合格点均为普通设置缺口 | 在模型说明中区分已有的初始分派与中途联合调整入口；后续用独立任务验证真正阻塞等需求，不用强行缺设置制造样本 |
| 预算 | 每次大量历史输入使200万前缀只支持约几十次行动 | 先减少无效交互，再单独比较前缀预算；保持完整任务总预算及共享成本口径清楚 |

**建议判断：可以继续做针对性修订和小规模机制验证，不宜直接把本轮视为完整4状态科学准入、马上扩大v224/v225。**

下一步优先完成上述可复现问题的零API修订与CPU验证；随后另冻结少量真实前缀验证，核查能否可靠定位、合法测试、明确交接方案，并获得有证据的实际组织需求。已有运行保留，不补写结果、不按成功与否更换题目。涉及新模型尝试和预算分配时单列新批次，不能冒充本轮自然续接。

本次审查未修改实验运行实现，未新开任何模型或容器。C/N更新仍为0；“图维护”“一次转交”“跨任务策略学习”不能混为已完成的同一件事。
