# v0.15 UCI 来源接入与 CPU 工作可行性

本记录确认一个真实公开数据来源已成为可执行的有限工作场景。它**不报告模型工作能力、在线训练收益或方法增量**。模型与训练部分应引用本记录的来源身份，并在各自冻结协议下另列实际结果。

## 来源准入

原始资产：`runs/assets/uci-online-retail-v015/online-retail.zip` 和 `Online Retail.xlsx`。许可与出处见 [设计说明](../design/retail-work-v015.md) 和 [固定来源清单](retail-v015-source-manifest.json)。

| 对象 | 实际观察 |
|---|---|
| 原始 ZIP | 23,715,478 bytes；SHA-256 `f5385cbb54bbebf7196389109c6b0621faab0c304e3702548165e71c84aede8b` |
| 原始 XLSX | 23,715,344 bytes；SHA-256 `43465a06f2ccf7c8b5bd2892bc7defb52f97487934fe93b16ae4c3936424676d` |
| 扫描记录 | 541,909 行、25,900 个不同发票号 |
| 原数据缺客户行 | 135,080 行 CustomerID 为空 |
| 取消记录 | 9,288 行 InvoiceNo 以 C/c 开头 |
| 固定有界资产 | 9 片段、18 个互斥客户、54 个完整发票、274 条原始记录 |
| 单片段大小 | 26–36 行；包括元数据、schema与全行的 data 正文 7,860–10,187 bytes |
| 用途 | train/development/locked 各3片段，所有派生责任留在对应用途 |

官方页标记“无缺失”，而本次原 XLSX 扫描实际发现上述空客户值；此处报告字节上的观察，不因网站摘要覆盖观测。所选短工作片段只包含单一非空客户的完整发票，故不能声称已用真实缺客户记录验证模型的缺失处理。相关规则仍公开，独立函数控制覆盖了它；二者证据层次不同。

数据为真实素材；期间、统计政策、角色分工、私有依据、审批与错误提交是模拟。f2 日期截止后部分客户可能为零，这仍是公开合同下的真实数据结果。片段有意偏向短发票且要求取消与普通发票，不能作为源总体分布的无偏样本。

## 实际 CPU 验证

命令：

```bash
.venv/bin/python scripts/import_retail_v015.py --root runs/assets/uci-online-retail-v015
.venv/bin/python -m scripts.retail_work_experiment_v015 --output runs/retail-v015-cpu
.venv/bin/python -m pytest -q tests/test_retail_work_v015.py
```

54 条可行路径（36 基本 case，加上18条 pair/chain 请求式通信路径）全部在实际轮转与角色机会预算内完成各自责任，R=1。规则策略只使用公开观察和真实工具返回；其 SQL 是 CPU 可行性见证，未作为模型提示、SFT 或 RL 行动输入。路径的成功仅说明存在有限可行操作。

6 个负例均给出预定范围内的失败结果：

| 负例 | 实际 R | 原因 |
|---|---:|---|
| implement 写错发票数 SQL | 0.2 | 读取完成，独立正确构建/固定成果未成立 |
| 错误 review 无条件批准 | 0.25 | 读取完成，判断错误 |
| 错误 review 指向正确 CustomerID 格 | 0.25 | 位置没有实际差异，不能因提交错误而给任意问题信用 |
| 正确 review 不行动 | 0 | 准备读取与原提交不给当前 actor 信用 |
| pair 错误 SQL | 0.2 | 仅真实依据送达成立 |
| chain 错误 SQL | 0.2 | 仅依据送达成立，错误成果与批准不算完成 |

准备阶段发现并修订一处边界：最初 f2 错误金额在聚合内部 +1，若日期区间没有符合行，最终左连接零行会隐藏此错误。修订后在最终客户金额 +1，确保所有声明的错误金额复核确有差异。三个用途 f2-review 均按最终代码重新运行，实际产生 `supported_located_issue`，R=1。旧54+6原始回执保留，追加3条修订后复验；没有把旧证据重写成新代码结果。其余准备/奖励/公开工具合同未改变。

合计63个闭合CPU episode、831个规则决策。所有真实事件账本均通过实际 learner `joint_return`，结算位置与终局总和一致；这不是构造浮点账本的替代检查，也不是模型概率验证。18组 proactive/requested 的**准备业务状态哈希完全相同**，说明不同合法通信路径可以从同一业务情境启动；未测模型自然频数，不据此宣布方法支持。

新定向测试4项通过，覆盖 GBP与取消/签名数量、DISTINCT发票和重复原行、时间边界与零客户、客户/发票用途隔离、派生任务不跨用途、源码来源 pin 防替换、角色真正可见的数据与原字段。新增文件及触及 domain 注册的 Ruff 通过。没有重跑全部旧回归。

原始证据：`runs/retail-v015-cpu/`、`runs/retail-v015-cpu-refined/`。摘要：[路径与负例](retail-v015-cpu.json)、[真实账本](retail-v015-ledger-controls.json)、[准备状态配对](retail-v015-initial-states.json)。GPU/API 在本来源准备与 CPU 验证中均未使用；没有为模型自动修 SQL、补采用或补审批。

## 当前边界

- train/development/locked 是同一 UCI 家族内部用途；客户隔离不等于独立来源泛化。
- 接入为单项目四类短责任，其中 pair 是真实双成员，chain 是真实三成员；四项目 P0→P1/P2→P3 的相互接口反馈仍未实现。
- SQL 结果独立性、工作证据可追溯及规则可行性已经验证；模型如何使用这些实际字段、是否修改逻辑、能否正确构建/复核、更新后是否改善，仍须依据真实采样与训练后评价。
- 公开数据可能进入过基础模型预训练；新合同与信息布局没有消除这种可能。不得将本素材接入直接解释为 ID-VTDO 支持或学习成功。
