# 执行热路径缓存优化

更新日期：2026年11月18日。部署修订v214，业务合同继续采用v213。

针对大仓库回合缓慢的问题，已实现并验证三类缓存，接入新运行入口。**Matplotlib历史状态的固定热路径回放由71.18秒降至7.40秒，约9.62倍；落盘字节与审计哈希完全一致。** 这是本机一次工程基准的量级，不是完整模型实验的速度保证。

当前v213六回合已自然结束，本次未停止、重载或改写它们，也没有启动新的付费实验。下一批应使用`proworksim.software_organization_runtime_v214`，旧运行版本保留。

## 已定位的瓶颈

先前Matplotlib回合约71分钟时，准备约4分钟、累计API请求约2.5–2.8分钟，公测实际执行约20秒。其余主要是本地处理；这个粗分解未将所有本地时间归到单个函数。

进一步源码及基准确认：

- `StreamCachedStore`在每次保存后清除已提交状态缓存；下一次观察又使用低内存Python解析器读取整个状态。368MB历史状态一次解析约14秒。
- `_bundle`在一次观察与工具链中多次读取同一不可变仓库版本。Matplotlib版本包约122MB。
- 每次事务需要三个规范状态哈希。大型不变字符串重复JSON转义、编码；落盘又做一次相同编码。

本次没有减少事务审计、跳过权限检查或缩减工具反馈。

## 实现变更

| 改动 | 实际效果 | 一致性约束 |
|---|---|---|
| 提交后保留状态缓存 | 原子保存后保留与落盘值对应的独立快照，后续读取复制可变容器，避免再次解码大文件 | 缓存绑定自己写入的文件身份；保存失败清除缓存；外部替换触发失效；保留fsync及原子替换 |
| 不可变版本解码缓存 | 同一版本包只解码一次，后续返回独立可变副本 | 每次先检查actor权限及版本身份，再查缓存；文件身份变化或事务回滚后的版本重建不能命中旧值 |
| JSON字符串编码缓存 | 保存与三个审计哈希复用不变字符串的转义结果 | 保留原JSON格式、键顺序规则、有限数值校验、SHA256算法；不缓存整个可变状态的哈希 |
| 私有运行绑定 | 新世界选择优化后的store及事务函数，原业务工具继续使用 | 不修改历史模块全局变量或已运行对象，不修改模型提示、权限、预算、评分和交付规则 |

编码条目预算384MiB，仓库解码条目预算256MiB，另有一份已提交状态缓存和容器开销，**640MiB不是进程总内存上限**。本次Matplotlib编码工作集约233MiB；192MiB的初版缓存容量会反复淘汰，因此按实测工作集调整为384MiB。所有缓存均按新世界独立创建。

512MiB以内的冷状态采用标准JSON解码器；更大的冷状态保留原流式读取。正常命中后只复制可变容器，大型不可变字符串可共享。冷启动峰值内存需要在后续实际大批并发时观察，既有进程和批次资源上限继续有效。

## 固定热路径测量

输入为**已结束的v212 Matplotlib COMBO状态**，不是活动世界。368.2MB状态和122MB级版本包读取自历史原件；所有写入位于新建基准目录。两轮操作各包含：加载状态、三个规范哈希、一次原子保存、两次提交后加载、两次版本包读取。

| 环节 | 旧版平均耗时 | 优化后平均耗时 |
|---|---:|---:|
| 每轮开始加载状态 | 7.09秒 | 0.14秒 |
| 三个规范哈希 | 9.96秒 | 1.84秒 |
| 原子保存 | 3.72秒 | 1.03秒 |
| 两次提交后加载 | 13.68秒 | 0.29秒 |
| 两次版本包读取 | 1.14秒 | 0.40秒 |
| 两轮合计 | **71.18秒** | **7.40秒** |

首轮加载包含不同缓存状态，符合两种提交实现的差异；仅看第二轮，同一操作组合仍约快8.63倍。版本包首次读取包含缓存填充，第二轮两次命中约0.05秒。

每轮三个规范摘要逐项相等，最终状态文件SHA256相等。最终优化回放复用已保存的旧版基准，未为同一旧路径重复运行；两轮不是同时测量，系统负载可能影响精确比值。旧版、初版缓存和最终回放记录均保留，不能据此承诺每个真实回合提速9.62倍。

测量脚本：`tools/benchmark_world_hotpath_v214.py`。原始基准位于`runs/software-benchmark-v214/hotpath-benchmark-r1`和`hotpath-benchmark-r2`，可审阅数据：[基准摘要](../../artifacts/software-benchmark-v214/performance-admission-r1/benchmark.json)。

## 必要一致性验证

四项CPU控制已通过：

1. Unicode、转义、数字、元组及键归一化的落盘字节／摘要一致；非法值失败不覆盖已提交状态；外部原子替换和版本文件变化会使缓存失效。
2. 同一初态下，工具定义、观察、工具结果、拒绝与请求重放一致；缓存预热后，另一名已注册成员仍不能读取作者的新私有版本。
3. 实际公开pytest、固定候选独立复核、显式合并和合法交付通过。
4. 写入后、提交前的故障可回滚；相同版本号重建不会读到旧缓存；落盘提交后模拟中断，重试同一请求不产生第二次效果。

比较业务状态时仅排除墙钟时间及由其变化产生的状态摘要字段；摘要算法本身另以相同输入逐字节验证，未省略业务字段。实际时间变化是优化目标，不能要求跨执行的墙钟字段相同。

此外完成一次真实SDK保存→新进程恢复→公开pytest→独立复核→合法交付控制：前缀1次、恢复段4次实际CPU公测；恢复段32个脚本响应，供应商API调用0、Docker调用0。容器执行协议未改，因此沿用v213已通过的隔离Docker验证，没有重复建容器。

恢复段记录状态缓存命中292次、冷加载1次、成功保存缓存58次；版本包命中363次、解码5次。脚本响应中的Token是合成控制值，不计入模型成绩或现金消耗。[准入与控制证据](../../artifacts/software-benchmark-v214/performance-admission-r1/admission.json)

## 新版本使用与剩余边界

新部署导入`software_organization_runtime_v214`。它保留v213的`CONTRACT`、工具、模型业务版本和执行策略，在创建新runtime时自动安装私有性能绑定；`DEPLOYMENT_VERSION`单独记录v214部署修订。缓存不进入模型工作区，不提供跨成员私有信息访问能力，也不授权新的模型回合。

本次只改变本地处理方式，未增加API费用、GPU占用或共享服务器配置变更。旧v213模型结果及费用记录继续使用原版本，不按优化后耗时回填。

完整回合仍包含模型延迟、公开测试、文件同步、SDK记录和协调流程。后续首个实际批次应分别记录API耗时、测试耗时、每次机会耗时和缓存命中，确认端到端收益；不能用热路径基准替代真实端到端测速。
