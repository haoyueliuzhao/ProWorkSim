补充优化 kernel 会改变实际数值执行路径，可能涉及精度、归约顺序与后续采样轨迹。若以后评估，需要独立的实现版本和准入，核对输出、token/采样轨迹、RNG、计费及环境身份，再明确区分结果修订。本轮没有安装这些依赖，没有把依赖替换混进原配置成绩。

## 低风险优化优先级

1. 保持现有三卡五会话连续派发，并将局部执行/评分异常留在异常集合，避免它们阻塞健康资源。全局 source、policy 或不可变准入证据损坏仍属于共享完整性故障。
2. 继续复用已有有界 CPU 预准备和独立评分。当前正常评分没有积压，不支持为了“加速”修改两评分槽、4 CPU / 16 GiB 限额或评分标准。
3. 宿主侧可评估小 JSON、记录处理和候选收尾开销，但有限样本中的 turn 外层差额只有约 2%–3.5%。任何后续异步收尾都必须保留唯一候选边界和既有资源限制；本文没有实施这类变更。
4. 优化数值 kernel 作为单独准入工作，不与上述宿主调整合并，也不据库警告预告倍率。

## ETA 的适用边界

当前给用户的谨慎规划区间是**流水线恢复后约 2–4 天**。这是条件外推，不是统计置信区间或保证；它不计过去的升级停机，未来故障、CPU 重型测试和共享显卡争用可能延长时间。

估算基点是 16:57 CST 的既有状态：剩 REF 456、MATCH 490、PROJECT 490。GPU6 的早期 MP 样本速率为 13.448/h；REF 的早期 15 回合 / 42.027 分钟约为 21.415/h。提出该 ETA 时，GPU3 已于 18:35:53 CST 注册准入，但其正式任务吞吐尚未实测；这比 16:57 的剩余任务计数基点更晚。不能直接赋予它“与 GPU6 完全相同”的实测速率，后面的近期单请求计时也不构成任务吞吐对照。

本报告**不假设 REF 结束后 GPU7 自动转跑 MP**。只保留两张 MP 卡时：假设 MP6/MP3 分别为 13.448/10 回合每小时，剩余 980 个 MP 回合约需 41.8 小时；若为 8/6，则约 70 小时；长尾压力假设 6/4.5，则约 93.3 小时。这些 GPU3 数值是明确情景假设，不是新的观测。REF 对应情景约 21.3–32.6 小时，仍须完成全部官方评分和异常闭合。

原 provisioner 的 REF→MP 门要求全部 500 个官方评分已知。一个延后处理的评分未知仍可能阻挡转卡；需在后续异常集合或单独明确的资源转接流程中处理，不能靠把未知填成失败来获得容量。实验分母、逐题状态和运行修订仍须保留，完成速度不替代能力指标。
