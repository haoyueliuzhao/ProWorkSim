# v068：恢复实验与并发瓶颈

本次继续原 Verified 500题、两模型、REF／PROJECT、5M／7.5M／10M 的12组6000回合计划。模型可见设置、题单、seed、评分标准和DeepSeek 1500元总预算不变。它是运行修复，不是新增实验条件；旧结果与异常原件全部保留。

## 为什么再次停队

10月28日约10:53，Requests-1921环境控制在容器已被官方评分器删除之后读取CA末态，得到404。私有克隆的评分函数持有另一份清理绑定，原TLS包装器未钩住实际执行的清理函数。CA测量缺失被混入资源清理错误，造成两项grader预约未释放，并使Qwen主队列停止。旧API协调器随后拒绝新的模型请求，但仍创建环境，进一步产生无模型请求的失败记录。

已根据两个准确容器ID的独立只读404证据释放这两项原预约；未删除其他容器，也未把缺失的CA证据改写成有效评分。新的TLS钩子在实际评分函数的清理绑定上工作，先完成CA／relay收尾，再删除容器。评分是否可信和资源是否已清理分别判断。具体证据与边界见[TLS修复说明](software-benchmark-v068-tls-lifecycle-recovery-r1.md)。

## 如何恢复

新的恢复库存合并v064原记录、v066 R3的Qwen记录与v067的API记录。主协调器为Qwen生成及剩余环境控制服务，API协调器独立生成并异步评分。两者继续使用同一个资源预约锁和原物理创建身份；不重复模型调用，不覆盖原报告，不将主协调器中的API暂停占位记录覆盖API真实结果。

已消费环境身份但零模型请求的任务单独留在恢复异常集合。`entered=true`在旧队列中表示进入过环境流程，不能据此声称调用过模型。恢复库存还单列已有半组环境控制的完成证据，继续尚未消费的另一半，避免重复运行已完成控制。

Qwen使用原BF16检查点与131072上下文、32768输出、0.6显存预约。当前恢复最多同时保留两个驻留，使用原尚未消费的模型服务身份；容量不足则等待。此前已停止并释放的GPU UUID可以重新选择，旧服务身份不会重启。各驻留仍须通过原完整上下文缓存容量准入。

## 并发为什么不能直接改成30

2026-10-28核验的[DeepSeek官方文档](https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit/)列出Flash每账户2500并发。本项目API内部上限为64，因此30路远端请求本身不是当前障碍。

| 限制 | 本轮数值 | 影响 |
| --- | ---: | --- |
| 原API固定生成并发 | 4 | 新调度已移除这个固定瓶颈 |
| 新API期望并发 | 32，可配置1—64 | 只是调度目标，不冒称实际已达到 |
| 共享环境槽 | 12 | Qwen和API共用；当前最直接的本地上限 |
| 每题actor＋controller预约 | 6CPU、32GiB | 30题仅环境即需180CPU、960GiB |
| 项目全部角色合计上限 | 152CPU、832GiB | 包含Qwen驻留、生成、评分与协调器 |

所以当前profile无法安全承载30个完整环境。新API调度每3秒按实际活动预约、CPU／RAM／磁盘余量计算准入，已有任务不因下调并发而被取消。原controller曾在4GiB限制下OOM，本轮保持16GiB，不为达到并发数字直接缩小限额。资源等待属于正常状态，不得消耗一个任务身份后再将其记为模型失败。

统计同时显示期望并发、资源允许并发、真实环境数、实际API inflight，以及各项限制原因。API请求数与任务数不同：环境准备、工具执行和测试期间不一定有API请求。详细调度与CPU控制见[API队列说明](software-benchmark-v068-api-queue-design.md)。

进一步只读审计了197份既有结果、1198份元数据：尚无可靠的内存峰值或逐工具CPU耗时记录，不能用“没有OOM”证明可以降低限额。15个已闭合API回合中，controller生命周期中位数约463秒；请求预约时间覆盖中位数约53%，其余时间仍包含环境与工具工作，不能直接称为CPU空闲。具体统计、边界及30路所需的条件见[并发瓶颈审计](software-benchmark-v068-concurrency-readonly-audit.md)。另有1项既有Qwen PROJECT异常已定位为SDK删除合法null参数，与预算无关；尚未热改正在运行的冻结配置，见[接口异常分析](software-benchmark-v068-sdk-null-cursor-analysis-r1.md)。

## 数据与安全边界

原唯一现金账本继续使用 `runs/software-benchmark-v064/full-verified-r1/api-budget/ledger.sqlite3`，准备及既有正式调用费用仍在总额内。新scope没有新开1500元预算。所有组继续保留完整500题分母，未知、未准入和未开始不会填成0分或混入已完成子集均值。

新协调器使用普通用户服务，分别4CPU／16GiB；辅助协调器显式计入原共享预约池。只使用原授权的隔离Docker路径与剩余资源身份，原共享服务器hold保持true，不改宿主挂载、网络、驱动、守护进程、其他用户服务或任务。启动、资源与进度以 `runs/software-benchmark-v068/recovery-r1/` 中运行凭据为准。

本次另完成固定组织人数修订：DIALOGUE／REVIEW为2人，SOP／COUNCIL为3人，CHIEF／PEER为4人。该项只有实现与CPU验证，真实协作评测仍未启动，见[组织审阅文档](software-fixed-organization-v065-review.md)。
