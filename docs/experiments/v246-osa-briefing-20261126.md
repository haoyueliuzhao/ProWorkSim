# 代码修复遇阻时，调整团队分工有用吗？

**ProWorkSim 实验汇报｜2026 年 11 月 26 日**

同样的 7 道历史失败题，允许组织策略 Agent（OSA）在任务中多次调整分工后，团队从**修对并交付 3 题**提高到**修对并交付 4 题**。新增通过的是 Sphinx-9591，原先通过的 3 题全部保住。平均每题 token 消耗增加约 **0.64%**。本轮验证了团队能在遇阻后改变工作方式；要判断这种调整能否稳定提高通过率，还需要更多同条件对照。

## 一、项目图怎样识别异常

项目图记录工作包、成员、代码版本，以及该版本的测试和交付结果。组织图记录谁负责实现、谁检查、成果交给谁、接下来由谁行动。两者通过**工作包和版本**关联。例如，甲修改了代码，乙在自己的旧版本上测试通过，项目图仍会保留甲的新版本上的失败记录。OSA 据此判断继续由甲排查，还是请乙承担一项具体诊断。

| 异常 | 团队看到什么 | OSA 需要判断什么 |
| --- | --- | --- |
| A1　反复修复失败 | 修改后，同一个测试仍然失败 | 原负责人还有明确的下一步吗？伙伴能否提供独立的复现或定位证据？ |
| A2　上下游依赖阻塞 | 下游成员要用上游补丁，但尚未拿到可用版本 | 上游还需完成工作，还是只差交接或下游采用？ |
| A3　集成冲突或回归 | 两份修改合并时发生冲突，或合并后原本通过的测试失败 | 谁处理冲突，谁检查合并后的版本？ |
| A4　缺少必要验证 | 已有候选补丁，但缺少当前版本所需的独立复核 | 谁能检查这个版本，并把接受或返修意见交给作者？ |
| A5　交付停滞 | 团队反复查看交付清单，却迟迟没有完成提交 | 最后卡在哪一步，由谁完成测试、固定版本或提交？ |

**最新 7 题主要验证了重复测试失败的触发机制。** 同一目标在两个不同代码版本上失败，或同一版本实际运行三次仍失败，都会触发重评。连续三次失败但目标各不相同，则记录为测试持续受阻，保留对根因的判断。OSA 也可以判断工作进展正常或现有证据不足，维持当前分工。其余四类用于描述和识别其他现场，本批没有逐类验证其收益。[异常规则及历史回放](v246-project-failure-replanning.md)

## 二、组织图可以调整什么

| 维度 | 对修题工作的具体影响 |
| --- | --- |
| D0　成员人数 | 本轮固定两名执行成员。OSA 管分工，代码仍由这两名成员修改。 |
| D1　角色职责 | 作者继续修复，伙伴临时负责诊断并返回证据。 |
| D2　工作包归属 | 将一项尚未开始的工作整体交给另一人，由新负责人完成。 |
| D3　协作关系 | 指明谁需要和谁配合、发现应反馈给谁。 |
| D4　依赖交接 | 指明上游要交出哪个版本的产物，以及下游怎样核对和采用。 |
| D5　独立复核 | 明确由谁检查指定补丁，并对该版本给出接受或返修意见。 |
| D6　集成与交付 | 合并出问题时，明确谁解决冲突、谁验证整合结果，再推进交付。 |
| D7　行动机会 | 为新责任人及后续验证、交付预留实际行动机会，让被分派的人能动手。 |

一次调整可以涉及多个维度。**Sphinx-9591** 开始由成员 001 实现。第 12 次行动时，OSA 维持分工。第 47 次行动时，项目图显示同一属性文档测试反复失败，OSA 保留 001 的实现责任，给 002 增加独立诊断职责（D1），明确反馈给 001（D3），并为诊断留出行动机会（D7）。002 发回诊断，001 读后确认与自己的判断一致，随后修改、测试并提交。该题从未通过变为通过。这个过程说明诊断确实进入了工作流程；现有记录无法判断缺少这条诊断时作者会怎么做。[线上决策和逐题记录](../../artifacts/software-benchmark-v246/remaining-seven-r1/results.json)

## 三、同题实验带来了多少收益

从原先选定的历史失败题中，取同样 7 题比较。两种配置都使用 DeepSeek Flash 非思考模式，两名成员从原始仓库和空白会话开始，每题共享 500 万输入加输出 token，OSA 的开销也计入其中。**单次 OSA** 在第 12 次行动机会起安排一次分工判断；**多轮 OSA** 采用修订后的提示和现场证据展示，允许后续异常再次唤起判断，每题没有固定次数上限。

| 同一批 7 题 | 入选时最近一次评分 | 单次 OSA 重测 | 多轮 OSA 重测 |
| --- | ---: | ---: | ---: |
| 最终代码通过官方验收 | 0/7 | 3/7（42.9%） | **4/7（57.1%）** |
| 正式提交的版本通过验收 | 选题只核对代码 | 3/7 | **4/7** |
| 平均每题实际 token | — | 396.43 万 | 398.98 万 |
| 7 题实际费用 | — | 44.94 元 | 45.35 元 |

**从第一次重测仍失败的 4 题看，本轮修回 1/4。** 七题共发生 7 次例行判断、3 次异常重评。三次重评都把独立诊断交给了伙伴，最终结果有所不同：

- **Sphinx-9591：未通过 → 通过。** 负责人收到并采用诊断后完成修复，这是本轮唯一新增通过的题。
- **Django-15916：通过 → 通过。** 第 41 次行动后，伙伴帮助定位新加测试及其入口的问题，负责人确认采用并最终提交。
- **Matplotlib-25960：未通过 → 未通过。** 第 57 次行动后，伙伴发回诊断，负责人也确认采用；后续测试仍失败，最终没有合法提交。

**如何解读。** 这组实验直接比较了两套 OSA 配置，同题净增 1 题。单次与多轮配置同时改变了提示、证据展示和决策时机，每题每版各独立运行一次，因此不能把增加的 14.3 个百分点全部归因于多轮调度。要单独估计再次决策的收益，可以固定新版提示和工具，从同一失败现场分成两支，一支继续原分工，一支允许 OSA 再次判断。

两题曾因 API 余额中断，均已恢复并取得最终评分；表中费用和 token 含原中断产生的消耗。此前另 5 题采用单次决策配置，已单列。[完整实验报告](v246-1-remaining-seven.md) · [含提示词原文的审计材料](v243-v246-2-pending-audit-20261126.md)
