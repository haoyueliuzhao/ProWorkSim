# 四阶段人工协作架构（P4）：结果与轨迹专项分析

分析日期：2026-10-18。只抽取已存结果与轨迹，没有启动模型、测试、分词或新验收。范围是 8 条原组织比较运行和 4 条输入表示配对运行，共 12 条 P4；另抽取必要 S1/P2 对照。本文所说“下降”是小样本描述差异，没有作统计显著性判断。

## 核心结果

P4 是人工预设的串行四阶段架构，不是四名成员自由协商组织。12 次中 2 次成功，10 次失败均未形成固定最终提交；没有“已提交但被独立验收判错”的 P4 失败。10 条失败的最后一名验证者中，7 条以硬上下文拒绝结束，3 条以共享团队 token 预约不足结束。这个 7/3 分类只说明最后一次资源终止，不能替代更早的候选缺失、交接缺失、权限错误和重复工作分析。

|---|---:|---:|---:|---:|---|
| 原表示，25 万团队预算，LA/HA/LB/HB | 0/4 | 0 | 234,162.75 | 4 | 3 次 context_capacity；1 次 shared_total_tokens |
| 原表示，50 万团队预算，LA/HA/LB/HB | 0/4 | 0 | 445,538.00 | 5 | 2 次 context_capacity；2 次 shared_total_tokens |

同一原比较中，单人 S1 在 25 万、50 万预算下分别为 1/4、1/4，P2 双阶段在 25 万下为 1/4，P4 均为 0/4。增加 P4 团队预算后平均消耗从 234,162.75 增至 445,538（+90.3%），未增加成功数。修订表示 Γ1 下 P4 与 S1 都为 2/2，但 P4 平均 430,639.5 token，S1 平均 143,857，P4 为 2.99 倍。不同输入协议不能合并后用于因果排名。

## 架构具体是什么

| 顺序 | 成员 | 人工指定职责 | 团队总 token 的本阶段新增释放比例 | 25 万预算新增额度 | 50 万预算新增额度 | 允许修改代码 | 允许最终提交 |
|---|---|---|---:|---:|---:|---|---|
| 1 | member_001 | implement：实现 | 35% | 87,500 | 175,000 | 是 | 否 |
| 2 | member_002 | review：复核 | 20% | 50,000 | 100,000 | 否 | 否 |
| 3 | member_003 | revise_integrate：修订/集成 | 25% | 62,500 | 125,000 | 是 | 否 |
| 4 | member_004 | validate_submit：验证/提交 | 20% | 50,000 | 100,000 | 否 | 是 |

每阶段对应一名成员；决定/attempt 上限为 44/26/32/26，公开测试额度各 8 次。预算按**累计释放额度减去团队实际消耗**计算，早期未用额度可向后顺延，不能向前返还，不是四份独立个人预算。成员均拥有各自从初始树开始的工作区：上阶段的编辑不会自动变成下阶段的代码；要先 `fix_patch` 发布，再由接收者明确 `adopt_candidate` 或在允许的阶段 `integrate_patch`。`review` 和 `validate_submit` 禁用 `write_file`、`replace_file`、`integrate_patch`，但允许整候选 `adopt_candidate`；非最终阶段禁用 `submit_integration`。前阶段结束后不能回到该成员修改。

定义位置：`src/proworksim/stage_budget_v047.py:17` 与 `src/proworksim/software_organization_v047.py:268`；证据 JSON 的 `/architecture` 同时保留原运行中的 `stage_plan`。这是一种有独立工作区、显式候选交接和不可逆阶段顺序的人工流水线，不能解释为自由组织能力的直接测量。

## 可直接复核的代表性轨迹

下面的 `outcomes/N` 均为原 `slot-result.json` 的 `/boundary/outcomes/N`，不是人工重演。证据 JSON 每个动作保留该原文件相对路径、JSON 指针、模型调用 ID、动作参数摘录、原反馈与状态。

### 1. 已做完实现，却没有提交权限

`org47-A-r0-P4-B250000`：

- `outcomes/2`：member_001 写入 UTC 转换修复；`/3` 的公开测试 `passed=true`；`/4` 发布 `patch-1`。
- `/5` 请求 `submit_integration`，参数 message 为：`Fixed utc_date_key to properly convert timestamps to UTC before extracting the date, including handling day/month/year rollover. All tests passed.`
- 同一动作原反馈：`code="architecture_stage_permission"`，`message="This operation is unavailable in your current architecture stage"`。
- `/6` 下一次调用预约因阶段余额不足拒绝：可用 4,156 token，而请求为 14,225 输入 + 2,048 输出预留。之后进入复核阶段。
- member_002 在 `/8` 采用 `patch-1`；member_003 却在 `/12` 从自己初始 `v1` 读代码、`/13` 再次实现、`/14` 通过公开测试，随后 context 拒绝，未发布。
- member_004 在 `/18` 测试自己的初始 `v1`，失败，随后 context 拒绝。

直接支持：实现、候选交接、最终提交不是同一件事；固定权限和阶段闭合放大了交接缺失。不能把一次公开测试通过追认为独立验收成功。

### 2. 最终验证者发现需要改代码，却被人工权限约束

`org47-B-r3-P4-B500000` 的 `outcomes/31`：member_004 请求 `write_file`，path=`migration.py`；原反馈仍为 `architecture_stage_permission` / `This operation is unavailable in your current architecture stage`。之后 `/32`–`/34` 再次列文件、读取 `migration.py` 和 `rule_v2.py`，`/35` 团队 token 预约不足，未测试、未提交。

其他同类原件包括 `org47-A-r2-P4-B250000` 的 `/18`（验证者 `replace_file rules.py` 被拒绝）和 `org47-B-r0-P4-B500000` 的 `/24`（验证者 `replace_file event_time.py` 被拒绝）。12 条 P4 共 10 次确认为架构阶段权限拒绝。这个计数只说明规则与模型动作发生冲突，不代表 10 次独立失败；Γ1 的两条成功运行也发生 4 次此类拒绝。

P2 对照 `org47-A-r0-P2-B250000` 中，第二名成员将复核、修订、提交合并在同一阶段，可以在自己的工作区修复：`outcomes/9 replace_file` → `/10 run_tests passed=true` → `/11 fix_patch` → `/12 submit_integration` → `/13 finish_stage`，最终 12/12 验收通过。该例没有整候选采用，而是第二人重新实现，因此它说明“有修改和提交权限的单一后阶段可以闭合流程”，不证明前后分工带来因果收益。

### 3. 输入容量直接阻断了已经接近交付的流程

`org47-B-r0-P4-B500000` 的 member_004：`outcomes/25 adopt_candidate patch-1` → `/26 run_tests passed=true` → `/27 model_budget_exhausted`。真实拒绝是 `context_capacity`，请求输入 16,816 + 输出预留 2,048 = 18,864 > 固定容量 18,432；不是总 token 已耗尽。此时团队只消耗 371,082 / 500,000 token，仍余 128,918。

表示配对的 LA Γ0 同样存在完整原链：`org48-LA-P4-G0-B500000` `/19 adopt_candidate patch-1` → `/20 run_tests passed=true` → `/21 model_budget_exhausted`。输入 16,485 + 2,048 = 18,533 > 18,432，仅超出 101，但没有实际生成；末次测试反馈 `feedback-468` 未能进入同成员下一次真实生成，团队仍余 228,474 token。来源为 `software-organization-v048-final.json` `/slots/2/last_executed_member_test_followup` 和 `/slots/2/rejections/2`；原边界经验序号 481（JSONL 第 482 行）。

直接支持：增加团队总 token 不能解决单次请求的 context 限制；流程达到公开测试通过，也可能在固定最终提交前中断。

### 4. LB Γ0 已有与 Γ1 成功树相同的文件，但没有形成合法交付

但它采用后整文件树的记录哈希，与 `org48-LB-P4-G1-B500000` 最终成功交付的哈希完全相等：

`0b57edcdcdb36e0169d50390e7421e40407a98c7a6073a6fe2970e464bf20fe6`

## Γ1 恢复交付说明什么

Γ1 把同一输入中的严格重复内容替换为可还原引用，保留原内容、权限、模型、18,432 context 容量、2,048 输出预留和团队预算；它不是新增人工角色或增大上下文模型。原表示的 2 条 P4 共 6 次 context 拒绝发生在复核、修订、验证三个阶段；Γ1 的 2 条变为 0 次。

- LA Γ1：`outcomes/27` 验证者采用 member_003 的 `patch-1`，`/28` 本人同版测试通过，`/29 fix_patch`，`/30 submit_integration`，`/31 finish_stage`。正式验收 12/12。
- LB Γ1：`outcomes/24` 验证者采用 member_003 的 `patch-2`，`/25` 本人同版测试通过，`/26 fix_patch`，`/27 submit_integration`，`/28 finish_stage`。正式验收 10/10。

对应的最终测试反馈都真实呈现给后续生成；候选采用、本人同版测试、固定最终提交的文件哈希绑定完整。正式成功由 0/2 变为 2/2，支持输入表示影响该架构能否闭合交付的判断。由于换表示会改变后续生成轨迹，不能将每个差异简化为同一条确定动作链的单因素重播，也不能推断所有 P4 失败都由 context 造成。

Γ1 仍保留明显流程开销：LA 实现者反复测试但没有发布，复核者采用未知 patch 被拒绝后测试初始树，修订者重新实现；LB 复核者尝试被禁用的 `integrate_patch`，修订者同样从自己的初始树重新修复。最终交付恢复不等于四人组织获得净收益：同表示的单人也 2/2 成功，成本约为 P4 的三分之一。

## 有证据的原因与仍待验证的改进

1. **有直接证据：显式候选交接经常未完成。** 原比较 8 槽中 5 槽没有固定 patch，7 槽最终验证者没有采用候选而保留初始树。输入可见、成员阅读、前人编辑都不能替代版本交接。
2. **有直接证据：人工权限和串行阶段阻止成员自行补齐后续工作。** 实现/修订无法提交，最终验证不能改代码；原请求与拒绝保存完整。权限冲突不是唯一原因，因为成功组也发生冲突。
3. **有直接证据：context 容量在公开反馈和后续工作之间中断了流程。** 最终验证者 7 条失败以该方式结束，其中 LA 例存在“采用—测试通过—反馈未呈现—无提交”的完整链。
4. **有直接证据：阶段预算和重复读取压缩了有效修改/测试/发布机会。** 高难 HA/HB 的高预算运行均没有固定候选、没有公开测试，不能用 context 一个因素解释。
5. **建议，尚无新实验验证：** 后续优先让候选交接成为明确的阶段产物，让最终负责人具备有约束的修订能力，减少无候选情况下的空转阶段；使用已验证的重复引用表示。是否需要取消阶段、调整比例或授权返回前阶段，应作为事前冻结的独立比较，不能据现有轨迹声称一定提高成功率。此次只分析旧结果，没有开展这些新实验。
