# 四人独立候选策略 I4：结果与轨迹原因分析

**分析日期：2026年10月18日。范围：已完成的冻结模型 v047 I4 八槽，辅以同面板 I2、S1 对照。只读取已有结果及原始轨迹，未运行新模型、测试或验收。**

I4 的主要问题分为两层：**低预算下，生成者在固定候选前就被分支预算阻断；提高预算后，部分任务能产生候选，但选择者仍可能停留在重复读取，未完成采用和提交。** 八槽中仅一槽正式提交并成功，另外七槽都没有正式提交。因此现有证据不能概括为“四个候选都写错了”，也不能将所有失败都归于预算。

## 结果及组织架构

I4 是人工预设的“4个隔离生成分支 → 原成员001选择”的架构。四个成员各自从初态求解，生成阶段不能互读分支；每人生成阶段最后固定的一份补丁进入候选池。生成总份额为团队预算的70%，四人等分，因此25万团队预算下每位生成者仅有43,750 token，50万下为87,500 token。生成分支之间不能借额，未用额度只转入选择阶段。

选择者仍是原成员001，不新增第五人。它可读取、采用和测试生成阶段冻结的候选，但不能编辑或合并代码；最终提交必须与最近一次采用的候选完全一致，并完成本人同版本测试、固定和主动提交。选择阶段预留至少30%预算，还可使用生成阶段余额。这一架构同时改变候选数、单分支额度、阶段权限和提交路径，并非只改变人数。

## 低预算：每个分支只能执行三次模型调用，候选池最终为空

25万预算的四槽、共16个生成分支，均实际调用模型3次后遇到阶段预算拒绝；全部没有在生成阶段固定候选。其已消耗token在35,568至40,949之间，虽未用尽名义43,750配额，但剩余不足以容纳下一次完整输入加预留输出。

例如LA的001已花36,118 token，只剩7,632；下一次准备输入为13,784 token，另须预留2,048输出，无法获准调用。该准备输入符合18,432上下文上限，拒绝原因是分支预算，不是context。拒绝前已有代码修改，但没有 `fix_patch`。这确立了该条实际路径被预算子池截断的事实；若换额度或动作顺序能否成功，本次轨迹不能证明。

16个分支没有统一推进到同一步：LA有4次编辑和1次公开测试，HA只有1次编辑，LB有3次编辑，HB仅有读取、没有实际编辑事件。四槽生成阶段总计花610,389 token，却没有合法候选；随后选择阶段又花366,089 token。团队整体仍有余额并不能帮助继续生成，因为余额只能向后传给无编辑权限的选择者。

**LA给出了“代码进展存在，但候选登记时机错误”的直接例子：**

1. 生成阶段未固定候选，候选池冻结为空。
2. 选择阶段001运行公开测试，公开测试通过；随后才固定 `patch-1`。
3. 提交被拒：`Final I files must exactly equal the explicitly selected fixed candidate`。
4. 尝试采用该补丁又被拒：`Select only a frozen generation candidate`。此时补丁属于选择阶段，不能补登记为已冻结的生成候选。
5. 最后调用 `finish_stage`，其理由仍写着“Completing generate stage...”，但真实当前阶段是select；未形成正式提交。

这只是**公开测试通过**，并没有该版本通过私有完整验收的记录，不能称其已经形成正确完整解。失败记录的 `R=0`来自未完成合法交付，不等同于已证代码全错。

原始证据：`runs/software-organization-v047/stage-A-r0/actual/episodes/org47-A-r0-I4-B250000/experience.jsonl` 第397行（事件396，提交拒绝）、第420行（事件419，采用拒绝）、第466行（事件465，结束阶段）。原汇总为 `/slots/4`，具体预算拒绝在 `/slots/4/cost_detail/stopping_rejections/0`；阶段测试和候选在 `/slots/4/architecture_stage_evidence/stages`。

其他低预算任务的选择者也尝试了当前阶段禁止的编辑操作：HA、LB、HB各发生两次 `This operation is unavailable in your current architecture stage` 拒绝。它们已经处于不能修改代码的select阶段，又没有可采用的生成候选；没有记录显示其通过有效候选路径形成交付。

## 提高预算后：候选生成有所恢复，选择行为仍有独立阻断

50万预算把单生成分支额度提升为87,500 token，实际生成调用增加到每人5或6次。LA产生3个合法候选；LB产生1个；HA和HB仍没有候选。HA/HB四名生成者全部遇到分支预算拒绝，后续选择阶段又分别消耗181,052和161,697 token，最终无提交。

**LA不是缺候选，而是选择动作停滞。** 四位成员的生成阶段公开测试均有通过记录，001、002、004固定了候选；003结束生成阶段但没有固定候选。随后001在选择阶段执行13次 `read_file`，花207,579 token。13次参数全部指向同一 `patch-1`、同一 `event_time.py`、`start_line=1`；首次 `max_lines=50`，其后12次为30。每次返回 `total_lines=23`，这些调用反复覆盖同一份候选的完整文件，未转向其他候选，也没有采用、选择阶段测试、固定或提交。最终下一次请求因团队token不足而停止。

真实动作示例：`read_file({"path":"event_time.py","patch_id":"patch-1","start_line":1,"max_lines":30})`。读取返回成功；现有记录不支持“因读文件报错而重试”的解释。该重复行为是可观察事实，为什么模型持续重复（例如策略能力或输入表示影响）仍是待检验假设，不能由本条轨迹唯一判定。

进一步仅抽取首段和末段两处真实输入：第1次读取的成功反馈出现在第2次选择调用的 `request-00023/selected-request.json#/messages/7`；第12次读取的成功反馈出现在第13次选择调用的 `request-00034/selected-request.json#/messages/9`。两处均包含23行文件的完整文本，且对应下一次调用实际产生了模型输出。13次工具返回均为 `ok=true`。因此这两个样本支持“工具已返回、反馈已进入实际输入后仍继续重复读取”，不支持工具没有返回的解释；没有全量重做输入测量。最后第13次读取后无后续实际生成，下一请求被团队预算阻断，不能声称其反馈被后续模型使用。

证据：高预算LA原始轨迹目录 `runs/software-organization-v047/stage-B-r0/actual/episodes/org47-B-r0-I4-B500000/`；世界文件 `episode/end/control/state.json` 的 `/software_events/23` 至 `/software_events/35`，事件序号24至36。所有原始工具调用的行号、参数及返回摘要均保留在 [evidence.json](evidence.json) 对应槽的 `raw_tool_events`。费用和生成测试见原汇总 `/slots/30`。

**LB展示了唯一走通的交付路径。** 002在生成阶段固定 `patch-1`；选择者001采用该候选、执行本人公开测试。第一次提交因尚未固定本人当前版本而被拒，随后001固定同版本、再次测试并正式提交，最终私有验收通过。这说明采用／测试／固定／提交的链条可以完成，但仅在一槽观察到完整成功。

原始高预算LB轨迹 `experience.jsonl` 第650行（事件649，采用成功）、第696行（事件695，要求固定当前版本）、第765行（事件764，正式提交成功）、第788行（事件787，结束选择阶段）。最终成功字段见原汇总 `/slots/36/R_joint`。

## 与双人和单人的比较支持什么

I2在25万下每个生成分支拥有87,500 token，为I4同预算的两倍。I2的LA两个生成者分别实际调用5和6次，002生成了唯一合法候选，001取得后完成交付；该槽为I2的唯一成功。I4同预算每人均只有3次调用且没有生成候选，这支持“分支额度切分压缩了候选完成机会”的机制解释。

但I2其余三槽也没有生成候选、没有提交；增加到双人分支额度并不能保证成功。I4在50万下虽拥有与低预算I2相同的单分支额度，LA仍因选择阶段重复读取失败。因此不能把“四人失败”全部解释为预算不足。

S1两个预算下都只在LB成功，LA已提交但完整验收未通过（Q=2/3），HA/HB无提交。可见较难任务中的无交付不是I4独有，现有数据不能将HA/HB的全部失败归因于组织架构；S1在LA也没有完整通过，不能把I4的候选公开测试通过视作其已解决了单人未解决的任务。

## 结论与可验证方向

**直接事实：** I4七个失败槽全为未提交。其中六槽在生成结束时没有合法候选；剩余高预算LA已有三候选，但选择者反复读取同一候选直至团队预算耗尽。八槽均进入选择阶段，没有永久退休造成选择者缺席，也没有硬context拒绝。

**由事实支持的机制判断：** 固定团队预算被拆为四个不能互借的生成子池，降低了每个分支在截止前完成“实现—测试—固定”的机会；空候选池与选择阶段不能编辑的规则，使后续余额无法继续修补并登记候选。候选存在后，选择策略本身的重复读取又能独立阻断交付。

**尚不能识别的原因：** 不能由本批证明调整比例一定提高成功率、所有未固定代码都能通过私有验收、减少重复读取必然足以成功，或更多成员本身降低智能。没有执行新的反事实实验，也没有把未提交版本私下补验后重新计分。

后续可优先验证三项相互独立的改变：让生成阶段拥有足以完成候选登记的资源或更明确的完成信号；明确空候选池时应采取的终止／回退规则；检验选择者读取同一固定候选后的记忆与进度保持。以上是待验证设计，不是本次已证收益，也没有在本次执行。
