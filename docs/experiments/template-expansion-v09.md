# v0.9 两模板、定向审阅与跨模板联动实验报告

日期：2026-09-23。依据：[v0.8审计](../reference/template-expansion-audit.md)、[实施计划](../template-expansion-v09-plan.md)。实现合同见[设计说明](../template-expansion-v09.md)，可操作示例见[示例目录](../../examples/templates-v09/README.md)。

本轮将工作对象从固定数值消费扩展为**记录集合核对**与**实际报告的定位审阅、回应和局部修复**。两个模板分别运行后，在同一世界连接资料更正、核对后继、成果发布、报告后继和实际审阅。共同内核增加的问题处理关系已在两类内容中使用；财务字段、匹配规则和正文标准仍属于领域层。

结果支持有限合成模板的机制可操作性，不证明通用财务审计、自由文稿审阅、模型规划能力或训练收益。合法“未解决”交付与完整资料不可得的阻塞均保留；专业充分性继续未评。

## 3. 模板需求如何进入各层

旧版完整源码的两个最小真实项目先创建、提交并读取核对形状和报告形状的JSON，再调用定位问题动作，均返回能力未启用。它证明既有submit/approve/revise不能表达所需关系，**不是已执行两个完整新模板，也不是v0.8违约缺陷**。[原公开缺口](v09-template-gaps.json)保留完整源身份、实际调用及固定交付。

| 需求 | 最终归属 |
| --- | --- |
| 材料、角色、节点、公开口径、交付/审阅范围 | 两个templates项目配置 |
| 集合覆盖、匹配、单位/期间/定义/币种、有限正文关系 | 两个domains内容合同与只读评价 |
| 谁读取、如何核对、撰写、提出问题和选择修复章节 | workers程序策略；无评价器答案输入 |
| 精确JSON键/数组索引是否存在 | 文件适配层locations |
| 固定提交上的问题、责任者回应、处理确认、批准约束 | 共用core/issues及工作投影/历史保护 |
| 工具拒绝事实与有限归因 | 通用运行器边界及策略报告 |

未增加财务本体、模板名称分支、PDF/Word解析器或第二套运行器。新增内容合同仍先经过共同的精确工作采用、提交时政策目标、版本哈希、贡献文件依赖检查，再交由领域规则判断。新格式为`world-core-v0.9`，评价为`finite-products-v0.9`；旧单项目经营/出版运行时仍保留0.5格式，不伪装迁移。

## 4. X1/X2：财务资料核对与差异处理

公开资料是两表18条原记录和口径说明，形成9个业务键。字段包括record_id、对象、指标、期间、定义、币种、单位、值及来源声明位置。匹配键为对象/指标；期间、定义、币种和单位规则用于判断可比性，而不是先把不相容记录混算。

有限人工真值如下；评价器不调用worker matcher生成自己的答案。

| 初始分类 | 键组数 | 合法处理 |
| --- | --- | --- |
| matched | 1 | 同适用范围数值一致 |
| converted | 1 | 按公开明确因子换算一致，保留原单位和来源 |
| conflict | 1 | cost左80、右90，保留双值及差值-10，不选赢家 |
| incomparable | 3 | 期间、定义或币种不适用，比较值和差值保留null |
| missing | 2 | 缺行或原值null，不补零 |
| ambiguous | 1 | 同键多个候选，保留所有原记录，不隐式去重 |

每个并集键恰一行，每条原记录有明确归属，无遗漏/重复匹配。交付包含比较行、差异分类、未解决项、汇总及精确源引用。冲突、不可比、缺失和歧义属于合同允许保留的未解决项；并非每次工作必须输出单一确定金额。

六个场景为综合交付、重排与别名/位置变化后的分拆交付、合法路线取证、当前不可得后恢复、五种实际错误产物及审阅修复。五个负对照涉及漏行、重复匹配、不可比强求差、缺失置零，以及来源引用与汇总正确但比较表实际数值错误；错误内容通过真实版本写入与提交，独立内容评价按预期失败，不由后台改正。

不可得情境执行真实request并留下世界条件；有权提供者改变可得性后，原世界重新请求、读取并继续。等待没有伪造资料。审阅修复情境先实际漏掉一组，审阅者定位到固定交付并提出问题，责任者在同一work/requirement撤回、重做和重新提交，实际读取证据后回应，有权主体确认，再批准。

结构变化不仅改文件名：实际行序、项目内别名、身份/显示名、文件名和来源JSON布局改变；两表移入`appendix`、口径移入`basis`，公开`data_path`定位。单份综合或两份顶层拆分产物都满足同一真值。交付行、候选ID、证据及未解决项展示顺序不是唯一合法解，重复仍不能借集合去重消失。

**来源location字符串在此领域中仅验证与源声明一致**，不解析任意字符串证明它对应当前数组下标。精确输入由对象版本、公开data_path、表内唯一record_id及完整覆盖共同限定。用于审阅问题的issue.locator则会检查实际JSON位置；两种口径没有混同。[财务证据](v09-reconciliation.json)。

## 5. X1/X2：研究报告审阅与定向修订

报告使用结构化章节，但真正面向读者的body必须同时符合有限论断；claim元数据正确不能掩盖正文错误。两种公开完整句式都可接受，例如：

```text
Revenue in 2026H1: 120; trend up; source dataset:metrics.revenue.value.
2026H1: Revenue = 120 (up) [dataset:metrics.revenue.value].
```

本模板检查公开范围内的数字、期间、趋势和引用关系。受检章节body按完整有限句式解析，追加额外句子不符合该语法；正文数值999但metadata120、数值正确但期间/引用不适用，都不能通过。开放背景、论证质量、专业完整性及文风明确未评，不以关键词存在代替完整质量评价。

作者与审阅程序仅持有公开端口。审阅者inspect实际固定提交，再read确切文件和提交采用快照对应的源版本，从实际正文与公开源判断问题；它不调用独立评价器。人工字面真值为收入120对基期100上升、成本70对基期80下降；不完备分支成本为明确null，正文unknown，不能置零。

八个分支覆盖：正确prose首交、compact加两文件、别名/显示名变化、显式未知、两个独立缺陷分次修复、正文期间与来源错误、迟到重复意见、错误意见的有据反驳。首次正确交付直接接受，没有固定“先退回一次”的流程。

双缺陷情境修复第一节后只确认第一项，第二项仍真实阻止approve；下一次只改第二节。没有新需求版本，原固定提交字节及无关背景保持。局部性指章节内容保持和新版本语义，不声称在文件系统做局部字节patch：底层仍写完整JSON新版本。

错误意见情境，责任者以真实读到的源值回应，有权审阅者接受反驳后批准，报告文件不因错误意见被迫改错。迟到旧提交意见保留historical，重复问题不增加关系；原问题status与当前applicability是两个维度。

实际worker观察与调用都核对原端口捕获。双缺陷分支另有测量器通过同一公开端口故意尝试批准，产生预期业务拒绝；它单独保留，不冒称属于worker自身决策轨迹。[报告证据](v09-research-review.json)。

## 6. X3：同一世界中的跨模板更新

每个条件使用一个世界、A核对项目和B报告项目。A的statement采用current_published；既有accepted核对工作由自己资料发布的维护规则产生后继。B的主报告采用A正式comparison并配置accepted后的维护规则，另有独立报告对象和fixed v1历史工作作对照。

初始A的冲突数为1、不可比数为3；B从公开来源形成两个实际章节，主工作和固定历史工作均完成。随后控制器以公开上游写入、批准和发布推动流程，资料更正将cost右值90改为80；upstream_error条件另按协议故意修改summary并作错误批准。A的程序工作人员从公开观察发现后继、重新采用与核对，再经真实提交、批准和发布comparison，使B形成后继。

B的继续程序通过公开工作、要求和发布信息发现新义务与政策目标，显式采用、读取和制作；公开审阅者读取实际提交、定位问题，责任者按原要求修复。**控制器没有直接revise B、改B文件、预填正确问题清单或重装项目**。错误条件的策略注入在协议中明确标注。

| 条件及观察点 | A核对质量 | B接口忠实性 | B正文表达 | 总体目标 |
| --- | --- | --- | --- | --- |
| 正确更正后 | 通过 | 通过，冲突0/不可比3 | 通过 | 达到有限目标 |
| 上游故意残留错误summary.conflict=1并获批准 | 失败 | 通过，忠实使用1 | 与所用接口一致 | 未达到冲突0目标 |
| A正确、B正文故意写999，修复前 | 通过 | 元数据仍忠实0 | 失败 | 未达到 |
| 同一B错误经定位审阅后修复 | 通过 | 通过 | 通过 | 达到有限目标 |

上游错误条件只注入一处summary错误，不能把它对下游的传播重复统计为多个独立根因。B正文条件则明确区分来源/metadata一致与读者实际看到的论断正确。错误获得机构批准不会被内容评价抹除，也不能因为下游通过把上游错误洗为正确。

更正只影响一组业务行，另8组核对内容保持；B不可比章节和背景保持，固定历史工作、采用、原提交及其机构审阅记录、旧版本字节及原观察均保持。更正后仍有6个未解决键，不意味着所有资料已解决。期望0/3及保留范围事先声明，不用matcher或报告评价器自产生整体真值。

三个条件各24项，共72/72；所有实际worker轨迹经规范化字段名后与独立端口捕获逐项相等。这是两个具体有限模板的联动，不是任意模板自动组合定理。[跨模板证据](v09-cross-template.json)。

## 7. X4：问题关系、作用域与一次代表恢复

共同关系由三个追加登记表达：issues固定提出者、work/requirement、提交、对象版本、位置及证据；issue_responses固定责任者回应与真实提交；issue_decisions记录对具体回应的处理。issue_views是派生查询，不通过改一个可变status字段改写事实。

创建时针对当前pending提交的blocking问题约束同一工作版本的批准，撤回、编辑、重交不会自动关闭它。它不阻止修复所需的重新提交。后来才到达的旧提交意见保留为historical；同一问题已经接受的处理事实明确绑定其回应/提交，不证明未来所有版本正确。新发现的缺陷应提出新的定位问题。

核心只检查身份、授权、已读证据、确切版本/位置、关系匹配和时序；不会判定自然语言意见是真理。accept_fix与accept_rebuttal都是机构决定；领域独立检查仍可能拒绝内容。

两类真实模板各有两个明确缺陷，实际局部修复、回应和确认检查28项：一项决定只关闭一项、另一项仍阻止批准；修错不改需求；重复问题/决定无新增关系；错问题回应不能混用；迟到旧意见不约束新版本；旧提交与字节保持。额外7项定点测试覆盖实际读取与授权、非空位置、同键异载荷、过期提交回应、跨项目拒绝及三个登记不可改写/删除。

恢复只增加**decide_issue的after_command_commit**一处。真实子进程`os._exit(73)`，同一检查点逐字节复制到控制组和故障组，以相同request_key执行/重试。比较完整状态，仅排除`wall_seconds`和`state_digests`诊断字段；另比较不可变版本字节、原命令结果、故障前实际捕获的观察及恢复后新观察；镜像文件另保留摘要引用，未作为本组正式字节比较断言。必须只产生一次决定且另一问题仍open。10项全部通过。

该结果不扩展为任意中断、断电、并发写者或策略checkpoint保证；本轮没有机械重跑所有旧故障矩阵。[关系及恢复证据](v09-issues.json)。

## 8. 拒绝事实与归因修订

v0.8公开持续策略将所有`ok=false`归为environment_error。完整旧源探针对六类真实调用保存原返回，再通过旧策略分类，均得到该标签。最后一个明确向已注册工具注入内部KeyError，其余是实际参数、权限、能力、旧工作和暂停约束。这不推翻旧pause实验曾真实返回拒绝的事实。

新版保留error.type/message，并由知道违反哪项合同的边界添加rejection的version、code、category和调用上下文。消费者不按错误文字猜测。未明确归因的普通异常保留unknown/unattributed_tool_rejection，不能声称已覆盖全部失败分类。

| 实际拒绝 | 新版预声明归因 |
| --- | --- |
| 非法工具签名参数 | policy_error |
| 无权操作世界 | policy_error |
| 未启用工具 | capability_gap |
| 使用已替代工作 | business_constraint |
| 世界暂停后请求新动作 | business_constraint |
| 明确注入的内部KeyError | environment_error |

六类24项全部符合期望。暂停后同一ContinuousWorker在有权resume后继续完成，由实际回归覆盖，不把业务约束永久粘为终止错误。旧P4脚本明确改为`public-continuous-work-P4-v0.9-rejection`，保留历史组标识但将预期改为world_paused业务约束；旧v0.8 JSON不修改。

两处格式缺口分别处理：开发初期invalid_arguments/world_paused没有实际调用context，24项仅22项通过，补齐后通过；首个冻结后又发现共享runner在非dict参数上格式化context时调用`.get()`，再次抛AttributeError。原世界未变；修后返回正常policy_error，拒绝尝试可按原运行器规则记账、推进时钟，不把“没有业务效果”误写成“完整state不变”。数组/字符串/整数/布尔四种实际旧入口及同身份重试回归通过，最终冻结直接重放原探针也通过。[拒绝证据](v09-rejections.json)。
