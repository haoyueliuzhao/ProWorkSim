# v069／v070：缩减API预算梯度并提高运行并发

用户在2026-10-28要求提高并发，随后将DeepSeek限定为每题累计输入＋输出500万token，并要求本地Qwen一并提速。本次保留Qwen的REF／PROJECT×5M／7.5M／10M六组；DeepSeek后续只继续REF／PROJECT×5M两组。后续目标合计八组4000个原计划回合，已有高预算DeepSeek结果和费用保留，不追溯删除或改写。

## DeepSeek：新准入范围与交接

先暂停旧混合预算API队列的所有新派发，已开始的任务自然完成。旧版控制器只接受1—64，因而本次以`desired=0`触发拒绝新准入；它不等同于完整退出，最后任务完成后原循环会停在等待。新的受限收尾器等待旧任务、请求、容器和评分都已结束，再核验原服务的用户、名称、ownership token与命令，只结束这一旧协调器，并汇集原评分证据。没有停止或重启Qwen，也没有取消旧高预算在途任务。

封存的5M目标仍是原1000回合：已有154条记录（69正常闭合、57技术未知、28环境未准入），另846条未消费身份可继续，REF／PROJECT各423条。原队列202个已派发身份全部排除，包括尚未创建容器的future；在途身份不能仅按API请求表判断。生成评分异步运行，原有未知仍单列，不重采已实际调用模型的回合。原1500元唯一账本继续包含准备及已发生的高预算组费用，没有新开预算。

## 真正扩展环境槽

之前的瓶颈是全局12个actor／controller对。v069增加逻辑槽12—17，上限变为18；每对仍预约6CPU／32GiB，每个actor和controller均保留16GiB，原OOM之后的内存修复不回退。新增槽共享原actor CPU池的固定片段，每个容器仍有原4／2CPU上限，不借用模型或评分器的CPU分区，不改宿主配置。

所有原、新消费者继续在同一个allocation lock下预约，总上限仍为152CPU／832GiB；新的actor准入还为至少两个评分器保留余量，已存在的评分预约不会重复扣除。CPU共享意味着多个本项目环境可能竞争同一片段，不宣称独占，也不能仅从槽位数推导同比完成率或速度提升。

本地新增第三个模型驻留后，三模型共预约288GiB。当前4个Qwen环境、两个协调器和两项评分余量计入后，API可达到11个环境；相较修改前的8个增加37.5%。18是逻辑全局上限，32是API期望值，均不是当前实际API并发。19:53的实际预约显示API11、Qwen4，全局15对，逻辑槽12、13、14已有真实任务；总预约134CPU／800GiB，加两项评分余量后仍满足152CPU／832GiB。

队列实施与6项CPU控制见[API专用队列](software-benchmark-v069-api-5m-expansion.md)，资源策略及6项不同CPU控制见[资源边界](software-benchmark-v069-resource-policy-cpu-control-r1.md)。交接分类与收尾另有7项定向CPU控制；没有为扩容重复下载模型、镜像或重跑环境控制。

## 本地Qwen：增加原配置驻留

19:38只读观察时GPU0、2均为100%设备利用率，两个本项目服务都有实际请求。GPU2对应服务近期decode约79token/s且有等待请求；GPU0对应服务近期约18—66token/s，包含prefill和不同上下文形状，不能据此作同请求的卡间性能比较。两卡排队说明本地瓶颈包含实际推理计算，不只是CPU测试等待。

GPU4当时剩余约60GiB，满足原50176MiB准入门。通过原尚未消费的model-3身份增加一个普通用户模型服务，继续使用原BF16权重、131072上下文、32768输出、0.6显存预约和原采样，不重载GPU0／2模型。新增12CPU／96GiB进入同一资源总账；原服务负责自身GPU租约及正常退出清理。

第三卡已于约19:46通过完整上下文缓存和原有中性准入检查，并于20:08:45在自然回合边界接到原槽108（astropy-8872，Qwen PROJECT 10M）。20:26:53观察时，该槽已留下37份有效宿主模型用量回执，证明新卡已经处理正式调用。现有Qwen协调器仍最多4个任务future，不把这次改变表述为6题并行，也没有迁移原在途回合。实际收益需要以完成速率继续观察，不能用“3张卡”直接声称完成速度提升50%。

对20:06时四个在途任务的只读分析进一步定位了等待原因。两个REF任务约93%—95%的墙钟时间在模型请求往返内，其中包含同卡排队；工具间隙约3%—5%。槽100有4次输出达到32768，每次耗时407—443秒；槽104另有两次同样长度输出耗时629／639秒。与它们同卡的PROJECT请求，即使只输出68、149、1210token，也分别等待约428、436、441秒。因而少量长响应会连带阻塞后面的短响应，增加独立驻留能减少这种排队。

不能将全部长输出归为思考：上述早期6个32K响应报告的reasoning token只有0—792；之后槽104又出现一次32768个全部为reasoning、finish=length的响应，耗时423.6秒。这是已记录输出形态差异，不是对模型内在推理过程的直接测量。槽100当时累计使用4,366,569／5,000,000 token，其中输入4,196,261、输出170,308；接近预算闭合。其他回合仍有较大余量，因此这次没有缩短既定输出或时间上限。

20:26:53的运行观察中，DeepSeek专用队列新增20个正常闭合回合、1个局部技术未知，保持11个实际环境；两个活动协调器无全局failure，旧混合预算协调器已经完成评分收尾并释放预约。该局部异常为controller未提供可信闭合结果，按原规则单列而非填为模型失败。详细快照见[运行观察](../../artifacts/software-benchmark-v069/runtime-observation-r1/snapshot.json)。
