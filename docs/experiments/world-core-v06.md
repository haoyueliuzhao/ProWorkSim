## 2. G0：修正共同误测，保留原输出

### 2.1 原反例与重算方式

原 E2 直接比较 attestation 的 `{"object_id":...,"version_id":...}` 与适配器的 `{"artifact_id":...,"version_id":...}`。两个模板都把合法确认测为 false，仍通过相等性。**原 31/31 是当时脚本的真实输出，不能再解释成正式确认维度已正确测量。**原 JSON 未覆盖；[v0.5 报告](state-consistency-v05.md)已补勘误。

本轮先逐字节复制原 22 个状态快照，再只重算测量投影，不实例化 World、不恢复文件、不执行工作人员动作。原目录完整文件摘要保持一致。结果为：

- 原测量的独立确认预期：0/22；修正后：22/22。
- 这些快照共含 30 处声明凭据确认，原全部 false，修正后全部 true；其余投影字段保持。
- 两模板对应的 11 个比较点仍相等，但现在还必须满足明确预期，不能靠共同 false 通过。

源码修复用 `VersionRef` 规范化目标、credential 和 attestation 的精确引用，并核对签发 ID、签发者、要求关联与工作范围；没有退化为只比对象名。

### 2.2 测量函数自身的敏感性

9 个独立夹具分别检查：合法混合引用、缺登记、错精确版本、错签发 ID、错签发者、错需求关联、错工作范围、错 credential 引用，以及历史确认面对新需求。最后一项要求历史正式确认仍存在，同时新需求适用性失败。

3 个测量变异为：重新直接比较原始字典、只比对象名、只判断 attestation 存在。各自触发预注册的合法混合引用／错版本／错签发 ID 断言。没有把导入或一般夹具错误算作检出。

随后在新目录真实运行原四条轨迹。仍保留 bootstrap ConfirmGrant 的原解释和经营／文稿不同回复时序的宏比较边界；没有把初始化签发伪称为工作人员执行的 Confirm 工具。31 项原关系检查（11 跨模板＋16 局部＋4 独立范围组件检查）全通过，另 22 项独立预期全通过，共 53。范围组件仍不是第五个适配器世界。

此修正只改变对应测量结论。没有重新运行无关的旧 E1、E3、E4、E5 或原十情境；它们继续按原范围解读，不能因本轮改脚本而声称旧实验全部重新验证。

## 4. M1／M2／M4：真实对象与作用域

### M1：项目加入、结束与世界保持

一个世界先创建材料，再装载 A/B。A 正式完成后，其提交和共享成果保留，B 的工作与待处理事件继续；C 在原世界动态加入。世界和主体身份保持，逻辑时间递增。非法项目包包含不合法声明，整体明确拒绝，业务状态与正式版本/镜像字节均保持。

业务原子性比较明确排除失败命令产生的时钟、观察和 journal 记账；它不声称“拒绝后所有运行日志也不变”。13 项检查全部通过。只有 M1 动态加入第三个项目。

### M2：同名与同人正反对照

A/B 使用相同本地 work-1 和 report.json，但底层工作及对象身份不同。A 的正式确认对 A 适用；明确共享并采用该凭据之后，对 B 的同名工作仍不适用，避免仅因不可读取而产生弱负例。B 审阅者在 B 可批准，在 A 无对应权力则拒绝。

精确版分享前拒绝，分享后可读；另一未共享新版和上游私有对象仍不可读。跨项目重试检查使用**同一 actor、相同负载和相同文本键，仅项目不同**：同项目返回原结果且无第二次效果，不同项目产生独立操作。工具参数伪造 project_id 被拒绝；实际阅读历史在人员切换后保持。14 项全部通过。

保持阅读历史不等于模拟模型记忆或实现保密规范；本轮没有模型认知状态实验。

### M4：动态创建与不同交付方式

A/B 包只规定产物角色、文件数和必需字段，不预建输出对象。工作人员实际创建中间草稿，并分别用一份聚合文件和两份分拆文件交付；两种组织均满足同一有限字段合同。

A 另有 work-2，实际提交缺 cost 的内容。delivery_only 仍留下 owner 的 accepted/decision_basis 记录；独立评价返回缺字段失败，正式提交未被重写。内部仍复用 review 字段存该完成决定，但其 actor 是 owner、basis 是 delivery_only，轨迹没有经理 approve 行动，不能把字段名称说成审阅已经发生。

跨项目写入、冒用对象身份和伪造确认均拒绝，原对象和正式确认保持。14 项全部通过。没有把一条历史示范路径固定成唯一合法解法；此处“合法”仍是声明的有限 JSON 合同。

## 5. M3／M5：关系变化、交错与恢复

### M3：同一发布的不同后果

世界资料 v1 明确共享：A 使用 current_applicable 并订阅后续发布，B 固定 v1。共同模型也实际分享给两个项目并固定采用。发布资料 v2 后，A 的关系为 update_required 并收到通知，B 仍 current；A 获得明确订阅的新版本读取权，B 只能读取原 v1。

发布、A 局部依据修订及受众修订均不改变工作人员文件字节；B 的无关业务事实保持，共同模型不被后台重写。无共享的局部对象编辑也不影响 B。最后的工作人员显式写入才创建 A 的新交付版本。10 项通过。

本组验证已声明关系的定向后果。current_applicable 在本轮资料上表示发布版本跟随政策，不是内核自动证明任意金融资料的领域适用性。资料变化目前形成需检查标记和通知，没有自动替工作人员计算新答案。

### M5：等待与完成并存

A 等待回复时，B 的一个工作实际交付完成，另一个工作有独立待回条件。A 修订形成新义务和新请求；原 A 回复随后实际送达，其旧条件已被替代，不能解除新 A 或 B 的条件。B 已完成的提交和文件保持。

结束 A 的 episode 不清空 B，也不移除两项仍未到期回复。同一主体切回 B 的行动仍使用 B 的工作上下文。8 项通过。没有要求历史上的撤回、批准或修订可以任意交换顺序。

### 共享发布的两个进程终止点

从同一真实检查点逐字节复制到不中断对照与两份故障世界；使用固定命令键发布共享资料新版本。切点为 after_apply（尚未提交）和 after_command_commit（已提交、尚未返回）。故障子进程执行 `os._exit(73)`，不经过 finally 或普通异常回滚。

每个切点执行 8 项检查：起始副本一致、实际到达退出点、提交前缀符合预期、完整恢复状态等同对照、全部不可变版本/镜像字节一致、公开结果一致、世界关系与历史观察保持、再次重试无效果。两个切点均通过，共 16/16。

完整状态规范化仅递归去掉 wall_seconds 和诊断 state_digests；项目注册、范围授权、别名、采用、消息、交互与读取收据继续比较。切点证据保存实际内存状态、磁盘提交状态及物理版本清单；本轮可以区分暂存版本与正式前缀。observe 返回本身不自动持久化为状态观察记录；比较的已保存 O 包括真实读取/交互，不宣称存在一份实际没有保存的全部观察历史。

这只支持一个世界、单写者、当前文件系统、共享发布与两个声明切点。没有额外验证机器丢失、断电或任意插件外部副作用。

## 6. 开发期问题与协议修订

开发记录没有覆盖。实现缺陷与测量夹具变化分别记录，详见 [v06-development.json](v06-development.json)和各组归档 development evidence。

### 已执行确认的集成缺陷

在未冻结的 v0.6 开发树中，真实工具探针发现：

1. 一次包装载重复追加两条 installed 历史；现由安装函数唯一记录。
2. required_credentials 只进入提交快照，未签发材料也可交付完成；现提交、批准与公开使能共用精确可读性和 registered_applicability 检查。
3. 声明 content_rules 最小值却未实现评价，负值仍被判通过；现拒绝不支持的规则，明确只验证字段覆盖/冲突。
4. 合法 object-scoped provide grant 未透传对象上下文，真实 request 被拒绝；现传递完整工作与对象范围，错对象仍拒绝。
5. 字符串拼接对象身份会使不同项目/别名组合碰撞，且世界与名为 world 的项目有冲突；现使用规范元组摘要。原版本虽拒绝覆盖，但会错误拒绝合法不同对象。

另收口了初始 JSON 数据类型、未来项目采用的预分享路径、归档 retain/cancel、显式采用更新和世界材料读取。针对这些合同的回归通过，不将“实现已改”代替检查证据。

原探针、世界和报告保存在 `runs/world-core-v06-integration-before`。探针执行时未采集源码摘要；归档中 b433… 摘要来自归档时、且已含部分后续修订，**不能作为 before 实现的精确身份**。这些缺陷属于本轮开发树，不归因于冻结 v0.5。

### 实验夹具的修订

- M1/M2/M4 dev1 为 37/41：一个跨项目查询尚未建立共享采用，返回 UNASSESSED；另三个断言误以为 delivery_only 必须 review=None。随后增加真实分享/采用，并检查 owner 和 decision_basis。
- dev2 为 40/41：仍硬编码原对象 ID 拼接形式；改为实际工具结果和别名注册查询。
- dev3 达到 41/41 后，检查发现跨项目幂等正例使用了不同 actor。冻结前改为同一 alice、相同负载/键，B 创建权显式配置；dev4 的 M2 14/14。
- M4 最初用第三项目放错误提交，偏离“仅生命周期加 C”的计划。冻结前收窄为 A 内新增 work-2，14 项标准不变，定向复验 14/14。
- M3/M5 初轮存在错误修订 power 和遗漏 B 第二工作 provider grant，属于构造失败，不是世界允许越权；其后对象身份变化使旧硬编码失效。另修正 delivery_only 的 review=None 预期，并让共同模型实际共享/采用。正式协议冻结前均完成。
- 新运行时测试首轮两项失败来自测试夹具把人员顺序解包错误，未到达目标凭据断言；修正后该文件 8 项通过。

这些过程说明初轮总数不能不加区分地解释成生产缺陷数量。正式报告对失败、未执行与预期拒绝分别留证。
