# v240 实验报告｜先查清上游产物，再决定谁做什么

2026 年 11 月 25 日。**三图方案改善了第一步的选择，但把太多未来工作列为了当前义务。** 在同一批真实现场的 30 次判断中，第一步正确从 27/30 升至 30/30，最终义务集合完全正确却从 19/30 降至 13/30。此次没有通过事前规定的 26/30 义务门槛。四个 Worker 候选已做零 API 准入核对，v241 真实续跑为 0 对。

口径校正：来稿回顾表中 v239 的 10/28、17/28 对应当轮原提示参照；当轮三图之前的首版结构化合同为 7/28、11/28。本报告以新一轮同期调用作比较。上轮 v239.3 的成绩和审计结论保留原记录。[上一期综合审计](v239-v239-3-audit-report-20261125.md)

## 1. 改了什么，怎样验证

**P0** 原样运行 v239.3。它根据工作包、回执和可用分工生成「组织选择＋一个首步」的组合，保存模型所报义务，再依据版本回执补全。

**P1** 把同一现场拆成三层。项目图记录成员实际可见的回执、版本以及上下游产物事实；工作义务图记录每项工作的完成状态、能否执行、所需前提和完成证据；组织图记录成员、责任、协作及预算。三图通过工作包、回执和行动 ID 关联。OSA 从现有方案中选择，程序只对组织图应用绑定基础版本的补丁。每项变更关联到具体义务；执行计划单列一个立即动作、后续条件、所需证据及复评触发项。[实现](../../src/proworksim/software_three_graph_v240.py)

以「下游等待上游，上游登记缺失」为例，程序保留取得当前有效交接的责任，同时把“产物是否已存在”记为未知。可以先查状态或查看产物引用。已核实无产物、已有待验证产物、已有可采纳产物、已被相应下游采用，分别开放执行上游工作、验证产物、采用产物、推进下游。原生就绪回执明确报告具名补丁尚未被采用时，沿用原执行器已核验上游完成与依赖版本的语义。多项依赖未全部满足时继续阻止下游推进。

v240.1 用零 API 控制分别验证了未执行的失败测试、无完成登记但已有产物、工作包已完成而缺复核、最终树已固定且可提交但仍欠提交。另检验了过期检查回执、固定两人时拒绝增员，以及离线增加与退出第三名成员。D0–D7 沿用既定定义，运行时只暴露现场确有权限且有预算的操作。六种依赖动作是控制器的计划语义；本轮未测 Worker 真实检索、验证或采用产物的成功率。[CPU 结果](../../artifacts/software-benchmark-v240/three-graphs-r1/cpu-controls.json)

## 2. 面板和评分

主面板有 **15 个真实决策现场、14 道题、8 个仓库**：持续失败 3 个、工程依赖 3 个、集成冲突 2 个、验证缺口 3 个、正常推进 4 个。回查 221 个历史分支，只发现 2 次原观察者的就绪回执，没有自然发生的同版本反复就绪未提交案例。计划中的第 16 个现场（A5）留空。两组均为 DeepSeek Flash 非思考模式，每现场每条件两次独立调用，同题反转条件顺序，共 **60 次主测＋4 次单列缺证探针**。输入输出预算相同，单次输出上限 2,048 token，未重采。均属历史开发材料。[冻结协议](../../artifacts/software-benchmark-v240/three-graphs-r1/protocol.json) · [A5 检索](../../artifacts/software-benchmark-v240/three-graphs-r1/a5-inventory.json)

义务集合继续用事前接受的多个答案评判。首步单独评分；因本次审计明确了无引用时的处理，事前将 q14 和 x04 的合格首步统一为先查状态或查看产物。保留原标准作敏感性分析。每个现场另冻结一个义务，要求 P1 读出完成状态与执行就绪状态，既包括 READY、BLOCKED，也包括 CONDITIONAL 和 NOT_APPLICABLE。标签来自回执与协议，模型能看到程序生成的图，因此该指标包含从图中读取状态的能力。P0 没有对应独立答题字段，相关指标记为不适用。[冻结参照及状态探针](../../artifacts/software-benchmark-v240/three-graphs-r1/references.json)

**首步的三次净改善都来自依赖现场。** P1 只开放当前证据足以支持的动作。在缺当前引用时先检查，遇已具名且可采用的补丁才允许采用。由此得到的 6/6 是模型和规则合起来的表现。同一批响应按历史首步标注重算，两组分别为 27/30 与 28/30；新规则下的差距有一部分来自审计对依赖处理标准的明确。

**共同欠项保全，过报仍会导致整套方案错误。** 将所有可接受答案共同包含的义务视为无歧义的必需项，10/15 个现场存在此类项目。两次重复共 32 个计数机会，P0 原答／最终均保留 31/32，P1 原答／最终均保留 32/32。这是可明确判定部分的保留率；其他五个现场没有各答案共同包含的标签。P1 在 v240.2 的主测中没有新补入的条目。其主要损失是将条件性的候选也提交为当前义务。例如模型正确决定先诊断，却把未来版本的测试也列入当前欠项；工作包还在等待完成登记及复核时，又列入最终固定、正式提交。P1 在 6/15 个现场两次都答对整套义务，P0 为 7/15。按任务等权，义务正确率分别为 P0 60.7%、P1 42.9%；按仓库等权为 60.9%、44.8%。这些是开发面板上的描述统计。

## 4. 事后修复与回放

已实现一个独立的结果整理步骤。保存模型原答和原执行计划，只把具有 UNSATISFIED 或 STALE 证据的已选条目列入当前欠项；UNKNOWN 等条目保留在待核查／后续清单中。无需删除后续行动，也不改变组织补丁、执行人、前置条件或报价。用同一批原始 P1 响应回放，义务集合匹配从 **13/30 升至 30/30**，共同欠项仍保留 **32/32**。此步骤是在看过本轮错误后设计的，测量的是已知现场下程序整理的效果；没有追加独立模型调用，也没有用回放成绩回填正式门槛。[修复实现](../../src/proworksim/software_obligation_projection_v240.py) · [逐项回放](../../artifacts/software-benchmark-v240/three-graphs-r1/projection-replay.json)
