## 六个核心算子的真实含义

新执行层以现有受管WorldCore和双成员FREE2作为底层，增加持久化、版本化的动态工作合同。它不是只把FREE2换名字：新约束实际进入工具事务，并约束代码编辑、消息、依赖采用和最终交付。

| 算子 | 真实执行规则 | 不能混淆的边界 |
|---|---|---|
| SPLIT_WORK | 原owner创建子包并保留每个子包的责任，范围完整且不重复 | 原父节点保留协调责任；新增ID不代表工作已完成 |
| ASSIGN_WORK | 向另一成员提出真实offer，等待其accept | 接受前原owner仍负责，宿主不代签接受 |
| TRANSFER_OWNERSHIP | 使用原offer／accept／decline，检查当前owner和任务版本 | 合法拒绝保留；本阶段不开放将任务退为无人负责 |
| ADD_COLLABORATION | 建立具体工作包的双向通信／交接边；没有该边的工作消息或补丁交接会被拒绝 | root_goal协商仍可用；不复制私有历史，不自动整合代码 |
| CHANGE_DEPENDENCY | 真实任务依赖绑定版本；下游begin_work要求上游本地完成、精确补丁已采用 | 先约束实际编辑准入，不改底层公平调度器；等待时可继续读取和协商 |
| ASSIGN_VERIFICATION | 工作owner指定另一个非作者，必须真实采用、同版本测试并显式复核 | 分配验证人不是已经验证；角色改名不能洗掉作者 |

新增begin_work和complete_work作为执行边界：写代码前选择本人实际负责的叶工作包；本地完成需固定候选及同版本公开测试。**本地完成不是官方resolved。** 最终提交还须全部叶工作包完成、每份贡献经过独立精确版本复核、伙伴补丁实际集成，以及原项目要求的最终固定与测试。

初始准备使用原create／claim真实回执建立全任务owner，准备完成前不暴露给模型。后续拆分单次工具事务内保持子包有owner；跨多个组织操作并不假设原子性。已接受转交后另一操作失败，不抹去已发生的责任变化。

本阶段采用**贡献级交叉复核**：两人都可实现不同工作包，再检查对方贡献。唯一最终导出身份仍为001；这不表示所有代码由001编写。该合同不同于“整棵最终代码树必须由从未参与实现者复核”，不能宣传两者等价。O0／O1／O2都使用同一新合同、工具和官方评分，避免把接口放宽只给某一组。

MERGE_WORK、子团队创建／解散、动态成员增减、撤销在途协作及底层优先调度不在本阶段接线范围。CREATE_ROLE仍只是带范围的职责说明，不单独算L2变化。

## O0／O1／O2如何产生

冻结的确定性生成器枚举2–4个公共范围锚的分区及两成员owner分配，给每个工作包分配另一成员验证，并加入题面明确支持的依赖。生成器不看后继成绩，不调用额外模型。

- O0：保留全任务单包、001负责、002验证的初始组织；同样显式建立协作和验证安排。
- O1：在具有两名实际工作owner的合法配置中，按冻结种子选择一个方案。
- O2：从其余合法配置中按事前规定的“范围—owner—验证人”结构差异选择另一个方案，平局由冻结哈希决定。

这是机制覆盖设计，不是按效用找最佳方案。实际生成多个配置，事前固定只运行三个；O1／O2随公开范围和依赖组合变化，不是给旧ASSIST／TRANSFER换标签。所有未选候选也保存，以便检查生成覆盖。

方案通过两个成员的真实SDK输入呈现；需要成员实际调用工具，接收者可以拒绝。引用前序回执的offer_id必须取实际返回值，不能把模板引用对象当作参数。宿主不会强改owner。若成员偏离提案，完整保留，报告目标图与实际图的距离，不把提案图当完成事实。

共同起点采用**零模型调用的真实SDK检查点**：原始代码、初始完整责任、私有会话和预算冻结后，三组分别恢复。因此本轮没有8次生成前缀的额外模型成本；检查点准备、环境和CPU时间仍计入墙钟与资源记录。

## 准入验证与失败原件

已通过：

- 3项结构等价与覆盖控制；3项生成器／真实工具schema控制；2项独立700元账本控制。
- 4项实际HarnessPort／WorldCore控制：责任闭合、部分操作失败保留、协作边影响真实发送、依赖阻止下游编辑、实际本地pytest、精确贡献交叉复核和合法交付。

早期控制失败已保留：合成计数缺请求摘要、脚本工具调用ID重用、本地pytest的user-site环境、以及将两文件pytest夹具放入SymPy原bin/test入口导致文件不存在。这些失败没有触发付费调用；最终使用原pytest入口镜像完成传输控制。没有修改真实SymPy任务的测试入口。

审计证据见[准入门](../../artifacts/software-benchmark-v211/admission-r1/gate.json)。归档脚本及摘要将保留所有修订，不把失败控制抹掉。

## 运行边界与判定

最多12条生成、2条评分、4条环境启动。只使用本批普通用户协调服务和私有隔离Docker容器，无宿主绑定、GPU、对外端口或容器出网，不修改共享服务器配置。API直连，真实请求及usage独立记录。

生成和评分异步。环境失败、执行未知与评分未知单独留档，其他题继续；不自动重采已调用模型的回合，也不填成正常模型失败。700元的全局最坏价格准入和每队Token约束保护费用；正常工具拒绝属于实际执行结果。

最终分别报告L0合法提案、L1实际状态变化、L2实际成员工作变化。通过机制阶段至少要求范围不丢、owner闭合、两类以上实际变化、作者及版本约束可信、部分执行可追溯。代码通过不自动证明组织机制成功；生命周期finished更不能替代工作结果。
