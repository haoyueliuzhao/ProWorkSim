# v114：未定回合处理方案与分析口径

本轮处理v113结束时的8个未定回合，随后更新REF／PROJECT通过率差异分析。两组均以OpenHands为基础；模型仍为DeepSeek Flash非思考，累计输入＋输出每题5M，不训练、不恢复Qwen或组织实验。

## 处理范围

| 原记录 | 已核实原因 | 本轮处理 |

候选与终态证据保留：7244／7251的原记录仍是`technical_unknown`，原归档的`official_final_candidate:false`也不改。新端点名为`recovered_stopped_code`，只评价可信停止树的代码状态，不声称原会话正常结束或获得了完整任务预算。原正式端点和含补充端点的诊断结果会分开呈现。尤其7244的停止树评分不能代表继续使用余下约3.26M预算后的能力。

## 环境修复边界

新地址来自本次DNS与6次有界公开GET检查，选定`16.58.42.220`；不采用旧`3.211.106.232`。旧地址在80／443均返回同样的502页面，两个被检查的当前地址均返回200。此检查只定位服务节点，不代替容器内环境资格。

用户已回复“允许评分侧更新CA”。新配置仅在Requests两题的评分容器中安装`/pws-fixtures/ca-v114`：原仓库CA文件保持原字节，原预测补丁保持原字节；SSL加载器只在原CA路径和SHA均吻合时，使用“原CA＋冻结当前公开CA”的评分专用副本。其他CA路径直接透传，不修改证书验证模式或主机名校验。报告明确记录**有效信任集改变**，不把它说成原TLS条件完全未变。宿主信任库、宿主网络与模型工作区均不修改。

新gold／empty覆盖两道HTTP题及两道测试reset修复题，共8个控制。另两道停止树补充候选的原环境在完整等价证据下复用。HTTP评分串行，并保留总评分并发2；不自动重试429或502。官方公开服务现有请求频率限制，故不并发轰击该服务。[httpbin官方说明](https://httpbin.org/)

## 执行与预算

最多26个新评分／生成容器、4个新专用卷：8个控制容器，4对原未调用回合生成环境，8个代码评分容器，最多2个独立交付评分容器。最多4对生成与2个评分，合计40 CPU／192 GiB；只使用原项目普通用户服务的新生命周期。容器默认network=none、drop ALL、无宿主绑定、端口或GPU；只有Requests评分使用既定私有网络能力及受限httpbin通道。

Requests新通道最多10个session、每session512连接／64 MiB，总计最多5,120连接／640 MiB。新4个原回合累计生成上限20M token；不重采已调用的7244／7251，不新做neutral或部署诊断。继续原累计350元账本，准备时可用195.65182408元，旧5.24288元未定预约保留。不能把剩余额度当成保证所有任务必然完成。

生成、原候选补评共享同一两槽评分门，局部异常独立留档，已清理的单题失败不阻塞其他任务。旧候选补评不作为新的独立任务，也不增加平均模型token的分母；原费用只计一次。旧结果、补丁、测试与来源证明不覆盖。

## 后续差异分析

处理后重新计算完整题单与同题配对结果、仓库分层、每题实际token和终止原因，并逐题复核分差。报告区分：预算结束、输入组织成本、工具使用／选择错误、模型修复错误、交付状态以及评分／环境故障。

当前仅作为待更新的中期证据：44个共同已评分任务为24个共同通过、11个共同失败、8个仅REF通过、1个仅PROJECT通过；不能代替完整50题结果。PROJECT每次agent请求平均输入约64,102 token，REF约25,215；摘要本身均不到总token的0.7%。已直接观察到PROJECT在每步追加整份受管观察并保留多份相同任务说明，增加输入占用。另有明确模型验证错误，不能把所有分差归于接口。正式结论以补评后同题记录为准，未经消融不量化某个机制的独立因果贡献。

未来原生历史修复已另行实现并通过CPU／真实SDK脚本控制，但不会在本批四个剩余回合中换掉已冻结的模型策略。其效果需要另批评价，不能计为本轮成绩提升。
