每条固定交付的完整门由独立来源/consumer API、所选上游回归、consumer执行时实际调用指定库API三项合取。七份固定交付结果完全一致：

两个非空独立输入组分别以`sensor = NULL`、`region != 'north'`开始，均得到`ValueError: Expression is not a single Comparison: ...`。每组执行只观察到`sqlparse.parse=1`，`Comparison.left/right=0`。属性调用缺失是同一提前异常的后果，不能另算一个独立失败原因。

**共同的实际代码断点**是把`sqlparse.parse(expression)[0]`得到的Statement直接判断为Comparison，而没有取其内部的比较节点。代码在返回记录前拒绝了合法表达式。当前[consumer初始桩](../../examples/software-sources-v028/sqlparse/consumer-stub.py)只有NotImplementedError，没有预植这段错误检查；错误是在模型实现中产生的。[固定参考实现](../../examples/software-sources-v028/sqlparse/consumer-reference.py)通过内部节点访问这一接口。此说明来自原始源码和已保存的动态异常，未在报告阶段重新执行。

`support-4`没有固定交付，独立assessment为`submitted=false`、`No fixed integrated delivery`，因此API/回归/调用探针的最终交付验收为**未执行**，不能填成相同的0/3或拿某个临时工作区代替验收对象。其真实探索测试失败另外报告。

## 4. 八槽真实工作过程

以下为原始行为描述，不是对失败轨迹追加有效Mapper类别。每槽原件统一位于`runs/software-allocation-v029/support/actual/collection/slot-N/`；`assessment.json`指定最终验收版本，`experience.jsonl`保存全程行为，`software-evidence.json`的过程前缀可能只截至选定固定交付。

### support-0：名义分工，代码编辑集中在B

B认领库修复、A认领consumer，但四次实际文件修改全部由B完成，A没有代码写入。A导入B的patch-1、测试并发布patch-2；B再导入产生consumer冲突，重写解决后提交最终delivery-2 / B v7。双方都有工作动作，但不能用任务名或patch作者证明A实现了consumer。5次可见回归均通过，独立consumer仍失败。

### support-1：双方重复修库，A编写consumer

B名义负责库、A负责consumer；双方实际都独立将Comparison.right修为`self.tokens[-1]`，A编写consumer并先提交。B导入A的patch-1，反复运行相同上游回归后提交delivery-2 / B v3。9次回归均绿色，没有新增成员consumer自测。两次SDK格式错误、五次世界工具拒绝并未阻止固定交付，但交付仍包含共同consumer错误。

### support-2：发生真实责任转交，后来的工作区未形成新交付

A负责库、B负责consumer，双方都做了库和consumer修改。A请求责任转移，B实际将consumer委派给A；A发布涵盖两项任务的patch-2，提交最终验收对象delivery-1 / A v4。B此后导入产生冲突并重写自身副本，但没有新的合法提交；这些后续动作保留在原始经历中，不能回填到已固定成果。12次可见测试中11次全过，第一次在原库缺陷上失败。模型某条patch说明提及`tokens[0].get_value()`，实际编辑回执是`tokens[-1]`，归因采用回执。

### support-3：冲突修复与等待唤醒实际发生

A先实现consumer，B修库并另写consumer。A导入B的patch-1时发生冲突，最终采用B的consumer版本；B随后导入A的patch-2并提交delivery-2 / B v4。两次等待均由实际工作事件唤醒。6次可见测试5次全过，另一次发生在A尚未导入修库时。协作闭合到了固定版本，但双方同一consumer错误仍保留。

### support-4：错误的冲突解覆盖正确修复，无固定交付

B将Comparison.right改为`self.tokens[-1].value`，错误地返回字符串；真实上游测试出现`'str' object has no attribute 'value'/'ttype'`。A曾独立正确改为`self.tokens[-1]`并写consumer，其前4次回归均5/5通过。B导入A的patch-1后发生库文件冲突，解冲突仍保留错误`.value`并发布patch-2；A回导再次冲突，最后也保留错误解。9次测试仅4次全过，其余包括冲突标记导致的驱动失败及错误返回类型失败。

A三次提交均被工具拒绝：当前版本未测试一次、当前版本未固定发布两次；另有越权发布不属于自己的任务。A最终决策预算耗尽，B格式门终止，未形成任何固定交付。A的consumer还静态可见错误导入/节点判断，但未进入最终独立验收，不能把这些静态问题写成已实测的额外失败。

### support-5：A完成全部源码，B导入与再发布

A认领库、B认领consumer，实际两次源码编辑都由A完成。A的patch-1已含两文件，B导入并测试后发布patch-2；A回导、发布patch-3，最后提交delivery-2 / A v5。A回导B的patch-2无实际字节变化，证据中`changed_paths=[]`、`authored_changed_paths=[]`，不能以B“Implemented consumer”的描述认定原创实现。7次可见测试全过，完整consumer依旧失败。

### support-6：consumer自主测试暴露错误，但没有修复

B先修库并发布仅包含库修复的patch-1；A通过消息请求该补丁，实际导入后编写consumer，测试、发布patch-2、提交delivery-1 / A v3并结束。这是可观察的生产者—消费者先后工作。B随后回导A的consumer，尝试固定和提交自己的整合树，多次被当前版本发布/任务所有权要求拒绝。

B后来新增`test_member.py`，真实调用`comparison_records(["A = B"])`。之后四次run_tests都得到同一ValueError；B未改consumer，继续读取和测试后耗尽48次决策。相关原始experience事件为seq661（写测试）、695/814/865/1086（四次失败测试），物理JSONL行为相应序号加1。因此不能概括成本轮所有成员都没测试consumer，也不能称B已修复错误。

该槽`software-evidence`选定交付前缀只有2次test，而全程runtime实际8次；后4次失败发生在A的固定交付之后，不改写该交付。源码另外有返回token而非字符串的潜在问题，但动态检查已在节点判断处提前异常，未触达该后续路径。

### support-7：重复修库，B导入consumer后再发布失败版本

双方各自实际修库，A另外编写consumer并发布含两文件的patch-1。B已有同一库修复，因此导入A补丁时实际变化仅consumer。A提交delivery-1并结束；B因未固定自己当前版本的一次提交被拒，继续较长时间读取，最终发布patch-2、测试并提交delivery-2 / B v3。31次read_file中B占28次。6次可见测试中5次绿色，初始缺陷版本一次失败，最终consumer共同错误仍在。

## 6. 为什么没有进入B/G/I

两成员的支持账完全相同：

| 成员 | 原始M | n_z | n+ | v | b | 配置自由度 |
|---|---:|---|---:|---:|---|---:|
| member_a | 8 | {} | 0 | 0 | {} | 0 |

8条联合经历对应16个成员投影，不能把后者称16条独立样本。8条都reward-eligible，record、permission、basis均真，但delivery均假，因此work-valid=0、mapped=0。这里最先阻断的是完整工作有效性，没有候选类可进入最低频数2的支持统计；不是已经发现多个可靠类却仅差一次频数。空的b表示无支持类别，不是一个合法的全零概率分布。

过程记录确实显示集中修改、重复实现、真实导入、委派、冲突、等待/唤醒等不同工作关系，但本轮不能把这些失败模式事后改名为有效Mapper类以凑支持。也不能从unmapped推断没有协作，或声称新Mapper已经在真实成功轨迹中证明了多类区分能力。

支持诊断中两成员`base_actor_mask`均为8/8 true，失败残余的诊断基础权重均为1、每成员总权重8，原始分母未删改。这说明当前来源/记录/可恢复自身动作条件满足；**不等于本轮已经执行并通过PPO行为概率、梯度或零优势门**。这些训练门没有运行，失败材料没有被丢掉，也没有实际执行Q=B更新。
