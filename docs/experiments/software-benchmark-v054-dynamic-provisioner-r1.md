# v054 动态常驻部署监控器 r1

本修订增加部署资源来源，不改变已固定的模型、数值路径、采样、上下文、预算、工具、题目、种子或评分器。现有任务和常驻模型不被打断。代码先在 `/tmp/proworksim-v054-dynamic-provisioner-r1` 准备，由主代理在运行边界统一集成、封源与启动；本报告不表示监控器已经在生产环境启动。

## 授权与资源条件

物理 GPU 0–7 均可承接新增 MATCH/PROJECT 常驻实例；全局最多八个实例。卡型固定本机 `NVIDIA A800-SXM4-80GB`，总显存至少 81,920 MiB、实际空闲显存至少 46,080 MiB。其他用户已有进程或高利用率不构成排除条件。监控器不停止其他作业，不降低原推理参数，不先运行占位分配。

轮询的显存只用于挑选候选。唯一常驻启动器先非阻塞取得物理 UUID 锁和全局实例锁，再读取实际显存并复核相同 UUID/索引；只有该检查通过才建立启动标记并加载权重。监控器不另持一把竞争锁。启动后的缓存预约继续使用原 `min(73728, free_mib-1024)`，原 native allocator、r3/r5 请求上下文和清账规则不变。

每张卡在本冻结策略中最多一次真正的加载尝试。启动器能证明零加载、零请求的 `gpu_lease_busy` 或 `gpu_capacity_gate` 可以等待后重新申请；已经开始的加载、模糊启动意图或失败的实际资格检查不会自动重试。失败仅阻止该新实例注册，其他已健康的实例可继续按队列策略工作。新实例若在交接请求中出现未知费用，保留现场并暂停精确登记的本实例进程组，不自动卸载、继续或复用。不同用户进程不在停止范围内。

## 每卡资格与证据范围

既有 GPU6 MATCH/PROJECT 与 GPU7 REF 的实际常驻进程、规格、ready 和真实交接回执按引用导入，不重新加载或重新运行准备请求。旧源码/实际运行记录保留其原身份，新队列明确记录该继承关系。

新增同型号卡复用原已通过的模型和数值配置容量证据；这不等于在新卡上重新完成了最大上下文容量试验。新卡必须通过自己的实时显存门、实际模型加载，以及一次 MATCH 会话和一次 PROJECT 会话的交接检查。每个独立准备许可最多两个真实生成请求，每会话一个；实际原输出上限 2,048 保持，使用明确的短合成提示，不使用正式任务内容、不占正式槽。准备许可另外绑定本部署 ID、物理 UUID、索引和 pool policy，回执中的真实 owner resource binding 再核对这些设备身份。

检查沿用已实现的真实 owner 控制：同一 PID/模型对象、只加载一次，独立 seed/窗口/ledger，原 RNG 与学习 guard 恢复，旧 socket 失效、请求缓存清理、allocator 保留。只有实际 `passed`、两个请求均结算且未结数为零的回执才允许登记。新卡的实际 token 单列准备成本，不计正式成绩，也不拿原 GPU6 的 775 token 当作新卡的验证结果。

## 追加登记与队列

冻结策略版本为 `v054-resident-pool-policy-v1`。注册目录 `events/` 使用顺序文件 `00000001.json` 等，每条包含前条引用、策略引用、部署与实际资格引用。写入先完成临时文件并 fsync，在独占登记锁下用不可覆盖的 hard link 发布完整事件；读者不会读到半写文件。注册和退役都是追加事件，旧记录不覆盖或删除。运行时 `event_reference` 是计算得到的文件引用，不写进事件本身形成循环 hash。

新队列每次领取固定正式槽时锁定当前注册引用。已经退役的注册不能再取得会话。池文件的追加不改变全局固定源码或任务绑定；每次新部署仍引用本次冻结源码。监控器不改变正式授权，不创建任务 claim，也不负责模型 episode/评分的重试。MATCH/PROJECT 已无 pending 库存时停止追加部署，保留已在途的准备及现有服务。

## GPU7 一次性转换

GPU7 在全部 500 个原 REF 槽完成前仅属于 REF。转换不依据成功率或分数：必须逐题匹配固定 slot 身份、generation 已闭合、官方 code 报告明确、无未决评分；另读原控制器费用 ledger，要求无执行/计账完整性故障、无在途预约或未知实际费用。REF 常驻状态还必须无活动会话、无在途请求、未中毒。

监控器先保存队列完整快照、实际 resident status、unit/InvocationID/PID 与转换意图，再仅停止这个已登记的 REF unit。确认其主进程退出、精确 cgroup 无子孙进程后，追加退役和闭合记录，随后按普通 MATCH/PROJECT 新卡流程重新取得 GPU7 的锁、复核实时显存并加载一次。任何不确定的中断或关闭失败都会保留转换失败记录，不自动再次尝试关闭或加载。其他卡不需要等待 GPU7 转换。

## 运行入口

主代理完成统一封源后，用项目宿主 `.venv/bin/python` 执行：

```text
tools/monitor_resident_pool_v054.py prepare
  --output <新的 pool runs 目录>
  --source-manifest <最终 source-manifest.json>
  --inherited-registry <现有两服务 registry.json>
  --inherited-admission <原真实 resident-admission-r1.json>
  --queue-state <接续队列 state.json>
```

此步骤只写策略，零模型、零 GPU 分配。实际监控命令为 `tools/monitor_resident_pool_v054.py run --policy <policy.json> --sha256 <真实 hash>`，应放入专属 `Restart=no` 的 user unit，环境 `PYTHONPATH=<repo>/src:<repo>`。每 30 秒观察一次，持续状态写入 `provisioner-state.json`；每个候选启动/准备检查采用自己的独立 systemd unit 和日志目录。重启监控器只接续能证明仍在运行或已有完整回执的准备过程，模糊意图不重放。

## 本次必要控制

只运行两个新增 CPU 合成状态控制，均通过，用时 0.05 秒：完整不可覆盖的事件发布、重复物理卡拒绝、未闭合 REF 禁止退役、退役后旧注册拒绝、固定 500 REF 身份与未知报告门，以及零加载资源等待和已启动失败不重试。未运行真实 GPU、新的模型探针或旧三组 CPU 链路。卡型/索引/八实例 lease 路由由并行部署适配代理的必要控制覆盖，实际新卡交接将在出现合格空闲显存后分别留下真实回执。

这些控制证明监控器的部署和记录逻辑，不能代替尚未发生的新显卡加载/真实两会话资格。当前没有据此增加正式完成率或声称新增卡已经就绪。
