# 角色感知上下文试跑总结报告

**实验：v203.2.3；报告日期：2026年11月15日。** 本轮计划4题×3条件，共12个双Agent回合。恢复批次实际运行11回合，均受公开测试接口故障影响；已对11份事先锁定的终态代码完成官方补评，**8份通过、3份未通过，评分技术未知为0**。Flask K1在恢复批次未启动。用户已决定保持130元累计上限，只补评、不再生成。

**本轮得到的是受损执行过程中的代码端点结果，尚不能判断角色感知上下文是否提高正确率或降低任务总成本。** 三组共同完成的三道题，补评结果完全一致；样本很小，且测试反馈共同失效，不能据此认定三种方法等效。

## 1. 三组到底有什么区别

三组都基于OpenHands及ProWorkSim受管接口，固定两人：001开发并最终交付，002独立复核。模型均为DeepSeek Flash非思考模式，不训练、不调整组织结构。

| 条件 | 直观解释 | 具体处理 |
|---|---|---|
| **K0 原有上下文** | 按现有方式阅读工作历史 | 保留原v117历史呈现与摘要；本身已有摘要和静态内容折叠，并非完全不压缩 |
| **K1 通用信息选择** | 从旧观察中挑与当前任务相关的信息 | 按通用相关性、版本等规则选择历史字段，不增加角色特定权重 |
| **K2 角色感知选择** | 同样的信息，按当前职责排优先级 | 开发者优先相关消息与工作信息，复核者优先测试／候选证据，准备提交时优先交付状态 |

K1/K2只处理成员**已经看到过的历史PROJECT观察字段**，包括消息、交接、候选目录、测试覆盖、交付状态和组织记录。先移除这些历史字段的原默认呈现，再把选中的完整字段卡集中呈现一次，避免只是追加摘要却继续保留全部原文。最新观察、题目、系统说明、动作、工具原件及不可选字段保留；历史摘要算法相同。

二者使用同一候选池和4,096本地估算Token的选择上限，仅排序规则不同。来源引用用于审计，没有新增全文读取工具，也不保证被省略的动态历史可以无损恢复。因此这是**历史观察字段选择**试验，不是整个对话或全部工具输出的压缩实验。

## 4. 为什么三组平均都接近500万Token

原记录确认，11个恢复回合**全部触及团队Token准入门**。每次继续调用还需预约下一次输入和最多32,768输出，因此最终账面通常略低于500万，并不要求恰好扣满。

这使总用量被共同上限限制：压缩可能改变预算内的请求数量，却未必降低最终总量。单看496万—498万的均值，既不能证明压缩有效，也不能证明压缩无效。当前更严重的问题是公开测试反馈失效，模型长期尝试却得不到正常验证，成本和策略效果被混在一起。

恢复批次输入占总量**99.72%**。开发成员消耗3,720.16万Token，复核成员1,746.85万；这包含各自代码阅读、历史、工具反馈及摘要，不能把复核成员的全部消耗当通信成本。43次摘要请求合计29.26万Token，已经纳入总量；其余1,026次为Agent请求。缓存输入包含于输入，不重复相加。

本报告计入了输入和输出，但没有将供应商总账按通信、工具、模板等来源作新的完整分账；因此不报告未经核验的“通信开销占比”。也不将字段选择器的本地估算节省量当作实际账单节省。

## 5. 故障及修复：为什么补评不能恢复实验有效性

| 问题 | 实际影响 | 处理与当前边界 |
|---|---|---|
| 旧176核准入检查 | 首次部署在模型调用前停止 | 独立修订为冻结池中的24核角色分配验证；旧失败保留 |
| 格式反馈后的消息索引错位 | 较早九个短回合共48次调用后中断 | 按投影前后索引映射及SHA核对来源；用原始失败响应重放验证，另立恢复尝试 |
| **测试脚本预加载缓存键不一致** | **11回合首次公开测试均失败，后续传输不可用；最终同步失败** | 新r5在进入缓存前规范化参数；删除私有源码后真实pytest验证通过，并增加永久传输失败时停止后续模型调用的检查 |
| Requests旧地址及空闲连接判定 | 评分环境先出现技术未知 | 新固定地址与严格HTTP帧完整性核验通过新gold／empty；TLS、部分响应和歧义情形仍不豁免，旧未知不改写 |

最主要的失效发生在求解阶段。预加载调用`load_base()`与实际测试调用`load_base(None)`被缓存识别为不同键，后者重新读取已被actor隔离清理的私有脚本，触发FileNotFoundError。传输通道随后保持失败状态，但模型继续运行到预算门，最后`sync_terminal`再报错。它不是单纯的末尾文件导出问题。

11份代码在最终同步前已唯一锁定。补评逐份核验原候选、补丁、树、版本和资源清理证据，只评原补丁、不修代码、不重新生成，因而代码是否通过官方测试可以确定；但无法补回模型当时没有得到的测试反馈。

新缓存修订与故障停止检查通过3项CPU控制。按用户决定，本轮没有再启动模型验证这些修订；下一轮正式模型实验仍需把修订接入真实部署并覆盖“actor封存后首次公开测试”的完整路径。

表中20次尝试不是20个独立任务；其中有重复任务与独立恢复。恢复批次缺少Flask K1，较早阶段的短暂失败调用不能补齐这一缺口。两阶段费用都保留，补评新增模型调用为0。费用采用冻结费率核算上界，不是供应商最终发票，也不包含CPU、内存、磁盘和评分墙钟成本。

累计上限130元，剩余**31.26元**，无未定API预约。最后一题被40元整队启动预约门挡住，不能说余额已用完。用户随后明确要求保持预算、只补评，故没有降低条件或再次调用模型。

现有11份候选全部补评完毕，评分未知为0，所有评分容器已清理；模型生成不再继续。本轮未训练、未使用GPU，也未修改共享服务器配置。清理已验证可重建的旧SDK展开目录约8.45GiB，档案、源码与实验结果保留。

## 7. 本轮可以得出的结论

1. 三组策略已实现，CPU与真实SDK控制证实角色排序及历史字段省略会实际改变输入；这只证明机制接线，不证明任务收益。
2. 11份受损执行所得代码中8份通过官方补评；共同三题三组结果一致。样本规模、缺失一组任务及测试故障均不支持方法优劣或等效结论。
3. 当前最明确的瓶颈是测试执行与失败传播。应先证明真实测试反馈和最终交付完整可用，再用冻结的新版本重做同题对照；继续增加预算不能替代这项修复。

用户目前未授权新增现金或恢复模型生成。本报告只结算现有实验与补评，不启动新回合。
