# v182 启动竞争修复与接续

v181 的四个真实零模型诊断全部通过；24 项 gold／empty 控制中，11 个仓库任务通过资格核验，Pylint-8898 的两个控制在容器启动见证读取处得到无法解析的 JSON，尚未执行官方测试，保留为环境未定。

首个同题四条件块并行启动时，多个线程同时写公共 `identity.json`。其中 M3-R 在任何容器预约及模型请求之前遇到 `FileExistsError`；另外三组继续生成。旧协调器把这个发生在进入任务前的错误也当成清理无法证明，停止了后续准入。这是启动与调度缺陷，不是模型失败。

本修订只改变宿主启动管理：模型标识创建加互斥；只对同时满足“原错误确为该文件竞争、没有任何物理 HTTP、没有 actor/controller/volume 预约”的原计划身份恢复首次进入；将旧 job 状态和证明追加保留后更新为 running，不删除旧记录，也不重采已调用模型的回合。后续局部启动异常仅在已消费资源却没有清理证明时才阻断新准入。

旧 v181 的三个在途回合继续运行，新协调器先补齐同题 M3-R 的未进入空位；首块结束后继续原预定顺序，不重复旧生成或评分。仍使用同一 250 元累计账本、原 v181 SDK 包、60 个身份、题目、模型、采样、工具、上下文和 5M 限额。四条件比较中应保留部署修订和启动时间差，不能宣称四组同时起跑。

临时共存两个普通用户协调器，各 8 CPU／32 GiB，使用不同 CPU 位置；生成仍共享最多 4 对、评分共享最多 2 路原预约槽。包括两个协调器的上界为 48 核等价、296 GiB，旧协调器自然结束后减少一个协调器的占用。没有新增系统 slice、宿主挂载或网络配置修改，不中断旧模型请求。全部容器身份沿用原计划中尚未消费的名额。

CPU 检查覆盖八线程同时创建标识，以及仅允许零调用零对象启动恢复。环境未定单独修复；不会因一题资格失败而取消其他题，也不会替换原题或将未知记为模型错误。
