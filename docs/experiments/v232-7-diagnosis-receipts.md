# v232.7｜修复仓库搜索证据与阻塞通知

上一轮 Sphinx-9591 中，诊断成员 002 搜到了失败测试的位置，却发现自己的可引用证据为空。它尝试把阻塞原因发给实现成员 001，消息又被“接收者无法承担新工作”的检查拒绝。本轮分别验证这两个接口，再看同一保存点上的模型自然行为。[原始在线记录](v232-6-need-followup.md)

## 改了什么

- **搜索有可引用的回执。** 仓库搜索直接返回本次操作的事件编号。模型看到的候选证据、调度提示和提交诊断时的校验共用一套筛选规则。编号只证明本人在当前分工生效后实际搜过相应范围，技术判断仍由成员作出。接收者若引用自己的证据跳过回读，还须符合原来的同版本条件。
- **允许记录已分配诊断的阻塞原因。** 在同一项待完成的诊断中，负责人可以把合规的阻塞说明发给组织图指定的在册接收者，即使对方已无法承担新工作。系统照常检查收发双方、沟通权限和引用。这条记录不分派工作、不补发模型调用。消息入账、接收者看到、接收者采取行动分别统计。

**为什么任务仍未通过。** 001 修改了测试预期，在 v8 工作树上运行自选公开测试并通过。回合到达团队预算边界，未形成合法提交。离线官方评分成功应用了锁定的工作树补丁，44 项原有回归检查均通过，但应由本题修复的 `tests/test_domain_py.py::test_pyproperty` 仍然失败。即使当时提交这个版本，其代码也无法通过官方验收。单题足以验证这次接口交接，尚不足以估计对任务通过率的影响。
