# v145：API故障修复与21项停止代码补评

本轮处理v143试跑中的21项技术未知。保持原40题×S1／FREE2／REVIEW2题单、候选和账本，新增执行层修复以及原停止代码的独立评分。没有新增模型尝试或API费用，不修改共享服务器配置。

## 核心原因

7396次API请求中21次异常，请求级比例0.284%；旧执行层一次异常就结束所在团队，最终放大成21/120＝17.5%的回合未知。19次是HTTP 500／503，另外2次只剩ValueError，历史日志不足以唯一还原原因。旧冷却逻辑还会被其他并发请求的成功清零，错误阶段和正文摘要也没有保留。

S1最后一次调用在14:21:36结算，未知请求都在15:02以后预约；不能把这次双人组受到的影响直接归因为协作架构。没有429限流证据，也没有异常仅由长上下文触发的证据。详见[根因统计与官方说明](software-benchmark-v145-api-rootcause.md)。

## 修复范围与验证

新版明确收到完整的临时HTTP错误后，同一请求最多3次物理尝试，每次独立计量。失败请求的费用和token上界继续保留；现金、团队5M、512次物理请求及总时间限制仍生效。共享滚动失败窗口不再被一次成功清空，退避时释放HTTP并发槽。截断响应、超时、断连、JSON解析未知不会盲目重试；新日志保留错误阶段、受限代码、HTTP状态、字节数／摘要、Retry-After与时间。

现金授权绑定唯一新账本，所有组共享原400元剩余的49.1863482元，不能重复复制余额。已通过23项CPU故障注入检查并接入新版受管宿主传输适配；**尚未调用真实API验证新版恢复效果，也未启动新的模型回合**。部署准备与边界见[API实现说明](software-benchmark-v145-api-resilience.md)。

## 原候选补评方法

21份候选均取原停止时最终交付成员member_001的唯一已提交源版本。10份补丁非空、11份仍为基线；没有选用另一成员的修改、较早版本或actor公开测试树。候选先导出、往返校验并锁定，再进入官方评分。恢复过程与用量边界见[停止候选恢复](software-benchmark-v145-stopped-candidate-recovery.md)。

评分使用原镜像、baseline、官方测试和已合格环境证据，采用新资源身份和run ID，最多两路、每容器4 CPU／16 GiB、每宿主评分进程4 GiB，默认network=none、drop ALL，无宿主绑定、GPU、新卷或新服务。仅四份Requests-1766／1921补评使用原已记录的私有HTTP／严格TLS通道，合计最多4 session、2048连接、256 MiB应用载荷；其他题不出网。原评分结果与模型工作区均不改写。

评分前21项冷启动校验通过。初版r1准备中的环境等价检查将`environment_factory`来源标签差异误认为有效环境变化，在创建任何容器前被拒绝；已单独保留r1，r2显式核对新旧来源与目录后比较有效配置。实际评分位于`runs/software-benchmark-v145/stopped-code-scoring-r2`。补评异常独立记账；只有无法证明自有资源清理的情况才停止新评分，避免扩大资源影响。

## 结果状态

21份补评均已执行并清理。v145先取得5份通过、14份未通过、2份评分网络未知；后者均为Requests-1766，端口80持久连接被60秒闲置门提前切断。随后独立v147实际gold／empty控制合格，原两份锁定候选重评均得到可信失败。因此**停止代码补评最终为5通过、16未通过、0评分未知**：FREE2为4通过／7未通过，REVIEW2为1通过／9未通过。v145原评分记录保留，[原补评摘要](../../artifacts/software-benchmark-v145/recovery-results-r1/summary.json)与[v147实际控评结果](../../artifacts/software-benchmark-v147/actual-controls-rescores-r1/summary.json)共同构成证据，不改写历史未知。

v147仅把该题的连接闲置等待延至180秒，总评分期限、连接／流量限额、CA、TLS及测试逻辑均未变。empty和两份候选的相关连接分别在82.45、86.83、78.74秒取得真实双向EOF，证明原60秒门会过早截断这些连接；没有忽略网络异常或直接把字节计量当作完整HTTP证据。详情见[Requests评分修订](software-benchmark-v147-requests1766-idle.md)。

补评端点为`recovered_stopped_code`。代码能够通过不等于原SDK回合正常完成，也不补造合法交付或权威API用量。原21项生成中断、7.252874元未定预约及用量未知均保留；原会话缺少已验证的联合恢复入口，本次没有把新会话或重采伪称为原地续接。

用户随后明确要求真实测试及网络故障恢复队列，并授权累计API上限450元。因此已经另行启动[v146独立恢复](software-benchmark-v146-independent-recovery-plan.md)：21项首次独立重跑，只有再次发生临时技术故障时才使用预留的第二次独立身份；评分网络故障只重评同一补丁。v145停止补评继续保留为补充，不能替代v146完整回合结果。

## 真实重测中的闭合修复与当前结果

真实运行发现另一处确定性缺陷：原导出器把运行ID前缀写死为v142。模型已经达到正常`bounded_work_closed`、API已结算时，新的v146 ID仍会在最终导出被拒绝。该错误只影响导出，不需要重新调用模型。v149将执行身份与模型／角色合同分开，并根据原冻结题单、正常SDK结束证据及停止的完整世界，自动纯补导出最终代码和合法交付证据；原错误文件保留。详见[正常闭合补导出](software-benchmark-v149-closed-export-recovery.md)。

正式评分当前由v151自动队列处理：代码与合法提交同树时复用同一次官方评分，只有不同版本才分别评分；技术评分失败最多同锁重试一次，正常未通过不重评。先前v150已经做过的重复同树评分作为额外历史观测保留，不用于挑选更好结果。主模型运行全程未因后处理交接而暂停。详见[正式评分与同树复用](software-benchmark-v150-v151-normal-export-scoring.md)。

北京时间2026-11-07 22:34的合并状态：21项首次恢复已全部派发，17项正常模型工作已补导出，13项已经完成代码和交付两个端点的正式测定，其中代码通过7项、合法交付通过6项；另4项仍生成、4项等待评分收尾。这是实际DeepSeek调用及完整模型回合的正式评分，不使用旧停止树补评替代。新队列1670次HTTP已结算，尚未出现新API传输错误；新增已结算约74.7251元，累计450元中扣除原费用和未定预约后约余24.4612元。该快照不是最终成绩。

后续状态应使用只读`tools/summarize_role_recovery_chain_v152.py`，合并146模型、149正常导出和151正式评分；仅看146的原始`technical_unknown`会把已经修复的导出记录再次误报为当前网络故障。
