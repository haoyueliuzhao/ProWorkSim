# v073：有一张合格显卡就先启动一个原驻留身份

v071 准备后，原指定 GPU1／GPU5 的剩余显存不足。v073 改为封存允许的资源范围，在每次真正启动时选择可用显卡，不再要求两张卡同时合格，也不因显存状态变化反复新建部署版本。初稿曾要求两张卡同时合格，真实准备因此拒绝，未写出绑定、授权或资源预约；该初稿的源码、测试和说明已保存到 `local-expansion-validation-r1/superseded-two-card-draft/`，由本修订取代。

`--prepare` 不查询 GPU、不预约资源，只为原未消费身份 model-4／model-5 封存能力授权：允许原范围 GPU0—7，活动驻留最多四个；每个服务仍为 12 CPU／96 GiB，所有任务继续受共享 152 CPU／832 GiB 总上限约束。原 model-1／model-3 保持运行，历史退出身份不重启，原 v071 授权原件不修改。

`--launch` 逐个身份持有原驻留分配锁，实时调用原容量检查：仅接受原允许的 A80080GB、至少 50176 MiB 剩余显存，并排除本项目活动驻留已使用的 UUID。优先 GPU7，其次 GPU0，其他合格卡按剩余容量排序。有一张合格卡就立即为一个身份调用原 `make_spec` 和 `unit_command`；第二项没有容量则等待，不消费身份。第一项写入的原 spec 会被第二项重新读取，因此即使显存尚未变化，也不会把两个新驻留分配到同一 UUID。

实际选中的 GPU 和容量观察写入原 spec 与启动意图，并引用本次能力授权。每次启动仍复查共享内存和磁盘余量，最终预约由原全局账本执行。暂时不足不消费身份；启动失败或回执不明确的身份保留证据、不盲目重启；已成功项不因其他项失败回滚。不停止其他用户进程，不修改共享主机配置。

模型继续使用原 BF16 Qwen3.5-9B、131072 上下文、32768 输出、0.6 显存比例和原采样；原中性准入、完整上下文缓存验证、就绪判断及资源清理由原生命周期承担。原主协调器仍最多四个任务 future，现有回合不迁移、不重采。新增本地驻留会消耗共享资源，因此 API 实际环境并发可能相应下降，不能同时宣称两侧最大并发都保持不变。

必要 CPU 控制共四项，均通过：准备阶段无 GPU 查询且单卡可先启动一项；双卡逐项选择不重复占用并拒绝重启已消费身份；共享资源不足不消费身份；GPU 范围和授权上限不能被突破。Ruff 和差异检查通过。测试全部使用临时文件及注入夹具，没有真实 GPU、模型、API、容器或服务调用；主流程的实际启动与就绪证据另行记录。
