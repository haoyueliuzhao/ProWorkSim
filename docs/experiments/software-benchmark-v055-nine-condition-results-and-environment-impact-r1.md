# 九组实验简明报告

2026-10-23。三种条件都让一个模型独立修复同一批 500 道代码题，使用同一个官方评分器。我们想弄清：成绩变化来自模型的运行设置，还是来自项目的工作方式。

**三种条件，分别是什么？**

| 条件 | 通俗名称 | 模型怎样工作 |
| --- | --- | --- |
| REF | 原生工具，较宽松设置 | 使用 OpenHands，可以用终端查代码、修改文件、自选公开测试；允许更长的上下文和单次输出 |
| MATCH | 原生工具，项目设置 | 仍用上述工具，但把推理设置和资源限制调到与项目组一致 |
| PROJECT | 项目工具，项目设置 | 沿用 MATCH 的设置，改用 ProWorkSim 规定的查阅、修改、测试和提交方式 |

**REF → MATCH：看运行设置改变后，能力变化多少。MATCH → PROJECT：看进入项目环境后，又变化多少。**

REF 也有预算限制。Qwen 前两组还改变了思考开关和推理后端，因此不能将它们的差距只归因于“预算少了”。

**项目工作方式，具体多了什么约束？**

例如定位一个错误：原生工具允许一条命令跨文件搜索，再运行自己选择的公开测试。PROJECT 需要通过规定接口列文件、在单个文件内搜索、分页读取结果，并使用预设测试入口。更多读取和操作步骤会占用有限的行动机会。

修好代码后，PROJECT 还要求对当前版本运行测试、固定补丁、正式提交，才能形成合法交付。报告分别统计“最终代码是否正确”和“是否完成项目交付”；**没提交，不会自动算作代码修复失败。**

**为什么要引入这些机制？因为项目面向多人协作。**

- 每个成员有独立代码副本，通过固定补丁交换成果，用于避免相互覆盖并保留版本来源。
- 任务领取、消息和责任转交，用于说明谁负责什么、怎样交接。
- 同版本测试、正式提交、预算和操作记录，用于确认交付的是哪版代码、做过什么验证、花费多少资源。

这些机制增加了工作规则，也为多人协作提供了基础。但本轮只有一个 Agent，没有实际分工和伙伴互检。正常闭合回合也没有执行跨成员消息或交接，任务板基本未用。因此，**本轮测到了协作环境的单人使用成本，尚未测到团队收益，不能把低分归因于大量协作沟通。**

**结果怎样？**

每组固定 500 题。下限为已确认成功比例；上限假设所有技术未定题最终都成功。这是结果范围，不是置信区间。

| 模型／模式 | REF | MATCH | PROJECT |
| --- | ---: | ---: | ---: |
| Qwen* | 25.0%—27.2% | 12.0%—13.2% | 13.0%—15.2% |
| DeepSeek 非思考 | 57.0%—58.4% | 54.6%—60.0% | 42.0%—50.4% |
| DeepSeek 思考 | 61.2%—63.2% | 37.6%—51.4% | 47.4%—53.2% |

*Qwen REF 开启思考，MATCH／PROJECT 关闭思考。运行中有已记录的程序修订，上表是累计结果。*

**目前最有把握的结论：**

1. **Qwen 的主要下降发生在运行设置改变时。** 换成项目接口后，没有显示同等规模的额外下降。
2. **项目环境确实影响了 DeepSeek 非思考模式的修复能力。** MATCH 已知成功 273 题，PROJECT 为 210 题；即使考虑全部未定结果，下降方向也不会反转。尚不能确定每条规则分别损失多少分。
3. **思考模式受短输出与历史处理影响。** 部分输出被截断，原生框架出现空历史摘要；不能把这些问题全解释成模型能力不足。PROJECT 与 MATCH 的优劣仍未确定。
4. **代码正确和交付完成是两件事。** 三种 PROJECT 条件分别有 17、38、52 个正确最终版本缺少该版本的合法交付证据。

下一步应先修复已发现的工具参数与执行器不一致，改善受管搜索及交付操作，再单独验证具体规则。多人协作是否值得这些额外步骤，需要在相同总预算下另做团队对照。
