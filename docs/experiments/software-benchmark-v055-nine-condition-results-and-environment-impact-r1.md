# 九组实验简明报告

2026-10-23。**本轮主要发现两点：当前累计预算不足以支撑“充分发挥模型能力”的参照测试；项目环境接口也存在需要修复和改善的问题。** 两者共同限制了结果的解释，不能把当前分数直接当作底座模型的充分能力。

**三种条件怎样比较？**

三组都以 **OpenHands** 为基础，在同一批500道代码题上使用一个实际Agent、同一官方评分器。

| 条件 | 工作方式 | 运行设置 |
| --- | --- | --- |
| REF | OpenHands原生工具，可跨文件搜索、自选公开测试 | 较长上下文和输出，但整题仍限50万token |
| MATCH | 仍用OpenHands原生工具 | 对齐项目的推理设置和资源限制 |
| PROJECT | OpenHands上接入ProWorkSim受管工具和协作规则 | 与MATCH相同 |

REF→MATCH看运行设置变化；MATCH→PROJECT看项目工具和工作流程的整体影响。REF是本轮的外部参照，**不代表预算已经充分**。Qwen REF开启思考，MATCH／PROJECT关闭，后端等也不同，前两组分差不能只归因于预算。

**九组结果**

每组分母固定500。区间下限为已确认成功比例，上限假设技术未定题全部成功；这是结果范围，不是置信区间。运行中已有程序修订，下表为累计结果。

| 模型／模式 | REF | MATCH | PROJECT |
| --- | ---: | ---: | ---: |
| Qwen | 25.0%—27.2% | 12.0%—13.2% | 13.0%—15.2% |
| DeepSeek 非思考 | 57.0%—58.4% | 54.6%—60.0% | 42.0%—50.4% |
| DeepSeek 思考 | 61.2%—63.2% | 37.6%—51.4% | 47.4%—53.2% |

**结论一：以充分能力评价为目标，当前累计预算上限过低。**

50万token累计计算每次输入和输出，重新输入已有历史也会再次计账；它不是50万新增文字。即使REF允许较长上下文，仍会很快受到整题预算限制。

| REF组 | 因累计预算截止／全部计划 | 占比 | 截止时调用次数中位数 |
| --- | ---: | ---: | ---: |
| Qwen | 469／500 | 93.8% | 25 |
| DeepSeek 非思考 | 266／500 | 53.2% | 26 |
| DeepSeek 思考 | 286／500 | 57.2% | 21 |

合计**1,021／1,500回合，68.1%**因累计预算截止，远未用满128次调用额度。停止时余额中位数仍有约4.5万—4.9万token，却不足以预约下一次完整输入与最大输出。预算停止子集的97.8%—99.0%实际token用于输入，三个REF均无历史摘要调用；主要消耗来自解题请求输入，并非大量新增输出或摘要调用。

这说明预算确实限制了继续修复的机会。但1,021个截止回合中已有325个代码成功，不能把其余688个未解决题全部归因于预算，另8个评分未知仍保留。还有17个计划回合未纳入本次停因审计。**需要提高预算做独立对照，才能量化分数被压低多少。** 小米60.0分对应的累计预算仍未核实，不能保证扩大预算就能追平。

**结论二：项目环境接口存在实现缺陷、操作负担和交付障碍。**

- **实现缺陷需要直接修复。** 查看代码差异的工具说明允许部分参数，实际执行器却拒绝这些合法参数；这是工具契约不一致。
- **查找和验证的操作负担需要改善。** 当前没有仓库级搜索，查阅和测试反馈需要分页，测试也限于预设入口。Qwen PROJECT中59.36%的记录动作是列文件，表明定位成本很高；DeepSeek没有同样程度的列文件现象，不能将这一比例推广到所有模型。
- **正确代码到正式交付之间还有障碍。** 修好后需要对当前版本测试、固定补丁、显式提交。Qwen、DeepSeek非思考、思考分别有17、38、52个正确最终版本缺少该版本的合法交付证据。报告把代码正确与项目交付分开计分，未提交不自动算代码错误。

整组证据以DeepSeek非思考最明确：同资源的MATCH已知成功273题，PROJECT为210题；即使把未定结果全部按最有利于PROJECT的方式补齐，PROJECT仍至少低4.2个百分点。这支持项目执行层存在净损失，但尚不能给每条规则分配损失百分点。Qwen及DeepSeek思考模式没有同样明确的PROJECT额外下降，不能概括为所有模型都受同等影响。

这些规则服务于多人协作：独立代码副本、任务责任、消息和补丁交接，以及可信的版本与交付记录。**需要改善的是具体实现和使用成本，协作机制本身的净收益尚未测量。** 本轮只有一个Agent，没有实际伙伴分工、互检或成果复用，不能以此判定多人协作无效。

后续应将两项工作分开验证：保持其他条件不变，提高累计预算；同时修复工具契约、改善受管搜索和交付操作。分别记录新版本效果，才能分清预算与接口各自的影响。
