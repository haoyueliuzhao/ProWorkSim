## 耗时与优化范围

原学习窗口有 16 槽、682 条决策，6,964,120 个输入 token 和161,827个输出目标，总实际序列长度7,125,947，单条最大15,906。当前功能式学习器对每个输出 token 逐层扫描并通过 checkpoint 重算保留完整前缀梯度；所有候选又从同一个完整 common 重复这些计算。已观测的 B 反传决策周期均值约129秒，但长短决策差异很大，不能当作稳定单步时长。

采用缓存的是“同一原始决策、同一个精确浮点 loss 权重”已经真实算出的裁剪前梯度。缓存未命中仍调用原函数和原 weighted loss backward，命中后按原顺序、原设备累积；所有候选仍各自完成全窗口、梯度裁剪和一次 actor/critic AdamW step。每个实际反传都核对缓存累积算子与原生累积结果逐位一致。

共享的无梯度行为概率门也只在相同完整状态、材料与源码绑定下复用。critic、更新后诊断和全部评估按原定义执行。旧435个 `src/scripts` Python文件与原clean提交逐字节核对，新版本只添加执行和缓存实现。

## CPU 和 CUDA 数值结果

| 控制 | 实际结果 | 能支持的结论 |
|---|---|---|
| 官方 tiny Qwen，FP32 CPU | B/加权/重复加权的7类张量树比较均逐位一致 | 此有限配置的 exact-weight 缓存通过 |
| 官方 tiny Qwen，BF16骨干+FP32 head/LoRA，CPU | 同上 | 混合精度 CPU 控制通过 |
| 原正式混合精度配置，CUDA A100，efficient-only attention | 21项比较全部逐位一致 | 原声明 profile 的有限 CUDA 控制通过 |
| 额外全FP32 CUDA 配置 | 严格逐位门失败，梯度最大绝对差4.66e-9 | 保留失败，不准许外推到所有 CUDA profile |
| BF16单位叶梯度事后乘权捷径 | CPU梯度相对L2差0.00846878，CUDA约0.0077587 | 严格门失败，明确不用于生产 |

每个 profile 的重复加权候选均命中3/3行，真实 actor forward/backward 均为0；首次加权候选命中1行、真实计算2行。正资格比较包含非零 LoRA、已存在3步的 Adam 状态、正负优势、非单位权重、固定残余、非线性梯度裁剪、更新后参数及 critic。

两配置 CPU最终资格耗时11.98秒。CUDA探针总计28.86秒，最高allocated18,733,568字节（17.87MiB）、reserved23,068,672字节（22MiB），没有加载9B或采样真实任务。GPU当时共享使用，这个时间不是9B速度基准。

**整份双配置 CUDA 探索报告的 `passed=false` 保持不变。** 正式准入只使用早已冻结的 mixed BF16/FP32 head/LoRA/efficient-only路径及其严格逐位门；并非根据新结果改选profile或放宽阈值。第一次CUDA启动在模型创建前因计数器初始化顺序失败，错误另存；仅修正lazy initialization顺序后执行同一数值控制。

## 完整 updater 对照

真实 tiny CPU LoRA 控制先以 autograd 填充 actor/critic 的3/3优化器状态，然后每个候选完整恢复相同common、原窗口与RNG。32条原token决策、64个输出目标、16槽分母均保留。

| 新执行情形 | 实际actor反传 | 缓存命中 | 行应用总数 | 与原updater完整状态 |
|---|---:|---:|---:|---|
| 冷B | 32 | 0 | 32 | 逐位相同 |
| 热B | 0 | 32 | 32 | 逐位相同 |
| 首个加权候选 | 2 | 30 | 32 | 逐位相同 |
| 重复加权候选 | 0 | 32 | 32 | 逐位相同 |

比较包含裁剪前梯度、actor、critic、两优化器全部状态及RNG；后续行为概率全部命中32行、不新增该项前向。该测试直接调用新增完整updater，并非只测试一个缓存加法函数。它不是9B训练成绩。

## 实际冻结清单的纯CPU预算核算

脚本读取真实P2材料和冻结配置，未加载模型、未读取开发/确认成绩、未执行选择。一个代表G-raw候选还通过原完整权重验证路径，682行及所有原分母一致。

- 27试训：原18,414行反传，精确去重4,338键，减少76.4418%；计算量比4.2448，不等于实测速度比。
- 本次原B不产生逐行缓存。其余26试训自己需要4,300键；它们覆盖644个B单位权重键，正式B还需补38键。
- 正式G-raw/I-P权重未定；最多再增加454键。新执行器预计总实际反传键数4,338–4,792，原B已发生的682次反传另账。
- 每键原始FP32梯度载荷4,456,448字节；预计19.33–21.36GB，加上元数据和容器开销。新报告不重复保存每候选1.20GB原rollout composition正文，而保存其摘要、权重和可重建的冻结来源；原材料不删除。
- 全27试训、432开发、3正式和48独立确认清单保持。导入原B的16条开发后，新执行器仍需416条开发和48条确认。

当前没有端到端9B加速实测。后续报告必须分别列出实际新反传、命中、完整行应用、真实optimizer步和占卡区间，不能把复用说成再次训练，也不能把旧B成本从总成本中抹去。

## 项目检查及环境失败

按项目要求执行 `.venv/bin/python -m pytest -q`：**1756 passed、120 skipped、12 failed，601.85秒**。12个失败均为已有测试的环境问题：轻量环境没有torch/jsonschema，或默认`/tmp`余量低于旧监督器测试的20GiB保护；不修改旧数值实现或降低保护阈值。

第一次使用`.train-venv`定向复核时发现该解释器未安装pytest，未执行测试，错误保留。随后使用已有resident解释器、已有test-only JSON Schema依赖、数据盘临时目录，只复核这12个失败节点：**12 passed，17.43秒**。没有安装依赖或修改正在使用的模型环境；不声称默认轻量环境整套零失败。

最终新增执行/资格/交接控制**19 passed**，包括B完成前不发信号、PID复用拒绝、发信号前重新核对源码与资格、导入B成本分账、完整清单屏障、资源保护及缺失证据阻断。缓存模块另有6项CPU控制通过。最终项目Ruff检查通过。

## 条件接管与发布

持久接管程序从独立clean提交执行。等待期间只读原B进度，不加载第二个9B、不对原B发信号。原B成功退出、完整开发与归档后，才经pidfd对来源与进程开始标识都匹配的旧supervisor正常结束；等待旧finisher保存原报告后，将原B作为旧执行结果导入新根目录。

新资格文件同时绑定原收据SHA、所有新实现与测试的相对路径SHA，以及原正式数值profile。接管开始、发信号之前、新计划准备及每次新worker启动都核查这些条件。原失败结果或未知结果不会因“优化”改写为通过。

实现与文档提交后启动持久等待；具体提交、PID和启动时B进度记录在[运行记录](software-allocation-v037.md)。本文准备阶段没有宣称接管已经发生或新候选已经训练完成。
