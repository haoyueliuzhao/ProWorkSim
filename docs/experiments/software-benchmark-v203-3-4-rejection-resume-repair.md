# v203.3.4：恢复后的格式拒绝回调修复及原队列接续

2026年11月16日。本修订不增加现金或模型尝试，继续使用v203.3.3独立80元账本及原16条续跑安排。

## 故障及影响

首个Astropy REASSIGN分支已真实调用9次后，在001返回一次多工具调用时终止。直接异常为 `Private summary history lost its original conversation binding`。费用均已结算，最终状态为执行技术未知，不能解释为模型代码失败，也不能把它从分配条件分母中删除。

根因是检查点恢复替换了SDK Conversation，但v117格式拒绝包装函数的闭包仍保留组装时的旧Conversation对象。通常的合法工具动作可以继续，直到某个响应需要进入格式拒绝路径才触发旧引用检查。前轮续接控制验证了正常工具、摘要和交付，没有覆盖“恢复后再次发生格式拒绝”这一分支，故未发现此问题。

## 修复范围与验证

新恢复模块在原恢复过程之后，将现有格式拒绝回调中的Conversation绑定换成该成员刚恢复的真实会话，保留原函数字节码、适配器、成员、记录目录和严格拒绝逻辑。已有拒绝收据从复制后的成员目录保留，不修改原模型响应、不重新执行被拒绝动作、不补发请求、不补预算。

必要的零API回归实际恢复此前包含摘要的双人SDK检查点，提供一次多工具调用，验证：

1. 正常返回原有`model_format_feedback`，不变成环境错误。
2. 被拒绝响应只计费一次，未执行任何世界动作。
3. 同一成员后续行动机会正常执行写文件，历史和预算能够继续使用。

三个脚本响应合计843个合成usage单位；这是0真实API、0现金的机制控制，不是模型Token效率结果。第一次测试断言误用了内部`model_format_error`而非外部`model_format_feedback`名称，保留失败记录；r3包含上述完整回归并通过。

## 如何继续实验

旧REASSIGN分支完整封存，不重采。仍在运行的旧KEEP分支不停止、不热改。新队列只接收原计划中从未调用的14个身份，顺序、题目、保存点、两个条件、重复次数和剩余Token不变，部署修订单列。

旧队列因首个分支的明确错误无法通过其首对门，因此不会再派发这14个身份。新队列同时检查旧活动数量与同一账本，确保新旧合计最多两个actor。若旧KEEP占用的足额现金预约使下一槽位暂不能入场，则等待它正常结束释放预约，不能以此中断在途任务。

修复版用接下来的原定配对身份检查真实恢复与费用完整性，不用评分高低决定是否继续。原首对的结果和未知仍保留在16条安排内；本轮不能伪称16条都用了相同部署版本，正式分析必须标记修订及未知。

## 评分与资源

四道题的新官方gold均通过、empty均失败，且控制容器已清理。新评分队列复用完全相同评分代码和镜像的这批资格，不重复控制。它等待旧评分队列排空后才占用唯一评分槽；生成与评分异步，不将隐藏评分反馈给模型。

新旧交接阶段最多两个普通用户生成服务，各8CPU／64GiB上限；两个评分服务各4CPU／16GiB，其中新评分只等待。actor合计最多2个、各4CPU／16GiB；grader合计最多1个、4CPU／16GiB。服务设置的上限合计为36CPU／208GiB，实际等待服务不占其上限用量；旧服务自然结束后回落。所有容器仍network=none、drop ALL，无宿主挂载、端口或GPU。不改变共享服务器配置。
